المطالبة بلعبة أضافها شخص آخر

إذا قام شخص ما بالفعل بإضافة لعبة GitHub العامة الخاصة بك إلى StarHermit، فلن تحتاج إلى إنشاء ملف القائمة الثانية. المطالبة ببطاقة البيانات الحالية لتصبح المالك المعتمد لها وإدارة بياناتها الوصفية، الاستضافة والنشر والواجهة الخلفية للخادم وعمليات النقل المستقبلية.

المطالبة محمية عن طريق التحكم في المستودع. إن معرفة معرف اللعبة أو عنوان URL للمستودع ليس كافيًا. يجب عليك إثبات السيطرة بإحدى طريقتين:

  1. ربط حساب GitHub الشخصي الذي يملك المستودع؛ أو
  2. قم بإيداع معرف مستخدم StarHermit الخاص بك كـ owner= في المستودع starhermit.txt.

الطريقة الثانية مفيدة بشكل خاص للمستودعات المملوكة للمؤسسة، لأن الطريقة الحالية يتطابق فحص تسجيل الدخول إلى GitHub مع مالكي المستودعات الشخصية ولا يستنتج عضوية المؤسسة.

ما يدعي التغييرات

مطالبة ناجحة:

  • يحتفظ بمعرف اللعبة/القائمة الحالي وتاريخه المتراكم؛
  • تغيير مستخدم StarHermit المُدير للقائمة إليك؛
  • يضع علامة على القائمة كـ isVerifiedOwner: true;
  • يقوم بتحديث البيانات التعريفية وعناصر التحكم الموثوقة من starhermit.txt حيثما ينطبق ذلك؛
  • توفير أو تحديث الواجهة الخلفية للبرنامج النصي/الحاوية المعلن عنها؛
  • تمكين استضافة النظام الأساسي حيثما كان ذلك متاحًا وقوائم الانتظار للنشر pending;
  • يزيل حق الوصول إلى الإدارة من الشخص الذي قدم تلك القائمة في الأصل.

المطالبة لا تمنح المرسل السابق حق الوصول إلى حساب GitHub الخاص بك، ولا يتم دمجها حسابات مستخدمي StarHermit. ينقل إدارة تلك القائمة المحددة.

قبل أن تبدأ

أنت بحاجة إلى:

  • حساب StarHermit ورمز الوصول الكامل للمستخدم، وليس رمز إطلاق على نطاق اللعبة.
  • كتابة الوصول إلى المستودع في حالة استخدام owner= طريقة الإثبات.
  • معرف قائمة StarHermit الحالي.
  • بالنسبة للعبة المستودع المستنسخة، صالحة starhermit.txt في جذر المستودع.

فقط github.com/<owner>/<repo> تشارك المستودعات ومواقع صفحات GitHub الخاصة بها في هذه المطالبة تدفق. لا يحتوي عنوان URL المستضاف التعسفي على ملكية مستودع GitHub لإثبات ذلك ولا يمكن المطالبة به الطريق.

الأمثلة أدناه تستخدم:

API=https://api.starhermit.com
ACCESS_TOKEN='your-full-user-access-token'
OWNER='your-github-login'
REPO='your-game-repository'

تستمر رموز الوصول لمدة 15 دقيقة. قم بتحديث بياناتك قبل البدء إذا كانت على وشك انتهاء الصلاحية.

الخطوة 1: ابحث عن القائمة الحالية

قائمة الألعاب المشتركة:

curl -sS "$API/api/v1/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

يتضمن كل عنصر القائمة غير القابلة للتغيير id، تطبيع repoUrl, ownerLogin, repoName، ال المقدم الحالي وحالة الملكية:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "isVerifiedOwner": false,
  "submittedByUserId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "submittedByUsername": "someone-else"
}

المباراة على حد سواء ownerLogin و repoName; لا تحدد لعبة فقط لأن اسم العرض الخاص بها هو مماثل. مع jq:

GAME_ID=$(
  curl -sS "$API/api/v1/github-games" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r --arg owner "$OWNER" --arg repo "$REPO" \
    '.[] | select((.ownerLogin | ascii_downcase) == ($owner | ascii_downcase)
               and (.repoName | ascii_downcase) == ($repo | ascii_downcase)) | .id' |
  head -n1
)

printf 'Listing ID: %s\n' "$GAME_ID"

توقف إذا كانت النتيجة فارغة. لا تتصل بالمطالبة بمعرف منسوخ من قائمة غير ذات صلة.

الخطوة الثانية: اختيار كيفية إثبات الملكية

الخيار أ: ربط حساب GitHub الخاص بمالك المستودع

استخدم هذا عندما يكون المستودع مملوكًا مباشرةً لتسجيل الدخول الشخصي الخاص بك إلى GitHub.

من تدفق حساب/إعدادات StarHermit، ابدأ GitHub OAuth وصلة الوضع أثناء تسجيل الدخول حساب StarHermit الذي يجب أن يدير اللعبة. يختلف الارتباط عن إنشاء ملف عن طريق الخطأ حساب StarHermit الثاني مع تسجيل الدخول إلى GitHub.

يبدأ تدفق واجهة برمجة التطبيقات عند:

GET /api/v1/auth/oauth/github/authorize?link=true

إنه يعتمد على المستعرض ويستخدم ملف تعريف ارتباط قصير العمر. يتطلب الربط أحدث إصدار من StarHermit المصادقة. أكمل ترخيص GitHub في نفس جلسة المتصفح التي بدأته.

التحقق من النتيجة:

curl -sS "$API/api/v1/me/github" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

مُتوقع:

{ "linked": true, "login": "octocat" }

يجب أن يتطابق تسجيل الدخول الذي تم إرجاعه مع القائمة الموجودة ownerLogin، غير حساس لحالة الأحرف. شخصية لا يثبت تسجيل الدخول إلى GitHub عضوية المنظمة التي تمتلك المستودع. ل المستودع المملوك للمؤسسة، استخدم الخيار ب.

الخيار ب: إضافة owner= ل starhermit.txt

وهذا يثبت السيطرة لأن الشخص الوحيد القادر على نشر محتوى المستودع يمكنه إضافة القيمة. تعيين owner إلى معرف مستخدم StarHermit غير القابل للتغيير (UUID)، لا اسم المستخدم أو اللقب الخاص بك.

احصل على هويتك:

STARHERMIT_USER_ID=$(
  curl -sS "$API/api/v1/me" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r '.id'
)

في جذر المستودع، قم بالإنشاء أو التحديث starhermit.txt:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

استبدل صاحب المثال بـ STARHERMIT_USER_ID. لا تضع اسم المستخدم أو اللقب الخاص بك هنا؛ يمكن أن تتغير، في حين أن معرف المستخدم هو معرف الملكية الثابتة.

للحصول على لعبة موثوقة، احتفظ بإعلان خلفي واحد فقط:

# JavaScript runtime:
server=server.js

# OR container runtime, never both:
# container.image=ghcr.io/your-org/orbit-server@sha256:<64-lowercase-hex>

قم بتنفيذ البيان ودفعه إلى المستودع/الإصدار الذي يمكن لـ StarHermit قراءته:

git add starhermit.txt
git commit -m "Declare StarHermit game ownership"
git push

قبل المطالبة، افتح الملف الخام للمستودع starhermit.txt URL في متصفح لم تتم مصادقته و تأكد من أن القيمة الجديدة قابلة للقراءة بشكل عام. المطالبة بقراءة المستودع في وقت الطلب؛ ان فالتغيير المحلي غير المدفوع لا يمكن أن يثبت أي شيء.

الخطوة 3: التحقق من صحة البيان

بالنسبة للعبة المستودع المستنسخة العادية، تتطلب المطالبة ما يلي:

  • starhermit.txt في جذر المستودع؛
  • غير فارغة name=;
  • launch= مشيرا إلى قريب مستودع .html أو .htm ملف؛
  • اختياري صالح server= المسار المنتهي في .js/.mjs، أو صالحة container.image= تصريح؛
  • لا يتم تشغيل كلا الخادمين في وقت واحد.

تحتفظ قائمة صفحات GitHub بعنوان URL المستضاف الخاص بها كهدف الإطلاق ولا تتطلب بيانًا عندما يتم إثبات ملكية GitHub الشخصية، على الرغم من أنه لا يزال من الممكن تحديث اسم البيان الصالح الخاص به اسم العرض.

إذا أعلنت اللعبة عن حاوية، فيجب أن تتوافق صورتها مع السجل ومساحة اسم المالك والملخص القواعد في خوادم الألعاب المستضافة بالحاويات. يمكن أيضًا أن تكون استضافة الحاويات مقيدة من قبل مشغل المنصة.

الخطوة 4: المطالبة بالقائمة

طلب المطالبة ليس له نص:

curl -sS -X POST \
  "$API/api/v1/me/github-games/$GAME_ID/claim" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

ناجحة 200 إرجاع اللعبة المحدثة:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "launchPath": "index.html",
  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "isVerifiedOwner": true,
  "metadataSource": "starhermit.txt",
  "hosting": {
    "hostingEnabled": true,
    "deployStatus": "pending"
  }
}

يجب أن يكون المعرف هو نفسه الموجود في الخطوة 1. لا تقم بإنشاء قائمة جديدة بعد المطالبة الناجحة.

يُسمح بالمطالبة بقائمة تديرها بالفعل عمدًا. ويعيد قراءة البيان، يعيد توفير الواجهة الخلفية ويعيد الاستضافة، بحيث يمكن استخدام نفس الاستدعاء لإعادة مزامنة اللعبة التي يديرها المالك بعد تغييرات المستودع.

الخطوة 5: التحقق من الاستلام والنشر

تأكد من ظهور اللعبة الآن في قائمتك المُدارة:

curl -sS "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" |
jq --arg id "$GAME_ID" '.[] | select(.id == $id)'

التحقق من حالة النشر:

curl -sS \
  "$API/api/v1/me/github-games/$GAME_ID/deployment" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

عادة ما يتم وضع المطالبة في قائمة انتظار النشر، لذلك pending مباشرة بعد المطالبة أمر طبيعي. استطلاع مع التراجع حتى يصل إلى الحالة المباشرة/النجاح للبيئة أو يتم الكشف عنها deployError.

بعد الاستحواذ، تتضمن نقاط نهاية الإدارة المتاحة لك ما يلي:

PUT    /api/v1/me/github-games/{id}/deployment  pin a commit/branch and redeploy
POST   /api/v1/me/github-games/{id}/bundle      upload built client/container output
PUT    /api/v1/me/github-games/{id}/hosting     requeue hosting where supported
POST   /api/v1/me/github-games/{id}/transfer    transfer management deliberately
DELETE /api/v1/me/github-games/{id}             remove the game

لم يعد المرسل الأصلي يرى هذه القائمة ضمنها GET /api/v1/me/github-games ولا يمكن استخدم نقاط نهاية الإدارة الخاصة بالمالك لذلك.

استكشاف الأخطاء وإصلاحها

403: ربط مالك المستودع أو إضافته owner=

معلومات تسجيل الدخول المرتبطة إلى GitHub غير متطابقة ownerLogin، أو البيان owner لا يتطابق تماما معرف مستخدم StarHermit الخاص بك.

  • يفحص GET /api/v1/me/github.
  • تحقق من الدقيق ownerLogin تم إرجاعها من خلال القائمة العامة.
  • بالنسبة لمستودعات المؤسسة، استخدم owner=<your StarHermit user ID> في الريبو.
  • تأكد من أنك دفعت البيان وأن عنوان URL الأولي الخاص به قابل للقراءة بشكل عام.

404: لا توجد لعبة مشتركة بهذا المعرف

المعرف خاطئ، أو تمت إزالة القائمة. كرر الخطوة 1. لا يمكن المطالبة بالقوائم المحذوفة.

400: مفقود أو غير صالح starhermit.txt

بالنسبة للمستودع المستنسخ، تأكد من صلاحية بيان الجذر name و HTML launch قيم. ايضا التحقق من صحة إعلانات البرنامج النصي/الحاوية الاختيارية. المطالبة لا تثق في بيانات التعريف في الأصل دخلها غير المالك؛ فهو يستبدلها ببيانات التعريف التي يتحكم فيها المستودع.

فشل المطالبة حول سبيكة/الواجهة الخلفية

قد يكون البرنامج النصي غير صالح أو قد تكون استضافة الحاوية غير متوفرة. تحقق من الخطأ الذي تم إرجاعه و إعلان الواجهة الخلفية، ثم استدعاء المطالبة مرة أخرى. تقوم المنصة بتعيين UUID الخاص باللعبة باعتباره سبيكة لها. لا يوجد سبيكة واضحة للاختيار أو الحل.

تم ربط GitHub ولكن حساب StarHermit الخاطئ يمتلك الرابط

قم بتسجيل الدخول إلى حساب StarHermit المقصود وأكمل OAuth وصلة تتدفق هناك. لا تدعي من حساب StarHermit ثاني مؤقت ومن ثم الاعتماد على دمج الحسابات؛ لعبة نقل API الإدارة، وليس هويات المستخدم.

ملاحظات أمنية

  • لا تقبل أبدًا رابط المطالبة أو معرف القائمة كدليل على ملكية المستودع.
  • لا تضع رموز الوصول إلى GitHub أو بيانات اعتماد الحاوية أو الأسرار الأخرى starhermit.txt.
  • استخدم دائمًا معرف مستخدم StarHermit غير القابل للتغيير في owner=; لا تستخدم اسم مستخدم أو لقب.
  • قم بمراجعة عنوان URL الحالي للقائمة والمستودع قبل المطالبة؛ أسماء العرض ليست فريدة من نوعها.
  • إذا قمت بنقل اللعبة لاحقًا، يصبح المستلم هو المدير ولكن حالة المالك المعتمد هي كذلك إعادة تعيين. ويجب عليهم تشغيل تدفق المطالبة بأنفسهم إذا كانوا يتحكمون في المستودع.
