Kontrak REST dan WebSocket

Kontrak yang dapat diunduh ini melengkapi halaman referensi. Gunakan mereka untuk memeriksa operasi, memvalidasi contoh payload, atau mengimpor permintaan REST ke klien yang kompatibel dengan OpenAPI.

Mengajukan Cakupan
Kontrak OpenAPI REST Metode REST publik, jalur, parameter, model permintaan JSON, respons sukses, dan kelompok kredensial; operasi pembangkitan yang dicadangkan ditandai tidak tersedia
Skema JSON WebSocket Bingkai teks yang diketahui berdasarkan protokol dan arah; Data gameplay/sinyal milik aplikasi tetap terbuka
Tata letak biner Awalan pengirim waktu nyata, awalan suara, relai tanpa bingkai, header aliran kontainer, dan potongan unggahan

kontrak SISA

File REST menggunakan OpenAPI 3.0.3 dan asal API publik. Setiap operasi tertaut ke halaman referensinya, yang membawa aturan otorisasi, validasi, batasan, dan kesalahan yang lengkap. x-credentials mengidentifikasi keluarga kredensial yang diterima; itu tidak menggantikan pemeriksaan kepemilikan atau keanggotaan. x-required-policies menjelaskan izin bernama tempat API menerapkannya.

Tanggapan mungkin mencakup bidang tambahan. JSON, metadata, diagnostik, dan unggahan khusus game hasilnya menggunakan bentuk terbuka di mana referensi permainan atau titik akhir menentukan isinya. Sukses skema bukanlah janji bahwa setiap penelepon diberi wewenang. Kesalahan titik akhir dapat berupa JSON, teks biasa, tanggapan kosong, atau Detail Masalah validasi; menggunakan penguraian respons defensif.

Jangan perlakukan operasi pembangkitan cadangan sebagai layanan yang berfungsi. Kontrak mereka menjelaskan saat ini 503 overloaded respons, bukan bidang permintaan atau perilaku pembuatan di masa mendatang.

Kontrak WebSocket

Pilih A $defs skema untuk protokol dan arah soket Anda. Misalnya, memvalidasi klien bingkai gerakan melawan GameRealtimeInput, bukan yang generik tahan lama GameCommand:

{ "type": "cmd", "data": { "type": "input", "realtime": true, "seq": 1, "x": 0.5 } }

realtime milik di dalam data. Bidang gameplay setelahnya adalah kontrak game Anda. Gunakan a Skema JSON 2020-12 validator dengan dokumen skema lengkap sehingga referensi lokal dapat diselesaikan. Dokumen root berisi definisi; memilih definisi diperlukan untuk memvalidasi bingkai.

Jenis bingkai di masa depan harus menjangkau pengendali bingkai yang tidak diketahui klien Anda daripada membuat penerimaannya terhenti lingkaran. Validasi bentuk JSON tidak memvalidasi aturan permainan, mengotorisasi keanggotaan, atau menerapkan tarif batas. Halaman referensi menentukan batasan peran dan ukuran/tarif.

Urutan byte GUID

Tiga grup UUID pertama adalah little-endian dalam header byte .NET GUID. Misalnya:

UUID:  00112233-4455-6677-8899-aabbccddeeff
Bytes: 33 22 11 00 55 44 77 66 88 99 aa bb cc dd ee ff

Decoder browser untuk awalan 16-byte:

function guidFromDotNet(bytes) {
  if (bytes.length !== 16) throw new Error('Expected a 16-byte GUID');
  const hex = i => bytes[i].toString(16).padStart(2, '0');
  return `${hex(3)}${hex(2)}${hex(1)}${hex(0)}-${hex(5)}${hex(4)}-${hex(7)}${hex(6)}-` +
    `${hex(8)}${hex(9)}-${hex(10)}${hex(11)}${hex(12)}${hex(13)}${hex(14)}${hex(15)}`;
}

Identifikasi awalan waktu nyata peserta, sementara awalan suara mengidentifikasi pengguna. Sebuah wadah aliran memiliki tipe satu byte diikuti oleh UUID sesi/pengguna, sehingga JSON-nya dimulai pada byte 33. Itu relay tidak menambahkan awalan. Membaca setiap soket dengan tata letak biner yang sama akan merusak muatan dan identitas.

Melihat kredensial dan pengidentifikasi, siklus hidup sesi, Dan Pemecahan masalah WebSocket.
