Server Game yang dihosting oleh kontainer

Game StarHermit dapat mengirimkan logika server otoritatifnya sebagai gambar kontainer, bukan a file JavaScript kotak pasir. Ini memungkinkan server menggunakan Rust, Go, C++, atau runtime lain yang bisa melayani HTTP dan WebSockets. Menghadapi browser API Permainan tetap sama: klien masih menggunakan token peluncuran cakupan game, sesi REST, dan ws/v1/games bingkai JSON.

Hosting kontainer terbuka untuk semua pengguna yang masuk di starhermit.com. Penerapan yang dihosting sendiri bisa membatasinya pada daftar yang diizinkan oleh operator; daftar izin yang tidak ditetapkan di sana tidak menerima siapa pun selain semua orang. Hal ini berlaku sama untuk gambar registri dan gambar yang diunggah server/image.tar, jadi tidak ada rute yang ada diam-diam lebih permisif dari yang lain.

Setelah pendaftaran game awal, pengembang juga dapat meluncurkan game bawaan .tar.gz mengandung server/image.tar (docker save keluaran) melalui POST /api/v1/me/github-games/{id}/bundle. Platform memuat dan mencerna pin gambar dan antrean penerapan ulang. Melihat GitHub Games — Mendorong bundel game dan itu tutorial server khusus.

Detail tentang push ini perlu diketahui sebelum Anda membuat pipeline rilis di sekitarnya:

  • Besar docker save dapat melebihi batas isi permintaan CDN ~100 MB, yang dijawab dengan a 413 platform tidak pernah melihat — tidak limitBytes, tidak ada apa pun di log mana pun yang dapat Anda baca. Dorong arsipnya ws/v1/game-upload alih-alih; arsip yang sama, sama tunjangan, jawaban yang sama.
  • Gambar yang Anda unggah adalah deklarasi itu sendiri. Sebuah game yang belum memiliki backend — satu ditambahkan dari folder yang diunggah yang menyatakan tidak ada — mendapatkan definisi wadahnya yang disediakan dari intisari baru saja dimuat. Anda tidak memerlukan a container.image= dalam manifes terlebih dahulu.
  • Pendorongan ulang akan menerapkan kenop yang dinyatakan dalam manifesnya dan mempertahankan kenop yang dihilangkan. Berubah container.port dan mengunggah ulang sekarang memindahkan penerapan ke port tersebut; meninggalkan manifesnya bundel tidak mengubah apa pun kecuali gambar.
  • Gambar yang diunggah menang atas manifes, termasuk lebih dari a server= garis, dan manifes mendeklarasikan keduanya server= Dan container.image= ditolak sebelum apa pun dimuat.
  • Tag gambar lokal Anda tidak memilih versi yang diterapkan. Gambar yang diunggah disematkan olehnya intisari konten. Anda dapat menandainya secara lokal sesuka Anda; verifikasi intisari dan penerapan yang diunggah status setelah publikasi.
  • ?mode=merge hanya menambal file klien. A server/image.tar dalam gabungan dimuat persis seperti saat diganti — gambar tidak dapat diperbarui setengahnya. Melihat pembaruan parsial.

Tampak

Deklarasikan gambar di repositori starhermit.txt:

name=Void Marshals
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html

container.image=ghcr.io/octocat/vm-server@sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
container.port=8080
container.health=/health
container.memory_mb=1024
container.cpu=1.0
container.env.LOG_LEVEL=info

Hanya container.image diperlukan. Port dan jalur kesehatan defaultnya adalah 8080 Dan /health. Memori dan CPU adalah permintaan, bukan jaminan; platform menjepitnya hingga batas operator.

Gambar Anda memiliki batas ukuran: 2 GiB tidak terkompresi kecuali operator telah menyetel game Anda yang lain, dan penarikan registri memiliki waktu lima menit. Tarikan yang melampaui langit-langit ditinggalkan di tengah jalan, dan diunggah image.tar atasnya ditolak dengan 413, dan gambar yang menjadi lebih besar setelah tidak dikompresi adalah dihapus lagi. container.env.* hanya untuk konfigurasi non-rahasia.

Pengajuan ditolak kecuali:

  • Gambar tersebut disematkan sebagai intisari name@sha256:<64 lowercase hex>. Tag yang dapat diubah tidak diterima.
  • Registri ini diizinkan dan gambar berada di bawah namespace pemilik repositori terverifikasi; saat ini artinya ghcr.io/<github-owner>/....
  • Manifes mendeklarasikan tepat satu waktu proses server. server= Dan container.image= saling eksklusif.
  • Nama lingkungan valid dan tidak dimulai dengan nama yang dicadangkan STARHERMIT_ awalan.

Jangan pernah memasukkan kredensial starhermit.txt; itu adalah file repositori publik.

Protokol v1

Kontainer menyajikan HTTP/1.1 aktif container.port. Setiap permintaan HTTP platform dan peningkatan WebSocket disertakan X-Starhermit-Invoke-Key, yang nilainya cocok dengan yang disuntikkan STARHERMIT_INVOKE_KEY; menolak permintaan jika tidak ada atau salah.

Titik akhir Tujuan
GET <container.health> Kembali 200 ketika server sudah siap
GET /describe Deklarasikan versi protokol, tick rate, kapasitas, dan pencapaian
POST /sessions Mulai sesi, atau pulihkan kapan snapshot hadir
GET /sessions/{sessionId}/snapshot Kembalikan kondisi tahan lama saat ini
DELETE /sessions/{sessionId} Hancurkan sebuah sesi
POST /sessions/{sessionId}/members Opsional: seorang pemain bergabung atau meninggalkan sesi lari
WS /control Saluran kontrol keluar seluruh penerapan
WS /stream Bingkai gameplay di kedua arah

Satu wadah menampung semua sesi langsung untuk satu pertandingan. Jaga agar status sesi tetap dikunci sessionId dan lakukan tidak berasumsi proses tersebut akan bertahan seumur hidup.

GET /describe

{
  "protocol": 1,
  "tickRateHz": 20,
  "maxSessions": 48,
  "replays": true,
  "persistent": false,
  "achievements": [
    { "key": "first-blood", "name": "First Blood", "description": "Score first.", "points": 10 }
  ]
}

protocol harus 1. tickRateHz Dan maxSessions adalah permintaan dan dapat dijepit. Platformnya tidak pernah melangkahi lingkaran wadah, jadi tickRateHz memberitahukannya seberapa cepat permainan Anda bergerak daripada bagaimana cepat untuk menjalankannya: inilah yang menghentikan platform meminta snapshot lebih cepat daripada yang dihasilkan game Anda negara bagian baru. Nyatakan laju sebenarnya putaran Anda berjalan. Tarif pecahan diterima (0.5 adalah satu centang setiap dua detik), dan kecepatan yang lambat akan memperpanjang interval antara permintaan snapshot — itulah berapa biaya permainan crash. Sebuah wadah yang menyatakan tidak ada yang meninggalkan pos pemeriksaan irama untuk biaya snapshot saja. Entri pencapaian menggunakan bidang dan batasan yang sama seperti pencapaian yang dinyatakan dalam naskah. Kunci yang dideklarasikan dan dibuat oleh pemilik nantinya dapat diberikan.

replays meminta platform untuk menjaga status terakhir setiap sesi yang selesai sebagai a memutar ulang, dilayani oleh GET /api/v1/games/{slug}/replays/{sessionId} (melihat API Game — Pemutaran ulang). Itu harus menjadi literal true atau false; permainan yang menyatakan tidak ada pemutaran ulang, dan titik akhir pemutaran ulangnya jawaban 404. Seperti halnya tick rate, ini adalah permintaan — operator dapat menjawab untuk permainan tertentu apa pun pilihannya — jadi cabangkan klien Anda replaysEnabled dari GET /api/v1/games/{slug} daripada aktif apa yang kamu nyatakan. Snapshot tidak terpengaruh: sesi langsung memerlukan titik pemulihan atau tidak, yang terakhir disimpan.

persistent (harfiah true/false) meminta sesi itu jeda alih-alih mengakhiri kapan setiap pemain telah pergi. Jeda menghentikan sesi: platform mengambil cuplikan terakhir, menyimpannya, dan panggilan DELETE /sessions/{id}; pemain berikutnya yang bergabung akan membawanya kembali POST /sessions dengan itu snapshot, persis seperti pemulihan kerusakan tetapi tanpa menghabiskan anggaran restart atau pengiriman resumed. Sesi persisten yang dipulihkan juga berlaku pausedMs, total waktu yang dihabiskan dijeda. Lihat tutorial sesi persisten.

linkedAchievements (rangkaian hingga 8 siput game lainnya) menempatkan pembukaan kunci pemain di dalamnya game ke dalam ctx POST /sessions, saat membuat dan memulihkan. Melihat Prestasi dari game lain.

Saat ini /describe pembaca tidak mengimpor a queues milik. Oleh karena itu, permainan kontainer digunakan yang implisit default Antrean perjodohan 1v1; menambahkan bentuk di sini tidak memungkinkan kecocokan yang lebih besar. Memeriksa GET /api/v1/games/{slug}/queues untuk bentuk yang efektif. Batas waktu nyata dimulai dan kursi AI batasan masih berlaku dalam bentuk itu; melihat penjaruman.

POST /sessions

Permintaannya memiliki bentuk konteks yang sama dengan yang diterima game JavaScript:

{
  "now": 1769500000000,
  "random": 0.418,
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "players": [
    { "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "name": "alice" }
  ],
  "sessionState": null,
  "playerStates": {
    "7c9e6679-7425-40de-944b-e07fc1f90ae7": null
  }
}

Semantik lapangan cocok dengan konteks naskah, termasuk kursi perjodohan, bendera AI, dan kursi kosong untuk permainan yang mengonfigurasi tenggat waktu mulai starhermit.txt. Tanggapi dengan amplop hasil standar, misalnya:

{ "ok": true, "sessionState": { "round": 1 } }

Tentang pemulihan, permintaan itu juga berisi snapshot, memegang keadaan terakhir yang dipertahankan oleh platform, dan restoredFrom, stempel waktu Unix-milidetik. Rekonstruksi sesi yang dapat diputar dari snapshot. Permainan persisten dipulihkan dengan cara yang sama ketika pemain bergabung kembali dengan sesi yang dijeda, dengan pausedMs di dalam tubuh.

GET /sessions/{sessionId}/snapshot

Kembalikan amplop standar dengan lengkap sessionState titik pemulihan:

{ "ok": true, "sessionState": { "round": 3, "scores": [2, 1] } }

Platform memeriksa sesi aktif secara berkala. Respons snapshot mungkin juga mencakup playerStates, eloUpdates, achievements, scores, atau result; mereka melewati validasi yang sama dan aturan persistensi sebagai hasil skrip. Untuk permainan dengan memutar ulang, keadaan terakhir a sesi selesai yang dicapai adalah apa yang disimpan platform sebagai pemutaran ulangnya — jadi buatlah keadaan itu dapat direkonstruksi, tidak hanya dapat dilanjutkan.

POST /sessions/{sessionId}/members

Opsional. Pemain bisa bergabung dengan sesi yang sedang berlangsung, melalui a ruang waktu nyata itu memungkinkan itu atau dengan menerima milik teman undang ke sesi yang mereka mainkan, dan ruangan memungkinkan pemain menyerahkan kursinya tanpa AI mengambilnya. Platform menanyakan wadah Anda sebelum perubahan bersifat final. Bodinya ctx biasa, dengan players sudah mencerminkan perubahan, ditambah membership:

{
  "now": 1769500000000,
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "players": [
    { "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "name": "alice" },
    { "id": "9b2f8c1a-1111-4222-8333-444455556666", "name": "carol" }
  ],
  "membership": { "change": "joined", "userId": "9b2f8c1a-1111-4222-8333-444455556666", "name": "carol", "team": 0, "slot": 1 }
}

change adalah joined atau left. Jawab dengan amplop standar:

  • Bergabung dapat ditolak. {"ok": false, "error": "This world is full."} memalingkan pemain, itu kursi dikembalikan dan tidak ada yang dicatat; undangan menerima jawaban 409 dan undangannya tetap ada tertunda. Jika Anda tidak menerapkan titik akhir, setiap penggabungan akan ditolak: 404, 405 Dan 501 berarti "game ini tidak mengambil pemain ditengah pertandingan", jadi game yang ditulis untuk daftar tetap tidak pernah memiliki orang asing terjatuh ke dalamnya.
  • Cuti sudah final apapun jawabanmu.
  • Jawabannya mungkin ada achievements Dan scores. A sessionState diabaikan: kirim a snapshot lebih /control jika perubahan itu layak untuk dijadikan pos pemeriksaan.

Setelah bergabung, perintah pemain baru mulai berdatangan /stream dan mereka masuk players pada setiap nanti pulihkan. Setelah keluar, rangkanya berhenti dan soketnya ditutup. Setiap klien yang terhubung menerima a membership bingkai bagaimanapun juga, dan sesi obrolan untung atau rugi anggota.

A menjeda sesi persisten tidak ditanyakan, karena tidak berjalan. Pemulihan itu melanjutkan itu membawa arus players, jadi perlakukan pemain yang belum pernah Anda lihat sebelumnya dalam pemulihan sebagai bergabung.

Aliran gameplay

WS /stream menggunakan pesan biner di kedua arah:

[1 byte type][16 byte sessionId][16 byte userId][payload...]

GUID menggunakan representasi kabel .NET 16-byte.

  • Tipe 1, platform → wadah: perintah pemain. Platform mencap id pengguna yang diautentikasi; payload adalah nilai JSON dari klien cmd.data.
  • Tipe 2, wadah → platform: muatan permainan. Alamat satu peserta dengan id pengguna mereka, atau gunakan id pengguna yang semuanya nol untuk disiarkan. Payloadnya harus berupa JSON yang valid; klien menerimanya di dalam {"type":"game","data":...}.

Sesi disematkan ke koneksi streaming untuk menjaga ketertiban. Jangan pernah menerima atau menurunkan pemain identitas dari perintah JSON—header yang diautentikasi bersifat otoritatif.

Saluran kontrol

Kirim pesan teks JSON aktif WS /control untuk efek tahan lama:

{ "type": "snapshot",     "sessionId": "...", "state": { "round": 3 } }
{ "type": "achievements", "sessionId": "...", "unlocks": { "<userId>": ["first-blood"] } }
{ "type": "elo",          "sessionId": "...", "updates": { "<userId>": 1312 } }   // absolute ratings, not deltas — see games.md#elo-per-match
{ "type": "scores",       "sessionId": "...", "scores": { "<boardKey>": { "<userId>": 4200 } } }
{ "type": "result",       "sessionId": "...", "result": { "kind": "win", "winner": "..." } }
{ "type": "backpressure", "load": 0.75 }

Platform menerima efek hanya untuk sesi yang diarahkan ke penerapan ini, memfilter penerimanya peserta sesi, membatasi kunci pencapaian pencapaian game (dideklarasikan, atau dibuat oleh pemiliknya), batas scores ke permainan itu sendiri papan peringkat yang dibuat pemilik — setiap pemain menyimpannya terbaik — dan menerapkan anggaran negara. result mengakhiri sesi; efek selanjutnya untuk sesi itu diabaikan. backpressure.load adalah dijepit ke 0..1 dan membantu akun platform untuk beban penerapan saat ini.

Dorong cuplikan setelah peristiwa penting secara semantik, seperti transisi sasaran atau putaran daripada hanya mengandalkan pos pemeriksaan berkala.

Lingkungan kontainer dan API server

Variabel Arti
STARHERMIT_PROTOCOL Versi protokol (1)
STARHERMIT_GAME_SLUG Siput game ini
STARHERMIT_INVOKE_KEY Rahasia diharapkan masuk X-Starhermit-Invoke-Key; mengautentikasi platform ke penampung Anda
STARHERMIT_REFRESH_KEY Rahasia terpisah hanya digunakan untuk memperbarui token server
STARHERMIT_API_BASE URL dasar API platform dapat dijangkau dari jaringan terisolasi
STARHERMIT_SERVER_TOKEN Token pembawa yang kedaluwarsa untuk API server-ke-server yang sempit
STARHERMIT_SERVER_TOKEN_EXPIRES_IN Masa pakai token server yang disuntikkan, dalam hitungan detik
PORT Port tempat container harus mendengarkan

Token server tidak memiliki identitas pemain dan tidak dapat menggunakan tindakan akun atau pemain. Itu bisa membaca GET /api/v1/time, rekonsiliasi sesinya sendiri, dan hubungi server yang didukung rute moderasi untuk permainannya sendiri. Rute generasi adalah dipesan dan tidak tersedia.

Perbarui token server

Token server yang disuntikkan akan kedaluwarsa (24 jam secara default). Segarkan dengan baik sebelumnya STARHERMIT_SERVER_TOKEN_EXPIRES_IN berlalu:

POST /api/v1/games/{slug}/server/token
X-Starhermit-Refresh-Key: <STARHERMIT_REFRESH_KEY>

{ "token": "eyJhbGciOi...", "expiresInSeconds": 86400 }

Titik akhir ini sengaja dipanggil tanpa token pembawa yang sudah habis masa berlakunya. Kunci penyegaran khusus dibandingkan dengan penerapan langsung dan berfungsi bahkan setelah token lama kedaluwarsa. Hal ini berbeda dari STARHERMIT_INVOKE_KEY: kunci pemanggilan mengautentikasi panggilan platform ke proses Anda, sedangkan kunci penyegaran mengautentikasi proses Anda ke platform. Keduanya berputar setiap kali wadah dimulai. Jadwalkan pembaruan kira-kira setengah dari masa pakai yang dilaporkan dan ganti token secara atom.

"Kapan pun wadah dimulai" mencakup lebih dari sekedar penerapan. Penerapan yang menganggur dihentikan setelah a mantra tenang tanpa sesi (15 menit secara default) dan dimulai lagi oleh pemain berikutnya. Kontainer yang rusak adalah dimulai ulang. Setiap awal adalah wadah baru dengan kunci baru dan token baru, jadi bacalah ketiganya dari lingkungan proses yang sedang berjalan. Jangan pernah memasukkannya ke dalam gambar, file konfigurasi, atau snapshot.

Jika permulaan gagal dengan The game container returned 401 for GET /describe, kunci platform dan kunci proses Anda tidak setuju. Membaca STARHERMIT_INVOKE_KEY saat startup dan bandingkan tanpa dimodifikasi. Jika validasi masih gagal, laporkan id game dan log startup yang sudah dibersihkan; jangan melonggarkan ceknya.

Rekonsiliasi suatu sesi

GET /api/v1/games/{slug}/server/sessions/{sessionId} dengan Authorization: Bearer <STARHERMIT_SERVER_TOKEN> mengembalikan tampilan sesi platform saat ini:

{
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "status": "active",
  "players": [
    { "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "username": "alice" }
  ],
  "createdAt": "2026-07-27T16:00:00Z",
  "finishedAt": null,
  "chatConversationId": "d290f1ee-6c54-4b01-90e6-d701748f0851",
  "result": null
}

Gunakan ini setelah restorasi ketika penampung perlu mengonfirmasi apakah platform masih mempertimbangkan sesi aktif. Token untuk game lain, atau token peluncuran pemain, dilarang.

Isolasi

Wadah permainan tidak memiliki akses internet. Itu hanya dapat menjangkau API StarHermit melalui STARHERMIT_API_BASE; itu tidak dapat menjangkau game lain, layanan platform, atau host. Penjual semuanya ketergantungan runtime ke dalam gambar.

Sistem file root bersifat read-only, kecuali yang kecil /tmp; prosesnya berjalan sebagai non-root yang dipaksakan pengguna tanpa kemampuan Linux, tanpa volume, dan CPU, memori, dan batasan proses. Jangan instal paket saat startup atau tetap cocok dengan status hanya ke disk lokal.

Kegagalan dan pemulihan

Jika proses terhenti, platform akan memulai ulang penerapan dan membuat ulang sesi langsung dari proses tersebut cuplikan terakhir. Pemain yang terhubung menerima bingkai platform:

{ "type": "resumed", "sessionId": "...", "lostMs": 750 }

Klien harus membuang prediksi lokal dan menunggu muatan keadaan penuh normal dari game tersebut. Sebuah sesi ditinggalkan alih-alih dipulihkan ketika tidak ada snapshot yang dapat digunakan, terlalu lama, atau sesi sudah habis terlalu sering dimulai ulang. Platform menyelesaikannya tanpa pemenang atau perubahan elo dan mengirimkan:

{ "type": "abandoned", "sessionId": "...", "reason": "server_failure" }

reason adalah server_failure ketika pemulihan tidak aman atau penggantian tidak pernah dimulai, dan restore_failed ketika membuat ulang sesi gagal. Menerbitkan gambar baru akan memulihkan sesi langsung menjadi penggantinya (atau meninggalkan yang terlalu basi). Permulaan yang gagal - waktu penarikan habis, itu kontainer keluar, atau tidak pernah menjawab waktu pemeriksaan kesehatannya — dicoba ulang dengan backoff, seperti a kecelakaan. Tiga upaya gagal dalam waktu sepuluh menit (dapat disesuaikan oleh operator) menonaktifkan penerapan (failed), dan itu benar bukan dibangunkan oleh permintaan pemain. Gangguan hosting sementara dapat dicoba ulang tanpa menghabiskan tunjangan kegagalan game.

Penerapan tanpa sesi langsung dihentikan setelah 15 menit tidak aktif (operator dapat mengatur permainan Anda di jendela yang berbeda). Dijeda gigih sesi diparkir di luar wadah dan tidak dilanjutkan. Permintaan sesi berikutnya terhadap a stopped penerapan membangunkannya (pending → gerbang kesehatan → running); kalah dalam perlombaan itu 503 mengatakan permainan dimulai. Hanya stopped terbangun ini cara - tidak pernah failed.

Desain POST /sessions restorasi dan irama snapshot sebagai bagian dari protokol permainan, bukan sebagai pengoptimalan opsional.

Pemilik game dapat membuat daftar dan mengakhiri sesi terdampar: GET/DELETE /api/v1/me/github-games/{id}/sessions[/{sessionId}].

Output server Anda dan laporan kerusakan

Sebagai pemilik game, Anda dapat membaca apa yang dicetak server Anda, dan apa yang terjadi ketika server down:

Metode Jalur Keterangan
MENDAPATKAN /api/v1/me/github-games/{id}/container/logs?tail=N Keluaran terbaru: { source, deploymentStatus, capturedAt, truncated, logs }
MENDAPATKAN /api/v1/me/github-games/{id}/container/crashes?page=&pageSize= Catatan kerusakan, yang terbaru terlebih dahulu
MENDAPATKAN /api/v1/me/github-games/{id}/container/crashes/{crashId} Satu catatan kerusakan, dengan keluaran yang diambil
  • Log ditayangkan langsung dari server yang sedang berjalan (source: "live"), yang terbaru disimpan, hingga 500 baris dan 256 KiB secara default. Ketika tidak ada yang berjalan, Anda mendapatkan output yang ditangkap pada crash terakhir (source: "last_crash"). Game yang backendnya berupa skrip, atau tidak memiliki skrip apa pun, akan mendapatkannya 409.
  • Rekor kecelakaan ditulis setiap kali server Anda mogok, berhenti menjawab, waktu habis memulai atau gagal memulai — sebelum penampung dihapus. Itu membawa jenis, kode keluar, intisari gambar, jumlah restart, sesi yang terpengaruh, dan output 64 KiB terakhir server Anda. Itu 50 yang terbaru disimpan, selama 30 hari.
  • Rahasia disunting. Kunci pemanggilan server Anda, kunci penyegaran, dan token server apa pun muncul sebagai [redacted]. Milikmu sendiri container.env.* nilai muncul seperti yang dicetak — jangan mencatat apa yang tidak Anda inginkan ingin disimpan.

Operator dapat mengubah setiap batasan tersebut, per game.
