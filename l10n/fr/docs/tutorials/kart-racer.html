Tutoriel : construire un pilote de kart multijoueur

Ce didacticiel crée la couche multijoueur d'un jeu de course de karting d'arcade : jusqu'à huit karts, privés des lobbys avec des amis, des rencontres rapides avec des inconnus, des pilotes de processeur remplissant les emplacements vides de la grille, un compte à rebours, tours, un ordre d'arrivée et des réalisations — sur l'API StarHermit. Il couvre le contrat netcode et la plateforme appelle ; votre moteur, votre dessin de piste et votre modèle de conduite sont les vôtres.

Tout ce qui est spécifique au jeu ici - le grand-prix la file d'attente, la disposition du cadre binaire, le bouton d'élément, les constantes physiques - est un exemple de valeur. Seuls les points finaux, les enveloppes de trame et les limites sont comportement de la plateforme, et chacun renvoie à sa page de référence.

1. Choisissez une architecture

Un coureur est la forme de jeu la plus difficile pour un budget de serveur : les karts se déplacent vite, entrent en collision et les joueurs ressentent 50 ms de décalage de direction. StarHermit vous propose deux façons de l'exécuter, toutes deux à partir d'un salle en temps réel:

A. Routé par l'hôte B. Script faisant autorité sur le serveur
Qui simule Le client de l'hôte de la salle, en tout cas il aime (60 Hz+) Ton server= script, tout au plus 30 Hz
Transport Images binaires activées ws/v1/realtime JSON cmd/game cadres sur ws/v1/games
Tricherie L'hôte est digne de confiance Les clients n'ont aucune autorité
Elo, réalisations du scénario Non (l'hôte publie un résultat serré) Oui - eloUpdates, achievements, rediffusions
Idéal pour Courses décontractées entre amis, physique en toute fidélité Courses classées avec une physique d'arcade simple

Commencez par A sauf si vous avez besoin d'un jeu classé ; la section 7 montre ce qui change pour B. A serveur de conteneur peut également piloter un huit-kart lié à la pièce course et simuler à 60 Hz avec autorité. Sa mise en relation directe avec l'API de jeux utilise actuellement un 1v1 implicite file d'attente, utilisez donc une salle en temps réel pour la plus grande grille. La plateforme ne suit pas la boucle du conteneur.

2. Manifester

Publiez le dossier de build distribuable avec ceci starhermit.txt à sa racine (voir le manifeste). Le control.* les lignes donnent aux joueurs une interface utilisateur de rereliure et votre client un API de contrôle pour lire les liaisons à partir de :

name=Turbo Hermits
launch=index.html
cover=art/cover.png
control.accelerate=KeyW+ArrowUp | Accelerate
control.brake=KeyS+ArrowDown | Brake / reverse
control.left=KeyA+ArrowLeft | Steer left
control.right=KeyD+ArrowRight | Steer right
control.drift=ShiftLeft+ShiftRight | Drift
control.item=Space | Use item

Le chemin A a Non server= doubler. Si un jeu contient un script, le démarrage d'une salle crée une session liée et seul le script peut mettre fin au match — celui de l'hôte POST .../result ça cesse d'être la façon dont les courses se terminent (article 7).

3. Connectez-vous et lisez les bases

Un jeu hébergé sur une plateforme s'ouvre avec #game_token=<jwt> dans l'URL - lisez-le une fois, supprimez-le avec history.replaceState, et actualisez-le avant son expiration de 60 minutes (détails dans le procédure pas à pas d'échecs et authentification). Votre limace est celle du jeton game_scope réclamation (ou location.hostname's première étiquette); ne le codez jamais en dur.

Au chargement, récupérez ce dont le menu a besoin :

GET /api/v1/games/{slug}/controls     # effective key bindings (manifest defaults + overrides)
GET /api/v1/games/{slug}/settings     # camera, volume, last chosen kart — your own keys
GET /api/v1/realtime/rooms/mine       # 200 → the player is still in a race; rejoin it

Enregistrez les choix de menu avec PATCH /api/v1/games/{slug}/settings ({"settings":{"kart":"hermit-crab"}}). Les paramètres suivent le joueur sur toutes les machines et ne nécessitent aucune déclaration.

4. Le hall

Un grand prix est gratuit, la salle dispose donc d'une équipe de huit places. Piste, nombre de tours et moteur les cours vont dans l'opaque metadata:

POST /api/v1/realtime/rooms
Authorization: Bearer <launch token>

{ "teamCount": 1, "seatsPerTeam": 8, "backfillAfterSeconds": 45,
  "aiPlayers": 0, "name": "Friday cup", "isVisible": true,
  "metadata": { "track": "coral-loop", "laps": 3, "cc": 150 } }

Avec un jeton de lancement, le jeu de la salle vient du jeton, donc gameSlug peut être omis. Le créateur est l'hôte au siège (0, 0). À partir de là, le hall est un flux de pièce ordinaire :

  • Amis — POST /rooms/{id}/invites avec {"toUserId": ...}. La plateforme les informe ; en acceptant de les asseoir. Afficher les six caractères joinCode pour que les amis puissent aussi le saisir POST /rooms/join-by-code.
  • Des étrangers — l'hôte appelle POST /rooms/{id}/open. Joueurs sans appel de chambre POST /rooms/quick-join avec {"seats": 1} et, sur 404, créez et ouvrez le leur.
  • Suivre le vote/le changement d'avis de l'hôte — PATCH /rooms/{id} avec du nouveau metadata et la chambre revision comme expectedRevision.
  • Solo contre les processeurs — créer avec "aiPlayers": 7, alors POST /rooms/{id}/start.

Une salle ouverte démarre d'elle-même lorsque les huit sièges sont remplis ou backfillAfterSeconds passe; l'hôte peut aussi POST /rooms/{id}/start. Chaque siège encore vide devient un participant IA – ce sont vos Pilotes de processeur.

5. Le socket de course (routé par l'hôte)

Connecter

Chaque participant ouvre la socket temps réel avec un ticket à usage unique :

const { ticket } = await api.post("/api/v1/realtime/connection-tickets"); // { ticket, expiresIn }
const ws = new WebSocket(
  `wss://api.starhermit.com/ws/v1/realtime?roomId=${roomId}&ticket=${encodeURIComponent(ticket)}`);
ws.binaryType = "arraybuffer";

Les cadres de texte sont des push JSON et des cadres de contrôle ; les images binaires sont un gameplay. Le roster pousser est votre grille : après le démarrage elle est figée, sièges IA inclus. Avec une équipe, l'emplacement sur la grille d'un kart est son des participants slot.

ws.onmessage = (e) => {
  if (typeof e.data === "string") return onControl(JSON.parse(e.data)); // roster, presence, event, ready, chat, result
  const bytes = new Uint8Array(e.data);
  const sender = guidFromDotNet(bytes.subarray(0, 16)); // server-stamped, trustworthy
  onGameplay(sender, new DataView(e.data, 16));          // your payload starts at byte 16
};

// The server prefixes the sender's participant id in .NET GUID byte order:
// the first three groups are little-endian.
function guidFromDotNet(b) {
  const h = (i) => b[i].toString(16).padStart(2, "0");
  return `${h(3)}${h(2)}${h(1)}${h(0)}-${h(5)}${h(4)}-${h(7)}${h(6)}-` +
         `${h(8)}${h(9)}-${h(10)}${h(11)}${h(12)}${h(13)}${h(14)}${h(15)}`;
}

Ne mettez jamais d'identifiant de joueur dans votre propre charge utile et faites-lui confiance - le préfixe de 16 octets est la seule identité que le serveur garantit.

Routage et budget

La plate-forme applique la forme du jeu routé par l'hôte :

  • A invité portée des images binaires seulement l'hôte - c'est le canal d'entrée.
  • Le l'hôte portée des images binaires chaque invité - c'est le canal d'instantané.
  • Chaque image est au maximum 8 Ko; chaque connexion peut envoyer 30 messages/seconde (2× rafale pour un seconde). Passer ferme la prise avec PolicyViolation.

Ainsi, l'hôte simule à la fréquence qui lui convient (60 Hz est typique), mais envoie instantanés à 20 Hz et les invités envoient des entrées à 20 Hz. Cela laisse de la marge pour le cadre de contrôle occasionnel.

Dispositions des cadres (exemple)

Entrées, invité → hôte, 7 octets :

Compenser Taper Champ
0 u8 1 = entrée
1 u16 seq — incrémente chaque envoi
3 i8 diriger, −127…127
4 u8 manette des gaz, 0…255
5 u8 bits : 0 frein, 1 dérive
6 u8 itemPresses — un compteur, pas un drapeau

itemPresses est un décompte courant des pressions sur les boutons d'un élément. À 20 Hz, une pression inférieure à 50 ms autrement, se situerait entre les échantillons ; avec un compteur, l'hôte déclenche un élément par incrément, mais le les presses ont débarqué.

Snapshots, hôte → invités, 4 + 22 octets par kart (176 octets pour une grille complète) :

Compenser Taper Champ
0 u8 2 = instantané
1 u16 tique hôte
3 u8 nombre de karts
par kart u8, f32 ×4, u8, u16, u8, u8 fente, x, z, cap, vitesse, tour, point de contrôle, article, drapeaux

Les invités rendent d'autres karts ~100 ms dans le passé, en interpolant entre les deux instantanés qui supportez ce moment-là et prédisez leur propre kart localement à partir de leurs entrées, en se dirigeant vers celui de l'hôte. position lorsqu’ils ne sont pas d’accord. Inclure la dernière entrée seq l'hôte a postulé par kart en flags ou un champ supplémentaire si vous souhaitez un rapprochement exact.

Compte à rebours, épreuves de course, arrivée

Les trames de contrôle sont au format JSON, d'une taille maximale de 4 Ko, et les tampons du serveur from avec l'identifiant de participant de l'expéditeur :

  • Les invités envoient {"type":"ready"} une fois la piste chargée.
  • L'hôte attend que chaque humain connecté soit prêt (ou un délai d'attente), puis envoie {"type":"event","kind":"countdown","goInMs":3000}. Les invités commencent leur compte à rebours local le reçu - aucune synchronisation d'horloge n'est nécessaire à cette précision.
  • D'autres rythmes de course sont également event cadres : {"kind":"lap","slot":3,"lap":2}, {"kind":"finished","slot":3,"place":1,"timeMs":94210}.
  • chat est accessible à tous, mais les invités sont limités à 10 images de contrôle par minute – suffisamment pour ready et quelques "gg"s, pas pour le gameplay.

Lorsque le dernier humain franchit la ligne (ou un chronomètre après la fin du vainqueur), l'hôte soumet le résultat, qui ferme la pièce et pousse {"type":"result"} à tout le monde :

POST /api/v1/realtime/rooms/{id}/result

{ "teamScores": [0],
  "metadata": { "track": "coral-loop",
                "order": [ { "slot": 3, "timeMs": 94210 }, { "slot": 0, "timeMs": 95002 } ],
                "bestLapMs": 30112 } }

teamScores nécessite exactement une entrée par équipe (bridée entre 0 et 50), ce qui n'apporte rien d'utile dans un gratuit pour tous; l'ordre de finition réside dans metadata. Une course par équipe, c'est la même pièce avec teamCount: 2 et les points de chaque équipe dans teamScores.

Pilotes de processeur, sortants et changements d'hôte

  • Les sièges AI sont à vous de conduire. La plateforme réserve le siège et nomme le conducteur ; celui de l'hôte la simulation le dirige (une ligne de course passant par les points de contrôle, avec quelques élastiques).
  • Un invité qui part à mi-course (POST /rooms/{id}/leave) conserve son kart sur la grille : le roster push montre le même participant id maintenant isAi: true, et le processeur de l'hôte prend le contrôle de ce kart.
  • Un invité qui laisse tomber est toujours dans la pièce ; gardez leur kart en roue libre et laissez-les se reconnecter — la prise la plus récente remplace l’ancienne.
  • Si l'hôte part, le rôle d'hôte passe à l'humain restant le plus ancien et au la poussée de la liste montre le nouveau isHost. Chaque invité détient déjà le dernier instantané complet, donc le nouveau l'hôte reprend la simulation et commence à envoyer des instantanés ; les entrées des invités sont désormais acheminées vers eux. La migration de l'hôte est le travail de votre code : la plate-forme ne fait que déplacer le rôle.
  • Si l'hôte se déconnecte simplement, la salle se ferme après 60 secondes sans prise hôte.

6. Autour de la course

  • Voix et chat. Chaque invité peut déjà chat sur le socket temps réel ; pour la voix, voir Voix.
  • Rematch. La salle est fermée après le résultat. Demandez à l'hôte de créer une nouvelle salle et d'inviter le les humains de la liste précédente, ou renvoyer tout le monde pour une participation rapide.
  • Classements des temps au tour. Le classement de la plateforme d'un jeu est son tableau elo, écrit uniquement par un serveur exécution. Un classement défini par l'éditeur accepte POST /api/v1/leaderboards/{id}/submit, mais ça le score est réclamé par le client – bien pour un contre-la-montre amical, pas pour quoi que ce soit avec des prix.

7. Variante B : courses faisant autorité sur le serveur

Pour une partie classée, déplacez la simulation dans un script. Le lobby est inchangé ; ajoutez le script et paramètres de mise en relation avec le manifeste :

server=server.js
matchmaking.max_wait_seconds=20
matchmaking.ai_players=7

Maintenant, deux choses créent des courses : démarrer une chambre crée une session limitée à la pièce pour ses humains, et mise en relation (POST /api/v1/games/{slug}/matchmaking?queue=grand-prix) en crée un quand huit les joueurs sont trouvés - ou, avec les paramètres ci-dessus, après 20 secondes avec des processeurs jusqu'à sept vides sièges. Un groupe d'amis peut faire la queue avec POST /realtime/rooms/{id}/matchmake.

Quoi qu'il en soit, les clients prennent le sessionId (la chambre est gameSessionId, ou celui du billet correspondant) et rejouer ws/v1/games?sessionId=…. Le socket en temps réel, le cas échéant, est conservé pour la liste uniquement.

Le scénario

Toute la simulation s'exécute dans onTick au plafond de 30 Hz. Chaque invocation est un nouveau bac à sable qui obtient sessionState in et le renvoie, alors gardez cet état petit - il est sérialisé à chaque tick.

const TRACK = { laps: 3, radius: 14,
  checkpoints: [[0, 0], [120, 0], [160, 60], [120, 120], [0, 120], [-40, 60]] };

globalThis.game = {
  tickRateHz: 30,
  replays: true,
  queues: [{ key: "grand-prix", teams: 8, teamSize: 1 }],
  achievements: [
    { key: "chequered-flag", name: "Chequered Flag", description: "Win a race.", points: 10 }
  ],

  createSession(ctx) {
    const karts = racers(ctx).map((r, i) => ({
      id: r.id, name: r.name, ai: r.ai, x: -8 * (i % 2), z: -6 * i, heading: 0, speed: 0,
      cp: 1, lap: 0, boost: 0, boosts: 1, input: {}, ack: 0, finishedAt: null
    }));
    return { ok: true, sessionState: { t: ctx.now, goAt: ctx.now + 4000, karts, order: [] } };
  },

  onPlayerMessage(ctx) {                       // durable commands: discrete actions
    const s = copy(ctx.sessionState);
    const k = s.karts.find((k) => k.id === ctx.message.from);
    if (ctx.message.data?.type === "use-item" && k && k.boosts > 0 && ctx.now >= s.goAt) {
      k.boosts--; k.boost = 1.2;
    }
    return { ok: true, sessionState: s };
  },

  onTick(ctx) {
    const s = copy(ctx.sessionState);
    const dt = Math.min(Math.max((ctx.now - s.t) / 1000, 0), 0.1);
    s.t = ctx.now;
    for (const i of ctx.inputs || []) {        // latest realtime input per player since last tick
      const k = s.karts.find((k) => k.id === i.from);
      if (k) { k.input = i.data; k.ack = Math.max(k.ack, Math.floor(+i.data.seq) || 0); }
    }
    if (ctx.now >= s.goAt) {
      for (const k of s.karts) {
        if (k.finishedAt) continue;
        move(k, k.ai ? aiInput(k) : k.input, dt);   // pure motion — shared with the client
        progress(k, s, ctx);                        // checkpoints, laps, finish — server only
      }
    }
    const snap = s.karts.map((k) =>
      [k.id, r2(k.x), r2(k.z), r3(k.heading), r2(k.speed), r2(k.boost), k.lap, k.cp, k.ack]);
    const out = { ok: true, sessionState: s,
      broadcast: [{ to: "all", data: { type: "snap", t: s.t, goAt: s.goAt, karts: snap } }] };
    if (raceOver(s, ctx)) Object.assign(out, finish(s, ctx));
    return out;
  }
};

Les aides sont du code de jeu ordinaire. Les parties qui intéressent la plateforme :

  • racers(ctx) lit la grille à partir du début de la session : ctx.room.roster pour un salle (les sièges AI ont userId: null, alors donnez-leur des identifiants comme ai-0-5), ctx.matchmaking.seats pour un course matchmaking (sauter les sièges avec id: null), autre ctx.players.
  • move(k, input, dt) doit fixer chaque valeur d'entrée — steer à −1…1, throttle à 0…1 — parce que ctx.inputs[].data est ce que le client a envoyé. Seulement from est digne de confiance. Gardez-le pur - non ctx, pas d'état de session — le client peut donc l'exécuter également (voir prédiction côté client).
  • Le hasard et le temps venir de ctx.random et ctx.now; il n'y a pas Date ou Math.random.
  • finish(s, ctx) retours result (qui termine la session et, pour une salle, la ferme), achievements pour le gagnant s'il est humain, et eloUpdates pour les coureurs humains - par exemple par paires elo à travers l'ordre de fin, lu et réécrit vers ctx.playerStates. Les sièges AI ne peuvent pas recevoir l'état du joueur, les notes ou les réalisations.
  • raceOver devrait également mettre fin à des courses que personne ne peut terminer – chaque humain disparu selon ctx.presence (chambres), ou une limite de temps stricte.
  • Rediffusions ne garder que le final sessionState. Gardez un tableau de temps au tour et une finition compacts ordre dedans, pas un journal de position par tick.

Le client

Envoyez la direction sous forme d'entrée en temps réel à chaque tick et les actions discrètes sous forme de commandes durables :

// ~30 Hz: latest-wins, batched into the next onTick
send({ type: "cmd", data: { type: "input", realtime: true, seq: ++seq,
                            steer, throttle, brake, drift } });

// on key press: a durable command, runs onPlayerMessage immediately
send({ type: "cmd", data: { type: "use-item" } });

Articles doit passer par une commande durable. Les entrées en temps réel sont les dernières victoires entre les ticks, et le la plateforme préserve uniquement les champs one-shot pass, tackle et shoot lorsqu'un échantillon plus récent remplace un ancien — tout autre bouton dans une entrée en temps réel peut être écrasé avant la coche le voit.

achievement les trames arrivent sur le même socket ; lire GET /api/v1/games/{slug}/achievements sur charge pour tout ce qui a été accordé avant son ouverture.

Prédiction côté client

En restituant uniquement ce que le serveur envoie, le kart a l'impression d'être dirigé dans la boue. Un pilotage le changement doit atteindre le serveur, attendre le prochain tick (jusqu'à 33 ms à 30 Hz) et revenir dans un délai snap — à 80 ms de ping, soit plus de 100 ms avant que le kart ne tourne. La prédiction cache cela : le client bouge son propre kart immédiatement et traite chacun snap comme correction, pas comme sur la photo.

Partagez le code de mouvement

Divisez la simulation comme le fait le script ci-dessus : un pur move(k, input, dt) pour la manipulation, et serveur uniquement progress pour les points de contrôle, les tours et les finitions. Exposer le code de mouvement de server.js comme deuxième global - le modèle que les échecs utilisent pour globalThis.chessRules - et chargez le même fichier dans le navigateur :

// server.js — shared by the platform's sandbox and the browser
function move(k, input, dt) { /* clamp input, integrate speed, heading, x, z, boost */ }
globalThis.kartPhysics = { move, TRACK };
globalThis.game = { /* ... as above ... */ };

<script src="server.js"></script>  <!-- defines kartPhysics; the client never calls game.* -->

Le client prédit mouvement seulement. Les tours, les positions, les éléments et l'ordre d'arrivée restent la propriété du serveur. appeler. Ne vous attendez pas à des résultats identiques : le bac à sable et le navigateur peuvent être en désaccord dans les derniers bits de Math.sin/Math.cos, et des postes dans snap sont arrondis. La réconciliation absorbe cette dérive.

Suivez le rythme du serveur

Le serveur n'exécute pas une étape par entrée. À chaque tick, il applique le dernier entrée qu'il contient pour ce kart, continue de l'utiliser jusqu'à ce qu'un nouveau arrive, et s'intègre en temps réel depuis le tick précédent. Alors reflète cette forme plutôt que de passer à la fréquence d'images d'affichage :

const pending = [];                              // inputs the server hasn't acknowledged yet
let seq = 0, predicted, previous;               // { x, z, heading, speed, boost }, seeded from the first snap
let error = { x: 0, z: 0, heading: 0 };          // visual offset, decays in render()

setInterval(() => {                              // 30 Hz, the script's tickRateHz
  if (!predicted || serverNow() < goAt) return;  // the server ignores movement before goAt
  const input = { steer: readSteer(), throttle: readThrottle(), brake: held("brake"), drift: held("drift") };
  const entry = { seq: ++seq, input, dt: 1 / 30 };
  send({ type: "cmd", data: { type: "input", realtime: true, seq: entry.seq, ...input } });
  pending.push(entry);
  previous = { ...predicted };
  kartPhysics.move(predicted, input, entry.dt);  // the kart responds now, not a round trip later
}, 1000 / 30);

L'envoi plus rapide que le taux de tick est inutile - seule la dernière entrée par tick est utilisée - et le la plate-forme laisse tomber les entrées en temps réel au-dessus de son plafond par connexion.

Réconcilier sur chaque snap

Le script fait écho ack, le plus haut seq il s'applique à chaque kart. Sur chaque snap, rembobinez votre kart à l'état du serveur et rejouez ce que le serveur n'a pas encore vu :

function onSnap(snap) {
  const [, x, z, heading, speed, boost, lap, cp, ack] = snap.karts.find((k) => k[0] === myId);
  while (pending.length && pending[0].seq <= ack) pending.shift();   // applied or superseded

  const corrected = { x, z, heading, speed, boost };
  for (const p of pending) kartPhysics.move(corrected, p.input, p.dt);

  if (!predicted) { predicted = corrected; previous = { ...corrected }; return; } // first snap
  error.x += predicted.x - corrected.x;          // what the player would see jump
  error.z += predicted.z - corrected.z;
  error.heading += predicted.heading - corrected.heading;
  if (Math.hypot(error.x, error.z) > 3) error = { x: 0, z: 0, heading: 0 }; // wall hit, bump: snap
  predicted = corrected;
  hud.lap = lap; hud.checkpoint = cp;            // progress is never predicted
}

Jeter tout jusqu'à ack est correct même si les dernières victoires ignorent certaines entrées : un saut l'entrée a été remplacée avant que le serveur ne soit coché, elle n'a donc jamais affecté non plus le kart du serveur.

Corrections fluides, rendu à la fréquence d'images

Les petites corrections doivent être invisibles. Dessinez le kart à la position prévue plus un signe en déclin décalage d'erreur, et interpoler entre les deux dernières étapes de prédiction de 30 Hz pour un affichage à 60 ou 144 Hz se déplace en douceur :

function render(frameDt) {
  const decay = Math.exp(-frameDt / 0.1);        // ~100 ms to absorb a correction
  error.x *= decay; error.z *= decay; error.heading *= decay;
  const a = sinceLastStep() * 30;                // 0…1 between prediction steps
  drawKart(lerp(previous.x, predicted.x, a) + error.x,
           lerp(previous.z, predicted.z, a) + error.z,
           lerpAngle(previous.heading, predicted.heading, a) + error.heading);
}

Ajustez le seuil d'accrochage plutôt que le déclin : une correction plus grande que la longueur d'un kart est un véritable problème. événement (une bosse que vous n'aviez pas prévu) et se lit mieux comme un instantané rapide que comme une diapositive lente.

Sachez ce qu'il ne faut pas prédire

  • Autres karts. Ils sont dessinés ~100 ms dans le passé (tampon snaps et interpoler entre les deux ce support serverNow() - 100), donc une collision prédite contre eux est une collision avec où ils étaient. Prévoyez les murs et la piste (ils ne bougent pas) et laissez le serveur résoudre bosses de kart à kart. La correction arrive dans un aller-retour. Si le tampon est à sec, extrapolez de la vitesse et du cap jusqu'à ~ 100 ms, puis maintenez.

Estimer l'horloge du serveur

snap.t et goAt sont l'heure du serveur (ctx.now). Gardez un décalage par rapport au plus petit écart observé, ce qui filtre les livraisons lentes :

let offset = Infinity;
function noteSnap(snap) { offset = Math.min(offset, performance.now() - snap.t); }
const serverNow = () => performance.now() - offset;

Démarrez le compte à rebours à partir de goAt, et la prédiction de porte dessus comme le fait la boucle ci-dessus. Un kart qui bouge avant goAt obtient localement un élastique vers le réseau par le premier snap après le départ.

Pour régler tout cela, ajoutez une latence artificielle dans le développement (délai send et onSnap de 100 à 200 ms) et enregistrez la taille de chaque correction - moyenne de corrections importantes et constantes move a dérivé du la copie du serveur ou un champ de saisie est serré différemment de chaque côté.
