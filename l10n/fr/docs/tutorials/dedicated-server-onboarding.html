Publier un serveur de jeu dédié et intégrer des joueurs dans le jeu

Ce tutoriel montre comment :

  1. Publiez ou mettez à jour un conteneur de serveur de jeu dédié avec l'API de téléchargement de bundles de StarHermit.
  2. Gardez le jeton de serveur StarHermit d'un conteneur de longue durée renouvelé.
  3. Intégrez des joueurs de Steam, Epic, GOG ou d'une version autonome sans les envoyer via un Fournisseur OAuth ou en leur demandant de visiter le tableau de bord StarHermit.
  4. Donnez à ces joueurs l'accès aux sessions StarHermit, au matchmaking, aux classements, aux réalisations, discussion de session, voix, amis, présence et rediffusions.

L'API destinée aux joueurs est la même, que l'exécutable provienne de Steam, Epic, GOG ou du vôtre. lanceur, ou https://<slug>.starhermit.com.

Limite importante : l'intégration n'est pas silencieuse

StarHermit n'expose pas actuellement de privilèges "créer un joueur arbitraire" point final d'un jeu serveur. Un conteneur STARHERMIT_SERVER_TOKEN n'a délibérément aucune identité de joueur et ne peut pas frapper comptes de joueurs ou usurper l'identité de joueurs.

L'enregistrement par clé publique nécessite également un e-mail valide et un lien de vérification unique. Donc:

  • Toi peut conservez l'enregistrement dans l'interface utilisateur de votre jeu et évitez Google/GitHub OAuth et le Tableau de bord StarHermit.
  • Toi ne peut pas créez silencieusement un compte StarHermit à partir uniquement d'un identifiant Steam, d'un identifiant de compte Epic ou de GOG Pièce d'identité. Le joueur doit consentir, fournir un e-mail et le confirmer une fois.
  • Générez et stockez la clé privée de chaque joueur sur son appareil. Ne générez pas la clé de chaque joueur sur votre serveur dédié, téléchargez des clés privées ou conservez une base de données de clés de garde, sauf si vous êtes assumer intentionnellement la responsabilité de tous ces comptes.

Pour un jeu natif, l'expérience prise en charge la plus fluide est la suivante : un panneau de compte en jeu génère le clé, demande un e-mail et son consentement, attend que le joueur confirme le lien dans sa boîte de réception, puis se connecte avec la clé et conserve le jeton d'actualisation dans le coffre-fort des informations d'identification du système d'exploitation. Le joueur n'a jamais besoin de naviguer sur le site StarHermit. Un joueur qui ne peut pas fournir et vérifier un e-mail ne peut pas terminer ce flux avec l'API actuelle.

Architecture et limites de confiance

Steam/Epic/GOG/native client
  ├─ owns the player's private key
  ├─ performs public-key registration/login
  ├─ holds player access + rotating refresh token
  ├─ optionally links the external platform identity
  └─ uses a game-scoped launch token for game/social APIs
                  │
                  │ REST + ws/v1/games
                  ▼
StarHermit API ───────── authenticated command ────────► your container
  ├─ creates sessions and matchmaking                     ├─ owns simulation
  ├─ stamps the trusted StarHermit user id                 ├─ never trusts payload identity
  ├─ persists snapshots/results/elo/achievements           └─ uses narrow server token only
  └─ supplies session chat, voice, friends, and replays

Le client du jeu prouve qui est le joueur. StarHermit appose cette identité sur le trafic envoyé au conteneur. Le conteneur n'accepte jamais un identifiant Steam ou un identifiant utilisateur fourni dans le gameplay JSON comme preuve d'identité.

Conditions préalables

Il vous faut :

  • Un compte développeur StarHermit et un jeton d'accès complet.
  • Un jeu enregistré que vous possédez, avec un gameSlug et backend faisant autorité. Le point de terminaison du bundle met à jour un jeu existant ; il ne crée pas de record de jeu et ne réserve pas de limace.
  • Hébergement de conteneur activé pour votre compte.
  • Docker ou un autre outil capable de produire un fichier compatible Docker docker save archive.
  • Un conteneur implémentant protocole de jeu v1.

Pour l'enregistrement initial en libre-service, utilisez un référentiel GitHub vérifié avec starhermit.txt et un valide container.image déclaration telle que décrite dans Jeux GitHub. Une fois le le jeu existe, les push de bundles peuvent publier directement les versions ultérieures du client et du serveur.

Partie 1 : mettre en œuvre le contrat conteneur

Votre processus doit écouter PORT et mettre en œuvre :

Point de terminaison Responsabilité
GET /health Retour 200 seulement lorsque les séances peuvent être acceptées
GET /describe Déclarer le protocole 1, taux/capacité de tick demandé et réalisations
POST /sessions Créez une session ou restaurez-en une à partir de snapshot
GET /sessions/{id}/snapshot Renvoie un point de restauration durable complet
DELETE /sessions/{id} Libérer la session
WS /stream Recevez des commandes de joueurs authentifiés et émettez des charges utiles de jeu
WS /control Push instantanés, réalisations, Elo, résultats et contre-pression

Valider X-Starhermit-Invoke-Key sur chaque requête HTTP et mise à niveau de WebSocket par rapport STARHERMIT_INVOKE_KEY. Cela authentifie StarHermit auprès de votre processus.

Une déclaration minimale est :

{
  "protocol": 1,
  "tickRateHz": 20,
  "maxSessions": 48,
  "replays": true,
  "achievements": [
    {
      "key": "first-win",
      "name": "First Win",
      "description": "Win a match.",
      "points": 10
    }
  ]
}

replays demande à la plateforme de conserver le dernier état de chaque session terminée, ce qui GET /api/v1/games/{slug}/replays/{sessionId} sert. Déclarez-le uniquement si votre jeu souhaite des replays ; sans cela, rien n'est conservé une fois le match terminé. Voir Serveurs de jeux de conteneurs — GET /describe.

Les frames de flux de gameplay utilisent :

[1 byte type][16 byte sessionId][16 byte userId][payload...]

Taper 1 est une commande entrante ; son identifiant utilisateur a été tamponné par le joueur StarHermit authentifié. Taper 2 est une charge utile JSON sortante adressée à ce joueur, ou à tout le monde lorsque l'ID utilisateur est tous des zéros.

Les effets durables sont dépassés /control:

{ "type": "snapshot", "sessionId": "...", "state": { "round": 4 } }
{ "type": "achievements", "sessionId": "...", "unlocks": { "<userId>": ["first-win"] } }
{ "type": "elo", "sessionId": "...", "updates": { "<userId>": 1248 } }
{ "type": "result", "sessionId": "...", "result": { "kind": "win", "winner": "<userId>" } }

StarHermit filtre ces mises à jour sur les participants à la session et les clés de réussite déclarées. Un résultat est borne. Voir Serveurs de jeux hébergés par des conteneurs pour le protocole complet, contrat d’instantané, d’isolement et de récupération.

Partie 2 : enregistrez le jeu une fois

Placez un manifeste dans le référentiel vérifié utilisé pour l'enregistrement initial :

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # your user ID from GET /api/v1/me, not username

container.image=ghcr.io/your-github-login/orbit-server@sha256:<64-lowercase-hex>
container.port=8080
container.health=/health
container.memory_mb=1024
container.cpu=1.0

Ensemble owner à l'immuable id renvoyé par GET /api/v1/me. N'utilisez pas le nom d'utilisateur du compte ou surnom; ce sont des valeurs d’affichage et peuvent changer.

Enregistrez-le :

API=https://api.starhermit.com
ACCESS_TOKEN='developer-access-token'

curl -sS -X POST "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "repoUrl":"https://github.com/your-github-login/orbit-league"
  }'

Enregistrez le retour id comme GAME_ID et gameSlug comme GAME_SLUG, puis confirmez que le backend existe : GET $API/api/v1/games/$GAME_SLUG réponses 200 une fois que c'est le cas. Un cadeau gameSlug seul ne le fait pas prouvez-le : chaque jeu vérifié en a un, inclus uniquement sur navigateur. Un enregistrement qui déclare un conteneur sans prouver que vous possédez le référentiel est refusé avec 403, et inscription initiale peut également échouer lorsque l’hébergement de conteneurs est indisponible ou restreint.

L'image sauvegardée par le registre dans le manifeste est suffisante pour déployer la première version. La rubrique suivante couvre le chemin de téléchargement direct, utile pour CI et pour les builds dont vous ne voulez pas plate-forme pour cloner ou extraire à nouveau.

Partie 3 : publier un bundle client et serveur dédié

Construire les archives

Le téléchargement est une archive tar compressée au format gzip avec cette présentation :

client/            optional static web client, including the registered launch file
server/image.tar   optional `docker save` output
starhermit.txt     the manifest

Au moins client/ ou server/image.tar doit être présent.

Si vous publiez via le tableau de bord Web StarHermit ou le client Windows plutôt que curl, vous ne le faites pas. construire cette archive à la main. Choisissez soit un dossier de distribution du serveur (holding starhermit.txt et image.tar) ou le image.tar tout seul, et le client emballe la mise en page ci-dessus. Le starhermit.txt valeurs - nom d'affichage et le container.* boutons - sont champs de la boîte de dialogue, pré-remplis à partir du manifeste du dossier lorsqu'il y en a un, donc un simple image.tar publie tout aussi bien.

rm -rf bundle game-bundle.tar.gz
mkdir -p bundle/client bundle/server

# Optional hosted web client.
cp -R dist/. bundle/client/

# Dedicated server image.
docker build -t orbit-server:release -f Dockerfile.server .
docker save orbit-server:release -o bundle/server/image.tar

# Keeps the artifact self-describing, and is what the dashboard/desktop clients require.
cp starhermit.txt bundle/starhermit.txt

tar -C bundle -czf game-bundle.tar.gz .

L'image doit fonctionner avec un système de fichiers racine en lecture seule, un utilisateur non root forcé, aucune capacité, aucun volumes, pas d'Internet et seulement un petit inscriptible /tmp. Dépendances du fournisseur dans l'image.

Téléchargez-le

POST /api/v1/me/github-games/{id}/bundle prend l'archive comme corps brut de la requête, et non comme un formulaire en plusieurs parties :

curl -sS -X POST "$API/api/v1/me/github-games/$GAME_ID/bundle" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game-bundle.tar.gz

Un paquet de plus de 100 Mo environ ne passera pas par cette voie. Le CDN devant l'API refuse un corps de requête important avec un 413 qui lui est propre - un que la plateforme ne voit jamais, donc elle porte non limitBytes et n'apparaît dans aucun journal que vous pouvez lire. UN docker save d'une image de serveur réelle atteint cette taille facilement. Si vous voyez un 413 sans limitBytes, c'est ça et pas celui de ton jeu allocation, qui est de gigaoctets.

Envoyez l'archive identique ws/v1/game-upload à la place - images après un La mise à niveau de WebSocket n'est pas un corps de requête, le plafond ne s'applique donc pas. Même disposition des archives, même allocation, mêmes réponses JSON ; le seul ajout est que vous devez envoyer {"type":"complete"} quand le dernier octet est supprimé, car rien n'est publié jusqu'à ce que vous le fassiez.

Exemple de réponse :

{
  "clientPublished": true,
  "serverImageLoaded": true,
  "imageDigest": "sha256:4e7d...",
  "bytesReceived": 318767104
}

La plateforme :

  • échange atomiquement client/, afin que les utilisateurs ne voient pas une version partiellement téléchargée ;
  • charges server/image.tar, calcule son résumé immuable et ré-épingle le déploiement ;
  • met en file d'attente l'ancien conteneur pour qu'il soit remplacé par l'image téléchargée ;
  • restaure les sessions actives éligibles à partir de leurs instantanés persistants.

Vous pouvez télécharger uniquement le client ou uniquement l'image du serveur. Utilisation de correctifs réservés au client ?mode=merge sur le même point de terminaison (voir mises à jour partielles); une image dans une fusion est toujours chargé en entier. L'allocation disque d'un jeu est 2 Go sur starhermit.com (réglable par l'opérateur) et peut être réglé par match ; parce qu'un push remplace le contenu d'un jeu plutôt que d'y ajouter, c'est à la fois la plus grande poussée et le plus de disque que le jeu peut occuper. 413 comprend limitBytes; un invalide retours d'archives ou d'images 422; et 507 signifie que le serveur n'a pas de place pour le moment — il est vérifié avant que votre corps ne soit lu, donc un téléchargement voué à l'échec est refusé plutôt qu'à moitié atterri. Ne mettez pas de liens symboliques, liens physiques, parcours de chemin ou fichiers en dehors de la disposition documentée dans l'archive.

Un téléchargement réussi ne signifie pas que le nouveau processus a déjà passé avec succès les contrôles de santé. Sonder l'existant GET /api/v1/me/github-games/{id}/deployment visualiser et tester une session réelle avant de promouvoir le construire. L’épinglage ultérieur d’une validation de référentiel ramène explicitement le déploiement au contenu du référentiel.

Changer un jeu existant de server= à un conteneur

Pris en charge, et il conserve le jeu : le même identifiant, slug, <uid>.starhermit.com adresse, joueurs, classements et réalisations. Il n’y a pas d’étape d’inscription distincte.

  1. Remplacer server=... avec votre container.* bloquer starhermit.txt. Les deux sont mutuellement exclusif; un manifeste déclarant les deux est refusé.
  2. Poussez un paquet transportant client/ (avec ce manifeste) et server/image.tar, sur ws/v1/game-upload s'il est grand.
  3. L'image que vous téléchargez est celle qui s'exécute. UN container.image= la ligne dans le même manifeste est c'est bien à conserver, mais le résumé téléchargé l'emporte.
  4. Sondage GET /api/v1/me/github-games/{id}/deployment jusqu'à ce qu'il lise running, puis démarrez un vrai chambre ou match.

Partie 4 : renouveler le jeton de plateforme du conteneur

Au démarrage le conteneur reçoit :

STARHERMIT_API_BASE
STARHERMIT_GAME_SLUG
STARHERMIT_SERVER_TOKEN
STARHERMIT_SERVER_TOKEN_EXPIRES_IN
STARHERMIT_REFRESH_KEY
STARHERMIT_INVOKE_KEY

STARHERMIT_SERVER_TOKEN est étroit : il représente le serveur de jeu, pas un joueur. Il expire après 24 heures par défaut. Programmer le renouvellement à environ la moitié de STARHERMIT_SERVER_TOKEN_EXPIRES_IN:

POST {STARHERMIT_API_BASE}/api/v1/games/{STARHERMIT_GAME_SLUG}/server/token
X-Starhermit-Refresh-Key: {STARHERMIT_REFRESH_KEY}

{ "token": "eyJhbGciOi...", "expiresInSeconds": 86400 }

Aucun jeton de porteur n'est requis pour ce point de terminaison. Cela permet la récupération même si l'ancien jeton a déjà expiré. Remplacez le jeton en mémoire de manière atomique et planifiez le prochain renouvellement à partir du nouveau expiresInSeconds.

Gardez les deux secrets de déploiement séparés :

  • STARHERMIT_INVOKE_KEY authentifie les requêtes StarHermit auprès de votre conteneur.
  • STARHERMIT_REFRESH_KEY authentifie votre conteneur lors du renouvellement de son token StarHermit.

Les deux tournent à chaque redémarrage du conteneur. Ne les enregistrez jamais, renvoyez-les /describe, mettez-les dans un instantané, ou envoyez-les à un joueur.

Partie 5 : intégrer un joueur non-StarHermit sans OAuth

Exécutez ce flux dans le jeu ou le lanceur natif, et non dans le conteneur dédié. La procédure complète, avec le code client testé, est Tutoriel : intégrer des joueurs avec une clé publique; en bref:

  1. Générer une clé par installation au premier lancement (Ed25519 recommandé) et conserver la clé privée dans le magasin d’informations d’identification du système d’exploitation. Ne le téléchargez jamais et ne générez jamais de clés de joueurs sur votre serveur.
  2. Demander le consentement et une adresse e-mail, alors POST /api/v1/auth/public-key/register avec { email, keyType, keyData } depuis l'appareil du joueur. Il est limité à une seule inscription par adresse et par IP toutes les 24 heures (429 avec Retry-After), donc ne le faites jamais via votre proxy serveur – chaque joueur partagerait son adresse IP.
  3. Attendez que le joueur confirme. Le lien envoyé par email ouvre une page qui ne change rien jusqu'à le joueur appuie sur Confirmer, ce qui crée le compte et joint la clé ; sur starhermit.com ils atterrissent ensuite sur le tableau de bord StarHermit, votre jeu ne reçoit donc pas ces jetons. Au lieu de cela, se connecte avec la clé jusqu'à ce que cela réussisse: challenge, signez StarHermit's octets de défi exacts, complete. Jusqu'à ce que le joueur confirme, complete réponses 401 "Public key not registered or revoked.".
  4. Gardez la séance avec POST /api/v1/auth/refresh, et reconnectez-vous avec la clé à chaque fois l'actualisation échoue. Acceptez les conditions actuelles lorsque GET /api/v1/me rapports termsAcceptanceRequired (les sessions de compte et les jetons de lancement de joueur peuvent — voir acceptation des conditions). Le jeton de déploiement de votre conteneur est exempté de conditions; cette exemption ne s’étend pas à ses joueurs.

Plus d'appareils. Chaque installation enregistre sa propre clé avec la même adresse e-mail du joueur, et la clé rejoint le compte existant. POST /api/v1/me/public-keys n'est pas une option pour ces joueurs : cela nécessite une session connectée via un fournisseur OAuth.

5. Ajoutez un nom destiné au joueur et une identité externe

Le compte généré commence par un pk-... nom d'utilisateur. Laissez le joueur choisir un surnom :

PATCH /api/v1/me
Authorization: Bearer <access-token>
Content-Type: application/json

{ "nickname": "RookPilot" }

Vous pouvez associer le compte à la plateforme sous laquelle l'exécutable s'exécute :

POST /api/v1/me/identities
Authorization: Bearer <access-token>
Content-Type: application/json

{
  "provider": "epic",
  "providerUserId": "epic-account-id",
  "metadata": "{\"displayName\":\"RookPilot\"}"
}

Utilisez un non réservé nom du fournisseur (epic, gog, ou votre propre identifiant de vitrine). Faire pas utiliser steam, google, github, ou tout autre nom que la plateforme considère comme un fournisseur OAuth – ceux sont rejetés même si ce fournisseur n’est pas configuré. Obtenez l'ID externe de cette plateforme SDK/session authentifié, et non à partir d'une entrée de lecteur modifiable. Ce point de terminaison associe une identité avec le compte StarHermit ; il ne constitue pas en soi une preuve de propriété de la vitrine et ne doit pas remplacer la propre vérification des tickets de la plateforme pour les achats ou les interdictions.

L'API de bibliothèque externe distincte est facultative et utilise actuellement la synchronisation de démonstration pendant que le fournisseur les intégrations sont finalisées ; il n'est pas requis pour le jeu sur serveur dédié.

Partie 6 : entrez dans le jeu et utilisez les services StarHermit

Remplacer {slug} dans les exemples HTTP ci-dessous avec GAME_SLUG, l'UUID du jeu que vous avez obtenu à inscription. Le nom du référentiel orbit-league est un nom d'affichage/source, pas le slug de l'API.

Fabriquez un jeton de jeu avec le moindre privilège

Utilisez le jeton d'accès complet une fois pour créer un jeton clôturé pour votre jeu :

POST /api/v1/games/{slug}/launch-token
Authorization: Bearer <access-token>

{ "token": "eyJhbGciOi...", "expiresInSeconds": 3600 }

Utilisez ce jeton de lancement pour le jeu et les API sociales de session autorisées. Actualisez-le avant expiration. Gardez le jeton de compte complet hors du code de jeu lorsque cela est possible.

Matchmaking

POST /api/v1/games/{slug}/matchmaking
Authorization: Bearer <game-token>

Sondage GET /api/v1/games/{slug}/matchmaking jusqu'à status est matched, puis connectez :

wss://api.starhermit.com/ws/v1/games?sessionId=<sessionId>&access_token=<game-token>

Les messages clients restent JSON :

{ "type": "cmd", "data": { "type": "input", "throttle": 0.8 } }

StarHermit convertit la commande en flux de conteneur et tamponne le StarHermit authentifié identifiant utilisateur. Votre conteneur renvoie des charges utiles de jeu faisant autorité via des trames de flux de type 2.

Classements et réalisations

Chaque jeu faisant autorité reçoit un classement Elo. Votre conteneur envoie les modifications Elo et déclare le succès se débloque /control; les clients lisent uniquement l'état de la plate-forme résultant :

GET /api/v1/games/{slug}/achievements
GET /api/v1/leaderboards/{leaderboardId}/entries

Un client Steam/Epic/GOG modifié ne peut pas soumettre directement les scores du classement du jeu ni réclamer un réalisation appartenant au jeu.

Chat et voix de session

GET /api/v1/games/{slug}/sessions/{sessionId} retours chatConversationId. Séance les conversations permettent aux participants de discuter et d'utiliser la voix même lorsqu'ils ne sont pas amis.

Flux vocal typique :

  1. GET /api/v1/voice/rooms?conversationId=<chatConversationId>.
  2. Si nécessaire, POST /api/v1/voice/rooms avec l'identifiant de la conversation.
  3. POST /api/v1/voice/rooms/{roomId}/join.
  4. Connecter wss://api.starhermit.com/ws/v1/voice?roomId=<roomId>&access_token=<game-token>.

Le même compte permet également les amis, la présence, les invitations à des jeux, les rediffusions et l'identité de profil sur toutes les constructions de vitrines. Conservez une clé/un compte StarHermit par humain plutôt que de créer un nouveau compte pour chaque match ou chaque lancement de vitrine.

Liste de contrôle de production

Édition

  • [ ] Le jeu possédé existant a un non nul gameSlug.
  • [ ] Le conteneur rejette une clé d'appel erronée ou manquante.
  • [ ] La clé d'appel, la clé d'actualisation et le jeton du serveur sont lus à partir de l'environnement au démarrage du processus, jamais intégrés dans l'image ni mis en cache sur le disque (les trois tournent à chaque démarrage du conteneur).
  • [ ] /health ne revient pas 200 avant que l'État puisse être accepté.
  • [ ] Le bundle utilise du brut application/gzip, pas un codage en plusieurs parties.
  • [ ] L'image fonctionne en lecture seule, non root, hors ligne et sans volumes.
  • [ ] L'état de déploiement et une véritable session de matchmaking sont testés après le téléchargement.
  • [ ] L'actualisation des jetons du serveur s'exécute avant la moitié de sa durée de vie et échange les jetons de manière atomique.
  • [ ] Aucun des secrets de déploiement n'est enregistré ou conservé dans les instantanés.

Intégration des joueurs

  • [ ] La paire de clés est générée sur l'appareil du lecteur et la clé privée utilise un stockage sécurisé.
  • [ ] La création de compte est divulguée et consentie.
  • [ ] La vérification de l'e-mail est effectuée une fois ; 429 Retry-After est respecté.
  • [ ] Les inscriptions et les jetons joueurs ne transitent pas par le serveur dédié.
  • [ ] Les jetons d'accès/actualisation sont stockés en toute sécurité et la rotation d'actualisation est sérialisée.
  • [ ] Les identifiants externes proviennent de l'état authentifié du SDK Steam/Epic/GOG.
  • [ ] Le gameplay utilise un jeton limité au jeu après la configuration initiale du compte.
  • [ ] Identifiants du client achievement, resumed, et abandoned cadres de jeu.
