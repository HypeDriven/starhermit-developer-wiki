Réclamez un jeu ajouté par quelqu'un d'autre

Si quelqu'un a déjà ajouté votre jeu GitHub public à StarHermit, vous n'avez pas besoin de créer un deuxième inscription. Réclamez la fiche existante pour devenir son propriétaire vérifié et gérer ses métadonnées, hébergement, déploiement, backend du serveur et transferts futurs.

La revendication est protégée par le contrôle du référentiel. Connaître l'ID du jeu ou l'URL du référentiel ne suffit pas. Vous devez prouver le contrôle de l’une des deux manières suivantes :

  1. Liez le compte GitHub personnel propriétaire du référentiel ; ou
  2. Validez votre identifiant utilisateur StarHermit immuable en tant que owner= dans le dépôt starhermit.txt.

La deuxième méthode est particulièrement utile pour les référentiels appartenant à l'organisation, car la version actuelle La vérification de connexion GitHub correspond aux propriétaires de référentiels personnels et ne déduit pas l'appartenance à une organisation.

Quels changements dans les revendications

Une réclamation réussie :

  • conserve l'ID de jeu/liste existant et son historique accumulé ;
  • remplace l'utilisateur StarHermit gérant de l'annonce par vous ;
  • marque la liste comme isVerifiedOwner: true;
  • actualise les métadonnées et les contrôles fiables de starhermit.txt le cas échéant ;
  • provisionne ou actualise un backend de script/conteneur déclaré ;
  • permet l'hébergement de la plate-forme lorsqu'elle est disponible et met en file d'attente le déploiement au fur et à mesure pending;
  • supprime l'accès à la gestion de la personne qui a initialement soumis cette annonce.

La réclamation ne donne pas au demandeur précédent l'accès à votre compte GitHub et ne fusionne pas Comptes utilisateurs StarHermit. Il transfère la gestion de cette annonce spécifique.

Avant de commencer

Il vous faut :

  • Un compte StarHermit et un jeton d'accès utilisateur complet, et non un jeton de lancement limité au jeu.
  • Accès en écriture au référentiel si vous utilisez le owner= méthode de preuve.
  • L'identifiant de liste StarHermit existant.
  • Pour un jeu de référentiel cloné, un valide starhermit.txt à la racine du référentiel.

Seulement github.com/<owner>/<repo> les référentiels et leurs sites GitHub Pages participent à cette réclamation couler. Une URL hébergée arbitraire n'a aucune propriété du référentiel GitHub à prouver et ne peut pas être revendiquée. manière.

Exemples d'utilisation ci-dessous :

API=https://api.starhermit.com
ACCESS_TOKEN='your-full-user-access-token'
OWNER='your-github-login'
REPO='your-game-repository'

Les jetons d'accès durent 15 minutes. Actualisez le vôtre avant de commencer s’il est presque expiré.

Étape 1 : trouver l'annonce existante

Liste des jeux partagés :

curl -sS "$API/api/v1/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Chaque élément comprend la liste immuable id, normalisé repoUrl, ownerLogin, repoName, le Soumissionnaire actuel et statut de propriétaire :

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "isVerifiedOwner": false,
  "submittedByUserId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "submittedByUsername": "someone-else"
}

Correspond aux deux ownerLogin et repoName; ne sélectionnez pas un jeu uniquement parce que son nom d'affichage est similaire. Avec jq:

GAME_ID=$(
  curl -sS "$API/api/v1/github-games" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r --arg owner "$OWNER" --arg repo "$REPO" \
    '.[] | select((.ownerLogin | ascii_downcase) == ($owner | ascii_downcase)
               and (.repoName | ascii_downcase) == ($repo | ascii_downcase)) | .id' |
  head -n1
)

printf 'Listing ID: %s\n' "$GAME_ID"

Arrêtez si le résultat est vide. N'appelez pas de réclamation avec un identifiant copié à partir d'une annonce sans rapport.

Étape 2 : choisissez comment prouver la propriété

Option A : lier le compte GitHub du propriétaire du référentiel

Utilisez-le lorsque le référentiel appartient directement à votre connexion GitHub personnelle.

À partir du flux de compte/paramètres de StarHermit, démarrez GitHub OAuth dans lien mode lorsque vous êtes connecté au Compte StarHermit qui devrait gérer le jeu. La création de liens est différente de la création accidentelle d'un deuxième compte StarHermit avec connexion GitHub.

Le flux API commence à :

GET /api/v1/auth/oauth/github/authorize?link=true

Il est piloté par le navigateur et utilise un cookie d'état de courte durée. La liaison nécessite un StarHermit récent authentification. Terminez l'autorisation GitHub dans la même session de navigateur qui l'a démarré.

Vérifiez le résultat :

curl -sS "$API/api/v1/me/github" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Attendu:

{ "linked": true, "login": "octocat" }

Le login renvoyé doit correspondre à celui de la liste existante ownerLogin, sans tenir compte de la casse. Un personnel La connexion à GitHub ne prouve pas l'appartenance à une organisation propriétaire du référentiel. Pour un référentiel appartenant à l’organisation, utilisez l’option B.

Option B : ajouter owner= à starhermit.txt

Cela prouve le contrôle car seule une personne capable de publier le contenu du référentiel peut ajouter de la valeur. Ensemble owner à votre identifiant utilisateur StarHermit immuable (UUID), pas votre nom d'utilisateur ou votre pseudo.

Obtenez votre pièce d'identité :

STARHERMIT_USER_ID=$(
  curl -sS "$API/api/v1/me" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r '.id'
)

À la racine du référentiel, créez ou mettez à jour starhermit.txt:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

Remplacez l'exemple de propriétaire par STARHERMIT_USER_ID. Ne mettez pas votre nom d'utilisateur ou votre pseudo ici ; ceux-ci peuvent changer, tandis que l'ID utilisateur est l'identifiant de propriété stable.

Pour un jeu faisant autorité, conservez exactement une déclaration backend :

# JavaScript runtime:
server=server.js

# OR container runtime, never both:
# container.image=ghcr.io/your-org/orbit-server@sha256:<64-lowercase-hex>

Valider et envoyer le manifeste vers le référentiel/version StarHermit peut lire :

git add starhermit.txt
git commit -m "Declare StarHermit game ownership"
git push

Avant de réclamer, ouvrez le fichier brut du référentiel starhermit.txt URL dans un navigateur non authentifié et confirmez que la nouvelle valeur est lisible publiquement. La revendication lit le référentiel au moment de la demande ; un un changement local non poussé ne peut rien prouver.

Étape 3 : valider le manifeste

Pour un jeu de référentiel cloné normal, la revendication nécessite :

  • starhermit.txt à la racine du référentiel ;
  • non vide name=;
  • launch= pointant vers un référentiel relatif .html ou .htm déposer;
  • un facultatif valide server= chemin se terminant par .js/.mjs, ou un valide container.image= déclaration;
  • jamais les deux environnements d'exécution du serveur à la fois.

Une liste de pages GitHub conserve son URL hébergée comme cible de lancement et ne nécessite pas de manifeste lorsque la propriété personnelle de GitHub est prouvée, bien qu'un nom de manifeste valide puisse toujours mettre à jour son nom d’affichage.

Si le jeu déclare un conteneur, son image doit satisfaire au registre, à l'espace de noms du propriétaire et au résumé. règles dans Serveurs de jeux hébergés par des conteneurs. L'hébergement de conteneurs peut également être restreinte par l’exploitant de la plateforme.

Étape 4 : revendiquer la fiche

La demande de réclamation n'a pas de corps :

curl -sS -X POST \
  "$API/api/v1/me/github-games/$GAME_ID/claim" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Un succès 200 renvoie le jeu mis à jour :

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "launchPath": "index.html",
  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "isVerifiedOwner": true,
  "metadataSource": "starhermit.txt",
  "hosting": {
    "hostingEnabled": true,
    "deployStatus": "pending"
  }
}

L'ID doit être le même que celui trouvé à l'étape 1. Ne créez pas de nouvelle annonce après une réclamation réussie.

Revendiquer une annonce que vous gérez déjà est intentionnellement autorisé. Il relit le manifeste, réapprovisionne le backend et remet l'hébergement en file d'attente, de sorte que le même appel puisse être utilisé pour resynchroniser un jeu géré par le propriétaire après les modifications du référentiel.

Étape 5 : vérifier la reprise et le déploiement

Confirmez que le jeu apparaît désormais dans votre liste gérée :

curl -sS "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" |
jq --arg id "$GAME_ID" '.[] | select(.id == $id)'

Vérifiez l'état du déploiement :

curl -sS \
  "$API/api/v1/me/github-games/$GAME_ID/deployment" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Une revendication met généralement un déploiement en file d'attente, donc pending immédiatement après la réclamation est normal. Sondage avec reculer jusqu'à ce qu'il atteigne l'état actif/succès de l'environnement ou qu'il expose deployError.

Après la prise de contrôle, les points de terminaison de gestion à votre disposition incluent :

PUT    /api/v1/me/github-games/{id}/deployment  pin a commit/branch and redeploy
POST   /api/v1/me/github-games/{id}/bundle      upload built client/container output
PUT    /api/v1/me/github-games/{id}/hosting     requeue hosting where supported
POST   /api/v1/me/github-games/{id}/transfer    transfer management deliberately
DELETE /api/v1/me/github-games/{id}             remove the game

L'auteur de l'envoi d'origine ne voit plus cette liste sous GET /api/v1/me/github-games et ne peut pas utilisez pour cela ces points de terminaison de gestion limités au propriétaire.

Dépannage

403 : lier le propriétaire du référentiel ou ajouter owner=

La connexion GitHub liée ne correspond pas ownerLogin, ou le manifeste owner ne correspond pas exactement votre identifiant StarHermit.

  • Vérifier GET /api/v1/me/github.
  • Vérifiez l'exact ownerLogin renvoyé par la liste publique.
  • Pour les référentiels d'organisation, utilisez owner=<your StarHermit user ID> dans le dépôt.
  • Confirmez que vous avez envoyé le manifeste et que son URL brute est lisible publiquement.

404: pas de jeu partagé avec cet identifiant

L'identifiant est erroné ou la fiche a été supprimée. Répétez l'étape 1. Les annonces supprimées ne peuvent pas être réclamées.

400: manquant ou invalide starhermit.txt

Pour un référentiel cloné, assurez-vous que le manifeste racine est valide name et HTML launch valeurs. Aussi valider les déclarations facultatives de script/conteneur. La revendication ne fait pas confiance aux métadonnées à l'origine inscrit par un non-propriétaire ; il le remplace par des métadonnées contrôlées par le référentiel.

La réclamation échoue autour du slug/backend

Le script n'est peut-être pas valide ou l'hébergement de conteneurs n'est peut-être pas disponible. Vérifiez l'erreur renvoyée et la déclaration backend, puis appelez à nouveau Claim. La plateforme attribue l'UUID du jeu comme slug ; il n’y a pas de problème manifeste à choisir ou à résoudre.

GitHub était lié mais le mauvais compte StarHermit possède le lien

Connectez-vous au compte StarHermit prévu et complétez le OAuth lien y couler. Ne réclamez pas à partir d'un deuxième compte StarHermit temporaire, puis comptez sur la fusion de comptes ; le jeu des transferts API gestion, pas les identités des utilisateurs.

Notes de sécurité

  • N’acceptez jamais un lien de réclamation ou un identifiant d’annonce comme preuve de propriété du référentiel.
  • Ne placez pas de jetons d'accès GitHub, d'informations d'identification de conteneur ou d'autres secrets dans starhermit.txt.
  • Utilisez toujours l'ID utilisateur StarHermit immuable dans owner=; n'utilisez pas de nom d'utilisateur ou de surnom.
  • Examinez la liste existante et l'URL du référentiel avant de réclamer ; les noms d’affichage ne sont pas uniques.
  • Si vous transférez le jeu ultérieurement, le destinataire devient le manager mais le statut de propriétaire vérifié est réinitialiser. Ils doivent exécuter eux-mêmes le flux de réclamations s’ils contrôlent le référentiel.
