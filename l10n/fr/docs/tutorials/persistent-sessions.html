Tutoriel : sessions persistantes – jeux qui s'arrêtent lorsque tout le monde part

Normalement, la plateforme met fin à un match auquel personne ne joue : une fois que tous les joueurs se sont déconnectés et que personne n'a joué. est revenu dans les cinq minutes, la session se termine comme abandoned avec raison players_left (voir API de jeux — Gameplay WebSocket). C'est vrai pour un jeu d'échecs jeu ou une course, et mauvais pour une ferme, un constructeur de ville, un donjon partagé ou n'importe quel monde, un groupe de les joueurs reviennent au fil des jours.

Un jeu peut demander sessions persistantes plutôt. Une session persistante se met en pause lorsque ses joueurs se déconnectent :

  1. Le dernier joueur part.
  2. Après environ 15 secondes sans personne connectée, la plateforme pauses la séance. Rien ne fonctionne : un jeu de script n'obtient pas onTick appels, et la session d'un jeu de conteneur est supprimée du conteneur.
  3. La session reste en pause dans le cadre de sa politique de rétention de récupération. Lire /sessions/{id}/recovery pour toute expiration plutôt que de supposer qu'il est conservé pour toujours.
  4. Le premier joueur à se connecter ws/v1/games reprend cela, avant que leur premier commandement ne soit manipulé. Le jeu continue là où il s'est arrêté.

Cette page montre comment l'activer, comment empêcher les horloges de votre jeu de sauter pendant une pause et ce que votre client doit faire.

1. Inscrivez-vous

La persistance est une déclaration par jeu, lue lorsque votre jeu est publié ou mis à jour - publiez un mettre à jour après l'avoir modifié. Ce doit être un littéral true ou false; tout le reste compte comme non déclaration, et un jeu qui ne déclare rien se comporte comme avant.

Jeu de scénario — un statique persistent sur le game objet (voir Scripts de jeu):

globalThis.game = {
  persistent: true,
  tickRateHz: 1,
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

Jeu de conteneurs — persistent dans votre GET /describe réponse (voir Serveurs de jeux de conteneurs):

{ "protocol": 1, "tickRateHz": 20, "maxSessions": 48, "persistent": true }

Rien ne change dans la façon dont les sessions sont créées : matchmaking, invitations, point de terminaison de l'IA et temps réel les salles produisent toutes des sessions persistantes pour un jeu persistant.

2. Gardez le temps de jeu immobile pendant la pause

La plateforme ne réécrit pas ctx.now — elle reste la véritable horloge murale, donc à tout moment absolu montrer aux joueurs (une date limite, un "récolte prête à") continue de signifier ce qu'il dit. Au lieu de cela, persistant les sessions obtiennent un champ de contexte supplémentaire :

ctx.pausedMs   // total milliseconds this session has spent paused, so far

Il ne fait que croître, et uniquement sur des sessions persistantes (les autres jeux ne voient jamais le terrain). Soustrayez-le et vous avoir un horloge de jeu ça s'arrête alors qu'il n'y a personne :

function gameTime(ctx) {
  return ctx.now - (ctx.pausedMs || 0);
}

globalThis.game = {
  persistent: true,
  tickRateHz: 1,

  createSession(ctx) {
    return { ok: true, sessionState: { lastTick: gameTime(ctx), crops: [] } };
  },

  onTick(ctx) {
    var state = ctx.sessionState;
    var t = gameTime(ctx);
    var dt = t - state.lastTick;      // never includes the time the world was paused
    state.crops.forEach(function (crop) { crop.growth += dt; });
    state.lastTick = t;
    return { ok: true, sessionState: state };
  },

  onPlayerMessage(ctx) { /* ... */ }
};

Stockez vos propres horodatages pendant le jeu (gameTime(ctx)), pas dans ctx.now, et comparez-les uniquement contre le temps de jeu. Si tu vouloir le monde peut avancer sans que personne ne regarde – des récoltes qui poussent pendant la nuit - utiliser ctx.now à la place et rattrapez votre retard dès le premier tick après un CV. De toute façon, c'est votre choix; la plateforme ne rapporte que ce qui s'est passé.

Deux détails sur le timing :

  • Pendant les ~15 secondes entre le départ du dernier joueur et la pause, la session est toujours coché normalement. Un joueur dont la connexion est interrompue et revient directement ne provoque pas de pause.
  • Après un CV, le suivant onTick vient un intervalle de tick plus tard. Le temps en pause n'est pas rejoué comme un arriéré de ticks manqués.

Un conteneur reçoit pausedMs au même endroit : dans le POST /sessions corps, il est envoyé quand la session est rétablie après une pause.

3. Votre client

Une session suspendue est toujours une session active, le flux client est donc celui que vous avez déjà :

  • Liste des mondes à rejoindre avec GET /api/v1/games/{slug}/sessions/mine. Chaque entrée a un pausedAt horodatage pendant qu'il est en pause et null pendant que quelqu'un est dedans, pour que tu puisses montrer "en pause depuis…" ou "2 amis jouent maintenant" (voir API de jeux – Sessions).
  • Rejoindre en ouvrant ws/v1/games?sessionId=… exactement comme avant. La reprise a lieu pendant le connecter. Il n'y a pas de spécial "repris" cadre pour cela - le jeu est simplement en cours d'exécution lorsque votre premier la commande arrive - alors demandez ou attendez le message d'état complet normal de votre jeu, comme vous le feriez sur toute reconnexion.
  • Gérez un CV échoué. Si la plateforme ne peut pas reprendre la session – probablement un conteneur jeu dont le serveur démarre toujours — vous recevez {"type":"error","error":"…"} et la prise est fermé avec le code 1001. La session reste en pause et rien n'est perdu. Reconnectez-vous après un court instant recul (quelques secondes, en croissance) et affichage "commencer le monde…" plutôt qu'une erreur.
  • presence les frames fonctionnent comme d'habitude, afin que les autres joueurs voient qui se trouve dans le monde en ce moment.

4. Mettre fin à une session persistante

Une session persistante se termine lorsque :

  • votre jeu signale un result (valeur de retour du script ou message de contrôle du conteneur), ou
  • le propriétaire du jeu y met fin (DELETE /api/v1/me/github-games/{id}/sessions/{sessionId}),
  • le dernier membre quitte explicitement un monde sans pièce à travers /sessions/{id}/leave, ou
  • ses données de récupération suspendues expirent conformément à la politique de rétention du déploiement.

La déconnexion laisse l’adhésion intacte ; Quitter explicitement renonce à l'adhésion. Voir Cycle de vie et récupération des sessions pour les deux flux.

Demander un nouveau jeu, oui pas retirez celles en pause du joueur, et les sessions en pause comptent toujours contre le plafond de sessions simultanées par joueur (20 par défaut). Donnez aux joueurs un moyen de terminer ou quitter un monde - un "abandonner le monde" commandez les réponses de votre script avec un result, Par exemple. Sinon, un joueur qui a rempli sa casquette ne peut rien commencer de nouveau.

onPlayerMessage(ctx) {
  var msg = ctx.message.data;
  if (msg.type === "close-world" && ctx.message.from === ctx.sessionState.ownerId) {
    return { ok: true, sessionState: ctx.sessionState, result: { kind: "closed" } };
  }
  /* ... */
}

5. Jeux de conteneurs : stationnement

Pour un jeu de conteneurs, une pause est un parc:

  1. La plateforme demande un instantané final (GET /sessions/{id}/snapshot) et le stocke durablement.
  2. Cela détruit la session (DELETE /sessions/{id}). Votre conteneur arrête de le simuler, et si s'il n'a pas d'autres sessions, le déploiement peut être arrêté après sa période d'inactivité.
  3. Lors de la prochaine jointure, il recrée la session avec POST /sessions, transportant le stocké snapshot et la mise à jour pausedMs — la même demande qu'une restauration sur incident — réveiller un déploiement arrêté d'abord si nécessaire.

L'instantané que vous renvoyez doit donc suffire à reconstruire le monde entier, pas seulement à en reprendre quelques-uns. secondes de jeu. Si cet instantané final échoue, la session est parquée depuis son dernier instantané périodique. point de contrôle. Contrairement à un crash, un parcage et une restauration ne sont pas comptabilisés dans votre budget de redémarrage, et les joueurs n'ont pas resumed cadre : personne n’était là pour voir l’État revenir en arrière.

Liste de contrôle

  • [ ] persistent: true déclaré (script) ou renvoyé de /describe (conteneur) et une mise à jour publiée.
  • [ ] Les chronomètres de jeu utilisent ctx.now - ctx.pausedMs, ou utiliser délibérément ctx.now et rattraper son retard.
  • [ ] Les listes de clients sessions/mine, montre pausedAt, et rejoint ws/v1/games.
  • [ ] Le client réessaye avec interruption après un error suivi du code de fermeture 1001 lors de la connexion.
  • [ ] Les joueurs ont un moyen de mettre fin à un monde, ils ne restent donc jamais bloqués à la limite de session.
  • Les instantanés [ ] (Conteneur) reconstruisent le monde entier.
