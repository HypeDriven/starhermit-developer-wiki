Procédure pas à pas d'intégration : créer un jeu sur StarHermit

Cette page parcourt le cycle de vie complet de l'intégration d'un jeu avec StarHermit, étape par étape : publication, lancement, menu, matchmaking, jeu, chat, voix, notes, rediffusions. Tout ce qui est montré s'applique à n'importe lequel jeu : votre jeu substitue son propre slug, ses propres commandes et son propre script de règles.

L'exemple courant est l'implémentation de référence d'échecs open source, jeu d'échecs starermite: un jeu d'échecs par correspondance (24 heures par coup, classé elo) construit comme un jeu par navigateur statique sans construction en HTML/JS/CSS vanille. Pour chaque étape, la procédure pas à pas montre les appels exacts effectués par un client de jeu et le fichier dans le référentiel de référence qui les effectue. Partout où des valeurs spécifiques aux échecs apparaissent : l'UUID du jeu de référence, les commandes de déplacement, l'encodage de l'échiquier, le "hal" L'IA, le délai de déplacement de 24 heures - ce sont des exemples de valeurs que votre propre jeu définit lui-même dans son propre script.

Lisez-le avec les pages de référence de l'API auxquelles il renvoie. La liste de contrôle à la fin condense tout ce que votre propre jeu doit reproduire.

1. Anatomie d'un jeu hébergé sur plateforme

Un jeu de plateforme scripté est un simple site statique plus un fichier de règles. L'implémentation de référence d'échecs, par exemple, n'a ni bundler, ni framework, ni étape de construction :

Déposer Rôle
index.html La page entière : tableau, menu, chat et interface utilisateur vocale
app.js Bootstrap de l'application, menu principal, matchmaking, invitations, rediffusions, profils
net.js Couche HTTP : chemins de jeu délimités, jetons de lancement, actualisation des jetons
game.js Contrôleur en jeu : gameplay WebSocket, chat, voix
ui.js Rendu du tableau et du menu
style.css Styles
server.js Les règles — voir ci-dessous
starhermit.txt Publier le manifeste

Dans l'implémentation de référence, server.js mérite une attention particulière. C'est les deux les choses à la fois :

  • Le script faisant autorité sur le serveur la plateforme s'exécute (via son hôte Jint) en exposant globalThis.game. Chaque mouvement est validé ici, sur le serveur, selon le contrat en game-scripts.md.
  • Le client moteur de règles partagé, exposé comme globalThis.chessRules, que le navigateur utilise pour le rendu du tableau, les aperçus de déplacement et la relecture.

Un fichier, une source de vérité, zéro règle d'autorité sur le client. Un client de jeu suivant ce modèle ne décide jamais si un mouvement est légal – il restitue ce que le serveur diffuse. Il s’agit de l’idée architecturale la plus importante dans un jeu de plateforme scripté, et l’implémentation de référence le démontre.

2. Publier votre jeu

La publication d'un jeu commence par le starhermit.txt manifeste à la racine du dépôt. Il déclare le jeu name, launch point d'entrée, owner, et server scénario. Facultatif cover= est l'illustration sur la tuile de la bibliothèque - voir Le starhermit.txt manifeste. Le manifeste de l'implémentation de référence, par exemple :

name=StarHermit Chess
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # StarHermit user ID, not username/nickname
server=server.js

Utilisez l'immuable id depuis GET /api/v1/me pour owner; les noms d'utilisateur et les surnoms sont affichés valeurs et ne doivent pas être utilisés comme identifiants de propriété manifestes.

La plateforme clone le dépôt, sert les fichiers statiques à <slug>.starhermit.com — le slug est l'uid que la plateforme attribue au jeu, jamais un nom que vous choisissez ; le jeu de référence est 83fd04b1-3cbe-4b09-a251-3733ad4b9d94, donc il est jouable en live sur 83fd04b1-3cbe-4b09-a251-3733ad4b9d94.starhermit.com - et les procurations /api et /ws au back-end même origine. Cette seule décision supprime toute une catégorie de travail : pas de CORS, pas de configuration de base d'API, pas de détection d'environnement – les clients de jeu utilisent simplement des chemins relatifs.

Plein débit : github-games.md et publisher.md.

3. Lancement et authentification

Le flux de référence d'échecs reçoit les informations d'identification du lanceur de plateforme :

  1. Le lanceur appelle POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/launch-token (affiché avec l'UUID du jeu de référence ; remplacez le vôtre) par le JWT complet de la plate-forme de l'utilisateur.
  2. Cela revient de courte durée, à l'échelle du jeu jeton:
{ "token": "<jwt>", "expiresInSeconds": 3600 }
  1. Il ouvre le jeu à index.html#game_token=<jwt>, éventuellement avec &session_id=<guid> ajouté pour les liens profonds d’invitation.

Dans l'implémentation de référence, le client lit le hachage une fois, puis le dépouille avec history.replaceState afin que le jeton ne s'attarde jamais dans la barre d'URL ou dans l'historique (app.js, App.init). Il décode la charge utile JWT pour deux revendications :

  • sub — l'identifiant de l'utilisateur
  • game_scope - la limace du jeu

Cette deuxième affirmation est importante : un client de jeu ne devrait jamais coder en dur son slug. L'implémentation de référence construit chaque URL d'API comme /api/v1/games/<slug> plus un suffixe (net.js, Net.gamePath), donc le même code fonctionne pour n'importe quel jeu, n'importe quel slug, n'importe quel déploiement.

Rafraîchir. Le jeton étendu est autorisé à rappeler launch-token pour son propre jeu, de sorte que les clients s'actualisent généralement périodiquement : l'implémentation de référence s'actualise toutes les 45 minutes (net.js, Net.startRefresh), confortablement dans la durée de vie de 60 minutes.

Un jeu ouvert directement peut à la place proposer connexion au navigateur, qui renvoie #access_token plutôt que celui du lanceur #game_token. Gérez les deux chemins d’entrée si vous soutenez les deux. Renouvelez en utilisant la durée de vie restituée et respectez la chaîne de renouvellement par défaut de 12 heures. plafond. UN 403 terms_acceptance_required oblige le joueur à accepter via leur compte; ou affichez les conditions dans le jeu et acceptez avec le jeton de lancement du joueur. Se reconnecter ne fonctionne pas enregistrer l’acceptation.

Référence d'authentification : auth.md, games.md.

4. Chargement du menu principal

Le menu d'un jeu s'ouvre généralement avec un petit lot de GET contre son propre slug. Dans l'implémentation de référence, c'est refreshMenu dans app.js:

Infos sur le jeu + mes statistiques :

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "name": "StarHermit Chess",
  "enabled": true,
  "leaderboardId": "<guid>",
  "maxConcurrentSessionsPerPlayer": 20,
  "me": {
    "userId": "<guid>",
    "elo": 1420,
    "wins": 31,
    "losses": 18,
    "draws": 4,
    "activeSessionCount": 3
  }
}

Le me Le bloc correspond à la carte de joueur entière : elo, enregistrement et nombre de sessions simultanées autorisées en cours d'utilisation (20 dans l'exemple des échecs).

Mes séances :

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/mine

[
  {
    "sessionId": "<guid>",
    "status": "active",
    "players": [ /* ... */ ],
    "createdAt": "…",
    "finishedAt": null,
    "myTurn": true,
    "deadline": 1784642591000
  }
]

myTurn et deadline sont ce qui rend utile la liste des sessions d'un jeu par correspondance : le joueur voit d'un coup d'œil quels jeux l'attendent et quand chaque coup doit être dû.

Classement des amis :

GET /api/v1/leaderboards/{leaderboardId}/entries?friendsOnly=true&page=1&pageSize=10

en utilisant le leaderboardId à partir de la réponse des informations sur le jeu.

Rediffusions récentes :

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/mine?limit=10

Invitations en attente :

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites

Références : games.md, leaderboards.md.

5. Faire participer les joueurs à une session – trois manières

Cette procédure pas à pas utilise la mise en relation, l'acceptation d'invitations et la pratique de l'IA pour créer des sessions. Les jeux qui ont besoin d'un lobby peuvent utiliser salles en temps réel, dont le flux de démarrage peut également créer une session faisant autorité liée.

un. Matchmaking

Dans l'implémentation de référence, App.startMatchmaking dans app.js:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking

La réponse est soit un ticket :

{ "ticketId": "<guid>", "status": "queued" }

ou une correspondance immédiate :

{ "status": "matched", "sessionId": "<guid>" }

Lorsqu'ils sont en file d'attente, les clients interrogent le point de terminaison de mise en relation – les sondages d'implémentation de référence GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking toutes les 3 secondes, et DELETE /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking annule le billet. Le client de référence s'assure également que le joueur n'est jamais coincé à regarder une roulette : après 30 secondes sans correspondance, un "Jouer contre Hal" Le bouton apparaît ("hal" est l'adversaire IA intégré de l'exemple d'échecs - voir §12), et POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai retours { "sessionId" }.

b. Invitation d'un ami

Dans l'implémentation de référence, App.inviteFriend dans app.js. Première liste d'amis — ce point de terminaison est explicitement autorisé pour les jetons liés au jeu :

GET /api/v1/me/friends

Envoyez ensuite l'invitation :

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites
{ "toUserId": "<guid>" }

Le destinataire accepte (ou refuse) de la part de son propre client :

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/accept   → { "sessionId": "<guid>" }
POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/decline  → 204

Accepter est ce qui crée la session. Le &session_id= le lien profond launch-hash (§3) y dépose le joueur invité directement.

Les invitations d'amis ne touchent que les personnes qui sont déjà amis. Pour attirer quelqu'un qui n'est pas (ou n'est pas du tout sur la plateforme), l'implémentation de référence propose également un Partager le lien d'invitation bouton (App.shareInviteLink) : une ligne de construction de chaîne qui copie

https://dashboard.starhermit.com/game-invite/<Net.userId>/<slug>

au presse-papiers. Le tableau de bord Web gère tout ce dont le destinataire a besoin : connexion, demande d'ami, surnom, lancement du jeu, puis renvoie l'invitation à jouer au partageur, afin qu'elle atterrisse dans cette même liste d'invitations. Voir Partager des liens pour la totalité du contrat.

c. La règle

Les sessions sont créées par matchmaking, invitation-acceptation, sessions/ai, ou démarrer une salle en temps réel avec un back-end de serveur. Pour un lobby avec des sièges, utilisez le API des salles en temps réel.

6. Jouer sur le gameplay WebSocket

La boucle de jeu est la même pour chaque jeu scripté : récupérer la session, ouvrir le socket, restituer les diffusions, envoyer des commandes. Dans l'implémentation de référence, cela réside dans game.js, GameController.

Récupérez la session :

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/{sessionId}

{
  "sessionId": "<guid>",
  "status": "active",
  "players": [ /* ... */ ],
  "createdAt": "…",
  "finishedAt": null,
  "chatConversationId": "<guid>",
  "result": null
}

Note chatConversationId — vous en aurez besoin pour le chat (§7) et la voix (§8).

Connectez la prise de jeu :

ws(s)://<host>/ws/v1/games?sessionId=<id>&access_token=<token>

Sur open, le client envoie immédiatement une commande de synchronisation :

{ "type": "cmd", "data": { "type": "sync" } }

À chaque déconnexion, il se reconnecte avec un recul exponentiel de 1 seconde jusqu'à un plafond de 30 secondes, et renvoie la synchronisation à chaque ouverture. La commande sync rend la reconnexion apatride et idempotente : tout ce que le client a manqué, le serveur le rediffuse.

L'enveloppe. Chaque image est une fine enveloppe JSON :

  • Client → serveur : {"type":"cmd","data":<command>}
  • Serveur → client : {"type":"game","data":…}, {"type":"error","error":…}, {"type":"presence","userId","online"}

Les commandes du jeu sont définies par votre propre script de règles. Les commandes de l'exemple d'échecs, par exemple (le data charge utile d'un cmd cadre):

{ "type": "sync" }
{ "type": "move", "from": "e2", "to": "e4", "promo": "q" }
{ "type": "resign" }
{ "type": "offer-draw" }
{ "type": "accept-draw" }
{ "type": "decline-draw" }

Dans l'exemple des échecs, promo n'est présent que sur les mouvements de promotion.

Les diffusions sont également définies par un script. Les diffusions de l'exemple d'échecs (le data charge utile d'un game cadre):

  • state — l'instantané complet :
{
  "type": "state",
  "white": "<userId>",
  "black": "<userId>",
  "ratings": { "white": 1420, "black": 1388 },
  "board": "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr",
  "turn": "w",
  "moves": [ { "from": "e2", "to": "e4", "promo": null, "san": "e4", "at": "…" } ],
  "status": "active",
  "result": null,
  "deadline": 1784642591000,
  "drawOfferBy": null,
  "ai": false,
  "aiName": null
}

Le board est une chaîne de 64 caractères, index = rank * 8 + file avec a1 = 0, en utilisant PNBRQK pour le blanc, pnbrqk pour le noir, . pour les cases vides — un encodage spécifique aux échecs ; votre jeu définit sa propre forme d'état.

  • moved — un seul mouvement a été appliqué.
  • draw-offered / draw-declined.
  • game-over — { "result": { "kind", "reason", "at" }, "view" }, où reason les valeurs sont définies par le script ; l'exemple d'échecs utilise checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

L'identité n'est jamais retirée des charges utiles. Le client envoie des commandes sans identifiant d'utilisateur et le script n'en fait jamais confiance à partir du fil : la plate-forme transmet l'expéditeur authentifié au script. Il n'y a rien à usurper.

Voir game-scripts.md pour le contrat de scénario derrière tout ça.

7. Chat en jeu

Chaque séance comporte un chatConversationId (§6) que les clients du jeu peuvent utiliser pour le chat en jeu. Dans l'implémentation de référence, initChat dans game.js l'utilise comme ceci :

GET  /api/v1/chat/conversations/{id}/messages?page=1&pageSize=50
POST /api/v1/chat/conversations/{id}/messages
     { "content": "good luck!" }

La socket de chat en temps réel ws/v1/chat est bloqué pour les jetons liés au jeu. Le client de référence l'essaye une fois, est refusé et revient à interroger le point de terminaison REST toutes les 5 secondes – prévoyez d'interroger dès le début dans votre propre jeu.

Le chat fonctionne même si les deux joueurs ne sont pas amis : la conversation de session (type "game") est créé avec les deux joueurs comme participants, les règles habituelles d'autorisation de chat sont donc déjà respectées.

Référence: chat.md.

8. Voix

La voix est facultative et les clients du jeu la conservent généralement désactivé par défaut. L'implémentation de référence le gère dans game.js, VoiceController. Lorsqu'un joueur l'active :

  1. Recherchez ou créez la salle liée à la conversation de la session :
GET  /api/v1/voice/rooms?conversationId=<chatConversationId>
POST /api/v1/voice/rooms
     { "conversationId": "<chatConversationId>" }
  1. Rejoignez-le :
POST /api/v1/voice/rooms/{roomId}/join
  1. Connectez la prise vocale :
ws(s)://<host>/ws/v1/voice?roomId=<id>&access_token=<token>

Les médias sont WebRTC peer-to-peer avec une négociation parfaite; la prise transporte uniquement la signalisation et le contrôle :

  • Signalisation: {"type":"rtc","to":<userId>,"payload":{"sdp":…}} ou {"type":"rtc","to":<userId>,"payload":{"ice":…}}
  • Contrôle: {"type":"mute","muted":…}, {"type":"speaking","speaking":…}
  • Événements du serveur : voice.roster, voice.participant_joined, voice.participant_left, voice.mute_changed, voice.speaking, voice.rtc

Si le P2P échoue, la solution de secours consiste en des trames binaires opus relayées par le serveur : un identifiant d'expéditeur de 16 octets suivi de la charge utile audio.

La voix est désactivé dans les jeux IA — le client de référence vérifie view.ai de la diffusion d’État et n’offre jamais la bascule.

Référence: voice.md.

9. Notes et classement

Les clients du jeu ne soumettent jamais de score. Lorsqu'une partie se termine, le scénario retours eloUpdates et le plate-forme les publie dans le classement du jeu. Les clients ne peuvent jamais écrire directement des entrées dans le classement ; le serveur doit également valider le gameplay derrière ses mises à jour de notation.

Le côté client est donc trivial : lisez les entrées (§4) et restituez-les, comme le fait l'implémentation de référence. Voir leaderboards.md.

10. Rediffusions

Un jeu qui déclare replays: true dans son script chaque session terminée est conservée par la plateforme ; les clients le récupèrent et le restituent simplement. Vérifier replaysEnabled sur GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94 avant d'offrir l'écran - un opérateur peut répondre d'un jeu dans un sens ou dans l'autre, et les points de terminaison ci-dessous reviennent 404 lorsque les rediffusions sont désactivées. Dans l'implémentation de référence, la récupération est App.loadReplays / App.openReplay dans app.js:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/mine?limit=10
GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/{sessionId}

Une charge utile de relecture (affichée avec la forme du résultat de l'exemple d'échecs) :

{
  "sessionId": "<guid>",
  "players": [ /* ... */ ],
  "finishedAt": "…",
  "result": {
    "kind": "win",
    "reason": "checkmate",
    "at": "…",
    "white": "<userId>",
    "black": "<userId>",
    "moveCount": 41,
    "eloBefore": { "white": 1420, "black": 1388 },
    "eloAfter": { "white": 1436, "black": 1372 }
  },
  "state": { "game": { "moves": [ /* ... */ ] } }
}

Les étapes du spectateur state.game.moves à travers le partage chessRules moteur localement - le même server.js fichier de règles, exécuté dans le navigateur — les rediffusions ne nécessitent donc aucun aller-retour du serveur ; conserver la version des règles utilisée pour une correspondance archivée lorsque les règles changent. Il s'agit du deuxième résultat de la conception à un fichier et à deux rôles du §1, un modèle que tout jeu peut adopter avec son propre fichier de règles.

11. Profils des joueurs

Les clients du jeu résolvent les autres joueurs via les points de terminaison du profil public. Dans l'implémentation de référence, App.profileFor dans app.js:

GET /api/v1/users/{id}/profile  → { "id": "…", "username": "…", "nickname": "…" }
GET /api/v1/users/{id}/avatar   → image/png, or 404

Deux règles d'interface utilisateur que le client de référence suit :

  • Rendre surnoms, jamais de noms d'utilisateur.
  • Revenir à "Player " + id.slice(0, 8) lorsqu'un profil manque ou qu'un pseudo est vide.

Référence: profile.md.

12. Les adversaires de l’IA s’entraînent

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai (illustré avec l'exemple de slug) crée une session où la plate-forme signale un siège ai: true dans createSession. Le script lui-même joue ce rôle – le comportement de l’IA est quelque chose que définit votre propre script. Dans l'exemple des échecs, le siège est joué par "hal", un moteur gourmand de capture de matériaux qui répond dans la même invocation qui traite le mouvement de l'humain.

Le script du jeu décide si la pratique modifie la note du joueur humain. Le siège AI ne peut pas recevoir des écritures sur l'état du joueur, la note ou les réalisations du compte. Conservez toutes les statistiques de l'IA en état de session.

13. Ce que le jeu de référence n'utilise PAS

L'implémentation de référence des échecs ne touche à aucun de ces éléments, mais ils sont tous disponibles pour les jeux qui en ont besoin :

  • Réalisations — n'importe quel jeu avec un server= le script peut les déclarer (game.achievements) et leur accordez l'autorité du serveur à partir de n'importe quel hook de cycle de vie ; les échecs ne le font tout simplement pas. Les titres de catalogue ont un chemin distinct revendiqué par le client : achievements.md, game-scripts.md.
  • Catalogue / droits — pour les jeux distribués et vendus par l'intermédiaire du catalogue : catalog.md.
  • Relais — le canal de relais haute fréquence pour les jeux rapides en temps réel où l'aller-retour du script par commande est trop lent : relay.md.
  • Bibliothèques externes — liaison des bibliothèques de jeux Steam, Epic ou GOG : external-libraries.md.

L'exemple des échecs, un jeu de société au tour par tour, n'a besoin d'aucun d'entre eux. Si votre jeu est en temps réel, distribué par catalogue ou nécessite des charges utiles binaires, ces pages sont l'endroit où chercher ensuite.

14. Liste de contrôle d'intégration

  • [ ] Ajouter un starhermit.txt manifeste (name, launch, owner, server; facultatif cover= pour la vignette bibliothèque).
  • [ ] Lire #game_token du hachage de l'URL une fois, puis supprimez-le avec history.replaceState.
  • [ ] Décoder le JWT pour sub (ID utilisateur) et game_scope (slug) – ne codez jamais en dur votre slug.
  • [ ] Créez tous les chemins d'API en tant qu'URL relatives de même origine : /api/v1/games/<slug> + suffixe.
  • [ ] Actualisez le jeton de lancement toutes les 45 minutes via POST …/launch-token.
  • [ ] Utilisez le cmd / sync Modèle WebSocket : enveloppez tout, synchronisez à chaque ouverture, reconnectez-vous avec un intervalle de 1 s à 30 s.
  • [ ] Concevez les commandes et les diffusions de votre script comme le contrat client — le client restitue des diffusions et envoie des commandes, rien de plus.
  • [ ] Renvoie un objet récapitulatif { turnPlayerId, deadline, status, moveCount } afin que la liste des sessions puisse indiquer à qui appartient le tour.
  • [ ] Terminez les parties en renvoyant un result - cette valeur de retour est ce qui alimente à la fois les replays et l'elo.
  • [ ] Déclarer replays: true dans votre script si vous souhaitez conserver les sessions terminées, et branchez l'interface utilisateur de relecture sur replaysEnabled.

La plate-forme fournit l'authentification, les sessions, la mise en relation et le stockage ; votre script fournit le règles du jeu. Commencez par le démarrage rapide du navigateur pour un premier téléchargement complet.
