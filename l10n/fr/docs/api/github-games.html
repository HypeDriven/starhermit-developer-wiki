Jeux GitHub

Publier un jeu depuis un dépôt GitHub sur ÉtoileErmite, ou enregistrez un jeu Web déjà hébergé. Pour les jeux de référentiel, la plateforme lit starhermit.txt, clone le dépôt et le sert à <slug>.starhermit.com. Parce que /api et /ws sont proxy de même origine à partir de ce sous-domaine, un jeu hébergé sur une plateforme a besoin pas de configuration CORS ou base API. Un commit épinglé contrôle quelle version du référentiel est active. Le implémentation de référence d'échecs est publié de cette manière et sert d'exemple de référence du modèle.

URL de base : https://api.starhermit.com. Tous les itinéraires sont sous api/v1/... et nécessitent un JWT, sauf indication contraire.

Les fichiers clients hébergés peuvent déclarer durées de vie du cache des dossiers et origines CORS supplémentaires dans starhermit.txt. Ces politiques sont publiées avec les fichiers clients ; une fusion sans manifeste conserve paramètres existants, tandis qu'un manifeste fourni les remplace.

Le manifeste : starhermit.txt

Lieu starhermit.txt à la racine du dépôt. Format: key=value des lignes, # commence un commentaire.

name=Your Game
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html        # repo-relative HTML entry
cover=art/cover.png      # optional cover art for the library tile; or an https:// URL
description=One-line pitch\nSecond line   # optional; or description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md          # optional; or release_notes=inline text
owner=<starhermit user id>  # UUID from GET /api/v1/me; do not use username/nickname
# Choose at most one authoritative backend, or omit both for a browser-only game:
server=server.js         # sandboxed JavaScript; see game-scripts.md
# container.image=ghcr.io/owner/game@sha256:<64 lowercase hex>; see container-games.md

control.up=KeyW+ArrowUp | Move forward
control.shoot=Space | Shoot
  • Il n'y a pas slug clé : la plateforme attribue un uid et l'utilise à la fois comme sous-domaine (<uid>.starhermit.com) et l'espace de noms de l'API du jeu (/api/v1/games/<uid>/…).
  • cover (alias cover_art, coverart) est l'illustration affichée sur la vignette de la bibliothèque du jeu : un chemin relatif au fichier de lancement, ou un chemin absolu https:// URL. Facultatif : sans cela, la vignette affiche le favicon de votre site. Relisez à chaque déploiement, donc changer la ligne change la couverture. Voir Couverture pour les cultures de tuiles.
  • description / release_notes (ou description.file / release_notes.file, qui nomme un .md/.markdown/.txt fichier relatif au manifeste) sont des textes facultatifs pour votre jeu. Ils sont relus à chaque déploiement comme cover. Voir Description et notes de version.
  • server déclare un backend JavaScript en bac à sable ; voir game-scripts.md.
  • container.image déclare un backend de conteneur ; voir container-games.md. Il doit être épinglé par résumé, hébergé dans l'espace de noms du propriétaire GitHub vérifié sur un registre sur liste autorisée et peut être accompagné de container.port, container.health, container.memory_mb, container.cpu, et non secret container.env.* valeurs.
  • Les deux clés backend sont facultatives pour un jeu par navigateur pur, mais elles s’excluent mutuellement.

Liaisons de contrôle par défaut

Un jeu peut déclarer zéro ou plusieurs actions sur le navigateur de bureau :

control.<action>=<code>[+<code>...][ | <label>]
  • Les actions sont en minuscules [a-z0-9_]{1,32} identifiants et conserver l’ordre manifeste.
  • Les codes sont KeyboardEvent.code valeurs; + sépare les touches alternatives pour une action.
  • L’étiquette facultative est affichée dans les interfaces utilisateur de remappage des contrôles et correspond par défaut à l’ID d’action.
  • Un manifeste peut déclarer jusqu'à 32 actions et 4 codes par action. Un code ne peut pas être utilisé par deux actions. Les lignes de contrôle invalides sont ignorées.
  • Jeux sans control.* les déclarations n'ont pas de contrôles API/UI (404 "This game declares no controls."). Les déclarations sont relues à partir de chaque build publié - chaque déploiement, téléchargement de dossier et remplacement du bundle push. Pas à pas: Tutoriel : ajouter des contrôles à votre jeu.

Les joueurs peuvent remplacer ces valeurs par défaut par jeu via le API de contrôle des jeux.

Enregistrez un jeu

POST /api/v1/me/github-games

{
  "repoUrl": "https://github.com/HypeDriven/starhermit-chess",
  "displayName": "StarHermit Chess",
  "launchPath": "index.html"
}

Malgré son nom historique, repoUrl accepte trois sources de lancement :

  1. A github.com/<owner>/<repo> dépôt. Le backend lit son manifeste et peut le déployer à l'hébergement StarHermit.
  2. Une URL de pages GitHub déjà hébergée telle que https://owner.github.io/game/. Référentiel l'identité est déduite de l'URL ; l'URL elle-même est lancée, sans clonage ni installation.
  3. Tout autre public http:// ou https:// URL du jeu Web hébergé. Il est lancé directement et ne participe pas à la revendication de propriété de GitHub.
  • displayName et launchPath sont des solutions de secours facultatives. Ils sont utiles pour un dépôt tiers sans métadonnées de manifeste fiables ; une URL hébergée directement est elle-même l'emplacement de lancement.
  • Pour les propriétaires de référentiels vérifiés, la plateforme valide starhermit.txt.
  • Un facultatif server= script ou container.image= le backend fournit un jeu faisant autorité ; voir game-scripts.md et container-games.md. L'hébergement de conteneurs est ouvert à tout utilisateur connecté sur starhermit.com ; un déploiement auto-hébergé peut le restreindre à une liste verte d'opérateur.
  • Un backend de serveur déclaré a besoin d’un propriétaire avéré. Soumettre un dépôt qui déclare server= ou container.image= sans connexion GitHub ou owner= la preuve est 403 (nommant les deux preuves), pas une liste réservée au navigateur qui prétend avoir un backend.
  • Limites : 100 jeux par utilisateur (pouvant être remplacés par l'opérateur par compte). Enregistrer une déclaration en double 409.

Les statuts d’inscription/déploiement incluent : InvalidUrl, LimitReached, Duplicate, MissingManualMetadata, MissingStarhermitTxt, InvalidLaunchPath, InvalidServerScriptPath, InvalidContainerImage, ServerProvisionConflict, RemovedByOwner.

Les erreurs utilisent la forme standard :

{ "error": "..." }

Ajouter un jeu à partir d'un dossier local

POST /api/v1/me/github-games/upload → 201

La contrepartie de l'enregistrement d'une URL : il n'y a pas de référentiel, et rien n'est cloné. Le dossier voyage comme un seul .tar.gz sur le corps de la requête et la plateforme héberge ce qu'elle contient. Mêmes archives formater comme pousser un paquet, donc le même emballage fonctionne pour les deux.

Le jeu créé a un gameSlug dès le départ, qu'il déclare ou non un serveur, donc un le téléchargement via un navigateur uniquement peut utiliser contrôles, paramètres par joueur, c'est emplacement de sauvegarde dans le cloud, salles en temps réel et lancez des jetons comme n'importe quel autre jeu.

client/           the game's files, published as-is
starhermit.txt    name= and launch= instead of the query parameters

Le manifeste est facultatif pour ce point final — les paramètres de requête peuvent fournir les mêmes valeurs — et les clients StarHermit en envoient toujours un, construit à partir de leurs champs manifestes. Envoi du fichier à l'intérieur votre build vaut toujours la peine d'être fait : il rend le build auto-descriptif et préremplit ces champs, donc il peut être re-téléchargé sans se souvenir des valeurs dont il avait besoin. Voir Le starhermit.txt manifeste pour le format, et notez que tout à côté du manifeste est téléchargé - téléchargez une version distribuable, pas une arborescence source.

Envoyez les octets directement - et non les données de formulaire en plusieurs parties - avec Content-Type: application/gzip:

tar -czf game.tar.gz client/ starhermit.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/upload?displayName=My%20Game" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game.tar.gz

{
  "game": { "id": "...", "displayName": "My Game", "launchPath": "index.html", "hosting": { "hostingEnabled": true } },
  "bytesReceived": 4194304
}

Les métadonnées sont résolues dans cet ordre, de sorte que la plupart des dossiers n'ont besoin d'aucun paramètre de requête :

  1. ?displayName= / ?launchPath= sur la demande.
  2. name= / launch= dans un starhermit.txt à la racine de l'archive.
  3. index.html à la racine de client/ - utilisé comme chemin de lancement lorsque rien d'autre n'en nomme un.

Notes spécifiques à cet itinéraire :

  • Le jeu est en direct dès le retour de l'appel. Il n'y a pas d'hébergement ou de déploiement séparé étape : deployStatus est live et deployedCommitSha est null, car il n'y a pas de commit.
  • Les fichiers ne peuvent pas être régénérés, de sorte que la plateforme ne les redéploye jamais de n'importe où. Un jeu ajouté de cette façon porte contentSource: upload et conserve sa version téléchargée jusqu'à ce que vous la publiiez un autre. Poussez une nouvelle build avec le point de terminaison du bundle ou téléchargez à nouveau le dossier.
  • Aucun référentiel ne signifie aucune réclamation. ownerLogin est vide, donc aucune connexion GitHub ne pourra jamais lui correspondre ; repoUrl porte un synthétique upload:<id> valeur plutôt qu’une URL.
  • A server/image.tar est refusé ici (422). Une image de serveur a besoin d'un jeu provisionné pour attacher à, qui n'existe pas jusqu'à ce que le jeu existe - créez d'abord le jeu, puis poussez l'image à /{id}/bundle.
  • Un chemin de lancement nommant un fichier que l'archive ne contient pas est refusé (422) pendant le téléchargement encore en mise en scène, plutôt que de devenir un 404 pour chaque joueur.

Les limites sont les mêmes que pour tout autre push : voir Limites de téléchargement.

Un dossier téléchargé peut apporter son propre backend de serveur

Si les archives starhermit.txt déclare la logique du serveur, le téléchargement le provisionne également - la même chose que le flux du référentiel, sans référentiel. Choisissez-en un style; déclarer les deux est refusé.

Déclaration Ce qui se produit
server=path/to/server.js Un backend de script. Le dossier voyage dans le dossier que vous téléchargez, donc sa source est lue directement à partir de l'archive — il n'y a rien à récupérer. Voir game-scripts.md.
container.image=name@sha256:… Un backend de conteneur, épinglé comme toujours. Voir container-games.md. L'image elle-même est ensuite poussée vers /{id}/bundle.

Les refus ici échouent à l'ensemble de la création - aucune ligne de jeu à moitié créée ne survit :

  • server= nommer un fichier que l’archive ne contient pas.
  • server= pointant en dehors des fichiers clients (../).
  • Déclarer les deux server= et container.image=.
  • Demander un conteneur où les conteneurs sont désactivés, ou à un propriétaire non approuvé pour eux.

Couverture

L'image affichée sur la vignette de votre jeu dans la bibliothèque. Réglez-le dans un sens ou dans l'autre : quelle que soit celle que vous utilisez, le anonyme GET /api/v1/github-games/{id}/cover voilà à quoi ça sert :

  • Dans votre construction — a cover= ligne d'entrée starhermit.txt, nommant une image par rapport au lancement fichier ou un absolu https:// URL. Relisez à chaque déploiement pour que votre référentiel reste la source de vérité.
  • Téléchargé — PUT /api/v1/me/github-games/{id}/cover avec l’image codée en base64. C'est qu'est-ce que le tableau de bord Web Gérer → Couverture ce que fait et ce qu'un opérateur StarHermit peut faire pour vous.
PUT /api/v1/me/github-games/{id}/cover
Authorization: Bearer <token>
Content-Type: application/json

{ "imageBase64": "iVBORw0KGgoAAAANSUhEUg..." }

Un téléchargement remplacements le manifeste, délibérément : un déploiement qui relit starhermit.txt doit ne défait jamais l’art que quelqu’un a choisi à la main. DELETE /api/v1/me/github-games/{id}/cover est le chemin du retour — il supprime le téléchargement et le manifeste cover= s'applique à nouveau.

PNG, JPEG, GIF, WEBP, BMP ou SVG, jusqu'à 4 Mo. Le type est reniflé à partir des octets, donc un Content-Type vous affirmez que ce n'est ni nécessaire ni cru, et les octets qui ne sont pas une image décodable sont refusés avec 400. Un parent cover= le chemin doit se terminer par .png, .jpg/.jpeg, .gif, .webp ou .svg (Non .., pas de leader /); une valeur inutilisable est supprimée plutôt que d'échouer le jeu.

La pochette est une affiche : les deux bibliothèques redimensionnez-le pour remplir la tuile et recadrez-le au centre quoi qu'il arrive pas adapté. Les carreaux n'ont pas la même forme.

Surface Tuile Recadrer
Client Windows Portrait 96×128 (3:4) Remplit le portrait ; l'art au sens large perd ses côtés
Tableau de bord Web Carré Remplit le carré ; l'art plus grand perd le haut et le bas

Gardez le sujet au centre pour que les deux recadrages soient corrects. Les couvertures SVG s'affichent sur la bibliothèque Web ; le Le client Windows ne peut pas décoder le SVG, de sorte que la vignette affiche le favicon à la place. Un jeu sans couverture à tout revient à son favicon (GET /api/v1/github-games/{id}/icon). L'icône est résolue à partir du URL que vous avez soumise et, lorsque la plateforme héberge le jeu, à partir de la copie sur laquelle elle est diffusée <uid>.starhermit.com - donc un bundle téléchargé avec un favicon dans ses fichiers reçoit toujours une icône.

Chiffres d'audience de votre jeu

GET /api/v1/me/github-games/{id}/stats → GameStatsDto

Combien de personnes jouent à un jeu tu as ajouté. Réservé au propriétaire du jeu – n'importe qui d'autre obtient 404, la même réponse qu'un jeu qui n'existe pas.

{
  "totalPlayers": 42,
  "playingNow": 3,
  "totalSessions": 130,
  "totalPlaytimeMinutes": 8140,
  "lastPlayedAt": "2026-07-29T08:45:24Z",
  "livenessWindowHours": 4
}
  • Agrégat uniquement. Vous apprenez la taille de votre public, jamais qui en fait partie.
  • totalPlayers compte personnes distinctes, pas des sessions - quelqu'un qui a joué six fois en est un joueur.
  • playingNow compte les joueurs distincts dont la session n'est pas terminée et a commencé à l'intérieur livenessWindowHours. La fenêtre compte : un client qui tombe en panne ou perd son réseau n'envoie jamais la session se termine, et sans cela, ces lignes se liraient comme des personnes jouant encore indéfiniment.
  • totalPlaytimeMinutes compte séances terminées uniquement, correspondant aux chiffres de temps de lecture par utilisateur dans activity.md. Une séance en vol n'apporte encore rien.
  • lastPlayedAt est null pour un jeu auquel personne n'a joué.

Les chiffres proviennent du même grand livre de lancement que chaque client écrit (voir activity.md), donc un un jeu dont les joueurs ne signalent jamais les lancements sera lu comme zéro.

Revendiquer la propriété

POST /api/v1/me/github-games/{id}/claim → GitHubGameDto

Reprenez une liste existante lorsque vous contrôlez son référentiel. Prouvez la propriété soit en reliant le connexion GitHub personnelle correspondant au propriétaire du référentiel, ou en s'engageant owner=<your StarHermit user ID> au référentiel starhermit.txt. owner devrait être le UUID immuable renvoyé sous la forme id par GET /api/v1/me, pas un nom d'utilisateur ou un pseudo. Le manifeste la méthode prend en charge les référentiels appartenant à l'organisation, qui ne sont pas déduits de l'organisation GitHub personnelle adhésion.

En cas de succès, la fiche existante conserve son identifiant/historique, devient gérée par le demandeur, s'actualise Métadonnées et déclarations backend contrôlées par le référentiel, ainsi que l'hébergement des files d'attente lorsque cela est disponible. Le l'auteur de l'envoi précédent perd l'accès à la gestion limité au propriétaire. Revendiquer une annonce que vous gérez déjà le resynchronise plutôt que de renvoyer un conflit.

Magasins de métadonnées d'identité GitHub {"login":"…"}; liez votre compte GitHub via le flux OAuth (voir auth.md). Vérifiez l'état du lien avec GET /api/v1/me/github → { linked, login }. Voir le tutoriel de réclamation étape par étape pour la découverte, les deux preuves méthodes, validation, prise de contrôle et dépannage.

Transférer la propriété

Un transfert est un en attente d'offre que le destinataire accepte, pas un mouvement immédiat - un jeu (et son octets hébergés, qui comptent pour le destinataire) ne peuvent pas être transférés sur un autre compte sans leur dis-le.

POST /api/v1/me/github-games/{id}/transfer (propriétaire) enregistre l'offre et renvoie un GameTransferOfferDto; le jeu reste le vôtre jusqu'à ce qu'il soit accepté.

{ "toUserId": "<user id>" }

// GameTransferOfferDto
{
  "id": "<offer id>",
  "gameId": "<game id>",
  "gameTitle": "StarHermit Chess",
  "fromUserId": "<guid>", "fromUsername": "alice",
  "toUserId": "<guid>",   "toUsername": "bob",
  "status": "pending",
  "createdAt": "2026-10-17T16:00:00Z"
}
  • Le destinataire le voit sous GET /transfers/incoming et accepte avec POST /transfers/{offerId}/accept. L'acceptation fait bouger le jeu maintenant, vérifié à ce moment-là par rapport au nombre de parties et à l'allocation d'hébergement du destinataire - afin qu'une offre puisse être faite et toujours ne parviennent pas à atterrir si le destinataire est à sa limite. Ils pourraient plutôt POST /transfers/{offerId}/decline.
  • L'offrant voit ses offres en attente sous GET /transfers/outgoing et peut en retirer un avec POST /transfers/{offerId}/cancel.
  • Tout est revérifié à l'acceptation : un jeu déplacé, supprimé ou repointé depuis que l'offre répond GameUnavailable, et proposer à nouveau le même jeu remplace une offre toujours en attente, donc deux live les offres d'un jeu ne peuvent pas être acceptées toutes les deux.

Pousser un pack de jeux

POST /api/v1/me/github-games/{id}/bundle publie la sortie construite sans demander à StarHermit de le faire clonez-le à nouveau. L'appelant doit posséder le jeu enregistré. Envoyez le .tar.gz octets directement, pas données de formulaire en plusieurs parties – avec Content-Type: application/gzip:

client/            optional static client files; must include the registered launch file
server/image.tar   optional output from `docker save`
starhermit.txt     optional manifest copy for bundle portability
remove.txt         merge only: client-relative paths to delete, one per line

Au moins client/ ou server/image.tar doit être présent (une fusion peut également être uniquement remove.txt). Les fichiers clients sont échangés de manière atomique. Un L'image du serveur est chargée, épinglée par la plate-forme et met en file d'attente le déploiement du conteneur sur redémarrez sur cette image. Une image téléchargée est prioritaire sur la référence de registre du manifeste, et sur un server= doubler; un manifeste déclarant les deux server= et container.image= est refusé avant que quoi que ce soit soit chargé. Tout le reste dans l'archive est ignoré.

Le téléchargement d'une image est en soi la déclaration. Si le jeu n'a pas encore de serveur backend - un dossier téléchargé qui n'en a déclaré aucun - en poussant server/image.tar dispositions un du résumé juste chargé, sous le gameSlug le jeu l'a déjà fait. Vous n'êtes pas obligé de nommer une image épinglée dans un résumé dans un manifeste d'abord, qui était circulaire : il fallait que la définition existe avant de pouvoir recevoir une image, et l'image était la seule chose qui pouvait la décrire.

Une re-push applique les boutons du conteneur déclarés par son manifeste, et uniquement ceux-là. Inclure starhermit.txt dans le paquet avec un changé container.port, container.health, container.memory_mb ou container.cpu et le déploiement le récupère au redémarrage ; laissez un bouton dehors et il conserve tout ce que vous avez défini la dernière fois. Omettez entièrement le manifeste et rien sur le déploiement change sauf l'image.

Un paquet dont starhermit.txt porte un utilisable name= aussi renomme le listing du jeu à cela - la mise à jour du nom d’affichage accompagne la poussée. Partir name= out (ou omettre le manifeste) pour conserver le nom actuel.

Les clients StarHermit créent ce bundle pour vous, à partir d'un dossier ou un seul .tar:

  • Fichiers clients — le dossier de distribution du jeu, ou un .tar de celui-ci. Un dossier est placé sous client/; a .tarles entrées de y sont réhébergées (une archive déjà sous client/ est laissé seul). ustar uniquement — Les archives GNU avec nom long et PAX sont refusées, car les réhéberger signifie réécrire les blocs de métadonnées qui nomment l'entrée suivante.

Quel que soit le la construction choisie transporte les champs pré-remplis, et tout ce qu'ils contiennent est écrit à la racine du bundle - donc une version sans manifeste est publiable, et une version livrée en tant que .tar peut toujours avoir son manifeste mis à jour.

Mises à jour partielles : ?mode=merge

Une poussée est un remplacer sauf demande contraire de votre part : les archives contiennent l'intégralité du jeu, et tout ce qui n'y figure pas. c'est parti. ?mode=merge (HTTP et le socket de téléchargement) en font un correctif du client en direct fichiers - la réponse au rechargement de gigaoctets d'actifs inchangés pour un correctif d'un seul fichier.

printf '%s\n' '# one client-relative path per line; a directory removes everything under it' \
    'assets/old-music.ogg' 'levels/cut/' > remove.txt
tar czf patch.tar.gz client/index.html client/js/app.js remove.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/$GAME_ID/bundle?mode=merge" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @patch.tar.gz

Avec mode=merge:

  • fichiers sous client/ sont ajoutés ou écrasés
  • chemins dans une racine remove.txt (# commentaires; un répertoire supprime tout son sous-arbre) sont supprimés
  • tous les autres fichiers live restent exactement tels quels

L'arbre fusionné est mis en scène comme une copie et échangé de manière atomique : les joueurs voient l'ancien jeu ou le un tout nouveau, jamais un mélange. Le résultat est limité par le le jeu allocation, pas celle du téléchargement, donc un jeu ne peut pas dépasser sa limite, un petit patch à la fois. Une fusion concerne uniquement les fichiers clients ; un server/image.tar est chargé exactement comme lors d'un remplacement. Un patch portant non starhermit.txt feuilles la pochette telle qu'elle était.

Une fusion est refusée (409/422, rien ne change) lorsque le jeu n'a encore rien publié, lorsqu'il supprimerait le fichier de lancement, ou quand remove.txt points en dehors du jeu. UN remove.txt dans un le remplacement simple est également refusé (422), car là, cela ne peut signifier que quelque chose que vous n'avez pas l'intention. mode doit être replace (par défaut) ou merge; tout le reste est 400.

Le même paramètre fonctionne sur le socket : ws/v1/game-upload?gameId=…&mode=merge. Le ready cadre le fait écho comme "apply":"merge".

Le point de terminaison met à jour un jeu enregistré existant ; il ne crée jamais le record du jeu — pour cela, voir ajouter un jeu à partir d'un dossier local. Il peut fournir le jeu backend du serveur, comme effet secondaire du chargement d’une image de serveur dans un jeu qui n’en avait pas. Voir le tutoriel de publication sur serveur dédié.

Télécharger via un WebSocket

GET /ws/v1/game-upload (mise à niveau) - utilisez-le pour tout ce qui dépasse environ 100 Mo.

Le CDN devant l'API refuse un corps de requête HTTP en gros 100 Mo avec un 413 de son propre. Ce refus n’atteint jamais la plateforme, il ne porte donc aucune limitBytes et n'apparaît dans aucun journal sait lire — un 413 sans limitBytes le champ est le CDN, pas l'allocation de votre jeu, qui est de deux des ordres de grandeur plus grands. Tout réaliste docker save va le frapper.

Les trames envoyées après la mise à niveau de WebSocket ne constituent pas un corps de requête, le plafond ne s'applique donc pas. Seul le transport diffère. Les trames binaires se concatènent exactement en octets sur les routes HTTP lisez, passez par le même pipeline, et chaque corps de refus, d'autorisation et de réussite est celui du HTTP route aurait produit - afin qu'un client puisse partager un chemin de code entre les deux.

wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&mode=merge&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?displayName=My%20Game&launchPath=index.html&access_token=$TOKEN

Passer gameId pour pousser vers un jeu que vous possédez (le /{id}/bundle itinéraire); omettez-le et passez displayName/launchPath pour en créer un à partir d'un dossier (le /upload itinéraire). Le jeton va dans le chaîne de requête car un navigateur ne peut pas définir de Authorization en-tête sur une poignée de main WebSocket ; c'est vérifié une fois, lors de la poignée de main, donc un téléchargement qui survit à son jeton d'accès se termine toujours.

Direction Cadre Signification
serveur → {"type":"ready","mode":"bundle","apply":"replace","limitBytes":N,"heartbeatSeconds":15} Allocation réglée et espace libre vérifié. Commencez à envoyer. mode est bundle ou create. apply est merge lorsque vous avez demandé une mise à jour partielle.
→ serveur binaire Octets d'archives, répartis comme vous le souhaitez : le serveur ne réassemble jamais les messages, donc 256 Ko à 1 Mo est une bonne valeur par défaut. Concaténés, vos frames doivent être exactement les .tar.gz.
serveur → {"type":"ack","bytesReceived":N} Progression de la réception, environ tous les 8 Mo. Conduisez votre barre de progression à partir de là.
→ serveur {"type":"complete"} L'archive a été envoyée dans son intégralité.
→ serveur {"type":"abort"} Abandonner. Répondu avec status: 499; rien n'est publié.
serveur → {"type":"progress","phase":"publishing","bytesReceived":N} Battement de cœur toutes les 15 secondes pendant le téléchargement. Ignorez-les, mais attendez-vous à eux.
serveur → {"type":"result","status":200,...} Succès. Le reste de l'objet est le corps de la réponse HTTP textuellement (status est 201 pour une création).
serveur → {"type":"error","status":413,"error":"...","limitBytes":N} Refus. status et le corps sont ce à quoi la route HTTP aurait répondu.

Rien n'est publié avant {"type":"complete"} arrive. C'est le seul comportement sans HTTP équivalent, et c'est délibéré : le marqueur de fin d'archive vit à l'intérieur les octets d'un tar, donc le la plate-forme termine la lecture d'une archive complète sans que la connexion ne se termine jamais. Une prise qui a simplement été supprimé après le dernier octet serait autrement publié exactement comme celui qui s'est terminé - remplacer silencieusement un jeu en direct par un push abandonné. Fermeture du socket sans les téléchargements de cadres rien.

La publication après votre dernier octet peut prendre du temps, notamment pour une image serveur. Attendre progress le cœur bat pendant qu'il se termine ; ne considérez pas un intervalle calme comme un échec de téléchargement.

Limites de téléchargement

Toutes les routes de téléchargement (les points de terminaison HTTP et WebSocket) partagent les mêmes règles.

Limite Valeur
Allocation de disque par jeu 2 Go sur starhermit.com (l'allocation peut varier selon le jeu/déploiement)
Fichiers hébergés par compte 20 Go sur tous les jeux d'un compte (réglable par l'opérateur par compte)
Déploiement du référentiel 50 Mo archive
starhermit.txt / remove.txt 256 Ko chaque; remove.txt répertorie au plus 10 000 chemins (422)
Application appliqué en streaming, donc une poussée surdimensionnée est coupée en plein vol

Un téléchargement ou un push est interrompu ce qui reste de l'allocation d'hébergement du compte (413 avec limitBytes), et un déploiement de référentiel qui le réussirait échoue avec une raison nommant l'allocation. Par poussée et par jeu ont le même numéro lors d'un remplacement. Une fusion est limitée par le résultant taille du jeu, donc un petit patch qui ferait que l'arbre vivant dépasserait l'allocation est refusé.

Statut Signification
400 mode n'est ni l'un ni l'autre replace ni merge.
409 Une fusion avec un jeu qui n'a pas encore de fichiers publiés.
413 Au-dessus de l'allocation. Le corps porte { "error", "limitBytes" }. A 413 sans limitBytes est le plafond de corps d'environ 100 Mo du CDN, pas ceci - utiliser la socket de téléchargement.
422 Archive mal formée, ou contenu inutilisable (fichier de lancement manquant, non client/, a server/image.tar sur la route de création, une fusion qui supprimerait le fichier de lancement, remove.txt sur un remplacement). Aussi un tronqué archive - le résultat ordinaire d'une connexion interrompue en cours de téléchargement.
507 Le serveur n'a pas de place pour le moment. Refusé avant que le corps soit lu lorsque la capacité de publication n'est pas disponible ; réessayez plus tard.

Les archives ne peuvent pas échapper à leur racine ni contenir de liens, et seuls les fichiers et répertoires normaux sont extrait — les liens symboliques, les liens physiques et les nœuds de périphérique sont rejetés. git archive en-têtes globaux PAX, ./-noms préfixés de tar -czf game.tgz ., et les noms de fichiers qui contiennent simplement .. (sprite..png) sont acceptés. UN .. le segment de chemin est toujours refusé.

La soumission, la réclamation, la modification d'URL, l'hébergement et le déploiement atteignent tous GitHub sur le seul jeton de la plateforme, donc ensemble, ils sont limités à 10 requêtes par minute et par compte (429, avec Retry-After). Un l'opérateur peut l'augmenter pour un seul compte.

Publiez votre propre jeu : procédure pas à pas

Il existe deux itinéraires. Si votre jeu réside dans un référentiel git, suivez les étapes numérotées ci-dessous. S'il ne s'agit que d'un dossier sur votre ordinateur, un seul appel fait tout : ajouter un jeu à partir d'un dossier local enregistre le jeu, publie le fichiers, et le laisse en direct - pas de bascule d'hébergement ni de broche de validation, car il n'y a pas de référentiel pour piste.

  1. Choisissez une source : pousser un dépôt contenant starhermit.txt à la racine (en déclarant éventuellement soit un server.js script ou image de conteneur), ou préparez l'URL publique d'un jeu par navigateur déjà hébergé.
  2. Liez votre identité GitHub via le flux OAuth (voir auth.md); vérifier avec GET /api/v1/me/github.
  3. Enregistrez le jeu: POST /api/v1/me/github-games avec le référentiel ou l'URL du jeu hébergé dans repoUrl.
  4. Jeux de référentiel uniquement : activer l'hébergement: PUT /api/v1/me/github-games/{id}/hosting avec { "enabled": true }.
  5. Jeux de référentiel uniquement : épinglez un commit: PUT /api/v1/me/github-games/{id}/deployment avec { "commit": "<sha>" }. Le commit épinglé contrôle la version live.
  6. Les joueurs lancent le jeu: un jeu de référentiel déployé est servi à <slug>.starhermit.com; un jeu hébergé directement ouvre son URL soumise. Chaque jeu avec un gameSlug - backend ou non - reçoit un jeton de lancement de POST /api/v1/games/<slug>/launch-token dans le fragment d'URL (éventuellement avec &session_id=<guid> pour inviter des liens profonds).

Pour le contrat complet côté client (comment le jeu lit le jeton de lancement et communique avec l'API), consultez le procédure pas à pas d'échecs de l’implémentation de référence.
