API de jeux

Le sous-système de jeux est au cœur de StarHermit : des jeux multijoueurs faisant autorité sur le serveur dont les règles s'exécutent soit dans un fichier JavaScript en bac à sable, soit dans un conteneur fourni par le développeur. Les deux environnements d'exécution partagent cette API REST destinée aux joueurs (api/v1/games/{slug}) et le gameplay WebSocket (ws/v1/games). Pour la création de serveur, voir Scripts de jeu ou Serveurs de jeux hébergés par des conteneurs. Pour un exemple complet d'exécution de script, consultez le Procédure pas à pas des échecs et HypeDriven/starhermit-échecs.

URL de base : https://api.starhermit.com.

Les points de terminaison des joueurs nécessitent une authentification et fonctionnent à la fois avec des jetons d'utilisateur complets et avec un lancement à l'échelle du jeu. jetons. Les deux /server/... les points de terminaison sont réservés aux conteneurs : la réconciliation de session utilise un jeton du porteur du serveur, tandis que le renouvellement du jeton utilise la clé d'actualisation du déploiement.

Quoi {slug} est

Le slug d'un jeu est son uide — la même valeur que son <uid>.starhermit.com adresse, par ex. 83fd04b1-3cbe-4b09-a251-3733ad4b9d94. Il est dérivé de l'identifiant immuable du jeu et rien peut le régler: pas starhermit.txt, pas le nom du dépôt, pas un opérateur. Un nom qu'un développeur pourrait choisir serait quelque chose pour lequel deux jeux pourraient se battre, et aurait besoin de la plate-forme pour arbitrer qui je l'ai compris ; un uid ne peut ni entrer en collision ni être demandé.

Un slug n'est pas un backend de serveur. Chaque jeu ajouté à partir d'un dossier local et chaque jeu du référentiel un propriétaire vérifié ajouté, en possède un – avec ou sans server= ou container.image= - parce que c'est l'adresse de la surface du jeu face au joueur : lancer des jetons, contrôles, paramètres, c'est emplacement de sauvegarde dans le cloud et chambres. Un Le jeu sur navigateur uniquement en a besoin autant que tout autre. Les seuls jeux sans slug sont le référentiel soumissions dont le propriétaire n'est pas vérifié (gameSlug est null dans GET /api/v1/me/github-games).

Les points de terminaison concernant le serveur d'un jeu : informations sur le jeu, réalisations, sessions, matchmaking, invitations, rediffusions - besoin d'un backend. GET /api/v1/games/{slug} réponses 404 pour un jeu qui a une limace et non backend, qui est le moyen de distinguer les deux.

Ne le codez pas en dur. Lisez-le à partir du jeton de lancement game_scope réclamation, ou — pour un jeu par navigateur hébergé sur plateforme — à partir de location.hostname, puisque le sous-domaine est l'uid.

Informations sur le jeu

GET /api/v1/games/{slug}

Renvoie la définition du jeu ainsi que les statistiques de l'appelant pour ce jeu. 404 si aucun jeu de ce type n'existe, ou si le jeu est uniquement disponible sur navigateur (il a un slug mais pas de serveur backend).

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "name": "Chess",
  "enabled": true,
  "leaderboardId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "maxConcurrentSessionsPerPlayer": 20,
  "replaysEnabled": true,
  "buildId": "s12",
  "me": {
    "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "elo": 1200,
    "wins": 4,
    "losses": 2,
    "draws": 1,
    "activeSessionCount": 2
  }
}
  • leaderboardId est facultatif.
  • me.elo par défaut 1200; wins/losses/draws sont lus à partir du document par joueur appartenant au runtime du serveur.
  • replaysEnabled indique si les sessions terminées de ce jeu sont conservées - lisez-le plutôt que de supposer, et masquez votre interface de relecture lorsqu'elle est false. Voir Rediffusions.
  • buildId nomme la logique du serveur servant actuellement le jeu (s + version script, ou c + préfixe de résumé d'image). Renvoyez-le comme ws/v1/games?build=… donc un client obsolète est refusé avec 409 {"error":"build_mismatch"} avant d'agir sur les champs déplacés. Omettre build se connecte comme avant.

Jetons de lancement

POST /api/v1/games/{slug}/launch-token

Crée un JWT à l'échelle du jeu (durée de vie par défaut 60 minutes) transportant game_scope={slug} et aucune demande d'autorisation. Un jeton étendu peut recréer un jeton pour son propre jeu — c'est le modèle d'actualisation du client — mais le renouvellement est limité par launch_chain (par défaut 12 heures à partir de la session utilisateur d'origine). Au-delà de ce plafond, le renouvellement est 403. Les clients doivent s'actualiser avant l'expiration du jeton ; le client de référence d'échecs, par exemple, s'actualise toutes les 45 minutes. Renouvelez également avant de reconnecter une prise - voir GameplayWebSocket.

{
  "token": "eyJhbGciOi...",
  "expiresInSeconds": 3600
}

Réalisations

GET /api/v1/games/{slug}/achievements

Chaque réalisation déclarée par le backend faisant autorité du jeu, avec l'état de déverrouillage de l'appelant. Secret les réalisations restent cachées jusqu'à ce que l'appelant les déverrouille. Accepte un JWT utilisateur complet ou un jeu à l'échelle du jeu jeton de lancement. 404 lorsque la limace n'a pas de définition de jeu faisant autorité.

[
  {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "key": "first-win",
    "name": "First Win",
    "description": "Win a match.",
    "icon": null,
    "secret": false,
    "points": 10,
    "unlocked": true,
    "unlockedAt": "2026-07-25T09:14:02Z"
  }
]

Les réalisations du jeu sont serveur faisant autorité: seul le script ou le conteneur du jeu les accorde, et le client a réclamé POST /api/v1/me/achievements/unlock le point final les refuse. Déblocages en direct arrive sur la socket de gameplay comme {"type":"achievement"} cadres. Les contrats complets sont en cours Réalisations, Scripts de jeu, et Serveurs de jeux de conteneurs.

GET /api/v1/games/{slug}/linked-achievements/{otherSlug}

Celui de l'appelant se déverrouille un autre jeu, afin que ce jeu puisse ouvrir des fonctionnalités basées sur eux. Travaux avec le jeton de lancement de ce jeu. Voir Réalisations — Réalisations d'autres jeux.

Liaisons de contrôle par joueur

Les jeux peuvent déclarer les contrôles du navigateur de bureau avec control.* entrées dans starhermit.txt. L'API des contrôles stocke un remplacement séparé pour chaque utilisateur et jeu. Les JWT utilisateur complet et les jetons de lancement à l'échelle du jeu sont accepté; un jeton de lancement game_scope doit correspondre {slug}.

GET /api/v1/games/{slug}/controls

Renvoie les liaisons effectives dans l’ordre manifeste. codes contient le remplacement de l'utilisateur lorsque il y en a un, sinon defaultCodes. Retours 404 "This game declares no controls." quand le constructions en direct starhermit.txt n'a pas de validité control.* line - déclarez-les et publiez un build ; voir Tutoriel : ajouter des contrôles à votre jeu.

{
  "actions": [
    {
      "action": "up",
      "label": "Run forward",
      "defaultCodes": ["KeyW", "ArrowUp"],
      "codes": ["KeyW", "ArrowUp"]
    },
    {
      "action": "shoot",
      "label": "Shoot",
      "defaultCodes": ["Space"],
      "codes": ["KeyJ"]
    }
  ]
}

PUT /api/v1/games/{slug}/controls

Remplace les remplacements de l'appelant. Le bindings l'objet peut contenir un sous-ensemble de l'objet déclaré actes ; les actions omises continuent d'utiliser leurs valeurs par défaut.

{
  "bindings": {
    "up": ["KeyW", "ArrowUp"],
    "shoot": ["KeyJ"]
  }
}

Chaque action doit être déclarée par le jeu. Chaque action doit avoir 1 à 4 valides KeyboardEvent.code valeurs, et aucun code ne peut être attribué à deux actions dans le résultat carte efficace. Retour d'actions, de codes ou de conflits non valides 400.

DELETE /api/v1/games/{slug}/controls

Supprime tous les remplacements de l'appelant et restaure les valeurs par défaut du manifeste. Retours 204. Les écritures du jeton de lancement sont intentionnelles, donc un jeu hébergé peut fournir son propre écran de reliure.

Paramètres de jeu par joueur

Où se trouve votre jeu ses propres options pour un lecteur — volume principal, détails graphiques, sous-titres taille, caméra préférée, dernier chargement choisi – afin qu'ils suivent ce joueur sur n'importe quelle machine à laquelle ils se connectent de. Un magasin de clé/valeur limité à un joueur et à un jeu. Pour une section Langue à côté des graphiques, Audio et commandes, voir localisez votre jeu et ajoutez des paramètres de langue.

Rien ne déclare un schéma. La plateforme stocke vos clés et vos valeurs et ne les lit jamais, vous ajoutez donc une option en l'écrivant : pas d'entrée de manifeste, pas de redéploiement, pas de version de plateforme. Cela aussi signifie que la plateforme ne peut pas les valider pour vous — une faute de frappe dans un nom de clé est un nouveau paramètre, pas un erreur.

Comme l'API de contrôle, un jeton de lancement à l'échelle du jeu est accepté (son game_scope doit correspondre {slug}), Ainsi, un écran d'options dans le jeu ne fonctionne qu'avec le jeton que le jeu détient déjà. Contrairement à contrôles, aucune déclaration manifeste n'est nécessaire : chaque jeu dispose d'un stockage de paramètres à partir du moment où il existe, y compris un jeu sur navigateur uniquement sans aucune logique de serveur.

Choisissez le bon magasin — le cloud enregistre maintenir la progression (une archive opaque par titre, 10 Mo, accessible également avec le jeton de lancement), et l'état du lecteur d'un backend de script ou de conteneur fait autorité sur le serveur et n'est pas accessible en écriture à partir d'un cliente. Les paramètres sont les petites préférences intermédiaires appartenant au client.

GET /api/v1/games/{slug}/settings

Tout ce que l'appelant a stocké pour ce jeu. settings est vide pour un joueur qui n'a jamais sauvegardé n'importe quoi - c'est un 200, pas un 404. Les clés reviennent triées.

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "settings": {
    "audio.master": 0.8,
    "graphics.detail": "ultra",
    "graphics.options": { "shadows": true, "msaa": 4 }
  },
  "count": 3,
  "bytes": 118,
  "updatedAt": "2026-08-07T15:04:11Z",
  "limits": { "maxKeys": 200, "maxKeyLength": 128, "maxTotalBytes": 2097152, "maxAccountBytes": 67108864 }
}

bytes est ce que coûtent actuellement les paramètres de ce joueur limits.maxTotalBytes. Lire le limites plutôt que de les coder en dur : l'allocation est un paramètre de l'opérateur, et un jeu peut être accordé le sien. maxKeys (200 par défaut) peut également être défini par jeu, et maxAccountBytes limite un paramètres du compte pour chaque jeu (64 Mo par défaut).

PUT /api/v1/games/{slug}/settings

Remplace toute la carte. Les clés que le corps omet sont supprimées — envoyez tout, ou utilisez PATCH.

{ "settings": { "audio.master": 0.8, "graphics.detail": "ultra" } }

Un vide settings L'objet efface les paramètres du jeu pour l'appelant. Renvoie la même forme que GET.

PATCH /api/v1/games/{slug}/settings

Fusionne avec ce qui est stocké, laissant les clés qu'il ne mentionne pas seules. UN null valeur supprime c'est clé. Cela fusionne les clés de configuration de niveau supérieur ; une valeur d'objet remplace la valeur entière à sa clé, y compris ses propriétés imbriquées. C'est ce qu'un L'écran d'options devrait utiliser - il peut enregistrer le curseur qui s'est déplacé sans première lecture et réécrire tout le reste.

{ "settings": { "audio.music": 0.25, "graphics.options": null } }

GET / PUT / DELETE /api/v1/games/{slug}/settings/{key}

Un réglage à la fois. GET retours { "key", "value", "updatedAt" }, ou 404 si l'appelant a Je ne l'ai jamais stocké. PUT prend { "value": <any JSON> } et stocke la valeur textuellement — y compris un explicite null, qui est ici une valeur comme une autre, pas une suppression. DELETE retours 204, et supprimer quelque chose qui n'existe pas est un non-opération plutôt qu'une erreur.

curl -X PUT "https://api.starhermit.com/api/v1/games/$SLUG/settings/audio.master" \
  -H "Authorization: Bearer $LAUNCH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"value": 0.35}'

Règles

Règle Valeur
Définition des noms 1 à 128 caractères de A-Z a-z 0-9 . _ - : — espace de noms librement (audio.master, graphics:shadows)
Valeurs N'importe quel JSON : nombre, chaîne, booléen, tableau, objet, null
Paramètres par joueur, par jeu 200
Octets par joueur, par jeu 2 Mo par défaut — un opérateur peut l'augmenter ou le diminuer et peut accorder à un jeu une allocation différente

Un seul paramètre peut utiliser la totalité de l'allocation d'octets ; il n’y a pas de plafond distinct plus petit par valeur.

Statut Signification
400 Mauvais nom de paramètre ou corps qui ne l'est pas {"settings": {...}} / {"value": ...}
404 Aucun jeu ne répond à cette balle, ou (une seule touche GET) rien n'est stocké sous cette clé
413 Au-delà de l'allocation : soit trop de paramètres, soit trop d'octets. Le message indique la limite

Un lot contenant une mauvaise clé n’écrit aucune des bonnes clés. Les paramètres sont par joueur et par game : rien ne fuit entre deux joueurs, ni entre deux parties d'un même joueur. Ils survivent à un le jeu est désactivé ou supprimé de la liste, car il s'agit des données du joueur plutôt que de celles du jeu.

Séances

GET /api/v1/games/{slug}/sessions/mine

Sessions actives de l'appelant pour ce jeu. myTurn et deadline sont analysés à partir de l'état du script summary objet (voir Scripts de jeu). pausedAt est réglé alors qu'un persistant la session est interrompue et personne n'y participe, et null sinon.

Les séances en salle sont incluses. A salle en temps réelLa session liée de répertorie tous les humains qui occupaient un siège au début de la salle, elle apparaît donc ici pour chacun d'eux pendant qu'elle est active. Les sièges AI ne sont pas disponibles players. Quitter la salle ou fermer la salle ne supprime personne de la session ; cette personne reste donc dans cette liste jusqu'à la fin de la session elle-même, sauf dans un cas particulier. participation en cours salle, où un joueur qui part cède son siège et est retiré de la séance, et un nouveau venu admis en cours de match y est ajouté. Il n'y a pas d'identifiant de salle dans la réponse : utilisez GET /api/v1/realtime/rooms/joined pour les chambres de l'appelant et correspondent à leurs gameSessionId contre sessionId.

Récupération et départ explicite

GET /api/v1/games/{slug}/sessions/{sessionId}/recovery renvoie un instantané, une restauration, valeurs de rétention et de transport. Les participants et le propriétaire du jeu peuvent le lire. Unités de temps et tout les champs de réponse sont décrits dans Cycle de vie et récupération des sessions.

POST /api/v1/games/{slug}/sessions/{sessionId}/leave abandonne son appartenance à un monde persistant sans salle en temps réel. Cela ne prend aucun corps et revient 204; le dernier départ humain met fin au monde. 403 signifie pas membre, 404 signifie pas de séance, 410 les moyens sont terminés, et 409 signifie un non persistant session ou une session limitée à la salle. Pour une session limitée à la salle, utilisez le /leave point final. Clôture un socket à lui seul préserve l’adhésion. Voir se déconnecter et partir.

POST /api/v1/games/{slug}/sessions/ai

Crée une session d'entraînement sur le siège AI de la plateforme : identifiant utilisateur fixe 00000000-0000-4000-8000-00000000a1a1, nom d'utilisateur "La maison". Le backend faisant autorité du jeu joue le rôle de l'IA – il n'y a pas de service de bot externe.

{ "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e" }

Matchmaking

Un script déclare les formes de correspondance qu'il accepte via game.queues. Un jeu sans accepté les déclarations en ont un implicite default file d'attente (deux équipes d'une). Le conteneur actuel /describe le lecteur fait pas importer queues, donc les jeux de conteneurs utilisent cette forme implicite 1v1. Un client qui ne nomme aucune file d'attente obtient le premier du jeu.

Jusqu'à huit files d'attente de scripts sont conservées. Les clés sont tronquées, en minuscules, non vides et au maximum 32 personnages; les clés en double conservent la première. teams est serré à 2–8 et teamSize à 1-16 ; les formes dépassant 32 joueurs au total sont écartées. Les déclarations invalides peuvent revenir à l'implicite 1v1, donc vérifiez les formes efficaces avec GET /queues après la publication.

GET /api/v1/games/{slug}/queues

[
  { "key": "duos", "teams": 2, "teamSize": 2, "players": 4 }
]

POST /api/v1/games/{slug}/matchmaking

Met l'appelant en file d'attente pour le couplage avec l'élo le plus proche. Répétable ?queues= les clés de requête nomment un sous-ensemble de ces formes (par exemple 1v1 et 2v2, pas 3v3). La correspondance ne remplit un ticket que par rapport à une forme autorisée. Par exemple:

POST /api/v1/games/{slug}/matchmaking?queues=solo&queues=duos
Authorization: Bearer <token>

Utiliser les clés renvoyées par GET /queues. ?queue=solo sélectionne une seule forme ; si les deux queue et queues sont fournis, leurs clés sont combinées et dédupliquées sans tenir compte de la casse. Une clé inconnue est 404; une liste vide après validation est 400. Retours 409 si l'appelant est déjà en file d'attente ou à leur plafond de sessions simultanées.

La recherche commence dans une bande elo étroite et s'élargit pendant que le ticket attend (par défaut 100, +10/s). Statuts : queued, matched, cancelled, expired (attendu après le plafond, par défaut 300 s, sans trouver quelqu'un - proposer un jeu d'entraînement plutôt que de tourner). Une fête est un salle en temps réel: POST /api/v1/realtime/rooms/{id}/matchmake (hôte, lobby) entre dans l’ensemble de la liste comme une seule équipe.

{
  "ticketId": "b3b7c8d2-5c1e-4f3a-9e2d-1a2b3c4d5e6f",
  "status": "queued",
  "sessionId": null,
  "waitedSeconds": 12,
  "searchEloBand": 220,
  "maxWaitSeconds": 300
}

Les jeux peuvent opter pour la date limite commence dans starhermit.txt: matchmaking.max_wait_seconds démarre une correspondance sous-remplie après l'attente, et matchmaking.ai_players limite le nombre de sièges vacants qui deviennent IA. Les autres sièges restent vides. Pleinement humain les matchs commencent tôt. maxWaitSeconds signale le paramètre de ce jeu ; ces billets restent queued jusqu'à ce que le matchmaking les démarre, plutôt que d'expirer à la limite d'attente globale.

GET /api/v1/games/{slug}/matchmaking

Renvoie le dernier ticket de l'appelant, ou 404. A matched le billet est signalé seulement pendant que c'est la séance est toujours active. Après la fin du match, c'est 404 donc le lobby propose un nouveau match au lieu de pointer vers un identifiant de session morte.

DELETE /api/v1/games/{slug}/matchmaking

Annule les tickets en file d'attente de l'appelant. Retours 204.

POST /api/v1/games/{slug}/invites

Corps de la requête :

{ "toUserId": "9b2f8c1a-1111-4222-8333-444455556666" }

La cible doit être un ami (403 sinon - voir Amis); 409 sur une invitation en double ou lorsque l'un des joueurs a atteint la limite de session. L'invité reçoit également un game_invite événement poussé sur leur socket de chat, avec kind: "session".

Inviter un ami à une partie en cours

Ajoutez la session dans laquelle vous jouez :

{ "toUserId": "9b2f8c1a-1111-4222-8333-444455556666", "sessionId": "3f0c…" }

Accepter alors admet l'ami à cette séance de course à pied au lieu d'en créer un nouveau, ils deviennent un acteur dans tous les sens du terme (socket, ctx.players, restaure, reconnecte). Votre jeu décide s'il les prend : la plateforme demande un script game.onMembershipChange(ctx) ou un conteneur POST /sessions/{id}/members, et un jeu qui n'a ni l'un ni l'autre refuse chacune de ces jointures. Règles:

  • La session doit être une session active de ce jeu qui toi jouer dans (403 sinon, 410 s'il est terminé), votre ami ne doit pas déjà y être (409), et il ne doit pas appartenir à une salle temps réel (409 — inviter à travers la salle, dont les sièges sont la liste).
  • La réponse porte targetSessionId; sessionId reste null jusqu'à ce que l'invitation soit acceptée.
  • Lors de l'acceptation, tout est à nouveau vérifié. Si le jeu refuse (complet, fermé…) l'acceptation est un 409 et l'invitation reste en attente. Si le match est terminé, l'invitation est annulé et les réponses acceptées 410 - cela ne se transforme jamais en un nouveau jeu.
  • Seule la limite de sessions simultanées de l’invité s’applique. Vous pouvez conserver une invitation en attente par ami et par destination, afin qu'une invitation à votre match et une invitation à un nouveau jeu puissent coexister.

Une plate-forme construite avant que cette fonctionnalité ignore sessionId et démarre une nouvelle session sur accepter ; targetSessionId dans la réponse vous indique ce que vous avez obtenu.

Quelle invitation envoyer ? Accepter une simple invitation (non sessionId) crée une nouvelle session pour les deux joueurs. Si l'invitant est déjà assis dans un salle en temps réel (un hall avec des sièges), invitez-les plutôt dans cette pièce — POST /api/v1/realtime/rooms/{id}/invites - alors acceptez de les asseoir à la table à laquelle vous vous trouvez réellement. Les deux avertissent l'invité de la même manière, donc n'envoyez jamais les deux pour une seule invitation : cela notifie deux fois.

Partager des liens (invitation par URL)

Le flux d'invitation ci-dessus nécessite que les deux joueurs soient déjà amis. Pour inviter quelqu'un qui est pas encore sur la plateforme (ou pas encore un ami), un jeu peut distribuer un partager le lien — une URL vers le tableau de bord Web qui automatise l'ensemble de l'intégration :

https://dashboard.starhermit.com/game-invite/<userId>/<gameSlug>
  • <userId> — l'identifiant utilisateur du joueur partageant. Un client de jeu l'a déjà : c'est le sub revendication de son jeton de lancement (l'implémentation de référence d'échecs l'expose comme Net.userId).
  • <gameSlug> — le slug du jeu (game_scope réclamer). Les jeux sans script faisant autorité ou backend de conteneur utilisent à la place l'identifiant de jeu GitHub (un GUID) ; le tableau de bord accepte l'un ou l'autre.
  • Chaîne de requête facultative : la vôtre. N'importe quoi après ? est transmis à votre jeu sans modification : …/game-invite/<userId>/<gameSlug>?room=K7MP2X&map=arena ouvre votre jeu à https://<game-id>.starhermit.com/…?room=K7MP2X&map=arena. Utilisez-le pour déposer le destinataire directement dans une pièce, un niveau ou un hall d'entrée. Il survit à la connexion du destinataire et est ajouté à votre l'URL du jeu plutôt que d'y remplacer quoi que ce soit. Le jeton de lancement arrive toujours dans le #game_token= fragment, donc les deux n’entrent jamais en collision. Encodez en URL les valeurs que vous y mettez.

Lorsque le destinataire ouvre le lien, le tableau de bord (pas le jeu) fait la partie d'invitation automatisée d'amis — aucun nouveau point de terminaison backend n'est impliqué, il compose les API existantes :

  1. Les connecte (OAuth via un fournisseur en direct) ou réutilise leur session existante. L’intention de lien survit à l’aller-retour de connexion.
  2. Affiche une boîte de dialogue de consentement nommant le partageur et le jeu, puis amis le partageur: il accepte la demande d'ami en attente du partageur s'il en existe une, sinon il en envoie une (POST /api/v1/me/friend-requests).
  3. Les invite à choisir un surnom si leur compte n'en a pas (les jeux affichent les surnoms de profil - voir Profil).
  4. Lance le jeu (la plateforme hébergée https://<game-id>.starhermit.com copie, avec un jeton de lancement dans le #game_token= fragment comme d'habitude).
  5. Envoie le jouer, inviter à nouveau le partageur avec POST /api/v1/games/{slug}/invites - Ainsi, un lien de partage se termine comme une invitation à un jeu normale que le partageur accepte (toast sur le tableau de bord, bulle sur le bureau ou liste d'invitations du jeu). Si l'amitié est toujours une demande en attente, le tableau de bord met l'invitation à jouer en file d'attente et l'envoie automatiquement une fois que le partageur l'accepte.

Ce que cela signifie pour votre client de jeu :

  • Offrir le lien coûte une ligne de création de chaîne - mettre un "Partager le lien d'invitation" à côté de votre interface utilisateur d'invitation à un ami et copiez l'URL dans le presse-papiers. Voir shareInviteLink() dans le implémentation de référence d'échecs.
  • Aucune manipulation particulière n’est nécessaire du côté réception. L'invitation du destinataire arrive via le flux d'invitation normal : votre GET .../invites l'interrogation montre au partageur l'invitation entrante, l'accepter crée la session et le destinataire voit la session apparaître dans GET .../sessions/mine (afficher les invitations sortantes en attente pour que l'attente soit visible — le client d'échecs "invité - en attente" cartes).
  • Le tableau de bord utilise également ces URL lui-même : le volet de détails de chaque jeu hébergé jouable comporte un Copier le lien d'invitation bouton, et le client Windows propose la même chose à partir du menu contextuel d'un jeu.

Rediffusions

Une rediffusion est le document d'état final d'une session terminée, conservé par la plateforme et renvoyé au joueurs qui y étaient. Les rediffusions sont une fonctionnalité facultative d'un jeu, désactivée sauf si le jeu le demande. eux, car une rediffusion est un stockage que la plateforme conserve aussi longtemps que le record du match existe.

Demandez-les dans le code de votre serveur — replays: true sur le game objet pour un scénario, "replays": true depuis /describe pour un serveur de conteneur - et publiez une mise à jour pour l'appliquer. Une plateforme L'opérateur peut également répondre pour un jeu particulier d'une manière ou d'une autre, alors traitez le replaysEnabled domaine de GET /api/v1/games/{slug} comme réponse plutôt que de supposer que votre déclaration est le dernier mot.

Les deux points de terminaison ci-dessous renvoient 404 pour un jeu dont les replays sont éteints, et rien n'en est caché sessions terminées du jeu - donc un client qui propose un écran de relecture devrait lire replaysEnabled d'abord.

Modèle de séance

  • Session status est "active" ou "finished".
  • Chaque session reçoit une conversation de chat par session (type "game") pour que les adversaires puissent discuter et passer des appels vocaux sans être amis (voir Chat et Voix).
  • Le plafond de sessions simultanées par joueur est par défaut de 20.
  • Un jeu qui déclare persistent garde les sessions vides en pause au lieu d’y mettre fin ; la connexion à un le reprend. Les sessions interrompues comptent dans le plafond. Voir le tutoriel sur les sessions persistantes.
  • Une session active à laquelle personne ne joue est à la retraite (statut finished, abandonné) : 5 minutes après son dernier ws/v1/games le socket se ferme sans que personne ne rejoigne le groupe, ou après 24 heures sans action du joueur. Les sessions persistantes s'interrompent à la place. Cela s'applique également aux sessions en salle ; fermer leur chambre ne les met pas fin.
  • Statuts des tickets de matchmaking : queued | matched | cancelled | expired.
  • Statuts d'invitation : pending | accepted | declined | cancelled.
  • Les sessions sont créées via le matchmaking, l'acceptation d'invitation, le point de terminaison de l'IA ou le démarrage d'une salle en temps réel. (séances en salle – voir Salles en temps réel) — il n'y a pas "créer un lobby" point final.
  • Les mises à jour d'Elo proviennent du script faisant autorité (eloUpdates) ou un canal de contrôle de conteneur, définissent les notes utilisées pour le matchmaking et sont publiées dans le classement du jeu (type de score elo). Les clients ne peuvent jamais soumettre directement leurs scores à un classement de jeu. (voir Classements).

ws/v1/games?sessionId={guid} (itinéraire neutre en version). Authentifiez-vous auprès du Authorization en-tête, ?ticket=, ou ?access_token=. Participants uniquement (403); lors de la connexion avec un jeton de lancement, son game_scope doit correspondre au jeu de la session. Une séance terminée est 410 {"error":"session_not_active"}. Facultatif ?build= est le buildId depuis GET /games/{slug} — l'inadéquation est 409 {"error":"build_mismatch"}.

  • Blocs de texte uniquement, 16 Ko maximum par cadre.
  • Une connexion plus récente remplace l'ancienne : la connexion précédente est fermée avec PolicyViolation.
  • Connexion à un compte en pause persistant session le reprend avant votre première commande. S'il ne peut pas être repris (généralement un conteneur en cours de démarrage), vous obtenez un error cadre et la prise se ferme avec le code 1001; la session reste en pause - reconnectez-vous avec l'interruption.

Le renouvellement ne fonctionne que tant que le jeton actuel est valide et dans les 12 heures (par défaut) suivant le lancement d'origine ; une fois qu'il est refusé (401/403), arrêtez de vous reconnecter et renvoyez le joueur au lanceur pour obtenir un nouveau jeton de lancement.

Client → serveur

Le cmd l'enveloppe est le contrat de plateforme ; le contenu de data sont définis par le backend faisant autorité de chaque jeu. Par exemple, l'implémentation de référence d'échecs envoie un mouvement comme celui-ci :

{ "type": "cmd", "data": { "type": "move", "from": "e2", "to": "e4" } }

Pour un environnement d'exécution de script, les commandes durables sont exécutées via onPlayerMessage; explicitement marqué { "type": "input", "realtime": true, ... } les données utilisent les dernières victoires et les regroupent dans la suivante onTick. Pour un environnement d'exécution de conteneur, la plateforme transmet les commandes authentifiées via son flux binaire et le conteneur possède sa boucle de simulation. Dans les deux cas, la plateforme fournit l’identité de l’expéditeur approuvé et les clients ne peuvent jamais relayer directement l’état. Voir Scripts de jeu — Objet contextuel et Serveurs de jeux de conteneurs – Flux de gameplay.

  • game — un message autorisé par le serveur qui vous est adressé.
  • error — une erreur de la plateforme ou de votre dernière commande.
  • presence — diffuser aux autres participants lorsque quelqu'un rejoint ou quitte.
  • membership — quelqu'un est devenu joueur dans cette session en milieu de match (joined) ou ont renoncé à leur siège (left); envoyé à chaque participant connecté. Voir Serveurs de jeux de conteneurs — membres.

Un type de trame séparé volontairement : il s'agit de la vérité de la plate-forme, pas des données de jeu relayées par un script. Émis à partir des chemins de mise à jour durables des deux environnements d'exécution. Voir Réalisations.

Raisons : players_left, idle_no_players, superseded (le joueur a demandé un nouveau jeu de ce titre), server_failure, restore_failed, operator_ended (le propriétaire du jeu y a mis fin), retention_expired (la rétention de récupération d'un monde en pause s'est écoulée). Stocké comme { "kind": "abandoned", "reason": "…" }. A persistant les sessions de jeu ne sont jamais terminé simplement pour déconnexion ou inactivité – ils font plutôt une pause. Le dernier humain quittant explicitement un monde autonome peut encore y mettre fin players_left; l'expiration de la récupération configurée peut y mettre fin comme retention_expired.

Limites

Ce que la plateforme impose ws/v1/games et sur les notes. Les nombres sont les valeurs par défaut de la plateforme ; un opérateur peut les régler.

Messages sur ws/v1/games

Limite Valeur Que se passe-t-il après
Taille du cadre 16 Ko par bloc de texte La prise est fermée avec 1009 (message trop gros).
Type de cadre Texte uniquement Une trame binaire obtient un error cadre; la prise reste ouverte.
Relations Un par joueur et par session Une connexion plus récente ferme l'ancienne avec 1008.
Entrées en temps réel ({"type":"input","realtime":true,…}) 60 par seconde par connexion, rafale jusqu'à 120 Des cadres supplémentaires sont laissé tomber silencieusement - Non error cadre.
Commandes durables aux scripts (tous les deux cmd) 20 par seconde par joueur et par session, avec une allocation de courte rafale Refusé avec un error cadre: "Too many commands; slow down."

Entrées en temps réel sont échantillonnés et non mis en file d'attente : la plateforme conserve les dernières entrées et mains de chaque joueur le lot au prochain de votre script onTick dans ctx.inputs. Envoi plus rapide que celui de votre jeu taux de tick ne gagne rien, car les entrées entre deux ticks fusionnent dans un. Envoyez à votre taux de tick ou lorsque l'entrée change.

Commandes durables aux scripts sont traités dans l'ordre et limités séparément du temps réel entrées. Envoyez des actions discrètes lorsqu'elles se produisent ; envoyer un mouvement continu à travers le temps réel marqué chemin d'entrée. La limite de commande peut varier selon le jeu. Les invocations de scripts sont également limitées par les paramètres du jeu. budgets. La trame d'erreur WebSocket contient un message, pas un statut HTTP. Votre script doit rejeter les commandes qui n'ont aucun sens, comme un mouvement hors tour.

Pour un récipient jeu, les commandes sont relayées vers votre conteneur dès leur arrivée, sans plateforme limite de taux sur eux. Votre serveur applique le sien. La limitation du débit d'entrée en temps réel s'applique aux scripts jeux uniquement.

Elo par match

La plateforme fait pas plafonner jusqu'où une note peut évoluer en un seul match. eloUpdates (scénario) et le elo message de contrôle (conteneur) porte le nom de chaque joueur nouvelle note absolue, pas un changement, et le la plateforme les applique tels qu’ils ont été envoyés. Ce qu'il applique :

  • Seuls les joueurs dans la session sont mis à jour. Les identifiants de toute autre personne et le siège AI sont supprimés.
  • Les mises à jour sont appliquées chaque fois que votre serveur les renvoie. Une séance le plate-forme se termine (abandoned: joueurs restants, inactifs, remplacés, panne de serveur, terminés par le propriétaire) publie Non elo changement.
  • La note est écrite dans la colonne des paires de matchmaking et sur le tableau elo du jeu comme une seule. entrée par joueur (leur dernière note).
  • Le propriétaire du jeu peut réinitialiser la note d'un joueur à 1200.

La taille d'un swing dépend donc de la décision de votre jeu. Utilisez un facteur K standard et fixez votre code. Le implémentation de référence d'échecs utilise K = 32, donc un jeu déplace un note d'au plus 32 points :

function eloAfter(mine, theirs, score /* 1 win, 0.5 draw, 0 loss */, K = 32) {
  const expected = 1 / (1 + Math.pow(10, (theirs - mine) / 400));
  const next = mine + K * (score - expected);
  return Math.round(Math.max(100, next));      // your floor, if you want one
}

Diagnostics du propriétaire et webhooks

Propriétaire uniquement. Un jeton de lancement à l'échelle du jeu ne peut pas les atteindre.

GET /api/v1/games/{slug}/diagnostics

Un instantané des sessions en direct (connexions actives, terminées et en direct), une mesure des scripts par rapport au CPU/ les budgets de mémoire/de relevé, la file d'attente de mise en relation (l'attente la plus longue et son élargissement), et la santé du point de terminaison du webhook.

Webhooks

GET/POST/DELETE /api/v1/games/{slug}/webhooks et POST .../{id}/resume. Jusqu'à 5 points de terminaison par jeu. Événements: session.created, session.finished (omettre events pour souscrire aux deux). Le le secret de signature est renvoyé une fois, lors de la création.

La plateforme POST du JSON avec :

  • X-Starhermit-Signature: t=<unix>,v1=<hmac-sha256> sur "<t>.<body>"
  • X-Starhermit-Event-Id — l'événement (clé d'idempotence ; se répète à travers les tentatives)
  • X-Starhermit-Delivery — cette tentative

L'URL doit être https et ne doit pas être résolue en une plage privée / bouclage / CGNAT (vérifiée sur inscription et encore avant chaque envoi). Les redirections ne sont pas suivies. Les points de terminaison défaillants reculent et sont désactivés après des échecs consécutifs ; resume efface le disjoncteur.

Durée d'exécution

Pour les jeux JavaScript, la plateforme exécute onTick balaie à la vitesse fixée demandée via game.tickRateHz; 0 désactive les ticks, et un jeu qui ne demande rien est coché à 0,25 Hz — déclarez un taux si votre gameplay dépend du tick. Un conteneur pilote sa propre boucle de simulation et déclare son tarif demandé via /describe; la plateforme utilise ce tarif pour la planification et politique d'instantané, pour ne pas accélérer le jeu. Voir Scripts de jeu – Taux de tick et Serveurs de jeux de conteneurs.

Cycle de vie d'un jeu

  1. Créer un jeton de lancement — POST /api/v1/games/{slug}/launch-token. Les clients doivent l'actualiser avant l'expiration (le client de référence d'échecs s'actualise toutes les 45 minutes).
  2. Récupérer l'état du jeu — GET /api/v1/games/{slug} pour info + vos stats ; GET .../sessions/mine pour les jeux en cours ; GET .../invites et GET /api/v1/realtime/rooms/invites pour les invitations en attente ; GET .../replays/mine pour l'histoire quand replaysEnabled; GET .../achievements pour l'écran de réussite.
  3. Trouver un adversaire, de trois manières :
    • Matchmaking : POST .../matchmaking, puis interrogez GET .../matchmaking toutes les 3 s jusqu'à status est matched (la réponse porte sessionId). DELETE .../matchmaking pour annuler.
    • Flux d'invitation : choisis un ami parmi GET /api/v1/me/friends (voir Amis), POST .../invites avec { "toUserId": "..." }; l'invité appelle POST .../invites/{inviteId}/accept, qui crée la session. (Si votre jeu place les joueurs dans un salle en temps réel commencez par les inviter dans la salle (même notification, mais si vous les acceptez, vous les placerez à la table dans laquelle vous vous trouvez déjà.)
    • Pratique de l'IA : POST .../sessions/ai.
  4. Charger la session — GET .../sessions/{sessionId}.
  5. Connectez le WebSocket — ws/v1/games?sessionId={guid} avec le jeton de lancement, puis envoyez la commande de synchronisation initiale définie par le backend du jeu - l'implémentation de référence d'échecs, par exemple, envoie {"type":"cmd","data":{"type":"sync"}}.
  6. Jouer - échange cmd/game frames tels que définis par le backend, surface achievement cadres et poignée resumed en rejetant la prédiction et en demandant un état complet.
  7. Résultat — le backend faisant autorité met fin au jeu ; la plateforme publie des mises à jour elo au classement et, pour un jeu avec rediffusions, archive l'état final.
  8. Rejouer — GET .../replays/{sessionId} pour l’état final complet.
