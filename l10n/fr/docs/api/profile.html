Profil

L'API de profil couvre le propre compte de l'utilisateur authentifié (/api/v1/me/...), les recherches publiques d'autres utilisateurs, les clés publiques, les identités liées, les paramètres de confidentialité, les droits et le rythme cardiaque de présence. Les itinéraires de compte nécessitent une autorisation ; le document de conditions actuel est public.

Les corps d’erreur varient ; voir Conventions API.

PATCH /api/v1/me

Tous les champs sont facultatifs. Contraintes : username 1 à 32 caractères ; nickname ≤64 caractères (plusieurs les comptes n'en ont pas); metadata ≤4096 caractères. Les noms d’utilisateur et les surnoms en partagent un espace de noms insensible à la casse : 409 lorsqu'un autre compte utilise le nom comme nom d'utilisateur ou surnom, ignorant le cas. Les surnoms sont normalisés par NFKC et les caractères de contrôle ou invisibles sont 400. Changement email nécessite en outre un Session authentifiée par OAuth, car l'adresse e-mail du compte peut approuver les liens d'identification ; une clé publique ou la session de vérification des e-mails obtient 403 pour ce champ mais peut toujours mettre à jour les autres. Renvoie 204 sur réussite, 409 sur conflit (nom d'utilisateur ou pseudo déjà pris).

{
  "username": "newname",
  "email": "new@example.com",
  "metadata": "{}",
  "nickname": "New Nick"
}

Acceptation des conditions

Avant d'utiliser des points de terminaison REST protégés ou d'ouvrir des WebSockets, le compte doit accepter le courant Conditions générales de StarHermit. Ceci s'applique aux jetons de compte et aux jetons de lancement de joueur, y compris les comptes qui accepté une révision plus ancienne. Cela ne s'applique pas aux ressources/connexions anonymes ou à celles d'un serveur de conteneur. propre jeton de déploiement. GET /api/v1/me et le point de terminaison d'acceptation restent disponibles avec leur niveau habituel autorisations de compte pendant que l'acceptation est en attente.

GET /api/v1/me comprend currentTermsHash et termsAcceptanceRequired. Le stocké termsAcceptedHash et termsAcceptedAt sont nuls avant première acceptation. Le hachage affiché dans le L'exemple de profil ci-dessus est abrégé ; utilisez toujours le hachage complet renvoyé par l'API.

GET /api/v1/terms

Anonyme; également lisible avec un jeton de lancement de joueur. Retours 200 avec Cache-Control: no-store:

{ "hash": "<current-64-character-lowercase-sha256>", "text": "<complete terms text>" }

Rendre text sous forme de texte brut. hash est SHA-256 des octets exacts du document UTF-8 ; utiliser le retour valeur plutôt que de hacher le texte d’affichage reformaté.

POST /api/v1/me/terms/accept

Une fois que l'utilisateur a lu et accepté explicitement la révision affichée, envoyez son hachage :

POST /api/v1/me/terms/accept
Authorization: Bearer <account-access-token>
Content-Type: application/json

{ "hash": "<hash-returned-with-the-displayed-text>" }

Retours 200 avec { "termsAcceptedHash", "termsAcceptedAt" }. Sessions OAuth et comptes à clé publique et jetons de lancement du joueur à l'échelle du jeu peut accepter. Un jeton de serveur conteneur ne peut pas agir pour un joueur. L'acceptation est stockée sur le compte et prend effet le prochaine requête avec le même jeton toujours valide ; il n'est pas nécessaire de rafraîchir le jeton.

Un hachage manquant/vide ou de plus de 64 caractères est renvoyé 400. Un hachage qui ne fait pas exactement correspondre aux retours de révision actuels 409:

{
  "error": "terms_version_mismatch",
  "termsHash": "<current-hash>",
  "termsUrl": "/api/v1/terms"
}

Récupérez et affichez le nouveau document et demandez à nouveau son acceptation ; n'acceptez pas silencieusement un remplacement révision. Autres demandes protégées avec retour d'acceptation en attente 403:

{
  "error": "terms_acceptance_required",
  "message": "Accept the latest terms of service before using the API.",
  "termsHash": "<current-hash>",
  "termsUrl": "/api/v1/terms",
  "acceptUrl": "/api/v1/me/terms/accept"
}

Un jeu hébergé peut afficher les termes et soumettre le hachage affiché avec son jeton de lancement de joueur lorsque le joueur appuie sur Accepter, réessayez. Il peut également envoyer le joueur vers l'interface utilisateur de son compte. Les connexions répétées ou l’actualisation du jeton ne corrigent pas l’acceptation en attente. Les mises à niveau WebSocket sont refusées avec HTTP 403 avant ouverture ; les navigateurs peuvent masquer le corps de la réponse, gérez donc l'acceptation via REST avant de vous connecter.

Exemple pour un compte ou un client de jeu (appelez acceptDisplayedTerms uniquement à partir de l'action Accepter de l'utilisateur) :

const api = 'https://api.starhermit.com';
async function loadTerms() {
  const response = await fetch(`${api}/api/v1/terms`);
  if (!response.ok) throw new Error(`Terms fetch failed: ${response.status}`);
  return response.json(); // Display text, retain this document's hash.
}
async function acceptDisplayedTerms(accountToken, displayedTerms) {
  const response = await fetch(`${api}/api/v1/me/terms/accept`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${accountToken}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ hash: displayedTerms.hash })
  });
  if (response.status === 409) {
    throw new Error('Terms changed. Reload and display them for a new acceptance.');
  }
  if (!response.ok) throw new Error(`Acceptance failed: ${response.status}`);
  return response.json();
}

Avatars

PUT /api/v1/me/avatar accepte une image PNG, carrée, ≤512×512 pixels, ≤1 Mo :

{ "imageBase64": "iVBORw0KGgoAAAANSUhEUg..." }

Renvoie 204. GET /api/v1/me/avatar renvoie votre avatar sous la forme image/png octets.

Clés publiques

Une clé enregistrée est un identifiant API : son détenteur peut compléter le flux de contestation à clé publique et recevez un jeton d'accès/rafraîchissement ordinaire paire. Cela rend une clé étiquetée séparément adaptée à un client de bureau ou à un pipeline de déploiement.

L'ajout de clés ou la révocation d'autres clés nécessitent une session authentifiée par OAuth. Une clé publique la session ne peut révoquer que sa propre clé via DELETE /api/v1/me/public-keys/current. Cela ne peut pas inscrire des remplacements ou révoquer d’autres appareils. La liste reste disponible pour toute session de compte complète ; le lancement du jeu et les jetons de serveur ne peuvent pas gérer les clés de compte.

GET /api/v1/me/public-keys

La liste comprend les lignes révoquées comme piste d'audit :

[
  {
    "id": "9b2f5c74-1d2e-4a6b-8c0d-1e2f3a4b5c6d",
    "keyType": "Ed25519",
    "keyData": "<base64-raw-32-byte-public-key>",
    "label": "orbit-league-production",
    "fingerprint": "4d9f3c...",
    "createdAt": "2026-07-01T12:00:00Z",
    "lastUsedAt": "2026-07-30T09:00:00Z",
    "isRevoked": false,
    "revokedAt": null,
    "metadata": null
  }
]

POST /api/v1/me/public-keys

Nécessite une session authentifiée par OAuth et joint la clé immédiatement ; contrairement aux anonymes inscription, aucun aller-retour par courrier électronique n’est nécessaire.

{
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>",
  "label": "orbit-league-production"
}

label est facultatif (128 caractères maximum). Les types de clés acceptés sont Ed25519, ECDSA-P256, et RSA-PSS; le matériel doit être standard Base64 : une clé publique brute de 32 octets pour Ed25519, un P-256 codé point de courbe pour ECDSA, ou un SPKI public pour RSA. Les clés RSA doivent comporter entre 2 048 et 8 192 bits. La plateforme canonise le matériel valide et limite un compte à 20 clés actives par défaut. fingerprint est le résumé hexadécimal SHA-256 minuscule du canonique keyType:keyData chaîne.

Retours 201 avec la clé créée. Retours de matériel invalides 400; une clé déjà active ou une clé complète la liste des clés revient 409 (ce dernier comprend limit). Le matériel de clé active est unique à l’échelle de la plateforme.

DELETE /api/v1/me/public-keys/{keyId}

Nécessite une session authentifiée par OAuth. La révocation est idempotente et met fin aux sessions de rafraîchissement par la clé; les jetons d'accès le nommant sont refusés lors de leur prochaine demande. Retours :

{ "revoked": [{ "id": "...", "isRevoked": true }], "sessionsEnded": 1 }

Une clé inconnue sur ce compte revient 404.

DELETE /api/v1/me/public-keys/all

L’opération de réponse à la compromission : révoquer chaque clé active et mettre fin à toutes les sessions authentifiées. Il a un explicite /all chemin afin qu’un ID de clé accidentellement vide ne puisse pas devenir une révocation groupée. Renvoie la même chose { revoked, sessionsEnded } forme.

DELETE /api/v1/me/public-keys/current

Une session de compte complète authentifiée avec une clé publique peut révoquer la clé utilisée pour cette session, sans nommer un identifiant de clé. Utilisez-le pour Oubliez cet appareil. ça renvoie pareil { revoked, sessionsEnded } façonner et invalider les sessions à l’aide de cette clé. Jeter les jetons stockés et la clé privée locale après succès. Une session sans retour de clé publique 409 avec code: "no_public_key_session"; les jetons de lancement de jeu sont refusés.

Pour un exemple complet de déploiement de machine, voir Télécharger des builds à partir de CI/CD avec une clé publique inscrite par OAuth.

  }
]

POST /api/v1/me/identities

{
  "provider": "epic",
  "providerUserId": "your-epic-account-id",
  "metadata": null
}

Le fournisseur nomme la plateforme connue sous le nom d'OAuth (google, github, discord, twitch, gitlab, linkedin, bitbucket, plus les noms réservés microsoft, facebook, twitter, x, apple, steam) sont rejeté ici, que ce fournisseur soit configuré ou non - ces identités sont pouvant être lié uniquement via une véritable connexion. Utilisez un nom non réservé (epic, gog, un identifiant de vitrine personnalisé). Voir Authentification.

DELETE /api/v1/me/identities/{identityId}

La suppression d'une identité gérée par OAuth nécessite une session authentifiée par OAuth, donc une clé publique volée ne peut pas supprimer l'itinéraire du propriétaire vers le compte. Renvoie 204.

Paramètres de confidentialité

GET /api/v1/me/privacy renvoie votre PrivacySettings; PUT /api/v1/me/privacy les remplace (renvoie 204):

{
  "onlineStatus": 1,
  "currentlyPlaying": 1,
  "recentLaunchActivity": 0,
  "hoursPlayed": 0,
  "recentDownloads": 0,
  "achievements": 2,
  "friendDiscoverability": 1,
  "profileVisibility": 2

Chaque champ est un PrivacyLevel énumération : 0 = Privé, 1 = Amis uniquement, 2 = Publique.

Battement de coeur de présence

POST /api/v1/me/heartbeat

Renvoie 204. Écrit LastSeenAt côté serveur, limité — c'est le signal de présence utilisé par les amis et le chat.

Jetons de lancement à l'échelle du jeu

Parmi les points de terminaison de cette page, un jeton de lancement à l'échelle du jeu ne peut appeler que :

  • GET /api/v1/users/{id}/avatar
  • GET /api/v1/users/{id}/profile
  • GET /api/v1/me/friends (voir Amis)
  • GET /api/v1/terms
  • POST /api/v1/me/terms/accept
  • POST /api/v1/me/heartbeat

Tout le reste renvoie 403 sous la clôture du jeu décrite dans Authentification.

Convention de nom d'affichage

Les interfaces utilisateur du jeu affichent généralement surnoms plutôt que les noms d'utilisateur lors du rendu des adversaires, en revenant à quelque chose comme "Player " + id.slice(0,8) lorsqu'aucun surnom n'est défini. L'implémentation de la référence d'échecs suit cette convention ; les autres clients du jeu devraient faire de même.
