Authentification

StarHermit a pas d'authentification par mot de passe. Il existe deux flux de connexion : l'authentification par clé publique (Ed25519, ECDSA-P256 ou RSA-PSS, avec enregistrement vérifié par e-mail) et OAuth. Toutes les routes d'authentification se trouvent sous api/v1/auth et sont anonymes, sauf indication contraire. Cette page couvre également les cycles de vie des jetons, les jetons de lancement à l'échelle du jeu et les tickets de connexion WebSocket.

Les corps d’erreur varient ; voir Conventions API.

Après la connexion : conditions actuelles

Une connexion réussie n’implique pas l’autorisation d’utiliser les API protégées. Les titulaires de compte doivent accepter les conditions actuelles de StarHermit avant les appels REST protégés ou Les mises à niveau de WebSocket réussissent. Les clients du compte peuvent vérifier GET /api/v1/me, aller chercher GET /api/v1/terms, et enregistrer l'acceptation explicite avec POST /api/v1/me/terms/accept. OAuth et clé publique les sessions de compte prennent en charge ce flux. L’actualisation des informations d’identification ne résout pas l’acceptation en attente.

Un jeu par navigateur ouvert directement peut recevoir un jeton étendu avant que le compte n'ait accepté. Si un appel de jeu revient 403 avec error: "terms_acceptance_required", aller chercher GET /api/v1/terms, afficher son texte et proposer une action Accepter explicite. Un jeton de lancement de joueur peut soumettre le message affiché hacher pour POST /api/v1/me/terms/accept; réessayez la demande initiale après acceptation. Ne traite pas ça réponse sous forme de boucle de connexion avec jeton expiré.

POST /api/v1/auth/public-key/register

Commence l’enregistrement de la clé publique et envoie un e-mail de vérification. Le dossier d'enregistrement en attente expire après 4 heures. Si userId est défini, l'e-mail doit correspondre à ce compte. Limitation à 1 e-mail par adresse et par IP toutes les 24 heures – en cas de limitation, la réponse est 429 avec un Retry-After en-tête.

Quand userId est défini et la paire ne vérifie pas, la réponse est 403 avec un seul message indépendamment de pourquoi: un compte inconnu et une mauvaise adresse répondent de manière identique. Ce point final prend pas d'informations d'identification - c'est obligatoire, car c'est ainsi qu'une nouvelle clé est attachée - donc les distinguer serait faites-en un oracle pour lequel les identifiants des utilisateurs existent, puis pour leurs adresses. Un appelant qui possède le compte sait déjà lequel des deux ils se sont trompés.

Demande:

{
  "email": "dev@example.com",
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>",
  "userId": null
}

Réponse — 202 :

{
  "registrationId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "email": "dev@example.com",
  "emailSent": true,
  "deferralReason": null,
  "message": "A verification email has been sent. The key will be attached once you confirm."
}

emailSent: false signifie que l'e-mail est en file d'attente pour une nouvelle tentative (deferralReason dit pourquoi); l'inscription est toujours accepté. Un e-mail ou un élément clé invalide est 400.

GET / POST /api/v1/auth/public-key/verify?token=

L'ouverture du lien envoyé par email ne change rien. GET affiche une page indiquant ce que ferait la confirmation - créer un compte, ou ajouter une clé au compte existant qui utilise déjà l'adresse - avec un Bouton Confirmer. Les scanners de courrier récupèrent les liens pour les prévisualiser, donc un lien envoyé par courrier électronique qui a agi sur GET serait racheté par celui qui l'aurait scanné. La même chose s'applique à la révocation et lien d'identité confirmations ci-dessous.

POST à la même URL le rachète : attache la clé, créant l'utilisateur (nom d'utilisateur pk-<hex12>, rôle User), sauf si un compte utilise déjà cette adresse e-mail, auquel cas la clé rejoint ce compte. L'e-mail est marqué comme vérifié. Le lien est à usage unique et expire au bout de 4 heures ; un inconnu, utilisé ou le jeton expiré est 400, tout comme un lien dont l'adresse n'est plus celle du compte — cela prouve contrôle de la boîte de réception à laquelle il a été envoyé, et seulement tant que cette adresse est toujours celle du compte.

Lorsque le joueur appuie sur Confirmer sur la page et que le déploiement est défini PublicKeyAuth:VerificationSuccessRedirectUri — starhermit.com le fait, sur le tableau de bord — ils sont envoyé là-bas avec les jetons dans le fragment (#access_token=…&refresh_token=…&token_type=Bearer&expires_in=900), connecté au tableau de bord. Un le client natif ne reçoit donc pas ces tokens ; il se connecte avec sa clé une fois que le joueur a confirmé. Un client API qui POSTs l'URL elle-même obtient JSON :

{
  "userId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "keyId": "9b2f5c74-1d2e-4a6b-8c0d-1e2f3a4b5c6d",
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "dGhpcyBpcyBh..."
}

Connexion par clé publique

POST /api/v1/auth/public-key/challenge

Lance un défi de connexion, valable 5 minutes et à usage unique.

La signature couvre la propre sérialisation du serveur payload, pas le JSON que vous avez reçu : compact, noms PascalCase dans l'ordre ChallengeId, Fingerprint, Issuer, Audience, Expiry, Nonce, ClientTimestamp, les valeurs copiées exactement telles qu'elles sont servies, et chaque + dans le nonce écrit comme \u002B (les dates gardent leur +). Voir le exemple travaillé.

Demande:

{
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>"
}

Réponse:

{
  "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "payload": {
    "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "fingerprint": "4d9f3c...",
    "issuer": "starhermit",
    "audience": "starhermit",
    "expiry": "2026-07-22T07:24:44.1234567+00:00",
    "nonce": "NmL+tgMum6HXU/pa3T9xjQ==",
    "clientTimestamp": "2026-07-22T07:19:44.1235521+00:00"
  },
  "expiresIn": 300
}

POST /api/v1/auth/public-key/complete

Vérifie la signature par rapport à une clé enregistrée et non révoquée et renvoie une paire de jetons. Un échec est 401: "Public key not registered or revoked." (y compris une clé dont le lien envoyé par email n'a pas été encore ouvert), "Invalid signature.", ou "Challenge not found or expired.". Défiez et terminez partager une limite de 60 requêtes par minute par IP (429).

Demande:

{
  "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "signature": "base64-signature...",
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>"
}

Réponse:

{
  "userId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "dGhpcyBpcyBh..."
}

Cycle de vie du jeton

POST /api/v1/auth/refresh

Actualisation rotative : l'ancien token est révoqué et remplacé. La réutilisation d’un jeton d’actualisation révoqué révoque toute la famille de jetons.

Demande:

{ "refreshToken": "dGhpcyBpcyBh..." }

Réponse:

{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "bmV3IHJlZnJlc2g..."
}

Lorsque l'actualisation cesse de fonctionner

Un jeton d'actualisation enregistre l'état du compte sous lequel il a été émis et l'actualisation le vérifie. Deux réponses votre client doit gérer plutôt que réessayer :

Statut Signification Ce que le client doit faire
401 La session a été révoquée côté plateforme – un "déconnectez-vous partout", ou une réponse de compromis. Toute la famille des jetons est brûlée, y compris le jeton qui vient d'être présenté. Jetez les deux jetons et démarrez une nouvelle connexion.
403 Le compte est suspendu. Arrêt. Se reconnecter ne servira à rien ; le même 403 revient à chaque itinéraire de connexion jusqu'à ce que la suspension soit levée.

Le 403 est délibérément distinct de 401, parce que les deux nécessitent des réactions opposées : l'un signifie "s'authentifier à nouveau", les autres moyens "s'authentifier à nouveau ne sert à rien". Un compte suspendu est refusé par chaque itinéraire de création d'informations d'identification - actualisation, achèvement de la clé publique, rappel OAuth, et les jetons de lancement de jeu – pas seulement par actualisation.

POST /api/v1/auth/logout

Révoque le jeton d'actualisation donné. Renvoie 200.

{ "refreshToken": "dGhpcyBpcyBh..." }

OAuth

La plateforme propose sept fournisseurs : google, github, discord, twitch, gitlab, linkedin, bitbucket. Seuls les fournisseurs pour lesquels ce déploiement dispose d’informations d’identification sont en ligne. Un client ne doit pas coder en dur la liste.

GET /api/v1/auth/oauth/providers

Anonyme. Renvoie les fournisseurs en direct dans l'ordre dans lequel ils doivent être proposés :

{
  "providers": [
    {
      "provider": "google",
      "displayName": "Google",
      "authorizeUrl": "/api/v1/auth/oauth/google/authorize",
      "linksExistingAccountsByEmail": true
    }
  ]
}

linksExistingAccountsByEmail est de savoir si une connexion auprès de ce fournisseur peut trouver un compte pour la personne possède déjà (le paramètre de confiance de l'opérateur pour ce fournisseur). Demander d'autoriser un nom qui ne l'est pas vivre est 404, pas une redirection vers la propre page d'erreur du fournisseur.

GET /api/v1/auth/oauth/{provider}/authorize?link=&client=

Renvoie une redirection 302 au fournisseur et définit un oauth_state cookie (HttpOnly, SameSite=Lax, 10 minutes). link=true commence à lier l'identité à l'utilisateur actuellement connecté ; la liaison nécessite authentification récente (dans les 5 minutes). client sélectionne une redirection client prise en charge. Pour un Jeu directement ouvert, utilisez gameId et en option returnUrl plutôt; voir Connectez-vous à partir d'un jeu par navigateur directement ouvert.

GET /api/v1/auth/oauth/{provider}/callback?code=&state=

Pour une connexion au compte ordinaire, renvoie une redirection 302 vers l'URL du frontend avec les jetons dans le fragment (la connexion au jeu renvoie à la place un jeton étendu directement au jeu, comme décrit ci-dessous) :

#access_token=…&refresh_token=…&token_type=Bearer&expires_in=900

Si le fournisseur refuse l'échange de jetons, le rappel répond 409 nommer l'erreur du fournisseur code (la description reste dans le journal du serveur).

Une connexion normale recherche ou crée l'utilisateur (nom d'utilisateur oauth-{provider}-{guid}, rôle User) et le nouveaux enregistrements de session auth_method=oauth. Une connexion dont (provider, providerUserId) est inconnu est adopté sur un compte existant seulement lorsque l'affirmation du fournisseur est fiable, exactement un le compte contient déjà cette adresse e-mail vérifiée et ce compte n'a pas encore d'identité de ce fournisseur. Tout le reste prévoit un compte séparé. L'adoption envoie un e-mail au compte nommant le fournisseur.

Ceci est important car seule une session authentifiée par OAuth peut effectuer des modifications d’informations d’identification à fort impact :

  • ajouter ou révoquer des clés publiques de compte ;
  • modifier l'e-mail du compte ;
  • supprimer une identité gérée par OAuth.

Les jetons à l'échelle du jeu ne peuvent jamais effectuer ces opérations. Un jeton d'actualisation conserve l'original méthode d'authentification de la session, donc l'actualisation d'une session OAuth ne supprime pas cette fonctionnalité et l'actualisation d'une session de clé publique ne l'ajoute pas.

Quand link=true, le rappel ne promeut pas automatiquement la session simplement parce qu'elle a visité un fournisseur OAuth. Un lien démarré à partir d’une session OAuth est immédiatement joint. Un lien démarré à partir de une session de clé publique, de vérification de courrier électronique ou héritée est maintenue jusqu'à ce que le propriétaire du compte ouvre le confirmation envoyée à l'adresse e-mail vérifiée du compte ; les rapports de fragment de redirection link=pending_email_confirmation. L'e-mail unique s'ouvre GET /api/v1/auth/oauth/link/confirm?token=…, une page nommant le compte fournisseur qui ne change rien ; son bouton Confirmer POSTc'est la même URL, qui crée l'identité ({ "provider", "linked": true } à un client API). Un lien dont l'adresse n'est plus celui du compte est refusé. Cela empêche qu'une clé publique volée relie le compte du fournisseur de l'attaquant et en le transformant en une connexion OAuth permanente.

Magasins de métadonnées d'identité GitHub {"login":"…"} — ceci est utilisé pour les contrôles de propriété du référentiel dans Jeux GitHub.

Clés publiques inscrites par OAuth pour l'automatisation

Une session OAuth peut appeler POST /api/v1/me/public-keys pour attacher immédiatement une clé de machine étiquetée. Plus tard, CI signe le défi normal de clé publique et utilise son jeton d'accès de courte durée pour télécharger un lot de jeux possédés ; la clé privée ne quitte jamais le magasin secret CI. Voir le tutoriel de téléchargement de build CI/CD pour la configuration, un assistant de signature et un flux de travail GitHub Actions.

Jetons

  • Jeton d'accès — JWT, durée de vie de 15 minutes (expires_in=900). Les réclamations incluent sub (l'identifiant de l'utilisateur) plus permission et les revendications de rôle. La révocation prend effet immédiatement.
  • Jeton d'actualisation — Un jeton rotatif opaque d'une durée de vie de 7 jours. Chaque actualisation émet un nouveau jeton d'actualisation et révoque l'ancien ; la réutilisation d'un jeton révoqué révoque toute la famille de jetons.

Connectez-vous à partir d'un jeu par navigateur directement ouvert

Un jeu hébergé ouvert en dehors du tableau de bord peut afficher un Se connecter bouton reliant à :

https://api.starhermit.com/api/v1/auth/games/{gameId}/sign-in

gameId est l'UUID immuable du jeu (le sous-domaine dans {gameId}.starhermit.com). Ermite des étoiles affiche ses fournisseurs de connexion activés. Continuer à signer dans un joueur existant ou créer un nouveau compte en utilisant les règles normales de correspondance de compte OAuth, puis redirige retour direct au jeu, sans visiter le tableau de bord.

L'optionnel returnUrl préserve une page de jeu spécifique, une chaîne de requête ou une route de hachage. Ça doit être une URL HTTPS absolue sur exactement l'origine hébergée de ce jeu ; d'autres jeux, des hôtes externes, les informations d'identification dans l'URL et les ports alternatifs sont rejetés avec 400. Omettez-le pour revenir au fichier de lancement publié. Retour des jeux inconnus, supprimés, non hébergés ou jamais publiés 404. Les deux les déploiements de référentiels et les jeux téléchargés sont pris en charge ; les URL externes/locales arbitraires ne le sont pas.

Naviguez dans le navigateur jusqu'au origine de l'API publique ci-dessus, plutôt que de récupérer la page ou de démarrer à travers le jeu /api procuration. Le cookie d'état OAuth et le rappel du fournisseur doivent utiliser le même Hôte API. Utilisez ce flux lorsque le jeu ne dispose pas de jeton valide fourni par le lanceur ou obtenu précédemment.

Exemple de bouton et de jeton de retour

<button id="starhermit-sign-in">Sign in</button>
<script type="module">
const api = 'https://api.starhermit.com';
const gameId = 'YOUR_GAME_UID';
const signIn = document.querySelector('#starhermit-sign-in');
let gameToken = null; // Or your existing launcher-provided game token.

// Read this before your game router or third-party scripts consume the fragment.
const auth = new URLSearchParams(location.hash.slice(1));
if (auth.has('access_token')) {
  gameToken = auth.get('access_token');
  const originalHash = auth.get('game_fragment');
  history.replaceState(null, '', location.pathname + location.search +
    (originalHash ? '#' + originalHash : ''));
}
signIn.hidden = Boolean(gameToken);
signIn.addEventListener('click', () => {
  const url = new URL(`/api/v1/auth/games/${gameId}/sign-in`, api);
  url.searchParams.set('returnUrl', location.href);
  location.assign(url.href);
});

// Pass gameToken to your game's API client as Authorization: Bearer <gameToken>.
// This example keeps it in memory; a reload can require sign-in again.
</script>

Le fragment de retour est :

#access_token=…&token_type=Bearer&expires_in=3600

access_token est un jeton de lancement à l'échelle du jeu, et non un jeton d'accès à l'échelle du compte. Pas de jeton d'actualisation est délivré. expires_in utilise la durée de vie du jeton de lancement configurée pour le déploiement (3 600 par défaut) secondes). Un fragment d'URL de retour d'origine est codé dans le format facultatif game_fragment champ; restaurez-le après avoir capturé le jeton et supprimé les données d'authentification de l'historique du navigateur. Ne connectez pas et ne transférez pas le jeton.

Renouveler avant expiration en utilisant POST /api/v1/games/{gameId}/launch-token avec le jeton actuel comme Autorisation au porteur, puis remplacez-la par celle restituée token. Le plafond habituel de la chaîne de renouvellement s'applique (12 heures par défaut). Si le token expire ou si le renouvellement est refusé, effacez-le et affichez Se connecter encore une fois. Voir Jetons de lancement de jeu.

Choisir soi-même un prestataire

Les jeux peuvent plutôt lire GET /api/v1/auth/oauth/providers et accédez à une offre authorizeUrl sur l'origine de l'API publique, en ajoutant gameId et éventuellement returnUrl. L'étape d'autorisation valide et stocke la cible dans l'état OAuth existant de dix minutes ; paramètres de requête de rappel je ne peux pas le changer. Le cookie du navigateur initiateur est toujours requis et le jeu est à nouveau vérifié avant d'émettre un jeton. Les comptes suspendus ne peuvent pas recevoir de jeton.

Ne combinez pas la connexion au jeu avec client ou link (400). A returnUrl sans gameId est aussi 400. La connexion normale au tableau de bord et au bureau continue d'utiliser leurs destinations frontales configurées et des paires de jetons de compte ordinaires.

Jetons de lancement de jeu

POST /api/v1/games/{slug}/launch-token (JWT) crée un JWT à l'échelle du jeu :

{
  "token": "eyJhbGciOi...",
  "expiresInSeconds": 3600
}

Le jeton porte un game_scope réclamation et par défaut à une durée de vie de 60 minutes. Le renouvellement copie un launch_chain heure de début en avant ; le renouvellement des 12 dernières heures (par défaut) est 403 et le titulaire doit partir revenir à une session de compte complète. Tous les détails sont dans Jeux.

Reconnexion des prises. Un socket ouvert avec un jeton de lancement (?access_token= sur ws/v1/games, ws/v1/realtime, ws/v1/voice) porte ce jeton dans son URL et une poignée de main avec un jeton expiré est refusé avec 401 avant la mise à niveau : le navigateur ne signale que le code de fermeture 1006, la même chose qu'un chute de réseau. Traitez un échec de reconnexion comme un échec d'authentification : avant de rouvrir, renouvelez via POST /api/v1/games/{slug}/launch-token (possible uniquement tant que le token actuel est encore valide et dans les 12 heures suivant le lancement d'origine) et créez l'URL avec le nouveau jeton. Une fois le renouvellement effectué refusé, renvoyer le joueur vers le lanceur, ou via connexion au jeu si c'est ainsi que le jeu a été ouvert. Réessayer la même URL ne pourra jamais être récupéré.

Clôture de jeu

Un jeton à l'échelle du jeu ne peut atteindre que :

  • le sien /api/v1/games/{scope} arbre,
  • /ws/v1/games,
  • salle en temps réel Itinéraires REST et /ws/v1/realtime pour son propre jeu, y compris les tickets de connexion,
  • GET /api/v1/time et GET /api/v1/terms,
  • POST /api/v1/me/terms/accept pour le consentement explicite du joueur authentifié,
  • GET /api/v1/me/friends,
  • GET /api/v1/users/{id}/avatar et GET /api/v1/users/{id}/profile,
  • le classement de son jeu,
  • celui du joueur sauvegarde dans le cloud pour son propre jeu (/api/v1/me/cloud-saves/game:<scope> et son /info) — pas d'autre clé,
  • les points de terminaison chat/voix REST et WebSocket attachés à ses propres sessions de jeu,
  • GET /api/v1/github-games/{id}/icon et /cover pour n'importe quel jeu (les deux sont publics de toute façon),
  • POST /api/v1/me/heartbeat, qui marque uniquement le joueur en ligne,
  • GET /api/v1/github-games/{id}/release-notes pour son propre jeu,
  • relais itinéraires, pour les relais liés à l'une de ses propres sessions ou salles de jeu.

/ws/v1/chat est bloqué pour les jetons de lancement. Tout le reste renvoie 403.

Flux de connexion typique (curl)

Connexion par clé publique, du défi à l'appel authentifié :

# 1. Request a challenge
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/challenge \
  -H "Content-Type: application/json" \
  -d '{"keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "challengeId": "...", "payload": { ... }, "expiresIn": 300 }

# 2. Sign the serialized payload JSON with your private key, then complete
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/complete \
  -H "Content-Type: application/json" \
  -d '{"challengeId":"...","signature":"base64-signature...","keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "userId": "...", "accessToken": "...", "refreshToken": "..." }

# 3. Call the API with the access token
curl -s https://api.starhermit.com/api/v1/me \
  -H "Authorization: Bearer eyJhbGciOi..."

# 4. When the access token expires (after 15 min), rotate the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

# 5. On logout, revoke the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

La connexion OAuth est pilotée par le navigateur : lire GET /api/v1/auth/oauth/providers, ouvrez un fournisseur en direct authorizeUrl, consentement complet, et le rappel amène l'utilisateur sur le frontend avec #access_token=…&refresh_token=… dans le fragment d'URL.

Révocation de clé par e-mail

Pour un propriétaire qui ne peut pas joindre DELETE /me/public-keys (pas de session OAuth, ou verrouillé par un vol clé). POST /api/v1/auth/public-key/revoke-request avec { "email": "…" } détient une demande et envoie un lien par e-mail. L'ouvrir (GET /api/v1/auth/public-key/revoke/confirm?token=…) affiche une page qui ne change rien ; son bouton Confirmer POSTc'est la même URL, qui révoque chaque clé active là-dessus compte et met fin aux sessions qu'ils ont authentifiées. Les deux ne sont pas authentifiés et numéro de problème séance. La demande répond toujours 202 avec le même corps, quoi qu'il trouve ; une demande par compte toutes les 15 minutes et le lien expire après 4 heures. La confirmation POST réponses 200 { "revoked": <count>, "sessionsEnded": <count> } à un client API, ou 400 pour un inconnu, utilisé ou un jeton expiré ou dont l'adresse n'est plus celle du compte.

Tickets de connexion WebSocket

POST /api/v1/realtime/connection-tickets échange le jeton au porteur de l'appelant contre un ticket unique valable environ 30 secondes. Passez-le comme ?ticket= sur n'importe quel /ws/v1/* poignée de main. Il porte le nom de l'appelant revendications textuelles (y compris game_scope et pk), est refusé sur REST et est dépensé à la première utilisation. Tout appelant authentifié peut demander, y compris un jeton de lancement lié au jeu. ?access_token= fonctionne toujours jusqu'à ce que les clients aient déménagé.

Un socket ouvert se termine lorsque ses informations d'identification sont révoquées. La révocation de la clé publique qui l'a ouvert se termine immédiatement ; une suspension ou une déconnexion partout y met fin en 30 secondes environ. Expiration du jeton ne termine pas un socket ouvert - actualisez avant de vous reconnecter.

Intégration intégrée pour les jeux natifs/en vitrine

Un client Steam, Epic, GOG ou autonome peut générer une clé sur l'appareil du joueur et présenter le flux d'enregistrement de clé publique dans sa propre interface utilisateur, évitant OAuth et une visite sur StarHermit tableau de bord. L'inscription n'est pas silencieuse : le joueur doit consentir, fournir un email et suivre les lien de vérification unique. Un jeton de serveur de jeu ne peut pas créer ou usurper l'identité de joueurs. Voir Tutoriel : intégrer des joueurs avec une clé publique, et le tutoriel sur le serveur dédié pour un jeu qui embarque également un serveur.
