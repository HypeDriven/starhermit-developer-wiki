Scripts de jeu

Un jeu faisant autorité StarHermit peut être défini par un fichier JavaScript unique exécuté côté serveur dans un bac à sable Jint moteur. Le script est la seule autorité sur les règles de ce jeu : il valide chaque commande du joueur, mute l'état, décide de ce que chaque client peut voir, calcule l'Elo et met fin aux parties. Les clients n’ont aucune autorité. Cette page documente le runtime JavaScript ; les jeux qui nécessitent une autre langue peuvent à la place implémenter le Serveur de jeu de conteneur protocole. Les deux utilisent la même face au joueur API de jeux. L'exemple concret tout au long est celui des échecs - l'implémentation de référence à HypeDriven/starhermit-échecs.

Modèle d'exécution

  • Un fichier JS par jeu, exécuté dans un nouveau moteur Jint en bac à sable par invocation. Rien ne persiste en mémoire entre les appels : tout l'état réside dans les documents que vous renvoyez.
  • Pas d'ambiance Date ou Math.random. Le temps et le hasard sont fournis sous la forme : ctx.now (ms époque) et ctx.random (flotter dans [0, 1)).
  • La plateforme appelle le script lorsqu'un joueur envoie une commande durable, lorsqu'une session est créée et périodiquement. onTick balayages (voir API de jeux – Minutage d'exécution). Temps réel {type:"input", realtime:true} les frames sont l'exception : ils sont mis en mémoire tampon et livrés par lots au tick suivant.

Points d'entrée

Exposer les gestionnaires sur globalThis.game. Six en option statique des déclarations les côtoient : tickRateHz demande à la plateforme à quelle fréquence appeler onTick — déclarez-le si votre jeu dépend du cocher, puisqu'un jeu qui ne dit rien est coché une fois toutes les quatre secondes (voir Taux de tick), achievements enregistre les succès du jeu (voir Réalisations), replays demande à la plateforme de conserver vos sessions terminées (voir Rediffusions), persistent pauses séances au lieu de les terminer lorsque tout le monde part (voir Sessions persistantes), linkedAchievements nomme d'autres jeux dont vous recevez les déverrouillages ctx.linkedAchievements (voir Réalisations d'autres jeux), et queues déclare les formes de match matchmaking acceptées (voir Jeux — Matchmaking). Un jeu qui déclare qu'aucune file d'attente n'a un 1v1 implicite :

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

Les déclarations sont lues en évaluant votre script quand le jeu est publié ou mis à jour, pas à chaque appel - il doit donc s'agir de valeurs statiques sur le game objet. Publier une mise à jour pour appliquer un changement.

  • createSession(ctx) - appelé lorsqu'une session est créée (matchmaking, invitation-acceptation, pratique de l'IA ou démarrage d'une salle en temps réel - voir Séances en salle).
  • onPlayerMessage(ctx) - a appelé à des commandes client durables reçues via le gameplay WebSocket. Entrées explicitement marquées realtime:true contourner ce point d’entrée.
  • onMembershipChange(ctx) - facultatif. Appelé lorsqu'un joueur rejoint ou quitte une session en cours (un salle de participation en cours, ou un inviter à un jeu en cours). ctx.players reflète déjà le changement, et ctx.membership est { change: "joined" | "left", userId, name, team, slot }. Retour { ok: false } refuser une jointure ; un script sans ce hook refuse chaque jointure. Un congé est définitif quel que soit votre retour. Les réalisations et les scores peuvent influencer le résultat ; un sessionState est ignoré.
  • onTick(ctx) — appelé par le service timer de la plateforme au taux de tick effectif ; les dernières entrées en temps réel sont disponibles dans ctx.inputs. Un jeu résolu à 0 Hz ne reçoit pas d'appels périodiques, mais la fonction doit toujours être présente pour satisfaire le contrat de script.

Objet contextuel

ctx = {
  now: 1721473200000,              // ms epoch, from the host clock
  random: 0.7231,                  // float in [0, 1), from the host RNG
  sessionId: "0f8fad5b-...",       // current session id
  pausedMs: 0,                     // persistent games only: total ms this session has spent paused
  players: [                       // session participants
    { id: "7c9e6679-...", name: "alice" },
    { id: "00000000-0000-4000-8000-00000000a1a1", name: "The House", ai: true }
  ],
  sessionState: { /* ... */ },     // this script's session document, or null
  playerStates: {                  // per-player documents (elo, history), or null
    "7c9e6679-...": { elo: 1200, wins: 4, losses: 2, draws: 1, /* ... */ }
  },
  message: {                       // onPlayerMessage only
    from: "7c9e6679-...",          // the authenticated user id — trusted
    data: { type: "move", from: "e2", to: "e4" }  // client payload — untrusted (example: a chess move)
  },
  inputs: [                        // onTick only; omitted when none are pending
    { from: "7c9e6679-...",        // authenticated sender id — trusted
      data: { type: "input", seq: 42, mx: 0.7, mz: -0.2 } }
  ]
}
  • Le siège AI (le cas échéant) est signalé par ai: true sur son entrée de joueur.
  • Un jeu qui déclare linkedAchievements obtient également ctx.linkedAchievements: { <playerId>: { <otherSlug>: [unlocked keys] } }, relisez à chaque invocation. Voir Réalisations d'autres jeux.
  • Les sessions liées à la salle (démarrées à partir d'une salle en temps réel) reçoivent deux champs ctx supplémentaires, ctx.room et ctx.presence, sur chaque invocation — voir Séances en salle.
  • Ne faites confiance à rien de ctx.message.data ou ctx.inputs[].data. L'identité de confiance est la correspondance from, que le serveur attache à partir de la connexion authentifiée — le client ne peut jamais le fournir ou l'usurper.
  • Les entrées optent pour le traitement par lots avec {type:"input", realtime:true, ...}. Non marqué input les commandes restent durables onPlayerMessage appelle à une compatibilité ascendante. Les entrées en temps réel utilisent un emplacement en attente par expéditeur : le mouvement correspond aux dernières victoires, tandis que pass, shoot, et tackle les bords d'action sont fusionnés afin qu'un échantillon de mouvement suivant ne puisse pas les effacer avant le prochain tick. Les scripts doivent bloquer et valider chaque valeur lors de la consommation du lot.

Taux de tick

La plateforme fonctionne onTick balayages par session active à un taux configurable. Votre script demande le tarif qu'il souhaite en déclarant un static tickRateHz sur l'objet de jeu, à côté des points d'entrée :

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • La déclaration est lue lorsque votre jeu est publié ou mis à jour, pas à chaque tick. Publiez une mise à jour après l'avoir modifiée.
  • Un jeu qui déclare aucun taux est coché à 0,25 Hz – une fois toutes les quatre secondes. C'est suffisant pour décider d'un chronomètre de déplacement ou d'un timeout et ne coûte presque rien à la plateforme, mais c'est beaucoup trop lent pour tout ce dont dépend votre gameplay. Si onTick pilote votre jeu, déclarez le taux dont vous avez besoin.
  • Les requêtes sont limitées au maximum de la plateforme (30 Hz par défaut), donc un jeu peut demander moins que ce que la plateforme permet mais jamais pour plus. Demander 0 pour désactiver complètement les ticks pour un jeu qui ne réagit qu'aux commandes du joueur.
  • Les tarifs peuvent être fractionnaire: 0.5 est une coche toutes les deux secondes. Le plus petit taux non nul est 0.01 Hz — un nombre positif plus petit lui est attribué plutôt que d'être lu comme une option de non-participation, car un la petite fraction est un jeu lent. La coche est désactivée uniquement pour 0 ou un taux négatif. Un disparu ou déclaration inutilisable (une chaîne, null, NaN) prend la valeur par défaut de 0,25 Hz.
  • Un opérateur peut modifier le tarif d'un jeu particulier, dans les deux sens.
  • Les entrées en temps réel sont les dernières victoires entre les ticks, tandis que les fronts d'action discrets restent ordonnés. Un destinataire lent peut ignorer un instantané obsolète mais ne peut pas retarder la simulation ou les autres destinataires.

Rediffusions

Lorsqu'une session se termine, la plateforme peut conserver son statut final sessionState comme le rejouer — le document signifié par GET /api/v1/games/{slug}/replays/{sessionId} (voir API de jeux – Replays). Une rediffusion est conservée aussi longtemps que le record du match. c'est, donc votre jeu en obtient un seulement s'il le demande:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • La déclaration doit être un littéral true ou false — tout le reste est lu comme aucune déclaration, et un jeu qui ne déclare rien n'a pas de rediffusion.
  • C'est lu lorsque votre jeu est publié ou mis à jour. Publiez une mise à jour après l'avoir modifiée.
  • Un opérateur de plateforme peut répondre d'une manière ou d'une autre pour un jeu particulier, la déclaration est donc une demande plutôt qu'une garantie. GET /api/v1/games/{slug} rapporte la réponse comme replaysEnabled — branchez votre interface utilisateur de relecture sur cela, pas sur ce que votre script a demandé.
  • Rien d'autre ne change lorsque les replays sont désactivés : l'état de votre session est toujours stocké et toujours restitué à chaque invocation comme ctx.sessionState, et c'est toujours le point de restauration en cas de crash. Quel jeu sans replays, on n'obtient pas une copie qui survit à la session, donc ses points de terminaison de replay répondent 404.
  • Concevoir la finale sessionState pour valoir la peine d'être rejoué - un journal de déménagement ou tout ce dont votre client a besoin pour reconstituer le match. L'implémentation de la référence d'échecs conserve state.game.moves et le fait avancer via le même module de règles que la plateforme exécute.

Sessions persistantes

Un jeu qui déclare persistent: true maintient ses sessions lorsque chaque joueur part. Environ 15 secondes après la dernière déconnexion, la session est en pause - Non onTick appels - et le premier le lecteur pour se reconnecter le reprend. La déconnexion ou l'inactivité met la session en pause au lieu de l'abandonner. Un résultat de jeu, propriétaire une action, un départ explicite du dernier membre, une expiration de rétention configurée ou un échec de récupération de terminal peuvent quand même y mettre fin. Voir Cycle de vie des sessions.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • Doit être un littéral true ou false. C'est lu lorsque votre jeu est publié ou mis à jour.
  • ctx.now reste l'horloge murale. Les sessions persistantes obtiennent également ctx.pausedMs, le temps total passé fait une pause, alors ctx.now - ctx.pausedMs est une horloge qui s'arrête alors que personne n'est là.
  • Les sessions interrompues sont prises en compte dans le plafond de sessions par joueur. Donnez donc aux joueurs une commande qui met fin à une session. monde avec un result.

Voir le tutoriel sur les sessions persistantes pour un exemple concret et le flux client.

Disposition des sièges pour le matchmaking

De nouvelles sessions de matchmaking reçoivent ctx.matchmaking sur chaque invocation (créer, commander et cocher). Il préserve la forme de la file d'attente et les sièges même si le jeu est redéployé ultérieurement :

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players contient uniquement des sièges occupés, avec team et ai:true pour l'IA. Les index des équipes/emplacements sont base zéro. Les identifiants IA sont stables au sein de cette session et ne sont pas des identifiants de compte StarHermit. Seuls les humains avoir un abonnement à une session/chat et peut recevoir des écritures sur l'état du joueur, la note ou les réalisations du compte. Conserver l'état de l'IA sessionState. Copiez les champs de liste dont les clients ont besoin dans l'état de votre jeu ou des émissions. Les sessions plus anciennes et les sessions sans matchmaking peuvent être omises ctx.matchmaking.

Déclarez une date limite de début et le nombre maximum d'IA dans starhermit.txt. Avec le nombre d'IA 0, les sièges vacants restent vides. Le même contexte est fourni aux serveurs de conteneurs.

Séances en salle

Une séance peut être lié à une salle en temps réel: quand un salle en temps réel pour un jeu avec un server= Le script démarre, la plateforme crée une session à N joueurs pour la salle humain participants (les sièges IA n'existent que dans la liste orientée script). C'est ainsi que fonctionnent les jeux en temps réel faisant autorité sur le serveur (par exemple le football) : les salles fournissent le lobby/le matchmaking, le script gère le match. Voir Salles en temps réel – le pont pour le cycle de vie côté pièce.

Chaque invocation (createSession, onPlayerMessage, onTick) d'une session liée à la salle reçoit deux champs ctx supplémentaires :

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online — l'utilisateur dispose d'un socket live sur l'un ou l'autre registre de connexion (salles en temps réel ou ws/v1/games).
  • presence.left — l'utilisateur ne détient plus de siège actif : il est explicitement parti et son siège a été converti en participant IA. left est permanent ; online peut battre. Le script devrait piloter la logique de prise de contrôle/rejoindre l’IA à partir de ces indicateurs.
  • La liste est relue à chaque invocation, de sorte que les conversions de sièges (humain → IA) apparaissent au fur et à mesure qu'elles se produisent.

Lorsqu'un script lié à la salle revient result, la plateforme termine la session, stocke le résultat dans la pièce et ferme la pièce — aucun résultat soumis par l'hôte n'est impliqué.

L’inverse n’est pas vrai : une salle fermant ne termine pas sa session. Si la salle se ferme en premier (par exemple parce que son dernier humain a quitté la salle sans participation en cours – jamais simplement parce que l'hôte s'est déconnecté, ce qui déplace uniquement le rôle d'hôte pendant que la session est active), la session continue de s'exécuter, ctx.room.roster devient vide et chaque humain montre left: true. Retour result alors si le match doit se terminer avec la salle. Voir Salles en temps réel – la règle de l'hôte de 60 secondes et les sessions limitées à la salle.

Forme de retour

Chaque point d'entrée renvoie la même forme (tous les champs sont facultatifs sauf ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

Règles clés :

  • sessionState et chaque entrée de playerStates remplacer les documents stockés - renvoyez toujours des documents complets, jamais de différences.
  • Seuls les messages répertoriés dans broadcast sont livrés aux clients, chacun adressé à des identifiants de joueur explicites ou "all". Rien d'autre ne fuit.
  • eloUpdates C'est la seule façon dont les notes changent. Les valeurs appartiennent à chaque joueur nouvelle note absolue, appliqué tel qu'envoyé — la plateforme ne plafonne pas le changement par match, alors fixez-le vous-même (voir Elo par match). L'hôte les utilise pour le matchmaking et les publie dans le classement du jeu ; les clients ne peuvent jamais soumettre leurs scores directement (voir Classements). Conservez la note dans playerStates[id].elo donc celui d'un propriétaire réinitialisation de la note atteint également votre copie.
  • achievements C'est la seule façon d'obtenir des réalisations. Les clés sont résolues en fonction des réalisations du jeu — déclarées ou créées par son propriétaire — et conservées par la plateforme ; voir Réalisations.
  • scores est la seule façon pour les classements de votre jeu de changer — voir Classements.
  • Terminer les jeux via result. L'hôte termine ensuite la session, et pour un jeu avec rediffusions archive la finale sessionState comme la rediffusion (servie par GET .../replays/{sessionId} - voir API de jeux).

Réalisations

Votre script est le seulement chose qui peut débloquer les succès de votre jeu. Il n'y a pas de client point final pour eux : POST /api/v1/me/achievements/unlock rejette catégoriquement les réalisations à l'échelle du jeu, et les points de terminaison CRUD de l'éditeur refusent d'y toucher. Le propriétaire du jeu peut ajouter des succès à côté ceux déclarés à travers /me/github-games/{id}/achievements; votre script les déverrouille par clé exactement de la même manière. Cela fait des réalisations en tant que serveur- fait autorité comme le reste du jeu, et c'est le mécanisme n'importe lequel jeu avec un server= scénario devrait utiliser - y compris celui dont le gameplay se déroule ailleurs (voir quels jeux peuvent utiliser cela).

Déclarer

Un statique achievements tableau sur le game objet. Seulement key est requis :

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
Champ Taper Remarques
key chaîne Requis. Identifiant stable, ≤ 128 caractères, unique dans le jeu. Les doublons après le premier sont ignorés.
name chaîne La valeur par défaut est key.
description chaîne La valeur par défaut est "".
icon chaîne URL facultative.
secret booléen Caché d'un joueur jusqu'à ils débloquez-le. La valeur par défaut est false.
points nombre Serré entre 0 et 10 000. La valeur par défaut est 0.

Le tableau est appliqué lorsque le jeu est publié ou mis à jour :

  • Les définitions correspondent à key — la modification d'un nom, d'une icône, de points ou d'un drapeau secret met à jour la définition existante et tous ceux qui l'ont déjà gagné la conservent.
  • Une clé que vous arrêtez de déclarer est supprimée seulement tant que personne ne l'a déverrouillé. L'historique gagné n'est jamais détruit, donc un succès retiré reste visible pour les joueurs qui le détiennent.
  • Au plus 100 réalisations par match ; les extras au-delà de cela sont supprimés.
  • La déclaration est meilleur effort: les entrées mal formées sont ignorées. Confirmez toujours les définitions publiées avec GET /api/v1/games/{slug}/achievements après avoir mis à jour le jeu.

Ouvrir

Renvoyez un achievements carte de n'importe lequel point d'entrée - createSession, onPlayerMessage, ou onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • Les déverrouillages sont idempotent - réaffirmer une clé que le joueur détient déjà est une opération impossible, donc un script peut attribuer en toute sécurité une condition qu'il réévalue à chaque tick au lieu de suivre "déjà récompensé" dans son propre état.
  • Les clés inconnues (ni déclarées ni créées par le propriétaire du jeu), les utilisateurs qui ne participent pas à cette session et le siège IA sont ignorés en silence.
  • Au plus 32 les clés sont acceptées par joueur et par invocation ; les autres clés du même tableau sont supprimées.
  • Les lignes sont conservées avec le reste des écritures de l'invocation, de sorte qu'un déverrouillage ne peut pas survivre à un échec d'invocation.

Livraison

Chaque déverrouillage nouvellement accordé est transmis au joueur qui gagne. ws/v1/games comme un cadre distinct - c'est la vérité de la plateforme, pas une de vos broadcast messages :

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

Déblocages accordés à partir de createSession atterrissent avant qu'une socket n'existe, donc ils arrivent sans cadre - les clients devraient lire GET /api/v1/games/{slug}/achievements en charge et traitez le châssis comme le chemin de mise à jour en direct. Pleine surface en Réalisations.

Classements

Outre le tableau elo, votre jeu peut avoir des classements créés par son propriétaire via POST /api/v1/me/github-games/{id}/leaderboards, chacun avec un key. Postez-leur en retournant scores depuis n'importe quel point d'entrée — clé du tableau → identifiant du joueur → numéro :

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • Chaque joueur garde son meilleur score sur chaque tableau, selon la direction de tri du tableau, alors signalez chaque résultat – le pire est simplement ignoré.
  • Seuls les participants à la session comptent. Clés inconnues ou inactives, et scores hors règles du plateau, sont abandonnés en silence. Au maximum 16 planches par retour.
  • Contrairement à eloUpdates, rien n'est publié sur playerStates — conservez votre propre copie playerStates si le jeu doit relire un record personnel.

Où votre script s'exécute

Un script qui récidive sans limite, épuise sa mémoire ou dépasse son budget temps échoue. invocation. Son résultat raté n'est pas appliqué. La commande ou la coche signale l'un des éléments suivants :

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

La part de votre jeu sur le serveur

  • L'heure du scénario. Toutes les sessions d'un jeu partagent un budget de temps de script, 2 000 ms par seconde par par défaut, facturé de ce que chaque invocation a réellement pris. Un jeu sur sa part est plutôt refusé que mis en file d'attente : une coche est ignorée, une commande reçoit une réponse avec "Ce jeu utilise plus que sa part du serveur en ce moment ; réessayez sous peu.", et la création d'une session renvoie 429.
  • Commandes. Chaque joueur peut envoyer 20 commandes durables par seconde et par session (avec une courte rafale allocation); au-delà de cela, une commande reçoit une réponse avec un error cadre, "Trop de commandes ; ralentir." Le cadre n'inclut pas de statut HTTP. La saisie en temps réel est limitée séparément.
  • Résultats. Le résultat avec lequel une session se termine peut être d'au plus 64 Ko ; un plus grand est refusé avec 422.
  • Taille du script. A server= le script peut faire au maximum 2 Mo ; un plus grand est refusé avec 422 avant il est stocké ou analysé.

Les opérateurs peuvent augmenter ou diminuer chacun de ces éléments pour un jeu individuel.

Budgets

Les scripts s'exécutent avec ces budgets de ressources :

  • ~ 250 ms CPU par appel
  • 32 Mo de mémoire
  • Un plafond de déclaration par invocation
  • Un budget d'octets d'état par joueur : tous les documents d'état doivent rester sérialisables et petits
  • Les valeurs s'imbriquent au maximum à 64 niveaux lorsqu'elles deviennent du texte. Tout ce qu'un point d'entrée renvoie, chaque déclaration, JSON.stringify, et Array.prototype.join/toString/toLocaleString refuser un une valeur plus profonde avec un RangeError (un retour échoue à l'invocation : "imbriqué sur plus de 64 niveaux profond"). JSON.parse déjà arrêté à 64, donc une valeur plus profonde ne pourrait jamais faire un aller-retour. flat s'aplatit jusqu'à 64 niveaux et se lance si le tableau s'emboîte plus profondément - y compris un tableau qui contient lui-même.
  • Un appel ne peut pas allouer plus que le budget mémoire. repeat, padStart/padEnd, concat et replace/replaceAll lancer RangeError: Invalid string length quand le résultat pourrait dépasser la moitié le budget en caractères (16 Mo avec la valeur par défaut de 32 Mo ; un remplacement d'expression régulière est limité comme si chaque position correspondante, ce qui n'affecte que les chaînes d'environ un million de caractères ou plus). ArrayBuffer et les tableaux tapés lancent RangeError au-delà du budget en octets et des tableaux au-delà Le budget/8 éléments est refusé. Le budget est également vérifié après le retour de votre crochet, donc un la déclaration finale en cas de dépassement de budget fait échouer l'invocation au lieu de réussir.

Le script de référence des échecs garde volontairement ses documents petits - pour exemple de respect du budget, son document par joueur est

{
  elo: 1200,
  wins: 0, losses: 0, draws: 0,
  lastColorVs: "9b2f8c1a-...",        // for color alternation on rematch
  lastColorOrder: "w",
  recentGames: [ /* up to 30 summaries */ ]
}

Le plafond de sessions simultanées est de 20 par joueur par défaut.

La fenêtre lisible par la plateforme

Tout dans sessionState est opaque à la plateforme sauf un champ :

sessionState.summary = {
  turnPlayerId: "7c9e6679-...",
  deadline: 1784642591000,
  status: "active",
  moveCount: 41
};

deadline est un horodatage Unix entier dans millisecondes, ou omis lorsqu'il n'y a pas de date limite. Une chaîne de date ISO n'est pas reconnue. turnPlayerId est l'UUID du joueur.

GET /api/v1/games/{slug}/sessions/mine lit summary calculer myTurn et deadline pour l'appelant. Gardez-le précis à chaque changement d’état ; conservez tout le reste là où votre script le souhaite.

Exemple concret : le script d'échecs

Tout dans cette section est spécifique à l'implémentation de référence des échecs - la forme de l'état, l'encodage du plateau, le jeu de commandes, les raisons de fin de partie, la constante Elo, l'IA et les délais d'attente ci-dessous sont les propres choix des échecs, définis dans son script. Rien de tout cela n’est lié au comportement de la plateforme ; votre jeu définit ses propres équivalents.

État de la session :

{
  white: "7c9e6679-...",
  black: "9b2f8c1a-...",
  aiId: "00000000-0000-4000-8000-00000000a1a1",   // present in AI games
  game: {
    board: "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr", // 64 chars
    turn: "w",
    castling: { K: true, Q: true, k: true, q: true },
    epSquare: null,
    halfmoveClock: 0,
    fullmove: 1,
    moves: [ { from: "e2", to: "e4", promo: null, san: "e4", at: 1721473200000 } ],
    positionCounts: { /* fen-key: count, for threefold repetition */ },
    status: "active"
  },
  createdAt: 1721473200000,
  deadline: 1721559600000,
  result: null,
  drawOfferBy: null,
  summary: { turnPlayerId: "...", deadline: "...", status: "active", moveCount: 1 }
}

Encodage de la carte : une chaîne de 64 caractères où index = rank * 8 + file et a1 est l'indice 0. PNBRQK sont des pièces blanches, pnbrqk noir, . est un carré vide.

Commandes gérées par onPlayerMessage: sync, move, resign, offer-draw, accept-draw, decline-draw (formes de fils dans API de jeux).

Jeu terminé reason valeurs: checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

Autres spécificités des échecs :

  • Élo utilise K=32, calculé en finishGame lorsqu'une partie se termine, et renvoyé via eloUpdates.
  • Jeu IA : lorsque le siège AI doit bouger, aiReply joue "hal" - un moteur gourmand de capture de matériaux - dans la même invocation. Il n'y a pas de bot externe.
  • Délais d'attente : onTick décide du chronomètre des mouvements de 24 heures - si aucun coup n'a été joué, le jeu est un timeout-no-moves dessiner; sinon le joueur qui bouge perd de timeout.

Déploiement

Déclarez le script dans le référentiel de votre jeu starhermit.txt manifeste:

server=server.js

La publication s'effectue via l'intégration GitHub — voir Jeux GitHub. La plateforme exécute le script dans les limites des budgets documentés. Ne combinez pas server= avec container.image=; utiliser le environnement d'exécution du conteneur à la place lors de l'expédition d'une image.

Meilleures pratiques

  • Validez chaque commande. Traiter ctx.message.data comme hostile : vérifiez les types, les portées, l'ordre du tour et le statut du jeu avant de toucher l'état.
  • Gardez les invocations rapides et les états petits. Vous disposez d'environ 250 ms et d'un budget d'octets par document de lecteur ; le script de référence des échecs, par exemple, majuscules recentGames à 30 entrées pour cette raison.
  • Utiliser ctx.now / ctx.random seulement. Non Date, Non Math.random — l'hôte possède l'horloge et les dés.
  • Conception broadcast messages comme seul contrat client. Les clients doivent être capables de restituer l'intégralité du jeu à partir de ce que le script envoie ; tout ce qui n'est pas diffusé n'existe pas pour eux.
  • Un fichier, deux surfaces. Le même fichier peut servir de règles côté client via une exportation distincte : l'implémentation de référence d'échecs, par exemple, expose globalThis.chessRules pour le navigateur (aperçu de déplacement, conseils de validation) et globalThis.game pour l'hôte. Une source de vérité, aucune autorité sur le client.
  • Terminez toujours les jeux via result ainsi la plateforme publie les mises à jour d'Elo et archive le replay lorsque votre jeu est terminé. rediffusions.
