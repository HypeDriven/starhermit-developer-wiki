Réalisations

Une réalisation appartient exactement à un propriétaire, et le propriétaire décide qui est autorisé à le déverrouiller :

Propriétaire Déclaré par Débloqué par Utilisez-le pour
Un jeu faisant autorité game.achievements dans un script, ou achievements à partir d'un conteneur /describe — ou par le propriétaire du jeu à travers /me/github-games/{id}/achievements Le runtime du serveur du jeu uniquement — faisant autorité sur le serveur Jeux avec un server= script ou container.image= back-end
Un titre de catalogue (SoftwareTitle) Un éditeur, via le API de l'éditeur Le client du joueur, via POST /api/v1/me/achievements/unlock (droit requis) Titres distribués dont le client est le seul à savoir que le joueur a gagné quelque chose

Les deux s’excluent mutuellement et la plateforme applique la séparation :

  • POST /api/v1/me/achievements/unlock refuse les réalisations à l'échelle du jeu — un client ne peut jamais en réclamer un.
  • Les points de terminaison CRUD de l’éditeur les refusent également. Vous n'avez pas besoin d'un éditeur pour un jeu que vous possédez : comme son propriétaire, toi sont son éditeur, et vous gérez ses réalisations à travers les points de terminaison du propriétaire plutôt.

URL de base : https://api.starhermit.com. Tous les itinéraires sont sous /api/v1/....

Méthode Chemin Authentification Description
OBTENIR /api/v1/games/{slug}/achievements Porteur Réalisations d'un jeu faisant autorité + état de déverrouillage de l'appelant
OBTENIR /api/v1/me/github-games/{id}/achievements JWT (propriétaire du jeu) Chaque réalisation de votre jeu, avec son origin et débloquer le compte
POSTE /api/v1/me/github-games/{id}/achievements JWT (propriétaire du jeu) Créez un succès pour votre jeu → 201
METTRE /api/v1/me/github-games/{id}/achievements/{achievementId} JWT (propriétaire du jeu) Mettez à jour celui que vous avez créé
SUPPRIMER /api/v1/me/github-games/{id}/achievements/{achievementId} JWT (propriétaire du jeu) Supprimez celui que vous avez créé et que personne n'a déverrouillé → 204
OBTENIR /api/v1/software/{titleId}/achievements Anonyme Définitions des réalisations d'un titre de catalogue
OBTENIR /api/v1/me/achievements?titleId= JWT Les déverrouillages de l'appelant (tous les propriétaires ou un titre)
POSTE /api/v1/me/achievements/unlock JWT Déverrouillage réclamé par le client — titres du catalogue uniquement

Lisez les erreurs de manière défensive comme décrit dans Conventions API. POST /me/achievements/unlock renvoie son 400 raison sous forme de texte brut.

Réalisations de jeu faisant autorité sur le serveur

C'est le mécanisme n'importe lequel le jeu doit être utilisé lorsqu'il dispose d'un backend de script ou de conteneur. Le le runtime du serveur est le seul rédacteur. Il doit valider que le joueur a gagné chaque déverrouillage ; rejeter les soumissions directes d'API ne valident pas à elles seules les événements signalés par un client modifié.

1. Déclarez-les dans votre script

Ajouter un statique achievements tableau au game objet - voir Scripts de jeu — Réalisations pour le contrat complet :

globalThis.game = {
  achievements: [
    { key: "first-win",  name: "First Win",  description: "Win a match.", points: 10 },
    { key: "flawless",   name: "Flawless",   description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

La déclaration est lue quand le jeu est publié ou mis à jour de son référentiel. Publiez une mise à jour pour appliquer une modification.

2. Déverrouillez-les depuis n’importe quel hook de cycle de vie

Renvoyez un achievements map — identifiant utilisateur → tableau de clés — à partir de createSession, onPlayerMessage, ou onTick:

return {
  ok: true,
  sessionState: state,
  achievements: { [winnerId]: ["first-win", "flawless"] },
  result: { kind: "win", winner: winnerId }
};

Les déverrouillages sont idempotent — rendre une clé que le joueur détient déjà est une opération impossible, donc un script peut réaffirmez une réussite à chaque tick sans vous soucier des doublons.

3. Le joueur est averti via le socket de jeu

Chaque déverrouillage nouvellement accordé est transmis uniquement au joueur gagnant, le ws/v1/games, comme son propre cadre type (vérité de la plateforme, pas un script relayé game message):

{
  "type": "achievement",
  "data": {
    "key": "first-win",
    "name": "First Win",
    "description": "Win a match.",
    "icon": null,
    "points": 10,
    "unlockedAt": "2026-07-25T09:14:02Z"
  }
}

Déblocages accordés à partir de createSession sont persistés avant que quiconque ait un socket, ils arrivent donc avec pas de cadre - lisez-les à partir du point de terminaison de la liste lors du chargement.

Backends de conteneurs

Un conteneur déclare les mêmes champs de réussite dans GET /describe, puis envoie un achievements message sur son contrôle WebSocket. La plateforme applique la même clé, participant, idempotence et règles de livraison. Voir Serveurs de jeux de conteneurs.

GET /api/v1/games/{slug}/achievements

Chaque réussite déclarée par le jeu, avec l'état de déverrouillage de l'appelant. 404 si la limace n'a pas définition de jeu faisant autorité (un jeu sans script ni backend de conteneur n'a aucun jeu appartenant réalisations — voir Quels jeux peuvent utiliser cela). Les réalisations secrètes sont cachées jusqu'à ce que le l'appelant les déverrouille. Classé par création, puis clé.

[
  {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "key": "first-win",
    "name": "First Win",
    "description": "Win a match.",
    "icon": null,
    "secret": false,
    "points": 10,
    "unlocked": true,
    "unlockedAt": "2026-07-25T09:14:02Z"
  }
]

Fonctionne avec un JWT utilisateur complet ou un jeton de lancement à l'échelle du jeu.

Quels jeux peuvent utiliser cela

Le mécanisme est disponible pour un jeu qui déclare soit un server= un script ou un container.image= back-end dans starhermit.txt. Le l'exécution du serveur rend le déverrouillage faisant autorité. Les cas d'utilisation basés sur des scripts incluent :

  • Jeux de plateforme scriptés — débloquer depuis onPlayerMessage / onTick au fur et à mesure que le match se déroule.
  • Jeux en temps réel dans une salle — a salle en temps réel pour un jeu avec un server= le script crée une session liée lorsqu'il démarre, et chaque hook de celle-ci la session peut accorder des réalisations.
  • Jeux solo et entraînements — une session contre le siège AI (POST /api/v1/games/{slug}/sessions/ai) exécute le même script et le même chemin de déverrouillage.
  • Jeux en temps réel routés par l'hôte — un jeu dont le gameplay s'étend sur canal binaire de salle en temps réel peut toujours expédier un script serveur uniquement en tant qu'autorité de réalisation : le démarrage de la salle crée la session liée et le script récompenses de createSession / onTick / durable cmd messages envoyés ws/v1/games tandis que le le chemin rapide continue de couler ws/v1/realtime.

Les sessions sauvegardées sur des conteneurs peuvent également déclarer et accorder des réalisations via leur protocole. Un jeu avec pas de backend faisant autorité (un jeu par navigateur pur, ou construit uniquement sur le relais homologue) n'a pas de chemin de déverrouillage faisant autorité sur le serveur. Le déverrouillage revendiqué par le client est disponible uniquement pour titres distribués dans le catalogue, ci-dessous.

Limites et règles

Règle Valeur
Réalisations déclarées par match 100 (extras ignorés)
Longueur de la clé de réussite 128 caractères
Clés de déverrouillage acceptées par joueur, par invocation 32
points fixé à 0-10 000 ; la valeur par défaut est 0
name par défaut le key lorsqu'il est omis
  • Une entrée de déclaration mal formée est ignoré. Un script qui ne parvient pas à évaluer génère un message vide liste; la déclaration d'un conteneur est lue après avoir passé les contrôles de santé. Vérifiez avec GET /api/v1/games/{slug}/achievements après le déploiement.
  • Définitions renversées par key. Une clé que votre backend cesse de déclarer est supprimée seulement si personne n'a je l'ai débloqué - l'histoire acquise n'est jamais détruite. Réalisations créées par le propriétaire via l'API ne sont jamais touchés par cela : seuls ceux déclarés sont réconciliés.
  • Les déverrouillages pour les utilisateurs qui ne participent pas à la session et pour le siège AI sont ignorés.

Réalisations d'autres jeux

Un jeu peut ouvrir des fonctionnalités en fonction de ce que le joueur a débloqué un autre jeu : une suite honorant l'original, ou des jeux d'une série partageant des produits cosmétiques. Il existe deux manières de les lire.

Depuis votre serveur : ctx.linkedAchievements (confiance)

Nommez les autres jeux de votre script, à côté de vos autres déclarations :

globalThis.game = {
  linkedAchievements: ["83fd04b1-3cbe-4b09-a251-3733ad4b9d94"], // other games' slugs (uids)
  // ...
};

Un conteneur renvoie la même chose linkedAchievements tableau de GET /describe. Chaque script le ctx d'invocation transporte alors les clés déverrouillées de chaque joueur humain dans ces jeux :

ctx.linkedAchievements = {
  "7c9e6679-...": {                                   // player id
    "83fd04b1-3cbe-4b09-a251-3733ad4b9d94": ["first-win", "checkmate-10"]
  }
};
  • Il est relu sur chaque invocation, donc un déverrouillage gagné dans l'autre partie en cours de match est visible sur le suivant. Un conteneur le reçoit dans le ctx de POST /sessions, c'est-à-dire à la création et à restaurer.
  • Au plus 8 jeux; entrées qui ne sont pas des chaînes non vides, des doublons et des slugs supérieurs à 100 les caractères sont supprimés. Comme les autres déclarations, elle est lue lors de la publication du jeu ou mis à jour.
  • Un jeu qui déclare que rien n'obtient non linkedAchievements champ et ne paie rien.
  • Utilisez cette voie pour tout ce que la plateforme doit imposer, comme débloquer un jeu ou accorder un réalisation de votre propre.

De votre client : GET /api/v1/games/{slug}/linked-achievements/{otherSlug}

Celui de l'appelant se déverrouille otherSlug. Il ne nécessite aucune déclaration, donc un jeu sur navigateur uniquement sans le serveur peut l'utiliser et il fonctionne avec le jeton de lancement pour {slug}: les propres points de terminaison de l'autre jeu restez à l'écart de ce jeton.

{
  "game": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "hidden": false,
  "unlocked": [
    { "key": "first-win", "unlockedAt": "2026-07-25T09:14:02Z" }
  ]
}

Un client peut mentir sur ce qu’il a reçu, alors considérez cela comme un indice concernant l’interface utilisateur et les cosmétiques, et non comme une preuve.

Ce qui est divulgué

  • Déverrouillez uniquement l'état du jeu que vous avez nommé: clés et heures de déverrouillage, jamais de noms, descriptions ou la liste des autres jeux auxquels le joueur a joué. Un succès secret que le joueur a débloqué est inclus.
  • Une limace qui ne correspond à aucun jeu répond comme un jeu sans rien débloqué.
  • La vie privée est respectée. Un joueur dont la confidentialité des réalisations est Private est caché: absent de ctx.linkedAchievements, et "hidden": true avec une liste vide du point de terminaison. Caché n'est pas la même chose que "n'en a pas", alors ne le traitez pas comme tel. FriendsOnly (le défaut) est divulgué, parce que le lecteur agit pour le joueur.

Succès créés par le propriétaire du jeu

Déclarer les succès dans le code n'est pas le seul moyen d'en donner à votre jeu. Si vous possédez un jeu avec un server= script ou container.image= backend, vous pouvez également créer des réalisations pour celui-ci via le API : comme le fait un éditeur pour un titre de catalogue, sans compte ni autorisation d'éditeur requis. Posséder le jeu représente la totalité de la subvention. Utilisez-le lorsqu'un concepteur souhaite ajouter ou reformuler réalisations sans changement de code, ou lorsque votre backend accorde des clés qu'il ne déclare pas.

Seul le serveur de votre jeu peut les débloquer, exactement comme ceux déclarés : votre script renvoie la clé dans achievements, ou votre conteneur l'envoie sur le canal de contrôle. Rien ne change sur le côté déverrouillage — les clés sont résolues contre tous des réalisations du jeu, déclarées et créées.

{id} est l'identifiant de votre jeu GET /api/v1/me/github-games.

POST /api/v1/me/github-games/{id}/achievements

{
  "key": "speedrunner",
  "name": "Speedrunner",
  "description": "Finish a level in under a minute.",
  "icon": "https://cdn.example/speedrunner.png",
  "secret": false,
  "points": 25
}

key, name et description sont nécessaires. Retours 201:

{
  "id": "…",
  "key": "speedrunner",
  "name": "Speedrunner",
  "description": "Finish a level in under a minute.",
  "icon": "https://cdn.example/speedrunner.png",
  "secret": false,
  "points": 25,
  "origin": "owner",
  "unlocks": 0,
  "createdAt": "…",
  "updatedAt": "…"
}

GET sur le même chemin répertorie toutes les réalisations du jeu sous cette forme : origin est declared pour ceux que votre script ou conteneur déclare et owner pour ceux créés ici, et unlocks compte combien de joueurs détiennent chacun.

PUT .../achievements/{achievementId} prend n'importe lequel de name, description, icon, secret et points; le key ne peut pas changer. DELETE le supprime.

Règles

Règle Valeur
Clé 1 à 128 caractères : lettres, chiffres, ., _, -, commençant par une lettre ou un chiffre
name / description requis; au maximum 200/2000 caractères
points 0 à 10 000 ; la valeur par défaut est 0
Réalisations créées par le propriétaire par jeu 200 (en plus des 100 déclarés)
  • Une réalisation déclarée reste celle de votre code. Créer une clé dont le jeu a déjà des retours 409, tout comme la modification ou la suppression d'un declared un - la prochaine mise à jour le remettrait en tant que code le déclare. Modifiez-le dans votre script ou /describe plutôt.
  • Si votre code déclare ultérieurement une clé que vous avez créée ici, la déclaration prend cette réalisation fini (origin devient declared). Les joueurs qui l'ont mérité le gardent.
  • Un succès débloqué par quelqu'un ne peut pas être supprimé (409).
  • 404 signifie que le jeu ne vous appartient pas ; 409 sur l'une de ces routes avec un message concernant un serveur backend signifie que le jeu n'en a pas - un jeu sur navigateur uniquement n'a rien qui puisse débloquer un réalisation.

Réalisations des titres de catalogue

Pour les logiciels distribués via le catalogue, où le client est le seul à respecter les état de déverrouillage. Les définitions sont lues de manière anonyme ; le déverrouillage nécessite un JWT et un non révoqué droit au titre.

GET /api/v1/software/{titleId}/achievements

AchievementDto[]. Les succès secrets sont masqués à moins qu'ils ne soient déverrouillés par l'appelant (et son criteria est retenu jusque-là). Les réalisations liées au jeu n'apparaissent jamais ici.

[
  {
    "id": "…",
    "key": "…",
    "name": "…",
    "description": "…",
    "icon": "…",
    "secret": false,
    "points": 10,
    "visibility": "…",
    "criteria": "…"
  }
]

POST /api/v1/me/achievements/unlock

{ "achievementDefinitionId": "…" }

Retours 204. Retours 400 lorsque la réalisation n'existe pas, lorsque l'appelant n'a aucun droit au titre (voir catalog.md), ou lorsque la réalisation est à l'échelle du jeu — ce sont accordé uniquement par le script faisant autorité du jeu ou le backend du conteneur. Ré-déverrouiller quelque chose déjà retenu revient 204.

La gestion côté éditeur (définition, mise à jour et suppression des réalisations de titres) réside dans publisher.md.

GET /api/v1/me/achievements

L'appelant se déverrouille lorsque UserAchievementDto[]. Sans titleId cela renvoie à chaque déverrouillage du l'utilisateur détient, à la fois pour le jeu et pour le titre; passer ?titleId= pour le restreindre à un seul titre de catalogue.

[
  {
    "id": "…",
    "achievementDefinitionId": "…",
    "key": "…",
    "name": "…",
    "description": "…",
    "icon": "…",
    "points": 10,
    "unlockedAt": "…"
  }
]

Pour l'écran de réussite d'un jeu, préférez GET /api/v1/games/{slug}/achievements, qui aussi renvoie les définitions du joueur pas encore débloqué.
