Contrats REST

Le fichier REST utilise OpenAPI 3.0.3 et l'origine de l'API publique. Chaque opération renvoie vers sa page de référence, qui contient les règles complètes d’autorisation, de validation, de limites et d’erreur. x-credentials identifie les familles de titres de compétences acceptées ; il ne remplace pas les chèques de propriété ou d'adhésion. x-required-policies décrit les autorisations nommées là où l'API les applique.

Les réponses peuvent inclure des champs supplémentaires. JSON, métadonnées, diagnostics et téléchargement spécifiques au jeu les résultats utilisent des formes ouvertes où la référence du jeu ou du point de terminaison définit leur contenu. Succès les schémas ne garantissent pas que chaque appelant est autorisé. Les erreurs de point de terminaison peuvent être du JSON, du texte brut, réponses vides ou détails du problème de validation ; utiliser analyse de la réponse défensive.

Ne traitez pas les opérations de génération réservées comme un service fonctionnel. Leur contrat décrit le courant 503 overloaded réponse, pas les futurs champs de requête ou le comportement de génération.

Contrats WebSocket

Choisissez un $defs schéma pour le protocole et la direction de votre socket. Par exemple, valider un client cadre de mouvement contre GameRealtimeInput, plutôt que le durable générique GameCommand:

{ "type": "cmd", "data": { "type": "input", "realtime": true, "seq": 1, "x": 0.5 } }

realtime appartient à l'intérieur data. Les champs de jeu qui suivent constituent le contrat de votre jeu. Utilisez un Schéma JSON 2020-12 validateur avec le document de schéma complet afin que les références locales soient résolues. Le document racine contient des définitions ; la sélection d’une définition est nécessaire pour valider un cadre.

Ordre des octets du GUID

Les trois premiers groupes UUID sont en petit-boutiste dans un en-tête d'octet GUID .NET. Par exemple:

UUID:  00112233-4455-6677-8899-aabbccddeeff
Bytes: 33 22 11 00 55 44 77 66 88 99 aa bb cc dd ee ff

Un décodeur de navigateur pour le préfixe de 16 octets :

function guidFromDotNet(bytes) {
  if (bytes.length !== 16) throw new Error('Expected a 16-byte GUID');
  const hex = i => bytes[i].toString(16).padStart(2, '0');
  return `${hex(3)}${hex(2)}${hex(1)}${hex(0)}-${hex(5)}${hex(4)}-${hex(7)}${hex(6)}-` +
    `${hex(8)}${hex(9)}-${hex(10)}${hex(11)}${hex(12)}${hex(13)}${hex(14)}${hex(15)}`;
}

Les préfixes en temps réel identifient participants, tandis que les préfixes vocaux identifient utilisateurs. Un conteneur le flux a un type d'un octet suivi des UUID de session/utilisateur, donc son JSON commence à l'octet 33. Le le relais n'ajoute aucun préfixe. La lecture de chaque socket selon la même disposition binaire corrompt les charges utiles et l'identité.
