Voix

StarHermit Voice fournit des salles vocales par conversation via une API REST (api/v1/voice) plus un WebSocket mixte binaire/texte (ws/v1/voice) pour la signalisation audio et WebRTC. Tous les points de terminaison REST nécessitent une authentification. La disponibilité vocale peut varier. Les corps d’erreur varient ; voir Conventions API.

Les chambres sont ancrées à un conversation en ligne; l'adhésion à la conversation contrôle tout, donc les règles d'amitié dans le chat régissent également la voix (les conversations de session de jeu contournent l'amitié). Limites : 3 salles actives par conversation, max 10 participants par salle, codec "opus".

Points de terminaison REST

Base: https://api.starhermit.com/api/v1/voice.

Méthode Chemin Authentification Description
POSTE /rooms JWT Créer une salle vocale pour une conversation
OBTENIR /rooms?conversationId= JWT Répertorier les salles pour une conversation
OBTENIR /rooms/{roomId} JWT Obtenez une chambre
POSTE /rooms/{roomId}/join JWT Rejoindre une salle (obligatoire avant le WS)
POSTE /rooms/{roomId}/leave JWT Quitter une pièce
POSTE /rooms/{roomId}/mute JWT Définissez votre propre état muet
POSTE /rooms/{roomId}/participants/{userId}/server-mute JWT (créateur) L'hôte coupe le son, le participant ne peut pas soulever
POSTE /rooms/{roomId}/close JWT Fermer une salle (créateur uniquement)

Créer une pièce

POST /rooms

{ "conversationId": "<guid>", "maxParticipants": 10 }

Renvoie un VoiceRoomDto.

Forme de la pièce

GET /rooms?conversationId=<guid> → VoiceRoomDto[]; GET /rooms/{roomId} → VoiceRoomDto:

{
  "id": "<guid>",
  "conversationId": "<guid>",
  "creatorUserId": "<guid>",
  "codec": "opus",
  "status": "Active",
  "maxParticipants": 10,
  "createdAt": "2026-07-22T07:00:00Z",
  "participants": [
    {
      "userId": "<guid>",
      "username": "alice",
      "isMuted": false,
      "isConnected": true,
      "joinedAt": "2026-07-22T07:01:00Z"
    }
  ]
}

Rejoindre, quitter, couper le son, fermer

POST /rooms/{roomId}/join → VoiceRoomDto. Cette jointure REST est requis avant d'ouvrir le WebSocket ; se connecter sans qu'il revienne 403. Rejoindre efface le nom du participant propre muet (isMuted); celui d'un hôte isServerMuted survit au congé et se reconnecte.

POST /rooms/{roomId}/leave → 204.

POST /rooms/{roomId}/mute avec { "muted": true } → 204. Il s'agit de la sourdine du participant et ne peut pas désactiver la sourdine de l'hôte.

POST /rooms/{roomId}/participants/{userId}/server-mute avec { "muted": true } → 204 (créateur uniquement). L'audio est supprimé si l'une ou l'autre des sourdines est définie.

POST /rooms/{roomId}/close → 204 (créateur uniquement).

Indiquez votre sourdine lors de la connexion plutôt que d'hériter de ce dont la ligne se souvient.

WebSocket : ws/v1/voice

Connectez-vous à wss://api.starhermit.com/ws/v1/voice?roomId=<guid> avec un JWT via le Authorization en-tête, ?ticket=, ou ?access_token=. Un REPOS préalable join est requis.

Le protocole est mixte :

Images binaires – audio

Les images binaires transportent de l'audio (par exemple Opus). Le serveur relaie chaque trame aux autres participants comme :

[16-byte senderUserId][audio…]

Le serveur préfixe le authentifié identifiant de l'expéditeur et ne fait jamais confiance à un expéditeur fourni par le client. L'audio des utilisateurs en sourdine est supprimé. Limites : 100 paquets/seconde par utilisateur, trame maximale de 4 000 octets.

Cadres de texte — client → contrôle serveur

{ "type": "mute", "muted": true }

{ "type": "speaking", "speaking": true }

{ "type": "rtc", "to": "<guid>", "payload": { } }

{ "type": "deafen", "deafened": true }

rtc les charges utiles sont une signalisation WebRTC opaque, transmise au participant adressé. deafen supprime l'audio binaire relayé entrant pour cette socket ; il ne coupe pas automatiquement le son audio sortant ou une connexion homologue distincte. Appliquez-les localement lorsque le joueur choisit Deafen.

La forme du participant REST expose son propre muet, pas le muet de l'hôte. La liste initiale des voix et les événements de participation inclure serverMuted; il n'y a pas d'événement push distinct de modification de la sourdine par l'hôte. Si votre jeu utilise le P2P audio, sa signalisation et son application de mise en sourdine par l'hôte doivent faire partie de votre propre intégration multimédia.

Lorsque la dernière prise vocale se déconnecte, l'adhésion à la salle vocale prend fin. Appeler REST join encore avant reconnectez-vous et restaurez la sourdine prévue avant d'envoyer l'audio.

Exemple de modèle d'intégration (issu de l'implémentation de référence des échecs)

La voix est facultative par session de jeu. Un client type enable() couler:

  1. GET /api/v1/voice/rooms?conversationId=<chatConversationId> pour trouver une chambre existante, sinon POST /api/v1/voice/rooms pour en créer un.
  2. POST /api/v1/voice/rooms/{roomId}/join.
  3. Ouvrir ws/v1/voice?roomId=<guid>.

Dans le implémentation de référence d'échecs, l'audio fonctionne sur WebRTC P2P avec une négociation parfaite ; la signalisation est échangée via le rtc messages de contrôle ({ "sdp": … } / { "ice": … } charges utiles), avec le chemin binaire Opus relayé par le serveur comme solution de secours.

Jetons de lancement à l'échelle du jeu peut utilisez la voix REST et WebSocket pour les salles attachées à leurs propres sessions de jeu.
