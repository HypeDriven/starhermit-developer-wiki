Performances natives pour les jeux de script

Un jeu avec moteur StarHermit exécute le même package dans les navigateurs et de manière native. Les deux exécutent votre code très différemment, alors choisissez où se trouve le travail le plus lourd avant de le porter ou de l'écrire. Cette page couvre le script vitesse, WebAssembly, scènes liées au GPU, travailleurs et mesures. Les chiffres sont des mesures du moteur de Octobre 2026.

Comment fonctionne votre code

Dans les navigateurs Nativement
Jeu Javascript Le V8 du navigateur, à pleine vitesse Le propre interprète du moteur, pas de JIT (par conception, pour des raisons de sécurité)
WebAssembly, domaine principal Le WebAssembly du navigateur L'interpréteur du moteur (API hôte 1.25 et versions ultérieures)
WebAssembly dans starhermit:script ouvriers L'interprète du moteur, pour des résultats précis L'interprète du moteur
  • Nativement, le vrai jeu JavaScript concerne 15 à 25 fois plus lent que le V8. Les micro-benchmarks peuvent suggérer environ 8×. Ne comptez pas sur eux.
  • Native WebAssembly concerne 8 à 17 fois plus lent que le V8 aujourd'hui. La plateforme prévoit de compiler WASM à l'avance au code natif signé au moment de la publication, ce qui devrait le rapprocher de la vitesse V8.
  • starhermit check exécute JavaScript exactement comme le fait un jeu fenêtré. Benchmark avec un --release construction de moteur uniquement.

Travail lourd par image

La simulation, le maillage, la recherche de chemin et la construction d'entités sont les points chauds habituels.

  1. Écrivez le code chaud dans Rust ou dans un autre langage WASM et exécutez-le en tant que WebAssembly, idéalement dans un starhermit:script travailleur. Le code écrit de cette façon obtient l'accélération prévue à l'avance sans changements.
  2. Choisissez un chemin avec runtime() depuis starhermit:engine (API hôte 1.26). "web" ça veut dire V8, donc JavaScript est bien là-bas. "native" signifie que vous devriez préférer le chemin WASM. Les travailleurs prennent toujours le dessus chemin natif et je ne peux pas importer starhermit:engine.
  3. Conservez du JavaScript simple pour la logique du jeu, l’interface utilisateur et l’orchestration. Répartissez les travaux lourds et rares sur les cadres.
  4. Ne compilez pas JavaScript ou TypeScript sur WebAssembly pour plus de rapidité. Le résultat a encore besoin d'un Modèle objet JavaScript, donc il ne gagne rien.

Pour de nombreuses entités similaires, starhermit:world graines fonctionne également de manière native.

Scènes liées au GPU

Nativement, le GPU ne devient généralement la limite qu'une fois le temps de script maîtrisé.

  • Utiliser InstancedMesh.setLevels([...]) avec des niveaux low-poly et une distance de tirage, et trois LOD (API hôte 1.26).
  • Tourner castShadow désactivé pour les accessoires petits ou éloignés.
  • Limitez les cascades d’ombres avec shadow.cascades = { count, maxDistance }, une extension de moteur.
  • Ensemble STARHERMIT_GPU_PASS_TIMES=1 pour imprimer le temps GPU pour chaque passe.

Ouvriers

  • Avant l'API hôte 1.27, conservez une référence à chaque travailleur que vous utilisez, car le garbage collection le termine. À partir de 1.27, un travailleur avec des auditeurs vit jusqu'à terminate().
  • Les travailleurs peuvent lire les fichiers de package (files) à partir de l'API hôte 1.26.
  • Les travailleurs peuvent envoyer des messages binaires et transférables à partir de l'API hôte 1.25.

Mesurer

  • Comparez le natif et le Web en utilisant la même version.
  • Les statistiques d'image du moteur rapportent le temps de script séparément du temps d'image. Les numéros de script-bench sont convient pour citer.
