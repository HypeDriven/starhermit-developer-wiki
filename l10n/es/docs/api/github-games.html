Juegos de GitHub

Publicar un juego desde un repositorio de GitHub en estrellaermitañoo registrar un juego web ya alojado. Para juegos de repositorio, la plataforma dice starhermit.txt, clona el repositorio y lo sirve en <slug>.starhermit.com. Porque /api y /ws tienen un proxy del mismo origen desde ese subdominio, un juego alojado en una plataforma necesita sin configuración CORS o basada en API. Una confirmación fija controla qué versión del repositorio está activa. El implementación de referencia de ajedrez se publica de esta manera y sirve como ejemplo de referencia del modelo.

URL básica: https://api.starhermit.com. Todas las rutas están bajo api/v1/... y requieren un JWT a menos que se indique lo contrario.

Los archivos de clientes alojados pueden declarar Duración de la caché de carpetas y orígenes CORS adicionales en starhermit.txt. Esas políticas se publican con los archivos del cliente; una fusión sin manifiesto conserva configuraciones existentes, mientras que un manifiesto proporcionado las reemplaza.

El manifiesto: starhermit.txt

Lugar starhermit.txt en la raíz del repositorio. Formato: key=value pauta, # inicia un comentario.

name=Your Game
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html        # repo-relative HTML entry
cover=art/cover.png      # optional cover art for the library tile; or an https:// URL
description=One-line pitch\nSecond line   # optional; or description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md          # optional; or release_notes=inline text
owner=<starhermit user id>  # UUID from GET /api/v1/me; do not use username/nickname
# Choose at most one authoritative backend, or omit both for a browser-only game:
server=server.js         # sandboxed JavaScript; see game-scripts.md
# container.image=ghcr.io/owner/game@sha256:<64 lowercase hex>; see container-games.md

control.up=KeyW+ArrowUp | Move forward
control.shoot=Space | Shoot
  • no hay slug Clave: la plataforma asigna un uid y lo utiliza como subdominio (<uid>.starhermit.com) y el espacio de nombres de la API del juego (/api/v1/games/<uid>/…).
  • cover (alias cover_art, coverart) es la obra de arte que se muestra en el mosaico de la biblioteca del juego: una ruta relativa al archivo de inicio, o una ruta absoluta https:// URL. Opcional: sin uno, el mosaico muestra el favicon de su sitio. Vuelva a leer en cada implementación, por lo que cambiar la línea cambia la portada. Ver Arte de portada para los cultivos de teja.
  • description / release_notes (o description.file / release_notes.file, que nombra un .md/.markdown/.txt archivo relativo al manifiesto) son textos opcionales para tu juego. Se vuelven a leer en cada implementación como cover. Ver Descripción y notas de la versión.
  • server declara un backend de JavaScript en un espacio aislado; ver game-scripts.md.
  • container.image declara un contenedor backend; ver container-games.md. Debe estar anclado en un resumen, alojado en el espacio de nombres del propietario verificado de GitHub en un registro incluido en la lista permitida y puede ir acompañado de container.port, container.health, container.memory_mb, container.cpu, y no secreto container.env.* valores.
  • Ambas claves de backend son opcionales para un juego de navegador puro, pero se excluyen mutuamente.

Enlaces de control predeterminados

Un juego puede declarar cero o más acciones del navegador de escritorio:

control.<action>=<code>[+<code>...][ | <label>]
  • Las acciones están en minúsculas. [a-z0-9_]{1,32} identificadores y conservar el orden manifiesto.
  • Los códigos son KeyboardEvent.code valores; + separa claves alternativas para una acción.
  • La etiqueta opcional se muestra en las IU de reasignación de controles y su valor predeterminado es la identificación de la acción.
  • Un manifiesto puede declarar hasta 32 acciones y 4 códigos por acción. Un código no puede ser utilizado por dos acciones. Las líneas de control no válidas se ignoran.
  • Juegos sin control.* las declaraciones no tienen controles API/UI (404 "This game declares no controls."). Las declaraciones se vuelven a leer desde cada compilación publicada: cada implementación, carga de carpeta y reemplazar el empuje del paquete. Paso a paso: Tutorial: añade controles a tu juego.

Los jugadores pueden anular estos valores predeterminados por juego a través del API de controles de juegos.

Registrar un juego

POST /api/v1/me/github-games

{
  "repoUrl": "https://github.com/HypeDriven/starhermit-chess",
  "displayName": "StarHermit Chess",
  "launchPath": "index.html"
}

A pesar de su nombre histórico, repoUrl Acepta tres fuentes de lanzamiento:

  1. A github.com/<owner>/<repo> repositorio. El backend lee su manifiesto y puede implementarlo. al alojamiento StarHermit.
  2. Una URL de páginas de GitHub ya alojada, como https://owner.github.io/game/. Repositorio la identidad se infiere de la URL; se inicia la URL en sí, sin clonación ni instalación.
  3. cualquier otro publico http:// o https:// URL del juego web alojado. Se lanza directamente y no participa en la reclamación de propiedad de GitHub.
  • displayName y launchPath son alternativas opcionales. Son útiles para un repositorio de terceros. sin metadatos de manifiesto confiables; una URL alojada directamente es en sí misma la ubicación de lanzamiento.
  • Para propietarios de repositorios verificados, la plataforma valida starhermit.txt.
  • Un opcional server= guión o container.image= el backend proporciona un juego autorizado; ver game-scripts.md y container-games.md. El alojamiento de contenedores está abierto a cualquier usuario que haya iniciado sesión en starhermit.com; una implementación autohospedada puede restringirla a una lista de operadores permitidos.
  • Un servidor backend declarado necesita un propietario probado. Presentar un repositorio que declare server= o container.image= sin iniciar sesión en GitHub o owner= la prueba es 403 (nombrando ambas pruebas), no una lista exclusiva del navegador que pretende tener un backend.
  • Límites: 100 juegos por usuario (anulable por el operador por cuenta). Registrar una devolución duplicada 409.

Los estados de registro/implementación incluyen: InvalidUrl, LimitReached, Duplicate, MissingManualMetadata, MissingStarhermitTxt, InvalidLaunchPath, InvalidServerScriptPath, InvalidContainerImage, ServerProvisionConflict, RemovedByOwner.

Los errores utilizan la forma estándar:

{ "error": "..." }

Agregar un juego desde una carpeta local

POST /api/v1/me/github-games/upload → 201

La contraparte de registrar una URL: no hay repositorio, y no se clona nada. la carpeta viaja como uno .tar.gz en el cuerpo de la solicitud y la plataforma aloja lo que contiene. Mismo archivo formato como empujando un paquete, por lo que el mismo embalaje sirve para ambos.

El juego creado tiene un gameSlug desde el principio, ya sea que declare o no un servidor, por lo que un la carga solo del navegador puede usar controles, configuración por jugador, es ranura para guardar en la nube, salas en tiempo real y lanzar tokens como cualquier otro juego.

client/           the game's files, published as-is
starhermit.txt    name= and launch= instead of the query parameters

El manifiesto es opcional para este punto final - los parámetros de consulta pueden proporcionar los mismos valores - y Los clientes de StarHermit siempre envían uno, creado a partir de sus campos de manifiesto. Envío del archivo al interior Todavía vale la pena hacer tu compilación: hace que la compilación sea autodescriptiva y completa previamente esos campos, por lo que se puede volver a cargar sin recordar qué valores necesitaba. Ver El starhermit.txt manifiesto para el formato, y tenga en cuenta que todo adyacente al manifiesto se carga — sube una compilación distribuible, no un árbol de fuentes.

Envíe los bytes directamente, no datos de formularios de varias partes, con Content-Type: application/gzip:

tar -czf game.tar.gz client/ starhermit.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/upload?displayName=My%20Game" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game.tar.gz

{
  "game": { "id": "...", "displayName": "My Game", "launchPath": "index.html", "hosting": { "hostingEnabled": true } },
  "bytesReceived": 4194304
}

Los metadatos se resuelven en este orden, por lo que la mayoría de las carpetas no necesitan ningún parámetro de consulta:

  1. ?displayName= / ?launchPath= en la solicitud.
  2. name= / launch= en un starhermit.txt en la raíz del archivo.
  3. index.html en la raíz de client/ - Se utiliza como ruta de lanzamiento cuando nada más lo nombra.

Notas específicas de esta ruta:

  • El juego se activa tan pronto como vuelve la llamada. No hay alojamiento ni implementación por separado paso: deployStatus es live y deployedCommitSha es null, porque no hay ningún compromiso.
  • Los archivos no se pueden regenerar., por lo que la plataforma nunca los vuelve a implementar desde ningún lugar. un juego agregado de esta manera lleva contentSource: upload y conserva su compilación cargada hasta que la publique otro. Impulsar una nueva construcción con el punto final del paquete o cargar la carpeta nuevamente.
  • Sin depósito significa que no hay reclamos. ownerLogin está vacío, por lo que ningún inicio de sesión de GitHub podrá igualarlo; repoUrl lleva un sintético upload:<id> valor en lugar de una URL.
  • A server/image.tar es rechazado aquí (422). Una imagen de servidor necesita un juego aprovisionado para adjuntar a, que no existe hasta que exista el juego: primero crea el juego y luego envía la imagen. a /{id}/bundle.
  • Se rechaza una ruta de inicio que nombra un archivo que el archivo no contiene (422) mientras la carga es todavía en preparación, en lugar de convertirse en un 404 para cada jugador.

Los límites son los mismos que para cualquier otro empujón: ver Límites de carga.

Una carpeta cargada puede traer su propio servidor backend

Si el archivo starhermit.txt declara la lógica del servidor, la carga también lo aprovisiona, lo mismo que hace el flujo del repositorio, sin un repositorio. Elige uno estilo; declarar ambos es rechazado.

Declaración Lo que sucede
server=path/to/server.js Un backend de script. El archivo viaja dentro de la carpeta que subes, por lo que su fuente se lee directamente desde el archivo: no hay nada que recuperar. Ver game-scripts.md.
container.image=name@sha256:… Un backend de contenedor, anclado en resumen como siempre. Ver container-games.md. La imagen en sí se empuja después a /{id}/bundle.

Los rechazos aquí fallan en toda la creación: ninguna fila del juego a medio hacer sobrevive:

  • server= nombrar un archivo que el archivo no contiene.
  • server= apuntando fuera de los archivos del cliente (../).
  • declarando ambos server= y container.image=.
  • Solicitar un contenedor donde los contenedores estén inhabilitados, o a un propietario no aprobado para ellos.

PNG, JPEG, GIF, WEBP, BMP o SVG, hasta 4 megas. La portada es un cartel: ambas bibliotecas escale para llenar el mosaico y recorte central lo que sea que haga no encaja. Los azulejos no tienen la misma forma.

Superficie Teja Cultivo

Mantenga el sujeto en el centro para que ambos cultivos se vean bien. Un juego sin cobertura en todo vuelve a su favicon (GET /api/v1/github-games/{id}/icon). El icono se resuelve desde el URL que enviaste y, cuando la plataforma aloja el juego, de la copia que sirve en <uid>.starhermit.com – por lo que un paquete subido con un favicon en sus archivos todavía tiene un ícono.

Cifras de audiencia de tu juego

GET /api/v1/me/github-games/{id}/stats → GameStatsDto

¿Cuántas personas juegan un juego? tu agregaste. Restringido al propietario del juego; cualquier otra persona podrá 404, La misma respuesta que un juego que no existe.

{
  "totalPlayers": 42,
  "playingNow": 3,
  "totalSessions": 130,
  "totalPlaytimeMinutes": 8140,
  "lastPlayedAt": "2026-07-29T08:45:24Z",
  "livenessWindowHours": 4
}
  • Solo agregado. Aprendes el tamaño de tu audiencia, nunca quién está en ella.
  • totalPlayers cuenta personas distintas, no sesiones: alguien que jugó seis veces es uno jugador.
  • playingNow cuenta distintos jugadores cuya sesión no ha finalizado y comenzó dentro livenessWindowHours. La ventana importa: un cliente que falla o pierde su red nunca envía el final de la sesión, y sin ella, esas filas se leerían como personas que siguen jugando indefinidamente.
  • totalPlaytimeMinutes cuenta solo sesiones completadas, igualando las cifras de tiempo de reproducción por usuario en activity.md. Una sesión en vuelo no aporta nada todavía.
  • lastPlayedAt es null para un juego que nadie ha jugado.

Las cifras provienen del mismo libro de lanzamiento que escribe cada cliente (ver activity.md), por lo que un el juego cuyos jugadores nunca reportan lanzamientos se leerá como cero.

Reclamar propiedad

Hazte cargo de un listado existente cuando controlas su repositorio. Demuestre la propiedad ya sea vinculando el inicio de sesión personal de GitHub que coincida con el propietario del repositorio, o confirmando owner=<your StarHermit user ID> al repositorio starhermit.txt. owner debería ser el UUID inmutable devuelto como id por GET /api/v1/me, no un nombre de usuario o apodo. el manifiesto El método admite repositorios propiedad de la organización, que no se infieren de la organización personal de GitHub. membresía.

En caso de éxito, el listado existente conserva su ID/historial, pasa a ser administrado por el reclamante y se actualiza metadatos controlados por el repositorio y declaraciones de backend, y alojamiento de colas cuando esté disponible. el El remitente anterior pierde el acceso de administración con ámbito de propietario. Reclamar un listado que ya administras lo vuelve a sincronizar en lugar de devolver un conflicto.

Almacenes de metadatos de identidad de GitHub {"login":"…"}; vincule su cuenta de GitHub a través del flujo de OAuth (consulte auth.md). Verifique el estado del enlace con GET /api/v1/me/github → { linked, login }. Ver el tutorial de reclamo paso a paso para el descubrimiento, ambas pruebas métodos, validación, adquisición y resolución de problemas.

Enviar un paquete de juegos

POST /api/v1/me/github-games/{id}/bundle publica resultados construidos sin pedirle a StarHermit que clonarlo de nuevo. La persona que llama debe ser propietaria del juego registrado. enviar el .tar.gz bytes directamente—no datos de formulario de varias partes, con Content-Type: application/gzip:

client/            optional static client files; must include the registered launch file
server/image.tar   optional output from `docker save`
starhermit.txt     optional manifest copy for bundle portability
remove.txt         merge only: client-relative paths to delete, one per line

Al menos client/ o server/image.tar debe estar presente (una fusión también puede ser solo remove.txt). Los archivos del cliente se intercambian atómicamente. un La imagen del servidor se carga, la plataforma fija el resumen y pone en cola la implementación del contenedor para reinicie en esa imagen. Una imagen cargada tiene prioridad sobre la referencia de registro del manifiesto, y más de un server= línea; un manifiesto declarando ambos server= y container.image= es rechazado antes de que se cargue algo. Todo lo demás que haya en el archivo se ignora.

Cargar una imagen es en sí misma la declaración. Si el juego aún no tiene servidor backend, un carpeta cargada que no declaró ninguna - empujando server/image.tar provisiones uno del resumen justo cargado, debajo del gameSlug el juego ya lo tiene. No es necesario nombrar una imagen fijada en un resumen en un manifiesto primero, que era circular: la definición tenía que existir antes de poder recibir una imagen, y la imagen era lo único que podía describirlo.

Un re-push aplica las perillas del contenedor que declara su manifiesto, y solo esas. Incluir starhermit.txt en el paquete con un cambio container.port, container.health, container.memory_mb o container.cpu y la implementación lo retoma al reiniciar; deja una perilla afuera y Mantiene lo que estableciste la última vez. Omitir el manifiesto por completo y nada sobre la implementación. cambia excepto la imagen.

Los clientes de StarHermit crean este paquete para usted, desde una carpeta o un solo .tar:

  • Archivos de clientes — la carpeta de distribución del juego, o un .tar de ello. Una carpeta está empaquetada debajo client/; a .tarLas entradas de se reubican allí (un archivo que ya está bajo client/ queda solo). solo ustar: se rechazan los archivos GNU de nombre largo y PAX, porque reubicarlos significa reescribiendo los bloques de metadatos que nombran la siguiente entrada.
  • Servidor dedicado — la carpeta de distribución del servidor, o la docker save .tar por sí solo. De una carpeta solo el manifiesto y image.tar están cargados: la imagen ya contiene su propios archivos del servidor, por lo que empaquetar el resto enviaría gigabytes para que la plataforma los descarte.

En ambos casos el starhermit.txt es editable en el cuadro de diálogo. Cualquiera que sea el La compilación seleccionada incluye campos precompletados, y todo lo que contienen se escribe en la raíz del paquete, por lo que una compilación sin manifiesto es publicable y una que se envía como .tar todavía puede tener su manifiesto actualizado.

mkdir -p bundle/server
mv image.tar bundle/server/image.tar
cp starhermit.txt bundle/
tar -C bundle -czf game-bundle.tar.gz .

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/$GAME_ID/bundle" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game-bundle.tar.gz

Actualizaciones parciales: ?mode=merge

Un empujón es un reemplazar a menos que pidas lo contrario: el archivo es el juego completo, y todo lo que no esté en ya no está. ?mode=merge (HTTP y el socket de carga por igual) lo convierte en un parche del cliente en vivo archivos: la respuesta a volver a cargar gigabytes de activos sin cambios para una solución de un solo archivo.

printf '%s\n' '# one client-relative path per line; a directory removes everything under it' \
    'assets/old-music.ogg' 'levels/cut/' > remove.txt
tar czf patch.tar.gz client/index.html client/js/app.js remove.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/$GAME_ID/bundle?mode=merge" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @patch.tar.gz

Con mode=merge:

  • archivos bajo client/ se agregan o sobrescriben
  • caminos en una raíz remove.txt (# comentarios; un directorio elimina todo su subárbol) se eliminan
  • todos los demás archivos en vivo permanecen exactamente como están

El árbol fusionado se presenta como una copia y se intercambia atómicamente: los jugadores ven el juego antiguo o el uno completamente nuevo, nunca una mezcla. El resultado está acotado por la juegos asignación, no la de la carga, por lo que un juego no puede crecer más allá de su límite, un pequeño parche a la vez. Una fusión se trata sólo de archivos de clientes; a server/image.tar se carga exactamente como en un reemplazo. Un parche que no lleva starhermit.txt hojas portada tal como estaba.

Se rechaza una fusión (409/422, nada cambia) cuando el juego no tiene nada publicado todavía, cuando eliminaría el archivo de inicio, o cuando remove.txt puntos fuera del juego. A remove.txt en un El reemplazo simple también se rechaza (422), porque allí sólo podría significar algo que no sabías pretender. mode debe ser replace (predeterminado) o merge; cualquier otra cosa es 400.

El mismo parámetro funciona en el socket: ws/v1/game-upload?gameId=…&mode=merge. El ready marco lo repite como "apply":"merge".

El terminal actualiza un juego registrado existente; nunca crea el registro del juego; para eso, consulte agregar un juego desde una carpeta local. Él poder aprovisionar el juego backend del servidor, como efecto secundario de cargar una imagen de servidor en un juego que no tenía ninguna. Ver el tutorial de publicación de servidor dedicado.

Cargar desde CI/CD

No mantenga un token OAuth interactivo en un repositorio secreto. Inicie sesión a través de OAuth una vez y utilice esa sesión para agregar una clave de implementación etiquetada por separado con POST /api/v1/me/public-keys. El CI el trabajo puede entonces firmar /auth/public-key/challenge, cambiarlo en /auth/public-key/completey utilizar el token de acceso de 15 minutos devuelto en este punto final del paquete.

La clave de implementación actúa como su cuenta propietaria, por lo que esa cuenta debe ser propietaria del juego objetivo. no puede agregar otra clave o revocar otras claves. Puede revocarse mediante /me/public-keys/current; administrar la inscripción y otras claves desde una sesión autenticada por OAuth. Utilice una clave por entorno para que un flujo de trabajo pueda desactivarse sin detener los demás. Archivos sobre aproximadamente 100 MB deben utilizar el transporte WebSocket a continuación.

Ver Cargue compilaciones desde CI/CD con una clave pública inscrita en OAuth para generación de claves, configuración secreta de GitHub, un script completo de carga/firma de desafíos, estático y diseños de paquetes de contenedores y un flujo de trabajo de GitHub Actions.

Cargar a través de un WebSocket

GET /ws/v1/game-upload (mejora) - Úselo para cualquier cosa que supere los 100 MB.

La CDN delante de la API rechaza un cuerpo de solicitud HTTP aproximadamente 100 megas con un 413 de su propio. Esa negativa nunca llega a la plataforma, por lo que no conlleva ningún efecto. limitBytes y no aparece en ningún registro sabe leer - un 413 sin limitBytes El campo es el CDN, no la asignación de tu juego, que son dos órdenes de magnitud mayores. Cualquier realista docker save lo golpeará.

Las tramas enviadas después de la actualización de WebSocket no son un cuerpo de solicitud, por lo que no se aplica el límite. Sólo el transporte difiere. Las tramas binarias se concatenan exactamente en los bytes que las rutas HTTP Lea, siga el mismo proceso y cada cuerpo de rechazo, concesión y éxito es el que HTTP ruta habría producido, por lo que un cliente puede compartir una ruta de código entre ambos.

wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&mode=merge&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?displayName=My%20Game&launchPath=index.html&access_token=$TOKEN

Aprobar gameId para acceder a un juego de tu propiedad (el /{id}/bundle ruta); omitirlo y pasar displayName/launchPath para crear uno desde una carpeta (la /upload ruta). La ficha va en el cadena de consulta porque un navegador no puede establecer una Authorization encabezado en un protocolo de enlace WebSocket; es verificado una vez, en el apretón de manos, por lo que una carga que sobrevive a su token de acceso aún finaliza.

Dirección Marco Significado
servidor → {"type":"ready","mode":"bundle","apply":"replace","limitBytes":N,"heartbeatSeconds":15} Asignación liquidada y espacio libre comprobado. Comience a enviar. mode es bundle o create. apply es merge cuando solicitó una actualización parcial.
→ servidor binario Archive bytes, fragmentados como desee: el servidor nunca vuelve a ensamblar los mensajes, por lo que 256 KB–1 MB es un buen valor predeterminado. Concatenados, sus marcos deben ser exactamente los .tar.gz.
servidor → {"type":"ack","bytesReceived":N} Progreso de recepción, aproximadamente cada 8 MB. Conduce tu barra de progreso a partir de esto.
→ servidor {"type":"complete"} El archivo ha sido enviado íntegramente.
→ servidor {"type":"abort"} Abandonar. Respondido con status: 499; no se publica nada.
servidor → {"type":"progress","phase":"publishing","bytesReceived":N} Latidos cada 15 segundos mientras llega la carga. Ignóralos, pero espéralos.
servidor → {"type":"result","status":200,...} Éxito. El resto del objeto es el cuerpo de la respuesta HTTP palabra por palabra (status es 201 para crear).
servidor → {"type":"error","status":413,"error":"...","limitBytes":N} Negativa. status y el cuerpo son lo que habría respondido la ruta HTTP.

No se publica nada hasta {"type":"complete"} llega. Este es el único comportamiento sin HTTP equivalente, y es deliberado: el marcador de fin de archivo vive adentro los bytes de un tar, por lo que el La plataforma termina de leer un archivo de apariencia completa sin que la conexión termine. un enchufe que simplemente se cayó después del último byte se publicaría exactamente igual que uno que terminó: Reemplazar silenciosamente un juego en vivo con un empujón abandonado. Cerrar el socket sin las cargas del marco. nada.

La publicación después del último byte puede llevar tiempo, especialmente para una imagen de servidor. Esperar progress latidos del corazón mientras termina; no trate un intervalo de silencio como un error de carga.

Límites de carga

Todas las rutas de carga (tanto los puntos finales HTTP como WebSocket) comparten las mismas reglas.

Límite Valor
Asignación de discos por juego 2GB en starhermit.com (la asignación puede variar según el juego/implementación)
Archivos alojados por cuenta 20GB en todos los juegos de una cuenta (ajustable por operador por cuenta)
Implementación del repositorio 50 megas archivo
starhermit.txt / remove.txt 256KB cada; remove.txt enumera como máximo 10.000 rutas (422)
Aplicación aplicado mientras transmite, por lo que un empujón de gran tamaño se corta en pleno vuelo

Una carga o envío se interrumpe en lo que queda de la asignación de alojamiento de la cuenta (413 con limitBytes), y una implementación de repositorio que lo aprobaría falla con un motivo que nombra la asignación. Por push y por juego son el mismo número en un reemplazo. Una fusión está limitada por el resultante tamaño del juego, por lo que se rechaza un pequeño parche que haría que el árbol vivo exceda lo permitido.

Estado Significado
400 mode tampoco lo es replace ni merge.
409 Una fusión con un juego que aún no tiene archivos publicados.
413 Por encima de la asignación. El cuerpo lleva { "error", "limitBytes" }. A 413 sin limitBytes es el límite del cuerpo de ~100 MB de la CDN, no esto: utilizar el socket de carga.
422 Archivo con formato incorrecto o contenido inutilizable (falta el archivo de inicio, no client/, a server/image.tar en la ruta de creación, una combinación que eliminaría el archivo de inicio, remove.txt en un reemplazo). También un truncado archivo: el resultado normal de una conexión interrumpida durante la carga.
507 El servidor no tiene espacio en este momento. Rechazado antes de leer el cuerpo cuando la capacidad de publicación no esté disponible; Vuelva a intentarlo más tarde.

Los archivos no pueden escapar de su raíz ni contener enlaces, y sólo se almacenan archivos y directorios normales. extraído: se rechazan los enlaces simbólicos, los enlaces físicos y los nodos de dispositivos. git archive encabezados globales PAX, ./-nombres con prefijo de tar -czf game.tgz .y nombres de archivos que simplemente contienen .. (sprite..png) son aceptados. A .. El segmento de ruta aún se rechaza.

Enviar, reclamar, cambiar URL, alojamiento e implementación llegan a GitHub en el único token de la plataforma, por lo que juntos están limitados a 10 solicitudes por minuto por cuenta (429, con Retry-After). un El operador puede aumentarlo para una cuenta.

Anclar una implementación

Sesiones en vivo (propietario)

GET /api/v1/me/github-games/{id}/sessions enumera las sesiones activas del servidor del juego. Eso devuelve la capacidad del asiento que estaba manteniendo una sesión estancada.

Publica tu propio juego: tutorial

Hay dos rutas. Si tu juego se encuentra en un repositorio de Git, sigue los pasos numerados a continuación. Si es solo una carpeta en su máquina, una llamada lo hace todo: agregar un juego desde una carpeta local registra el juego, publica el archivos y lo deja activo: sin alternar alojamiento ni pin de confirmación, porque no hay ningún repositorio para pista.

  1. Elige una fuente: envía un repositorio que contiene starhermit.txt en la raíz (opcionalmente declarando un server.js script o imagen de contenedor), o preparar la URL pública de un juego de navegador ya alojado.
  2. Vincula tu identidad de GitHub a través del flujo OAuth (ver auth.md); verificar con GET /api/v1/me/github.
  3. Registra el juego: POST /api/v1/me/github-games con el repositorio o la URL del juego alojado en repoUrl.
  4. Solo juegos de repositorio: habilite el alojamiento: PUT /api/v1/me/github-games/{id}/hosting con { "enabled": true }.
  5. Solo juegos de repositorio: fijar una confirmación: PUT /api/v1/me/github-games/{id}/deployment con { "commit": "<sha>" }. La confirmación fijada controla la versión en vivo.
  6. Los jugadores inician el juego.: un juego de repositorio implementado se sirve en <slug>.starhermit.com; un juego alojado directamente abre la URL enviada. Cada juego con un gameSlug - backend o no - recibe un token de lanzamiento de POST /api/v1/games/<slug>/launch-token en el fragmento de URL (opcionalmente con &session_id=<guid> para invitar a enlaces profundos).

Para conocer el contrato completo del lado del cliente (cómo el juego lee el token de lanzamiento y se comunica con la API), consulte el tutorial de ajedrez de la implementación de referencia.
