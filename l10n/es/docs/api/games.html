API de juegos

El subsistema de juegos es el núcleo de StarHermit: juegos multijugador autorizados por el servidor cuyas reglas se ejecutan en un archivo JavaScript en un espacio aislado o en un contenedor proporcionado por el desarrollador. Ambos tiempos de ejecución comparten esta API REST orientada al jugador (api/v1/games/{slug}) y juego WebSocket (ws/v1/games). Para la creación de servidores, consulte Guiones de juego o Servidores de juegos alojados en contenedores. Para obtener un ejemplo completo de tiempo de ejecución de script, consulte la Tutorial de ajedrez y HypeDriven/ajedrez ermitaño estrella.

URL básica: https://api.starhermit.com.

Los puntos finales de los jugadores requieren autenticación y funcionan tanto con tokens de usuario completos como con inicios específicos del juego. fichas. los dos /server/... Los puntos finales son solo contenedores: la conciliación de sesiones utiliza un estrecho token portador del servidor, mientras que la renovación del token utiliza la clave de actualización de implementación.

Qué {slug} es

La babosa de un juego es su fluido — el mismo valor que su <uid>.starhermit.com dirección, p.e. 83fd04b1-3cbe-4b09-a251-3733ad4b9d94. Se deriva de la identificación inmutable del juego y nada puedo configurarlo: no starhermit.txt, ni el nombre del repositorio, ni un operador. Un nombre que un desarrollador podría elegir sería algo por lo que dos juegos podrían competir, y necesitaría que la plataforma arbitrara quién lo tengo; un fluido no puede colisionar ni solicitarse.

Un slug no es un servidor backend. Cada juego agregado desde una carpeta local y cada juego del repositorio. un propietario verificado agregó, tiene uno, con o sin server= o container.image= - porque es la dirección de la superficie de cara al jugador del juego: fichas de lanzamiento, controles, ajustes, es ranura para guardar en la nube y alojamiento. un El juego exclusivo para navegador los necesita tanto como cualquier otro. Los únicos juegos sin slug son los de repositorio. envíos cuyo propietario no está verificado (gameSlug es null en GET /api/v1/me/github-games).

Los puntos finales sobre el servidor de un juego: información del juego, logros, sesiones, emparejamiento, invitaciones, repeticiones: necesita un backend. GET /api/v1/games/{slug} respuestas 404 para un juego que tiene un slug y no backend, que es la forma de diferenciarlos.

POST /api/v1/games/{slug}/launch-token

Crea un JWT con ámbito de juego (vida útil predeterminada de 60 minutos) que lleva game_scope={slug} y sin reclamos de permiso. Un token con alcance puede volver a acuñar un token para su propio juego (este es el patrón de actualización del cliente), pero la renovación está limitada por launch_chain (predeterminado 12 horas desde la sesión del usuario original). Más allá de ese techo la renovación es 403. Los clientes deben actualizar antes de que caduque el token; el cliente de referencia de ajedrez, por ejemplo, se actualiza cada 45 minutos. Renueve también antes de volver a conectar un enchufe; consulte Jugabilidad WebSocket.

Nada declara un esquema. La plataforma almacena tus claves y tus valores y nunca los lee, entonces agrega una opción escribiéndola: sin entrada de manifiesto, sin reimplementación, sin lanzamiento de plataforma. Al igual que la API de controles, se acepta un token de inicio con ámbito de juego (su game_scope debe coincidir {slug}), por lo que una pantalla de opciones del juego funciona únicamente con el token que ya tiene el juego. a diferencia controles, no se necesita ninguna declaración de manifiesto: cada juego tiene almacenamiento de configuración desde el momento en que existe, incluido un juego solo para navegador sin ninguna lógica de servidor.

Elija la tienda adecuada guardado en la nube mantener el progreso (un archivo opaco por título, 10 MB, accesible también con el token de lanzamiento), y el propio estado del reproductor de un script o contenedor backend tiene autoridad para el servidor y no se puede escribir desde un cliente. Las configuraciones son las pequeñas preferencias intermedias propiedad del cliente.

GET /api/v1/games/{slug}/settings

Todo lo que la persona que llama tiene almacenado para este juego. settings está vacío para un jugador que nunca ha guardado cualquier cosa, eso es un 200, no un 404. Las llaves regresan ordenadas.

  "settings": {
    "audio.master": 0.8,
    "graphics.detail": "ultra",
    "graphics.options": { "shadows": true, "msaa": 4 }
  },
  "count": 3,
  "bytes": 118,
  "updatedAt": "2026-08-07T15:04:11Z",
  "limits": { "maxKeys": 200, "maxKeyLength": 128, "maxTotalBytes": 2097152, "maxAccountBytes": 67108864 }

bytes es lo que cuesta actualmente la configuración de este reproductor limits.maxTotalBytes. Lea el límites en lugar de codificarlos: la asignación es una configuración del operador, y se puede otorgar un juego el suyo. maxKeys (200 por defecto) también se puede configurar por juego, y maxAccountBytes límites uno configuración de la cuenta en cada juego (64 MB de forma predeterminada).

PUT /api/v1/games/{slug}/settings

Reemplaza todo el mapa. Las claves que el cuerpo omite se eliminan - enviar todo, o usar PATCH.

{ "settings": { "audio.master": 0.8, "graphics.detail": "ultra" } }

un vacío settings El objeto borra la configuración del juego para la persona que llama. Devuelve la misma forma que GET.

PATCH /api/v1/games/{slug}/settings

Se fusiona con lo que está almacenado, dejando claves que no menciona solas. A null valor elimina es clave. Esto fusiona claves de configuración de nivel superior; un valor de objeto reemplaza el valor completo en su clave, incluidas sus propiedades anidadas. Esto es lo que un pantalla de opciones debe usar: puede guardar el control deslizante que se movió sin leerlo primero y reescribiendo todo lo demás.

{ "settings": { "audio.music": 0.25, "graphics.options": null } }

GET / PUT / DELETE /api/v1/games/{slug}/settings/{key}

Una configuración a la vez. GET regresa { "key", "value", "updatedAt" }, o 404 si la persona que llama tiene Nunca lo almacené. PUT acepta { "value": <any JSON> } y almacena el valor literal - incluyendo un explícito null, que aquí es un valor como cualquier otro, no una eliminación. DELETE regresa 204, y eliminar algo que no está allí es una operación no operativa en lugar de un error.

curl -X PUT "https://api.starhermit.com/api/v1/games/$SLUG/settings/audio.master" \
  -H "Authorization: Bearer $LAUNCH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"value": 0.35}'

Normas

Regla Valor
Configurar nombres 1–128 caracteres de A-Z a-z 0-9 . _ - : - espacio de nombres libremente (audio.master, graphics:shadows)
Valores Cualquier JSON: número, cadena, booleano, matriz, objeto, null
Configuraciones por jugador, por juego 200
Bytes por jugador, por juego 2 MB por defecto — un operador puede aumentarlo o reducirlo, y puede conceder a un juego una asignación diferente

Una única configuración puede utilizar toda la asignación de bytes; no existe un límite por valor más pequeño separado.

Estado Significado
400 Nombre de configuración incorrecto o cuerpo que no lo es {"settings": {...}} / {"value": ...}
404 Ningún juego responde a esa bala, o (una sola tecla GET) no se almacena nada bajo esa clave
413 Por encima de la asignación: demasiadas configuraciones o demasiados bytes. El mensaje indica el límite.

Un lote que contiene una clave incorrecta no escribe ninguna de las buenas. Los ajustes son por jugador y por juego: no se filtra nada entre dos jugadores, o entre dos juegos del mismo jugador. Sobreviven a un el juego se desactiva o se elimina de la lista, porque son datos del jugador y no del juego.

Casamentero

Un script declara las formas coincidentes que acepta a través de game.queues. Un juego sin aceptación. las declaraciones tienen una implícita default cola (dos equipos de uno). El contenedor actual /describe el lector lo hace no importar queues, por lo que los juegos de contenedores usan esa forma implícita de 1 contra 1. Un cliente que no nombra ninguna cola obtiene el primero del juego.

Se conservan hasta ocho colas de scripts. Las claves están recortadas, en minúsculas, no vacías y como máximo 32 personajes; Las claves duplicadas conservan la primera. teams se fija entre 2 y 8 y teamSize al 1 al 16; Las formas que superen los 32 jugadores en total se descartan. Las declaraciones no válidas pueden volver a ser implícitas. 1v1, así que verifica las formas efectivas con GET /queues después de publicar.

POST /api/v1/games/{slug}/matchmaking

Pone en cola a la persona que llama para el emparejamiento elo más cercano. repetible ?queues= claves de consulta nombre a subconjunto de esas formas (por ejemplo, 1v1 y 2v2, no 3v3). La comparación solo llena un boleto con una forma permitida. Por ejemplo:

POST /api/v1/games/{slug}/matchmaking?queues=solo&queues=duos
Authorization: Bearer <token>

Utilice las claves devueltas por GET /queues. ?queue=solo selecciona una sola forma; si ambos queue y queues se suministran, sus claves se combinan y se deduplican sin distinguir entre mayúsculas y minúsculas. Una clave desconocida es 404; una lista vacía después de la validación es 400. Devoluciones 409 si la persona que llama ya está en cola o en su límite de sesiones concurrentes.

La búsqueda comienza en una banda elo estrecha y se amplía mientras espera el ticket (predeterminado 100, +10/s). Estados: queued, matched, cancelled, expired (esperó más allá del límite, por defecto 300 s, sin encontrar a alguien: ofrecer un juego de práctica en lugar de girar). modelo de sesión

  • Sesión status es "active" o "finished".
  • Cada sesión recibe una conversación de chat por sesión (escriba "game") para que los oponentes puedan chatear y realizar llamadas de voz sin ser amigos (ver Charlar y Voz).

En su lugar, las sesiones persistentes se pausan. Esto también se aplica a las sesiones en sala; cerrar su habitación no los acaba.
  • Estados de los boletos de emparejamiento: queued | matched | cancelled | expired.
  • Estados de invitación: pending | accepted | declined | cancelled.
  • Las sesiones se crean a través del emparejamiento, la aceptación de invitación, el punto final de IA o el inicio de una sala en tiempo real. (sesiones en sala – ver Salas en tiempo real) — no hay "crear lobby" punto final.

Elo por partido

La plataforma hace no limitar hasta dónde puede moverse una calificación en un partido. eloUpdates (guión) y el elo mensaje de control (contenedor) llevar el de cada jugador nueva calificación absoluta, no es un cambio, y el la plataforma los aplica tal como se enviaron. Qué hace cumplir:

  • Sólo jugadores en la sesión. están actualizados. Se eliminan las identificaciones de cualquier otra persona y el puesto de IA.
  • Las actualizaciones se aplican cada vez que su servidor las devuelve. una sesión la plataforma termina (abandoned: jugadores abandonados, inactivos, reemplazados, falla del servidor, finalizado por el propietario) publica No elo cambio.
  • La calificación se escribe en la columna de pares de emparejamiento y en el tablero de elo del juego como uno solo. entrada por jugador (su última calificación).
  • El propietario del juego puede restablecer la calificación de un jugador a 1200.

Entonces, el tamaño de un swing es decisión de tu juego. Utilice un factor K estándar y fije su código. El implementación de referencia de ajedrez usa K = 32, por lo que un juego mueve un calificación de como máximo 32 puntos:

function eloAfter(mine, theirs, score /* 1 win, 0.5 draw, 0 loss */, K = 32) {
  const expected = 1 / (1 + Math.pow(10, (theirs - mine) / 400));
  const next = mine + K * (score - expected);
  return Math.round(Math.max(100, next));      // your floor, if you want one
}

Diagnósticos de propietarios y webhooks

Sólo propietario. Un token de lanzamiento relacionado con el juego no puede alcanzarlos.

GET /api/v1/games/{slug}/diagnostics

Una instantánea de las sesiones en vivo (activas, finalizadas, conexiones en vivo), medición de scripts contra CPU/ presupuestos de memoria/estado de cuenta, la cola de emparejamiento (la espera más larga y hasta qué punto se ha ampliado), y estado del punto final del webhook.

Ganchos web

GET/POST/DELETE /api/v1/games/{slug}/webhooks y POST .../{id}/resume. Hasta 5 puntos finales por juego. Eventos: session.created, session.finished (omitir events suscribirse a ambos). el se devuelve el secreto de firma una vez, al crear.

La plataforma PUBLICA JSON con:

  • X-Starhermit-Signature: t=<unix>,v1=<hmac-sha256> encima "<t>.<body>"
  • X-Starhermit-Event-Id — el evento (clave de idempotencia; se repite en todos los reintentos)
  • X-Starhermit-Delivery - este intento

La URL debe ser https y no debe resolverse en un rango privado/bucle invertido/CGNAT (verificado en registro y nuevamente antes de cada envío). No se siguen las redirecciones. Los puntos finales fallidos retroceden y se desactivan después de fallos consecutivos; resume limpia el disyuntor.

Tiempo de ejecución

Para juegos JavaScript, la plataforma ejecuta onTick barre a la tasa fijada solicitada a través game.tickRateHz; 0 desactiva los ticks y un juego que no solicita nada se marca en 0,25Hz — declara una tarifa si tu juego depende del tick. Un contenedor impulsa su propio bucle de simulación y declara su tarifa solicitada mediante /describe; la plataforma utiliza esa tarifa para programar y política de instantáneas, no para dar un paso al juego. Ver Guiones del juego: tasa de ticks y Servidores de juegos en contenedores.

Ciclo de vida de un juego

  1. Acuña una ficha de lanzamiento — POST /api/v1/games/{slug}/launch-token. Los clientes deben actualizarlo antes de que caduque (el cliente de referencia de ajedrez se actualiza cada 45 minutos).
  2. Obtener el estado del juego — GET /api/v1/games/{slug} para información + tus estadísticas; GET .../sessions/mine para juegos en curso; GET .../invites y GET /api/v1/realtime/rooms/invites para invitaciones pendientes; GET .../replays/mine para la historia cuando replaysEnabled; GET .../achievements para la pantalla de logros.
  3. encontrar un oponente, una de tres maneras:
    • Casamentero: POST .../matchmaking, luego encuesta GET .../matchmaking cada 3 s hasta status es matched (la respuesta lleva sessionId). DELETE .../matchmaking para cancelar.
    • Flujo de invitación: elige un amigo de GET /api/v1/me/friends (ver Amigos), POST .../invites con { "toUserId": "..." }; el invitado llama POST .../invites/{inviteId}/accept, que crea la sesión. (Si tu juego sienta a los jugadores en un sala en tiempo real primero, invítelos a la sala; la misma notificación, pero al aceptarlos se ubicará en la mesa en la que ya se encuentra).
    • Práctica de IA: POST .../sessions/ai.
  4. Cargar la sesión — GET .../sessions/{sessionId}.
  5. Conecte el WebSocket — ws/v1/games?sessionId={guid} con el token de lanzamiento, luego envíe cualquier comando de sincronización inicial que defina el backend del juego; la implementación de referencia de ajedrez, por ejemplo, envía {"type":"cmd","data":{"type":"sync"}}.
  6. Jugar - intercambio cmd/game marcos definidos por el backend, superficie achievement marcos y manija resumed descartando la predicción y solicitando un estado completo.
  7. Resultado — el backend autorizado finaliza el juego; la plataforma publica actualizaciones de elo en la tabla de clasificación y, para un juego con repeticiones, archiva el estado final.
  8. Repetición — GET .../replays/{sessionId} para el estado final completo.
