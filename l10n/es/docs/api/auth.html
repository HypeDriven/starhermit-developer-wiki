Autenticación

StarHermit tiene sin autenticación de contraseña. Hay dos flujos de inicio de sesión: autenticación de clave pública (Ed25519, ECDSA-P256 o RSA-PSS, con registro verificado por correo electrónico) y OAuth. Todas las rutas de autenticación se encuentran bajo api/v1/auth y son anónimos excepto donde se indique lo contrario. Esta página también cubre los ciclos de vida de los tokens, los tokens de lanzamiento relacionados con el juego y los tickets de conexión de WebSocket.

Los cuerpos de error varían; ver Convenciones API.

Después de iniciar sesión: términos actuales

El inicio de sesión exitoso no implica permiso para utilizar API protegidas. Los titulares de cuentas deben aceptar los términos actuales de StarHermit antes de llamadas REST protegidas o Las actualizaciones de WebSocket se realizan correctamente. Los clientes de la cuenta pueden comprobar GET /api/v1/me, buscar GET /api/v1/terms, y registrar la aceptación explícita con POST /api/v1/me/terms/accept. Tanto OAuth como clave pública Las sesiones de cuenta admiten este flujo. La actualización de las credenciales no resuelve la aceptación pendiente.

Un juego de navegador abierto directamente puede recibir un token de alcance antes de que la cuenta lo acepte. Si regresa una llamada de juego 403 con error: "terms_acceptance_required", buscar GET /api/v1/terms, mostrar su texto y ofrecer una acción de aceptación explícita. Un token de lanzamiento de jugador puede enviar el mensaje mostrado hash a POST /api/v1/me/terms/accept; Vuelva a intentar la solicitud original después de la aceptación. No trates esto respuesta como un bucle de inicio de sesión de token caducado.

POST /api/v1/auth/public-key/register

Comienza el registro de clave pública y envía un correo electrónico de verificación. El registro de registro pendiente caduca después de 4 horas. Si userId está configurado, el correo electrónico debe coincidir con esa cuenta. Limitado a 1 correo electrónico por dirección y por IP cada 24 horas; cuando se limita, la respuesta es 429 con un Retry-After encabezamiento.

Cuando userId está configurado y el par no se verifica, la respuesta es 403 con un solo mensaje independientemente de por qué: una cuenta desconocida y una dirección incorrecta responden de manera idéntica. Este punto final toma No hay credenciales (tiene que ser así, ya que así es como se adjunta una nueva clave), por lo que distinguirlas sería conviértalo en un oráculo para el cual existen identificadores de usuario y luego para sus direcciones. Una persona que llama y es propietaria del La cuenta ya sabe en cuál de los dos se equivocaron.

Abrir el enlace enviado por correo electrónico no cambia nada. Lo mismo se aplica a la revocación y vínculo de identidad confirmaciones a continuación.

Emite un desafío de inicio de sesión, válido por 5 minutos y de un solo uso.

Ciclo de vida del token

POST /api/v1/auth/refresh

Actualización rotativa: el token antiguo se revoca y se reemplaza. La reutilización de un token de actualización revocado revoca toda la familia de tokens.

Pedido:

{ "refreshToken": "dGhpcyBpcyBh..." }

Respuesta:

{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "bmV3IHJlZnJlc2g..."
}

Cuando la actualización deja de funcionar

Un token de actualización registra el estado de la cuenta bajo el cual se emitió y la actualización lo verifica. Dos respuestas su cliente debe manejar en lugar de volver a intentarlo:

Estado Significado Qué debe hacer el cliente
401 La sesión fue revocada en la plataforma: un "cerrar sesión en todas partes", o una respuesta de compromiso. Se quema toda la familia de fichas, incluida la ficha que se acaba de presentar. Descarta ambos tokens y comienza un nuevo inicio de sesión.
403 la cuenta es suspendido. Detener. Iniciar sesión nuevamente no ayudará; lo mismo 403 regresa de cada ruta de registro hasta que se levante la suspensión.

El 403 es deliberadamente distinto de 401, porque los dos necesitan reacciones opuestas: uno significa "autenticarse nuevamente", el otro significa "autenticarse de nuevo no tiene sentido". Una cuenta suspendida es rechazado por cada ruta de acuñación de credenciales: actualización, finalización de clave pública, devolución de llamada de OAuth, y tokens de lanzamiento de juegos, no solo mediante actualización.

POST /api/v1/auth/logout

Revoca el token de actualización proporcionado. Devuelve 200.

{ "refreshToken": "dGhpcyBpcyBh..." }

OAuth

La plataforma incluye siete proveedores: google, github, discord, twitch, gitlab, linkedin, bitbucket. Solo los proveedores para los que esta implementación tiene credenciales están activos. Un cliente no debe codificar la lista.

GET /api/v1/auth/oauth/providers

Anónimo. Devuelve los proveedores activos en el orden en que deberían ofrecerse:

{
  "providers": [
    {
      "provider": "google",
      "displayName": "Google",
      "authorizeUrl": "/api/v1/auth/oauth/google/authorize",
      "linksExistingAccountsByEmail": true
    }
  ]
}

linksExistingAccountsByEmail es si un inicio de sesión en ese proveedor puede encontrar una cuenta que la persona ya tiene (la configuración de confianza del operador para ese proveedor). Solicitar autorización para un nombre que no es vivir es 404, no una redirección a la página de error del propio proveedor.

GET /api/v1/auth/oauth/{provider}/authorize?link=&client=

Devuelve una redirección 302 al proveedor y establece un oauth_state cookie (HttpOnly, SameSite=Lax, 10 minutos). link=true comienza a vincular la identidad al usuario actualmente conectado; la vinculación requiere autenticación reciente (dentro de los 5 minutos). client selecciona una redirección de cliente compatible. por un juego abierto directamente, usar gameId y opcional returnUrl en cambio; ver Iniciar sesión desde un juego de navegador abierto directamente.

GET /api/v1/auth/oauth/{provider}/callback?code=&state=

Para el inicio de sesión de cuenta normal, devuelve una redirección 302 a la URL del frontend con los tokens en el fragmento (el inicio de sesión en el juego devuelve un token con alcance directamente al juego, como se describe a continuación):

#access_token=…&refresh_token=…&token_type=Bearer&expires_in=900

Si el proveedor rechaza el intercambio de token, la devolución de llamada responde 409 nombrar el error del proveedor código (la descripción permanece en el registro del servidor).

Un inicio de sesión normal busca o crea el usuario (nombre de usuario oauth-{provider}-{guid}, role User) y el nuevos registros de sesión auth_method=oauth. Un inicio de sesión cuyo (provider, providerUserId) se desconoce es adoptado en una cuenta existente sólo cuando se confía en la afirmación del proveedor, exactamente uno La cuenta ya contiene ese correo electrónico verificado y esa cuenta aún no tiene identidad de este proveedor. Todo lo demás se provisiona en una cuenta separada. La adopción envía un correo electrónico a la cuenta nombrando al proveedor.

Esto es importante porque solo una sesión autenticada por OAuth puede realizar cambios de credenciales de alto impacto:

  • agregar o revocar claves públicas de cuenta;
  • cambiar el correo electrónico de la cuenta;
  • eliminar una identidad administrada por OAuth.

Los tokens relacionados con el juego nunca pueden realizar estas operaciones. Un token de actualización conserva el original método de autenticación de la sesión, por lo que actualizar una sesión OAuth no elimina esta capacidad y actualizar una sesión de clave pública no la agrega.

Cuando link=true, la devolución de llamada no promueve automáticamente la sesión simplemente porque visitó un proveedor de OAuth. Se adjunta inmediatamente un enlace iniciado desde una sesión de OAuth. Un enlace comenzaba desde Se mantiene una sesión de clave pública, verificación de correo electrónico o heredada hasta que el propietario de la cuenta abre la cuenta. confirmación enviada al correo electrónico verificado de la cuenta; los informes del fragmento de redirección link=pending_email_confirmation. Se abre el correo electrónico único GET /api/v1/auth/oauth/link/confirm?token=…, una página que nombra la cuenta del proveedor y que no cambia nada; su botón Confirmar POSTes la misma URL, que crea la identidad ({ "provider", "linked": true } a un cliente API). Un enlace cuya dirección ya no es la cuenta es rechazada. Esto evita que una clave pública robada vincule la cuenta de proveedor del atacante y convertirla en un inicio de sesión OAuth permanente.

Almacenes de metadatos de identidad de GitHub {"login":"…"} — esto se utiliza para verificaciones de propiedad del repositorio en Juegos de GitHub.

Claves públicas inscritas en OAuth para automatización

Una sesión de OAuth puede llamar POST /api/v1/me/public-keys para adjuntar una llave de máquina etiquetada inmediatamente. Más tarde, CI firma el desafío de clave pública normal y usa su token de acceso de corta duración para cargar un paquete de juego propio; la clave privada nunca sale del almacén secreto de CI. Ver el tutorial de carga de compilación de CI/CD para la configuración, un asistente de firma y un flujo de trabajo de acciones de GitHub.

Fichas

  • token de acceso — JWT, vida útil de 15 minutos (expires_in=900). Las reclamaciones incluyen sub (la identificación del usuario) más permission y reivindicaciones de roles. La revocación surte efecto inmediatamente.
  • Actualizar ficha — Un token giratorio opaco con una vida útil de 7 días. Cada actualización emite un nuevo token de actualización y revoca el anterior; reutilizar un token revocado revoca toda la familia de tokens.

el opcional returnUrl conserva una página de juego específica, una cadena de consulta o una ruta hash. debe ser una URL HTTPS absoluta exactamente sobre el origen alojado de ese juego; otros juegos, hosts externos, Las credenciales en la URL y los puertos alternativos se rechazan con 400. Navegue por el navegador hasta origen de API pública arriba, en lugar de buscar la página o iniciar a través del juego /api apoderado. La cookie de estado de OAuth y la devolución de llamada del proveedor deben utilizar la misma Anfitrión API. Utilice este flujo cuando el juego no tenga un token válido proporcionado por el iniciador u obtenido previamente.

Ejemplo de botón y token de retorno

<button id="starhermit-sign-in">Sign in</button>
<script type="module">
const api = 'https://api.starhermit.com';
const gameId = 'YOUR_GAME_UID';
const signIn = document.querySelector('#starhermit-sign-in');
let gameToken = null; // Or your existing launcher-provided game token.

// Read this before your game router or third-party scripts consume the fragment.
const auth = new URLSearchParams(location.hash.slice(1));
if (auth.has('access_token')) {
  gameToken = auth.get('access_token');
  const originalHash = auth.get('game_fragment');
  history.replaceState(null, '', location.pathname + location.search +
    (originalHash ? '#' + originalHash : ''));
}
signIn.hidden = Boolean(gameToken);
signIn.addEventListener('click', () => {
  const url = new URL(`/api/v1/auth/games/${gameId}/sign-in`, api);
  url.searchParams.set('returnUrl', location.href);
  location.assign(url.href);
});

// Pass gameToken to your game's API client as Authorization: Bearer <gameToken>.
// This example keeps it in memory; a reload can require sign-in again.
</script>

El fragmento de retorno es:

#access_token=…&token_type=Bearer&expires_in=3600

access_token es un token de lanzamiento con ámbito de juego, no un token de acceso para toda la cuenta. Sin token de actualización se emite. expires_in utiliza la vida útil del token de inicio configurado de la implementación (predeterminado 3600 segundos). Un fragmento de URL de retorno original está codificado en el archivo opcional game_fragment campo; restáurelo después de capturar el token y eliminar los datos de autenticación del historial del navegador. No registre ni reenvíe el token.

Renovar antes de que caduque usando POST /api/v1/games/{gameId}/launch-token con el token actual como Autorización al portador, luego reemplácela con la devuelta. token. El techo habitual de la cadena de renovación aplica (predeterminado 12 horas). Si el token caduca o se rechaza la renovación, bórrelo y muestre Iniciar sesión otra vez. Ver Fichas de lanzamiento del juego.

Elegir un proveedor usted mismo

En su lugar, los juegos pueden leer GET /api/v1/auth/oauth/providers y navegar a una oferta authorizeUrl en el origen de la API pública, agregando gameId y opcionalmente returnUrl. El paso de autorización valida y almacena el objetivo en el estado OAuth existente de diez minutos; parámetros de consulta de devolución de llamada no puedo cambiarlo. La cookie del navegador de inicio aún es necesaria y el juego se vuelve a verificar. antes de emitir una ficha. Las cuentas suspendidas no pueden recibir un token.

No combine el inicio de sesión en el juego con client o link (400). A returnUrl sin gameId también es 400. El inicio de sesión normal en el panel y el escritorio continúa usando sus destinos de interfaz configurados y pares de tokens de cuentas ordinarias.

Fichas de lanzamiento del juego

POST /api/v1/games/{slug}/launch-token (JWT) crea un JWT con alcance de juego:

{
  "token": "eyJhbGciOi...",
  "expiresInSeconds": 3600
}

La ficha lleva un game_scope reclamo y por defecto tiene una vida útil de 60 minutos. La renovación copia una launch_chain hora de inicio adelantada; la renovación de las últimas 12 horas (predeterminada) es 403 y el titular debe ir volver a una sesión de cuenta completa. Todos los detalles están en Juegos.

Reconexión de enchufes. Un socket se abrió con un token de lanzamiento (?access_token= en ws/v1/games, ws/v1/realtime, ws/v1/voice) lleva ese token en su URL y un protocolo de enlace con un token caducado es rechazado con 401 antes de la actualización: el navegador solo informa el código de cierre 1006, lo mismo que un caída de la red. Trate una reconexión fallida como posiblemente una falla de autenticación: antes de reabrir, renueve a través de POST /api/v1/games/{slug}/launch-token (solo es posible mientras el token actual aún sea válido y dentro de las 12 horas posteriores al lanzamiento original) y cree la URL con el nuevo token. Una vez realizada la renovación rechazado, envíe el jugador de regreso al lanzador, o a través de iniciar sesión en el juego si así se abrió el juego. Volver a intentar la misma URL nunca podrá recuperarse.

Esgrima de ámbito de juego

Un token con ámbito de juego solo puede alcanzar:

  • su propio /api/v1/games/{scope} árbol,
  • /ws/v1/games,
  • sala en tiempo real rutas de DESCANSO y /ws/v1/realtime para su propio juego, incluidos los billetes de conexión,
  • GET /api/v1/time y GET /api/v1/terms,
  • POST /api/v1/me/terms/accept por el consentimiento explícito del jugador autenticado,
  • GET /api/v1/me/friends,
  • GET /api/v1/users/{id}/avatar y GET /api/v1/users/{id}/profile,
  • la tabla de clasificación de su juego,
  • el del jugador guardar en la nube para su propio juego (/api/v1/me/cloud-saves/game:<scope> y su /info) — ninguna otra clave,
  • los puntos finales REST y WebSocket de chat/voz adjuntos a sus propias sesiones de juego,
  • GET /api/v1/github-games/{id}/icon y /cover para cualquier juego (ambos son públicos de todos modos),
  • POST /api/v1/me/heartbeat, que sólo marca al jugador en línea,
  • GET /api/v1/github-games/{id}/release-notes para su propio juego,
  • relé rutas, para relevos vinculados a una de sus propias sesiones o salas de juego.

/ws/v1/chat está bloqueado para tokens de lanzamiento. Todo lo demás devuelve 403.

Flujo de inicio de sesión típico (curl)

Inicio de sesión con clave pública, desde el desafío hasta la llamada autenticada:

# 1. Request a challenge
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/challenge \
  -H "Content-Type: application/json" \
  -d '{"keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "challengeId": "...", "payload": { ... }, "expiresIn": 300 }

# 2. Sign the serialized payload JSON with your private key, then complete
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/complete \
  -H "Content-Type: application/json" \
  -d '{"challengeId":"...","signature":"base64-signature...","keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "userId": "...", "accessToken": "...", "refreshToken": "..." }

# 3. Call the API with the access token
curl -s https://api.starhermit.com/api/v1/me \
  -H "Authorization: Bearer eyJhbGciOi..."

# 4. When the access token expires (after 15 min), rotate the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

# 5. On logout, revoke the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

El inicio de sesión de OAuth se realiza mediante navegador: leer GET /api/v1/auth/oauth/providers, abre la cuenta de un proveedor en vivo authorizeUrl, consentimiento completo y la devolución de llamada lleva al usuario a la interfaz con #access_token=…&refresh_token=… en el fragmento de URL.

Boletos de conexión WebSocket

POST /api/v1/realtime/connection-tickets intercambia el token al portador de la persona que llama por un billete único válido unos 30 segundos. Pasalo como ?ticket= en cualquier /ws/v1/* apretón de manos. Lleva la información de la persona que llama. afirmaciones palabra por palabra (incluyendo game_scope y pk), se rechaza en REST y se gasta en el primer uso. Cualquier persona que llame autenticada puede preguntar, incluido un token de inicio del juego. ?access_token= todavía funciona hasta que los clientes se hayan mudado.

Un socket abierto finaliza cuando se revoca su credencial. Finaliza la revocación de la clave pública que la abrió inmediatamente; una suspensión o un cierre de sesión en cualquier lugar finaliza en unos 30 segundos. Caducidad del token no finaliza un socket abierto: actualice antes de volver a conectarse.

El registro no es silencioso: el jugador debe dar su consentimiento, proporcionar un correo electrónico y seguir las enlace de verificación único.
