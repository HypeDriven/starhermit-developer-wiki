Guiones de juego

Un juego autorizado de StarHermit puede definirse mediante un único archivo JavaScript ejecutado en el lado del servidor en un espacio aislado Jint motor. El script es la única autoridad sobre las reglas de ese juego: valida cada comando de jugador, muta el estado, decide lo que cada cliente puede ver, calcula Elo y finaliza los juegos. Los clientes no tienen autoridad. Esta página documenta el tiempo de ejecución de JavaScript; Los juegos que necesitan otro idioma pueden implementar el Servidor de juegos de contenedores protocolo. Ambos usan la misma orientación hacia el jugador. API de juegos. El ejemplo trabajado en todo momento es el ajedrez, la implementación de referencia en HypeDriven/ajedrez ermitaño estrella.

Modelo de ejecución

  • Un archivo JS por juego, ejecutado en un Motor Jint nuevo en espacio aislado por invocación. Nada persiste en la memoria entre llamadas: todo el estado reside en los documentos que devuelve.
  • Sin ambiente Date o Math.random. El tiempo y la aleatoriedad se proporcionan como: ctx.now (época ms) y ctx.random (flotar en [0, 1)).
  • La plataforma invoca el script cuando un jugador envía un comando duradero, cuando se crea una sesión y periódicamente. onTick barridos (ver API de juegos: tiempo de ejecución). En tiempo real {type:"input", realtime:true} los fotogramas son la excepción: se almacenan en buffer y se entregan como un lote para el siguiente tick.

Puntos de entrada

Exponer a los manipuladores en globalThis.game. Seis opcionales estático Las declaraciones se encuentran junto a ellos: tickRateHz pregunta a la plataforma con qué frecuencia invocar onTick — declaralo si tu juego depende del tick, ya que un juego que no dice nada se marca una vez cada cuatro segundos (ver tasa de tic), achievements registra los logros del juego (ver Logros), replays solicita a la plataforma que conserve sus sesiones finalizadas (ver Repeticiones), persistent pausas sesiones en lugar de finalizarlas cuando todos se van (ver Sesiones persistentes), linkedAchievements nombra otros juegos cuyos desbloqueos recibes en ctx.linkedAchievements (ver Logros de otros juegos.), y queues declara las formas de emparejamiento casamentero acepta (ver Juegos: emparejamiento). un juego que no declara colas tiene un 1v1 implícito:

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }

  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }

Las declaraciones se leen evaluando su guión. cuando el juego se publica o actualiza, no en cada invocación, por lo que deben ser valores estáticos en el game objeto. Publicar una actualización para aplicar un cambio.

  • createSession(ctx) - se llama cuando se crea una sesión (emparejamiento, aceptación de invitación, práctica de IA o inicio de una sala en tiempo real; consulte Sesiones en sala).
  • onPlayerMessage(ctx) — solicitó comandos de cliente duraderos recibidos a través del WebSocket del juego. Entradas marcadas explícitamente realtime:true omita este punto de entrada.
  • onMembershipChange(ctx) - opcional. Se llama cuando un jugador se une o abandona una sesión de carrera (una sala de unión en progreso, o un invitar a un juego en progreso). ctx.players ya refleja el cambio, y ctx.membership es { change: "joined" | "left", userId, name, team, slot }. Devolver { ok: false } rechazar una unión; un script sin este gancho rechaza todas las uniones. Un permiso es definitivo independientemente de lo que regrese. Los logros y las puntuaciones pueden influir en el resultado; a sessionState es ignorado.
  • onTick(ctx) — llamado por el servicio de cronómetro de la plataforma al ritmo de tick efectivo; Las últimas entradas en tiempo real están disponibles en ctx.inputs. Un juego que se resuelve a 0 Hz no recibe llamadas periódicas, pero la función aún debería estar presente para cumplir con el contrato del script.

Un jugador sin valoración aún lee 1200. Es idéntico al crear, marcar, enviar mensajes y restaurar; cambiar una calificación sólo a través de eloUpdates.

Los scripts deben fijar y validar cada valor al consumir el lote.

tasa de tic

La plataforma funciona onTick barridos por sesión activa a un ritmo configurable. Su script solicita la tarifa que quiere declarando una estática tickRateHz en el objeto del juego, junto a los puntos de entrada:

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • Se lee la declaración cuando tu juego se publica o actualiza, no en cada tic. Publicar una actualización después de cambiarla.
  • Un juego que no declara ninguna frecuencia se marca en 0,25 Hz. – una vez cada cuatro segundos. Eso es suficiente para adjudicar un reloj de movimiento o un tiempo de espera y no le cuesta casi nada a la plataforma, pero es demasiado lento para cualquier cosa de la que dependa tu juego. Si onTick impulsa tu juego, declara la tarifa que necesitas.
  • Las solicitudes se limitan al máximo de la plataforma (30Hz por defecto), por lo que un juego puede pedir menos de lo que permite la plataforma pero nunca por más. Pedir 0 Desactivar ticks por completo para un juego. que sólo reacciona a los comandos del jugador.
  • Las tarifas pueden ser fraccionario: 0.5 es un tic cada dos segundos. La tasa más pequeña distinta de cero es 0.01 Hz: se le eleva un número positivo más pequeño en lugar de leerse como una exclusión voluntaria, porque pequeña fracción es un juego lento. El tictac está desactivado sólo para 0 o una tasa negativa. Un desaparecido o declaración inutilizable (una cadena, null, NaN) toma el valor predeterminado de 0,25 Hz.
  • Un operador puede anular la tarifa de un juego en particular, en cualquier dirección.
  • Las entradas en tiempo real son las últimas ganancias entre ticks, mientras que los bordes de acción discretos permanecen ordenados. Un destinatario lento puede omitir una instantánea obsoleta, pero no puede retrasar la simulación ni a otros destinatarios.

Repeticiones

Cuando finaliza una sesión, la plataforma puede mantener su final sessionState como el repetición — el documento entregado por GET /api/v1/games/{slug}/replays/{sessionId} (ver API de juegos: repeticiones). Una repetición se almacena mientras dure el registro del partido. es, entonces tu juego obtiene uno solo si te lo pide:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • La declaración debe ser literal. true o false — cualquier otra cosa se considerará sin declaración, y un juego que no declara nada no tiene repeticiones.
  • se lee cuando tu juego se publica o actualiza. Publicar una actualización después de cambiarla.
  • Un operador de plataforma puede responder por un juego en particular de cualquier manera, por lo que la declaración es una solicitud. en lugar de una garantía. GET /api/v1/games/{slug} informa la respuesta como replaysEnabled — ramifique su interfaz de usuario de repetición en eso, no en lo que solicitó su secuencia de comandos.
  • Nada más cambia con las repeticiones desactivadas: el estado de tu sesión aún se almacena y se devuelve a cada invocación como ctx.sessionState, y sigue siendo el punto de restauración por fallo. que juego sin repeticiones no se obtiene una copia que sobrevive a la sesión, por lo que sus puntos finales de reproducción responden 404.
  • Diseñar la final sessionState para que valga la pena reproducirlo: un registro de movimientos o lo que su cliente necesite para reconstruir el partido. La implementación de referencia de ajedrez mantiene state.game.moves y lo pisa a través del mismo módulo de reglas que ejecuta la plataforma.

Sesiones persistentes

Un juego que declara persistent: true mantiene sus sesiones cuando cada jugador se va. alrededor de 15 Segundos después de la última desconexión, la sesión se interrumpe. pausado - No onTick llamadas - y la primera El reproductor se vuelve a conectar y lo reanuda. La desconexión o la inactividad pausan la sesión en lugar de abandonarla. Un resultado del juego, dueño. acción, la licencia explícita del miembro final, el vencimiento de la retención configurada o la falla de recuperación del terminal pueden todavía terminarlo. Ver Ciclo de vida de la sesión.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • debe ser literal true o false. se lee cuando tu juego se publica o actualiza.
  • ctx.now se queda el reloj de pared. Las sesiones persistentes también obtienen ctx.pausedMs, el tiempo total empleado pausado, entonces ctx.now - ctx.pausedMs Es un reloj que se detiene mientras no hay nadie.
  • Las sesiones en pausa cuentan para el límite de sesiones por jugador, así que dales a los jugadores un comando que finalice una mundo con un result.

Ver el tutorial de sesiones persistentes para ver un ejemplo trabajado y el flujo de clientes.

Disposición de los asientos de emparejamiento

Nuevas sesiones emparejadas reciben ctx.matchmaking en cada invocación (crear, ordenar y marcar). Conserva la forma de la cola y los asientos incluso si el juego se vuelve a implementar más tarde:

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players contiene únicamente asientos ocupados, con team y ai:true para IA. Los índices de equipo/espacio son de base cero. Los ID de AI son estables dentro de esta sesión y no son ID de cuenta de StarHermit. Solo humanos tiene membresía de sesión/chat y puede recibir escrituras sobre el estado del jugador, la calificación o los logros de la cuenta. Mantener el estado de la IA en sessionState. Copie los campos de la lista que los clientes necesiten en el estado de su juego. o transmisiones. Se pueden omitir las sesiones más antiguas y las que no son de emparejamiento. ctx.matchmaking.

Declarar una fecha límite de inicio y el recuento máximo de IA en starhermit.txt. Con recuento de IA 0, los asientos vacantes permanecen vacíos. El mismo contexto se entrega a los servidores de contenedores.

Sesiones en sala

Una sesión puede ser vinculado a una habitación en tiempo real: cuando un sala en tiempo real para un juego con un server= Cuando se inicia el script, la plataforma crea una sesión de N jugadores para la sala. humano participantes (los asientos AI existen solo en la lista orientada al guión). Así es como se ejecutan los juegos en tiempo real autorizados por el servidor (por ejemplo, fútbol): las salas proporcionan el lobby/emparejamiento, el script ejecuta el partido. Ver Salas en tiempo real: el puente para el ciclo de vida del lado de la habitación.

Cada invocación (createSession, onPlayerMessage, onTick) de una sesión limitada a una sala recibe dos campos ctx adicionales:

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online — el usuario tiene un socket en vivo en cualquiera de los registros de conexión (salas en tiempo real o ws/v1/games).
  • presence.left — el usuario ya no tiene un asiento activo: lo abandonó explícitamente y su asiento se convirtió en un participante de IA. left es permanente; online puede aletear. Se espera que el script impulse la lógica de adquisición/reunión de la IA desde estos indicadores.
  • La lista se relee en cada invocación, por lo que las conversiones de asientos (humanos → IA) aparecen a medida que ocurren.

Cuando regresa un guión limitado a una habitación result, la plataforma finaliza la sesión, almacena el resultado en la habitación y cierra la habitación — no se trata de ningún resultado enviado por el anfitrión.

Lo contrario no es cierto: un cierre de sala no finaliza su sesión. Si la sala se cierra primero (por ejemplo, porque el último ser humano abandonó una sala sin unirse en progreso, nunca simplemente porque el anfitrión se desconectó, lo que solo mueve la función de anfitrión mientras la sesión está activa), la sesión continúa ejecutándose. ctx.room.roster se vuelve vacío y cada ser humano muestra left: true. Devolver result entonces si el partido debe terminar con la habitación. Ver Salas en tiempo real: la regla del anfitrión de 60 segundos y sesiones limitadas a la sala.

Forma de retorno

Cada punto de entrada devuelve la misma forma (todos los campos son opcionales excepto ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

Reglas clave:

  • sessionState y cada entrada de playerStates reemplazar los documentos almacenados: siempre devuelve documentos completos, nunca diferencias.
  • Sólo los mensajes enumerados en broadcast se entregan a los clientes, cada uno dirigido a identificadores de jugador explícitos o "all". No se filtra nada más.
  • eloUpdates es la única forma en que cambian las calificaciones. Los valores son de cada jugador. nueva calificación absoluta, aplicado tal como se envió: la plataforma no limita el cambio por partido, así que fíjelo usted mismo (consulte Elo por partido). El anfitrión los utiliza para buscar emparejamientos y los publica en la tabla de clasificación del juego; Los clientes nunca pueden enviar puntuaciones directamente (ver Tablas de clasificación). Mantener la calificación en playerStates[id].elo entonces un dueño reinicio de calificación llega a tu copia también.
  • achievements es la única forma en que se otorgan los logros. Las claves se resuelven en función de los logros del juego (declarados o creados por su propietario) y la plataforma las conserva; ver Logros.
  • scores es la única forma en que cambian las tablas de clasificación de tu juego; consulta Tablas de clasificación.
  • Finalizar juegos vía result. Luego, el anfitrión finaliza la sesión y, para un juego con repeticiones archiva la final sessionState como la repetición (servida por GET .../replays/{sessionId} - ver API de juegos).

Logros

Tu guión es el solo cosa que puede desbloquear los logros de tu juego. no hay cliente punto final para ellos: POST /api/v1/me/achievements/unlock rechaza de plano los logros relacionados con el juego, y los puntos finales CRUD del editor se niegan a tocarlos. El propietario del juego puede agregar logros al lado los declarados mediante /me/github-games/{id}/achievements; su secuencia de comandos los desbloquea mediante clave exactamente de la misma manera. Esto hace que los logros como servidor- autoritario como el resto del juego, y es el mecanismo cualquier juego con un server= guión debería usar, incluido uno cuyo juego se ejecuta en otro lugar (consulte ¿Qué juegos pueden usar esto?).

Declarar

una estática achievements matriz en el game objeto. Solo key se requiere:

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
Campo Tipo Notas
key cadena Requerido. Identificación estable, ≤ 128 caracteres, única dentro del juego. Los duplicados posteriores al primero se ignoran.
name cadena El valor predeterminado es key.
description cadena El valor predeterminado es "".
icon cadena URL opcional.
secret booleano Oculto de un jugador hasta ellos desbloquearlo. El valor predeterminado es false.
points número Sujetado a 0–10000. El valor predeterminado es 0.

La matriz se aplica cuando el juego se publica o actualiza:

  • Las definiciones coinciden con key — editar un nombre, icono, puntos o bandera secreta actualiza la definición existente y todos los que ya la obtuvieron la conservan.
  • Se elimina una clave que dejas de declarar solo mientras nadie lo haya desbloqueado. El historial obtenido nunca se destruye, por lo que un logro retirado permanece visible para los jugadores que lo poseen.
  • A lo sumo 100 logros por juego; los extras más allá de eso se eliminan.
  • La declaración es mejor esfuerzo: se omiten las entradas con formato incorrecto. Confirme siempre las definiciones publicadas con GET /api/v1/games/{slug}/achievements después de actualizar el juego.

Descubrir

Devolver un achievements mapa de cualquier punto de entrada— createSession, onPlayerMessage, o onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • Los desbloqueos son idempotente — reafirmar una clave que el jugador ya posee no es una operación, por lo que un script puede otorgar con seguridad una condición que reevalúa en cada tick en lugar de realizar un seguimiento "ya premiado" en su propio estado.
  • Las claves desconocidas (ni declaradas ni creadas por el propietario del juego), los usuarios que no participan en esta sesión y el puesto de IA se ignoran silenciosamente.
  • A lo sumo 32 las claves se aceptan por jugador por invocación; Se eliminan más claves en la misma matriz.
  • Las filas persisten con el resto de las escrituras de la invocación, por lo que un desbloqueo no puede sobrevivir a una invocación fallida.

Entrega

Cada desbloqueo recién otorgado se envía al jugador que lo obtuvo. ws/v1/games como un marco distinto - es la verdad de la plataforma, no una de tus broadcast mensajes:

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

Desbloqueos otorgados desde createSession aterrizan antes de que exista cualquier enchufe, por lo que llegan sin marco. los clientes deben leer GET /api/v1/games/{slug}/achievements en carga y trate el marco como el ruta de actualización en vivo. Superficie completa en Logros.

Tablas de clasificación

Además del tablero elo, tu juego puede tener tablas de clasificación que su propietario crea a través de POST /api/v1/me/github-games/{id}/leaderboards, cada uno con un key. Publicarles regresando scores desde cualquier punto de entrada: clave del tablero → identificación del jugador → número:

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • Cada jugador mantiene su mejor puntuación en cada tablero, según la dirección de clasificación del tablero, así que informe cada resultado, uno peor, simplemente se ignora.
  • Sólo cuentan los participantes de la sesión. Claves desconocidas o inactivas y puntuaciones fuera de las reglas del tablero. se dejan caer silenciosamente. Como máximo 16 tableros por devolución.
  • A diferencia de eloUpdates, no se publica nada en playerStates — guarde su propia copia en playerStates si el juego necesita leer una marca personal.

Dónde se ejecuta tu script

Un script que se repite sin límite, agota su memoria o excede su presupuesto de tiempo falla. invocación. Su resultado fallido no se aplica. El comando o tick informa uno de:

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

La parte del servidor que le corresponde a tu juego

  • Hora del guión. Todas las sesiones de un juego comparten un presupuesto de tiempo de guión, 2000 ms por segundo por por defecto, cargado con lo que realmente tomó cada invocación. Un juego sobre su parte se rechaza más bien que en cola: se omite un tic, se responde a un comando con "Este juego está usando más de lo que le corresponde. del servidor ahora mismo; Inténtalo de nuevo en breve.", y al crear una sesión se devuelve 429.
  • Comandos. Cada jugador puede enviar 20 comandos duraderos por segundo por sesión (con una breve ráfaga asignación); más allá de eso, una orden se responde con un error marco, "Demasiados comandos; desacelerar." El marco no incluye un estado HTTP. La entrada en tiempo real está limitada por separado.
  • Resultados. El resultado con el que finaliza una sesión puede ser como máximo 64 KB; uno más grande es rechazado con 422.
  • Tamaño del guión. A server= el script puede tener como máximo 2 MB; uno más grande es rechazado con 422 antes se almacena o analiza.

Los operadores pueden subir o bajar cada uno de estos para un juego individual.

Presupuestos

Los scripts se ejecutan con estos presupuestos de recursos:

  • ~250 ms de CPU por invocación
  • Memoria de 32MB
  • Un límite de declaración por invocación
  • Un presupuesto de bytes estatales por jugador: todos los documentos estatales deben ser serializables y pequeños
  • Los valores se anidan como máximo en 64 niveles de profundidad cuando se convierten en texto. Todo lo que devuelve un punto de entrada, cada declaración, JSON.stringify, y Array.prototype.join/toString/toLocaleString rechazar un valor más profundo con un RangeError (uno devuelto falla la invocación: "anidado más de 64 niveles profundo"). JSON.parse ya se detuvo en 64, por lo que un valor más profundo nunca podría regresar. flat se aplana hasta 64 niveles y se lanza si la matriz se anida más profundamente, incluida una matriz que contiene mismo.
  • Una llamada no puede asignar más que el presupuesto de memoria. repeat, padStart/padEnd, concat y replace/replaceAll tirar RangeError: Invalid string length cuando el resultado podría exceder la mitad el presupuesto en caracteres (16M con el valor predeterminado de 32 MB; un reemplazo de expresiones regulares está limitado como si cada posición coincidente, que sólo afecta a cadenas de aproximadamente un millón de caracteres o más). ArrayBuffer y arrojar matrices escritas RangeError más allá del presupuesto en bytes y matrices más allá presupuesto/8 elementos son rechazados. El presupuesto también se verifica después de que regrese su anzuelo, por lo que un La declaración final por encima del presupuesto fracasa en la invocación en lugar de tener éxito.

El script de referencia de ajedrez mantiene sus documentos pequeños a propósito; como ejemplo de cómo mantenerse dentro del presupuesto, su documento por jugador es

{
  elo: 1200,
  wins: 0, losses: 0, draws: 0,
  lastColorVs: "9b2f8c1a-...",        // for color alternation on rematch
  lastColorOrder: "w",
  recentGames: [ /* up to 30 summaries */ ]
}

El límite de sesiones simultáneas es de 20 por jugador de forma predeterminada.

La ventana legible por la plataforma

Todo en sessionState es opaco a la plataforma excepto un campo:

sessionState.summary = {
  turnPlayerId: "7c9e6679-...",
  deadline: 1784642591000,
  status: "active",
  moveCount: 41
};

deadline es una marca de tiempo entera de Unix en milisegundos, u omitido cuando no hay fecha límite. No se reconoce una cadena de fecha ISO. turnPlayerId es el UUID del jugador.

Ejemplo resuelto: el guión de ajedrez

Todo lo que se incluye en esta sección es específico de la implementación de referencia del ajedrez: la forma del estado, la codificación del tablero, el conjunto de comandos, los motivos de finalización del juego, la constante Elo, la IA y los tiempos de espera a continuación son elecciones propias del ajedrez, definidas en su guión. Nada de esto es comportamiento de plataforma; Tu juego define sus propios equivalentes.

Estado de la sesión:

{
  white: "7c9e6679-...",
  black: "9b2f8c1a-...",
  aiId: "00000000-0000-4000-8000-00000000a1a1",   // present in AI games
  game: {
    board: "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr", // 64 chars
    turn: "w",
    castling: { K: true, Q: true, k: true, q: true },
    epSquare: null,
    halfmoveClock: 0,
    fullmove: 1,
    moves: [ { from: "e2", to: "e4", promo: null, san: "e4", at: 1721473200000 } ],
    positionCounts: { /* fen-key: count, for threefold repetition */ },
    status: "active"
  },
  createdAt: 1721473200000,
  deadline: 1721559600000,
  result: null,
  drawOfferBy: null,
  summary: { turnPlayerId: "...", deadline: "...", status: "active", moveCount: 1 }
}

Codificación del tablero: una cadena de 64 caracteres donde index = rank * 8 + file y a1 es el índice 0. PNBRQK son piezas blancas, pnbrqk negro, . es un cuadrado vacío.

Comandos manejados por onPlayerMessage: sync, move, resign, offer-draw, accept-draw, decline-draw (formas de alambre en API de juegos).

Juego terminado reason valores: checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

Otros detalles del ajedrez:

  • elo utiliza K=32, calculado en finishGame cuando termina un juego y regresa a través de eloUpdates.
  • Juego de IA: cuando el asiento de la IA se va a mover, aiReply juega "hala" – un codicioso motor de captura de material – dentro de la misma invocación. No hay ningún bot externo.
  • Tiempos de espera: onTick adjudica el reloj de movimientos de 24 horas: si no se han realizado movimientos, el juego es un timeout-no-moves dibujar; de lo contrario, el jugador que mueve pierde por timeout.

Despliegue

Declara el script en el repositorio de tu juego. starhermit.txt manifiesto:

server=server.js

La publicación fluye a través de la integración de GitHub; consulte Juegos de GitHub. La plataforma ejecuta el script dentro de los presupuestos documentados. no combinar server= con container.image=; utilizar el tiempo de ejecución del contenedor en su lugar al enviar una imagen.

Mejores prácticas

  • Valida cada comando. Tratar ctx.message.data como hostil: verifique los tipos, rangos, orden de turno y estado del juego antes de tocar el estado.
  • Mantenga las invocaciones rápidas y el estado pequeño. Tienes ~250 ms y un presupuesto de bytes por documento de reproductor; el guión de referencia de ajedrez, por ejemplo, mayúsculas recentGames en 30 entradas por este motivo.
  • Usar ctx.now / ctx.random solo. No Date, No Math.random — el anfitrión es dueño del reloj y de los dados.
  • Diseño broadcast mensajes como único contrato de cliente. Los clientes deben poder renderizar el juego completo a partir de lo que envía el script; todo lo que no se transmite no existe para ellos.
  • Una lima, dos superficies. El mismo archivo puede funcionar como reglas del lado del cliente a través de una exportación separada: la implementación de referencia de ajedrez, por ejemplo, expone globalThis.chessRules para el navegador (mover vista previa, sugerencias de validación) y globalThis.game para el anfitrión. Una fuente de verdad, cero autoridad sobre el cliente.
  • Finalizar siempre los juegos mediante result para que la plataforma publique actualizaciones de Elo y archive la repetición cuando tu juego haya terminado. repeticiones.
