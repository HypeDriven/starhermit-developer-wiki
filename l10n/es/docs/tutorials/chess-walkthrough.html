Tutorial de integración: creación de un juego en StarHermit

Esta página recorre el ciclo de vida completo de la integración de un juego con StarHermit, paso a paso: publicación, inicio, menú, emparejamiento, juego, chat, voz, calificaciones, repeticiones. Todo lo mostrado se aplica a cualquier Juego: tu juego sustituye su propio slug, sus propios comandos y su propio script de reglas.

El ejemplo en ejecución es la implementación de referencia de ajedrez de código abierto, ajedrez-ermitaño-estrella: un juego de ajedrez por correspondencia (24 horas por movimiento, con clasificación elo) creado como un juego de navegador estático sin compilación en HTML/JS/CSS básico. Para cada paso, el tutorial muestra las llamadas exactas que realiza un cliente de juego y el archivo en el repositorio de referencia que las realiza. Dondequiera que aparezcan valores específicos del ajedrez (el UUID del juego de referencia, comandos de movimiento, la codificación del tablero, el "hala" IA, la fecha límite de movimiento de 24 horas: son valores de ejemplo que tu propio juego define en su propio guión.

Léalo junto con las páginas de referencia de API a las que enlaza. La lista de verificación al final condensa todo en lo que tu propio juego necesita replicar.

1. Anatomía de un juego alojado en una plataforma

Un juego de plataformas con guión es un sitio estático simple más un archivo de reglas. La implementación de referencia de ajedrez, por ejemplo, no tiene paquete, marco ni paso de compilación:

Archivo Role
index.html Toda la página: tablero, menú, chat y UI de voz
app.js Arranque de la aplicación, menú principal, emparejamiento, invitaciones, repeticiones, perfiles
net.js Capa HTTP: rutas de juego con alcance, tokens de lanzamiento, actualización de tokens
game.js Controlador en el juego: juego WebSocket, chat, voz
ui.js Representación de tablero y menú
style.css Estilos
server.js Las reglas - ver más abajo
starhermit.txt Publicar manifiesto

En la implementación de referencia, server.js merece especial atención. Es ambos cosas a la vez:

  • El script autoritativo del servidor la plataforma se ejecuta (a través de su host Jint) exponiendo globalThis.game. Cada movimiento se valida aquí, en el servidor, según el contrato en game-scripts.md.
  • el del cliente motor de reglas compartidas, expuesto como globalThis.chessRules, que el navegador utiliza para renderizar tableros, mover vistas previas y reproducir reproducciones.

Un archivo, una fuente de verdad, autoridad de reglas cero en el cliente. Un cliente de juego que sigue este patrón nunca decide si un movimiento es legal: muestra lo que transmite el servidor. Esta es la idea arquitectónica más importante en un juego de plataformas con guión, y la implementación de referencia lo demuestra.

2. Publicar tu juego

La publicación de cualquier juego comienza con el starhermit.txt manifiesto en la raíz del repositorio. Declara el juego name, launch punto de entrada, owner, y server guion. Opcional cover= es la obra de arte en el mosaico de la biblioteca; consulte El starhermit.txt manifiesto. El manifiesto de la implementación de referencia, por ejemplo:

name=StarHermit Chess
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # StarHermit user ID, not username/nickname
server=server.js

Usa lo inmutable id de GET /api/v1/me para owner; Se muestran los nombres de usuario y apodos. valores y no deben utilizarse como identificadores de propiedad manifiesta.

La plataforma clona el repositorio, sirve los archivos estáticos en <slug>.starhermit.com — el slug es el fluido que la plataforma asigna al juego, nunca un nombre que tú elijas; el juego de referencia es 83fd04b1-3cbe-4b09-a251-3733ad4b9d94, por lo que se puede reproducir en vivo en 83fd04b1-3cbe-4b09-a251-3733ad4b9d94.starhermit.com - y apoderados /api y /ws al fondo mismo origen. Esa única decisión elimina toda una categoría de trabajo: sin CORS, sin configuración basada en API, sin detección de entorno: los clientes de juegos solo usan rutas relativas.

Flujo completo: github-games.md y publisher.md.

3. Lanzamiento y autenticación.

El flujo de referencia de ajedrez recibe las credenciales del iniciador de la plataforma:

  1. El lanzador llama POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/launch-token (se muestra con el UUID del juego de referencia; sustitúyalo por el suyo) con el JWT de plataforma completa del usuario.
  2. Vuelve a ser de corta duración, ámbito del juego simbólico:
{ "token": "<jwt>", "expiresInSeconds": 3600 }
  1. Abre el juego en index.html#game_token=<jwt>, opcionalmente con &session_id=<guid> adjunto para invitar a enlaces profundos.

En la implementación de referencia, el cliente lee el hash. una vez, luego lo pela con history.replaceState para que el token nunca permanezca en la barra de URL o en el historial (app.js, App.init). Decodifica la carga útil JWT para dos reclamaciones:

  • sub — la identificación del usuario
  • game_scope - la babosa del juego

Ese segundo reclamo importa: un cliente de juego nunca debería codificar su slug. La implementación de referencia construye cada URL de API como /api/v1/games/<slug> más un sufijo (net.js, Net.gamePath), por lo que el mismo código funciona para cualquier juego, cualquier slug, cualquier implementación.

Refrescar. El token con alcance puede volver a llamarse launch-token para su propio juego, por lo que los clientes normalmente se actualizan periódicamente: la implementación de referencia se actualiza cada 45 minutos (net.js, Net.startRefresh), cómodamente dentro de la vida útil de 60 minutos.

Un juego abierto directamente puede ofrecer en cambio inicio de sesión en el navegador, que regresa #access_token en lugar del lanzador #game_token. Maneje ambas rutas de entrada si apoyas a ambos. Renueve utilizando la vida útil devuelta y respete la cadena de renovación predeterminada de 12 horas techo. A 403 terms_acceptance_required requiere que el jugador aceptar a través de su cuenta; o muestra los términos en el juego y acepta con el token de inicio del jugador. Iniciar sesión nuevamente no aceptación del registro.

Referencia de autenticación: auth.md, games.md.

5. Involucrar a los jugadores en una sesión: tres formas

Este tutorial utiliza práctica de emparejamiento, aceptación de invitaciones e inteligencia artificial para crear sesiones. Los juegos que necesitan un lobby pueden usar salas en tiempo real, cuyo flujo de inicio también puede crear una sesión autorizada vinculada.

a. Casamentero

En la implementación de referencia, App.startMatchmaking en app.js:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking

La respuesta es un ticket:

{ "ticketId": "<guid>", "status": "queued" }

o una coincidencia inmediata:

{ "status": "matched", "sessionId": "<guid>" }

Mientras están en cola, los clientes sondean el punto final de emparejamiento: las encuestas de implementación de referencia. GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking cada 3 segundos y DELETE /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking cancela el billete. El cliente de referencia también se asegura de que el jugador nunca se quede atascado mirando una ruleta: después de 30 segundos sin igual, un "jugar contra hal" Aparece el botón ("hala" es el oponente de IA integrado del ejemplo de ajedrez (ver §12), y POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai regresa { "sessionId" }.

b. invitación de amigo

En la implementación de referencia, App.inviteFriend en app.js. Primera lista de amigos: este punto final está permitido explícitamente para tokens con ámbito de juego:

GET /api/v1/me/friends

Luego envía la invitación:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites
{ "toUserId": "<guid>" }

El destinatario acepta (o rechaza) de su propio cliente:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/accept   → { "sessionId": "<guid>" }
POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/decline  → 204

Aceptar es lo que crea la sesión. El &session_id= launch-hash deep-link (§3) coloca al jugador invitado directamente en él.

Las invitaciones de amigos solo llegan a personas que ya son amigos. Para atraer a alguien que no está (o que no está en absoluto) en la plataforma, la implementación de referencia también ofrece una Compartir enlace de invitación botón (App.shareInviteLink): una línea de construcción de cadenas que copia

https://dashboard.starhermit.com/game-invite/<Net.userId>/<slug>

al portapapeles. El panel web maneja todo lo que el destinatario necesita (iniciar sesión, la solicitud de amistad, un apodo, iniciar el juego) y luego envía la invitación a jugar de nuevo al que comparte, por lo que llega a esta misma lista de invitaciones. Ver Compartir enlaces por el contrato completo.

do. la regla

Las sesiones se crean mediante emparejamiento, invitación-aceptación, sessions/ai, o iniciar una sala en tiempo real con un servidor de fondo. Para un vestíbulo con asientos, utilice el API de salas en tiempo real.

6. Jugar sobre el juego WebSocket

El bucle de juego es el mismo para todos los juegos con guión: recuperar la sesión, abrir el socket, renderizar transmisiones, enviar comandos. En la implementación de referencia esto vive en game.js, GameController.

Obtener la sesión:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/{sessionId}

{
  "sessionId": "<guid>",
  "status": "active",
  "players": [ /* ... */ ],
  "createdAt": "…",
  "finishedAt": null,
  "chatConversationId": "<guid>",
  "result": null
}

Nota chatConversationId — lo necesitarás para chatear (§7) y voz (§8).

Conecte la toma de juego:

ws(s)://<host>/ws/v1/games?sessionId=<id>&access_token=<token>

En open, el cliente envía inmediatamente un comando de sincronización:

{ "type": "cmd", "data": { "type": "sync" } }

En cualquier desconexión, se vuelve a conectar con un retroceso exponencial desde 1 segundo hasta un límite máximo de 30 segundos, y reenvía la sincronización en cada apertura. El comando sync hace que la reconexión sea sin estado y idempotente: todo lo que el cliente perdió, el servidor lo retransmite.

El sobre. Cada cuadro es un sobre JSON delgado:

  • Cliente → servidor: {"type":"cmd","data":<command>}
  • Servidor → cliente: {"type":"game","data":…}, {"type":"error","error":…}, {"type":"presence","userId","online"}

Los comandos del juego están definidos por tu propio script de reglas. Las órdenes del ejemplo del ajedrez, por ejemplo (la data carga útil de un cmd marco):

{ "type": "sync" }
{ "type": "move", "from": "e2", "to": "e4", "promo": "q" }
{ "type": "resign" }
{ "type": "offer-draw" }
{ "type": "accept-draw" }
{ "type": "decline-draw" }

En el ejemplo del ajedrez, promo sólo está presente en movimientos de promoción.

Las transmisiones también están definidas por script. Las transmisiones del ejemplo de ajedrez (las data carga útil de un game marco):

  • state - la instantánea completa:
{
  "type": "state",
  "white": "<userId>",
  "black": "<userId>",
  "ratings": { "white": 1420, "black": 1388 },
  "board": "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr",
  "turn": "w",
  "moves": [ { "from": "e2", "to": "e4", "promo": null, "san": "e4", "at": "…" } ],
  "status": "active",
  "result": null,
  "deadline": 1784642591000,
  "drawOfferBy": null,
  "ai": false,
  "aiName": null
}

El board es una cadena de 64 caracteres, index = rank * 8 + file con a1 = 0, usando PNBRQK para blanco, pnbrqk para negro, . para casillas vacías: una codificación específica del ajedrez; Tu juego define su propia forma de estado.

  • moved – se aplicó un solo movimiento.
  • draw-offered / draw-declined.
  • game-over — { "result": { "kind", "reason", "at" }, "view" }, dónde reason los valores están definidos por script; el ejemplo de ajedrez usa checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

La identidad nunca se quita de las cargas útiles. El cliente envía comandos sin identificación de usuario y el script nunca confía en uno del cable: la plataforma pasa el remitente autenticado al script. No hay nada que falsificar.

Ver game-scripts.md por el contrato de guión detrás de todo esto.

7. Chat en el juego

Cada sesión lleva un chatConversationId (§6) que los clientes del juego pueden usar para el chat dentro del juego. En la implementación de referencia, initChat en game.js lo usa así:

GET  /api/v1/chat/conversations/{id}/messages?page=1&pageSize=50
POST /api/v1/chat/conversations/{id}/messages
     { "content": "good luck!" }

El socket de chat en tiempo real ws/v1/chat es bloqueado para tokens relacionados con el juego. El cliente de referencia lo intenta una vez, es rechazado y vuelve a sondear el punto final REST cada 5 segundos; planifique sondear desde el principio en su propio juego.

El chat funciona aunque los dos jugadores no sean amigos: la conversación de sesión (escriba "game") se crea con ambos jugadores como participantes, por lo que las reglas habituales de permisos de chat ya se cumplen.

Referencia: chat.md.

8. Voz

La voz es opcional y los clientes del juego normalmente la conservan. desactivado por defecto. La implementación de referencia lo maneja en game.js, VoiceController. Cuando un jugador lo habilita:

  1. Busque o cree la sala vinculada a la conversación de la sesión:
GET  /api/v1/voice/rooms?conversationId=<chatConversationId>
POST /api/v1/voice/rooms
     { "conversationId": "<chatConversationId>" }
  1. Únase a él:
POST /api/v1/voice/rooms/{roomId}/join
  1. Conecte la toma de voz:
ws(s)://<host>/ws/v1/voice?roomId=<id>&access_token=<token>

Los medios son WebRTC peer-to-peer con negociación perfecta; la toma sólo lleva señalización y control:

  • Señalización: {"type":"rtc","to":<userId>,"payload":{"sdp":…}} o {"type":"rtc","to":<userId>,"payload":{"ice":…}}
  • Control: {"type":"mute","muted":…}, {"type":"speaking","speaking":…}
  • Eventos del servidor: voice.roster, voice.participant_joined, voice.participant_left, voice.mute_changed, voice.speaking, voice.rtc

Si P2P falla, el recurso alternativo son los fotogramas binarios opus transmitidos por el servidor: una identificación del remitente de 16 bytes seguida de la carga útil de audio.

La voz es deshabilitado en juegos de IA — el cliente de referencia comprueba view.ai de la transmisión estatal y nunca ofrece el interruptor.

Referencia: voice.md.

9. Calificaciones y clasificación

Los clientes del juego nunca envían una puntuación. Cuando termina un juego, el guion regresa eloUpdates y el plataforma los publica en la tabla de clasificación del juego. Los clientes nunca pueden escribir entradas en la tabla de clasificación directamente; el servidor también debe validar la jugabilidad detrás de sus actualizaciones de calificación.

Por lo tanto, el lado del cliente es trivial: lea las entradas (§4) y renderícelas, como lo hace la implementación de referencia. Ver leaderboards.md.

10. Repeticiones

Un juego que declara replays: true en su script tiene guardadas todas las sesiones finalizadas por la plataforma; los clientes simplemente lo buscan y lo renderizan. Controlar replaysEnabled en GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94 antes de ofrecer la pantalla: un operador puede responder por un juego de cualquier manera, y los puntos finales a continuación regresan 404 cuando las repeticiones están apagadas. En la implementación de referencia, la búsqueda es App.loadReplays / App.openReplay en app.js:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/mine?limit=10
GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/{sessionId}

Una carga útil de repetición (que se muestra con la forma del resultado del ejemplo de ajedrez):

{
  "sessionId": "<guid>",
  "players": [ /* ... */ ],
  "finishedAt": "…",
  "result": {
    "kind": "win",
    "reason": "checkmate",
    "at": "…",
    "white": "<userId>",
    "black": "<userId>",
    "moveCount": 41,
    "eloBefore": { "white": 1420, "black": 1388 },
    "eloAfter": { "white": 1436, "black": 1372 }
  },
  "state": { "game": { "moves": [ /* ... */ ] } }
}

El espectador camina state.game.moves a través del compartido chessRules motor localmente - lo mismo server.js archivo de reglas, que se ejecuta en el navegador, por lo que las repeticiones no necesitan viajes de ida y vuelta al servidor; conservar la versión de las reglas utilizada para una partida archivada cuando las reglas cambian. Esta es la segunda recompensa del diseño de una fila y dos roles del §1, un patrón que cualquier juego puede adoptar con su propio archivo de reglas.

11. Perfiles de jugadores

Los clientes del juego resuelven a otros jugadores a través de puntos finales de perfil público. En la implementación de referencia, App.profileFor en app.js:

GET /api/v1/users/{id}/profile  → { "id": "…", "username": "…", "nickname": "…" }
GET /api/v1/users/{id}/avatar   → image/png, or 404

Dos reglas de UI que sigue el cliente de referencia:

  • Prestar apodos, nunca nombres de usuario.
  • retroceder a "Player " + id.slice(0, 8) cuando falta un perfil o un apodo está vacío.

Referencia: profile.md.

12. Oponentes de práctica de IA

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai (que se muestra con el ejemplo) crea una sesión en la que la plataforma marca un asiento ai: true en createSession. El guión en sí desempeña ese papel: el comportamiento de la IA es algo que define su propio guión. En el ejemplo del ajedrez, el asiento lo juega "hala", un codicioso motor de captura de material que responde dentro de la misma invocación que procesa el movimiento del ser humano.

El guión del juego decide si la práctica cambia la calificación del jugador humano. El asiento de IA no puede recibir escrituras de estado de jugador, calificación o logros de la cuenta. Mantenga las estadísticas de IA en estado de sesión.

13. Lo que NO usa el juego de referencia

La implementación de referencia de ajedrez no toca ninguno de estos, pero todos están disponibles para juegos que los necesitan:

  • Logros - cualquier juego con un server= script puede declararlos (game.achievements) y otorgarles autoridad de servidor desde cualquier enlace de ciclo de vida; el ajedrez simplemente no lo hace. Los títulos del catálogo tienen una ruta separada reclamada por el cliente: achievements.md, game-scripts.md.
  • Catálogo / derechos — para juegos distribuidos y vendidos a través del catálogo: catalog.md.
  • Relé — el canal de retransmisión de alta frecuencia para juegos de ritmo rápido en tiempo real donde el recorrido de ida y vuelta del script por comando es demasiado lento: relay.md.
  • Bibliotecas externas — vincular bibliotecas de juegos Steam, Epic o GOG: external-libraries.md.

El ejemplo del ajedrez, un juego de mesa por turnos, no necesita ninguno de ellos. Si su juego es en tiempo real, se distribuye por catálogo o necesita cargas útiles binarias, esas páginas son el lugar donde debe buscar a continuación.

14. Lista de verificación de integración

  • [ ] Agregar un starhermit.txt manifiesto (name, launch, owner, server; opcional cover= para el mosaico de la biblioteca).
  • [ ] Leer #game_token del hash de URL una vez, luego quítelo con history.replaceState.
  • [] Decodifica el JWT para sub (identificación de usuario) y game_scope (babosa): nunca codifique su babosa.
  • [] Cree todas las rutas de API como URL relativas del mismo origen: /api/v1/games/<slug> + sufijo.
  • [] Actualiza el token de lanzamiento cada 45 minutos a través de POST …/launch-token.
  • [ ] Utilice el cmd / sync Patrón WebSocket: envolver todo, sincronizar en cada apertura, volver a conectar con un retroceso de 1s→30s.
  • [] Diseña los comandos y transmisiones de tu script como el contrato del cliente — el cliente realiza transmisiones y envía comandos, nada más.
  • [] Devolver un objeto de resumen { turnPlayerId, deadline, status, moveCount } para que la lista de sesiones pueda mostrar de quién es el turno.
  • [] Termina los juegos devolviendo un result — ese valor de retorno es lo que impulsa tanto las repeticiones como el elo.
  • [ ] Declarar replays: true en su secuencia de comandos si desea que se mantengan las sesiones terminadas y bifurque la interfaz de usuario de reproducción en replaysEnabled.

La plataforma proporciona autenticación, sesiones, emparejamiento y almacenamiento; su guión proporciona la reglas del juego. Empezar con el inicio rápido del navegador para una primera carga completa.
