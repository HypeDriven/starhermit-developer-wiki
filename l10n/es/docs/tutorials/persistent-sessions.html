Tutorial: sesiones persistentes: juegos que se detienen cuando todos se van

Normalmente la plataforma finaliza un partido en el que nadie está jugando: una vez que todos los jugadores se han desconectado y nadie ha regresado en cinco minutos, la sesión termina como abandoned con razón players_left (ver API de juegos: WebSocket de juego). Eso es correcto para un ajedrez. juego o una carrera, y mal para una granja, un constructor de ciudades, una mazmorra compartida o cualquier mundo en el que un grupo de Los jugadores regresan a más de días.

Un juego puede pedir sesiones persistentes en cambio. Una sesión persistente se detiene cuando sus jugadores se desconectan:

  1. El último jugador se marcha.
  2. Después de unos 15 segundos sin que nadie estuviera conectado, la plataforma pausas la sesión. No se ejecuta nada: un juego de guión no recibe onTick llamadas, y la sesión de un juego contenedor se elimina del contenedor.
  3. La sesión permanece pausada dentro de su política de retención de recuperación. Leer /sessions/{id}/recovery por cualquier vencimiento en lugar de asumir que se conservará para siempre.
  4. El primer jugador en conectarse. ws/v1/games currículums antes de que su primera orden sea manejado. El juego continúa desde donde se detuvo.

Esta página muestra cómo activarlo, cómo evitar que los relojes del juego salten durante una pausa y lo que su cliente necesita hacer.

1. Optar por

La persistencia es una declaración por juego, léala cuando su juego se publique o actualice; publique una actualizar después de cambiarlo. debe ser literal true o false; cualquier otra cosa cuenta como no declaración, y un juego que no declara nada se comporta como antes.

juego de guion - una estática persistent en el game objeto (ver Guiones de juego):

globalThis.game = {
  persistent: true,
  tickRateHz: 1,
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

Juego de contenedores — persistent en tu GET /describe respuesta (ver Servidores de juegos en contenedores):

{ "protocol": 1, "tickRateHz": 20, "maxSessions": 48, "persistent": true }

Nada cambia sobre cómo se crean las sesiones: emparejamiento, invitaciones, el punto final de IA y tiempo real. Todas las salas producen sesiones persistentes para un juego persistente.

2. Mantén el tiempo del juego quieto mientras esté en pausa

La plataforma no reescribe. ctx.now — sigue siendo el reloj de pared real, por lo que cualquier hora absoluta que desees mostrar a los jugadores (una fecha límite, una "cosecha lista en") sigue significando lo que dice. En cambio, persistente Las sesiones obtienen un campo de contexto adicional:

ctx.pausedMs   // total milliseconds this session has spent paused, so far

Sólo crece, y sólo en sesiones persistentes (otros juegos nunca salen al campo). restalo y tu tener un reloj de juego que se detiene mientras no hay nadie:

function gameTime(ctx) {
  return ctx.now - (ctx.pausedMs || 0);
}

globalThis.game = {
  persistent: true,
  tickRateHz: 1,

  createSession(ctx) {
    return { ok: true, sessionState: { lastTick: gameTime(ctx), crops: [] } };
  },

  onTick(ctx) {
    var state = ctx.sessionState;
    var t = gameTime(ctx);
    var dt = t - state.lastTick;      // never includes the time the world was paused
    state.crops.forEach(function (crop) { crop.growth += dt; });
    state.lastTick = t;
    return { ok: true, sessionState: state };
  },

  onPlayerMessage(ctx) { /* ... */ }
};

Almacene sus propias marcas de tiempo en el tiempo del juego (gameTime(ctx)), no en ctx.nowy compararlos sólo contra el tiempo de juego. Si usted desear el mundo siga adelante sin que nadie esté mirando: cultivos que crecen durante la noche - usar ctx.now en su lugar, póngase al día con el primer tic después de un currículum. De cualquier manera es tuyo elección; la plataforma solo informa lo sucedido.

Dos detalles del momento:

  • Durante los ~15 segundos entre la salida del último jugador y la pausa, la sesión aún continúa. marcó normalmente. Un jugador cuya conexión se cae y vuelve inmediatamente no provoca una pausa.
  • Después de un currículum, el siguiente onTick viene un intervalo de tic después. El tiempo pausado no se reproduce. como una acumulación de tics omitidos.

Un contenedor recibe pausedMs en el mismo lugar: en el POST /sessions cuerpo se envía cuando la sesión se restablece después de una pausa.

3. Tu cliente

Una sesión pausada sigue siendo una sesión activa, por lo que el flujo de clientes es el que ya tienes:

  • Listar mundos para volver a unirse con GET /api/v1/games/{slug}/sessions/mine. Cada entrada tiene un pausedAt marca de tiempo mientras está en pausa y null mientras alguien está en él, para que puedas mostrar "pausado desde…" o "2 amigos jugando ahora" (ver API de juegos: sesiones).
  • Reunirse con abriendo ws/v1/games?sessionId=… exactamente como antes. El currículum ocurre durante el conectar. no hay nada especial "reanudado" marco para ello: el juego simplemente se está ejecutando cuando tu primer llega el comando, así que solicita o espera el mensaje normal de estado completo de tu juego, como lo harías en cualquier reconexión.
  • Manejar un currículum fallido. Si la plataforma no puede reanudar la sesión, lo más probable es que sea un contenedor. juego cuyo servidor aún se está iniciando: recibirás {"type":"error","error":"…"} y el enchufe se cierra con código 1001. La sesión permanece pausada y no se pierde nada. Vuelva a conectarse después de un breve retroceder (unos segundos, creciendo) y mostrar "empezando el mundo..." en lugar de un error.
  • presence Los marcos funcionan como de costumbre, por lo que los otros jugadores ven quién está en el mundo en este momento.

4. Finalizar una sesión persistente

Una sesión persistente finaliza cuando:

  • tu juego reporta un result (valor de retorno del script o mensaje de control del contenedor), o
  • el propietario del juego lo finaliza (DELETE /api/v1/me/github-games/{id}/sessions/{sessionId}),
  • el último miembro deja explícitamente un mundo sin habitación a través de /sessions/{id}/leave, o
  • sus datos de recuperación pausados ​​caducan según la política de retención de la implementación.

La desconexión deja la membresía intacta; Al salir explícitamente se renuncia a la membresía. Ver Ciclo de vida y recuperación de la sesión. para ambos flujos.

Pedir un nuevo juego no no retire las pausadas del reproductor y las sesiones pausadas seguirán contando contra el límite de sesiones simultáneas por jugador (20 por defecto). Dar a los jugadores una manera de terminar o dejar un mundo - un "abandonar el mundo" ordena las respuestas de tu guión con un result, Por ejemplo. De lo contrario, un jugador que haya llenado su límite no podrá empezar nada nuevo.

onPlayerMessage(ctx) {
  var msg = ctx.message.data;
  if (msg.type === "close-world" && ctx.message.from === ctx.sessionState.ownerId) {
    return { ok: true, sessionState: ctx.sessionState, result: { kind: "closed" } };
  }
  /* ... */
}

5. Juegos de contenedores: aparcamiento

Para un juego de contenedores, una pausa es una parque:

  1. La plataforma solicita una instantánea final (GET /sessions/{id}/snapshot) y lo almacena de forma duradera.
  2. Derriba la sesión (DELETE /sessions/{id}). Su contenedor deja de simularlo, y si Si no tiene otras sesiones, la implementación se puede detener después de su período de inactividad.
  3. En la siguiente unión, recrea la sesión con POST /sessions, llevando lo almacenado snapshot y el actualizado pausedMs - la misma solicitud que una restauración por fallo: reactivar una implementación detenida primero si es necesario.

Así que la instantánea que devuelvas debe ser suficiente para reconstruir el mundo entero, no sólo para retomar algunas segundos de juego. Si esa instantánea final falla, la sesión se estaciona desde su último período periódico. puesto de control. A diferencia de un accidente, un estacionamiento y restauración no se cuenta en su presupuesto de reinicio, y los jugadores no obtienen resumed cuadro: nadie estaba allí para ver el estado retroceder.
