Publicar un servidor de juego dedicado y jugadores integrados en el juego

Este tutorial muestra cómo:

  1. Publique o actualice un contenedor de servidor de juegos dedicado con la API de carga de paquetes de StarHermit.
  2. Mantenga renovado el token del servidor StarHermit de un contenedor de larga duración.
  3. Incorpora jugadores de Steam, Epic, GOG o una versión independiente sin enviarlos a través de un Proveedor de OAuth o solicitarles que visiten el panel de StarHermit.
  4. Dale a esos jugadores acceso a sesiones de StarHermit, emparejamiento, tablas de clasificación, logros, chat de sesión, voz, amigos, presencia y repeticiones.

La API orientada al jugador es la misma ya sea que el ejecutable provenga de Steam, Epic, GOG o el tuyo propio. lanzador, o https://<slug>.starhermit.com.

Límite importante: incrustado no es silencioso

StarHermit actualmente no expone un privilegio "crear jugador arbitrario" punto final de un juego servidor. un contenedor STARHERMIT_SERVER_TOKEN deliberadamente no tiene identidad de jugador y no puede acuñar cuentas de jugadores o hacerse pasar por jugadores.

El registro de clave pública también requiere un correo electrónico válido y un enlace de verificación único. Por lo tanto:

  • Tú poder mantenga el registro dentro de la interfaz de usuario de su juego y evite Google/GitHub OAuth y el Panel de control de StarHermit.
  • Tú no puedo cree silenciosamente una cuenta StarHermit solo desde una ID de Steam, ID de cuenta de Epic o GOG Identificación. El jugador debe dar su consentimiento, proporcionar un correo electrónico y confirmarlo una vez.
  • Genera y almacena la clave privada de cada jugador en su dispositivo. No generes la clave de cada jugador. en su servidor dedicado, cargue claves privadas o mantenga una base de datos de claves de custodia a menos que esté asumiendo intencionalmente la responsabilidad de todas esas cuentas.

Para un juego nativo, la experiencia admitida más fluida es: un panel de cuenta en el juego genera el clave, solicita correo electrónico y consentimiento, espera mientras el jugador confirma el enlace en su bandeja de entrada y luego inicia sesión con la clave y mantiene el token de actualización en la bóveda de credenciales del sistema operativo. El jugador nunca necesita navegue por el sitio de StarHermit. Un jugador que no puede proporcionar y verificar un correo electrónico no puede completar este flujo con la API actual.

Arquitectura y límites de confianza

Steam/Epic/GOG/native client
  ├─ owns the player's private key
  ├─ performs public-key registration/login
  ├─ holds player access + rotating refresh token
  ├─ optionally links the external platform identity
  └─ uses a game-scoped launch token for game/social APIs
                  │
                  │ REST + ws/v1/games
                  ▼
StarHermit API ───────── authenticated command ────────► your container
  ├─ creates sessions and matchmaking                     ├─ owns simulation
  ├─ stamps the trusted StarHermit user id                 ├─ never trusts payload identity
  ├─ persists snapshots/results/elo/achievements           └─ uses narrow server token only
  └─ supplies session chat, voice, friends, and replays

El cliente del juego demuestra quién es el jugador. StarHermit estampa esa identidad en el tráfico enviado al contenedor. El contenedor nunca acepta una ID de Steam o una ID de usuario proporcionada dentro del JSON del juego como prueba. de identidad.

Requisitos previos

Necesitas:

  • Una cuenta de desarrollador de StarHermit y un token de acceso completo.
  • Un juego registrado de tu propiedad, con un gameSlug y backend autorizado. El punto final del paquete actualiza un juego existente; no crea un registro de juego ni reserva un slug.
  • Alojamiento de contenedores habilitado para su cuenta.
  • Docker u otra herramienta capaz de producir un archivo compatible con Docker. docker save archivo.
  • Un contenedor que implementa protocolo de juego v1.

Para el registro de autoservicio inicial, utilice un repositorio de GitHub verificado con starhermit.txt y un válido container.image declaración como se describe en Juegos de GitHub. Una vez que el El juego existe, los paquetes push pueden publicar compilaciones posteriores de clientes y servidores directamente.

Parte 1: implementar el contrato de contenedor

Su proceso debe escuchar PORT e implementar:

Punto final Responsabilidad
GET /health Devolver 200 Sólo cuando se pueden aceptar sesiones.
GET /describe Declarar protocolo 1, tasa/capacidad de ticks solicitada y logros
POST /sessions Crear una sesión o restaurar una desde snapshot
GET /sessions/{id}/snapshot Devolver un punto de restauración duradero completo
DELETE /sessions/{id} Liberar la sesión
WS /stream Reciba comandos de jugadores autenticados y emita cargas útiles del juego
WS /control Instantáneas push, logros, Elo, resultados y contrapresión

Validar X-Starhermit-Invoke-Key en cada solicitud HTTP y actualización de WebSocket contra STARHERMIT_INVOKE_KEY. Esto autentica a StarHermit en su proceso.

Una declaración mínima es:

{
  "protocol": 1,
  "tickRateHz": 20,
  "maxSessions": 48,
  "replays": true,
  "achievements": [
    {
      "key": "first-win",
      "name": "First Win",
      "description": "Win a match.",
      "points": 10
    }
  ]
}

replays pide a la plataforma que mantenga el último estado de cada sesión terminada, que es lo que GET /api/v1/games/{slug}/replays/{sessionId} sirve. Declaralo sólo si tu juego quiere repeticiones; sin él, no se conserva nada una vez finalizado el partido. Ver Servidores de juegos en contenedores: GET /describe.

Los marcos de transmisión del juego utilizan:

[1 byte type][16 byte sessionId][16 byte userId][payload...]

Tipo 1 es un comando entrante; su ID de usuario fue sellado por el jugador autenticado de StarHermit. Tipo 2 es una carga útil JSON saliente dirigida a ese jugador, o a todos cuando el ID de usuario es todos ceros.

Los efectos duraderos pasan /control:

{ "type": "snapshot", "sessionId": "...", "state": { "round": 4 } }
{ "type": "achievements", "sessionId": "...", "unlocks": { "<userId>": ["first-win"] } }
{ "type": "elo", "sessionId": "...", "updates": { "<userId>": 1248 } }
{ "type": "result", "sessionId": "...", "result": { "kind": "win", "winner": "<userId>" } }

StarHermit filtra estas actualizaciones según los participantes de la sesión y las claves de logros declaradas. un resultado es terminales. Ver Servidores de juegos alojados en contenedores para el protocolo completo, contrato de instantánea, aislamiento y recuperación.

Parte 2: registra el juego una vez

Coloque un manifiesto en el repositorio verificado utilizado para el registro inicial:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # your user ID from GET /api/v1/me, not username

container.image=ghcr.io/your-github-login/orbit-server@sha256:<64-lowercase-hex>
container.port=8080
container.health=/health
container.memory_mb=1024
container.cpu=1.0

Colocar owner a lo inmutable id devuelto por GET /api/v1/me. No utilice el nombre de usuario de la cuenta o apodo; esos son valores de visualización y pueden cambiar.

Regístrelo:

API=https://api.starhermit.com
ACCESS_TOKEN='developer-access-token'

curl -sS -X POST "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "repoUrl":"https://github.com/your-github-login/orbit-league"
  }'

guardar lo devuelto id como GAME_ID y gameSlug como GAME_SLUG, luego confirme que el backend existe: GET $API/api/v1/games/$GAME_SLUG respuestas 200 una vez que lo haga. un regalo gameSlug solo no pruébalo: cada juego verificado tiene uno, incluido solo para navegador. Un registro que declara una contenedor sin demostrar que es propietario del repositorio se rechaza con 403y registro inicial También puede fallar cuando el alojamiento de contenedores no está disponible o está restringido.

La imagen respaldada por el registro en el manifiesto es suficiente para implementar la primera versión. La siguiente sección cubre la ruta de carga directa, útil para CI y para compilaciones que no desea plataforma para clonar o extraer nuevamente.

Parte 3: publicar un paquete de cliente y servidor dedicado

construir el archivo

La carga es un archivo tar comprimido con gzip con este diseño:

client/            optional static web client, including the registered launch file
server/image.tar   optional `docker save` output
starhermit.txt     the manifest

Al menos client/ o server/image.tar debe estar presente.

Si publica a través del panel web de StarHermit o del cliente de Windows en lugar de curl, no construya este archivo a mano. Elija ya sea un carpeta de distribución del servidor (tenencia starhermit.txt y image.tar) o el image.tar por sí solo, y el cliente empaqueta el diseño anterior. El starhermit.txt valores: nombre para mostrar y el container.* perillas - son campos en el cuadro de diálogo, precompletados desde el manifiesto de la carpeta cuando hay uno, por lo que un simple image.tar publica igual de bien.

rm -rf bundle game-bundle.tar.gz
mkdir -p bundle/client bundle/server

# Optional hosted web client.
cp -R dist/. bundle/client/

# Dedicated server image.
docker build -t orbit-server:release -f Dockerfile.server .
docker save orbit-server:release -o bundle/server/image.tar

# Keeps the artifact self-describing, and is what the dashboard/desktop clients require.
cp starhermit.txt bundle/starhermit.txt

tar -C bundle -czf game-bundle.tar.gz .

La imagen debe funcionar con un sistema de archivos raíz de solo lectura, usuario no raíz forzado, sin capacidades, sin volúmenes, sin internet y solo un pequeño espacio grabable /tmp. Dependencias del proveedor en la imagen.

Subirlo

POST /api/v1/me/github-games/{id}/bundle toma el archivo como el cuerpo de la solicitud sin formato, no como un forma multiparte:

curl -sS -X POST "$API/api/v1/me/github-games/$GAME_ID/bundle" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game-bundle.tar.gz

Un paquete de más de 100 MB no pasará por esta ruta. El CDN frente a la API rechaza un cuerpo de solicitud grande con un 413 propio, uno que la plataforma nunca ve, por lo que lleva no limitBytes y no aparece en ningún registro que puedas leer. A docker save de una imagen de servidor real alcanza ese tamaño fácilmente. Si ves un 413 sin limitBytes, eso es esto y no el de tu juego asignación, que es de gigabytes.

Envía el archivo idéntico ws/v1/game-upload en su lugar, fotogramas después de un La actualización de WebSocket no es un cuerpo de solicitud, por lo que no se aplica el límite. Mismo diseño de archivo, mismo asignación, mismas respuestas JSON; la única adición es que debes enviar {"type":"complete"} cuando el último byte está fuera, porque no se publica nada hasta que lo hagas.

Respuesta de ejemplo:

{
  "clientPublished": true,
  "serverImageLoaded": true,
  "imageDigest": "sha256:4e7d...",
  "bytesReceived": 318767104
}

La plataforma:

  • se intercambia atómicamente client/, para que los usuarios no vean una compilación parcialmente cargada;
  • cargas server/image.tar, calcula su resumen inmutable y vuelve a fijar la implementación;
  • pone en cola el contenedor antiguo para ser reemplazado por la imagen cargada;
  • restaura sesiones activas elegibles a partir de sus instantáneas persistentes.

Puede cargar solo la imagen del cliente o solo la imagen del servidor. Uso de parches solo para el cliente ?mode=merge en el mismo punto final (ver actualizaciones parciales); una imagen en una fusión todavía está cargado entero. La asignación de discos de un juego es 2GB en starhermit.com (ajustable por el operador) y puede estar sintonizado por juego; porque un push reemplaza el contenido de un juego en lugar de agregarlo, eso es a la vez el empujón más grande y la mayor cantidad de disco que puede ocupar el juego. 413 incluye limitBytes; un inválido devoluciones de archivos o imágenes 422; y 507 significa que el servidor no tiene espacio en este momento; está marcado antes de que se lea su cuerpo, por lo que una carga condenada al fracaso se rechaza en lugar de aterrizar a medias. No pongas enlaces simbólicos, enlaces duros, recorrido de ruta o archivos fuera del diseño documentado en el archivo.

Una carga exitosa no significa que el nuevo proceso haya pasado los controles de estado todavía. Encuesta los existentes GET /api/v1/me/github-games/{id}/deployment ver y probar una sesión real antes de promocionar el construir. Fijar una confirmación del repositorio más tarde cambia explícitamente la implementación al contenido del repositorio.

Cambiar un juego existente de server= a un contenedor

Compatible y mantiene el juego: la misma identificación, slug, <uid>.starhermit.com dirección, jugadores, tablas de clasificación y logros. No hay un paso de registro separado.

  1. Reemplazar server=... con tu container.* bosquejar starhermit.txt. Los dos son mutuamente exclusivo; se rechaza un manifiesto declarando ambos.
  2. Empuje un paquete que lleva client/ (con ese manifiesto) y server/image.tar, encima ws/v1/game-upload si es grande.
  3. La imagen que subes es la que corre. A container.image= línea en el mismo manifiesto es Está bien conservarlo, pero el resumen subido lo supera.
  4. Encuesta GET /api/v1/me/github-games/{id}/deployment hasta que lee running, luego comienza una verdadera habitación o partido.

Parte 4: renovar el token de plataforma del contenedor

Al inicio, el contenedor recibe:

STARHERMIT_API_BASE
STARHERMIT_GAME_SLUG
STARHERMIT_SERVER_TOKEN
STARHERMIT_SERVER_TOKEN_EXPIRES_IN
STARHERMIT_REFRESH_KEY
STARHERMIT_INVOKE_KEY

STARHERMIT_SERVER_TOKEN es estrecho: representa el servidor del juego, no un jugador. Caduca después 24 horas por defecto. Programar la renovación aproximadamente a la mitad del STARHERMIT_SERVER_TOKEN_EXPIRES_IN:

POST {STARHERMIT_API_BASE}/api/v1/games/{STARHERMIT_GAME_SLUG}/server/token
X-Starhermit-Refresh-Key: {STARHERMIT_REFRESH_KEY}

{ "token": "eyJhbGciOi...", "expiresInSeconds": 86400 }

No se requiere ningún token de portador para este punto final. Eso permite la recuperación incluso si el token antiguo tiene ya caducado. Reemplace el token en memoria de forma atómica y programe la próxima renovación desde el nuevo expiresInSeconds.

Mantenga separados los dos secretos de implementación:

  • STARHERMIT_INVOKE_KEY autentica las solicitudes de StarHermit en su contenedor.
  • STARHERMIT_REFRESH_KEY autentica su contenedor al renovar su token StarHermit.

Ambos rotan en cada reinicio del contenedor. Nunca los registres, devuélvelos en /describe, ponlos en un instantánea o enviarla a un jugador.

Parte 5: incorporar un reproductor que no sea StarHermit y sin OAuth

Ejecute este flujo en el juego o iniciador nativo, no en el contenedor dedicado. El tutorial completo, con código de cliente probado, es Tutorial: jugadores incorporados con clave pública; en breve:

  1. Generar una clave por instalación en el primer lanzamiento (se recomienda Ed25519) y mantenga la clave privada en el almacén de credenciales del sistema operativo. Nunca lo cargues y nunca generes claves de jugadores en tu servidor.
  2. Solicitar consentimiento y una dirección de correo electrónico, entonces POST /api/v1/auth/public-key/register con { email, keyType, keyData } desde el dispositivo del jugador. Está limitado a un registro por dirección y por IP cada 24 horas (429 con Retry-After), así que nunca lo hagas proxy a través de tu servidor: cada jugador compartiría su IP.
  3. Espere a que el jugador confirme. El enlace enviado por correo electrónico abre una página que no cambia nada hasta que el jugador presiona Confirmar, lo que crea la cuenta y adjunta la clave; en starhermit.com luego aterrizan en el panel de StarHermit, por lo que su juego no recibe esos tokens. en lugar de eso inicia sesión con la clave hasta que tenga éxito: challenge, firma StarHermit's bytes de desafío exactos, complete. hasta el El jugador confirma complete respuestas 401 "Public key not registered or revoked.".
  4. mantener la sesión con POST /api/v1/auth/refreshe inicie sesión con la clave nuevamente cuando la actualización falla. Aceptar los términos actuales cuando GET /api/v1/me informes termsAcceptanceRequired (tanto las sesiones de cuenta como los tokens de inicio de jugador pueden; consulte aceptación de términos). El token de implementación de su contenedor es exento de términos; esa exención no se extiende a sus jugadores.

Más dispositivos. Cada instalación registra su propia clave con la misma dirección de correo electrónico del jugador, y la clave se une a la cuenta existente. POST /api/v1/me/public-keys no es una opción para estos jugadores: requiere una sesión que haya iniciado sesión a través de un proveedor de OAuth.

5. Agregue un nombre de cara al jugador y una identidad externa.

La cuenta generada comienza con un pk-... nombre de usuario. Deja que el jugador elija un apodo:

PATCH /api/v1/me
Authorization: Bearer <access-token>
Content-Type: application/json

{ "nickname": "RookPilot" }

Puede asociar la cuenta con la plataforma en la que se ejecuta el ejecutable:

POST /api/v1/me/identities
Authorization: Bearer <access-token>
Content-Type: application/json

{
  "provider": "epic",
  "providerUserId": "epic-account-id",
  "metadata": "{\"displayName\":\"RookPilot\"}"
}

Utilice un no reservado nombre del proveedor (epic, gog, o su propia identificación de tienda). Hacer no usar steam, google, github, o cualquier otro nombre que la plataforma trate como proveedor de OAuth: aquellos son rechazados incluso si ese proveedor no está configurado. Obtener el ID externo de esa plataforma SDK/sesión autenticada, no desde la entrada editable del reproductor. Este punto final asocia una identidad con la cuenta StarHermit; no es en sí mismo una prueba de propiedad del escaparate y no debe reemplazar Verificación de tickets propia de la plataforma para compras o baneos.

La API de biblioteca externa independiente es opcional y actualmente utiliza sincronización de demostración mientras el proveedor las integraciones están finalizadas; no es necesario para jugar en servidor dedicado.

Parte 6: ingresa al juego y usa los servicios de StarHermit

Reemplazar {slug} en los ejemplos HTTP siguientes con GAME_SLUG, el UUID del juego que obtuviste en registro. El nombre del repositorio orbit-league es un nombre para mostrar/fuente, no el slug API.

Acuña una ficha de juego con privilegios mínimos

Usa el token de acceso completo una vez para acuñar un token cercado para tu juego:

POST /api/v1/games/{slug}/launch-token
Authorization: Bearer <access-token>

{ "token": "eyJhbGciOi...", "expiresInSeconds": 3600 }

Utilice este token de lanzamiento para el juego y las API sociales de sesión permitidas. Actualízalo antes de que caduque. Mantenga el token de cuenta completo fuera del código del juego siempre que sea posible.

Casamentero

POST /api/v1/games/{slug}/matchmaking
Authorization: Bearer <game-token>

Encuesta GET /api/v1/games/{slug}/matchmaking hasta status es matched, luego conecta:

wss://api.starhermit.com/ws/v1/games?sessionId=<sessionId>&access_token=<game-token>

Los mensajes del cliente siguen siendo JSON:

{ "type": "cmd", "data": { "type": "input", "throttle": 0.8 } }

StarHermit convierte el comando en el flujo del contenedor y sella el StarHermit autenticado identificación de usuario. Su contenedor devuelve cargas útiles autorizadas del juego a través de fotogramas de flujo de tipo 2.

Tablas de clasificación y logros

Cada juego autorizado recibe una tabla de clasificación Elo. Su contenedor envía cambios Elo y declarados El logro se desbloquea /control; los clientes solo leen el estado de la plataforma resultante:

GET /api/v1/games/{slug}/achievements
GET /api/v1/leaderboards/{leaderboardId}/entries

Un cliente Steam/Epic/GOG modificado no puede enviar directamente las puntuaciones de la tabla de clasificación del juego ni reclamar una logro propiedad del juego.

Sesión de chat y voz.

GET /api/v1/games/{slug}/sessions/{sessionId} regresa chatConversationId. Sesión Las conversaciones permiten a los participantes chatear y usar la voz incluso cuando no son amigos.

Flujo de voz típico:

  1. GET /api/v1/voice/rooms?conversationId=<chatConversationId>.
  2. Si es necesario, POST /api/v1/voice/rooms con el ID de la conversación.
  3. POST /api/v1/voice/rooms/{roomId}/join.
  4. Conectar wss://api.starhermit.com/ws/v1/voice?roomId=<roomId>&access_token=<game-token>.

La misma cuenta también habilita amigos, presencia, invitaciones a juegos, repeticiones e identidad de perfil en todos todas las construcciones de escaparates. Mantenga una clave/cuenta de StarHermit por persona en lugar de crear una cuenta nueva para cada partido o cada lanzamiento de tienda.

Lista de verificación de producción

Publicación

  • [] El juego de propiedad existente tiene un valor no nulo gameSlug.
  • [] El contenedor rechaza una clave de invocación incorrecta o faltante.
  • [] La clave de invocación, la clave de actualización y el token del servidor se leen desde el entorno al inicio del proceso, nunca se integran en la imagen ni se almacenan en caché en el disco (los tres rotan en cada inicio del contenedor).
  • [ ] /health no regresa 200 antes de que el estado pueda ser aceptado.
  • [] El paquete usa raw application/gzip, no codificación multiparte.
  • [] La imagen funciona como modo de solo lectura, no raíz, sin conexión y sin volúmenes.
  • [] El estado de implementación y una sesión de emparejamiento real se prueban después de la carga.
  • [] La actualización del token del servidor se ejecuta antes de la mitad de su vida útil e intercambia tokens de forma atómica.
  • [] Ninguno de los secretos de implementación se registra ni persiste en las instantáneas.

Incorporación de jugadores

  • [] El par de claves se genera en el dispositivo del reproductor y la clave privada utiliza un almacenamiento seguro.
  • [] La creación de cuentas se divulga y se consiente.
  • [] La verificación del correo electrónico se completa una vez; 429 Retry-After es respetado.
  • [] Los tokens de registro y de jugador no pasan por el servidor dedicado.
  • [] Los tokens de acceso/actualización se almacenan de forma segura y la rotación de actualización se serializa.
  • [] Las ID externas provienen del estado autenticado del SDK de Steam/Epic/GOG.
  • [] El juego utiliza un token específico del juego después de la configuración inicial de la cuenta.
  • [] Identificadores de cliente achievement, resumed, y abandoned marcos de juego.
