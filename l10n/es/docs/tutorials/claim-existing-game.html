Reclama un juego que alguien más agregó

Si alguien ya agregó su juego público de GitHub a StarHermit, no necesita crear un segundo listado. Reclame el listado existente para convertirse en su propietario verificado y administrar sus metadatos. alojamiento, implementación, servidor backend y transferencias futuras.

La reclamación está protegida por el control del repositorio. No basta con conocer el ID del juego o la URL del repositorio. Debe demostrar control de una de dos maneras:

  1. Vincular la cuenta personal de GitHub propietaria del repositorio; o
  2. Confirme su ID de usuario inmutable de StarHermit como owner= en el repositorio starhermit.txt.

El segundo método es especialmente útil para los repositorios propiedad de la organización, porque la actual La verificación de inicio de sesión de GitHub coincide con los propietarios del repositorio personal y no infiere la membresía de la organización.

¿Qué cambios de reclamo?

Un reclamo exitoso:

  • mantiene el ID del juego/listado existente y su historial acumulado;
  • le cambia el usuario administrador de StarHermit del listado;
  • marca el listado como isVerifiedOwner: true;
  • actualiza metadatos y controles confiables desde starhermit.txt donde se aplica;
  • aprovisiona o actualiza un script/contenedor backend declarado;
  • permite el alojamiento de la plataforma cuando esté disponible y pone en cola la implementación según sea necesario pending;
  • elimina el acceso de administración de la persona que envió originalmente ese listado.

El reclamo no le da al remitente anterior acceso a su cuenta de GitHub y no se fusiona Cuentas de usuario de StarHermit. Transfiere la gestión de ese listado específico.

Antes de comenzar

Necesitas:

  • Una cuenta de StarHermit y un token de acceso completo de usuario, no un token de lanzamiento específico para el juego.
  • Acceso de escritura al repositorio si se utiliza el owner= método de prueba.
  • El ID de listado de StarHermit existente.
  • Para un juego de repositorio clonado, un válido starhermit.txt en la raíz del repositorio.

Solo github.com/<owner>/<repo> Los repositorios y sus sitios de páginas de GitHub participan en este reclamo. fluir. Una URL alojada arbitraria no tiene propiedad del repositorio de GitHub para demostrarlo y no se puede reclamar así. manera.

Ejemplos de uso a continuación:

API=https://api.starhermit.com
ACCESS_TOKEN='your-full-user-access-token'
OWNER='your-github-login'
REPO='your-game-repository'

Los tokens de acceso duran 15 minutos. Actualiza el tuyo antes de comenzar si está a punto de caducar.

Paso 1: busque el listado existente

Lista de juegos compartidos:

curl -sS "$API/api/v1/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Cada artículo incluye el listado inmutable. id, normalizado repoUrl, ownerLogin, repoName, el remitente actual y estado de propiedad:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "isVerifiedOwner": false,
  "submittedByUserId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "submittedByUsername": "someone-else"
}

Coincidencia en ambos ownerLogin y repoName; no seleccione un juego sólo porque su nombre para mostrar es similar. Con jq:

GAME_ID=$(
  curl -sS "$API/api/v1/github-games" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r --arg owner "$OWNER" --arg repo "$REPO" \
    '.[] | select((.ownerLogin | ascii_downcase) == ($owner | ascii_downcase)
               and (.repoName | ascii_downcase) == ($repo | ascii_downcase)) | .id' |
  head -n1
)

printf 'Listing ID: %s\n' "$GAME_ID"

Deténgase si el resultado está vacío. No llame al reclamo con una identificación copiada de un listado no relacionado.

Paso 2: elige cómo demostrar la propiedad

Opción A: vincular la cuenta de GitHub del propietario del repositorio

Úselo cuando el repositorio sea propiedad directa de su inicio de sesión personal de GitHub.

Desde el flujo de configuración/cuenta de StarHermit, inicie GitHub OAuth en enlace modo mientras estás registrado en el Cuenta de StarHermit que debería gestionar el juego. Vincular es diferente a crear accidentalmente un segunda cuenta de StarHermit con inicio de sesión en GitHub.

El flujo de API comienza en:

GET /api/v1/auth/oauth/github/authorize?link=true

Está controlado por el navegador y utiliza una cookie de estado de corta duración. La vinculación requiere StarHermit reciente autenticación. Complete la autorización de GitHub en la misma sesión del navegador que la inició.

Verifique el resultado:

curl -sS "$API/api/v1/me/github" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Esperado:

{ "linked": true, "login": "octocat" }

El inicio de sesión devuelto debe coincidir con el del listado existente. ownerLogin, sin distinguir entre mayúsculas y minúsculas. un personal El inicio de sesión en GitHub no prueba la membresía de una organización propietaria del repositorio. para un repositorio propiedad de la organización, utilice la opción B.

Opción B: agregar owner= a starhermit.txt

Esto demuestra control porque sólo alguien capaz de publicar contenido del repositorio puede agregar valor. Colocar owner a su ID de usuario inmutable de StarHermit (UUID), no su nombre de usuario o apodo.

Obtenga su identificación:

STARHERMIT_USER_ID=$(
  curl -sS "$API/api/v1/me" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r '.id'
)

En la raíz del repositorio, cree o actualice starhermit.txt:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

Reemplace el propietario de ejemplo con STARHERMIT_USER_ID. No pongas aquí tu nombre de usuario o apodo; estos pueden cambiar, mientras que la identificación de usuario es el identificador de propiedad estable.

Para un juego autorizado, conserve exactamente una declaración de backend:

# JavaScript runtime:
server=server.js

# OR container runtime, never both:
# container.image=ghcr.io/your-org/orbit-server@sha256:<64-lowercase-hex>

Confirme y envíe el manifiesto al repositorio/versión que StarHermit puede leer:

git add starhermit.txt
git commit -m "Declare StarHermit game ownership"
git push

Antes de reclamar, abra el archivo raw del repositorio. starhermit.txt URL en un navegador no autenticado y Confirme que el nuevo valor sea legible públicamente. Claiming lee el repositorio en el momento de la solicitud; un El cambio local no impulsado no puede probar nada.

Paso 3: validar el manifiesto

Para un juego de repositorio clonado normal, reclamar requiere:

  • starhermit.txt en la raíz del repositorio;
  • no vacío name=;
  • launch= apuntando a un repositorio relativo .html o .htm archivo;
  • una opción válida server= camino que termina en .js/.mjs, o un válido container.image= declaración;
  • nunca ambos tiempos de ejecución del servidor a la vez.

Una lista de páginas de GitHub mantiene su URL alojada como destino de lanzamiento y no requiere un manifiesto. cuando se demuestra la propiedad personal de GitHub, aunque un nombre de manifiesto válido aún puede actualizar su nombre para mostrar.

Si el juego declara un contenedor, su imagen debe cumplir con el registro, el espacio de nombres del propietario y el resumen. reglas en Servidores de juegos alojados en contenedores. El alojamiento de contenedores también puede ser restringido por el operador de la plataforma.

Paso 4: reclama el listado

La solicitud de reclamación no tiene cuerpo:

curl -sS -X POST \
  "$API/api/v1/me/github-games/$GAME_ID/claim" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Un exitoso 200 devuelve el juego actualizado:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "launchPath": "index.html",
  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "isVerifiedOwner": true,
  "metadataSource": "starhermit.txt",
  "hosting": {
    "hostingEnabled": true,
    "deployStatus": "pending"
  }
}

La identificación debe ser la misma que se encontró en el Paso 1. No cree una lista nueva después de un reclamo exitoso.

Se permite intencionalmente reclamar un listado que ya administras. Vuelve a leer el manifiesto, vuelve a aprovisionar el backend y vuelve a poner en cola el alojamiento, de modo que la misma llamada pueda usarse para resincronizar un Juego administrado por el propietario después de cambios en el repositorio.

Paso 5: verificar la adquisición y la implementación

Confirma que el juego ahora aparece en tu lista administrada:

curl -sS "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" |
jq --arg id "$GAME_ID" '.[] | select(.id == $id)'

Verifique el estado de implementación:

curl -sS \
  "$API/api/v1/me/github-games/$GAME_ID/deployment" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Un reclamo comúnmente pone en cola una implementación, por lo que pending inmediatamente después del reclamo es normal. Encuesta con retroceder hasta que alcance el estado activo/éxito del entorno o se exponga deployError.

Después de la adquisición, los puntos finales de administración disponibles para usted incluyen:

PUT    /api/v1/me/github-games/{id}/deployment  pin a commit/branch and redeploy
POST   /api/v1/me/github-games/{id}/bundle      upload built client/container output
PUT    /api/v1/me/github-games/{id}/hosting     requeue hosting where supported
POST   /api/v1/me/github-games/{id}/transfer    transfer management deliberately
DELETE /api/v1/me/github-games/{id}             remove the game

El remitente original ya no ve este listado en GET /api/v1/me/github-games y no puedo utilice estos puntos finales de administración con ámbito de propietario para ello.

Solución de problemas

403: vincular el propietario del repositorio o agregar owner=

El inicio de sesión de GitHub vinculado no coincide ownerLogin, o el manifiesto owner no coincide exactamente su ID de usuario de StarHermit.

  • Controlar GET /api/v1/me/github.
  • comprobar el exacto ownerLogin devuelto por la cotización pública.
  • Para repositorios de organizaciones, utilice owner=<your StarHermit user ID> en el repositorio.
  • Confirme que envió el manifiesto y que su URL sin formato es legible públicamente.

404: no hay juego compartido con ese ID

La identificación es incorrecta o se eliminó la lista. Repita el paso 1. Los listados eliminados no son reclamables.

400: faltante o inválido starhermit.txt

Para un repositorio clonado, asegúrese de que el manifiesto raíz tenga valores válidos. name y HTML launch valores. también validar declaraciones de script/contenedor opcionales. La reclamación no confía en los metadatos originalmente. ingresado por un no propietario; lo reemplaza con metadatos controlados por el repositorio.

El reclamo falla alrededor del slug/backend

Es posible que el script no sea válido o que el alojamiento del contenedor no esté disponible. Verifique el error devuelto y la declaración de backend, luego llame al reclamo nuevamente. La plataforma asigna el UUID del juego como slug; no hay ninguna babosa manifiesta que elegir o resolver.

GitHub fue vinculado pero la cuenta StarHermit incorrecta posee el enlace

Inicie sesión en la cuenta StarHermit deseada y complete OAuth enlace fluir allí. no reclamar desde una segunda cuenta temporal de StarHermit y luego depender de la fusión de cuentas; el juego de transferencias API gestión, no identidades de usuarios.

Notas de seguridad

  • Nunca acepte un enlace de reclamo o una identificación de listado como prueba de propiedad del repositorio.
  • No coloque tokens de acceso de GitHub, credenciales de contenedor u otros secretos en starhermit.txt.
  • Utilice siempre el ID de usuario inmutable de StarHermit en owner=; no utilice un nombre de usuario o apodo.
  • Revise el listado existente y la URL del repositorio antes de realizar el reclamo; Los nombres para mostrar no son únicos.
  • Si luego transfieres el juego, el destinatario se convierte en administrador, pero el estado de propietario verificado es restablecer. Deben ejecutar el flujo de reclamos ellos mismos si controlan el repositorio.
