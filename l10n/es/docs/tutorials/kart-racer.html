Un gran premio es todos contra todos, por lo que la sala tiene un equipo de ocho asientos. Pista, recuento de vueltas y motor. clase ir en el opaco metadata:

Con una ficha de lanzamiento, el juego de la sala proviene de la ficha, por lo que gameSlug se puede omitir. el creador es el anfitrión en el asiento (0, 0). Desde aquí, el vestíbulo es el flujo normal de la habitación:

  • Amigos — POST /rooms/{id}/invites con {"toUserId": ...}. La plataforma les notifica; aceptarlos los sienta. Mostrar los seis caracteres joinCode para que tus amigos también puedan escribirlo en POST /rooms/join-by-code.
  • extraños — el anfitrión llama POST /rooms/{id}/open. Jugadores sin room call POST /rooms/quick-join con {"seats": 1} y, en 404, crear y abrir los suyos propios.
  • Seguimiento del voto/cambio de opinión del anfitrión — PATCH /rooms/{id} con nuevo metadata y la habitación revision como expectedRevision.
  • Solo contra CPU - crear con "aiPlayers": 7, entonces POST /rooms/{id}/start.

Una sala abierta comienza por sí sola cuando los ocho asientos se llenan o backfillAfterSeconds pases; el anfitrión también puede POST /rooms/{id}/start. Cada asiento aún vacío se convierte en un participante de la IA: esos son sus Controladores de CPU.

5. El socket de carrera (enrutado por host)

Conectar

Cada participante abre el socket en tiempo real con un ticket de un solo uso:

const { ticket } = await api.post("/api/v1/realtime/connection-tickets"); // { ticket, expiresIn }
const ws = new WebSocket(
  `wss://api.starhermit.com/ws/v1/realtime?roomId=${roomId}&ticket=${encodeURIComponent(ticket)}`);
ws.binaryType = "arraybuffer";

Los marcos de texto son marcos de control y push JSON; Los marcos binarios son un juego. El roster empujar es Tu parrilla: después del inicio se congela, incluidos los asientos AI. Con un equipo, la plaza de parrilla de un kart es su del participante slot.

ws.onmessage = (e) => {
  if (typeof e.data === "string") return onControl(JSON.parse(e.data)); // roster, presence, event, ready, chat, result
  const bytes = new Uint8Array(e.data);
  const sender = guidFromDotNet(bytes.subarray(0, 16)); // server-stamped, trustworthy
  onGameplay(sender, new DataView(e.data, 16));          // your payload starts at byte 16
};

// The server prefixes the sender's participant id in .NET GUID byte order:
// the first three groups are little-endian.
function guidFromDotNet(b) {
  const h = (i) => b[i].toString(16).padStart(2, "0");
  return `${h(3)}${h(2)}${h(1)}${h(0)}-${h(5)}${h(4)}-${h(7)}${h(6)}-` +
         `${h(8)}${h(9)}-${h(10)}${h(11)}${h(12)}${h(13)}${h(14)}${h(15)}`;
}

Nunca coloques una identificación de jugador en tu propia carga útil y confía en ella: el prefijo de 16 bytes es la única identidad. que el servidor garantiza.

Enrutamiento y presupuesto

La plataforma impone la forma del juego enrutado por el anfitrión:

  • A huéspedes alcance de los fotogramas binarios solo el anfitrión - ese es el canal de entrada.
  • El anfitrión alcance de los fotogramas binarios cada invitado - ese es el canal de instantáneas.
  • Cada cuadro es como máximo 8 KB; cada conexión puede enviar 30 mensajes/segundo (2× ráfaga por uno segundo). Al pasar se cierra el enchufe con PolicyViolation.

Entonces, el anfitrión simula al ritmo que le parezca adecuado (60 Hz es típico), pero envía instantáneas en 20 Hz y los invitados envían entradas a 20 Hz. Eso deja espacio para el marco de control ocasional.

Diseños de marco (ejemplo)

Entradas, invitado → host, 7 bytes:

Compensar Tipo Campo
0 u8 1 = entrada
1 u16 seq — incrementa cada envío
3 i8 dirigir, −127…127
4 u8 acelerador, 0…255
5 u8 bits: 0 freno, 1 deriva
6 u8 itemPresses — un contador, no una bandera

itemPresses es un recuento continuo de pulsaciones de botones de elementos. A 20 Hz, una pulsación inferior a 50 ms de lo contrario, quedará entre muestras; Con un contador, el anfitrión dispara un elemento por incremento, sin embargo, el Las prensas aterrizaron.

Instantáneas, anfitrión → invitados, 4 + 22 bytes por kart (176 bytes para una cuadrícula completa):

Compensar Tipo Campo
0 u8 2 = instantánea
1 u16 garrapata del anfitrión
3 u8 recuento de karts
por kart u8, f32 ×4, u8, u16, u8, u8 espacio, x, z, rumbo, velocidad, vuelta, punto de control, artículo, banderas

Los invitados rinden otros karts. ~100 ms en el pasado, interpolando entre las dos instantáneas que mantener ese tiempo, y predecir su propio kart localmente a partir de sus entradas, acercándose al anfitrión posición cuando no están de acuerdo. Incluir la última entrada seq el anfitrión solicitó por kart en flags o un campo adicional si desea una conciliación exacta.

Cuenta regresiva, eventos de carrera, finalización.

Los marcos de control son JSON, como máximo 4 KB, y los sellos del servidor from con la identificación del participante del remitente:

  • Los invitados envían {"type":"ready"} una vez cargada la pista.
  • El anfitrión espera a que cada humano conectado esté listo (o que se agote el tiempo de espera), luego envía {"type":"event","kind":"countdown","goInMs":3000}. Los invitados comienzan su cuenta regresiva local el recibo: no se necesita sincronización del reloj con esta precisión.
  • Otros ritmos de carrera también son event marcos: {"kind":"lap","slot":3,"lap":2}, {"kind":"finished","slot":3,"place":1,"timeMs":94210}.
  • chat está disponible para todos, pero los invitados están limitados a 10 cuadros de control por minuto, suficiente para ready y algunos "gg"s, no para jugar.

Cuando el último humano cruza la línea (o un cronómetro después de que se acabe el ganador), el anfitrión envía el resultado, que cierra la habitación y empuja {"type":"result"} a todos:

POST /api/v1/realtime/rooms/{id}/result

{ "teamScores": [0],
  "metadata": { "track": "coral-loop",
                "order": [ { "slot": 3, "timeMs": 94210 }, { "slot": 0, "timeMs": 95002 } ],
                "bestLapMs": 30112 } }

teamScores necesita exactamente una entrada por equipo (fijada entre 0 y 50), lo que no conlleva nada útil en un todos contra todos; el orden final vive en metadata. Una carrera por equipos es la misma sala con teamCount: 2 y los puntos de cada equipo en teamScores.

Controladores de CPU, abandonos y cambios de host

  • Los asientos AI son tuyos para conducir. La plataforma reserva el asiento y nombra al conductor; el anfitrión la simulación lo dirige (una línea de carrera a través de los puntos de control, con algunas bandas elásticas).
  • Un invitado que se marcha a mitad de carrera. (POST /rooms/{id}/leave) mantiene su kart en la parrilla: el roster push muestra al mismo participante id ahora isAi: true, y la CPU del host se hace cargo de ese kart.
  • Un invitado que cae todavía está en la habitación; mantenga su kart en marcha y déjeles volver a conectarse. el enchufe más nuevo reemplaza al anterior.
  • Si el anfitrión se va, el rol de anfitrión pasa al humano restante que lleva más tiempo unido y al roster push muestra lo nuevo isHost. Todos los invitados ya tienen la última instantánea completa, por lo que la nueva el anfitrión reanuda la simulación y comienza a enviar instantáneas; las entradas de los invitados ahora se dirigen a ellos. La migración del host es tarea de su código: la plataforma solo mueve la función.
  • Si el host simplemente se desconecta, la habitación se cierra después de 60 segundos sin enchufe de host.

Una tabla de clasificación definida por el editor acepta POST /api/v1/leaderboards/{id}/submit, pero eso La puntuación la reclama el cliente: está bien para una contrarreloj amistosa, no para nada con premios.

7. Variante B: carreras con autoridad en el servidor

Para juegos clasificados, traslada la simulación a un guión. El vestíbulo no ha cambiado; agrega el guión y configuración de emparejamiento para el manifiesto:

De cualquier manera, los clientes toman la sessionId (la habitación gameSessionId, o los billetes coincidentes) y jugar más ws/v1/games?sessionId=…. El socket en tiempo real, si lo hubiera, se conserva únicamente para la lista.

el guión

Toda la simulación se ejecuta onTick en el techo de 30 Hz. Cada invocación es una nueva caja de arena que obtiene sessionState entra y lo devuelve, así que mantenga ese estado pequeño: se serializa en cada tic.

const TRACK = { laps: 3, radius: 14,
  checkpoints: [[0, 0], [120, 0], [160, 60], [120, 120], [0, 120], [-40, 60]] };

globalThis.game = {
  tickRateHz: 30,
  replays: true,
  queues: [{ key: "grand-prix", teams: 8, teamSize: 1 }],
  achievements: [
    { key: "chequered-flag", name: "Chequered Flag", description: "Win a race.", points: 10 }
  ],

  createSession(ctx) {
    const karts = racers(ctx).map((r, i) => ({
      id: r.id, name: r.name, ai: r.ai, x: -8 * (i % 2), z: -6 * i, heading: 0, speed: 0,
      cp: 1, lap: 0, boost: 0, boosts: 1, input: {}, ack: 0, finishedAt: null
    }));
    return { ok: true, sessionState: { t: ctx.now, goAt: ctx.now + 4000, karts, order: [] } };
  },

  onPlayerMessage(ctx) {                       // durable commands: discrete actions
    const s = copy(ctx.sessionState);
    const k = s.karts.find((k) => k.id === ctx.message.from);
    if (ctx.message.data?.type === "use-item" && k && k.boosts > 0 && ctx.now >= s.goAt) {
      k.boosts--; k.boost = 1.2;
    }
    return { ok: true, sessionState: s };
  },

  onTick(ctx) {
    const s = copy(ctx.sessionState);
    const dt = Math.min(Math.max((ctx.now - s.t) / 1000, 0), 0.1);
    s.t = ctx.now;
    for (const i of ctx.inputs || []) {        // latest realtime input per player since last tick
      const k = s.karts.find((k) => k.id === i.from);
      if (k) { k.input = i.data; k.ack = Math.max(k.ack, Math.floor(+i.data.seq) || 0); }
    }
    if (ctx.now >= s.goAt) {
      for (const k of s.karts) {
        if (k.finishedAt) continue;
        move(k, k.ai ? aiInput(k) : k.input, dt);   // pure motion — shared with the client
        progress(k, s, ctx);                        // checkpoints, laps, finish — server only
      }
    }
    const snap = s.karts.map((k) =>
      [k.id, r2(k.x), r2(k.z), r3(k.heading), r2(k.speed), r2(k.boost), k.lap, k.cp, k.ack]);
    const out = { ok: true, sessionState: s,
      broadcast: [{ to: "all", data: { type: "snap", t: s.t, goAt: s.goAt, karts: snap } }] };
    if (raceOver(s, ctx)) Object.assign(out, finish(s, ctx));
    return out;
  }
};

Los ayudantes son códigos de juego normales. Las partes que le interesan a la plataforma:

  • racers(ctx) lee la grilla desde cualquier inicio que haya tenido la sesión: ctx.room.roster por un sala (los asientos AI tienen userId: null, así que dales identificadores como ai-0-5), ctx.matchmaking.seats por un carrera emparejada (saltar asientos con id: null), demás ctx.players.
  • move(k, input, dt) debe sujetar cada valor de entrada — steer a −1…1, throttle a 0…1 — porque ctx.inputs[].data es lo que el cliente envió. Solo from es de confianza. Mantenlo puro no ctx, sin estado de sesión, por lo que el cliente también puede ejecutarlo (consulte predicción del lado del cliente).
  • Aleatoriedad y tiempo venir de ctx.random y ctx.now; no hay Date o Math.random.
  • finish(s, ctx) regresa result (que finaliza la sesión y, para una sala, la cierra), achievements para el ganador si es humano, y eloUpdates para corredores humanos, por ejemplo, por parejas elo en el orden de finalización, leído y escrito de nuevo en ctx.playerStates. Los asientos AI no pueden recibir el estado del jugador, calificaciones o logros.
  • raceOver También deberíamos poner fin a las carreras que nadie puede terminar: cada ser humano se va según sus reglas. ctx.presence (habitaciones), o un límite de tiempo estricto.
  • Repeticiones mantener sólo el final sessionState. Mantenga una tabla compacta de tiempos de vuelta y finalización. orden en él, no un registro de posición por tick.

el cliente

Envíe dirección como entrada en tiempo real en cada tic y acciones discretas como comandos duraderos:

// ~30 Hz: latest-wins, batched into the next onTick
send({ type: "cmd", data: { type: "input", realtime: true, seq: ++seq,
                            steer, throttle, brake, drift } });

// on key press: a durable command, runs onPlayerMessage immediately
send({ type: "cmd", data: { type: "use-item" } });

Elementos debe pasar por un comando duradero. Las entradas en tiempo real son las últimas ganancias entre ticks, y el La plataforma conserva sólo los campos de un solo uso. pass, tackle y shoot cuando una muestra más nueva reemplaza uno anterior: cualquier otro botón en una entrada en tiempo real se puede sobrescribir antes de marcar lo ve.

achievement los marcos llegan al mismo enchufe; leer GET /api/v1/games/{slug}/achievements en carga por cualquier cosa concedida antes de su apertura.

Predicción del lado del cliente

Renderizar solo lo que envía el servidor hace que el kart se sienta como si lo condujeran a través del barro. una direccion El cambio tiene que llegar al servidor, esperar el siguiente tic (hasta 33 ms a 30 Hz) y regresar en un snap — con un ping de 80 ms, es decir, más de 100 ms antes de que el kart gire. La predicción esconde que: el cliente se mueve su propio kart inmediatamente y trata a cada uno snap Como corrección, no como en la imagen.

Comparte el código de movimiento

Divida la simulación como lo hace el script anterior: un puro move(k, input, dt) para el manejo y solo servidor progress para puntos de control, vueltas y llegadas. Exponer el código de movimiento de server.js como segundo global: el patrón que utiliza el ajedrez para globalThis.chessRules - y cargar el mismo archivo en el navegador:

El cliente predice solo movimiento. Las vueltas, posiciones, elementos y el orden de llegada quedan en manos del servidor. llamar. No espere resultados idénticos: el sandbox y el navegador pueden no coincidir en los últimos bits de Math.sin/Math.cosy posiciones en snap son redondeados. La reconciliación absorbe esa tendencia.

Paso al ritmo del servidor

El servidor no ejecuta un paso por entrada. En cada tick se aplica el el último entrada que tiene para ese kart, lo sigue usando hasta que llega uno más nuevo y se integra en tiempo real desde el marca anterior. Así que refleje esa forma en lugar de avanzar a la velocidad de fotogramas de la pantalla:

const pending = [];                              // inputs the server hasn't acknowledged yet
let seq = 0, predicted, previous;               // { x, z, heading, speed, boost }, seeded from the first snap
let error = { x: 0, z: 0, heading: 0 };          // visual offset, decays in render()

setInterval(() => {                              // 30 Hz, the script's tickRateHz
  if (!predicted || serverNow() < goAt) return;  // the server ignores movement before goAt
  const input = { steer: readSteer(), throttle: readThrottle(), brake: held("brake"), drift: held("drift") };
  const entry = { seq: ++seq, input, dt: 1 / 30 };
  send({ type: "cmd", data: { type: "input", realtime: true, seq: entry.seq, ...input } });
  pending.push(entry);
  previous = { ...predicted };
  kartPhysics.move(predicted, input, entry.dt);  // the kart responds now, not a round trip later
}, 1000 / 30);

Enviar más rápido que la tasa de ticks se desperdicia (solo se utiliza la última entrada por tick) y el La plataforma deja caer las entradas en tiempo real por encima de su límite por conexión.

Conciliar en cada snap

El guión hace eco ack, el más alto seq se ha aplicado para cada kart. en cada snap, rebobina tu kart al estado del servidor y reproduce lo que el servidor aún no ha visto:

function onSnap(snap) {
  const [, x, z, heading, speed, boost, lap, cp, ack] = snap.karts.find((k) => k[0] === myId);
  while (pending.length && pending[0].seq <= ack) pending.shift();   // applied or superseded

  const corrected = { x, z, heading, speed, boost };
  for (const p of pending) kartPhysics.move(corrected, p.input, p.dt);

  if (!predicted) { predicted = corrected; previous = { ...corrected }; return; } // first snap
  error.x += predicted.x - corrected.x;          // what the player would see jump
  error.z += predicted.z - corrected.z;
  error.heading += predicted.heading - corrected.heading;
  if (Math.hypot(error.x, error.z) > 3) error = { x: 0, z: 0, heading: 0 }; // wall hit, bump: snap
  predicted = corrected;
  hud.lap = lap; hud.checkpoint = cp;            // progress is never predicted
}

Descartando todo hasta ack tiene razón a pesar de que last-wins omite algunas entradas: un omitido La entrada fue reemplazada antes de que el servidor funcionara, por lo que tampoco afectó al kart del servidor.

Correcciones suaves, renderizado a velocidad de fotogramas

Las pequeñas correcciones deberían ser invisibles. Dibuja el kart en la posición prevista más un decaimiento. compensación de error e interpolar entre los dos últimos pasos de predicción de 30 Hz para que una pantalla de 60 o 144 Hz se mueve suavemente:

function render(frameDt) {
  const decay = Math.exp(-frameDt / 0.1);        // ~100 ms to absorb a correction
  error.x *= decay; error.z *= decay; error.heading *= decay;
  const a = sinceLastStep() * 30;                // 0…1 between prediction steps
  drawKart(lerp(previous.x, predicted.x, a) + error.x,
           lerp(previous.z, predicted.z, a) + error.z,
           lerpAngle(previous.heading, predicted.heading, a) + error.heading);
}

Ajuste el umbral de aceleración en lugar de la caída: una corrección mayor que la longitud de un kart es real evento (un golpe que no predijo) y se lee mejor como un chasquido rápido que como una diapositiva lenta.

Sepa qué no predecir

  • Otros karts. Se extraen ~100 ms en el pasado (búfer snaps e interpolar entre los dos ese soporte serverNow() - 100), por lo que una colisión predicha contra ellos es una colisión con donde ellos eran. Predice las paredes y la pista (no se mueven) y deja que el servidor resuelva Golpes de kart a kart. La corrección llega en un viaje de ida y vuelta. Si el buffer se seca, extrapolar desde la velocidad y el rumbo hasta ~100 ms, luego manténgalo presionado.
  • Elementos. use-item es un comando duradero, por lo que se ejecuta en onPlayerMessage tan pronto como llegue - sin esperar tictac. Reproduzca la llama y el sonido al presionar la tecla; deja que la velocidad llegue reconciliación, ya que boost esta en el snap. Si el servidor se niega (no quedan cargos), el siguiente snap lo hace retroceder.

Estimar el reloj del servidor

snap.t y goAt son la hora del servidor (ctx.now). Mantenga una compensación desde la brecha más pequeña observada, que filtra entregas lentas:

let offset = Infinity;
function noteSnap(snap) { offset = Math.min(offset, performance.now() - snap.t); }
const serverNow = () => performance.now() - offset;

Inicia la cuenta regresiva desde goAty predicción de puerta en él como lo hace el bucle anterior. Un kart que se mueve antes goAt localmente vuelve a la red con una banda elástica por el primer snap después del inicio.

Para ajustar todo esto, agregue latencia artificial en el desarrollo (retraso send y onSnap entre 100 y 200 ms) y registrar el tamaño de cada corrección: correcciones grandes y constantes significan move se ha alejado de la copia del servidor o un campo de entrada se fija de forma diferente en cada lado.
