Rendimiento nativo para juegos de script

Un juego con motor StarHermit ejecuta el mismo paquete en los navegadores y de forma nativa. Los dos ejecutan su código muy de manera diferente, así que elija dónde reside el trabajo pesado antes de transferirlo o escribirlo. Esta página cubre el guión. velocidad, WebAssembly, escenas vinculadas a GPU, trabajadores y medición. Las cifras son medidas del motor de Octubre de 2026, a partir del motor 1.26.1.

Cómo se ejecuta tu código

En navegadores De forma nativa
JavaScript del juego El V8 del navegador, a toda velocidad Intérprete propio del motor, sin JIT (por diseño, por seguridad)
WebAssembly, ámbito principal El WebAssembly del navegador Código nativo compilado en plataforma desde el motor 1.26.1 (detalles); de lo contrario, el intérprete del motor (host API 1.25 y posterior)
Asamblea web en starhermit:script trabajadores El intérprete del motor, para resultados exactos en bits Código nativo compilado en plataforma, como en el ámbito principal
  • De forma nativa, JavaScript para juegos reales se trata de 15-25 veces más lento que el V8. Los micro-benchmarks pueden sugerir aproximadamente 8×. No confíes en ellos.
  • El WebAssembly nativo que la plataforma ha compilado se ejecuta en aproximadamente velocidad V8: aproximadamente 7 veces más rápido que el intérprete en el punto de referencia de simulación del motor, aproximadamente 1,4 veces el tiempo del V8. interpretado WebAssembly es entre 8 y 18 veces más lento que V8.
  • starhermit check ejecuta JavaScript exactamente como lo hace un juego con ventana. Punto de referencia con un --release Construcción del motor únicamente.

Asamblea web compilada

Desde el motor 1.26.1, cuando publicas un juego que contiene .wasm módulos, la plataforma compila cada uno módulo con anticipación en una compilación de espacio aislado y firma el resultado. El tiempo de ejecución nativo lo descarga, verifica la firma, la almacena en caché y la ejecuta como código nativo. No necesitas cambiar el juego; simplemente publícalo.

  • Dónde: Windows x86-64, Linux x86-64 e Intel macOS, en CPU x86-64-v2 o posterior (SSE4.2 y POPCNT). Los Apple Silicon Macs y las CPU más antiguas todavía interpretan, al igual que los módulos que utilizar SIMD.
  • Cuando: una instancia creada antes de que se haya descargado el código compilado sigue interpretando. Más tarde Las instancias se ejecutan compiladas, incluido el siguiente lanzamiento, que las carga desde la memoria caché del disco.
  • Mismos resultados: El código compilado coincide con el intérprete bit por bit, incluido el combustible y las trampas.
  • Marque y deshabilite: con --dev, el registro muestra para cada módulo si se ejecutó compilado o interpretado y por qué. STARHERMIT_WASM_AOT=0 desactiva la compilación.
  • Los navegadores no han cambiado: el dominio principal usa el WebAssembly del navegador y los trabajadores usan el intérprete del motor.

Trabajo pesado por cuadro

La simulación, el mallado, la búsqueda de rutas y la creación de entidades son los puntos calientes habituales.

  1. Escriba el código activo en Rust u otro lenguaje WASM y ejecutarlo como WebAssembly, idealmente en un starhermit:script obrero. Una vez publicado el juego, se ejecuta de forma nativa a una velocidad cercana a la V8, mientras que JavaScript simple permanece entre 15 y 25 veces más lento.
  2. Elige un camino con runtime() de starhermit:engine (API de host 1.26). "web" significa V8, entonces JavaScript está bien allí. "native" significa que deberías preferir la ruta WASM. Los trabajadores siempre toman la ruta nativa y no se puede importar starhermit:engine.
  3. Mantenga JavaScript simple para la lógica del juego, la interfaz de usuario y la orquestación. Distribuya trabajos pesados ​​poco comunes entre los marcos.
  4. No compile JavaScript o TypeScript en WebAssembly para mayor velocidad. El resultado todavía necesita un Modelo de objetos JavaScript, por lo que no gana nada.

Para muchas entidades similares, starhermit:world granos ejecutar de forma nativa también.

Escenas vinculadas a GPU

De forma nativa, la GPU generalmente se convierte en el límite solo después de que el tiempo del script esté bajo control.

  • Usar InstancedMesh.setLevels([...]) con niveles de baja poli y una distancia de dibujo, y tres LOD (API de host 1.26).
  • Doblar castShadow desactivado para accesorios pequeños o distantes.
  • Limite las cascadas de sombras con shadow.cascades = { count, maxDistance }, una extensión del motor.
  • Colocar STARHERMIT_GPU_PASS_TIMES=1 para imprimir el tiempo de GPU para cada pasada.

Trabajadores

  • Antes de Host API 1.27, mantenga una referencia a cada trabajador que utilice, porque la recolección de basura lo termina. Desde el 1.27, un trabajador con oyentes vive hasta terminate().
  • Los trabajadores pueden leer archivos de paquetes (files) de la API de host 1.26.
  • Los trabajadores pueden enviar mensajes binarios y transferibles desde la API del host 1.25.

Medición

  • Compare nativo y web usando la misma compilación.
  • Las estadísticas de fotogramas del motor informan el tiempo del script por separado del tiempo de fotograma. Los números del banco de scripts son adecuado para citar.
