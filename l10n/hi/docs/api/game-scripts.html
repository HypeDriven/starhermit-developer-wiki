गेम स्क्रिप्ट

एक StarHermit आधिकारिक गेम को इसके द्वारा परिभाषित किया जा सकता है एकल जावास्क्रिप्ट फ़ाइल सैंडबॉक्स में सर्वर-साइड निष्पादित जिन्ट इंजन। स्क्रिप्ट उस गेम के नियमों पर एकमात्र अधिकार है: यह प्रत्येक खिलाड़ी के आदेश को मान्य करता है, स्थिति को बदलता है, यह तय करता है कि प्रत्येक ग्राहक क्या देख सकता है, एलो की गणना करता है, और गेम को समाप्त करता है। ग्राहकों के पास शून्य अधिकार है. यह पृष्ठ जावास्क्रिप्ट रनटाइम का दस्तावेजीकरण करता है; जिन खेलों को किसी अन्य भाषा की आवश्यकता है, वे इसके बजाय इसे लागू कर सकते हैं कंटेनर गेम सर्वर शिष्टाचार। दोनों एक ही प्लेयर-फेसिंग का उपयोग करते हैं गेम्स एपीआई. संपूर्ण रूप से काम किया गया उदाहरण शतरंज है - संदर्भ कार्यान्वयन हाइपड्राइवन/स्टारहर्मिट-शतरंज.

निष्पादन मॉडल

  • प्रति गेम एक जेएस फ़ाइल, एक में निष्पादित प्रति आह्वान ताजा सैंडबॉक्स्ड जिंट इंजन. कॉल के बीच मेमोरी में कुछ भी नहीं रहता है - आपके द्वारा लौटाए गए दस्तावेज़ों में सारी स्थिति रहती है।
  • कोई परिवेश नहीं Date या Math.random. समय और यादृच्छिकता की आपूर्ति इस प्रकार की जाती है: ctx.now (एमएस युग) और ctx.random (अंदर तैरें [0, 1)).
  • जब कोई खिलाड़ी एक टिकाऊ कमांड भेजता है, जब एक सत्र बनाया जाता है, और समय-समय पर प्लेटफ़ॉर्म स्क्रिप्ट को आमंत्रित करता है onTick झाडू (देखें) गेम्स एपीआई - रनटाइम टाइमिंग). रियल टाइम {type:"input", realtime:true} फ़्रेम अपवाद हैं: उन्हें नवीनतम-जीत बफ़र किया जाता है और अगले टिक पर एक बैच के रूप में वितरित किया जाता है।

प्रवेश स्थल

संचालकों को बेनकाब करें globalThis.game. छह वैकल्पिक स्थिर घोषणाएँ उनके साथ बैठती हैं: tickRateHz मंच से पूछता है कि कितनी बार आह्वान करना है onTick - यदि आपका गेम इस पर निर्भर करता है तो इसे घोषित करें टिक करें, क्योंकि जो गेम कुछ भी नहीं कहता उसे हर चार सेकंड में एक बार टिक किया जाता है (देखें)। टिक दर), achievements खेल की उपलब्धियों को दर्ज करता है (देखें)। उपलब्धियों), replays मंच से आपके समाप्त सत्रों को रखने के लिए कहता है (देखें)। रिप्ले), persistent रुकता है सभी के चले जाने पर सत्र समाप्त करने के बजाय (देखें)। लगातार सत्र), linkedAchievements अन्य खेलों के नाम बताएं जिनके अनलॉक आपको प्राप्त होते हैं ctx.linkedAchievements (देखना अन्य खेलों से उपलब्धियां), और queues घोषित करता है मंगनी मंगनी के आकार स्वीकार करता है (देखें) खेल - मंगनी करना). एक खेल यह घोषणा करता है कि किसी भी कतार में एक अंतर्निहित 1v1 नहीं है:

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

आपकी स्क्रिप्ट का मूल्यांकन करके घोषणाएँ पढ़ी जाती हैं जब गेम प्रकाशित या अपडेट किया जाता है, प्रत्येक आह्वान पर नहीं - इसलिए उन्हें स्थिर मान होना चाहिए game वस्तु। एक अद्यतन प्रकाशित करें परिवर्तन लागू करने के लिए.

  • createSession(ctx) - जब कोई सत्र बनाया जाता है (मैचमेकिंग, आमंत्रण-स्वीकृति, एआई अभ्यास, या रीयलटाइम रूम शुरू होता है - देखें) कहा जाता है कमरे में बंद सत्र).
  • onPlayerMessage(ctx) - गेमप्ले वेबसॉकेट पर प्राप्त टिकाऊ क्लाइंट कमांड के लिए कहा जाता है। इनपुट स्पष्ट रूप से चिह्नित realtime:true इस प्रवेश बिंदु को बायपास करें.
  • onMembershipChange(ctx) - वैकल्पिक। जब कोई खिलाड़ी चालू सत्र में शामिल होता है या छोड़ता है तो कॉल किया जाता है (a प्रगति कक्ष में शामिल हों, या एक चल रहे खेल में आमंत्रित करें). ctx.players पहले से ही परिवर्तन को दर्शाता है, और ctx.membership है { change: "joined" | "left", userId, name, team, slot }. वापस करना { ok: false } शामिल होने से इंकार करना; इस हुक के बिना एक स्क्रिप्ट प्रत्येक जुड़ाव को अस्वीकार कर देती है। आप चाहे जो भी लौटें, छुट्टी अंतिम है। उपलब्धियाँ और अंक परिणाम पर निर्भर हो सकते हैं; ए sessionState नजरअंदाज कर दिया जाता है.
  • onTick(ctx) - प्लेटफ़ॉर्म की टाइमर सेवा द्वारा प्रभावी टिक दर पर कॉल किया गया; नवीनतम रियलटाइम इनपुट उपलब्ध हैं ctx.inputs. 0 हर्ट्ज़ रिज़ॉल्यूशन वाले गेम को आवधिक कॉल प्राप्त नहीं होती हैं, लेकिन स्क्रिप्ट अनुबंध को पूरा करने के लिए फ़ंक्शन अभी भी मौजूद होना चाहिए।

प्रसंग वस्तु

ctx = {
  now: 1721473200000,              // ms epoch, from the host clock
  random: 0.7231,                  // float in [0, 1), from the host RNG
  sessionId: "0f8fad5b-...",       // current session id
  pausedMs: 0,                     // persistent games only: total ms this session has spent paused
  players: [                       // session participants
    { id: "7c9e6679-...", name: "alice", elo: 1312 },
    { id: "00000000-0000-4000-8000-00000000a1a1", name: "The House", ai: true, elo: 1200 }
  ],
  sessionState: { /* ... */ },     // this script's session document, or null
  playerStates: {                  // per-player documents (elo, history), or null
    "7c9e6679-...": { elo: 1200, wins: 4, losses: 2, draws: 1, /* ... */ }
  },
  message: {                       // onPlayerMessage only
    from: "7c9e6679-...",          // the authenticated user id — trusted
    data: { type: "move", from: "e2", to: "e4" }  // client payload — untrusted (example: a chess move)
  },
  inputs: [                        // onTick only; omitted when none are pending
    { from: "7c9e6679-...",        // authenticated sender id — trusted
      data: { type: "input", seq: 42, mx: 0.7, mz: -0.2 } }
  ]
}
  • एआई सीट (यदि मौजूद हो) को ध्वजांकित किया गया है ai: true इसके खिलाड़ी प्रविष्टि पर।
  • प्रत्येक खिलाड़ी की प्रविष्टि होती है elo, इस गेम के लिए इसकी वर्तमान रेटिंग - वही संख्या संग्रहीत है playerStates[id].elo, रोस्टर पर एक कंटेनर गेम सामने आया (जो पढ़ नहीं सकता केवल स्क्रिप्ट playerStates) इससे तर्क मिलान का बीजारोपण किया जा सकता है। एक खिलाड़ी जिसके पास अभी तक कोई रेटिंग नहीं है वह पढ़ता है 1200. यह बनाने, टिक करने, संदेश भेजने और पुनर्स्थापित करने में समान है; के माध्यम से ही रेटिंग बदलें eloUpdates.
  • एक खेल जो घोषणा करता है linkedAchievements भी मिलता है ctx.linkedAchievements: { <playerId>: { <otherSlug>: [unlocked keys] } }, प्रत्येक आह्वान पर दोबारा पढ़ें। देखना अन्य खेलों से उपलब्धियां.
  • रूम-बाउंड सेशन (रियलटाइम रूम से शुरू) को दो अतिरिक्त सीटीएक्स फ़ील्ड मिलते हैं, ctx.room और ctx.presence, पर प्रत्येक मंगलाचरण - देखें कमरे में बंद सत्र.
  • किसी पर भरोसा मत करो ctx.message.data या ctx.inputs[].data. विश्वसनीय पहचान संगत है from, जिसे सर्वर प्रमाणित कनेक्शन से जोड़ता है - क्लाइंट कभी भी इसकी आपूर्ति या धोखाधड़ी नहीं कर सकता है।
  • इनपुट के साथ बैचिंग का विकल्प चुनें {type:"input", realtime:true, ...}. अगोचर input आदेश टिकाऊ रहते हैं onPlayerMessage पश्चगामी अनुकूलता की मांग करता है। रीयलटाइम इनपुट प्रति प्रेषक एक लंबित स्लॉट का उपयोग करते हैं: आंदोलन नवीनतम-जीत है, जबकि pass, shoot, और tackle एक्शन किनारों को मर्ज कर दिया गया है, इसलिए अगला मूवमेंट नमूना अगले टिक से पहले उन्हें मिटा नहीं सकता है। बैच का उपभोग करते समय स्क्रिप्ट को प्रत्येक मान को क्लैंप और मान्य करना होगा।

टिक दर

मंच चलता है onTick कॉन्फ़िगर करने योग्य दर पर प्रति सक्रिय सत्र स्वीप। आपकी स्क्रिप्ट वह दर मांगती है जो वह चाहती है एक स्थैतिक घोषित करके tickRateHz गेम ऑब्जेक्ट पर, प्रवेश बिंदुओं के साथ:

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • घोषणापत्र पढ़ा जाता है जब आपका गेम प्रकाशित या अपडेट किया जाता है, हर टिक पर नहीं। किसी अपडेट को बदलने के बाद उसे प्रकाशित करें.
  • कोई गेम जो कोई दर घोषित नहीं करता, उसे 0.25 हर्ट्ज़ पर टिक कर दिया जाता है - हर चार सेकंड में एक बार। यह काफी है एक चाल घड़ी या एक टाइमआउट का निर्णय करें और प्लेटफ़ॉर्म पर लगभग कुछ भी खर्च न हो, लेकिन यह बहुत धीमा है किसी भी चीज़ के लिए आपका गेमप्ले निर्भर करता है। अगर onTick आपके गेम को संचालित करता है, आपको आवश्यक दर घोषित करता है।
  • अनुरोधों को प्लेटफ़ॉर्म पर अधिकतम रखा जाता है (30 हर्ट्ज डिफ़ॉल्ट रूप से), इसलिए कोई गेम कम मांग सकता है प्लेटफ़ॉर्म जितनी अनुमति देता है उससे अधिक कभी नहीं। पूछना 0 किसी गेम के लिए टिक्स को पूरी तरह से अक्षम करना वह केवल खिलाड़ी के आदेशों पर प्रतिक्रिया करता है।
  • दरें हो सकती हैं आंशिक: 0.5 हर दो सेकंड में एक टिक है. सबसे छोटी गैर-शून्य दर है 0.01 हर्ट्ज - एक छोटी सकारात्मक संख्या को ऑप्ट-आउट के रूप में पढ़ने के बजाय इसमें बढ़ाया जाता है, क्योंकि ए छोटा अंश एक धीमा खेल है. टिक लगाना केवल के लिए बंद है 0 या एक नकारात्मक दर. एक लापता या अनुपयोगी घोषणा (एक स्ट्रिंग, null, NaN) 0.25 हर्ट्ज डिफ़ॉल्ट लेता है।
  • एक ऑपरेटर किसी विशेष गेम के लिए दर को किसी भी दिशा में ओवरराइड कर सकता है।
  • रीयलटाइम इनपुट टिकों के बीच नवीनतम-जीत हैं, जबकि असतत कार्रवाई किनारों का आदेश दिया गया है। एक धीमा प्राप्तकर्ता एक अप्रचलित स्नैपशॉट को छोड़ सकता है लेकिन सिमुलेशन या अन्य प्राप्तकर्ताओं में देरी नहीं कर सकता है।

रिप्ले

जब एक सत्र समाप्त हो जाता है, तो प्लेटफ़ॉर्म अपना अंतिम सत्र रख सकता है sessionState के रूप में REPLAY - द दस्तावेज़ द्वारा परोसा गया GET /api/v1/games/{slug}/replays/{sessionId} (देखना गेम्स एपीआई - रिप्ले). रीप्ले को मैच के रिकॉर्ड के बराबर लंबे समय तक संग्रहित रखा जाता है है, तो आपके गेम को एक तभी मिलता है जब वह पूछता है:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • घोषणा शाब्दिक होनी चाहिए true या false - और कुछ भी घोषणा नहीं के रूप में पढ़ा जाता है, और एक ऐसा गेम जो कुछ भी घोषित नहीं करता, उसका कोई रिप्ले नहीं होता।
  • यह पढ़ा जाता है जब आपका गेम प्रकाशित या अपडेट किया जाता है. किसी अपडेट को बदलने के बाद उसे प्रकाशित करें.
  • एक प्लेटफ़ॉर्म ऑपरेटर किसी विशेष गेम के लिए किसी भी तरह से उत्तर दे सकता है, इसलिए घोषणा एक अनुरोध है गारंटी के बजाय. GET /api/v1/games/{slug} उत्तर को इस प्रकार रिपोर्ट करता है replaysEnabled — अपने रीप्ले यूआई को उस पर केंद्रित करें, न कि उस पर जो आपकी स्क्रिप्ट ने मांगा है।
  • रीप्ले बंद होने पर और कुछ नहीं बदलता: आपकी सत्र स्थिति अभी भी संग्रहीत है और अभी भी उसे वापस सौंप दी गई है हर आह्वान के रूप में ctx.sessionState, और यह अभी भी क्रैश पुनर्स्थापना बिंदु है। क्या खेल है रिप्ले के बिना एक प्रति नहीं मिलती है जो सत्र को समाप्त कर देती है, इसलिए इसका रिप्ले एंडपॉइंट उत्तर देता है 404.
  • अंतिम डिज़ाइन करें sessionState दोबारा चलाने लायक होना - एक मूव लॉग, या जो कुछ भी आपके ग्राहक को चाहिए मैच का पुनर्निर्माण करने के लिए. शतरंज संदर्भ कार्यान्वयन रहता है state.game.moves और इसे चरणबद्ध करें उन्हीं नियम मॉड्यूल के माध्यम से प्लेटफ़ॉर्म निष्पादित होता है।

लगातार सत्र

एक खेल जो घोषणा करता है persistent: true प्रत्येक खिलाड़ी के चले जाने पर अपना सत्र रखता है। लगभग 15 अंतिम डिस्कनेक्ट के कुछ सेकंड बाद सत्र होता है रुका हुआ - नहीं onTick कॉल - और पहला पुन: कनेक्ट करने के लिए प्लेयर इसे फिर से शुरू करता है। डिस्कनेक्ट या निष्क्रियता सत्र को छोड़ने के बजाय रोक देती है। एक खेल परिणाम, मालिक कार्रवाई, स्पष्ट अंतिम-सदस्य अवकाश, कॉन्फ़िगर अवधारण समाप्ति, या टर्मिनल पुनर्प्राप्ति विफलता हो सकती है फिर भी इसे ख़त्म करो. देखना सत्र जीवनचक्र.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • शाब्दिक होना चाहिए true या false. यह पढ़ा जाता है जब आपका गेम प्रकाशित या अपडेट किया जाता है.
  • ctx.now दीवार घड़ी रहती है. लगातार सेशन भी मिलते हैं ctx.pausedMs, व्यतीत किया गया कुल समय रुका हुआ, इसलिए ctx.now - ctx.pausedMs एक ऐसी घड़ी है जो तब भी खड़ी रहती है जब वहां कोई नहीं होता।
  • रुके हुए सत्रों की गणना प्रति-खिलाड़ी सत्र सीमा के विरुद्ध की जाती है, इसलिए खिलाड़ियों को एक आदेश दें जो समाप्त होता है एक के साथ दुनिया result.

देखें लगातार सत्र ट्यूटोरियल एक सुव्यवस्थित उदाहरण और ग्राहक प्रवाह के लिए।

मंगनी सीट लेआउट

नए मैचमेड सत्र प्राप्त होते हैं ctx.matchmaking पर प्रत्येक मंगलाचरण (बनाएँ, आदेश दें और टिक करें)। यह कतार के आकार और सीटों को सुरक्षित रखता है, भले ही खेल को बाद में फिर से तैनात किया गया हो:

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players इसमें केवल कब्जे वाली सीटें शामिल हैं team और ai:true एआई के लिए. टीम/स्लॉट इंडेक्स हैं शून्य आधारित. इस सत्र के भीतर AI आईडी स्थिर हैं और StarHermit खाता आईडी नहीं हैं। केवल मनुष्य सत्र/चैट सदस्यता है और खाता प्लेयर-स्टेट, रेटिंग या उपलब्धि लेखन प्राप्त कर सकते हैं। AI स्थिति को अंदर रखें sessionState. ग्राहकों को जिस भी रोस्टर फ़ील्ड की आवश्यकता हो उसे अपने गेम की स्थिति में कॉपी करें या प्रसारण. पुराने सत्र और गैर-मैचमेकिंग सत्र छोड़े जा सकते हैं ctx.matchmaking.

आरंभ की समय सीमा और अधिकतम एआई गिनती की घोषणा करें starhermit.txt. एआई गिनती के साथ 0, खाली सीटें खाली ही रह जाती हैं। वही संदर्भ कंटेनर सर्वर तक पहुंचाया जाता है।

कमरे में बंद सत्र

एक सत्र हो सकता है एक वास्तविक समय के कमरे से बंधा हुआ: जब ए वास्तविक समय कक्ष के साथ एक खेल के लिए server= स्क्रिप्ट शुरू होती है, प्लेटफ़ॉर्म कमरे के लिए एक एन-प्लेयर सत्र बनाता है इंसान प्रतिभागी (एआई सीटें केवल स्क्रिप्ट-फेसिंग रोस्टर में मौजूद हैं)। सर्वर-प्राधिकृत रीयलटाइम गेम (जैसे फ़ुटबॉल) इस प्रकार चलते हैं: कमरे लॉबी/मैचमेकिंग प्रदान करते हैं, स्क्रिप्ट मैच चलाती है। देखना रीयलटाइम कमरे - पुल कमरे के किनारे के जीवनचक्र के लिए।

प्रत्येक आह्वान (createSession, onPlayerMessage, onTick) एक कमरे में बंद सत्र को दो अतिरिक्त ctx फ़ील्ड प्राप्त होते हैं:

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online - उपयोगकर्ता के पास किसी भी कनेक्शन रजिस्ट्री (रियलटाइम रूम) पर एक लाइव सॉकेट है या ws/v1/games).
  • presence.left - उपयोगकर्ता के पास अब सक्रिय सीट नहीं है: वे स्पष्ट रूप से चले गए और उनकी सीट एआई प्रतिभागी में बदल दी गई। left स्थायी है; online फड़फड़ा सकता है. उम्मीद है कि स्क्रिप्ट इन झंडों से एआई अधिग्रहण/पुनः जुड़ने के तर्क को प्रेरित करेगी।
  • प्रत्येक आह्वान पर रोस्टर को दोबारा पढ़ा जाता है, इसलिए सीट रूपांतरण (मानव → एआई) जैसे ही होते हैं, दिखाई देते हैं।

जब रूम-बाउंड स्क्रिप्ट वापस आती है result, मंच सत्र समाप्त करता है, परिणाम को कमरे में संग्रहीत करता है, और कमरा बंद कर देता है - होस्ट द्वारा सबमिट किया गया कोई परिणाम शामिल नहीं है।

इसका विपरीत सत्य नहीं है: कमरा बंद करने से उसका सत्र समाप्त नहीं होता है। यदि कमरा पहले बंद हो जाता है (उदाहरण के लिए क्योंकि उसके अंतिम व्यक्ति ने बिना प्रगति के कमरा छोड़ दिया - कभी नहीं क्योंकि मेजबान ऑफ़लाइन हो गया, जो सत्र सक्रिय होने पर केवल मेजबान भूमिका को स्थानांतरित करता है), सत्र चलता रहता है, ctx.room.roster खाली हो जाता है और हर इंसान दिखाता है left: true. वापस करना result तो फिर मैच रूम के साथ ख़त्म होना चाहिए. देखना रीयलटाइम रूम - 60-सेकंड होस्ट नियम और रूम-बाउंड सत्र.

वापसी का आकार

प्रत्येक प्रवेश बिंदु एक ही आकार देता है (सभी फ़ील्ड वैकल्पिक हैं ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

मुख्य नियम:

  • sessionState और प्रत्येक प्रविष्टि playerStates प्रतिस्थापित करें संग्रहीत दस्तावेज़ - हमेशा पूर्ण दस्तावेज़ लौटाएँ, कभी भिन्न नहीं होंगे।
  • केवल संदेश सूचीबद्ध हैं broadcast ग्राहकों को वितरित किए जाते हैं, प्रत्येक को स्पष्ट प्लेयर आईडी या को संबोधित किया जाता है "all". और कुछ भी लीक नहीं होता.
  • eloUpdates रेटिंग बदलने का यही एकमात्र तरीका है। मूल्य प्रत्येक खिलाड़ी के हैं नई निरपेक्ष रेटिंग, भेजे गए अनुसार लागू किया गया - प्लेटफ़ॉर्म प्रति मैच परिवर्तन को सीमित नहीं करता है, इसलिए इसे स्वयं क्लैंप करें (देखें)। एलो प्रति मैच). मेजबान उन्हें मैचमेकिंग के लिए उपयोग करता है और उन्हें गेम के लीडरबोर्ड पर प्रकाशित करता है; ग्राहक कभी भी सीधे स्कोर प्रस्तुत नहीं कर सकते (देखें)। लीडरबोर्ड). रेटिंग अंदर रखें playerStates[id].elo तो एक मालिक का रेटिंग रीसेट आपकी कॉपी भी पहुंचती है.
  • achievements उपलब्धियाँ प्रदान करने का यही एकमात्र तरीका है। कुंजियों का समाधान गेम की उपलब्धियों के आधार पर किया जाता है - घोषित किया जाता है, या उसके मालिक द्वारा बनाया जाता है - और प्लेटफ़ॉर्म द्वारा जारी रखा जाता है; देखना उपलब्धियों.
  • scores यह आपके गेम के लीडरबोर्ड को बदलने का एकमात्र तरीका है - देखें लीडरबोर्ड.
  • के माध्यम से खेल समाप्त करें result. फिर मेज़बान सत्र समाप्त करता है, और उसके साथ खेल के लिए रिप्ले अंतिम को संग्रहीत करता है sessionState रीप्ले के रूप में (द्वारा परोसा गया)। GET .../replays/{sessionId} - देखना गेम्स एपीआई).

उपलब्धियों

आपकी स्क्रिप्ट है केवल वह चीज़ जो आपके गेम की उपलब्धियों को अनलॉक कर सकती है। कोई ग्राहक नहीं है उनके लिए समापन बिंदु: POST /api/v1/me/achievements/unlock गेम-स्कोप वाली उपलब्धियों को सिरे से खारिज करता है, और प्रकाशक सीआरयूडी एंडपॉइंट उन्हें छूने से इनकार करते हैं। गेम का मालिक बगल में उपलब्धियां जोड़ सकता है के माध्यम से घोषित किए गए /me/github-games/{id}/achievements; आपकी स्क्रिप्ट ठीक उसी तरह कुंजी द्वारा उन्हें अनलॉक करती है। यह सर्वर के रूप में उपलब्धियाँ बनाता है- बाकी खेल की तरह आधिकारिक, और यह तंत्र है कोई एक के साथ खेल server= स्क्रिप्ट उपयोग करना चाहिए - जिसमें वह भी शामिल है जिसका गेमप्ले कहीं और चलता है (देखें)। कौन से खेल इसका उपयोग कर सकते हैं).

प्रचार

एक स्थैतिक achievements पर सरणी game वस्तु। केवल key आवश्यक है:

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
मैदान प्रकार टिप्पणियाँ
key डोरी आवश्यक। स्थिर आईडी, ≤ 128 वर्ण, खेल के भीतर अद्वितीय। पहले के बाद डुप्लिकेट को नजरअंदाज कर दिया जाता है।
name डोरी के लिए डिफ़ॉल्ट key.
description डोरी के लिए डिफ़ॉल्ट "".
icon डोरी वैकल्पिक यूआरएल.
secret बूलियन तक एक खिलाड़ी से छिपा हुआ वे इसे अनलॉक करें. के लिए डिफ़ॉल्ट false.
points संख्या 0-10000 तक सीमित। के लिए डिफ़ॉल्ट 0.

गेम प्रकाशित या अद्यतन होने पर सरणी लागू की जाती है:

  • परिभाषाओं का मिलान किया जाता है key - किसी नाम, आइकन, बिंदुओं या गुप्त ध्वज को संपादित करने से मौजूदा परिभाषा अपडेट हो जाती है, और हर कोई जिसने इसे पहले ही अर्जित कर लिया है, वह इसे रखता है।
  • जिस कुंजी को आप घोषित करना बंद करते हैं वह हटा दी जाती है केवल जबकि किसी ने इसे अनलॉक नहीं किया है. अर्जित इतिहास कभी नष्ट नहीं होता है, इसलिए सेवानिवृत्त उपलब्धि इसे धारण करने वाले खिलाड़ियों को दिखाई देती रहती है।
  • अधिक से अधिक 100 प्रति खेल उपलब्धियाँ; उससे अधिक अतिरिक्त हटा दिए जाते हैं।
  • घोषणा है सर्वोत्तम प्रयास: विकृत प्रविष्टियाँ छोड़ दी जाती हैं। हमेशा प्रकाशित परिभाषाओं की पुष्टि करें GET /api/v1/games/{slug}/achievements गेम को अपडेट करने के बाद.

अनलॉक

एक लौटें achievements से मानचित्र कोई प्रवेश बिंदु - createSession, onPlayerMessage, या onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • अनलॉक हैं निष्क्रिय - खिलाड़ी के पास पहले से मौजूद कुंजी पर दोबारा जोर देना एक नो-ऑप है, इसलिए एक स्क्रिप्ट उस स्थिति से सुरक्षित रूप से पुरस्कार दे सकती है जो ट्रैकिंग के बजाय प्रत्येक टिक पर पुनर्मूल्यांकन करती है "पहले ही सम्मानित किया जा चुका है" अपने ही राज्य में.
  • अज्ञात कुंजियाँ (न तो गेम के मालिक द्वारा घोषित और न ही बनाई गई), जो उपयोगकर्ता इस सत्र के भागीदार नहीं हैं, और एआई सीट को चुपचाप अनदेखा कर दिया जाता है।
  • अधिक से अधिक 32 चाबियाँ प्रति खिलाड़ी प्रति आमंत्रण स्वीकार की जाती हैं; उसी सरणी में आगे की कुंजियाँ हटा दी जाती हैं।
  • शेष मंगलाचरण के लेखन के साथ पंक्तियाँ बनी रहती हैं, इसलिए एक अनलॉक विफल मंगलाचरण से बच नहीं सकता है।

वितरण

प्रत्येक नए दिए गए अनलॉक को कमाई करने वाले खिलाड़ी के पास भेज दिया जाता है ws/v1/games एक विशिष्ट ढाँचे के रूप में - यह मंच का सत्य है, आपका नहीं broadcast संदेश:

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

से अनलॉक दिए गए createSession किसी भी सॉकेट के मौजूद होने से पहले भूमि, इसलिए वे बिना किसी फ्रेम के पहुंचते हैं - ग्राहकों को पढ़ना चाहिए GET /api/v1/games/{slug}/achievements लोड पर और फ्रेम को इस रूप में मानें लाइव-अपडेट पथ. पूरी सतह अंदर उपलब्धियों.

लीडरबोर्ड

एलो बोर्ड के अलावा, आपके गेम में लीडरबोर्ड भी हो सकते हैं जिसके माध्यम से उसका मालिक बनाता है POST /api/v1/me/github-games/{id}/leaderboards, प्रत्येक के साथ एक key. लौटकर उन्हें पोस्ट करें scores किसी भी प्रवेश बिंदु से - बोर्ड कुंजी → प्लेयर आईडी → संख्या:

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • प्रत्येक खिलाड़ी अपना रखता है श्रेष्ठ बोर्ड की क्रमबद्ध दिशा के अनुसार प्रत्येक बोर्ड पर स्कोर करें, इसलिए रिपोर्ट करें हर परिणाम - एक बदतर परिणाम को आसानी से नजरअंदाज कर दिया जाता है।
  • केवल सत्र प्रतिभागियों की गिनती होती है। अज्ञात या निष्क्रिय कुंजियाँ, और बोर्ड के नियमों के बाहर स्कोर, चुपचाप गिरा दिए जाते हैं. प्रति रिटर्न अधिकतम 16 बोर्ड।
  • भिन्न eloUpdates, कुछ भी प्रकाशित नहीं किया गया है playerStates - अपनी प्रति अपने पास रखें playerStates यदि गेम को व्यक्तिगत सर्वश्रेष्ठ बैक पढ़ने की आवश्यकता है।

जहां आपकी स्क्रिप्ट चलती है

एक स्क्रिप्ट जो बिना किसी सीमा के दोहराई जाती है, उसकी मेमोरी समाप्त हो जाती है, या उसके समय बजट से अधिक हो जाती है, वह विफल हो जाती है मंगलाचरण. इसका असफल परिणाम लागू नहीं होता है। आदेश या टिक इनमें से किसी एक की रिपोर्ट करता है:

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

सर्वर में आपके गेम का हिस्सा

  • स्क्रिप्ट का समय. गेम के सभी सत्र स्क्रिप्ट समय का बजट साझा करते हैं, 2000 एमएस प्रति सेकंड डिफ़ॉल्ट, प्रत्येक आह्वान पर वास्तव में जो लिया गया उसका शुल्क लिया जाता है। इसके बजाय इसके हिस्से पर एक खेल से इनकार कर दिया जाता है पंक्तिबद्ध से: एक टिक छोड़ दिया जाता है, एक आदेश का उत्तर दिया जाता है "यह गेम अपने हिस्से से ज्यादा का उपयोग कर रहा है अभी सर्वर का; शीघ्र ही पुनः प्रयास करें.", और एक सत्र रिटर्न बनाना 429.
  • आदेश. प्रत्येक खिलाड़ी प्रति सत्र प्रति सेकंड 20 टिकाऊ कमांड भेज सकता है (एक छोटे विस्फोट के साथ)। भत्ता); इसके अलावा एक आदेश का उत्तर a के साथ दिया जाता है error चौखटा, "बहुत सारे आदेश; गति कम करो।" फ़्रेम में HTTP स्थिति शामिल नहीं है. रीयलटाइम इनपुट अलग से सीमित है।
  • परिणाम। एक सत्र के समापन पर परिणाम अधिकतम 64 केबी हो सकता है; बड़े को अस्वीकार कर दिया जाता है 422.
  • स्क्रिप्ट का आकार. A server= स्क्रिप्ट अधिकतम 2 एमबी की हो सकती है; बड़े को अस्वीकार कर दिया जाता है 422 पहले इसे संग्रहित या पार्स किया जाता है.

ऑपरेटर व्यक्तिगत गेम के लिए इनमें से प्रत्येक को बढ़ा या घटा सकते हैं।

बजट

स्क्रिप्ट इन संसाधन बजट के अंतर्गत चलती हैं:

  • ~250 एमएस सीपीयू प्रति आह्वान
  • 32 एमबी मेमोरी
  • प्रति मंगलाचरण एक वक्तव्य कैप
  • प्रति खिलाड़ी राज्य बाइट बजट - सभी राज्य दस्तावेज़ क्रमबद्ध और छोटे रहने चाहिए
  • जब वे टेक्स्ट बन जाते हैं तो मान अधिकतम 64 स्तरों पर गहराई तक टिक जाते हैं। प्रवेश बिंदु से कुछ भी वापस आता है, प्रत्येक घोषणा, JSON.stringify, और Array.prototype.join/toString/toLocaleString इनकार ए ए के साथ गहरा मूल्य RangeError (एक लौटाया गया आह्वान विफल रहता है: "64 से अधिक स्तरों पर नेस्टेड गहरा"). JSON.parse पहले ही 64 पर रुक चुका है, इसलिए अधिक गहरा मूल्य कभी भी राउंड-ट्रिप नहीं कर सकता। flat 64 स्तरों तक चपटा होता है और यदि सरणी अधिक गहराई में स्थित होती है, तो फेंकता है - जिसमें शामिल सरणी भी शामिल है स्वयं.
  • एक कॉल मेमोरी बजट से अधिक आवंटित नहीं कर सकती। repeat, padStart/padEnd, concat और replace/replaceAll फेंक RangeError: Invalid string length जब परिणाम आधे से अधिक हो सकता है वर्णों में बजट (डिफ़ॉल्ट 32 एमबी पर 16एम; एक रेगेक्स प्रतिस्थापन को प्रत्येक की तरह सीमित किया गया है स्थिति का मिलान किया गया, जो केवल लगभग दस लाख या अधिक वर्णों की स्ट्रिंग को प्रभावित करता है)। ArrayBuffer और टाइप की गई सरणियाँ फेंकें RangeError बजट को बाइट्स में, और सरणियों को अतीत में बजट/8 तत्वों को अस्वीकार कर दिया गया है। आपके हुक के वापस आने के बाद बजट की भी जाँच की जाती है, इसलिए ओवर-बजट अंतिम विवरण सफल होने के बजाय आह्वान को विफल कर देता है।

शतरंज संदर्भ स्क्रिप्ट अपने दस्तावेज़ों को उद्देश्य से छोटा रखती है - बजट के भीतर रहने के उदाहरण के रूप में, इसका प्रति-खिलाड़ी दस्तावेज़ है

{
  elo: 1200,
  wins: 0, losses: 0, draws: 0,
  lastColorVs: "9b2f8c1a-...",        // for color alternation on rematch
  lastColorOrder: "w",
  recentGames: [ /* up to 30 summaries */ ]
}

समवर्ती-सत्र की सीमा डिफ़ॉल्ट रूप से प्रति खिलाड़ी 20 है।

प्लेटफ़ॉर्म-पठनीय विंडो

में सब कुछ sessionState मंच के लिए अपारदर्शी है के अलावा एक फ़ील्ड:

sessionState.summary = {
  turnPlayerId: "7c9e6679-...",
  deadline: 1784642591000,
  status: "active",
  moveCount: 41
};

deadline में एक पूर्णांक यूनिक्स टाइमस्टैम्प है मिलीसेकंड, या कोई समय सीमा न होने पर छोड़ दिया जाता है। ISO दिनांक स्ट्रिंग की पहचान नहीं की गई है. turnPlayerId प्लेयर UUID है.

GET /api/v1/games/{slug}/sessions/mine पढ़ता summary गणना करना myTurn और deadline कॉल करने वाले के लिए. प्रत्येक राज्य परिवर्तन पर इसे सटीक रखें; बाकी सब कुछ वहीं रखें जहां आपकी स्क्रिप्ट पसंद हो।

कार्यान्वित उदाहरण: शतरंज की स्क्रिप्ट

इस खंड में सब कुछ शतरंज संदर्भ कार्यान्वयन के लिए विशिष्ट है - राज्य आकार, बोर्ड एन्कोडिंग, कमांड सेट, गेम-ओवर कारण, एलो स्थिरांक, एआई और नीचे दिए गए टाइमआउट शतरंज की अपनी पसंद हैं, जो इसकी स्क्रिप्ट में परिभाषित हैं। इनमें से कोई भी प्लेटफ़ॉर्म व्यवहार नहीं है; आपका गेम अपने स्वयं के समकक्षों को परिभाषित करता है।

सत्र स्थिति:

{
  white: "7c9e6679-...",
  black: "9b2f8c1a-...",

  game: {
    board: "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr", // 64 chars
    turn: "w",
    castling: { K: true, Q: true, k: true, q: true },

बोर्ड एन्कोडिंग: एक 64-वर्ण स्ट्रिंग जहां index = rank * 8 + file और a1 सूचकांक 0 है. PNBRQK सफेद टुकड़े हैं, pnbrqk काला, . एक खाली वर्ग है.

शतरंज की अन्य बारीकियाँ:

  • एलो K=32 का उपयोग करता है, जिसकी गणना की जाती है finishGame जब कोई खेल समाप्त होता है, और वापस लौटता है eloUpdates.
  • एआई प्ले: जब एआई सीट हिलनी हो, aiReply नाटकों "एचएएल" - एक लालची सामग्री-कब्जा इंजन - एक ही आह्वान के अंदर। कोई बाहरी बॉट नहीं है.
  • समय समाप्ति: onTick 24 घंटे की चाल घड़ी का निर्णय करता है - यदि कोई चाल नहीं खेली गई है तो खेल एक है timeout-no-moves खींचना; अन्यथा आगे बढ़ने वाला खिलाड़ी हार जाता है timeout.

तैनाती

अपने गेम रिपॉजिटरी में स्क्रिप्ट घोषित करें starhermit.txt घोषणापत्र:

server=server.js

प्रकाशन GitHub एकीकरण के माध्यम से प्रवाहित होता है - देखें गिटहब गेम्स. प्लेटफ़ॉर्म प्रलेखित बजट के भीतर स्क्रिप्ट को निष्पादित करता है। गठबंधन मत करो server= साथ container.image=; उपयोग कंटेनर रनटाइम इसके बजाय एक छवि शिपिंग करते समय।

सर्वोत्तम प्रथाएं

  • प्रत्येक आदेश को मान्य करें. इलाज ctx.message.data शत्रुतापूर्ण के रूप में: स्थिति को छूने से पहले प्रकार, रेंज, टर्न ऑर्डर और गेम की स्थिति की जांच करें।
  • आह्वान तेज़ रखें और कथन छोटा रखें। आपके पास ~250 एमएस और प्रति खिलाड़ी दस्तावेज़ एक बाइट बजट है; शतरंज संदर्भ स्क्रिप्ट, उदाहरण के लिए, कैप्स recentGames इस कारण से 30 प्रविष्टियों पर।
  • उपयोग ctx.now / ctx.random केवल। नहीं Date, नहीं Math.random - मेजबान घड़ी और पासे का मालिक है।
  • डिज़ाइन broadcast एकमात्र ग्राहक अनुबंध के रूप में संदेश। ग्राहकों को स्क्रिप्ट द्वारा भेजी गई सामग्री के आधार पर संपूर्ण गेम प्रस्तुत करने में सक्षम होना चाहिए; जो कुछ भी प्रसारित नहीं होता वह उनके लिए अस्तित्व में नहीं है।
  • एक फ़ाइल, दो सतहें। एक ही फ़ाइल एक अलग निर्यात के माध्यम से क्लाइंट-साइड नियमों के रूप में दोगुनी हो सकती है: शतरंज संदर्भ कार्यान्वयन, उदाहरण के लिए, उजागर करता है globalThis.chessRules ब्राउज़र के लिए (पूर्वावलोकन स्थानांतरित करें, सत्यापन संकेत) और globalThis.game मेज़बान के लिए. सत्य का एक स्रोत, ग्राहक पर शून्य अधिकार।
