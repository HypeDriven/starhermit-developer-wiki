गिटहब गेम्स

GitHub रिपॉजिटरी से गेम प्रकाशित करें स्टारहर्मिट, या पहले से ही होस्ट किए गए वेब गेम को पंजीकृत करें। रिपॉजिटरी गेम के लिए, प्लेटफ़ॉर्म पढ़ता है starhermit.txt, रेपो को क्लोन करता है, और इसे यहां परोसता है <slug>.starhermit.com. क्योंकि /api और /ws उस उपडोमेन से समान-उत्पत्ति का अनुमान लगाया जाता है, एक प्लेटफ़ॉर्म-होस्टेड गेम की आवश्यकता होती है कोई सीओआरएस या एपीआई-बेस कॉन्फ़िगरेशन नहीं. एक पिन किया गया कमिट नियंत्रित करता है कि कौन सा रिपॉजिटरी संस्करण लाइव है। शतरंज संदर्भ कार्यान्वयन इस प्रकार प्रकाशित किया जाता है और मॉडल के संदर्भ उदाहरण के रूप में कार्य करता है।

आधार यूआरएल: https://api.starhermit.com. सभी मार्ग नीचे हैं api/v1/... और जब तक उल्लेख न किया गया हो, JWT की आवश्यकता होती है।

होस्ट की गई क्लाइंट फ़ाइलें घोषित कर सकती हैं फ़ोल्डर कैश जीवनकाल और अतिरिक्त CORS मूल में starhermit.txt. वे नीतियाँ क्लाइंट फ़ाइलों के साथ प्रकाशित होती हैं; एक प्रकट-मुक्त मर्ज बरकरार रहता है मौजूदा सेटिंग्स, जबकि एक आपूर्ति किया गया मेनिफेस्ट उन्हें प्रतिस्थापित करता है।

प्रकट: starhermit.txt

जगह starhermit.txt रेपो रूट पर. प्रारूप: key=value पंक्तियाँ, # एक टिप्पणी शुरू करता है.

name=Your Game
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html        # repo-relative HTML entry
cover=art/cover.png      # optional cover art for the library tile; or an https:// URL
description=One-line pitch\nSecond line   # optional; or description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md          # optional; or release_notes=inline text
owner=<starhermit user id>  # UUID from GET /api/v1/me; do not use username/nickname
# Choose at most one authoritative backend, or omit both for a browser-only game:
server=server.js         # sandboxed JavaScript; see game-scripts.md
# container.image=ghcr.io/owner/game@sha256:<64 lowercase hex>; see container-games.md

control.up=KeyW+ArrowUp | Move forward
control.shoot=Space | Shoot
  • कोई नहीं है slug कुंजी: प्लेटफ़ॉर्म एक यूआईडी निर्दिष्ट करता है और इसे उपडोमेन दोनों के रूप में उपयोग करता है (<uid>.starhermit.com) और गेम एपीआई नेमस्पेस (/api/v1/games/<uid>/…).
  • cover (उपनाम cover_art, coverart) गेम की लाइब्रेरी टाइल पर दिखाई गई कलाकृति है: लॉन्च फ़ाइल से संबंधित एक पथ, या एक निरपेक्ष https:// यूआरएल. वैकल्पिक - इसके बिना टाइल आपकी साइट का फ़ेविकॉन दिखाती है। प्रत्येक तैनाती पर दोबारा पढ़ें, इसलिए लाइन बदलने से कवर बदल जाता है। देखना कवर आर्ट टाइल वाली फसलों के लिए.
  • description / release_notes (या description.file / release_notes.file, कौन सा नाम ए .md/.markdown/.txt मेनिफेस्ट से संबंधित फ़ाइल) आपके गेम के लिए वैकल्पिक टेक्स्ट हैं। उन्हें प्रत्येक परिनियोजन पर पुनः पढ़ा जाता है cover. देखना विवरण और रिलीज़ नोट्स.
  • server एक सैंडबॉक्स्ड जावास्क्रिप्ट बैकएंड घोषित करता है; देखना game-scripts.md.
  • container.image एक कंटेनर बैकएंड घोषित करता है; देखना container-games.md. इसे डाइजेस्ट-पिन किया जाना चाहिए, एक स्वीकृत रजिस्ट्री पर सत्यापित GitHub मालिक के नामस्थान में होस्ट किया जाना चाहिए, और इसके साथ होना चाहिए container.port, container.health, container.memory_mb, container.cpu, और गैर-गुप्त container.env.* मूल्य.
  • दोनों बैकएंड कुंजियाँ शुद्ध ब्राउज़र गेम के लिए वैकल्पिक हैं, लेकिन वे एक-दूसरे के साथ परस्पर अनन्य हैं।

डिफ़ॉल्ट नियंत्रण बाइंडिंग

एक गेम शून्य या अधिक डेस्कटॉप-ब्राउज़र क्रियाओं की घोषणा कर सकता है:

control.<action>=<code>[+<code>...][ | <label>]
  • क्रियाएँ लोअरकेस हैं [a-z0-9_]{1,32} पहचानकर्ता और प्रकट क्रम बनाए रखें।
  • कोड हैं KeyboardEvent.code मूल्य; + एक क्रिया के लिए वैकल्पिक कुंजियाँ अलग करता है।
  • वैकल्पिक लेबल नियंत्रण-रीमैपिंग यूआई में दिखाया गया है और एक्शन आईडी पर डिफ़ॉल्ट है।
  • एक मेनिफेस्ट प्रति क्रिया अधिकतम 32 क्रियाएँ और 4 कोड घोषित कर सकता है। एक कोड का उपयोग नहीं किया जा सकता दो क्रियाएं. अमान्य नियंत्रण रेखाओं पर ध्यान नहीं दिया जाता.
  • नहीं के साथ खेल control.* घोषणाओं में कोई नियंत्रण नहीं है एपीआई/यूआई (404 "This game declares no controls."). प्रत्येक प्रकाशित बिल्ड - प्रत्येक परिनियोजन, फ़ोल्डर अपलोड से घोषणाएँ फिर से पढ़ी जाती हैं और बंडल पुश को प्रतिस्थापित करना। क्रमशः: ट्यूटोरियल: अपने गेम में नियंत्रण जोड़ें.

खिलाड़ी प्रति गेम इन डिफॉल्ट्स को ओवरराइड कर सकते हैं गेम्स एपीआई को नियंत्रित करते हैं.

एक खेल पंजीकृत करें

POST /api/v1/me/github-games

{
  "repoUrl": "https://github.com/HypeDriven/starhermit-chess",
  "displayName": "StarHermit Chess",
  "launchPath": "index.html"
}

अपने ऐतिहासिक नाम के बावजूद, repoUrl तीन लॉन्च स्रोत स्वीकार करता है:

  1. A github.com/<owner>/<repo> भण्डार. बैकएंड इसके मेनिफेस्ट को पढ़ता है और इसे तैनात कर सकता है StarHermit होस्टिंग के लिए।
  2. पहले से ही होस्ट किया गया GitHub पेज URL जैसे https://owner.github.io/game/. भण्डार यूआरएल से पहचान का अनुमान लगाया जाता है; यूआरएल स्वयं लॉन्च किया गया है, बिना किसी क्लोन या इंस्टॉल के।
  3. कोई अन्य जनता http:// या https:// होस्ट किया गया वेब-गेम URL. इसे सीधे लॉन्च किया जाता है और GitHub स्वामित्व के दावे में भाग नहीं लेता है।
  • displayName और launchPath वैकल्पिक फ़ॉलबैक हैं. वे तृतीय-पक्ष रेपो के लिए उपयोगी हैं विश्वसनीय प्रकट मेटाडेटा के बिना; प्रत्यक्ष रूप से होस्ट किया गया यूआरएल स्वयं लॉन्च स्थान है।
  • सत्यापित रिपॉजिटरी मालिकों के लिए प्लेटफ़ॉर्म मान्य होता है starhermit.txt.
  • एक वैकल्पिक server= स्क्रिप्ट या container.image= बैकएंड प्रावधान एक आधिकारिक खेल है; देखना game-scripts.md और container-games.md. कंटेनर होस्टिंग Starhermit.com पर साइन-इन किए गए किसी भी उपयोगकर्ता के लिए खुली है; एक स्व-होस्टेड परिनियोजन इसे ऑपरेटर अनुमति सूची तक सीमित कर सकता है।
  • एक घोषित सर्वर बैकएंड को एक सिद्ध स्वामी की आवश्यकता होती है। एक रेपो सबमिट करना जो घोषित करता है server= या container.image= GitHub-लॉगिन के बिना या owner= प्रमाण है 403 (दोनों प्रमाणों का नामकरण), केवल ब्राउज़र-सूची नहीं जो बैकएंड होने का दिखावा करती है।
  • सीमाएँ: प्रति उपयोगकर्ता 100 गेम (प्रति खाता ऑपरेटर-ओवरराइडेबल)। डुप्लिकेट रिटर्न पंजीकृत करना 409.

पंजीकरण/तैनाती स्थितियों में शामिल हैं: InvalidUrl, LimitReached, Duplicate, MissingManualMetadata, MissingStarhermitTxt, InvalidLaunchPath, InvalidServerScriptPath, InvalidContainerImage, ServerProvisionConflict, RemovedByOwner.

स्थानीय फ़ोल्डर से गेम जोड़ें

POST /api/v1/me/github-games/upload → 201

URL पंजीकृत करने का समकक्ष: कोई भंडार नहीं है, और कुछ भी क्लोन नहीं किया गया है। फ़ोल्डर एक होकर यात्रा करता है .tar.gz अनुरोध निकाय पर और प्लेटफ़ॉर्म होस्ट करता है कि इसमें क्या शामिल है। वही पुरालेख के रूप में प्रारूपित करें एक बंडल को धकेलना, इसलिए एक ही पैकेजिंग दोनों के लिए काम करती है।

बनाए गए गेम में एक है gameSlug शुरू से ही, यह एक सर्वर घोषित करता है या नहीं, इसलिए a ब्राउज़र-केवल अपलोड का उपयोग कर सकते हैं को नियंत्रित करता है, प्रति-खिलाड़ी सेटिंग्स, इसका क्लाउड-सेव स्लॉट, वास्तविक समय के कमरे और किसी भी अन्य गेम की तरह टोकन लॉन्च करें।

client/           the game's files, published as-is
starhermit.txt    name= and launch= instead of the query parameters

मेनिफेस्ट वैकल्पिक है यह समापन बिंदु - क्वेरी पैरामीटर समान मान प्रदान कर सकते हैं - और StarHermit क्लाइंट हमेशा अपने मेनिफेस्ट फ़ील्ड से निर्मित एक भेजते हैं। फ़ाइल को अंदर भेजना आपका निर्माण अभी भी करने योग्य है: यह निर्माण को स्व-वर्णन योग्य बनाता है और उन फ़ील्ड्स को पहले से भर देता है, इसलिए यह यह याद रखे बिना कि उसे किन मूल्यों की आवश्यकता है, पुनः अपलोड किया जा सकता है। देखना starhermit.txt घोषणापत्र प्रारूप के लिए, और उस पर ध्यान दें सब कुछ मेनिफेस्ट के बगल में अपलोड किया गया है - एक वितरण योग्य बिल्ड अपलोड करें, स्रोत ट्री नहीं।

बाइट्स को सीधे भेजें - मल्टीपार्ट फॉर्म डेटा नहीं - के साथ Content-Type: application/gzip:

tar -czf game.tar.gz client/ starhermit.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/upload?displayName=My%20Game" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game.tar.gz

{
  "game": { "id": "...", "displayName": "My Game", "launchPath": "index.html", "hosting": { "hostingEnabled": true } },
  "bytesReceived": 4194304
}

मेटाडेटा इस क्रम में हल होता है, इसलिए अधिकांश फ़ोल्डरों को किसी क्वेरी पैरामीटर की आवश्यकता नहीं होती है:

  1. ?displayName= / ?launchPath= अनुरोध पर.
  2. name= / launch= में एक starhermit.txt पुरालेख रूट पर.
  3. index.html के मूल में client/ - लॉन्च पथ के रूप में उपयोग किया जाता है जब कोई और नाम नहीं देता है।

इस मार्ग के लिए विशिष्ट नोट्स:

  • कॉल रिटर्न होते ही गेम लाइव हो जाता है। कोई अलग होस्टिंग या तैनाती नहीं है कदम: deployStatus है live और deployedCommitSha है null, क्योंकि कोई प्रतिबद्धता नहीं है।
  • फ़ाइलें पुन: उत्पन्न नहीं की जा सकतीं, इसलिए प्लेटफ़ॉर्म उन्हें कभी भी कहीं से भी पुनः तैनात नहीं करता है। एक खेल इस प्रकार जोड़ा गया contentSource: upload और जब तक आप प्रकाशित नहीं करते तब तक इसका अपलोड किया गया निर्माण बरकरार रहता है एक और. के साथ एक नया निर्माण पुश करें बंडल समापन बिंदु या फ़ोल्डर को दोबारा अपलोड करें.
  • कोई रिपोजिटरी का मतलब कोई दावा नहीं है। ownerLogin खाली है, इसलिए कोई भी GitHub लॉगिन कभी भी इसका मिलान नहीं कर सकता; repoUrl एक सिंथेटिक ले जाता है upload:<id> यूआरएल के बजाय मूल्य।
  • A server/image.tar यहां मना कर दिया गया है (422). एक सर्वर छवि के लिए एक प्रावधानित गेम की आवश्यकता होती है संलग्न करें, जो गेम के अस्तित्व में आने तक अस्तित्व में नहीं है - पहले गेम बनाएं, फिर छवि को पुश करें को /{id}/bundle.
  • जिस फ़ाइल को संग्रह में शामिल नहीं किया गया है उसका नामकरण करने वाले लॉन्च पथ को अस्वीकार कर दिया गया है (422) जबकि अपलोड है प्रत्येक खिलाड़ी के लिए 404 बनने के बजाय, अभी भी स्टेजिंग में है।

सीमाएँ किसी भी अन्य धक्का के समान ही हैं: देखें अपलोड सीमा.

अपलोड किया गया फ़ोल्डर अपना स्वयं का सर्वर बैकएंड ला सकता है

यदि पुरालेख है starhermit.txt सर्वर लॉजिक, अपलोड की घोषणा करता है इसका प्रावधान भी करता है - वही चीज़ जो रिपॉजिटरी प्रवाह करता है, बिना रिपॉजिटरी के। एक चुनें शैली; दोनों को घोषित करने से इंकार कर दिया गया है।

घोषणा क्या होता है
server=path/to/server.js एक स्क्रिप्ट बैकएंड. फ़ाइल यात्रा करती है आपके द्वारा अपलोड किए गए फ़ोल्डर के अंदर, इसलिए इसका स्रोत सीधे संग्रह से पढ़ा जाता है - लाने के लिए कुछ भी नहीं है। देखना game-scripts.md.
container.image=name@sha256:… एक कंटेनर बैकएंड, हमेशा की तरह डाइजेस्ट-पिन किया हुआ। देखना container-games.md. बाद में छवि को स्वयं ही धकेल दिया जाता है /{id}/bundle.

यहां इनकार करने से पूरी रचना विफल हो जाती है - कोई भी आधी-अधूरी गेम पंक्ति जीवित नहीं रहती है:

  • server= उस फ़ाइल का नामकरण करना जिसमें संग्रह शामिल नहीं है।
  • server= क्लाइंट फ़ाइलों के बाहर इंगित करते हुए (../).
  • दोनों की घोषणा server= और container.image=.
  • ऐसे कंटेनर के लिए पूछना जहां कंटेनर अक्षम हैं, या ऐसे मालिक से जिसके लिए उन्हें मंजूरी नहीं दी गई है।

कवर आर्ट

लाइब्रेरी में आपके गेम की टाइल पर दिखाई गई छवि। इसे किसी भी तरह से सेट करें - आप जो भी उपयोग करें, वह गुमनाम GET /api/v1/github-games/{id}/cover यह वही है जो इसे परोसता है:

  • आपके निर्माण में — a cover= लाइन में starhermit.txt, लॉन्च से संबंधित एक छवि का नामकरण फ़ाइल या पूर्ण https:// यूआरएल. प्रत्येक परिनियोजन पर दोबारा पढ़ें, ताकि आपका भंडार सत्य का स्रोत बना रहे।
  • अपलोड किए गए — PUT /api/v1/me/github-games/{id}/cover छवि बेस64-एन्कोडेड के साथ। ये है वेब डैशबोर्ड क्या है प्रबंधित करें → कवर कला करता है, और एक StarHermit ऑपरेटर आपके लिए क्या कर सकता है।
PUT /api/v1/me/github-games/{id}/cover
Authorization: Bearer <token>
Content-Type: application/json

{ "imageBase64": "iVBORw0KGgoAAAANSUhEUg..." }

एक अपलोड ओवरराइड प्रकट, जानबूझकर: एक तैनाती जो फिर से पढ़ती है starhermit.txt अवश्य किसी के हाथ से चुनी गई कला को कभी भी पूर्ववत न करें। DELETE /api/v1/me/github-games/{id}/cover वापसी का रास्ता है - यह अपलोड और मैनिफ़ेस्ट को हटा देता है cover= पुनः लागू होता है.

पीएनजी, जेपीईजी, जीआईएफ, वेबपी, बीएमपी या एसवीजी, तक 4 एमबी. प्रकार को बाइट्स से सूँघा जाता है, इसलिए a Content-Type आप दावा करते हैं कि न तो इसकी आवश्यकता है और न ही विश्वास किया जाता है, और बाइट्स जो डिकोड करने योग्य छवि नहीं हैं से इंकार कर दिया जाता है 400. एक रिश्तेदार cover= पथ समाप्त होना चाहिए .png, .jpg/.jpeg, .gif, .webp या .svg (नहीं .., कोई नेतृत्व नहीं /); विफल होने के बजाय एक अनुपयोगी मान हटा दिया जाता है खेल.

कवर कला पोस्टर कला है: दोनों पुस्तकालय टाइल और केंद्र-फसल को भरने के लिए इसे स्केल करें जो कुछ भी करता है उपयुक्त नहीं. टाइल्स का आकार एक जैसा नहीं है.

सतह टाइल काटना
विंडोज़ क्लाइंट 96×128 पोर्ट्रेट (3:4) चित्र भरता है; व्यापक कला पक्ष खो देती है
वेब डैशबोर्ड वर्ग वर्ग भरता है; लम्बी कला ऊपर और नीचे खो देती है

विषय को केंद्र में रखें ताकि दोनों फसलें सही दिखें। एसवीजी वेब लाइब्रेरी पर शो को कवर करता है; द विंडोज़ क्लाइंट एसवीजी को डीकोड नहीं कर सकता है, इसलिए वह टाइल इसके बजाय फ़ेविकॉन दिखाती है। एक ऐसा खेल जिसमें कोई कवर नहीं है सभी वापस उसके फ़ेविकॉन पर आ जाते हैं (GET /api/v1/github-games/{id}/icon). आइकन से हल किया गया है आपके द्वारा सबमिट किया गया यूआरएल और, जब प्लेटफ़ॉर्म गेम होस्ट करता है, तो उस कॉपी से जिस पर वह काम करता है <uid>.starhermit.com - इसलिए फ़ाइलों में फ़ेविकॉन के साथ अपलोड किए गए बंडल को अभी भी एक आइकन मिलता है।

GET /api/v1/me/github-games/{id}/stats → GameStatsDto

{
  "totalPlayers": 42,
  "playingNow": 3,
  "totalSessions": 130,
  "totalPlaytimeMinutes": 8140,
  "lastPlayedAt": "2026-07-29T08:45:24Z",

}
  • केवल समुच्चय. आप अपने दर्शकों का आकार सीखते हैं, यह नहीं कि इसमें कौन है।
  • totalPlayers गिनता विशिष्ट लोग, सत्र नहीं - जिसने छह बार खेला वह एक है खिलाड़ी.
  • playingNow उन विशिष्ट खिलाड़ियों की गणना करता है जिनका सत्र समाप्त नहीं हुआ है और अंदर शुरू हुआ livenessWindowHours. विंडो मायने रखती है: जो क्लाइंट क्रैश हो गया है या उसका नेटवर्क खो गया है वह कभी नहीं भेजता है सत्र समाप्त हो गया, और इसके बिना उन पंक्तियों को पढ़ा जाएगा जैसे लोग अभी भी अनिश्चित काल तक खेल रहे हैं।
  • totalPlaytimeMinutes गिनता केवल पूर्ण सत्र, प्रति-उपयोगकर्ता प्लेटाइम आंकड़ों का मिलान में activity.md. उड़ान में एक सत्र अभी तक कुछ भी योगदान नहीं देता है।
  • lastPlayedAt है null एक ऐसे खेल के लिए जिसे किसी ने नहीं खेला है.

आंकड़े उसी लॉन्च लेजर से आते हैं जो प्रत्येक ग्राहक लिखता है (देखें)। activity.md), तो ए वह गेम जिसके खिलाड़ी कभी भी लॉन्च की रिपोर्ट नहीं करते, उसे शून्य पढ़ा जाएगा।

स्वामित्व का दावा करें

POST /api/v1/me/github-games/{id}/claim → GitHubGameDto

जब आप किसी मौजूदा सूची के भंडार को नियंत्रित करते हैं तो उसे अपने कब्जे में ले लें। या तो लिंक करके स्वामित्व सिद्ध करें व्यक्तिगत GitHub लॉगिन रिपॉजिटरी स्वामी से मेल खाता है, या कमिट करके owner=<your StarHermit user ID> भंडार के लिए starhermit.txt. owner होना चाहिए अपरिवर्तनीय यूयूआईडी के रूप में लौटाया गया id द्वारा GET /api/v1/me, नहीं एक उपयोक्तानाम या उपनाम. प्रकट विधि संगठन-स्वामित्व वाली रिपॉजिटरी का समर्थन करती है, जिसका अनुमान व्यक्तिगत GitHub org से नहीं लगाया जाता है सदस्यता.

सफल होने पर, मौजूदा सूची अपनी आईडी/इतिहास रखती है, दावेदार द्वारा प्रबंधित हो जाती है, ताज़ा हो जाती है रिपॉजिटरी-नियंत्रित मेटाडेटा और बैकएंड घोषणाएं, और जहां उपलब्ध हो वहां होस्टिंग कतारें। द पिछला सबमिट करने वाला स्वामी-दायरे वाली प्रबंधन पहुंच खो देता है। उस सूची का दावा करना जिसे आप पहले से ही प्रबंधित कर रहे हैं किसी विरोध को वापस करने के बजाय इसे पुन: सिंक्रनाइज़ करता है।

GitHub पहचान मेटाडेटा स्टोर {"login":"…"}; अपने GitHub खाते को OAuth प्रवाह के माध्यम से लिंक करें (देखें)। auth.md). लिंक स्थिति जांचें GET /api/v1/me/github → { linked, login }. देखें चरण-दर-चरण दावा ट्यूटोरियल खोज के लिए, दोनों प्रमाण तरीके, सत्यापन, अधिग्रहण और समस्या निवारण।

स्थानांतरण स्वामित्व

स्थानांतरण एक है लंबित प्रस्ताव को प्राप्तकर्ता स्वीकार करता है, कोई तात्कालिक कदम नहीं - एक खेल (और यह) होस्ट किए गए बाइट्स, जो प्राप्तकर्ता के विरुद्ध गिने जाते हैं) को उनके बिना किसी अन्य खाते पर नहीं भेजा जा सकता ऐसा कहो.

POST /api/v1/me/github-games/{id}/transfer (मालिक) प्रस्ताव को रिकॉर्ड करता है और लौटाता है GameTransferOfferDto; जब तक इसे स्वीकार नहीं किया जाता तब तक गेम आपका ही रहता है।

  • प्राप्तकर्ता इसे नीचे देखता है GET /transfers/incoming और साथ स्वीकार करता है POST /transfers/{offerId}/accept. स्वीकृति खेल को आगे बढ़ाती है अब, उसी क्षण जाँच की गई प्राप्तकर्ता के स्वयं के गेम-गिनती और होस्टिंग भत्ते के विरुद्ध - इसलिए एक प्रस्ताव दिया जा सकता है और फिर भी यदि प्राप्तकर्ता अपनी सीमा पर है तो उतरने में विफल। वे इसके बजाय कर सकते हैं POST /transfers/{offerId}/decline.

गेम बंडल पुश करें

POST /api/v1/me/github-games/{id}/bundle StarHermit से पूछे बिना निर्मित आउटपुट प्रकाशित करता है इसे फिर से क्लोन करें। कॉल करने वाले के पास पंजीकृत गेम होना चाहिए। भेजो .tar.gz सीधे बाइट्स—नहीं मल्टीपार्ट फॉर्म डेटा-साथ Content-Type: application/gzip:

client/            optional static client files; must include the registered launch file
server/image.tar   optional output from `docker save`
starhermit.txt     optional manifest copy for bundle portability
remove.txt         merge only: client-relative paths to delete, one per line

कम से कम client/ या server/image.tar मौजूद होना चाहिए (एक विलय भी हो सकता है)। remove.txt). क्लाइंट फ़ाइलें परमाणु रूप से स्वैप की जाती हैं। ए सर्वर छवि को लोड किया जाता है, प्लेटफ़ॉर्म द्वारा डाइजेस्ट-पिन किया जाता है, और कंटेनर परिनियोजन को कतारबद्ध किया जाता है उस छवि पर पुनः आरंभ करें. अपलोड की गई छवि को मेनिफेस्ट के रजिस्ट्री संदर्भ पर प्राथमिकता दी जाती है, और एक से अधिक server= रेखा; दोनों की घोषणा करने वाला एक प्रकटीकरण server= और container.image= मना कर दिया जाता है कुछ भी लोड होने से पहले. संग्रह में अन्य किसी भी चीज़ को नज़रअंदाज कर दिया जाता है।

एक छवि अपलोड करना स्वयं ही घोषणा है। यदि गेम में अभी तक कोई सर्वर बैकएंड नहीं है - a अपलोड किया गया फ़ोल्डर जिसमें कोई नहीं घोषित किया गया - पुश करना server/image.tar डाइजेस्ट से केवल एक प्रावधान के अंतर्गत लोड किया गया gameSlug खेल पहले से ही है. आपको डाइजेस्ट-पिन की गई छवि को नाम देने की आवश्यकता नहीं है मेनिफेस्ट पहले, जो गोलाकार था: छवि प्राप्त करने से पहले परिभाषा का अस्तित्व होना आवश्यक था, और छवि ही एकमात्र ऐसी चीज़ थी जो इसका वर्णन कर सकती थी।

एक पुन: धक्का कंटेनर नॉब्स को उसकी प्रकट घोषणाओं पर लागू करता है, और केवल उन पर। शामिल करना starhermit.txt एक बदले हुए बंडल में container.port, container.health, container.memory_mb या container.cpu और परिनियोजन इसे पुनरारंभ करने पर उठाता है; एक घुंडी बाहर छोड़ें और यह वह सब रखता है जो आपने पिछली बार सेट किया था। मेनिफेस्ट को पूरी तरह से हटा दें और परिनियोजन के बारे में कुछ भी नहीं बताएं छवि को छोड़कर परिवर्तन.

एक बंडल जिसका starhermit.txt एक प्रयोग योग्य ले जाता है name= भी गेम की सूची का नाम बदल देता है इसके लिए - डिस्प्ले-नाम अपडेट पुश के साथ-साथ चलता है। छुट्टी name= रखने के लिए बाहर रखें (या मेनिफेस्ट को छोड़ दें)। वर्तमान नाम.

StarHermit क्लाइंट एक फ़ोल्डर से आपके लिए यह बंडल बनाते हैं या एक .tar:

  • क्लाइंट फ़ाइलें - गेम का वितरण फ़ोल्डर, या a .tar इसका. नीचे एक फ़ोल्डर पैक किया गया है client/; a .tarकी प्रविष्टियाँ वहां दोबारा रखी गई हैं (एक संग्रह पहले से ही नीचे है)। client/ बाकी है अकेले)। केवल यूस्टार - जीएनयू लंबे नाम और पैक्स अभिलेखागार को अस्वीकार कर दिया गया है, क्योंकि उन्हें पुनः होम करने का मतलब है निम्नलिखित प्रविष्टि को नाम देने वाले मेटाडेटा ब्लॉक को फिर से लिखना।
  • समर्पित सेवक - सर्वर का वितरण फ़ोल्डर, या docker save .tar अपने दम पर। किसी फ़ोल्डर से केवल मैनिफ़ेस्ट और image.tar अपलोड किए गए हैं: छवि में पहले से ही आपका शामिल है सर्वर की अपनी फ़ाइलें हैं, इसलिए बाकी को पैक करने से प्लेटफ़ॉर्म को त्यागने के लिए गीगाबाइट भेज दिए जाएंगे।

दोनों ही मामलों में starhermit.txt संवाद में संपादन योग्य है. जो भी हो चुनी गई बिल्ड कैरी फ़ील्ड को पहले से भर देती है, और जो कुछ भी वे रखते हैं वह बंडल रूट पर लिखा होता है - इसलिए बिना मेनिफेस्ट वाला बिल्ड प्रकाशन योग्य है, और जो एक के रूप में भेजा जाता है .tar अभी भी इसका प्रकटीकरण हो सकता है अद्यतन किया गया।

docker save my-game-server:release -o image.tar
mkdir -p bundle/server
mv image.tar bundle/server/image.tar
cp starhermit.txt bundle/
tar -C bundle -czf game-bundle.tar.gz .

  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game-bundle.tar.gz

आंशिक अद्यतन: ?mode=merge

एक धक्का है एक प्रतिस्थापित करें जब तक आप अन्यथा न पूछें: संग्रह ही पूरा खेल है, और इसमें कुछ भी नहीं है यह चला गया है. ?mode=merge (HTTP और अपलोड सॉकेट समान) इसे बनाता है पैबंद लाइव क्लाइंट का फ़ाइलें - एक-फ़ाइल सुधार के लिए अपरिवर्तित परिसंपत्तियों के गीगाबाइट को फिर से अपलोड करने का उत्तर।

printf '%s\n' '# one client-relative path per line; a directory removes everything under it' \
    'assets/old-music.ogg' 'levels/cut/' > remove.txt
tar czf patch.tar.gz client/index.html client/js/app.js remove.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/$GAME_ID/bundle?mode=merge" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @patch.tar.gz

साथ mode=merge:

  • फ़ाइलों के अंतर्गत client/ जोड़ा या अधिलेखित किया गया है
  • जड़ में पथ remove.txt (# टिप्पणियाँ; एक निर्देशिका अपने संपूर्ण उपवृक्ष को हटा देती है) हटा दिए जाते हैं
  • हर दूसरी लाइव फ़ाइल बिल्कुल वैसी ही रहती है जैसी वह है

मर्ज किए गए पेड़ को एक प्रतिलिपि के रूप में मंचित किया जाता है और परमाणु रूप से स्वैप किया जाता है - खिलाड़ी पुराने गेम या देखते हैं बिल्कुल नया, कभी मिश्रण नहीं। परिणाम से घिरा है खेल का भत्ता, अपलोड का नहीं, इसलिए एक खेल एक समय में एक छोटे पैच की सीमा से आगे नहीं बढ़ सकता। मर्ज केवल क्लाइंट फ़ाइलों के बारे में है; ए server/image.tar एक प्रतिस्थापन के रूप में बिल्कुल लोड किया गया है। एक पैच ले जाने वाला नं starhermit.txt पत्तियां कला को वैसा ही कवर करें जैसा वह था।

विलय अस्वीकार कर दिया गया है (409/422, कुछ भी नहीं बदलता है) जब गेम में अभी तक कुछ भी प्रकाशित नहीं हुआ है, जब यह लॉन्च फ़ाइल को हटा देगा, या कब remove.txt खेल के बाहर अंक. ए remove.txt एक में सादा प्रतिस्थापन भी अस्वीकार कर दिया गया है (422), क्योंकि वहां इसका मतलब केवल वही हो सकता है जो आपने नहीं किया इरादा. mode होना ही चाहिए replace (डिफ़ॉल्ट) या merge; और कुछ भी है 400.

सॉकेट पर समान पैरामीटर काम करता है: ws/v1/game-upload?gameId=…&mode=merge. ready ढाँचा इसे इस रूप में प्रतिध्वनित करता है "apply":"merge".

एंडपॉइंट मौजूदा पंजीकृत गेम को अपडेट करता है; यह कभी भी गेम रिकॉर्ड नहीं बनाता - उसके लिए, देखें स्थानीय फ़ोल्डर से गेम जोड़ना. यह कर सकना खेल का प्रावधान करें सर्वर बैकएंड, एक सर्वर छवि को ऐसे गेम में लोड करने के साइड इफेक्ट के रूप में जिसमें कुछ भी नहीं था। देखें समर्पित-सर्वर प्रकाशन ट्यूटोरियल.

सीआई/सीडी से अपलोड करें

किसी इंटरैक्टिव OAuth टोकन को रिपॉजिटरी में गुप्त न रखें। एक बार OAuth के माध्यम से साइन इन करें और उपयोग करें उस सत्र के साथ एक अलग लेबल वाली परिनियोजन कुंजी जोड़ने के लिए POST /api/v1/me/public-keys. सीआई नौकरी तो हस्ताक्षर कर सकते हैं /auth/public-key/challenge, इसे एक्सचेंज करें /auth/public-key/complete, और उपयोग करें इस बंडल एंडपॉइंट पर 15 मिनट का एक्सेस टोकन लौटाया गया।

परिनियोजन कुंजी उसके स्वामित्व वाले खाते के रूप में कार्य करती है, इसलिए उस खाते को लक्ष्य गेम का स्वामी होना चाहिए। यह नहीं हो सकता अन्य कुंजी जोड़ें या अन्य कुंजियाँ निरस्त करें। यह स्वयं को निरस्त कर सकता है /me/public-keys/current; OAuth-प्रमाणित सत्र से नामांकन और अन्य कुंजियाँ प्रबंधित करें। प्रति एक कुंजी का प्रयोग करें पर्यावरण ताकि एक वर्कफ़्लो को दूसरे को रोके बिना अक्षम किया जा सके। मोटे तौर पर पुरालेख 100 एमबी को नीचे दिए गए वेबसॉकेट ट्रांसपोर्ट का उपयोग करना होगा।

देखना OAuth-नामांकित सार्वजनिक कुंजी के साथ CI/CD से बिल्ड अपलोड करें कुंजी पीढ़ी के लिए, GitHub गुप्त सेटअप, एक पूर्ण चुनौती-हस्ताक्षर/अपलोडर स्क्रिप्ट, स्थिर और कंटेनर बंडल लेआउट, और एक GitHub क्रियाएँ वर्कफ़्लो।

वेबसॉकेट पर अपलोड करें

GET /ws/v1/game-upload (उन्नत करना) - लगभग 100 एमबी से अधिक की किसी भी चीज़ के लिए इसका उपयोग करें।

एपीआई के सामने सीडीएन मोटे तौर पर HTTP अनुरोध निकाय को अस्वीकार कर देता है 100 एमबी के साथ 413 इसके अपना. वह इनकार कभी भी मंच तक नहीं पहुंचता, इसलिए उसका कोई मतलब नहीं है limitBytes और नो लॉग यू में दिखाई देता है पढ़ सकते हैं - ए 413 नहीं के साथ limitBytes फ़ील्ड सीडीएन है, आपके गेम का भत्ता नहीं, जो दो है परिमाण का क्रम बड़ा। कोई यथार्थवादी docker save इस पर प्रहार करेंगे.

वेबसॉकेट अपग्रेड के बाद भेजे गए फ़्रेम अनुरोध निकाय नहीं हैं, इसलिए सीमा लागू नहीं होती है। केवल परिवहन भिन्न है। बाइनरी फ़्रेम बिल्कुल HTTP मार्गों के बाइट्स में संयोजित होते हैं पढ़ें, एक ही पाइपलाइन से गुजरें, और हर इनकार, भत्ता और सफलता निकाय HTTP ही है रूट का उत्पादन हुआ होगा - इसलिए एक ग्राहक दोनों में एक कोड पथ साझा कर सकता है।

wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&mode=merge&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?displayName=My%20Game&launchPath=index.html&access_token=$TOKEN

उत्तीर्ण gameId आपके स्वामित्व वाले गेम को आगे बढ़ाने के लिए (द /{id}/bundle मार्ग); इसे छोड़ें और पास करें displayName/launchPath किसी फ़ोल्डर से एक बनाने के लिए ( /upload मार्ग)। टोकन अंदर चला जाता है क्वेरी स्ट्रिंग क्योंकि ब्राउज़र सेट नहीं कर सकता Authorization वेबसॉकेट हैंडशेक पर हेडर; यह है हैंडशेक पर एक बार जांच की जाती है, इसलिए एक अपलोड जो इसके एक्सेस टोकन से अधिक समय तक रहता है, अभी भी समाप्त होता है।

दिशा चौखटा अर्थ
सर्वर → {"type":"ready","mode":"bundle","apply":"replace","limitBytes":N,"heartbeatSeconds":15} भत्ते का निपटान और खाली स्थान की जाँच की गई। भेजना प्रारंभ करें. mode है bundle या create. apply है merge जब आपने आंशिक अद्यतन के लिए पूछा।
→ सर्वर द्विआधारी पुरालेख बाइट्स, आपकी इच्छानुसार खंडित - सर्वर कभी भी संदेशों को दोबारा इकट्ठा नहीं करता है, इसलिए 256 केबी-1 एमबी एक अच्छा डिफ़ॉल्ट है। संयोजित, आपके फ़्रेम बिलकुल वैसे ही होने चाहिए .tar.gz.
सर्वर → {"type":"ack","bytesReceived":N} रसीद की प्रगति, लगभग हर 8 एमबी। इससे अपनी प्रगति पट्टी चलाएँ।
→ सर्वर {"type":"complete"} पूरा पुरालेख भेज दिया गया है.
→ सर्वर {"type":"abort"} छोड़ देना। के साथ उत्तर दिया status: 499; कुछ भी प्रकाशित नहीं है.
सर्वर → {"type":"progress","phase":"publishing","bytesReceived":N} अपलोड लैंड होने पर हर 15 सेकंड में दिल की धड़कन। उन्हें नज़रअंदाज करें, लेकिन उनसे उम्मीद रखें।
सर्वर → {"type":"result","status":200,...} सफलता। ऑब्जेक्ट का शेष भाग HTTP प्रतिक्रिया निकाय शब्दशः है (status है 201 एक सृजन के लिए)।
सर्वर → {"type":"error","status":413,"error":"...","limitBytes":N} इनकार. status और बॉडी वही है जो HTTP रूट ने उत्तर दिया होगा।

जब तक कुछ भी प्रकाशित नहीं होता {"type":"complete"} आता है. यह बिना HTTP वाला एक व्यवहार है समतुल्य, और यह जानबूझकर किया गया है: संग्रह का अंत मार्कर रहता है अंदर एक टार बाइट्स, तो प्लेटफ़ॉर्म कनेक्शन को कभी भी ख़त्म किए बिना एक संपूर्ण दिखने वाले संग्रह को पढ़ना समाप्त कर देता है। एक सॉकेट वह बस अंतिम बाइट के बाद गिरा दिया गया अन्यथा बिल्कुल उसी तरह प्रकाशित होगा जो समाप्त हुआ था - चुपचाप एक लाइव गेम को एक परित्यक्त पुश से बदल दिया गया। फ़्रेम अपलोड किए बिना सॉकेट बंद करना कुछ नहीं.

आपके अंतिम बाइट के बाद प्रकाशन में समय लग सकता है, विशेषकर सर्वर छवि के लिए। अपेक्षा करना progress ख़त्म होते समय दिल की धड़कन; किसी शांत अंतराल को अपलोड विफलता न समझें।

स्थिति अर्थ
400 mode नहीं है replace और न merge.
409 ऐसे गेम के विरुद्ध एक मर्ज जिसकी अभी तक कोई प्रकाशित फ़ाइल नहीं है।
413 भत्ते से अधिक. शरीर ढोता है { "error", "limitBytes" }. A 413 बिना limitBytes सीडीएन की ~100 एमबी बॉडी कैप है, यह नहीं - अपलोड सॉकेट का उपयोग करें.
422 विकृत संग्रह, या अनुपयोगी सामग्री (लापता लॉन्च फ़ाइल, नहीं)। client/, a server/image.tar क्रिएट रूट पर, एक मर्ज जो लॉन्च फ़ाइल को हटा देगा, remove.txt एक प्रतिस्थापन पर)। साथ ही ए छंटनी की गई संग्रह - अपलोड के बीच में कनेक्शन छूट जाने का सामान्य परिणाम।

पुरालेख अपने रूट से बाहर नहीं निकल सकते हैं या उनमें लिंक नहीं हो सकते हैं, और केवल नियमित फ़ाइलें और निर्देशिकाएं ही होती हैं निकाले गए - सिम्लिंक, हार्ड लिंक और डिवाइस नोड्स अस्वीकार कर दिए गए हैं। git archive PAX वैश्विक हेडर, ./-उपसर्ग नाम से tar -czf game.tgz ., और फ़ाइल नाम जिनमें केवल शामिल हैं .. दर सीमा

सबमिट करें, दावा करें, URL बदलें, होस्टिंग और परिनियोजन सभी प्लेटफ़ॉर्म के एक टोकन पर GitHub तक पहुंचें, इसलिए कुल मिलाकर वे प्रति खाता प्रति मिनट 10 अनुरोधों तक सीमित हैं (429, साथ Retry-After). एक ऑपरेटर इसे एक खाते के लिए जुटा सकता है।

होस्टिंग सक्षम करें

{ "enabled": true }

एक परिनियोजन पिन करें

PUT /api/v1/me/github-games/{id}/deployment → GameHostingView

{ "commit": "<sha or branch>" }

commit वैकल्पिक है. शा/शाखा कतारों को पिन करने से पुनः तैनाती होती है; मतदान GET /api/v1/me/github-games/{id}/deployment स्थिति के लिए.

यह उस गेम के लिए अस्वीकार कर दिया गया है जिसमें कोई रिपॉजिटरी (एक अपलोड किया गया बंडल) नाम नहीं है: एक कमिट पिन करना क्या है किसी गेम को उसके रिपॉजिटरी में ले जाता है, और बंडल-निर्मित गेम में कोई नहीं होता है। अपलोड किए गए गेम को पुनः परिनियोजित करना github.com लाने के बजाय वॉल्यूम पर अभी भी फ़ाइलों को सत्यापित करता है।

गेम को नए URL पर ले जाएं

PUT /api/v1/me/github-games/{id}/url

{ "repoUrl": "https://github.com/you/new-repo", "displayName": "optional for a hosted URL" }

पंक्ति जीवित रहती है - uid, <uid>.starhermit.com, खेलने का समय, रेटिंग्स - और से पुनः तैनात किया गया है गंतव्य. जीथब गंतव्य ऐसा होना चाहिए जिससे कॉल करने वाला यह साबित कर सके कि वे इसे नियंत्रित करते हैं (403 अन्यथा), और उसके starhermit.txt ए का नाम नहीं लेना चाहिए अलग owner= (403). एक स्क्रिप्टेड या कंटेनर बैकएंड तब तक अक्षम है जब तक कि गंतव्य इसे घोषित न कर दे।

लाइव सत्र (मालिक)

GET /api/v1/me/github-games/{id}/sessions गेम के सर्वर के सक्रिय सत्रों को सूचीबद्ध करता है। DELETE .../sessions/{sessionId} प्लेटफ़ॉर्म परित्याग पथ के माध्यम से एक समाप्त होता है (कोई विजेता नहीं, नहीं एलो, कारण operator_ended). इससे अटके हुए सत्र की क्षमता वाली सीट वापस आ जाती है।

लीडरबोर्ड और उपलब्धियाँ (मालिक)

किसी गेम का स्वामी उसका प्रकाशक होता है: आप बना सकते हैं लीडरबोर्ड और उपलब्धियों इसके लिए के अंतर्गत /me/github-games/{id}/leaderboards और /achievements बिना प्रकाशक खाते के. केवल आपके गेम का सर्वर उन्हें लिखता है, इसलिए गेम को इसकी आवश्यकता है server= स्क्रिप्ट या container.image= बैकएंड - एक ब्राउज़र-केवल गेम मिलता है 409. देखना लीडरबोर्ड, उपलब्धियों और यह ट्यूटोरियल.

  • स्थानीय फ़ोल्डर से जोड़े गए गेम के लिए, repoUrl एक सिंथेटिक है upload:<id> मार्कर और ownerLogin/repoName खाली हैं - नाम के लिए कोई भंडार नहीं है, और एक खाली मालिक ही सूची को दावा योग्य नहीं बनाता है।
  • coverArtSource है "upload", "manifest" या null, और coverArtUpdatedAt वह समय है जब वह कवर आखिरी बार बदला गया था - इसका उपयोग कैश-बस्ट करने के लिए करें /cover यूआरएल. कुछ भी गैर-शून्य का मतलब है कि खेल में लाने के लिए कवर कला है; null मतलब वापस गिरना /icon. दोनों स्रोत समान नहीं हैं: एक अपलोड हमेशा जीतता है, और यह एकमात्र है DELETE /cover हटा सकते हैं.
  • description प्रकट का विवरण है, या null. releaseNotesUpdatedAt वह समय है जब रिलीज़ नोट अंतिम होते हैं बदला हुआ पाठ (null जब खेल में कुछ भी न हो)। समान नोटों को पुनः तैनात करने से यह स्थानांतरित नहीं होता है, इसलिए इसे चलाना सुरक्षित है "नया क्या है" बैज: खिलाड़ी द्वारा अंतिम बार देखे गए मूल्य को याद रखें और तुलना करें। नोट स्वयं सूची में नहीं हैं; देखना विवरण और रिलीज़ नोट्स.
  • SharedGitHubGameDto का विस्तार GitHubGameDto साथ submittedByUserId और submittedByUsername.

अपना खुद का गेम प्रकाशित करें: वॉकथ्रू

इसमें दो मार्ग हैं। यदि आपका गेम गिट रिपॉजिटरी में रहता है, तो नीचे दिए गए चरणों का पालन करें। यदि यह आपकी मशीन पर सिर्फ एक फ़ोल्डर है, तो एक कॉल यह सब कर देती है: स्थानीय फ़ोल्डर से गेम जोड़ें खेल को पंजीकृत करता है, प्रकाशित करता है फ़ाइलें, और इसे लाइव छोड़ देता है - कोई होस्टिंग टॉगल नहीं और कोई कमिट पिन नहीं, क्योंकि इसमें कोई रिपॉजिटरी नहीं है ट्रैक.

  1. एक स्रोत चुनें: एक रेपो युक्त पुश करें starhermit.txt मूल पर (वैकल्पिक रूप से या तो a घोषित करना)। server.js स्क्रिप्ट या कंटेनर छवि), या पहले से होस्ट किए गए ब्राउज़र गेम का सार्वजनिक यूआरएल तैयार करें।
  2. अपनी GitHub पहचान लिंक करें OAuth प्रवाह के माध्यम से (देखें auth.md); के साथ सत्यापित करें GET /api/v1/me/github.
  3. खेल को पंजीकृत करें: POST /api/v1/me/github-games रिपॉजिटरी या होस्टेड-गेम यूआरएल के साथ repoUrl.
  4. केवल रिपॉजिटरी गेम - होस्टिंग सक्षम करें: PUT /api/v1/me/github-games/{id}/hosting साथ { "enabled": true }.
  5. केवल रिपॉजिटरी गेम - एक कमिट पिन करें: PUT /api/v1/me/github-games/{id}/deployment साथ { "commit": "<sha>" }. पिन किया गया कमिट लाइव संस्करण को नियंत्रित करता है।
  6. खिलाड़ी गेम लॉन्च करते हैं: एक तैनात रिपॉजिटरी गेम यहां परोसा जाता है <slug>.starhermit.com; प्रत्यक्ष रूप से होस्ट किया गया गेम अपना सबमिट किया गया URL खोलता है। ए के साथ हर खेल gameSlug - बैकएंड या नहीं - से एक लॉन्च टोकन प्राप्त होता है POST /api/v1/games/<slug>/launch-token यूआरएल खंड में (वैकल्पिक रूप से &session_id=<guid> डीप-लिंक आमंत्रित करने के लिए)।

पूर्ण क्लाइंट-साइड अनुबंध के लिए - गेम लॉन्च टोकन को कैसे पढ़ता है और एपीआई से बात करता है - देखें शतरंज का पूर्वाभ्यास संदर्भ कार्यान्वयन का.
