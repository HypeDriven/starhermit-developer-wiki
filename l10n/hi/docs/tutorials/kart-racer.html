ट्यूटोरियल: एक मल्टीप्लेयर कार्ट रेसर बनाएं

यह ट्यूटोरियल एक आर्केड कार्ट रेसर की मल्टीप्लेयर परत बनाता है - आठ कार्ट तक, निजी दोस्तों के साथ लॉबी, अजनबियों के साथ जल्दी-जल्दी जुड़ना, सीपीयू ड्राइवर खाली ग्रिड स्लॉट भरना, उलटी गिनती, लैप्स, एक फिनिशिंग ऑर्डर और उपलब्धियां - स्टारहर्मिट एपीआई पर। इसमें नेटकोड अनुबंध शामिल है और प्लेटफ़ॉर्म कॉल करता है; आपका इंजन, ट्रैक आर्ट और हैंडलिंग मॉडल आपका अपना है।

यहां सब कुछ गेम-विशिष्ट है - द grand-prix कतार, बाइनरी फ्रेम लेआउट, आइटम बटन, भौतिकी स्थिरांक - एक उदाहरण मान है। केवल समापन बिंदु, फ़्रेम लिफ़ाफ़े और सीमाएँ हैं प्लेटफ़ॉर्म व्यवहार, और प्रत्येक उसके संदर्भ पृष्ठ से लिंक करता है।

1. एक वास्तुकला चुनें

सर्वर टिक बजट के लिए रेसर गेम का सबसे कठिन आकार है: कार्ट तेजी से चलते हैं, टकराते हैं, और खिलाड़ियों को 50 एमएस का स्टीयरिंग लैग महसूस होता है। StarHermit आपको इसे चलाने के दो तरीके देता है, दोनों एक से शुरू होते हैं वास्तविक समय कक्ष:

A. होस्ट-रूटेड बी. सर्वर-आधिकारिक स्क्रिप्ट
अनुकरण कौन करता है रूम होस्ट का ग्राहक, किसी भी दर पर इसे पसंद करता है (60 हर्ट्ज+) आपका server= स्क्रिप्ट, ज़्यादा से ज़्यादा 30 हर्ट्ज
परिवहन बाइनरी फ़्रेम चालू ws/v1/realtime JSON cmd/game फ़्रेम चालू ws/v1/games
बेईमानी करना मेज़बान पर भरोसा है ग्राहकों के पास शून्य अधिकार है
एलो, स्क्रिप्ट उपलब्धियाँ नहीं (मेजबान एक क्लैंप्ड परिणाम पोस्ट करता है) हाँ - eloUpdates, achievements, रिप्ले
के लिए सर्वोत्तम दोस्तों के साथ आकस्मिक दौड़, पूर्ण निष्ठा भौतिकी सरल आर्केड भौतिकी के साथ रैंक वाली रेसिंग

के साथ शुरू A जब तक आपको रैंक वाले खेल की आवश्यकता न हो; धारा 7 दिखाती है कि किस लिए परिवर्तन होता है B. A कंटेनर सर्वर आठ-कार्ट भी चला सकते हैं कमरे में बंद दौड़ और आधिकारिक तौर पर 60 हर्ट्ज़ पर अनुकरण करें। इसका प्रत्यक्ष गेम्स एपीआई मैचमेकिंग वर्तमान में एक अंतर्निहित 1v1 का उपयोग करता है कतार, इसलिए बड़े ग्रिड के लिए रीयलटाइम रूम का उपयोग करें। प्लेटफ़ॉर्म कंटेनर के लूप को स्टेप नहीं करता है।

2. प्रकट होना

इसके साथ वितरण योग्य बिल्ड फ़ोल्डर प्रकाशित करें starhermit.txt इसके मूल में (देखें) प्रकट). control.* लाइनें खिलाड़ियों को एक रिबाइंडिंग यूआई और आपका प्रदान करती हैं ग्राहक ए एपीआई को नियंत्रित करता है यहां से बाइंडिंग पढ़ने के लिए:

name=Turbo Hermits
launch=index.html
cover=art/cover.png
control.accelerate=KeyW+ArrowUp | Accelerate
control.brake=KeyS+ArrowDown | Brake / reverse
control.left=KeyA+ArrowLeft | Steer left
control.right=KeyD+ArrowRight | Steer right
control.drift=ShiftLeft+ShiftRight | Drift
control.item=Space | Use item

पथ A है नहीं server= रेखा। यदि कोई गेम एक स्क्रिप्ट भेजता है, तो एक कमरा शुरू करने से एक बाध्य सत्र बनता है और केवल स्क्रिप्ट ही मैच को समाप्त कर सकती है - मेज़बान की POST .../result दौड़ समाप्त होने का तरीका बंद हो जाता है (धारा 7).

3. साइन इन करें और मूल बातें पढ़ें

एक प्लेटफ़ॉर्म-होस्टेड गेम इसके साथ खोला जाता है #game_token=<jwt> यूआरएल में - इसे एक बार पढ़ें, इसे हटा दें history.replaceState, और इसकी 60 मिनट की समाप्ति से पहले इसे ताज़ा करें (विवरण यहां दिया गया है)। शतरंज का पूर्वाभ्यास और प्रमाणन). आपका स्लग टोकन है game_scope दावा (या location.hostnameका पहला लेबल); इसे कभी भी हार्ड-कोड न करें।

लोड होने पर, मेनू को जो चाहिए वह प्राप्त करें:

GET /api/v1/games/{slug}/controls     # effective key bindings (manifest defaults + overrides)
GET /api/v1/games/{slug}/settings     # camera, volume, last chosen kart — your own keys
GET /api/v1/realtime/rooms/mine       # 200 → the player is still in a race; rejoin it

इसके साथ मेनू विकल्प सहेजें PATCH /api/v1/games/{slug}/settings ({"settings":{"kart":"hermit-crab"}}). सेटिंग्स सभी मशीनों में प्लेयर का अनुसरण करती हैं और किसी घोषणा की आवश्यकता नहीं है।

4. लॉबी

ग्रांड प्रिक्स सभी के लिए निःशुल्क है, इसलिए कमरे में आठ सीटों वाली एक टीम है। ट्रैक, लैप गिनती और इंजन कक्षा अपारदर्शी में जाओ metadata:

POST /api/v1/realtime/rooms
Authorization: Bearer <launch token>

{ "teamCount": 1, "seatsPerTeam": 8, "backfillAfterSeconds": 45,
  "aiPlayers": 0, "name": "Friday cup", "isVisible": true,
  "metadata": { "track": "coral-loop", "laps": 3, "cc": 150 } }

लॉन्च टोकन के साथ कमरे का गेम टोकन से आता है, इसलिए gameSlug मिटाया जा सकता है। रचयिता सीट पर मेजबान है (0, 0). यहाँ से लॉबी साधारण कमरे की तरह बहती है:

  • दोस्त — POST /rooms/{id}/invites साथ {"toUserId": ...}. मंच उन्हें सूचित करता है; उन्हें सीटें स्वीकार करना. छः अक्षर दिखाओ joinCode ताकि मित्र भी इसे टाइप कर सकें POST /rooms/join-by-code.
  • अजनबी - मेज़बान कॉल करता है POST /rooms/{id}/open. बिना कमरे वाले खिलाड़ी कॉल करते हैं POST /rooms/quick-join साथ {"seats": 1} और पर 404, अपना खुद का बनाएं और खोलें।
  • ट्रैक वोट/मेजबान का मन परिवर्तन — PATCH /rooms/{id} नये के साथ metadata और कमरे का revision जैसा expectedRevision.
  • सीपीयू के विरुद्ध एकल - साथ बनाएं "aiPlayers": 7, तब POST /rooms/{id}/start.

जब सभी आठ सीटें भर जाती हैं तो एक खुला कमरा अपने आप शुरू हो जाता है backfillAfterSeconds गुजरता है; मेज़बान भी कर सकते हैं POST /rooms/{id}/start. प्रत्येक अभी भी खाली सीट एआई भागीदार बन जाती है - वे आपकी हैं सीपीयू ड्राइवर.

5. रेस सॉकेट (मेजबान-रूटेड)

जोड़ना

प्रत्येक प्रतिभागी एक-उपयोग टिकट के साथ रीयलटाइम सॉकेट खोलता है:

const { ticket } = await api.post("/api/v1/realtime/connection-tickets"); // { ticket, expiresIn }
const ws = new WebSocket(
  `wss://api.starhermit.com/ws/v1/realtime?roomId=${roomId}&ticket=${encodeURIComponent(ticket)}`);
ws.binaryType = "arraybuffer";

टेक्स्ट फ़्रेम JSON पुश और नियंत्रण फ़्रेम हैं; बाइनरी फ़्रेम गेमप्ले हैं। roster धक्का है आपका ग्रिड: शुरू होने के बाद यह जम गया है, एआई सीटें शामिल हैं। एक टीम के साथ, एक कार्ट का ग्रिड स्लॉट उसका होता है प्रतिभागी का slot.

ws.onmessage = (e) => {
  if (typeof e.data === "string") return onControl(JSON.parse(e.data)); // roster, presence, event, ready, chat, result
  const bytes = new Uint8Array(e.data);
  const sender = guidFromDotNet(bytes.subarray(0, 16)); // server-stamped, trustworthy
  onGameplay(sender, new DataView(e.data, 16));          // your payload starts at byte 16
};

// The server prefixes the sender's participant id in .NET GUID byte order:
// the first three groups are little-endian.
function guidFromDotNet(b) {
  const h = (i) => b[i].toString(16).padStart(2, "0");
  return `${h(3)}${h(2)}${h(1)}${h(0)}-${h(5)}${h(4)}-${h(7)}${h(6)}-` +
         `${h(8)}${h(9)}-${h(10)}${h(11)}${h(12)}${h(13)}${h(14)}${h(15)}`;
}

अपने पेलोड में कभी भी प्लेयर आईडी न रखें और उस पर भरोसा न करें - 16-बाइट उपसर्ग ही एकमात्र पहचान है जिसकी सर्वर गारंटी देता है.

रूटिंग और बजट

प्लेटफ़ॉर्म होस्ट-रूटेड प्ले के आकार को लागू करता है:

  • A अतिथि का बाइनरी फ्रेम पहुँचते हैं केवल मेजबान - वह इनपुट चैनल है।
  • मेज़बान का बाइनरी फ्रेम पहुँचते हैं हर मेहमान - वह स्नैपशॉट चैनल है।
  • प्रत्येक फ़्रेम अधिकतम है 8 केबी; प्रत्येक कनेक्शन भेज सकता है 30 संदेश/सेकंड (2× एक के लिए फट गया दूसरा). ऊपर जाने से सॉकेट बंद हो जाता है PolicyViolation.

तो मेजबान जो भी दर सही लगता है उस पर अनुकरण करता है (60 हर्ट्ज सामान्य है) लेकिन भेजता है स्नैपशॉट पर 20 हर्ट्ज़, और मेहमान 20 हर्ट्ज़ पर इनपुट भेजते हैं। यह कभी-कभार नियंत्रण फ्रेम के लिए हेडरूम छोड़ देता है।

फ़्रेम लेआउट (उदाहरण)

इनपुट, अतिथि → होस्ट, 7 बाइट्स:

ओफ़्सेट प्रकार मैदान
0 u8 1 = इनपुट
1 u16 seq - प्रत्येक प्रेषण में वृद्धि
3 i8 स्टीयर, −127…127
4 u8 गला घोंटना, 0…255
5 u8 बिट्स: 0 ब्रेक, 1 ड्रिफ्ट
6 u8 itemPresses - एक काउंटर, झंडा नहीं

itemPresses आइटम-बटन दबाने की चालू गिनती है। 20 हर्ट्ज़ पर 50 एमएस से छोटा प्रेस होगा अन्यथा नमूनों के बीच गिरना; एक काउंटर के साथ मेजबान प्रति वेतन वृद्धि एक आइटम फायर करता है, हालाँकि प्रेस उतरे.

स्नैपशॉट, होस्ट → अतिथि, 4 + 22 बाइट्स प्रति कार्ट (पूर्ण ग्रिड के लिए 176 बाइट्स):

ओफ़्सेट प्रकार मैदान
0 u8 2 = स्नैपशॉट
1 u16 होस्ट टिक
3 u8 कार्ट गिनती
प्रति कार्ट u8, f32 ×4, u8, u16, u8, u8 स्लॉट, एक्स, जेड, हेडिंग, स्पीड, लैप, चेकपॉइंट, आइटम, झंडे

अतिथि अन्य कार्ट प्रस्तुत करते हैं ~ 100 एमएस अतीत में, दो स्नैपशॉट के बीच अंतरवेश उस समय को ब्रैकेट करें, और अपने इनपुट से स्थानीय रूप से अपने स्वयं के कार्ट की भविष्यवाणी करें, जिससे मेजबान की ओर आसानी हो स्थिति जब वे असहमत हों। अंतिम इनपुट शामिल करें seq होस्ट ने प्रति कार्ट लागू किया flags या एक यदि आप सटीक मिलान चाहते हैं तो अतिरिक्त फ़ील्ड।

उलटी गिनती, दौड़ प्रतियोगिताएं, समापन

नियंत्रण फ़्रेम JSON हैं, अधिकतम 4 KB, और सर्वर स्टैम्प from प्रेषक की प्रतिभागी आईडी के साथ:

  • मेहमान भेजते हैं {"type":"ready"} एक बार ट्रैक लोड हो गया।
  • होस्ट प्रत्येक कनेक्टेड मानव के तैयार होने (या टाइमआउट) की प्रतीक्षा करता है, फिर भेजता है {"type":"event","kind":"countdown","goInMs":3000}. मेहमान अपनी स्थानीय उलटी गिनती शुरू करते हैं रसीद - इस परिशुद्धता पर कोई घड़ी सिंक की आवश्यकता नहीं है।
  • अन्य रेस बीट भी हैं event फ़्रेम: {"kind":"lap","slot":3,"lap":2}, {"kind":"finished","slot":3,"place":1,"timeMs":94210}.
  • chat सभी के लिए उपलब्ध है, लेकिन मेहमानों के लिए प्रति मिनट 10 नियंत्रण फ़्रेम तक सीमित हैं - जो कि बहुत है ready और कुछ "जीजी"s, गेमप्ले के लिए नहीं।

जब अंतिम मानव रेखा पार कर जाता है (या विजेता के समाप्त होने के बाद एक टाइमर), तो मेज़बान सबमिट कर देता है परिणाम, जो कमरे को बंद कर देता है और धक्का देता है {"type":"result"} सबके लिए:

POST /api/v1/realtime/rooms/{id}/result

{ "teamScores": [0],
  "metadata": { "track": "coral-loop",
                "order": [ { "slot": 3, "timeMs": 94210 }, { "slot": 0, "timeMs": 95002 } ],
                "bestLapMs": 30112 } }

teamScores प्रति टीम बिल्कुल एक प्रविष्टि की आवश्यकता है (0-50 तक सीमित), जिसमें कुछ भी उपयोगी नहीं है सभी के लिए मुफ़्त; अंतिम क्रम रहता है metadata. एक टीम दौड़ के साथ एक ही कमरा है teamCount: 2 और प्रत्येक टीम के अंक teamScores.

सीपीयू ड्राइवर, लीवर और होस्ट परिवर्तन

  • ड्राइव करने के लिए AI सीटें आपकी हैं। प्लेटफ़ॉर्म सीट आरक्षित करता है और ड्राइवर का नाम बताता है; मेज़बान का सिमुलेशन इसे चलाता है (कुछ रबर-बैंडिंग के साथ चौकियों के माध्यम से एक रेसिंग लाइन)।
  • एक अतिथि जो दौड़ के बीच में ही चला जाता है (POST /rooms/{id}/leave) उनके कार्ट को ग्रिड पर रखता है: रोस्टर पुश उसी प्रतिभागी को दिखाता है id अब isAi: true, और होस्ट का सीपीयू उस कार्ट पर कब्ज़ा कर लेता है।
  • एक मेहमान जो छोड़ता है अभी भी कमरे में है; उनके कार्ट को चालू रखें और उन्हें पुनः कनेक्ट होने दें - नवीनतम सॉकेट पुराने सॉकेट का स्थान ले लेता है।
  • यदि मेज़बान चला जाए, मेज़बान की भूमिका सबसे लंबे समय तक जुड़े रहने वाले शेष मानव के पास चली जाती है रोस्टर पुश नया दिखाता है isHost. प्रत्येक अतिथि के पास पहले से ही नवीनतम पूर्ण स्नैपशॉट है, इसलिए नया होस्ट इससे सिमुलेशन फिर से शुरू करता है और स्नैपशॉट भेजना शुरू करता है; अतिथि इनपुट अब उन तक पहुंच रहे हैं। होस्ट माइग्रेशन आपके कोड का काम है - प्लेटफ़ॉर्म केवल भूमिका को आगे बढ़ाता है।
  • यदि होस्ट बस डिस्कनेक्ट हो जाता है, होस्ट सॉकेट के बिना कमरा 60 सेकंड के बाद बंद हो जाता है।

6. दौड़ के आसपास

  • आवाज और बातचीत. प्रत्येक अतिथि पहले से ही कर सकता है chat रीयलटाइम सॉकेट पर; आवाज के लिए, देखें आवाज़.
  • दोबारा मैच करें. नतीजे के बाद कमरा बंद है. मेज़बान से एक नया कमरा बनाने और आमंत्रित करने को कहें पिछले रोस्टर के इंसान, या सभी को शीघ्र-ज्वाइन पर वापस भेज दें।
  • लैप-टाइम लीडरबोर्ड। किसी गेम का प्लेटफ़ॉर्म लीडरबोर्ड उसका एलो बोर्ड होता है, जो केवल एक सर्वर द्वारा लिखा जाता है रनटाइम. प्रकाशक द्वारा परिभाषित लीडरबोर्ड स्वीकार करता है POST /api/v1/leaderboards/{id}/submit, लेकिन वह ग्राहक द्वारा स्कोर का दावा किया जाता है - एक दोस्ताना समय परीक्षण के लिए ठीक है, पुरस्कार वाली किसी भी चीज़ के लिए नहीं।

7. वेरिएंट बी: सर्वर-आधिकारिक रेसिंग

रैंक किए गए खेल के लिए, सिमुलेशन को एक स्क्रिप्ट में ले जाएं। लॉबी अपरिवर्तित है; स्क्रिप्ट जोड़ें और मेनिफेस्ट में मिलान सेटिंग:

server=server.js
matchmaking.max_wait_seconds=20
matchmaking.ai_players=7

अब दो चीज़ें दौड़ पैदा करती हैं: एक कमरा शुरू करना अपने मनुष्यों के लिए एक कमरे में बंद सत्र बनाता है, और मंगनी करना (POST /api/v1/games/{slug}/matchmaking?queue=grand-prix) आठ होने पर एक बनाता है खिलाड़ी मिल जाते हैं - या, उपरोक्त सेटिंग्स के साथ, 20 सेकंड के बाद सीपीयू सात तक खाली हो जाते हैं सीटें. दोस्तों की एक लॉबी एक साथ कतार में लग सकती है POST /realtime/rooms/{id}/matchmake.

किसी भी तरह, ग्राहक इसे लेते हैं sessionId (कमरे का gameSessionId, या मिलान टिकट) और फिर से खेलना ws/v1/games?sessionId=…. रियलटाइम सॉकेट, यदि कोई हो, केवल रोस्टर के लिए रखा जाता है।

लिपि

संपूर्ण अनुकरण चलता है onTick 30 हर्ट्ज़ छत पर। प्रत्येक आह्वान एक ताज़ा सैंडबॉक्स है मिलता है sessionState अंदर और इसे वापस लौटाता है, इसलिए उस स्थिति को छोटा रखें - यह हर टिक को क्रमबद्ध करता है।

const TRACK = { laps: 3, radius: 14,
  checkpoints: [[0, 0], [120, 0], [160, 60], [120, 120], [0, 120], [-40, 60]] };

globalThis.game = {
  tickRateHz: 30,
  replays: true,
  queues: [{ key: "grand-prix", teams: 8, teamSize: 1 }],
  achievements: [
    { key: "chequered-flag", name: "Chequered Flag", description: "Win a race.", points: 10 }
  ],

  createSession(ctx) {
    const karts = racers(ctx).map((r, i) => ({
      id: r.id, name: r.name, ai: r.ai, x: -8 * (i % 2), z: -6 * i, heading: 0, speed: 0,
      cp: 1, lap: 0, boost: 0, boosts: 1, input: {}, ack: 0, finishedAt: null
    }));
    return { ok: true, sessionState: { t: ctx.now, goAt: ctx.now + 4000, karts, order: [] } };
  },

  onPlayerMessage(ctx) {                       // durable commands: discrete actions
    const s = copy(ctx.sessionState);
    const k = s.karts.find((k) => k.id === ctx.message.from);
    if (ctx.message.data?.type === "use-item" && k && k.boosts > 0 && ctx.now >= s.goAt) {
      k.boosts--; k.boost = 1.2;
    }
    return { ok: true, sessionState: s };
  },

  onTick(ctx) {
    const s = copy(ctx.sessionState);
    const dt = Math.min(Math.max((ctx.now - s.t) / 1000, 0), 0.1);
    s.t = ctx.now;
    for (const i of ctx.inputs || []) {        // latest realtime input per player since last tick
      const k = s.karts.find((k) => k.id === i.from);
      if (k) { k.input = i.data; k.ack = Math.max(k.ack, Math.floor(+i.data.seq) || 0); }
    }
    if (ctx.now >= s.goAt) {
      for (const k of s.karts) {
        if (k.finishedAt) continue;
        move(k, k.ai ? aiInput(k) : k.input, dt);   // pure motion — shared with the client
        progress(k, s, ctx);                        // checkpoints, laps, finish — server only
      }
    }
    const snap = s.karts.map((k) =>
      [k.id, r2(k.x), r2(k.z), r3(k.heading), r2(k.speed), r2(k.boost), k.lap, k.cp, k.ack]);
    const out = { ok: true, sessionState: s,
      broadcast: [{ to: "all", data: { type: "snap", t: s.t, goAt: s.goAt, karts: snap } }] };
    if (raceOver(s, ctx)) Object.assign(out, finish(s, ctx));
    return out;
  }
};

मददगार साधारण गेम कोड हैं। प्लेटफ़ॉर्म जिन भागों की परवाह करता है:

  • racers(ctx) सत्र की शुरुआत चाहे जो भी हो, ग्रिड को पढ़ता है: ctx.room.roster एक के लिए कमरा (एआई सीटें हैं userId: null, तो उन्हें इस तरह की आईडी दें ai-0-5), ctx.matchmaking.seats एक के लिए मैचमेड रेस (सीटें छोड़ें id: null), अन्य ctx.players.
  • move(k, input, dt) अवश्य प्रत्येक इनपुट मान को क्लैंप करें — steer से −1…1, throttle से 0…1-- क्योंकि ctx.inputs[].data ग्राहक ने जो कुछ भी भेजा है। केवल from भरोसा किया जाता है. इसे शुद्ध रखें - नहीं ctx, कोई सत्र स्थिति नहीं - इसलिए ग्राहक इसे भी चला सकता है (देखें)। ग्राहक-पक्ष भविष्यवाणी).
  • यादृच्छिकता और समय से आते हैं ctx.random और ctx.now; कोई नहीं है Date या Math.random.
  • finish(s, ctx) रिटर्न result (जो सत्र समाप्त करता है और, एक कमरे के लिए, इसे बंद कर देता है), achievements विजेता के लिए यदि मानव, और eloUpdates मानव रेसरों के लिए - उदाहरण के लिए जोड़ीदार अंतिम क्रम में एलो, से पढ़ें और वापस लिखें ctx.playerStates. एआई सीटें नहीं हो सकतीं खिलाड़ी की स्थिति, रेटिंग या उपलब्धियाँ प्राप्त करें।
  • raceOver उन जातियों को भी ख़त्म करना चाहिए जिन्हें कोई ख़त्म नहीं कर सकता - हर इंसान के अनुसार चला गया ctx.presence (कमरे), या एक कठिन समय सीमा।
  • रिप्ले केवल रखें अंतिम sessionState. एक कॉम्पैक्ट लैप-टाइम टेबल और फिनिशिंग रखें इसमें ऑर्डर करें, प्रति-टिक स्थिति लॉग नहीं।

ग्राहक

हर टिक पर रियलटाइम इनपुट के रूप में स्टीयरिंग भेजें और टिकाऊ कमांड के रूप में अलग-अलग क्रियाएं करें:

// ~30 Hz: latest-wins, batched into the next onTick
send({ type: "cmd", data: { type: "input", realtime: true, seq: ++seq,
                            steer, throttle, brake, drift } });

// on key press: a durable command, runs onPlayerMessage immediately
send({ type: "cmd", data: { type: "use-item" } });

सामान अवश्य एक टिकाऊ आदेश से गुजरें। रीयलटाइम इनपुट टिकों के बीच नवीनतम जीत हैं, और प्लेटफ़ॉर्म केवल एक-शॉट फ़ील्ड को सुरक्षित रखता है pass, tackle और shoot जब एक नया नमूना पुराने को प्रतिस्थापित करता है - रीयलटाइम इनपुट में किसी भी अन्य बटन को टिक से पहले ओवरराइट किया जा सकता है इसे देखता है.

achievement फ़्रेम एक ही सॉकेट पर आते हैं; पढ़ना GET /api/v1/games/{slug}/achievements पर खुलने से पहले दी गई किसी भी चीज़ के लिए लोड करें।

ग्राहक-पक्ष भविष्यवाणी

केवल वही प्रस्तुत करना जो सर्वर भेजता है, कार्ट को ऐसा महसूस कराता है जैसे उसे कीचड़ में चलाया गया हो। एक स्टीयरिंग परिवर्तन को सर्वर तक पहुंचना होगा, अगले टिक की प्रतीक्षा करनी होगी (30 हर्ट्ज पर 33 एमएस तक), और वापस आना होगा snap - 80 एमएस पिंग पर जो कार्ट घूमने से पहले 100 एमएस से अधिक है। भविष्यवाणी यह छिपाती है: ग्राहक चलता है इसका अपना कार्ट तुरंत और प्रत्येक का इलाज करता है snap सुधार के रूप में, चित्र के रूप में नहीं।

मोशन कोड साझा करें

सिमुलेशन को उपरोक्त स्क्रिप्ट की तरह विभाजित करें: एक शुद्ध move(k, input, dt) संभालने के लिए, और केवल सर्वर progress चौकियों, लैप्स और फिनिशिंग के लिए। मोशन कोड को उजागर करें server.js दूसरे वैश्विक के रूप में - शतरंज जिस पैटर्न का उपयोग करता है globalThis.chessRules - और उसी फ़ाइल को इसमें लोड करें ब्राउज़र:

// server.js — shared by the platform's sandbox and the browser
function move(k, input, dt) { /* clamp input, integrate speed, heading, x, z, boost */ }
globalThis.kartPhysics = { move, TRACK };
globalThis.game = { /* ... as above ... */ };

<script src="server.js"></script>  <!-- defines kartPhysics; the client never calls game.* -->

ग्राहक भविष्यवाणी करता है केवल गति. अंतराल, स्थिति, आइटम और अंतिम क्रम सर्वर का रहता है बुलाओ. बिट-समान परिणामों की अपेक्षा न करें: सैंडबॉक्स और ब्राउज़र अंतिम बिट्स में असहमत हो सकते हैं Math.sin/Math.cos, और पदों में snap गोलाकार हैं. मेल-मिलाप उस बहाव को सोख लेता है।

सर्वर की लय पर कदम रखें

सर्वर प्रति इनपुट एक चरण नहीं चलता है। प्रत्येक टिक यह लागू होता है नवीनतम यह इनपुट को धारण करता है वह कार्ट, नया आने तक इसका उपयोग करता रहता है, और उसके बाद से वास्तविक समय में एकीकृत हो जाता है पिछला टिक. इसलिए डिस्प्ले फ़्रेम दर पर कदम बढ़ाने के बजाय उस आकार को प्रतिबिंबित करें:

const pending = [];                              // inputs the server hasn't acknowledged yet
let seq = 0, predicted, previous;               // { x, z, heading, speed, boost }, seeded from the first snap
let error = { x: 0, z: 0, heading: 0 };          // visual offset, decays in render()

setInterval(() => {                              // 30 Hz, the script's tickRateHz
  if (!predicted || serverNow() < goAt) return;  // the server ignores movement before goAt
  const input = { steer: readSteer(), throttle: readThrottle(), brake: held("brake"), drift: held("drift") };
  const entry = { seq: ++seq, input, dt: 1 / 30 };
  send({ type: "cmd", data: { type: "input", realtime: true, seq: entry.seq, ...input } });
  pending.push(entry);
  previous = { ...predicted };
  kartPhysics.move(predicted, input, entry.dt);  // the kart responds now, not a round trip later
}, 1000 / 30);

टिक दर से अधिक तेजी से भेजना व्यर्थ है - प्रति टिक केवल नवीनतम इनपुट का उपयोग किया जाता है - और प्लेटफ़ॉर्म रीयलटाइम इनपुट को अपनी प्रति-कनेक्शन सीमा से ऊपर छोड़ देता है।

हर बात पर सामंजस्य बिठाएं snap

स्क्रिप्ट गूँजती है ack, उच्चतम seq इसने प्रत्येक कार्ट के लिए आवेदन किया है। सभी के ऊपर snap, अपने को रिवाइंड करें सर्वर की स्थिति पर कार्ट करें और जो सर्वर ने अभी तक नहीं देखा है उसे दोबारा चलाएं:

function onSnap(snap) {
  const [, x, z, heading, speed, boost, lap, cp, ack] = snap.karts.find((k) => k[0] === myId);
  while (pending.length && pending[0].seq <= ack) pending.shift();   // applied or superseded

  const corrected = { x, z, heading, speed, boost };
  for (const p of pending) kartPhysics.move(corrected, p.input, p.dt);

  if (!predicted) { predicted = corrected; previous = { ...corrected }; return; } // first snap
  error.x += predicted.x - corrected.x;          // what the player would see jump
  error.z += predicted.z - corrected.z;
  error.heading += predicted.heading - corrected.heading;
  if (Math.hypot(error.x, error.z) > 3) error = { x: 0, z: 0, heading: 0 }; // wall hit, bump: snap
  predicted = corrected;
  hud.lap = lap; hud.checkpoint = cp;            // progress is never predicted
}

तक सब कुछ त्याग देना ack सही है भले ही नवीनतम-जीत कुछ इनपुट छोड़ देता है: एक छोड़ दिया गया सर्वर टिक करने से पहले इनपुट को हटा दिया गया था, इसलिए इसने सर्वर के कार्ट को कभी भी प्रभावित नहीं किया।

सुचारू सुधार, फ्रेम दर पर प्रस्तुत करना

छोटे सुधार अदृश्य होने चाहिए. कार्ट को पूर्वानुमानित स्थिति के साथ-साथ एक क्षयकारी स्थान पर ड्रा करें त्रुटि ऑफसेट, और पिछले दो 30 हर्ट्ज भविष्यवाणी चरणों के बीच इंटरपोलेट करें ताकि 60 या 144 हर्ट्ज डिस्प्ले हो सुचारू रूप से चलता है:

function render(frameDt) {
  const decay = Math.exp(-frameDt / 0.1);        // ~100 ms to absorb a correction
  error.x *= decay; error.z *= decay; error.heading *= decay;
  const a = sinceLastStep() * 30;                // 0…1 between prediction steps
  drawKart(lerp(previous.x, predicted.x, a) + error.x,
           lerp(previous.z, predicted.z, a) + error.z,
           lerpAngle(previous.heading, predicted.heading, a) + error.heading);
}

क्षय के बजाय स्नैप थ्रेशोल्ड को ट्यून करें: कार्ट लंबाई से बड़ा सुधार वास्तविक है घटना (एक उछाल जिसकी आपने भविष्यवाणी नहीं की थी) और धीमी स्लाइड की तुलना में त्वरित स्नैप के रूप में बेहतर ढंग से पढ़ता है।

जानिए क्या भविष्यवाणी नहीं करनी चाहिए

  • अन्य कार्ट. वे अतीत में ~100 एमएस खींचे गए हैं (बफर)। snaps और के बीच प्रक्षेप करें दो वह कोष्ठक serverNow() - 100), इसलिए उनके विरुद्ध भविष्यवाणी की गई टक्कर एक टक्कर है वे कहाँ थे. दीवारों और ट्रैक का अनुमान लगाएं - वे हिलते नहीं हैं - और सर्वर को समाधान करने दें कार्ट-टू-कार्ट बम्प्स। सुधार एक राउंड ट्रिप के भीतर आता है। यदि बफ़र सूख जाता है, तो एक्सट्रपलेशन करें गति और दिशा से ~100 एमएस तक, फिर रुकें।
  • सामान। use-item एक टिकाऊ कमांड है, इसलिए यह चलता रहता है onPlayerMessage जैसे ही यह आता है - कोई टिक नहीं रुको. कुंजी दबाने पर लौ और ध्वनि बजाएं; गति को आने दो सुलह, तब से boost में है snap. यदि सर्वर मना कर देता है (कोई शुल्क नहीं बचा है), तो अगला snap इसे वापस रोल करता है.
  • जाति अवस्था. लैप गिनती, स्थिति और समापन से आते हैं snap और केवल आपकी स्क्रिप्ट का प्रसारण होता है।

सर्वर घड़ी का अनुमान लगाएं

snap.t और goAt सर्वर समय हैं (ctx.now). सबसे छोटे देखे गए अंतर से ऑफसेट रखें, जो धीमी डिलीवरी को फ़िल्टर करता है:

let offset = Infinity;
function noteSnap(snap) { offset = Math.min(offset, performance.now() - snap.t); }
const serverNow = () => performance.now() - offset;

से उलटी गिनती शुरू करें goAt, और उस पर गेट भविष्यवाणी जैसा कि ऊपर लूप करता है। एक कार्ट जो चलती है पहले goAt स्थानीय स्तर पर रबर-बैंड से पहले ग्रिड में वापस लाया जाता है snap शुरुआत के बाद.

यह सब समायोजित करने के लिए, विकास में कृत्रिम विलंबता (विलंब) जोड़ें send और onSnap 100-200 एमएस तक) और प्रत्येक सुधार का आकार लॉग करें - स्थिर बड़े सुधार का मतलब है move से भटक गया है सर्वर की प्रतिलिपि, या इनपुट फ़ील्ड को प्रत्येक तरफ अलग-अलग क्लैंप किया जा रहा है।
