认领其他人添加的游戏

如果有人已经将您的公共 GitHub 游戏添加到 StarHermit，您无需创建 第二次上市。声明现有列表成为其经过验证的所有者并管理其元数据， 托管、部署、服务器后端和未来的传输。

声明受到存储库控制的保护。仅仅知道游戏 ID 或存储库 URL 是不够的。 您必须通过以下两种方式之一证明控制权：

  1. 链接拥有该存储库的个人 GitHub 帐户；或者
  2. 将您的不可变 StarHermit 用户 ID 提交为 owner= 在存储库的 starhermit.txt.

第二种方法对于组织拥有的存储库特别有用，因为当前 GitHub 登录检查与个人存储库所有者相匹配，并且不会推断组织成员身份。

声明发生了什么变化

索赔成功：

  • 保留现有游戏/列表 ID 及其累积历史记录；
  • 将列表的管理 StarHermit 用户更改为您；
  • 将列表标记为 isVerifiedOwner: true;
  • 刷新可信元数据和控制 starhermit.txt 如适用；
  • 提供或刷新已声明的脚本/容器后端；
  • 启用可用的平台托管并将部署排队为 pending;
  • 删除最初提交该列表的人员的管理权限。

声明不会让之前的提交者访问您的 GitHub 帐户，并且不会合并 StarHermit 用户帐户。它转移该特定列表的管理。

开始之前

您需要：

  • StarHermit 帐户和完整的用户访问令牌，而不是游戏范围的启动令牌。
  • 如果使用的话，可以对存储库进行写访问 owner= 证明方法。
  • 现有的 StarHermit 列表 ID。
  • 对于克隆存储库游戏，有效的 starhermit.txt 在存储库根目录下。

仅有的 github.com/<owner>/<repo> 存储库及其 GitHub Pages 站点参与此声明 流动。任意托管 URL 没有可证明的 GitHub 存储库所有权，因此无法声明这一点 方式。

下面的例子使用：

API=https://api.starhermit.com
ACCESS_TOKEN='your-full-user-access-token'
OWNER='your-github-login'
REPO='your-game-repository'

访问令牌持续 15 分钟。如果即将过期，请在开始之前刷新您的。

第1步：找到现有的列表

列出共享游戏：

curl -sS "$API/api/v1/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

每个项目都包含不可变的列表 id, 归一化 repoUrl, ownerLogin, repoName, 的 当前提交者和所有权状态：

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "isVerifiedOwner": false,
  "submittedByUserId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "submittedByUsername": "someone-else"
}

两者都匹配 ownerLogin 和 repoName;不要仅仅因为游戏的显示名称是而选择游戏 类似。和 jq:

GAME_ID=$(
  curl -sS "$API/api/v1/github-games" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r --arg owner "$OWNER" --arg repo "$REPO" \
    '.[] | select((.ownerLogin | ascii_downcase) == ($owner | ascii_downcase)
               and (.repoName | ascii_downcase) == ($repo | ascii_downcase)) | .id' |
  head -n1
)

printf 'Listing ID: %s\n' "$GAME_ID"

如果结果为空则停止。请勿使用从不相关列表中复制的 ID 致电索赔。

第2步：选择如何证明所有权

选项 A：链接存储库所有者的 GitHub 帐户

当存储库由您的个人 GitHub 登录名直接拥有时，请使用此选项。

从 StarHermit 的帐户/设置流程中，启动 GitHub OAuth 关联 模式，同时登录 应该管理游戏的 StarHermit 帐户。链接与意外创建链接不同 使用 GitHub 登录的第二个 StarHermit 帐户。

API 流程开始于：

GET /api/v1/auth/oauth/github/authorize?link=true

它是浏览器驱动的并使用短期状态 cookie。链接需要最近的 StarHermit 认证。在启动它的同一浏览器会话中完成 GitHub 授权。

验证结果：

curl -sS "$API/api/v1/me/github" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

预期的：

{ "linked": true, "login": "octocat" }

返回的登录名必须与现有列表匹配 ownerLogin，不区分大小写。个人的 GitHub 登录并不能证明拥有该存储库的组织的成员资格。对于一个 组织拥有的存储库，请使用选项 B。

选项B：添加 owner= 到 starhermit.txt

这证明了控制力，因为只有能够发布存储库内容的人才能增加价值。 放 owner 到您不可变的 StarHermit 用户 ID (UUID)， 不是 您的用户名或昵称。

获取您的身份证：

STARHERMIT_USER_ID=$(
  curl -sS "$API/api/v1/me" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r '.id'
)

在存储库根目录中，创建或更新 starhermit.txt:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

将示例所有者替换为 STARHERMIT_USER_ID。不要将您的用户名或昵称放在这里； 这些可以改变，而用户 ID 是稳定的所有权标识符。

对于一款权威游戏，只保留一个后端声明：

# JavaScript runtime:
server=server.js

# OR container runtime, never both:
# container.image=ghcr.io/your-org/orbit-server@sha256:<64-lowercase-hex>

提交清单并将其推送到 StarHermit 可以读取的存储库/版本：

git add starhermit.txt
git commit -m "Declare StarHermit game ownership"
git push

在声明之前，打开存储库的原始 starhermit.txt 未经身份验证的浏览器中的 URL 以及 确认新值是公开可读的。声明在请求时读取存储库；一个 未经推动的局部变革不能证明任何事情。

第 3 步：验证清单

对于普通的克隆存储库游戏，声明需要：

  • starhermit.txt 在存储库根目录下；
  • 非空 name=;
  • launch= 指向存储库相关的 .html 或者 .htm 文件;
  • 有效的可选 server= 路径结束于 .js/.mjs，或有效的 container.image= 宣言;
  • 永远不会两个服务器同时运行。

GitHub Pages 列表将其托管 URL 作为启动目标，并且不需要清单 当个人 GitHub 所有权得到证明时，尽管有效的清单名称仍然可以更新其 显示名称。

如果游戏声明了一个容器，它的镜像必须满足注册表、所有者命名空间和摘要 规则在 容器托管的游戏服务器。容器托管也可以 受平台运营商限制。

第 4 步：认领列表

索赔请求没有正文：

curl -sS -X POST \
  "$API/api/v1/me/github-games/$GAME_ID/claim" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

一个成功的 200 返回更新后的游戏：

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "launchPath": "index.html",
  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "isVerifiedOwner": true,
  "metadataSource": "starhermit.txt",
  "hosting": {
    "hostingEnabled": true,
    "deployStatus": "pending"
  }
}

ID 应与步骤 1 中找到的 ID 相同。申领成功后请勿创建新列表。

特意允许声明您已经管理的列表。它重新读取清单， 重新配置后端并重新排队托管，因此可以使用相同的调用来重新同步 存储库更改后所有者管理的游戏。

第 5 步：验证接管和部署

确认游戏现在出现在您的托管列表中：

curl -sS "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" |
jq --arg id "$GAME_ID" '.[] | select(.id == $id)'

检查部署状态：

curl -sS \
  "$API/api/v1/me/github-games/$GAME_ID/deployment" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

声明通常会对部署进行排队，因此 pending 索赔后立即正常。投票与 退避，直到达到环境的实时/成功状态或暴露 deployError.

接管后，您可用的管理端点包括：

PUT    /api/v1/me/github-games/{id}/deployment  pin a commit/branch and redeploy
POST   /api/v1/me/github-games/{id}/bundle      upload built client/container output
PUT    /api/v1/me/github-games/{id}/hosting     requeue hosting where supported
POST   /api/v1/me/github-games/{id}/transfer    transfer management deliberately
DELETE /api/v1/me/github-games/{id}             remove the game

原始提交者不再在下面看到此列表 GET /api/v1/me/github-games 并且不能 为其使用这些所有者范围的管理端点。

故障排除

403：链接存储库所有者或添加 owner=

链接的 GitHub 登录名不匹配 ownerLogin，或清单 owner 不完全匹配 您的 StarHermit 用户 ID。

  • 查看 GET /api/v1/me/github.
  • 检查准确的 ownerLogin 由公开上市返回。
  • 对于组织存储库，使用 owner=<your StarHermit user ID> 在回购协议中。
  • 确认您推送了清单并且其原始 URL 是公开可读的。

404: 没有与该 ID 共享的游戏

ID 错误，或者列表已被删除。重复步骤 1。已删除的列表不可领取。

400: 缺失或无效 starhermit.txt

对于克隆存储库，请确保根清单有效 name 和 HTML launch 价值观。还有 验证可选脚本/容器声明。该声明最初并不信任元数据 由非所有者输入；它用存储库控制的元数据替换它。

slug/后端的声明失败

该脚本可能无效或容器托管可能不可用。检查返回的错误并 后端声明，然后再次调用claim。平台将游戏的UUID分配为其slug； 没有明显的问题可供选择或解决。

GitHub 已链接，但错误的 StarHermit 帐户拥有该链接

登录目标 StarHermit 帐户并完成 OAuth 关联 流向那里。请勿索赔 从临时的第二个 StarHermit 帐户，然后依靠帐户合并； API传输游戏 管理，而不是用户身份。

安全说明

  • 切勿接受声明链接或列表 ID 作为存储库所有权的证明。
  • 不要将 GitHub 访问令牌、容器凭据或其他机密放入 starhermit.txt.
  • 始终使用不可变的 StarHermit 用户 ID owner=;不要使用用户名或昵称。
  • 在声明之前查看现有列表和存储库 URL；显示名称不唯一。
  • 如果您稍后转让游戏，接收者将成为管理员，但已验证所有者状态为 重置。如果他们控制存储库，他们必须自己运行声明流程。
