GitHub 游戏

将游戏从 GitHub 存储库发布到 星隐士，或者注册一个已经托管的网页游戏。对于存储库游戏，平台读取 starhermit.txt，克隆存储库，并将其提供给 <slug>.starhermit.com。因为 /api 和 /ws 被代理来自该子域的同源，平台托管的游戏需要 没有 CORS 或基于 API 的配置。固定提交控制哪个存储库版本处于活动状态。这 国际象棋参考实现 以这种方式发布并作为模型的参考示例。

基本网址： https://api.starhermit.com。所有路线均在 api/v1/... 除非另有说明，否则需要 JWT。

托管客户端文件可以声明 文件夹缓存生命周期 和 其他 CORS 来源 在 starhermit.txt。这些政策与客户文件一起发布；无清单合并保留 现有设置，而提供的清单将替换它们。

清单： starhermit.txt

地方 starhermit.txt 在回购根目录下。格式： key=value 线， # 开始发表评论。

name=Your Game
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html        # repo-relative HTML entry
cover=art/cover.png      # optional cover art for the library tile; or an https:// URL
description=One-line pitch\nSecond line   # optional; or description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md          # optional; or release_notes=inline text
owner=<starhermit user id>  # UUID from GET /api/v1/me; do not use username/nickname
# Choose at most one authoritative backend, or omit both for a browser-only game:
server=server.js         # sandboxed JavaScript; see game-scripts.md
# container.image=ghcr.io/owner/game@sha256:<64 lowercase hex>; see container-games.md

control.up=KeyW+ArrowUp | Move forward
control.shoot=Space | Shoot
  • 没有 slug key：平台分配一个 uid 并将其用作子域（<uid>.starhermit.com）和游戏 API 命名空间（/api/v1/games/<uid>/…).
  • cover （别名 cover_art, coverart) 是游戏库图块上显示的艺术作品：相对于启动文件的路径，或绝对路径 https:// 网址。可选 — 如果没有，磁贴会显示您网站的图标。每次部署时都要重新阅读，因此更改行会更改封面。看 封面艺术 对于瓦片作物。
  • description / release_notes （或者 description.file / release_notes.file，其中命名为 .md/.markdown/.txt 相对于清单的文件）是游戏的可选文本。每次部署时都会重新读取它们，例如 cover。看 描述和发行说明.
  • server 声明一个沙盒 JavaScript 后端；看 game-scripts.md.
  • container.image 声明一个容器后端；看 container-games.md。它必须是摘要固定的，托管在许可名单注册表上经过验证的 GitHub 所有者的命名空间中，并且可能附带 container.port, container.health, container.memory_mb, container.cpu，并且非秘密 container.env.* 价值观。
  • 对于纯页游来说，这两个后端键都是可选的，但它们是互斥的。

默认控件绑定

游戏可以声明零个或多个桌面浏览器操作：

control.<action>=<code>[+<code>...][ | <label>]
  • 动作都是小写的 [a-z0-9_]{1,32} 标识符并保留清单顺序。
  • 代码是 KeyboardEvent.code 价值观； + 分隔一个操作的备用键。
  • 可选标签显示在控件重新映射 UI 中，默认为操作 ID。
  • 一个清单最多可以声明 32 个操作，每个操作有 4 个代码。代码不能被使用 两个动作。无效的控制线将被忽略。
  • 游戏没有 control.* 声明没有控件 API/UI (404 "This game declares no controls."）。从每个已发布的构建中重新读取声明 - 每个部署、文件夹上传 并取代捆绑推送。步步： 教程：向游戏添加控件.

注册一个游戏

POST /api/v1/me/github-games

{
  "repoUrl": "https://github.com/HypeDriven/starhermit-chess",
  "displayName": "StarHermit Chess",
  "launchPath": "index.html"
}

尽管它的历史名称， repoUrl 接受三个启动源：

  1. A github.com/<owner>/<repo> 存储库。后端读取其清单并可以部署它 到 StarHermit 托管。
  2. 已托管的 GitHub Pages URL，例如 https://owner.github.io/game/。存储库 身份是从 URL 推断出来的； URL 本身已启动，无需克隆或安装。
  3. 任何其他公众 http:// 或者 https:// 托管网页游戏 URL。它是直接启动的 不参与 GitHub 所有权声明。
  • displayName 和 launchPath 是可选的后备方案。它们对于第三方存储库很有用 没有可信的清单元数据；直接托管 URL 本身就是启动位置。
  • 对于经过验证的存储库所有者，平台会进行验证 starhermit.txt.
  • 可选的 server= 脚本或 container.image= 后台提供权威游戏；看 game-scripts.md 和 container-games.md。容器托管对 starhermit.com 上的任何登录用户开放；自托管部署可以将其限制在操作员允许列表中。
  • 声明的服务器后端需要经过验证的所有者。 提交一个声明的存储库 server= 或者 container.image= 没有 GitHub 登录或 owner= 证明是 403 （命名两个证明），而不是假装有后端的仅浏览器列表。
  • 限制：每个用户 100 场游戏（每个帐户可由操作员覆盖）。登记重复申报表 409.

注册/部署状态包括： InvalidUrl, LimitReached, Duplicate, MissingManualMetadata, MissingStarhermitTxt, InvalidLaunchPath, InvalidServerScriptPath, InvalidContainerImage, ServerProvisionConflict, RemovedByOwner.

错误使用标准形状：

{ "error": "..." }

从本地文件夹添加游戏

POST /api/v1/me/github-games/upload → 201

注册 URL 的对应部分： 没有存储库，并且没有任何内容被克隆。文件夹 一体旅行 .tar.gz 请求主体和平台托管其包含的内容。相同的存档 格式为 推一捆，因此相同的包装适用于两者。

创建的游戏有一个 gameSlug 从一开始，无论它是否声明一个服务器，所以 仅浏览器上传即可使用 控制, 每个玩家的设置， 它是 云保存槽, 实时房间 并像其他游戏一样启动代币。

client/           the game's files, published as-is
starhermit.txt    name= and launch= instead of the query parameters

清单是可选的 这个端点 — 查询参数可以提供相同的值 — 并且 StarHermit 客户总是发送一个根据其清单字段构建的。将文件传送到里面 您的构建仍然值得做：它使构建具有自我描述性并预填充这些字段，因此它 可以重新上传，而无需记住它需要哪些值。看 这 starhermit.txt 显现 对于格式，并注意 一切 清单旁边已上传 — 上传可分发的版本，而不是源代码树。

直接发送字节——而不是多部分形式的数据——用 Content-Type: application/gzip:

tar -czf game.tar.gz client/ starhermit.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/upload?displayName=My%20Game" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game.tar.gz

{
  "game": { "id": "...", "displayName": "My Game", "launchPath": "index.html", "hosting": { "hostingEnabled": true } },
  "bytesReceived": 4194304
}

元数据按此顺序解析，因此大多数文件夹根本不需要查询参数：

  1. ?displayName= / ?launchPath= 根据要求。
  2. name= / launch= 在一个 starhermit.txt 在存档根目录下。
  3. index.html 在根 client/ - 当没有其他名称时用作启动路径。

此路线的具体注意事项：

  • 电话一回，比赛就开始了。 没有单独的托管或部署 步骤： deployStatus 是 live 和 deployedCommitSha 是 null，因为没有提交。
  • 文件无法重新生成，因此平台永远不会从任何地方重新部署它们。一场比赛 添加这种方式进行 contentSource: upload 并保留其上传的版本直到您发布 另一个。推送新版本 束端点 或重新上传该文件夹。
  • 没有存储库意味着没有声明。 ownerLogin 是空的，所以没有 GitHub 登录可以匹配它； repoUrl 携带合成的 upload:<id> 值而不是 URL。
  • A server/image.tar 在这里被拒绝 (422）。服务器映像需要配置游戏才能 附加到，直到游戏出现才存在 - 首先创建游戏，然后推送图像 到 /{id}/bundle.
  • 命名存档不包含的文件的启动路径被拒绝（422) 上传时 仍然处于舞台阶段，而不是成为每个玩家的 404。

限制与任何其他推送相同：请参阅 上传限制.

上传的文件夹可以自带服务器后端

如果存档的 starhermit.txt 声明服务器逻辑，上传 也提供它——与没有存储库的存储库流程所做的事情相同。选择一个 风格；声明两者均被拒绝。

宣言 会发生什么
server=path/to/server.js 脚本后端。文件行进 在您上传的文件夹内，因此它的源代码是直接从存档中读取的——没有任何东西可以获取。看 game-scripts.md.
container.image=name@sha256:… 容器后端，一如既往地固定摘要。看 container-games.md。图像本身随后被推送到 /{id}/bundle.

这里的拒绝会让整个创作失败——没有一个半成品的游戏能够幸存下来：

  • server= 命名存档中不包含的文件。
  • server= 指向客户端文件外部（../).
  • 声明两者 server= 和 container.image=.
  • 要求提供禁用容器的容器，或者向未经批准使用容器的所有者索要容器。

封面艺术

库中游戏图块上显示的图像。无论您使用哪种方式， 匿名 GET /api/v1/github-games/{id}/cover 是为它服务的：

  • 在你的构建中 — a cover= 线路输入 starhermit.txt，命名与启动相关的图像 文件或绝对 https:// 网址。每次部署时都要重新阅读，以便您的存储库始终是事实的来源。
  • 已上传 — PUT /api/v1/me/github-games/{id}/cover 图像经过 base64 编码。这是 网络仪表板是什么 管理 → 封面艺术 是做什么的，以及 StarHermit 接线员可以为您做什么。
PUT /api/v1/me/github-games/{id}/cover
Authorization: Bearer <token>
Content-Type: application/json

{ "imageBase64": "iVBORw0KGgoAAAANSUhEUg..." }

一次上传 覆盖 故意地清单：重新读取的部署 starhermit.txt 必须 永远不要撤销某人亲手选择的艺术。 DELETE /api/v1/me/github-games/{id}/cover 是回去的路—— 它会删除上传和清单 cover= 再次申请。

PNG、JPEG、GIF、WEBP、BMP 或 SVG，最多 4MB。该类型是从字节中嗅探出来的，因此 Content-Type 您断言既不需要也不相信，并且字节不是可解码的图像 被拒绝 400。一个亲戚 cover= 路径必须结束于 .png, .jpg/.jpeg, .gif, .webp 或者 .svg （不 .., 无前导 /）；不可用的值被丢弃而不是失败 游戏。

封面艺术是海报艺术：两个图书馆 缩放它以填充瓷砖并中心裁剪 不管做什么 不适合。瓷砖的形状不一样。

表面 瓦 庄稼
Windows客户端 96×128 肖像 (3:4) 填充肖像；更广泛的艺术失去了侧面
网络仪表板 正方形 填满正方形；更高的艺术失去了顶部和底部

将主题保持在中心，这样两种裁剪看起来都正确。 SVG 涵盖了网络库中的显示；的 Windows 客户端无法解码 SVG，因此该图块显示的是网站图标。一款没有封面的游戏 一切都回到它的图标（GET /api/v1/github-games/{id}/icon）。该图标是从 您提交的 URL，以及当平台托管游戏时，来自其提供的副本的 URL <uid>.starhermit.com - 因此，文件中带有网站图标的上传包仍然会获得一个图标。

您的游戏的观众人数

GET /api/v1/me/github-games/{id}/stats → GameStatsDto

一个游戏有多少人玩 你添加了。仅限游戏所有者 - 其他任何人都可以获得 404, 与不存在的游戏相同的答案。

{
  "totalPlayers": 42,
  "playingNow": 3,
  "totalSessions": 130,
  "totalPlaytimeMinutes": 8140,
  "lastPlayedAt": "2026-07-29T08:45:24Z",
  "livenessWindowHours": 4
}
  • 仅聚合。 你了解的是你的受众的规模，而不是其中的人员。
  • totalPlayers 计数 不同的人，而不是会话——玩过六次的人就是一次 玩家。
  • playingNow 统计会话尚未结束的不同玩家 和 开始在里面 livenessWindowHours。窗口很重要：崩溃或丢失网络的客户端永远不会发送 会话结束，如果没有它，这些行将被视为人们仍在无限期地玩。
  • totalPlaytimeMinutes 计数 仅已完成的会话，匹配每个用户的游戏时间数字 在 activity.md。飞行中的会话还没有做出任何贡献。
  • lastPlayedAt 是 null 对于一个没有人玩过的游戏。

数字来自每个客户写入的同一个启动分类账（请参阅 activity.md），所以一个 玩家从未报告启动的游戏将读取为零。

主张所有权

POST /api/v1/me/github-games/{id}/claim → GitHubGameDto

当您控制现有列表的存储库时，接管该列表。通过链接来证明所有权 与存储库所有者匹配的个人 GitHub 登录，或通过提交 owner=<your StarHermit user ID> 到存储库的 starhermit.txt. owner 应该是 不可变的 UUID 返回为 id 经过 GET /api/v1/me, 不是 用户名或昵称。清单 方法支持组织拥有的存储库，这些存储库不是从个人 GitHub 组织推断的 会员资格。

成功后，现有列表保留其 ID/历史记录，由索赔人管理，刷新 存储库控制的元数据和后端声明，以及可用的队列托管。的 先前的提交者失去了所有者范围的管理访问权限。认领您已经管理的列表 重新同步它而不是返回冲突。

GitHub 身份元数据存储 {"login":"…"};通过 OAuth 流程链接您的 GitHub 帐户（请参阅 auth.md）。检查链接状态 GET /api/v1/me/github → { linked, login }。请参阅 分步索赔教程 为了发现，两个证明 方法、验证、接管和故障排除。

转让所有权

推送游戏捆绑包

POST /api/v1/me/github-games/{id}/bundle 无需询问 StarHermit 即可发布构建的输出 再次克隆它。调用者必须拥有已注册的游戏。发送 .tar.gz 直接字节——不是 多部分表单数据—带有 Content-Type: application/gzip:

至少 client/ 或者 server/image.tar 必须存在（合并也可能只是 remove.txt）。客户端文件以原子方式交换。一个 服务器映像已加载，由平台摘要固定，并将容器部署排队到 在该图像上重新启动。上传的图像优先于清单的注册表引用， 并超过一个 server= 线;声明两者的清单 server= 和 container.image= 被拒绝 在加载任何内容之前。存档中的任何其他内容都将被忽略。

上传图片本身就是一种声明。 如果游戏还没有服务器后端 - 已上传声明无的文件夹 — 推送 server/image.tar 文摘中的规定之一 已加载，下 gameSlug 游戏已经有了。您不必在文件中命名摘要固定图像 首先体现出来，这是循环的：定义必须先存在才能接收图像， 图像是唯一可以描述它的东西。

重新推送会应用其清单声明的容器旋钮，并且仅应用这些旋钮。 包括 starhermit.txt 在捆绑包中进行了更改 container.port, container.health, container.memory_mb 或者 container.cpu 并且部署会在重新启动时拾取它；留下一个旋钮并 它会保留您上次设置的内容。完全省略清单，不涉及部署 除了图像之外的变化。

一个捆绑包，其 starhermit.txt 携带一个可用的 name= 还 重命名游戏列表 对它—— 显示名称更新与推送一起进行。离开 name= 出（或省略清单）以保留 当前名称。

和 mode=merge:

  • 文件下 client/ 被添加或覆盖
  • 根中的路径 remove.txt (# 评论;目录删除其整个子树）被删除
  • 所有其他实时文件都保持原样

合并的树作为副本上演并自动交换 - 玩家看到旧游戏或新游戏 全新的，绝不混合。结果有界于 游戏的 津贴，而不是上传的，所以 一款游戏的发展不能一次一小部分地超出其限制。合并仅涉及客户端文件；一个 server/image.tar 加载方式与替换时完全相同。补丁没有携带 starhermit.txt 叶子 封面艺术原样。

合并被拒绝 (409/422，没有任何变化）当游戏还没有发布任何内容时，当它 会删除启动文件，或者当 remove.txt 游戏外的分数。一个 remove.txt 在一个 普通替换也被拒绝（422），因为在那里它只能代表你不代表的东西 打算。 mode 必须是 replace （默认）或 merge;其他的都是 400.

相同的参数适用于套接字： ws/v1/game-upload?gameId=…&mode=merge。这 ready 框架 呼应它作为 "apply":"merge".

终端更新已注册的游戏；它永远不会创造游戏记录——为此，请参阅 从本地文件夹添加游戏。它 能 提供游戏的 服务器后端，作为将服务器图像加载到没有服务器图像的游戏中的副作用。请参阅 专用服务器发布教程.

通过 WebSocket 上传

GET /ws/v1/game-upload （升级） - 将此用于任何超过 100 MB 的内容。

API 前面的 CDN 大致拒绝 HTTP 请求正文 100MB 与一个 413 其 拥有。该拒绝从未到达平台，因此它不包含任何内容 limitBytes 并且出现在没有日志中 可以阅读——a 413 没有 limitBytes 字段是 CDN，不是你的游戏的限额，是两个 大了几个数量级。任何现实的 docker save 会击中它。

WebSocket 升级后发送的帧不是请求正文，因此不适用上限。 只是运输方式不同。 二进制帧准确地连接成 HTTP 路由的字节 读取，通过相同的管道，并且每个拒绝、允许和成功主体都是 HTTP 主体 路线会产生 - 因此客户端可以在两者之间共享一个代码路径。

wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&mode=merge&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?displayName=My%20Game&launchPath=index.html&access_token=$TOKEN

经过 gameId 推送到您拥有的游戏（ /{id}/bundle 路线）;省略它并通过 displayName/launchPath 从文件夹（ /upload 路线）。令牌进入 查询字符串，因为浏览器无法设置 Authorization WebSocket 握手的标头；是的 在握手时检查一次，因此超过其访问令牌的上传仍然会完成。

方向 框架 意义
服务器 → {"type":"ready","mode":"bundle","apply":"replace","limitBytes":N,"heartbeatSeconds":15} 已结算津贴并检查可用空间。开始发送。 mode 是 bundle 或者 create. apply 是 merge 当您要求部分更新时。
→ 服务器 二进制 存档字节，无论您喜欢如何分块 - 服务器永远不会重新组装消息，因此 256 KB - 1 MB 是一个很好的默认值。连接起来，你的帧必须完全是 .tar.gz.
服务器 → {"type":"ack","bytesReceived":N} 接收进度，大约每 8 MB。由此驱动你的进度条。
→ 服务器 {"type":"complete"} 档案已完整发送。
→ 服务器 {"type":"abort"} 放弃。回答为 status: 499;没有任何内容被发布。
服务器 → {"type":"progress","phase":"publishing","bytesReceived":N} 上传落地时每 15 秒心跳一次。忽略它们，但期待它们。
服务器 → {"type":"result","status":200,...} 成功。对象的其余部分是逐字的 HTTP 响应正文 (status 是 201 用于创建）。
服务器 → {"type":"error","status":413,"error":"...","limitBytes":N} 拒绝。 status 正文是 HTTP 路由会回答的内容。

直到 {"type":"complete"} 到达。 这是没有 HTTP 的一种行为 等效的，并且是故意的：存档结束标记存在 里面 一个 tar 的字节，所以 平台完成读取完整的档案，而连接不会终止。一个插座 在最后一个字节之后简单地丢弃，否则会像完成的那样发布 - 默默地用废弃的推送替换实时游戏。关闭套接字而不上传帧 什么也没有。

最后一个字节之后的发布可能需要一些时间，尤其是对于服务器映像而言。预计 progress 完成时心跳；不要将安静间隔视为上传失败。

上传限制

所有上传路由（HTTP 端点和 WebSocket）都共享相同的规则。

限制 价值
每场比赛的磁盘限额 2GB 在 starhermit.com 上（津贴可能因游戏/部署而异）
每个帐户托管文件 20GB 跨帐户的所有游戏（每个帐户的操作员可调）

starhermit.txt / remove.txt 256KB 每个; remove.txt 最多列出 10,000 条路径 (422)

地位 意义
400 mode 两者都不是 replace 也不 merge.
409 针对尚未发布文件的游戏的合并。
413 超过津贴了。身体承载 { "error", "limitBytes" }. A 413 没有 limitBytes 是 CDN 的 ~100 MB 主体上限，而不是这个 — 使用上传套接字.
422 存档格式错误或内容不可用（缺少启动文件，没有 client/, a server/image.tar 在创建路线上，合并将删除启动文件， remove.txt 更换时）。还有一个 被截断的 存档 — 上传过程中连接断开的普通结果。

发布您自己的游戏：演练

有两条路线。如果您的游戏位于 git 存储库中，请按照下面的编号步骤操作。 如果它只是您计算机上的一个文件夹，则一次调用即可完成所有操作： 从本地文件夹添加游戏 注册游戏，发布 文件，并使其保持活动状态 - 没有托管切换，也没有提交 pin，因为没有存储库 轨道。

  1. 选择来源：推送包含以下内容的存储库 starhermit.txt 在根（可选地声明一个 server.js 脚本或容器图像），或准备已托管的浏览器游戏的公共 URL。
  2. 链接您的 GitHub 身份 通过 OAuth 流程（请参阅 auth.md）；验证与 GET /api/v1/me/github.
  3. 注册游戏: POST /api/v1/me/github-games 存储库或托管游戏 URL 位于 repoUrl.
  4. 仅限存储库游戏 - 启用托管: PUT /api/v1/me/github-games/{id}/hosting 和 { "enabled": true }.
  5. 仅限存储库游戏 - 固定提交: PUT /api/v1/me/github-games/{id}/deployment 和 { "commit": "<sha>" }。固定提交控制实时版本。
  6. 玩家启动游戏：部署的存储库游戏位于 <slug>.starhermit.com;直接托管的游戏会打开其提交的 URL。每场比赛都有一个 gameSlug — 无论是否后端 — 从以下位置接收启动令牌 POST /api/v1/games/<slug>/launch-token 在 URL 片段中（可选 &session_id=<guid> 用于邀请深层链接）。

有关完整的客户端合约 - 游戏如何读取启动令牌并与 API 对话 - 请参阅 国际象棋演练 参考实现。
