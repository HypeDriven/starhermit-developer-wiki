实时房间

实时房间是快节奏多人游戏的通用大厅：房间创建、朋友邀请、快速加入配对、按需 AI 玩家加上 AI 座位回填以及角色感知实时传输（ws/v1/realtime）。该子系统故意与游戏无关——房间的范围是根据游戏而定的，房间 metadata 是一个不透明的每游戏 JSON blob，并且 teamCount = 1 模型免费为所有游戏。

一场比赛以两种方式之一进行：

  • 主机路由（默认） — 平台服务器是一个智能传输，而不是模拟器：房间创建者的客户端是 主持人 并运行权威的游戏模拟；其他客户端（来宾）将输入发送到主机并接收主机的快照。服务器强制执行路由、角色、容量、速率限制和身份——客户端不能互相欺骗，并且只有服务器分配的主机可以广播。
  • 房间限制会话（服务器权威） - 对于发布的游戏 server= 脚本或 容器：当房间启动时，平台会创建一个绑定的N人会话（脚本化的 或容器）运行模拟服务器端。然后游戏玩法就结束了 ws/v1/games 实时 WS 仅用于大厅/名册。看 桥 以下。

将此与 对等中继 （不透明扇出绑定到现有房间/会话名册，默认情况下禁用）和普通 脚本游戏 （服务器权威，有会话匹配和邀请，但没有房间大厅）。实时房间是 默认启用.

所有 REST 端点都需要身份验证，并使用完整的用户令牌和游戏范围的启动令牌。错误体各不相同；看 API约定.

数据模型

房间 生命周期： Lobby → Open （对接会）→ Playing （名单冻结，空座位用 AI 回填至房间限额）→ Closed。创建的房间 joinInProgress 不断地吸引玩家 Playing.

  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "hostUserId": "<guid>",
  "status": "Lobby",
  "gameSessionId": null,
  "config": {
    "teamCount": 2,
    "seatsPerTeam": 5,
    "backfillAfterSeconds": 30,
    "aiPlayers": 0,

    "joinInProgress": false,
    "metadata": { "map": "arena" }

      "isHost": true,
      "team": 0,

  "joinCode": "K7MP2X",
  "isVisible": false,
  "revision": 1,
  "createdAt": "2026-07-22T07:00:00Z",
  "openedAt": null,
  "startedAt": null,
  "closedAt": null,
  "result": null
}
  • config.metadata 是平台从不解释的不透明 JSON blob。它，以及提交的 结果的元数据，最多可能为 16 KB (413），一个房间最多有100个座位；操作员可以 为一场比赛改变其中任何一个。
  • config.aiPlayers 是创建者要求比赛开始时有多少位 AI 玩家 - 他们在创建房间时就座（请参阅 以下）。它记录请求；这 participants 花名册对于实际拥有席位的人具有权威性。
  • 人工智能参与者有 userId: null, isAi: true，以及服务器生成的随机昵称，在房间内是唯一的。
  • (team, slot) 是参与者的座位坐标；人类按连接顺序就座。
  • gameSessionId 是绑定的游戏会话，当房间开始进行带有服务器后端的游戏时设置 - a server= 脚本或 容器 （看 桥); null 否则。它也包含在名册推送中。
  • result 是结果，在房间关闭时设置 - 对于主机路由的游戏由主机提交，对于房间限制的会话由脚本返回。
  • joinCode 是六个字符（已删除相似读对）。这是邀请函 join-by-code。列表中从不包含它。
  • isVisible 列出房间 GET /rooms。开放（快速加入）和上市是独立的。
  • revision 仅当主机编辑配置时才会发生碰撞（PATCH），绝不会在座位已满时。将其传递为 expectedRevision 在 PATCH 用于比较和交换（409 关于冲突）。

邀请: { "id", "roomId", "gameSlug", "fromUserId", "fromUsername", "toUserId", "status", "createdAt", "notified" } 和 status 之一 pending | accepted | declined | expired （当房间在得到答复之前关闭或开始时，邀请就会过期）。 notified 出现在对的响应中 POST /rooms/{id}/invites 并报告受邀者的通知是否到达实时连接；这是 null 上市时。

REST 端点

根据： https://api.starhermit.com/api/v1/realtime - 所以 POST /rooms 下面是 POST /api/v1/realtime/rooms.

方法 小路 WHO 描述
邮政 /rooms 任何人 创建一个大厅，可以选择配备人工智能玩家；呼叫者成为主持人
得到 /rooms?gameSlug=[&includeInProgress=true] 任何人 浏览仍然有座位的已开放、已列出的房间，并在被询问时运行正在加入的房间（无代码，无名册；最多 50 个）
邮政 /rooms/join-by-code 任何人 使用房间的加入代码入座（适用于未列出的/仍在大堂的房间）
修补 /rooms/{id} 主持人 重命名、列出/取消列出、替换元数据、切换 joinInProgress，设置回填余量（expectedRevision 化学文摘社）
邮政 /rooms/{id}/matchmake 主持人、大堂 将整个名单作为一个团体/团队进行排队
得到 /rooms/{id} 参与者+受邀者 房间+名册
邮政 /api/v1/realtime/connection-tickets 任何人 一度 ?ticket= 用于实时（和其他）套接字
邮政 /rooms/{id}/invites 参与者 邀请朋友；通知他们（409 一式两份）
得到 /rooms/invites 任何人 呼叫者待处理的房间邀请（跨游戏）
邮政 /rooms/invites/{inviteId}/accept 受邀者 加入房间（已分配座位）
邮政 /rooms/invites/{inviteId}/decline 受邀者 衰退 （204)
邮政 /rooms/{id}/open 主持人 开放对接会；开始回填倒计时
邮政 /rooms/quick-join 任何人 加入最古老的开放房间，获得免费游戏席位，可选择匹配过滤器
邮政 /rooms/{id}/start 主持人 用 AI 填补空位、状态 → Playing
邮政 /rooms/{id}/leave 参与者 离开;在“大厅/开放”中，座位被移除，在“游戏”中，座位会转换为 AI 参与者，或者在“加入”房间中，座位会被腾出
邮政 /rooms/{id}/seats 主持人 比赛开始前重新平衡座位
邮政 /rooms/{id}/result 主持人 提交结果；房间 → Closed
得到 /rooms/mine 任何人 呼叫者的活动房间（如果有）（重新连接）
得到 /rooms/joined[?gameSlug=] 任何人 呼叫者在每个房间都有一个座位，包括世界（如果没有，则为空列表）

创建一个房间—— POST /rooms

{ "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "teamCount": 2, "seatsPerTeam": 5, "backfillAfterSeconds": 30, "aiPlayers": 0, "backfillAiPlayers": 4, "name": "Friday night", "isVisible": false, "metadata": { "map": "arena" } }
  • gameSlug 完整用户令牌是必需的。对于游戏范围的启动令牌，slug 是从令牌的 game_scope （不匹配的主体值被拒绝 403).
  • 上限： teamCount 1–2, seatsPerTeam 1–100，总座位数 ≤ 100（一组 100 人，或两队 50 人）。 backfillAfterSeconds 默认为 30 并且必须是 至少 1 (400 否则）;有 无上限 超出 32 位整数的大小。一个长 不过，倒计时仅在有人保持联系时才有效： Open 没有人的房间 ws/v1/realtime 60 分钟后关闭（参见 自动房间生命周期), 因此，只有当参与者保持套接字打开时，才会达到比该时间更长的倒计时。 大房间受带宽限制，而不是座位限制：每个客人的帧都会发送到主机，每个主机帧都会复制到每个客人​​ - 请参阅 确定大房间的尺寸.
  • aiPlayers 默认为 0。范围 0–(teamCount × seatsPerTeam) − 1 — 主持人总是需要座位，所以全人工智能房间是 400.
  • backfillAiPlayers 限制比赛开始时仍空着的座位数给 AI — 请参阅 回填余量。省略或 null 充满了它们。
  • joinInProgress （默认 false）在开始后保持房间占用玩家 - 请参阅 加入进行中.
  • 每个用户一个活动房间：当您在任何非活动房间时创建或加入Closed 房间返还 409.
  • 创建者成为主持人，坐在第 0 队、第 0 号位置。返回房间。

人工智能玩家

aiPlayers 说有多少 AI 玩家 比赛应该开始于。它们不是稍后兑现的承诺 - 服务器会立即就座它们，因此您返回的房间已经包含它们：

  • 他们是普通参与者（isAi: true, userId: null，独特的昵称）并出现在名册和每个 roster 从房间存在的那一刻起就推动。
  • 他们 占座，因此它们减少了留给人类的容量：邀请和快速加入仅填充剩余的容量，并且 POST /rooms/invites/{id}/accept 回报 409 一旦没有空闲座位。你得到的人工智能数量正是你所要求的——再也不会从匹配中得到更多。
  • 放置位置填充 最空的队伍优先 （排名较低的球队指数），最低的空闲位置。所以一个 teamCount: 2, seatsPerTeam: 1 房间有 aiPlayers: 1 将人工智能置于主机对面，更大的房间可以保持平衡。按照您喜欢的方式重新安装它们 POST /rooms/{id}/seats 比赛开始前。
  • 它们与开始时回填是分开的，开始时回填会填充房间开始时没有人占用的座位 - 直到房间的 回填津贴.

回填余量

当房间启动时——在回填截止日期、一旦填满或在主机强制启动时—— 没有人坐的座位给了AI玩家。 backfillAiPlayers 决定多少：

backfillAiPlayers 开始时
省略/ null （默认） 每个空位都成为AI玩家
0 无AI：比赛开始时座位空着
n 最多 n 空座位变成AI；除此之外的任何内容都留空

上限 AI 转到 最空的队伍优先 （与较低的团队指数相关），所以 2 × 3 房间有 一台主机和 backfillAiPlayers: 3 开始2对2。范围 0–teamCount × seatsPerTeam， 别的 400。 主持人可以在比赛前更改它 PATCH /rooms/{id} ("backfillAiPlayers": 2），或 返回到填满每个座位 "backfillAllEmptySeats": true。不影响 aiPlayers, 创建房间时谁就座。

如果你的游戏注定要玩得不够充分——一场混战，八人中有六人就可以了 玩家——使用 0 让你的游戏处理空座位。默认情况下，房间永远不会启动 有一个空座位。

与电脑单人对战 因此是两个调用——创建一个房间，其中每个其他座位都是 AI，然后启动它：

POST /api/v1/realtime/rooms
{ "gameSlug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94", "teamCount": 2, "seatsPerTeam": 1, "aiPlayers": 1 }

POST /api/v1/realtime/rooms/{id}/start

人工智能座位是身份和座位预订，而不是机器人服务——平台上没有任何东西可以为你播放它们。主机路由的游戏在自己的模拟中驱动它们；一个游戏 server= 脚本找到它们 ctx.room.roster 标记的 ai: true 并在脚本中播放它们（参见 游戏脚本).

邀请

POST /rooms/{id}/invites 和 { "toUserId": "<guid>" }。邀请是 仅限好友 (403 否则;与游戏邀请相同的友谊规则），仅限参与者，并且仅当房间需要加入时： Lobby/Open， 或者 Playing 和 joinInProgress. 409 如果用户已经在房间中或已有待处理的邀请； 400 邀请自己的时候。返回邀请。

受邀者会收到通知。 发送房间邀请会发出 game_invite 推 在被邀请者的聊天套接字上并将邀请添加到 GET /api/v1/me/game-invites，因此 StarHermit 仪表板（或除您的游戏之外的任何地方）中的朋友仍然会听说它。你做 不是 还需要发送游戏 API 邀请——这会通知两次。响应的 notified 告诉您推送是否达到实时连接； false 只是意味着被邀请者现在尚未连接，而是会从收件箱中看到邀请。

由于一个通知涵盖了两个邀请系统，因此其有效负载携带 kind: "room" 加 roomId 和 acceptPath/declinePath 为了 这 邀请。在下面的实时端点应答房间邀请 - 房间邀请 ID 在以下位置无效 /games/{slug}/invites/... 反之亦然。

GET /rooms/invites 列出呼叫者在所有游戏中待处理的房间邀请（启动令牌只能看到自己游戏的房间邀请）。将其用作游戏客户端轮询的房间邀请收件箱。统一邀请收件箱位于 GET /api/v1/me/game-invites 也返回这些。

POST /rooms/invites/{inviteId}/accept 让呼叫者入座并返回房间。 派对固定：邀请加入的人会在主持人的团队中就座，空间有限，然后溢出到其他团队。 409 如果房间已满，已经开始/关闭，或者呼叫者在另一个活动房间（世界 除外）。接受呼叫者已经坐在的房间的邀请只是接受它。

POST /rooms/invites/{inviteId}/decline → 204.

对接会

POST /rooms/{id}/open （仅主机）： Lobby → Open， 套 openedAt，并开始回填倒计时。幂等虽然已经 Open; 409 一次 Playing/Closed.

一个 Open 房间不会等待一次倒计时 每个座位都有人 ——由人类或人工智能玩家在创建时配置。它从那里开始，然后，所以响应 open （或填充最后一个座位的连接）可以已经是 Playing 房间有 startedAt 放。每个座位上都有人工智能创建的房间，但主人的座位在打开的那一刻就开始了。

GET /rooms?gameSlug= 浏览该游戏开放的、列出的仍然有座位的房间，最早开放的房间在前，上限为 50。每行都有名称、主机名称、玩家/容量计数， freeSeats、元数据、 startedAt 和 joinInProgress — 没有加入代码，也没有名册。添加 includeInProgress=true 还列出正在运行的 正在进行中的加入 房间有空位，之后每个房间还都满了。

POST /rooms/join-by-code 和 { "joinCode": "K7MP2X" } 坐下。代码不区分空格和大小写。与快速加入不同，这适用于仍处于未列出状态的房间 Lobby。当房间关闭时，代码就会被释放。

PATCH /rooms/{id} （主持人）： { "name", "isVisible", "metadata", "joinInProgress", "backfillAiPlayers", "backfillAllEmptySeats", "expectedRevision" }。省略的字段将被保留；发送 name: "" 清除名称。一个 Playing 房间仍然可以重命名、列出或不列出、替换其元数据并切换 joinInProgress;回填设置被拒绝（409）比赛开始后。

POST /rooms/{id}/matchmake （主持人， Lobby 仅）排队房间的 人类 名册为一 政党/团队；预先入座的人工智能参与者不是党员。使用默认策略时，聚会规模 必须等于所选队列的 teamSize。与一个 清单开始截止日期, 较小的一方可以在截止日期前占据较大的团队；剩余席位成为AI最多 游戏配置的上限，然后留空。各方保持在一起，门票不会合并为一组。

使用 ?queue=duos 对于一种形状或重复 ?queues= 允许子集，如 Games API 中：

POST /api/v1/realtime/rooms/{id}/matchmake?queues=duos&queues=trios
Authorization: Bearer <token>

返回 婚介票， 包括 status 和 sessionId 当匹配时。主持人投票 GET /api/v1/games/{slug}/matchmaking 并取消 DELETE 在那条路上。已经排队的房间或派对不适合任何允许的形状 回报 409。这种权威的配对流程与开房间快速加入是分开的 及其房间级回填倒计时。

POST /rooms/quick-join 和 { "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "seats": 1 } 将调用者置于 最古老的开放式房间，有空闲座位 对于该游戏 slug，AI 座位算作已占用，因此剩余座位全部为 AI 的房间将被跳过。 404 当没有房间符合条件时，客户应该创建自己的房间并打开它。仅支持单座快速加入（seats 必须是 1).

过滤器。 添加其中任何一个即可仅加入适合的房间；给定的每个过滤器都必须保持，并且 上面的行为没有给出：

{ "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "seats": 1, "teamCount": 2, "seatsPerTeam": 4, "metadata": { "mode": "ranked", "map": "arena" }, "includeInProgress": true }
筛选 匹配的房间…
teamCount 队伍人数就是这样
seatsPerTeam 每队的座位就是这样
metadata 元数据包含 每一个 给予的财产，具有同等价值。您未命名的属性将被忽略，因此 {"mode":"ranked"} 比赛 {"mode":"ranked","map":"desert"}。值以 JSON 形式进行比较：按值排列数字 (1 等于 1.0），无论键顺序如何，对象都是按顺序排列的。必须是一个对象 (400 否则）。

includeInProgress: true 还考虑上市、运行 正在进行中的加入 有空座的房间；不管怎样，仍然入住的房间是第一位的。如果没有它，则永远不会加入正在运行的匹配，因此早于加入进行中的客户端永远不会加入其中。一个 metadata 过滤器携带您的游戏放入房间元数据中的 ID，这就是客户端加入的方式 一个特定的 列出的房间，因为列表没有加入代码。

最古老且有空闲座位的匹配开放房间获胜。当没有匹配时， 404 说 "No open room with free seats matches those filters." — 创建和打开房间的常见提示 您自己使用该元数据，以便下一个玩家的过滤快速加入找到它。

开始、座位、离开、结果

POST /rooms/{id}/start （仅限主机）：填写 仍然空着 座位 - 所有座位，或取决于房间的座位数 回填津贴 — 与人工智能参与者 (isAi: true, userId: null，独特的随机昵称） - 坐在创建位置的人工智能玩家保留他们的ID，昵称和座位 - 冻结名单，集 status: "Playing"，并返回冻结的名单。如果游戏有服务器后端（ server= 脚本或容器），这也会创建房间限制的会话（请参阅 桥）；返回的房间和名册推送进行 gameSessionId. A 容器 无法创建的会话（最常见的是部署仍从空闲状态唤醒）使房间未启动： start 回答该错误（重试），并且满室或回填清扫在下一次扫描时重试。脚本失败仍会启动房间主机路由。 幂等 — 开始一个 Playing room再次返回名册。当回填截止日期过后，房间可能会自动启动。

POST /rooms/{id}/seats （仅限主机， Lobby/Open 仅）重新安排参与者：

{ "seats": [ { "participantId": "<guid>", "team": 1, "slot": 0 } ] }

400 对于房间团队/时段范围之外的座位或未知参与者； 409 如果两个参与者共享一个座位。

POST /rooms/{id}/leave 根据房间状态表现：

  • 大堂/开放: 座椅已拆除。如果 主持人 离开，主持人角色转移给剩余时间最长的人类参与者；如果没有人留下，房间就 Closed.
  • 玩， 正在进行中的加入 房间: 座位是 腾出 （不提供给AI），玩家被从绑定会话中删除（他们的 ws/v1/games 插座关闭）并告知游戏。当最后一个人离开且绑定会话仍处于活动状态时，房间将处于活动状态 不是 关闭：世界保持列出状态并可加入，第一个回来的玩家担任主机角色。
  • 玩（AI接管）：比赛继续——离开者的座位变成AI座位： isAi: true, userId: null，具有新鲜独特的昵称和相同的参与者 id, team, slot， 和 joinedAt。离开者立即被释放（单活动房间规则不再计算他们，因此他们可以创建或加入另一个房间），而花名册推送告诉每个客户，人工智能现在占据了该席位。如果离职者​​是 主持人 和至少一名其他人类遗骸，主人角色转移到加入时间最长的剩余人类，房间保持不变 Playing （客户端主机迁移是游戏关心的）；如果没有人留下，房间就 Closed.

返回房间。

POST /rooms/{id}/result （仅限主机， Playing 仅）记录结果，关闭房间，并通过 WebSocket 将结果扇出。 仅限主机路由的游戏 — 当脚本返回时，具有绑定脚本会话的房间结束 result，它会自动关闭房间（参见 桥).

{ "teamScores": [3, 1], "metadata": { "durationSeconds": 360 } }

teamScores 每个团队必须只有一个参赛作品；每个分数都被合理限制在 0-50 之间。钳位结果存储在房间的 result 并作为连接的参与者推送 {"type":"result"} 控制框架。

GET /rooms/mine 返回调用者当前的非Closed 房间（用于重新连接），或 404。一名球员 谁也属于 世界 得到占据他们的房间，否则 他们最近加入的世界。

GET /rooms/joined 列表 每一个 呼叫者坐在房间里，最新的在前——他们的世界 以及占据他们的一个房间 - 作为完整的房间（包括名册和加入代码）。发射 令牌只能看到自己的游戏房间；具有完整的令牌， ?gameSlug= 缩小它。它回答一个空 列表，不是一个 404，因此客户端可以在每次启动时询问，而不会记录错误。

加入进行中

创建的房间（或 PATCH编辑）与 "joinInProgress": true 不断地吸引玩家 start。 邀请， join-by-code 并快速加入 includeInProgress: true 然后做一个 Playing 房间 与一个 空缺 座位——里面没有人，不是人工智能——所以这样的房间通常是这样开始的 "backfillAiPlayers": 0。如果没有标志，启动的房间将像以前一样拒绝每次连接。

  • 比赛决定。 如果房间绑定了游戏会话，则新人可以进入该房间 保留座位之前的会话：平台询问脚本的 game.onMembershipChange(ctx) 或一个 集装箱的 POST /sessions/{id}/members。一场比赛 拒绝（或两者都没有）获得座位靠背，并且连接是 409;已接受的邀请将保留 待定。一旦被接纳，该玩家在任何意义上都是会话玩家——有效于 ws/v1/games, 在恢复和重新连接中。
  • 离开时腾出座位 并将玩家从会话中删除，并告知游戏。
  • 世界比它的访客更长寿。 当最后一个人离开且会话仍处于活动状态时， 房间保持开放、列出且可加入；第一个回来的玩家成为主持人。一个房间绑定到一个 活动会话也不会因其主机离线而关闭（请参阅 60秒主持人规则）。会话自己的 生命周期决定何时结束——a 执着的 游戏暂停 而不是结束——房间也随之关闭。
  • 找一个。 GET /rooms?includeInProgress=true 列出正在运行且有空闲房间的加入进程 座位； POST /rooms/quick-join 和 includeInProgress: true 连接一个（添加一个 metadata 过滤到 选择一个特定的房间）。快速加入会跳过呼叫者已经所在的房间。

世界不算是你的房间

一个玩家可能处于 一次一个活动房间：创建、通过代码加入、快速加入或 接受邀请是 409 "You are already in an active room." 当他们在另一个座位上占据座位时 未关闭的房间。一个座位在一个 世界 不算：a Playing, joinInProgress 房间限制 到一个活动会话 执着的 游戏。世界持续多久 由于其会议和房间在最后一位访客离开后仍保持开放，因此其中的一个座位是会员资格， 不是玩家所在的大厅 - 他们可以在任何游戏中属于多个世界，并且仍然使用 一间普通房间。正在进行中的比赛如果不是持久的，仍然有效：它结束了，而 它运行时玩家就在其中。同一房间的第二个座位被拒绝（409）在每条路径上。列出一个 玩家的世界 GET /rooms/joined.

网络套接字： ws/v1/realtime

连接到 wss://api.starhermit.com/ws/v1/realtime?roomId=<guid> 通过 JWT Authorization 标头， ?ticket= 从 POST /api/v1/realtime/connection-tickets， 或者 ?access_token=。更喜欢门票：它是一次性的，并且是秒有效的。 仅限参与者 (403 否则）;启动令牌的 game_scope 必须等于房间的 gameSlug。最新的连接取代了用户之前的连接——旧的套接字被关闭 PolicyViolation ("被更新的连接取代").

二进制帧（游戏玩法）

二进制帧是游戏通道 主机路由 游戏（房间内的脚本会话结束 ws/v1/games 相反 - 请参阅 桥）。服务器 从不解析 它们的有效负载——主机权限是游戏的合同——但它强制执行路由和身份：

  • 服务器 在每个帧前面加上发送者的 16 字节参与者 ID 前缀 （.NET 字节顺序的参与者 GUID）。客户端必须剥离前 16 个字节，并且决不能信任有效负载内的发件人 ID。
  • 主人→房间：主机的帧分散到每个其他连接的参​​与者（快照）。
  • 仅限客人 → 主持人：访客的帧被传递给主机，而不是其他人（输入）。
  • 框架尺寸上限： 8KB。速率限制： 每个连接每秒 30 条消息，令牌桶具有 1 秒的 2× 突发裕度。违规会关闭套接字 PolicyViolation.

JSON 文本控制框架

小 JSON 帧 (≤ 4KB) 进行大厅和比赛活动：

{ "type": "ready" }
{ "type": "chat", "text": "Ready to race" }
{ "type": "event", "kind": "countdown", "goInMs": 3000 }
  • 这 主持人 可以发送 event, chat， 和 ready;帧被广播给所有其他参与者。
  • 嘉宾 只能发送 ready 和 chat （同时广播），速率限制为 每分钟 10 个.
  • 服务器 重新标记每个控制帧 发送者的参与者 ID：客户端提供的 from 被剥离并替换为 "from": "<participantId>".
  • 无法解析的框架，未知的 type，或者发送者的角色可能不会发送的类型关闭套接字 PolicyViolation.

服务器推送

服务器自行推送 JSON 文本帧：

  • {"type":"presence","userId":"<guid>","online":true|false} — 每次连接/断开时。
  • {"type":"roster","roomId":"<guid>","status":"Playing","participants":[ ... ]} — 连接插座以及整个房间的连接、离开、座位更换、打开和启动。名单推后 start 是冻结的比赛名单，包括AI席位，并携带 gameSessionId 当房间有绑定的脚本会话时。
  • {"type":"result","roomId":"<guid>","teamScores":[3,1],"metadata":{...}} — 当主机提交结果时，或者当绑定脚本返回结果时。

确定大房间的尺寸

一个房间最多可容纳 100 名玩家，但实际限制是带宽。二进制通道是 主机路由：

  • 每个访客帧都会发送给主机；
  • 每个主机帧都被复制到每个来宾；
  • 每个帧携带 16 字节的发送者前缀。

接下来有两件事：

  • 主人的下载量随着客人数量的增加而增长。 它接收每位客人的意见。
  • 平台出口随着房间大小的平方而增长。 描述每个主机的快照 玩家随着玩家数量的增加而增长，并且它会被复制到每个客人。

工作示例：100 名玩家。每个访客每秒发送 30 个 32 字节的输入。主机发送20 快照/秒，每个播放器 12 字节，每个约 1.2 KB。每条消息的 TLS/TCP/WebSocket 开销为 取约70字节。

每个连接的限制限制了最坏的情况，而不是典型的情况。一个可容纳 100 名玩家的房间 每个连接以 30/s 的速度发送 8 KB 帧大约 390兆比特/秒 平台出口。

对于大房间：

  • 保持较低的宾客投入率 (10–20 Hz)，并且仅在输入发生变化时才发送输入。主持人 接收每位客人的输入，每秒处理数千条消息通常比较困难 对浏览器主机的限制大于带宽。
  • 保持快照较小。 量化仓位，根据最后确认的状态发送增量， 并将很少变化的实体分散到多个快照中。最多单帧 8 KB，在 100 名玩家的情况下，每个玩家还剩下大约 80 字节。
  • 房间频道不能针对一位客人。 主机帧发送给每个人，因此每个客人 接收整个世界。如果您的游戏需要每个玩家的兴趣管理（仅限附近 玩家，战争迷雾），在 容器游戏服务器 反而。一个 容器可以将帧寻址到各个玩家，主机不再是玩家的家 连接。

自动房间生命周期

  • 一个 Open 当回填截止日期过后，房间自动启动；空座位成为唯一命名的人工智能参与者，直到房间的 回填津贴.
  • 一个 Open 一旦每个座位都被占用（人类、创建时配置的人工智能玩家或混合），房间也会自动启动，而无需等待截止日期。
  • A Playing 当主人没有房间时，房间就会关闭 ws/v1/realtime 连接超过 60 秒 - 除非它绑定到仍处于活动状态的游戏会话，在这种情况下，主机角色会移动（见下文）。已连接的客人会收到最终名册推送，显示房间已关闭。
  • A Lobby 或者 Open 房间在没有连接参与者的情况下超过 60 分钟后关闭。

仅仅失去连接的参与者不会受到影响：重新连接套接字（最新的连接取代）并且 GET /rooms/mine 当房间还活着时，两者都会继续工作。

60 秒主持人规则和房间限制会议

服务器运行的匹配不属于其主机。 A Playing 房间绑定到游戏会话，即 仍然 active 永远不会因为主机离线而关闭：主机角色转移到联网的人身上 如果有的话，否则什么也不会发生。会话的生命周期决定了比赛的时间 结束，并在结束时关闭房间。以下规则适用于主持人路由的房间（无会话），并且 会话结束后转到绑定房间。

因此，房间内的游戏不需要主机的实时套接字。 一位主持比赛的主持人 ws/v1/games 并关闭（或从不打开） ws/v1/realtime 会议期间不关闭房间 是 active;仅当您的游戏需要名单推送时才打开实时套接字。

对于主机路由的房间，只需 ws/v1/realtime 套接字算作主机的连接。 时钟 当主机的最后一个实时套接字关闭时启动；从未连接过的主机是从 房间的 startedAt.

关闭房间并不会结束其在房间内的会话。 绑定房间在其关闭时仍然可以关闭 会话运行——通常是在最后一个人的时候 树叶 一个房间没有 正在进行中的加入。关闭它（名册推送、每个席位都已释放、等待邀请 已过期）不做任何其他事情：

  • 会话保持 active。它的玩家可以继续玩 ws/v1/games，并且脚本保留 以滴答率运行。
  • 从下一次调用开始， ctx.room.roster 是 空的 和每个人在 ctx.presence 有 left: true，因为关闭房间可以释放每个座位。 online 仍然反映 ws/v1/games 插座。一个处理的脚本 "每个人都离开了" 因为比赛结束后应该返回 result 然后。
  • 如果脚本稍后返回 result，会话照常结束，但是房间的 result 停留 null：房间已经关闭，因此结果仅存储在会话中。
  • 如果脚本永远不会返回 result，该会话像任何其他游戏会话一样退出：5 分钟 最后一次之后 ws/v1/games 套接字关闭，或 24 小时后没有玩家操作（请参阅 游戏——会话模型).

简而言之：一场房间内的比赛在主机离线后仍然存在；如果它必须结束时它的玩家 离开房间，在脚本中结束 ctx.presence 显示所有人都离开了。

安全概要

  • 每个端点都使用完整的 JWT 或者 游戏范围内的启动代币；启动令牌的 game_scope 必须与房间相匹配 gameSlug，因此两个游戏永远无法看到或加入彼此的房间。
  • 仅限参与者（加上待邀请者）阅读； open, seats, start， 和 result 仅限主机；邀请仅限好友。
  • 验证：席位/团队上限、始终为主持人留下席位的 AI 计数、每个用户一个活动房间（世界除外）、每个席位一名占用者、幂等开始、结果分数限制在 0-50、邀请随房间过期。
  • 传输：服务器标记的发件人 ID、基于角色的路由、帧大小上限、每个连接速率限制、无服务器端二进制有效负载解析。

房间内的会议

对于具有服务器后端的游戏 - server= 其清单中的脚本，或 容器 — 实时房间可以进行比赛 服务器权威 而不是在主机客户端上。以下几点是针对脚本编写的；容器通过其接收相同的名册 POST /sessions ctx（room, presence）和会员资格变更通过 POST /sessions/{id}/members。这将房间（大厅、邀请、匹配、​​回填）与服务器端模拟、经过验证的输入和脚本拥有的结果结合在一起。

  • 房间启动时创建会话。 当房间进入时 Playing，平台打造N人玩家 游戏环节 对于人类参与者。 AI席位仅存在于面向剧本的名单中。房间反应和花名册推动暴露 gameSessionId 这样客户就知道要打开哪个游戏套接字。
  • 游戏玩法移至 ws/v1/games. 客户端连接到 ws/v1/games?sessionId=<gameSessionId> 和交流 cmd/game 带有脚本的框架，就像任何脚本游戏一样；实时 WS 仅在名册/状态下保持连接。会话按照其脚本请求的支持速率进行计时 game.tickRateHz — 不请求任何内容的脚本在 0.25 Hz 处勾选，这是实时游戏所不需要的，因此声明一个（请参阅 游戏脚本).
  • 扩展脚本 ctx. 每次调用房间限制会话（createSession, onPlayerMessage, onTick）另外收到 ctx.room （房间 ID、元数据和冻结名单 — 人类 和 AI座位，按团队排序然后分配）和 ctx.presence ({ "<userId>": { online, left } } 对于每个现在或曾经是人类参与者的用户）。详情见 游戏脚本——房间限制的会话.
  • 服务器权威成就。 绑定会话的每个钩子都可以通过返回来授予成就 achievements: {userId: [keys]}，就像任何有脚本的游戏一样——包括来自 createSession，房间一开始就触发。解锁被推送给赚钱的玩家 ws/v1/games 作为 {"type":"achievement"} 帧。看 成就.
  • 脚本结束了比赛。 当脚本返回时 result，平台完成会话，将结果存储在房间中，并关闭房间（包括最终名单推送）。 POST /rooms/{id}/result 不用于房间内的游戏。
  • 启动失败。 如果会话创建失败，脚本支持的房间可以在没有绑定会话的情况下启动；检查 gameSessionId 在选择游戏交通工具之前。当容器支持的房间的服务器无法创建会话时，该房间将保持未启动状态。出现临时启动错误时通过退避重试；不要将其切换到主机模拟。
  • 主机路由的游戏可以纯粹为了成就而绑定会话。 二进制游戏通道永远不会在绑定会话上门控，因此在主机客户端上模拟的游戏仍然可以发送 server= 脚本的唯一作用是权威成就（和 elo）授予，而快速路径不断流动 ws/v1/realtime.

游戏如何使用它

  1. 创造：大厅创建者调用 POST /rooms 其团队布局不透明 metadata 斑点，无论多少 aiPlayers 比赛应从 开始，并成为东道主。在这里，人工智能占据了所有其他座位，这就是整个单人与计算机的流程。
  2. 邀请：主持人列出好友（GET /api/v1/me/friends）并发送 POST /rooms/{id}/invites。平台通知每个被邀请者（game_invite 推+ GET /api/v1/me/game-invites），这样他们就可以在不打开游戏的情况下从仪表板接受；已在游戏中的受邀者通过投票看到相同的邀请 GET /rooms/invites。接受后，他们将成为东道主团队的席位。
  3. 打开: 主持人打电话 POST /rooms/{id}/open。单人玩家打电话 POST /rooms/quick-join 并降落在最古老的开放房间，有一个空闲座位（在 404 他们创建并打开自己的房间）。
  4. 连接: 大家都打开 ws/v1/realtime?roomId=… 和手表 roster/presence 当座位填满时推动。
  5. 开始：在回填截止时间，当所有席位都被占用时，或者当主持人强制开始时，剩余的空席位成​​为AI参与者（最多 回填津贴）并且名册冻结。 主机路由游戏：访客以二进制帧的形式发送输入（它们仅到达主机）；主机广播快照。 房间限定脚本游戏: 每个人都连接 ws/v1/games?sessionId=<gameSessionId> 并与脚本进行对抗 cmd/game 帧。
  6. 比赛中途离开： 在一个 正在进行中的加入 房间内的座位已腾出给下一位玩家。否则，在比赛期间离开的球员 Playing 被 AI 参与者取代（同一座位，服务器生成的新昵称），并且可以立即再次排队；如果主机离开，主机角色将传递给加入时间最长的剩余人员。在主机路由的游戏中，断开实时连接的主机在比赛结束前有 60 秒的时间重新连接；房间内的比赛永远不会因为主人不在而结束。
  7. 结束：主机路由 — 主机 POST 结果；服务器夹紧分数，存储结果，将其推送到所有套接字，然后关闭房间。房间限制 — 脚本返回 result 平台将其存储并关闭房间。
