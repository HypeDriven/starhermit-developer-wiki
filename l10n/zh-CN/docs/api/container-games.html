容器托管的游戏服务器

StarHermit 游戏可以将其权威服务器逻辑作为容器映像而不是 沙盒 JavaScript 文件。这使得服务器可以使用 Rust、Go、C++ 或任何其他可以运行的运行时 提供 HTTP 和 WebSocket 服务。面向浏览器的 游戏API 保持不变：客户仍然 使用游戏范围的启动令牌、REST 会话以及 ws/v1/games JSON 帧。

容器托管对 starhermit.com 上的任何登录用户开放。自托管部署可以 将其限制在运营商许可名单中；那里未设定的许可名单不承认任何人，而不是所有人。 这同样适用于注册表映像和上传的 server/image.tar，所以两条路线都不是 安静地比对方更宽容。

初始游戏注册后，开发者还可以推送构建的游戏 .tar.gz 含有 server/image.tar (docker save 输出）通过 POST /api/v1/me/github-games/{id}/bundle。平台加载并摘要固定图像和队列 部署重新启动。看 GitHub Games — 推送游戏包 和 专用服务器教程.

在围绕该推送构建发布管道之前，值得了解有关该推送的以下详细信息：

  • 一个大 docker save 可以超过 CDN 的 ~100 MB 请求正文上限，其答案为 413 平台永远不会看到——没有 limitBytes，任何日志中都没有您可以阅读的内容。将存档推过去 ws/v1/game-upload 反而;相同的存档，相同的 补贴，同样的答案。
  • 您上传的图像本身就是声明。 一款还没有后端的游戏——一个是从 声明为 none 的上传文件夹 — 从摘要中获取其容器定义 刚刚加载。您不需要 container.image= 首先在清单中。
  • 重新推送会应用其清单声明的旋钮并保留其省略的旋钮。 改变 container.port 现在重新上传会将部署移动到该端口；遗漏清单 捆绑包的内容除了图像外什么都没有改变。
  • 上传的图像胜过清单，包括超过 server= 线和清单 声明两者 server= 和 container.image= 在加载任何内容之前被拒绝。
  • 您的本地镜像标签不会选择已部署的版本。 上传的图像由其固定 内容摘要。您可以根据需要在本地标记它；验证上传的摘要和部署 发布后的状态。
  • ?mode=merge 仅修补客户端文件。 A server/image.tar 在合并中加载完全一样 替换时——图像不能半更新。看 部分更新.

显现

在存储库中声明图像 starhermit.txt:

name=Void Marshals
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html

container.image=ghcr.io/octocat/vm-server@sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
container.port=8080
container.health=/health
container.memory_mb=1024
container.cpu=1.0
container.env.LOG_LEVEL=info

仅有的 container.image 是必须的。端口和健康路径默认为 8080 和 /health。 内存和CPU是请求，不是保证；平台将它们限制在操作员限制范围内。

您的映像有大小上限：未压缩的 2 GiB，除非操作员已将您的游戏设置为另一个，并且 注册表拉取需要五分钟。超过天花板的拉力被中途放弃，上传 image.tar 超过它被拒绝 413，并且一旦未压缩就会变得更大的图像是 再次删除。 container.env.* 仅用于非秘密配置。

提交将被拒绝，除非：

  • 图像被摘要固定为 name@sha256:<64 lowercase hex>。不接受可变标签。
  • 注册表已列入白名单，且映像位于经过验证的存储库所有者的命名空间下； 目前这意味着 ghcr.io/<github-owner>/....
  • 该清单恰好声明了一个服务器运行时。 server= 和 container.image= 是相互的 独家。
  • 环境名称有效且不以保留开头 STARHERMIT_ 前缀。

切勿将凭据放入 starhermit.txt;它是一个公共存储库文件。

协议v1

容器提供 HTTP/1.1 服务 container.port。每个平台 HTTP 请求和 WebSocket 升级都包括 X-Starhermit-Invoke-Key，其值 匹配注入的 STARHERMIT_INVOKE_KEY;当请求不存在或错误时拒绝请求。

端点 目的
GET <container.health> 返回 200 当服务器准备好时
GET /describe 声明协议版本、滴答率、容量和成就
POST /sessions 启动会话，或在以下情况下恢复会话 snapshot 存在
GET /sessions/{sessionId}/snapshot 返回当前的持久状态
DELETE /sessions/{sessionId} 拆除会话
POST /sessions/{sessionId}/members 选修的： 玩家正在加入或离开正在运行的会话
WS /control 部署范围的出站控制通道
WS /stream 两个方向的游戏框架

一个容器承载一场游戏的所有实时会话。保持会话状态由 sessionId 并做 不要假设该过程将在一场比赛的生命周期中持续存在。

GET /describe

{
  "protocol": 1,
  "tickRateHz": 20,
  "maxSessions": 48,
  "replays": true,
  "persistent": false,
  "achievements": [
    { "key": "first-blood", "name": "First Blood", "description": "Score first.", "points": 10 }
  ]
}

protocol 必须是 1. tickRateHz 和 maxSessions 是请求并且可能被限制。平台 永远不会进入容器的循环，所以 tickRateHz 告诉它你的游戏有多快 动作 而不是如何 快速运行它：它可以阻止平台请求快照的速度快于游戏生成的速度 新状态。声明循环实际运行的速率。接受分数费率（0.5 是一 每两秒打勾一次），并且缓慢的速率确实会延长快照请求之间的间隔 - 这就是游戏崩溃所花费的费用。未声明任何内容的容器离开检查点 节奏到快照成本单独。成就条目使用与以下相同的字段和限制 剧本宣布的成就。声明的和所有者创建的密钥可以稍后授予。

replays 要求平台将每个已完成会话的最后状态保留为 重播，服务于 GET /api/v1/games/{slug}/replays/{sessionId} （看 游戏 API — 重播）。它必须 是字面意思 true 或者 false;没有声明任何内容的游戏没有重播及其重播端点 回答 404。与滴答率一样，它是一个请求 - 操作员可以回答特定游戏 不管怎样——所以让你的客户分支 replaysEnabled 从 GET /api/v1/games/{slug} 而不是在 你声明了什么。无论哪种方式，快照都不受影响：实时会话是否需要还原点 或者不保留最后一个。

persistent （文字 true/false）要求会话 暂停而不是结束 当每个 玩家已离开。暂停会停顿会话：平台拍摄最终快照并存储它，然后 来电 DELETE /sessions/{id};下一个加入的玩家将其带回来 POST /sessions 与 那个 snapshot，与崩溃恢复完全相同，但不花费重新启动预算或发送 resumed。恢复的持久会话还带有 pausedMs，暂停所花费的总时间。请参阅 持久会话教程.

linkedAchievements （最多 8 个其他游戏的 slugs 的数组）将玩家的解锁内容放在这些游戏中 游戏进入ctx POST /sessions，在创建和恢复时。看 其他游戏的成就.

目前的 /describe 读者不导入 queues 财产。因此容器游戏使用 隐含的 default 1v1配对队列；此处添加形状不会启用更大的匹配。 查看 GET /api/v1/games/{slug}/queues 以获得有效的形状。清单截止日期开始和 AI 席位 限制仍然适用于该形状；看 牵线搭桥.

POST /sessions

该请求与 JavaScript 游戏收到的上下文形状相同：

{
  "now": 1769500000000,
  "random": 0.418,
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "players": [
    { "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "name": "alice", "elo": 1312 }
  ],
  "sessionState": null,
  "playerStates": {
    "7c9e6679-7425-40de-944b-e07fc1f90ae7": null
  }
}

字段语义匹配 脚本上下文， 包括 匹配席位、AI旗帜和空座 用于游戏 配置开始截止日期 starhermit.txt，以及每个玩家当前的 elo （1200 直到 评级）。因为容器游戏无法仅读取脚本 playerStates，那个名单 elo 是如何 它在比赛之间向前推进评分，而不是从 1200 开始每场比赛；更改评级 仅通过发送 eloUpdates。使用标准结果信封进行响应，例如：

{ "ok": true, "sessionState": { "round": 1 } }

恢复时请求还包含 snapshot，保存平台保留的最后一个状态， 和 restoredFrom，Unix 毫秒时间戳。从快照重建可播放会话。 当玩家重新加入暂停的会话时，持久游戏会以相同的方式恢复， pausedMs 在身体里。

GET /sessions/{sessionId}/snapshot

返回带有完整信息的标准信封 sessionState 还原点：

{ "ok": true, "sessionState": { "round": 3, "scores": [2, 1] } }

平台定期检查活动会话。快照响应还可以包括 playerStates, eloUpdates, achievements, scores， 或者 result;他们通过了相同的验证并且 作为脚本结果的持久性规则。对于与 重播，最后一个状态a 达到的已完成会话是平台保留的重播内容 - 因此请设置该状态 可重建，而不仅仅是可恢复。

POST /sessions/{sessionId}/members

选修的。玩家可以 加入正在进行的会话，通过一个 实时房间 这允许 或者接受朋友的 邀请加入他们正在玩的会话, 房间可以让玩家让出自己的座位，而无需人工智能占据。平台询问你的容器 在更改最终完成之前。主体是普通的ctx，带有 players 已经反映了 改变，加上 membership:

{
  "now": 1769500000000,
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "players": [
    { "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "name": "alice" },
    { "id": "9b2f8c1a-1111-4222-8333-444455556666", "name": "carol" }
  ],
  "membership": { "change": "joined", "userId": "9b2f8c1a-1111-4222-8333-444455556666", "name": "carol", "team": 0, "slot": 1 }
}

change 是 joined 或者 left。使用标准信封答复：

  • 可以拒绝加入。 {"ok": false, "error": "This world is full."} 将玩家转开， 座位被退还并且没有任何记录；邀请接受答案 409 并且邀请仍然存在 待定。如果您不实现端点，则每个加入都会被拒绝： 404, 405 和 501 意思是 "这场比赛不会让玩家中途休息"，所以为固定名单编写的游戏永远不会有 陌生人掉进了里面。
  • 休假是最后的决定 无论你回答什么。
  • 答案可能会带有 achievements 和 scores. A sessionState 被忽略：发送 snapshot 超过 /control 如果更改值得检查点。

加入后，新玩家的命令开始到达 /stream 他们在 players 在每一个 稍后恢复。离开后，它们的框架停止并且它们的套接字关闭。每个连接的客户端 收到一个 membership 框架 无论哪种方式，会话聊天都会得到或失去 会员。

A 暂停的持久会话 没有被问到，因为它没有运行。恢复的是 恢复它携带当前 players，因此将您之前在恢复中未见过的玩家视为 加入了。

游戏直播

WS /stream 在两个方向上使用二进制消息：

[1 byte type][16 byte sessionId][16 byte userId][payload...]

GUID 使用其 16 字节 .NET 线路表示形式。

  • 类型1、平台→集装箱： 玩家命令。平台对经过认证的用户id进行标记； 有效负载是来自客户端的 JSON 值 cmd.data.
  • 类型2、容器→平台： 游戏有效负载。使用其用户 ID 来称呼一名参与者，或使用 要广播的全零用户 ID。有效负载必须是有效的 JSON；客户在里面收到它 {"type":"game","data":...}.

会话固定到流连接以保持顺序。绝不接受或派生玩家 来自命令 JSON 的身份 - 经过身份验证的标头具有权威性。

控制通道

发送 JSON 文本消息 WS /control 为了获得持久的效果：

{ "type": "snapshot",     "sessionId": "...", "state": { "round": 3 } }
{ "type": "achievements", "sessionId": "...", "unlocks": { "<userId>": ["first-blood"] } }
{ "type": "elo",          "sessionId": "...", "updates": { "<userId>": 1312 } }   // absolute ratings, not deltas — see games.md#elo-per-match
{ "type": "scores",       "sessionId": "...", "scores": { "<boardKey>": { "<userId>": 4200 } } }
{ "type": "result",       "sessionId": "...", "result": { "kind": "win", "winner": "..." } }
{ "type": "backpressure", "load": 0.75 }

该平台仅接受路由到此部署的会话的效果，过滤收件人 会话参与者，将成就键限制为游戏的成就（由声明或创建） 它的所有者），限制 scores 到游戏本身的 所有者创建的排行榜 — 每个玩家都保留自己的 最好的——并应用国家预算。 result 结束会话；该会话的后续影响将被忽略。 backpressure.load 是 夹在 0..1 并帮助平台考虑当前的部署负载。

在语义上重要的事件（例如进球或回合转换）之后推送快照，而不是 而不是仅依赖定期检查点。

容器环境和服务器API

多变的 意义
STARHERMIT_PROTOCOL 协议版本（1)
STARHERMIT_GAME_SLUG 这游戏的梗
STARHERMIT_INVOKE_KEY 秘密预计在 X-Starhermit-Invoke-Key;向您的容器验证平台
STARHERMIT_REFRESH_KEY 仅用于更新服务器令牌的单独秘密
STARHERMIT_API_BASE 可从隔离网络访问平台 API 基本 URL
STARHERMIT_SERVER_TOKEN 窄服务器到服务器 API 的不记名令牌即将过期

服务器令牌没有玩家身份，不能使用帐户或玩家操作。它可以读取 GET /api/v1/time，协调自己的会话，并调用服务器支持的 审核路线 为了自己的游戏。生成路线是 已保留且不可用.

更新服务器令牌

注入的服务器令牌会过期（默认为 24​​ 小时）。之前刷新一下就好了 STARHERMIT_SERVER_TOKEN_EXPIRES_IN 经过：

POST /api/v1/games/{slug}/server/token
X-Starhermit-Refresh-Key: <STARHERMIT_REFRESH_KEY>

{ "token": "eyJhbGciOi...", "expiresInSeconds": 86400 }

有意在不使用过期的承载令牌的情况下调用此端点。专用刷新键 与实时部署进行比较，即使在旧令牌过期后也能正常工作。它是独特的 来自 STARHERMIT_INVOKE_KEY：调用密钥验证对您的进程的平台调用，而 刷新密钥向平台验证您的流程。每当容器启动时，两者都会旋转。 在报告生命周期的一半左右安排更新并自动替换令牌。

"每当容器启动时" 不仅仅包括部署。空闲部署在以下时间后停止 没有会话的安静时段（默认为 15 分钟），并由下一个玩家重新开始。一个坠毁的集装箱是 重新启动。每次启动都是一个带有新密钥和新令牌的新容器，因此请从 运行过程的环境。切勿将它们烘焙到映像、配置文件或快照中。

如果启动失败 The game container returned 401 for GET /describe，平台的关键和 你的流程的关键不同意。读 STARHERMIT_INVOKE_KEY 在启动时并比较未修改的情况。如果验证仍然失败， 报告游戏 ID 和清理的启动日志；不要松开支票。

协调会话

GET /api/v1/games/{slug}/server/sessions/{sessionId} 和 Authorization: Bearer <STARHERMIT_SERVER_TOKEN> 返回平台的当前会话视图：

{
  "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "status": "active",
  "players": [
    { "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "username": "alice" }
  ],
  "createdAt": "2026-07-27T16:00:00Z",
  "finishedAt": null,
  "chatConversationId": "d290f1ee-6c54-4b01-90e6-d701748f0851",
  "result": null
}

恢复后容器需要确认平台是否还考虑时使用此 会话处于活动状态。禁止使用其他游戏的令牌或玩家启动令牌。

chatConversationId 可以是 null 在已完成的会话上，即使它在实时状态下有一个：当 比赛结束，没有人发送聊天消息，平台宁愿放弃空游戏对话 而不是在会话行的生命周期内保留它，并且该字段读取 null 然后。将其视为现在 仅当会话处于 active.

隔离

游戏容器无法访问互联网。它只能通过 StarHermit API 访问 STARHERMIT_API_BASE;它无法到达其他游戏、平台服务或主机。供应商全部 运行时依赖关系到图像中。

根文件系统是只读的，除了一个小的 /tmp;该进程以强制非 root 身份运行 没有 Linux 功能、没有卷以及 CPU、内存和进程限制的用户。请勿安装 启动或持久时的包仅将状态匹配到本地磁盘。

失败与恢复

如果进程终止，平台将重新启动部署并从其进程重新创建其实时会话。 最后的快照。连接的玩家收到一个平台框架：

{ "type": "resumed", "sessionId": "...", "lostMs": 750 }

客户端应放弃本地预测并等待游戏的正常全状态负载。一次会议 当不存在可用快照、太旧或会话已损坏时，将被放弃而不是恢复 重新启动过于频繁。平台在没有获胜者或 elo 变化的情况下完成比赛并发送：

{ "type": "abandoned", "sessionId": "...", "reason": "server_failure" }

reason 是 server_failure 当恢复不安全或更换从未开始时，以及 restore_failed 当重新创建会话失败时。发布新图像可恢复实时会话 进行替换（或放弃那些太陈旧的）。启动失败——拉超时， 容器退出，或者它从未及时回答其运行状况检查 - 会通过退避重试，就像 崩溃。十分钟内三次失败尝试（操作员可调）将禁用部署（failed), 它是 不是 被玩家的需求唤醒。临时托管中断可以在不花费游戏故障津贴的情况下重试。

没有实时会话的部署将在闲置 15 分钟后停止（操作员可以将游戏设置为不同的窗口）。 已暂停 执着的 会话停在容器外并且不会继续运行。 下一个会话请求针对 stopped 部署唤醒它（pending → 健康门 → running）；输掉那场比赛是 503 说比赛开始了。仅有的 stopped 被唤醒这个 方式——从不 failed.

设计 POST /sessions 恢复和快照节奏作为游戏协议的一部分，而不是作为 可选的优化。

游戏所有者可以列出并结束搁浅的会话： GET/DELETE /api/v1/me/github-games/{id}/sessions[/{sessionId}].
