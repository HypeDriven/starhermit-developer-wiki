游戏脚本

StarHermit 权威游戏可以由 单个 JavaScript 文件 在沙盒中的服务器端执行 金特 引擎。该脚本是该游戏规则的唯一权威：它验证每个玩家命令、改变状态、决定每个客户端可以看到的内容、计算 Elo 并结束游戏。客户的权限为零。该页面记录了 JavaScript 运行时；需要另一种语言的游戏可能会实现 容器游戏服务器 协议。两者都使用相同的面向玩家的 游戏API。贯穿始终的工作示例是国际象棋——参考实现位于 HypeDriven/明星隐士国际象棋.

执行模型

  • 每个游戏一个 JS 文件，在 每次调用新鲜的沙盒 Jint 引擎。在调用之间，内存中不会保留任何内容——所有状态都存在于您返回的文档中。
  • 无环境 Date 或者 Math.random。时间和随机性提供为： ctx.now （纪元女士）和 ctx.random （漂浮在 [0, 1)).
  • 当玩家发送持久命令、创建会话以及定期时，平台会调用脚本 onTick 扫掠（参见 游戏 API — 运行时计时）。即时的 {type:"input", realtime:true} 帧是例外：它们被缓冲最新胜利并作为批次传递到下一个报价。

切入点

公开处理程序 globalThis.game。六种可选 静止的 声明与它们并排放置： tickRateHz 询问平台调用频率 onTick — 如果你的游戏依赖于 勾选，因为没有任何内容的游戏每四秒勾选一次（请参阅 滴答率), achievements 注册游戏的成就（参见 成就), replays 要求平台保留您已完成的会话（请参阅 重播), persistent 停顿 会议，而不是在每个人都离开时结束会议（请参阅 持续会话), linkedAchievements 列出您在其中获得解锁的其他游戏 ctx.linkedAchievements （看 其他游戏的成就）， 和 queues 宣称 匹配匹配接受的形状（参见 游戏 — 对接会）。一场比赛 声明没有队列有一个隐式 1v1：

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

通过评估您的脚本来读取声明 游戏发布或更新时, 不是在每次调用时 - 所以它们必须是静态值 game 目的。发布更新 应用更改。

  • createSession(ctx) — 创建会话时调用（匹配、接受邀请、AI 练习或实时房间启动 — 请参阅 房间内的会议).
  • onPlayerMessage(ctx) — 要求通过游戏 WebSocket 接收持久的客户端命令。输入明确标记 realtime:true 绕过这个入口点。
  • onMembershipChange(ctx) - 选修的。当玩家加入或离开正在运行的会话时调用（ 正在进行中的加入室，或一个 邀请参加正在进行的游戏). ctx.players 已经反映了变化，并且 ctx.membership 是 { change: "joined" | "left", userId, name, team, slot }。返回 { ok: false } 拒绝加入；没有此钩子的脚本会拒绝每个连接。无论您返回，休假都是最终决定。成就和分数可能取决于结果；一个 sessionState 被忽略。
  • onTick(ctx) — 由平台的计时器服务以有效滴答率调用；最新的实时输入可在 ctx.inputs。分辨率为 0 Hz 的游戏不会收到定期调用，但该函数仍应存在以满足脚本契约。

上下文对象

ctx = {
  now: 1721473200000,              // ms epoch, from the host clock
  random: 0.7231,                  // float in [0, 1), from the host RNG
  sessionId: "0f8fad5b-...",       // current session id
  pausedMs: 0,                     // persistent games only: total ms this session has spent paused
  players: [                       // session participants
    { id: "7c9e6679-...", name: "alice", elo: 1312 },
    { id: "00000000-0000-4000-8000-00000000a1a1", name: "The House", ai: true, elo: 1200 }
  ],
  sessionState: { /* ... */ },     // this script's session document, or null
  playerStates: {                  // per-player documents (elo, history), or null
    "7c9e6679-...": { elo: 1200, wins: 4, losses: 2, draws: 1, /* ... */ }
  },
  message: {                       // onPlayerMessage only
    from: "7c9e6679-...",          // the authenticated user id — trusted
    data: { type: "move", from: "e2", to: "e4" }  // client payload — untrusted (example: a chess move)
  },
  inputs: [                        // onTick only; omitted when none are pending
    { from: "7c9e6679-...",        // authenticated sender id — trusted
      data: { type: "input", seq: 42, mx: 0.7, mz: -0.2 } }
  ]
}
  • AI 席位（如果存在）标记为 ai: true 在其玩家条目上。
  • 每个玩家参赛作品都带有 elo，该游戏的当前评级 - 与存储在中的相同数字 playerStates[id].elo，出现在名单上，因此是一个容器游戏（无法读取 仅脚本 playerStates) 可以从中播种匹配逻辑。尚未评分的玩家正在阅读 1200。它在创建、勾选、消息和恢复方面是相同的；只能通过以下方式更改评级 eloUpdates.
  • 一款游戏宣告 linkedAchievements 还得到 ctx.linkedAchievements: { <playerId>: { <otherSlug>: [unlocked keys] } }，在每次调用时重新读取。看 其他游戏的成就.
  • 房间绑定会话（从实时房间开始）获得两个额外的 ctx 字段， ctx.room 和 ctx.presence， 在 每一个 调用——参见 房间内的会议.
  • 不信任任何来自 ctx.message.data 或者 ctx.inputs[].data. 可信身份对应的是 from，服务器从经过身份验证的连接附加它 - 客户端永远无法提供或欺骗它。
  • 输入选择批处理 {type:"input", realtime:true, ...}。未标记 input 命令保持持久 onPlayerMessage 要求向后兼容。实时输入对每个发送者使用一个待处理槽：移动是最新获胜，而 pass, shoot， 和 tackle 动作边缘被合并，因此后续移动样本无法在下一个刻度之前擦除它们。脚本在使用批次时必须限制并验证每个值。

滴答率

平台运行 onTick 以可配置的速率扫描每个活动会话。 您的脚本要求它想要的速率 通过声明静态 tickRateHz 在游戏对象上的入口点旁边：

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • 声明已读 当您的游戏发布或更新时，不是在每个刻度上。更改后发布更新。
  • 声明无速率的游戏以 0.25 Hz 为刻度 ——每四秒一次。这已经足够了 裁决移动时钟或超时，平台几乎不花费任何成本，但速度太慢 对于您的游戏玩法所依赖的任何内容。如果 onTick 驱动您的游戏，声明您需要的速率。
  • 请求被限制在平台最大值（30赫兹 默认情况下），因此游戏可以要求更少 超出平台允许的范围，但绝不会超过。询问 0 完全禁用游戏的刻度 只对玩家的命令做出反应。
  • 价格可能是 分数: 0.5 是每两秒一次。最小的非零利率是 0.01 Hz — 向其提出一个较小的正数，而不是将其视为选择退出，因为 小分数是一个缓慢的游戏。勾选仅关闭 0 或负利率。缺失或 不可用的声明（字符串， null, NaN) 采用默认值 0.25 Hz。
  • 操作员可以在任一方向上覆盖特定游戏的费率。
  • 实时输入是报价之间的最新胜利，而离散动作边缘保持有序。速度慢的接收者可以跳过过时的快照，但不能延迟模拟或其他接收者。

重播

当会话结束时，平台可以保留其最终结果 sessionState 作为 重播 — 的 文件送达者 GET /api/v1/games/{slug}/replays/{sessionId} （看 游戏 API — 重播）。重播的存储时间与比赛记录一样长 是，所以 只有当你的游戏提出要求时，你的游戏才会得到一个:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • 声明必须是文字 true 或者 false — 其他任何内容都被视为没有声明，并且 没有声明任何内容的游戏没有重播。
  • 已读 当您的游戏发布或更新时。更改后发布更新。
  • 平台运营商可以以任何一种方式回答特定游戏，因此声明是一个请求 而不是保证。 GET /api/v1/games/{slug} 将答案报告为 replaysEnabled — 将您的重播 UI 分支到此，而不是您的脚本要求的内容。
  • 重播关闭后没有其他任何变化：您的会话状态仍然被存储并仍然返回给 每次调用都作为 ctx.sessionState，并且仍然是崩溃恢复点。什么游戏啊 没有重播不会得到比会话寿命更长的副本，因此它的重播端点答案 404.
  • 设计最终作品 sessionState 值得重播——移动日志，或者您的客户需要的任何内容 重建比赛。国际象棋参考实现保留 state.game.moves 并踩它 通过平台执行的相同规则模块。

持续会话

一款游戏宣告 persistent: true 当每个玩家离开时，会话仍保持不变。约15 最后一次断开会话后的秒数 暂停 - 不 onTick 来电——以及第一个 播放器重新连接即可恢复。断开连接或不活动会暂停会话，而不是放弃它。游戏结果，楼主 操作、明确的最终成员离开、配置的保留到期或终端恢复失败都可以 还是结束吧。看 会话生命周期.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • 必须是字面意思 true 或者 false。已读 当您的游戏发布或更新时.
  • ctx.now 保持挂钟。持久会话也得到 ctx.pausedMs，花费的总时间 暂停了，所以 ctx.now - ctx.pausedMs 是一个无人在场时静止不动的时钟。
  • 暂停的会话会计入每个玩家的会话上限，因此请给玩家一个结束会话的命令 世界有一个 result.

请参阅 持久会话教程 一个有效的例子和客户流程。

对接会座位布局

新的匹配会话收到 ctx.matchmaking 在 每一个 调用（创建、命令和勾选）。 即使稍后重新部署游戏，它也会保留队列形状和座位：

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players 仅包含占用的座位， team 和 ai:true 对于人工智能。团队/槽位索引为 零基础。 AI ID 在此会话中保持稳定，并且不是 StarHermit 帐户 ID。只有人类 拥有会话/聊天会员资格，可以接收帐户玩家状态、评级或成就写入。 保持AI状态 sessionState。将客户需要的名册字段复制到游戏状态中 或广播。较旧的会话和非匹配会话可以省略 ctx.matchmaking.

声明开始截止日期和最大 AI 数量 starhermit.txt。 与AI计数 0，空位依然空着。相同的上下文被传递到容器服务器。

房间内的会议

一个会话可以是 绑定到实时房间：当一个 实时房间 对于一个游戏 server= 脚本开始，平台为房间创建一个 N 玩家会话 人类 参与者（AI 席位仅存在于面向脚本的名册中）。这就是服务器权威的实时游戏（例如足球）的运行方式：房间提供大厅/匹配，脚本运行比赛。看 实时房间——桥梁 对于房间侧的生命周期。

每次调用 (createSession, onPlayerMessage, onTick) 的房间绑定会话接收两个额外的 ctx 字段：

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online — 用户在任一连接注册表上都有一个实时套接字（实时房间 或者 ws/v1/games).
  • presence.left — 用户不再拥有活跃席位：他们明确离开，他们的席位被转换为 AI 参与者。 left 是永久的； online 可能会扑动。该脚本预计将驱动 AI 从这些标志接管/重新加入逻辑。
  • 每次调用时都会重新读取名册，因此座位转换（人类→人工智能）会在发生时显示出来。

当房间绑定的脚本返回时 result，平台结束会话， 将结果存储在房间中，并关闭房间 ——不涉及主办方提交的结果。

反之则不然： 房间关闭并没有结束其会话。 如果房间首先关闭（例如，因为最后一个人在没有加入的情况下离开了房间 - 不仅仅是因为主机离线，这只会在会话处于活动状态时移动主机角色），会话将继续运行， ctx.room.roster 变得空虚，每个人都表现出来 left: true。返回 result 那么比赛是否应该以房间结束。看 实时房间 — 60 秒的主持人规则和房间限制会话.

返回形状

每个入口点返回相同的形状（所有字段都是可选的，除了 ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

关键规则：

  • sessionState 和每个条目 playerStates 代替 存储的文档 - 始终返回完整的文档，从不差异。
  • 仅列出的消息 broadcast 发送给客户端，每个地址都指向明确的玩家 ID 或 "all"。没有其他泄漏。
  • eloUpdates 是评级改变的唯一方式。数值是每个玩家的 新的绝对评级，按发送时应用 - 平台不会限制每场比赛的更改，因此请自行限制（请参阅 每场比赛 Elo）。主机使用它们进行匹配并将其发布到游戏排行榜；客户永远不能直接提交分数（请参阅 排行榜）。保留评级 playerStates[id].elo 所以一个业主的 评级重置 也到达您的副本。
  • achievements 这是授予成就的唯一途径。密钥根据游戏的成就进行解析（由其所有者声明或创建）并由平台保留；看 成就.
  • scores 是你的游戏自己的排行榜发生变化的唯一方式 - 请参阅 排行榜.
  • 结束游戏通过 result。然后主持人结束会议，并进行游戏 重播 存档决赛 sessionState 作为重播（由 GET .../replays/{sessionId} - 看 游戏API).

成就

你的脚本是 仅有的 可以解锁游戏成就的东西。没有客户 他们的终点： POST /api/v1/me/achievements/unlock 完全拒绝游戏范围内的成就， 并且发布者 CRUD 端点拒绝接触它们。游戏所有者可以添加成就 所宣布的通过 /me/github-games/{id}/achievements; 您的脚本以完全相同的方式通过密钥解锁这些内容。这使得作为服务器的成就- 和游戏的其他部分一样权威，这就是机制 任何 游戏与 server= 脚本 应该使用 - 包括其游戏玩法在其他地方运行的游戏（请参阅 哪些游戏可以使用这个).

宣布

静态的 achievements 数组上的 game 目的。仅有的 key 是必须的：

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
场地 类型 笔记
key 细绳 必需的。 稳定的id，≤128个字符，游戏内唯一。第一个之后的重复项将被忽略。
name 细绳 默认为 key.
description 细绳 默认为 "".
icon 细绳 可选网址。
secret 布尔值 对玩家隐藏直至 他们 解锁它。默认为 false.
points 数字 限制在 0–10000。默认为 0.

该数组在游戏发布或更新时应用：

  • 定义匹配 key - 编辑名称、图标、点数或秘密标志会更新现有定义，并且每个已经获得它的人都会保留它。
  • 您停止声明的密钥已被删除 仅当没有人解锁时。赢得的历史永远不会被破坏，因此拥有该成就的玩家仍然可以看到已退役的成就。
  • 最多 100 每场比赛的成就；除此之外的额外内容将被删除。
  • 声明是 尽最大努力：跳过格式错误的条目。始终确认已发布的定义 GET /api/v1/games/{slug}/achievements 更新游戏后。

开锁

返回一个 achievements 地图来自 任何 入口点—— createSession, onPlayerMessage， 或者 onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • 解锁有 幂等的 - 重新断言玩家已经持有的密钥是无操作的，因此脚本可以安全地根据每次勾选时重新评估的条件进行奖励，而不是跟踪 "已经授予" 在它自己的状态下。
  • 未知的密钥（游戏所有者既未声明也未创建）、不是本次会话参与者的用户以及 AI 席位将被默默忽略。
  • 最多 32 每个玩家每次调用都接受密钥；同一数组中的其他键将被删除。
  • 行与调用的其余写入一起保留，因此解锁无法在调用失败后继续存在。

送货

每个新授予的解锁都会被推送给赚钱的玩家 ws/v1/games 作为一个独特的框架—— 这是平台真理，不是你的 broadcast 消息：

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

解锁授予自 createSession 在任何套接字存在之前着陆，因此它们到达时没有框架 - 客户应该阅读 GET /api/v1/games/{slug}/achievements 加载并将框架视为 实时更新路径。全表面在 成就.

排行榜

除了 elo 板之外，您的游戏还可以拥有其所有者通过以下方式创建的排行榜 POST /api/v1/me/github-games/{id}/leaderboards, 每个都有一个 key。通过返回发布给他们 scores 从任意入口点 — 棋盘钥匙 → 玩家 ID → 数量：

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • 每个玩家都保留自己的 最好的 每个板上的分数，按板的排序方向，因此报告 每一个结果——更糟糕的结果都会被忽略。
  • 仅会话参与者计数。未知或不活动的键，以及超出棋盘规则的分数， 都被默默地丢弃了。每次返回最多 16 个板。
  • 不像 eloUpdates，没有任何内容发布到 playerStates — 保留您自己的副本 playerStates 如果比赛需要回读个人最好成绩。

你的脚本运行的地方

无限制地递归、耗尽内存或超出其时间预算的脚本会失败 调用。其失败结果不被应用。命令或刻度报告以下之一：

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

您的游戏在服务器中的份额

  • 脚本时间。 游戏的所有会话共享脚本时间预算，即每秒 2000 毫秒 默认情况下，根据每次调用实际花费的时间来收费。超过其份额的游戏被拒绝 比排队：跳过一个刻度，用以下命令应答命令 "该游戏的使用量超过了其份额 现在的服务器；稍后再试。"，并创建会话返回 429.
  • 命令。 每个玩家在每个会话中每秒可以发送 20 个持久命令（带有短突发） 津贴）；除此之外，命令的响应是 error 框架， "命令太多；减速。" 该帧不包含 HTTP 状态。实时输入受到单独限制。
  • 结果。 会话结束的结果最多可能是 64 KB；较大的被拒绝 422.
  • 脚本大小。 A server= 脚本最多可为 2 MB；较大的被拒绝 422 之前 它被存储或解析。

运营商可以针对单个游戏提高或降低其中的每一项。

预算

脚本在这些资源预算下运行：

  • 每次调用约 250 毫秒 CPU
  • 32MB内存
  • 每次调用的语句上限
  • 每个玩家的状态字节预算 - 所有状态文档必须保持可序列化且较小
  • 当值变成文本时，最多嵌套 64 层。入口点返回的任何内容，每个 声明， JSON.stringify， 和 Array.prototype.join/toString/toLocaleString 拒绝一个 更深层次的价值 RangeError （返回的调用失败： "嵌套超过 64 层 深"). JSON.parse 已经停在 64 处，因此更深的值永远无法往返。 flat 展平最多 64 层，如果数组嵌套更深，则抛出异常 — 包括包含以下内容的数组 本身。
  • 一次调用分配的内存不能超过内存预算。 repeat, padStart/padEnd, concat 和 replace/replaceAll 扔 RangeError: Invalid string length 当结果可能超过一半时 以字符为单位的预算（默认为 32 MB，为 16M；正则表达式替换是有限的，就好像每个 位置匹配，仅影响大约一百万个字符或更多的字符串）。 ArrayBuffer 和类型化数组抛出 RangeError 超出了以字节为单位的预算，并且超出了数组 预算/8 项被拒绝。预算也会在您的钩子返回后进行检查，因此 超出预算的最终语句使调用失败而不是成功。

国际象棋参考脚本故意保持其文档较小——作为保持在预算之内的一个例子，它的每个玩家文档是

{
  elo: 1200,
  wins: 0, losses: 0, draws: 0,
  lastColorVs: "9b2f8c1a-...",        // for color alternation on rematch
  lastColorOrder: "w",
  recentGames: [ /* up to 30 summaries */ ]
}

默认情况下，每个玩家的并发会话上限为 20 个。

平台可读窗口

一切都在 sessionState 对平台不透明 除了 一个字段：

sessionState.summary = {
  turnPlayerId: "7c9e6679-...",
  deadline: 1784642591000,
  status: "active",
  moveCount: 41
};

deadline 是一个整数 Unix 时间戳 毫秒，或在没有截止日期时省略。 无法识别 ISO 日期字符串。 turnPlayerId 是玩家的 UUID。

GET /api/v1/games/{slug}/sessions/mine 读 summary 计算 myTurn 和 deadline 对于来电者。保持每次状态变化的准确性；将其他所有内容保留在您的脚本喜欢的地方。

工作示例：国际象棋脚本

本节中的所有内容均特定于国际象棋参考实现 - 状态形状、棋盘编码、命令集、游戏结束原因、Elo 常数、AI 和下面的超时是国际象棋自己的选择，在其脚本中定义。这些都不是平台行为；你的游戏定义了它自己的等价物。

会话状态：

{

  black: "9b2f8c1a-...",

  game: {
    board: "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr", // 64 chars

    castling: { K: true, Q: true, k: true, q: true },

  },

板编码：64 个字符的字符串，其中 index = rank * 8 + file 和 a1 是索引 0。 PNBRQK 是白色的碎片， pnbrqk 黑色的， . 是一个空的正方形。

  • 埃洛 使用 K=32，计算公式为 finishGame 当游戏结束时，并通过返回 eloUpdates.

最佳实践

  • 验证每个命令。 对待 ctx.message.data 作为敌对：在触摸状态之前检查类型、范围、回合顺序和游戏状态。
  • 保持调用快，状态小。 每个玩家文档有大约 250 毫秒和字节预算；国际象棋参考脚本，例如 caps recentGames 因此，有 30 个条目。
  • 使用 ctx.now / ctx.random 仅有的。 不 Date， 不 Math.random — 主持人拥有时钟和骰子。
  • 设计 broadcast 消息作为唯一的客户端合约。 客户端必须能够根据脚本发送的内容渲染整个游戏；任何不广播的东西对他们来说都不存在。
  • 一个锉刀，两个表面。 同一文件可以通过单独的导出兼作客户端规则：例如，国际象棋参考实现公开了 globalThis.chessRules 对于浏览器（移动预览、验证提示）和 globalThis.game 对于主机。一种真相来源，对客户零权威。
  • 始终通过以下方式结束游戏 result 因此，当您的游戏出现问题时，平台会发布 Elo 更新并存档重播 重播.
