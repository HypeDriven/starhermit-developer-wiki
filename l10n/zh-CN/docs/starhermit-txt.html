这 starhermit.txt 显现

starhermit.txt 是一个小的纯文本文件，它告诉 StarHermit 你的游戏叫什么，如何 启动它，以及它运行什么类型的服务器（如果有）。这是平台在其中查找的一个文件 您发布的所有内容。

它属于您上传内容的根目录 — 既适用于游戏的客户端文件，也适用于专用的 服务器。

严格来说您不必自己创作该文件。 Windows 客户端和 Web 仪表板 将清单显示为 可编辑字段：无论你的构建已经携带什么，都会预填充它们，并且 当您按“上传”时，它们保存的任何内容都会作为清单写入捆绑包中。所以一个构建 不 starhermit.txt 仍然可以发布，并且 .tar - 您无法就地编辑 - 就像 可作为文件夹进行编辑。在构建中传送文件仍然值得做：它与 工件，因此下次有人上传时这些值是正确的。

令人惊讶的规则

清单旁边的所有内容均已上传。

您选择的文件夹不是平台为构建而挖掘的项目目录 - 该文件夹的 内容 是 已发布的游戏，按原样复制。相邻的每个文件和每个子文件夹 starhermit.txt，在任何深度，都会上升并提供给玩家。

所以选择你的 可分发的构建输出，不是你的源树。上传工作目录 意味着将您的源代码、笔记、未缩小的资源和半成品实验发送到 每个玩家，并将游戏的磁盘空间刻录到无人加载的文件上。

少数名称总是被跳过，因为它们从来不是已发布游戏的一部分： .git, node_modules, .DS_Store, Thumbs.db。其他一切都是公平的游戏——包括 README.md, .env 文件， *.psd 来源和 *.map 文件。如果你不把它交给玩家， 不要将其放在清单旁边。

它去哪里

一个游戏客户端

my-game-dist/
  starhermit.txt        <- belongs at this level
  index.html            <- your launch file
  game.js
  assets/
    sprites.png
    music.ogg

挑选 my-game-dist/。内容成为游戏，服务于 https://<slug>.starhermit.com/， 和 index.html 是玩家加载的内容。

或者选择一个 .tar 正是那个布局 — "从 .tar 添加" 在桌面客户端中， .tar 仪表板中的字段。客户端读取存档的条目，将它们重新放置到包中 为您预填清单字段 starhermit.txt 在里面。使用 --format=ustar:

tar --format=ustar -cf my-game.tar -C my-game-dist .

使用 GNU 长名称或 PAX 扩展标头的档案将被拒绝。这些格式存储条目的真实值 中的路径 分离 元数据块，因此重新定位它们意味着重写元数据 - 并获取它 稍有错误就会发布腐败的游戏。如果您的构建达到了 ustar 路径限制（100 个字节 名称，155 为其目录前缀），缩短最深的文件夹名称或上传文件夹。

专用服务器

my-server-dist/
  starhermit.txt        <- belongs at this level
  image.tar            <- docker save output of your server image

挑选 my-server-dist/ — 或选择 image.tar 靠自己，因为清单可以来自 而是对话框的字段。与客户端文件夹不同，服务器发行版有两个有意义的文件夹： 文件：清单和生成的容器映像

docker save my-server:latest > image.tar

服务器文件夹中的任何其他内容都会被留下而不是上传 - 平台运行您的 容器，因此映像已经包含服务器的文件。无论如何，将清单保留在这里意味着 服务器构建是自描述的，可以自行重新上传。

格式

线路 key=value。空白行被忽略， # 开始注释，键周围有空格， 值被修剪。键名不区分大小写，除了文件夹路径 cache.<folder> 区分大小写；未知的键会被忽略，因此拼写错误会悄悄失败 - 对照下表检查您的拼写。

# My Game - browser-only
name=My Game
launch=index.html

每个游戏都可以设置的按键

钥匙 别名 意义
name — 玩家看到的显示名称。必需的，除非您在上传表单中传递显示名称。
launch launch_path, html 条目路径 .html，相对于清单。默认为 index.html 当该名称的文件位于根目录时。
cover cover_art, coverart 游戏库图块上的艺术品。相对于启动文件的路径（cover.png, art/box.jpg) 或绝对值 https:// 网址。可选 - 如果没有，磁贴会显示网站图标。一个坏的值会被丢弃而不是拒绝游戏。
description — 玩家可以通过商店页面的文字了解您的游戏。一条线；写 \n 用于换行。或者使用 description.file 将其保存在文件中。看 描述和发行说明.
release_notes releasenotes 此版本中发生了什么变化。规则相同 description; release_notes.file 而是指向一个文件。
owner username, user 仅存储库流。 拥有者星隐者 用户 ID (UUID) 从 GET /api/v1/me，不是用户名。让你 认领其他人添加的列表 通过证明您控制存储库。上传时被忽略 - 请参阅 谁拥有上传的游戏.

描述和发行说明

游戏旁边显示的两个可选文本： 描述 （游戏是什么）和 发行说明 （您正在发布的版本中发生了什么变化）。每一个都可以写成 自行显现或保存在自己的文件中。

排队，对于短文本。清单每个键一行，所以写 \n 无论你想要什么 换行符（和 \\ 对于字面反斜杠）：

name=Asteroid Garden
launch=index.html
description=Tend a garden on a drifting asteroid.\nPlant, water, and dodge the meteor showers.
release_notes=- New: night cycle\n- Fixed: seeds vanishing after a reload

来自文件，对于任何更长的内容 - 这是用于真实发行说明的形式：

name=Asteroid Garden
launch=index.html
description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md

my-game-dist/
  starhermit.txt
  DESCRIPTION.md
  CHANGELOG.md
  index.html
钥匙 别名 意义
description — 描述文本，内联。
description.file — 通往a的路径 .md, .markdown 或者 .txt 保存描述的文件。
release_notes releasenotes 发行说明文本，内联。
release_notes.file releasenotes.file 通往a的路径 .md, .markdown 或者 .txt 包含发行说明的文件。

规则：

  • 文件路径是相对于 starhermit.txt （存储库游戏的存储库根），而不是 到启动文件。不 .., 无前导 /，并且仅 .md, .markdown 或者 .txt;任何其他路径 被忽略而不是拒绝游戏。该文件必须是 里面 你发布什么，就是这样 像清单旁边的所有其他文件一样提供给玩家。不要在里面放任何东西 不会向他们展示。
  • 文件胜过内联行。 声明两者，内联文本只是后备，使用 当找不到文件时。
  • 每次清单出现时都会重新读取该文本：每次上传或推送都带有 清单，以及每个存储库部署（来自正在部署的提交）。删除这两行和 文本被清除。声明但丢失的文件，没有内联后备，将文本保留为 游戏已经有了。
  • 为什么清单中是文件而不是多行文本？ 每个其他键都是逐行读取的。如果一个 发行说明的一段可以放在清单中，该说明碰巧说 owner=someone 将被读作 owner= 线。
  • 尺寸：描述被削减为 4,000 个字符，发行说明被削减为 20,000 个字符。较长的文字是 缩短，而不是拒绝。行尾被标准化，前导和尾随空白行被修剪。
  • 格式化：文本完全按照写入方式存储。 Markdown 是一个明智的选择，但是否 它是否呈现或显示为纯文本取决于显示它的客户端。
  • 发行说明是替换而不是累积。 每个发布都带有注释 那 建造。保留 您自己的变更日志中的完整历史记录并发布玩家需要的部分。

客户阅读游戏列表中的描述和发行说明 GET /api/v1/github-games/{id}/release-notes.

浏览器资源缓存

使用 cache.<folder>=<seconds> 设置 Cache-Control: public, max-age=<seconds> 托管静态 文件。持续时间是整数 0–31536000 （一年）：

cache..=0
cache.audio=31536000
cache.audio/live=0
cache.assets/textures=604800

这里 cache.. 将整个站点默认值设置为零（重用时重新验证）， audio/ 缓存一年， audio/live/ 重新验证，并且 assets/textures/ 缓存一周。使用内容哈希文件名 长期资产：重新部署不会使已缓存在玩家浏览器中的副本失效。

路径区分大小写，相对于托管根（存储库根或捆绑包的根） client/ 目录），并匹配整个文件夹，包括后代。 audio 不匹配 audiobooks。 尾部斜杠是可选的；最具体的文件夹获胜，最后一个重复的文件夹获胜。使用 . 仅适用于 root 默认；绝对路径、空段、 ./.. 段、反斜杠、 %, ?, #, : 和控制字符被拒绝。如果没有匹配规则，就没有显式的静态 Cache-Control 标头。 API 调用、WebSocket 和外部流式丢失资产后备措施 不受影响。

允许其他网站访问您托管的游戏

对于另一个源的浏览器客户端，声明最多 五 确切的 HTTP/HTTPS 起源：

cors.origins=https://example.com,https://play.example.org,http://localhost:5173

例如，发布此清单后，上的开发页面 http://localhost:5173 可以取 来自您托管游戏的资产：

const response = await fetch('https://YOUR_GAME_UID.starhermit.com/assets/levels.json');
if (!response.ok) throw new Error(`Asset request failed: ${response.status}`);
const levels = await response.json();

每个源都是一个方案、确切的主机名和可选端口。通配符、裸域、凭据、 路径（甚至是尾随的 /），查询和片段被拒绝。方案和端口必须匹配； 不隐式包含子域。重复 cors.origins 行组合，最多有 5 个 清单中的条目（重复项也算在内）。省略密钥以不允许其他来源； 空值无效。

这适用于静态资产、缺失资产后备和 /api/ 请求于 你的游戏主机。 允许的来源接收经过认证的 CORS 标头；选项 飞行前允许 GET、HEAD、POST、PUT、 PATCH、DELETE 和 OPTIONS 以及请求的标头。 API认证授权依然 申请。这不会配置 CORS api.starhermit.com，更改 WebSocket 起源规则，或放宽 页游登录允许的返回URL。在自己的托管源上运行的游戏不需要 额外的 CORS 声明。

发布缓存和 CORS 设置

这两个策略都与客户端文件一起发布。存储库部署读取固定的提交。 在捆绑中，根 starhermit.txt 优先于 client/starhermit.txt。 没有清单的合并上传保留现有策略；提供的清单取代了它们 （省略设置会清除它）。没有清单的完全更换将清除这两项政策。 无效设置在替换实时文件之前拒绝发布（422 用于上传；失败的 存储库部署）。看 捆绑更新.

控制

声明您的游戏使用的键盘操作，默认按键玩家可以重新绑定：

control.left=KeyA+ArrowLeft | Move left
control.jump=Space+KeyW | Jump

control.<action>=<code>[+<code>...][ | <label>]: 动作 ID 是小写字母、数字和 _;代码是 KeyboardEvent.code 值（KeyA, Space, ArrowLeft)，每个加入的操作最多 4 个 与 +;最多 32 个动作，并且两个动作无键。无效的行会被默默地跳过，并且 没有有效线的游戏没有控件 - 其控件 API 答案 404 "This game declares no controls."。当您发布包含它们的版本时，它们就会生效。 看 教程：向游戏添加控件.

具有服务器逻辑的游戏的按键

挑选 一 服务器风格。声明两者 server= 和 container.image= 被拒绝。

这些工作在 上传的文件夹 以及存储库。一个 server= 脚本在内部传播 您上传的文件夹及其来源是直接从存档中读取的，因此具有权威性的游戏 规则根本不需要存储库。如果声明无法兑现——脚本丢失， 指向文件夹之外，或要求您未获准运行的容器 - 整个上传过程是 拒绝而不是创建半配置的游戏。

钥匙 意义
server （别名 server_script) 作为 StarHermit 沙箱中的权威服务器运行的 JavaScript 文件的路径。看 游戏脚本.
container.image A 摘要固定 图像 （name@sha256:<64 hex>）作为服务器运行。标签被拒绝。看 容器游戏服务器.
container.port 您的容器监听的端口。
container.memory_mb 请求的内存以 MiB 为单位，限制在操作员限制内。
container.cpu 容器的 CPU 限制。
container.health 为平台探针设置路径以准备就绪。
container.env.<NAME> 传递到容器的环境变量。

在每个人的座位都坐满之前开始匹配

这些设置适用于使用 StarHermit 配对的权威游戏，其中任一 JavaScript 或容器服务器：

matchmaking.max_wait_seconds=30
matchmaking.ai_players=2
钥匙 意义
matchmaking.max_wait_seconds 整数 0–86400。当最旧的选定票已等待这么多秒时，开始未满的匹配。 0 立即开始。省略保留默认的完全人类匹配或过期行为。
matchmaking.ai_players 整数 0–31， 默认 0。在截止日期前，用 AI 填补这么多空缺席位；将任何其他空位留空。需要 matchmaking.max_wait_seconds.

队列的容量来自脚本的 game.queues;没有声明就是1v1。 当前容器 /describe 读者不导入 queues，所以容器匹配使用 隐式 1v1 形状。例如，在脚本声明的八个座位队列中，三个人在等待， 上面的设置从三个人类、两个人工智能玩家和三个空座位开始。一个完整的人 比赛可以在截止日期之前开始并且没有AI。将人工智能设置为 0 允许仅人类匹配 空座位，如果游戏支持的话，还包括一个人。

平台检查排队和定期匹配检查（默认每个 5秒), 因此，在正常负载下，启动可能会在截止时间之后最多有一个扫描间隔。 Elo 兼容性 并且每张票证允许的队列子集仍然适用。各方保持在一个团队中；在 截止日期较小的聚会或单独的玩家可以占据较大的团队，并保留剩余的席位 可用于 AI 或留空。门票不会合并为一支球队。

您的游戏服务器必须接受未满的匹配并实现 AI 行为。 星隐标记 人工智能玩家；它不会产生他们的动作。被拒绝的会话将取消所选的票证。 冻结座位布局如下： ctx.matchmaking，并且占用的座位出现在 ctx.players; 看 服务器上下文。空座位不会自动出现 由迟到的加入填充。

存储库重新部署和上传应用这些设置。提供的清单没有密钥重置 他们；没有清单的补丁会保留它们。无效值被拒绝（上传 422，或者失败的 存储库部署）。这些设置不会影响明确的练习游戏或实时房间 快速加入/回填。

如何创建一个

  1. 打开纯文本编辑器 - 记事本、TextEdit、VS Code 等等。不是词。
  2. 键入您的游戏所需的按键，每行一个（从下面的示例开始）。
  3. 另存为 starhermit.txt 在您要上传的文件夹中，编码为 UTF-8。

在 Windows 上，记事本 "文本文档" 保存类型追加 .txt 无论您输入什么内容，因此命名 文件 starhermit.txt 产量 starhermit.txt.txt。要么选择 所有文件 在保存对话框中，或者 打开文件资源管理器 文件扩展名 之后查看并重命名。一个名为 starhermit.txt.txt 未找到，拒绝上传。

名称是准确的：全部小写，没有空格。 Starhermit.txt 和 starhermit.TXT 工作是因为 查找不区分大小写，但是 starhermit.text, starhermit.cfg 和 manifest.txt 不要。

示例

仅限浏览器的游戏

name=Asteroid Garden
launch=index.html

带有封面艺术的游戏

name=Asteroid Garden
launch=index.html
cover=art/cover.png

根据启动文件解析相对路径（无 .., 无前导 /，没有查询字符串）和 必须结束于 .png, .jpg/.jpeg, .gif, .webp 或者 .svg。绝对 URL 必须是 https:// — http:// 被丢弃——并且字节被嗅探，因此 URL 本身不需要图像扩展。

该行在每次部署时都会重新读取，因此更改它会更改封面并删除它会删除 盖。图像集来自 管理 → 封面艺术 在网络仪表板中（或由 StarHermit 操作员） 覆盖它：该选择存在于构建之外，因此重新部署永远不会撤消它。删除 上传再次回到这一行。

图书馆瓷砖

封面艺术是海报艺术：两个图书馆 缩放它以填充瓷砖并中心裁剪 不管做什么 不适合。瓷砖的形状不一样。

表面 瓦 庄稼
Windows客户端 96×128 肖像 (3:4) 填充肖像；更广泛的艺术失去了侧面
网络仪表板 正方形 填满正方形；更高的艺术失去了顶部和底部

将主题保留在 中心。一张 3:4 的肖像，中间的方块是构图，或者 中间 3:4 条带的正方形，在两种作物中都能存活。从未应用信箱 — 空 您在艺术周围添加的边距会与其他所有内容一起被裁剪掉。

SVG 封面显示在网络库中。 Windows 客户端没有 SVG 解码器，因此图块会回退 到网站图标，同时网络图块仍显示封面。如果需要，可以选择 PNG、JPEG 或 WEBP 两者上都有相同的瓷砖。

声明您拥有的列表 - 仅限存储库游戏

放 owner 返回为不可变的 StarHermit 用户 ID id 经过 GET /api/v1/me——不是 个人资料用户名或昵称：

name=My Game
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

谁拥有上传的游戏

上传它的帐户。 始终如此，无需配置任何内容。

上传背后没有存储库，因此任何人都无法证明其控制权： 平台将上传帐户记录为提交者，并将 GitHub 所有者字段留空，因此 没有声明可以与该行匹配。一个 owner= 上传的版本中的行被忽略，并且客户端会这样做 不提供一个领域——把一个游戏放在另一个人的名字下会指派他们的责任 对于他们未发布的内容，这不是上传表单应该能够做到的事情。

将您已经拥有的游戏交给其他人是从管理菜单中单独进行的、经过深思熟虑的操作 事后，而不是添加它时做出的决定。

改为从 GitHub 存储库发布

如果您的游戏位于 github.com 存储库，放置 starhermit.txt 在 存储库根目录 和 提交存储库 URL — 平台直接从存储库读取清单，无需上传 参与。上述所有内容均保持不变，除了 "相邻的一切" 意味着一切 存储库，这是将构建输出和源保留在单独的存储库中（或使用 您构建的输出的文件夹上传）。

看 GitHub 游戏 对于存储库流程，以及 从本地文件夹添加游戏 用于上传 客户端调用的端点。

限制

一场比赛可能占据 2GB 在 starhermit.com 上（津贴可能因部署而异），即 还有单个替换上传的上限。一个 ?mode=merge 补丁受到生成的树的限制，因此少量上传将使实时游戏超出 津贴被拒绝。深深地 嵌套路径被拒绝：存档格式将路径限制为文件名的 100 个字符加上 155 个字符 对于其目录前缀，因此缩短很长的文件夹链。
