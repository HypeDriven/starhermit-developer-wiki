脚本游戏的本机性能

StarHermit 引擎游戏在浏览器和本机中运行相同的包。两者运行你的代码非常 不同的是，因此在移植或编写繁重的工作之前选择它所在的位置。本页涵盖脚本 速度、WebAssembly、GPU 绑定场景、工作人员和测量。数字是发动机测量值 2026 年 10 月。

你的代码如何运行

在浏览器中 原生地
游戏JavaScript 浏览器的V8，全速 引擎自己的解释器，无 JIT（出于安全考虑而设计）
WebAssembly，主要领域 浏览器的 WebAssembly 引擎的解释器（主机 API 1.25 及更高版本）
WebAssembly 中 starhermit:script 工人 引擎的解释器，用于获得位精确的结果 引擎的解释器
  • 本质上，真正的游戏 JavaScript 是关于 比 V8 慢 15–25 倍。微基准可以建议 约8×。不要依赖他们。
  • Native WebAssembly 是关于 比 V8 慢 8–17 倍 今天。平台计划编译WASM 在发布时提前签署本机代码，这应该使其接近 V8 的速度。
  • starhermit check 运行 JavaScript 的方式与窗口游戏完全相同。基准测试 --release 仅引擎构建。

每帧工作繁重

模拟、网格划分、寻路和实体构建是常见的热点。

  1. 用 Rust 或其他 WASM 语言编写热代码 并将其作为 WebAssembly 运行，最好在 starhermit:script 工人。以这种方式编写的代码可以获得计划的提前加速，而无需 变化。
  2. 选择一条路径 runtime() 从 starhermit:engine （主机 API 1.26）。 "web" 意味着V8，所以 JavaScript 在那里很好。 "native" 意味着您应该更喜欢 WASM 路径。工人们总是把 本机路径，无法导入 starhermit:engine.
  3. 为游戏逻辑、UI 和编排保留简单的 JavaScript。 将罕见的繁重工作分散到各个框架之间。
  4. 不要为了速度而将 JavaScript 或 TypeScript 编译为 WebAssembly。 结果还需要 JavaScript 对象模型，因此它一无所获。

对于许多类似的实体来说， starhermit:world 内核 也可以本地运行。

GPU 密集场景

本质上，GPU 通常只有在脚本时间得到控制后才成为限制。

  • 使用 InstancedMesh.setLevels([...]) 具有低多边形水平和绘制距离，以及三 LOD （主机 API 1.26）。
  • 转动 castShadow 关闭小或远距离的道具。
  • 限制阴影级联 shadow.cascades = { count, maxDistance }，引擎扩展。
  • 放 STARHERMIT_GPU_PASS_TIMES=1 打印每次传递的 GPU 时间。

工人

  • 在主机 API 1.27 之前，请保留对您使用的每个工作线程的引用，因为垃圾收集 终止它。从 1.27 开始，一个有听众的工人生活到 terminate().
  • 工作人员可以读取包文件（files）来自主机 API 1.26。
  • Worker 可以从主机 API 1.25 发送二进制和可传输消息。

测量

  • 使用相同的构建来比较本机和网络。
  • 引擎的帧统计数据将脚本时间与帧时间分开报告。脚本台编号是 适合引用。
