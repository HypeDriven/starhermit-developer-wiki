کھیل ہی کھیل میں سکرپٹ

ایک StarHermit مستند گیم کی تعریف a کے ذریعے کی جا سکتی ہے۔ واحد جاوا اسکرپٹ فائل ایک سینڈ باکس میں سرور سائیڈ کو پھانسی دی گئی۔ جنٹ انجن اسکرپٹ اس گیم کے قواعد پر واحد اختیار ہے: یہ ہر کھلاڑی کی کمانڈ کی توثیق کرتا ہے، حالت کو تبدیل کرتا ہے، فیصلہ کرتا ہے کہ ہر کلائنٹ کیا دیکھ سکتا ہے، Elo کی گنتی کرتا ہے، اور گیمز کو ختم کرتا ہے۔ کلائنٹس کے پاس کوئی اختیار نہیں ہے۔ یہ صفحہ جاوا اسکرپٹ کے رن ٹائم کو دستاویز کرتا ہے۔ گیمز جن کو دوسری زبان کی ضرورت ہوتی ہے اس کے بجائے لاگو کر سکتے ہیں۔ کنٹینر گیم سرور پروٹوکول دونوں ایک ہی کھلاڑی کا سامنا کرتے ہیں۔ گیمز API. کام کی مثال شطرنج ہے - حوالہ پر عمل درآمد HypeDriven/starhermit-chess.

پھانسی کا ماڈل

  • فی گیم ایک جے ایس فائل، ایک میں عمل میں آئی تازہ سینڈ باکسڈ جنٹ انجن فی درخواست. کالوں کے درمیان میموری میں کچھ بھی برقرار نہیں رہتا ہے - تمام ریاست ان دستاویزات میں رہتی ہے جو آپ واپس کرتے ہیں۔
  • کوئی محیطی نہیں۔ Date یا Math.random. وقت اور بے ترتیبی اس طرح فراہم کی جاتی ہے: ctx.now (ms epoch) اور ctx.random (اندر تیرنا [0, 1)).
  • پلیٹ فارم اسکرپٹ کو طلب کرتا ہے جب کوئی کھلاڑی پائیدار کمانڈ بھیجتا ہے، جب سیشن بنتا ہے، اور وقتاً فوقتاً onTick جھاڑو (دیکھیں۔ گیمز API - رن ٹائم ٹائمنگ)۔ ریئل ٹائم {type:"input", realtime:true} فریم مستثنیٰ ہیں: وہ تازہ ترین جیتوں کو بفر کیا جاتا ہے اور اگلے ٹک پر بیچ کے طور پر پہنچایا جاتا ہے۔

انٹری پوائنٹس

پر ہینڈلرز کو بے نقاب globalThis.game. چھ اختیاری۔ جامد اعلانات ان کے ساتھ بیٹھتے ہیں: tickRateHz پلیٹ فارم سے پوچھتا ہے کہ کتنی بار پکارنا ہے۔ onTick - اگر آپ کا گیم اس پر منحصر ہے تو اس کا اعلان کریں۔ ٹک، کیونکہ ایک گیم جس میں کہا جاتا ہے کہ ہر چار سیکنڈ میں ایک بار ٹک نہیں کیا جاتا ہے (دیکھیں۔ ٹک ریٹ), achievements گیم کی کامیابیوں کو رجسٹر کرتا ہے (دیکھیں۔ کامیابیاں), replays پلیٹ فارم سے آپ کے مکمل سیشنز رکھنے کے لیے کہتا ہے (دیکھیں۔ ری پلے کرتا ہے۔), persistent روکتا ہے سیشن ختم کرنے کے بجائے جب سب چلے جائیں (دیکھیں۔ مستقل سیشن), linkedAchievements دوسرے گیمز کے نام جن کے ان لاک آپ کو موصول ہوتے ہیں۔ ctx.linkedAchievements (دیکھیں۔ دوسرے کھیلوں سے کامیابیاں)، اور queues اعلان کرتا ہے میچ میکنگ کی شکلیں قبول کرتی ہیں (دیکھیں۔ گیمز - میچ میکنگ)۔ ایک کھیل جو اعلان کرتا ہے کہ کوئی قطار نہیں ہے اس میں ایک مضمر 1v1 ہے:

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

اعلانات آپ کے اسکرپٹ کا جائزہ لے کر پڑھے جاتے ہیں۔ جب گیم شائع یا اپ ڈیٹ کیا جاتا ہے۔, ہر درخواست پر نہیں - لہذا ان کی جامد اقدار ہونی چاہئیں game اعتراض ایک اپ ڈیٹ شائع کریں۔ تبدیلی کا اطلاق کرنے کے لیے۔

  • createSession(ctx) - اس وقت بلایا جاتا ہے جب کوئی سیشن بنتا ہے (میچ میکنگ، انوائٹ-قبول، AI پریکٹس، یا ریئل ٹائم روم شروع ہوتا ہے - دیکھیں کمرہ بند سیشن).
  • onPlayerMessage(ctx) - گیم پلے WebSocket پر موصول ہونے والی پائیدار کلائنٹ کمانڈز کے لیے بلایا گیا۔ ان پٹس کو واضح طور پر نشان زد کیا گیا ہے۔ realtime:true اس انٹری پوائنٹ کو بائی پاس کریں۔
  • onMembershipChange(ctx) - اختیاری اس وقت کال کیا جاتا ہے جب کوئی کھلاڑی رننگ سیشن میں شامل ہوتا ہے یا چھوڑتا ہے (a جوائن ان پروگریس روم، یا ایک جاری کھیل میں مدعو کریں۔). ctx.players پہلے سے ہی تبدیلی کی عکاسی کرتا ہے، اور ctx.membership ہے { change: "joined" | "left", userId, name, team, slot }. واپسی { ok: false } شمولیت سے انکار کرنا؛ اس ہک کے بغیر اسکرپٹ ہر شمولیت سے انکار کرتا ہے۔ آپ جو بھی واپس کریں گے رخصت حتمی ہے۔ کامیابیاں اور اسکور نتیجہ پر سوار ہو سکتے ہیں۔ a sessionState نظر انداز کیا جاتا ہے.
  • onTick(ctx) - مؤثر ٹک ریٹ پر پلیٹ فارم کی ٹائمر سروس کے ذریعہ بلایا جاتا ہے۔ میں تازہ ترین ریئل ٹائم ان پٹ دستیاب ہیں۔ ctx.inputs. 0 ہرٹز پر حل کرنے والی گیم کو وقفہ وقفہ سے کالیں موصول نہیں ہوتی ہیں، لیکن اسکرپٹ کے معاہدے کو پورا کرنے کے لیے فنکشن کو پھر بھی موجود ہونا چاہیے۔

سیاق و سباق کا اعتراض

ctx = {
  now: 1721473200000,              // ms epoch, from the host clock
  random: 0.7231,                  // float in [0, 1), from the host RNG
  sessionId: "0f8fad5b-...",       // current session id
  pausedMs: 0,                     // persistent games only: total ms this session has spent paused
  players: [                       // session participants
    { id: "7c9e6679-...", name: "alice" },
    { id: "00000000-0000-4000-8000-00000000a1a1", name: "The House", ai: true }
  ],
  sessionState: { /* ... */ },     // this script's session document, or null
  playerStates: {                  // per-player documents (elo, history), or null
    "7c9e6679-...": { elo: 1200, wins: 4, losses: 2, draws: 1, /* ... */ }
  },
  message: {                       // onPlayerMessage only
    from: "7c9e6679-...",          // the authenticated user id — trusted
    data: { type: "move", from: "e2", to: "e4" }  // client payload — untrusted (example: a chess move)
  },
  inputs: [                        // onTick only; omitted when none are pending
    { from: "7c9e6679-...",        // authenticated sender id — trusted
      data: { type: "input", seq: 42, mx: 0.7, mz: -0.2 } }
  ]
}
  • AI سیٹ (اگر موجود ہو) کے ساتھ جھنڈا لگا ہوا ہے۔ ai: true اس کے کھلاڑی کے اندراج پر۔
  • ایک کھیل جو اعلان کرتا ہے۔ linkedAchievements بھی ملتا ہے ctx.linkedAchievements: { <playerId>: { <otherSlug>: [unlocked keys] } }، ہر درخواست پر دوبارہ پڑھیں۔ دیکھیں دوسرے کھیلوں سے کامیابیاں.
  • کمرے کے پابند سیشن (ایک حقیقی وقت کے کمرے سے شروع) دو اضافی ctx فیلڈز حاصل کرتے ہیں، ctx.room اور ctx.presenceپر ہر invocation — دیکھیں کمرہ بند سیشن.
  • سے کسی چیز پر بھروسہ نہ کریں۔ ctx.message.data یا ctx.inputs[].data. قابل اعتماد شناخت اسی کے مطابق ہے۔ from، جسے سرور تصدیق شدہ کنکشن سے منسلک کرتا ہے — کلائنٹ اسے کبھی بھی سپلائی یا دھوکہ نہیں دے سکتا۔
  • ان پٹ کے ساتھ بیچنگ کا انتخاب کرتے ہیں۔ {type:"input", realtime:true, ...}. نشان زدہ input احکامات پائیدار رہتے ہیں onPlayerMessage پسماندہ مطابقت کا مطالبہ کرتا ہے۔ ریئل ٹائم ان پٹس فی مرسل ایک زیر التواء سلاٹ استعمال کرتے ہیں: تحریک تازہ ترین جیت ہے، جبکہ pass, shoot، اور tackle ایکشن کناروں کو ضم کر دیا گیا ہے لہذا مندرجہ ذیل حرکت کا نمونہ انہیں اگلی ٹک سے پہلے مٹا نہیں سکتا۔ بیچ استعمال کرتے وقت اسکرپٹ کو ہر قدر کو کلیمپ اور درست کرنا چاہیے۔

ٹک ریٹ

پلیٹ فارم چلتا ہے۔ onTick ایک قابل ترتیب شرح پر فی فعال سیشن جھاڑو۔ آپ کا اسکرپٹ اس کی مطلوبہ شرح مانگتا ہے۔ جامد کا اعلان کرکے tickRateHz گیم آبجیکٹ پر، انٹری پوائنٹس کے ساتھ:

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • اعلامیہ پڑھا جاتا ہے۔ جب آپ کا گیم شائع یا اپ ڈیٹ ہوتا ہے۔ہر ٹک پر نہیں۔ اسے تبدیل کرنے کے بعد اپ ڈیٹ شائع کریں۔
  • ایک گیم جس میں کوئی شرح نہیں ہے اس پر 0.25 ہرٹج پر ٹک کیا جاتا ہے۔ - ہر چار سیکنڈ میں ایک بار۔ یہ کافی ہے موو کلاک یا ٹائم آؤٹ کا فیصلہ کریں اور پلیٹ فارم کی قیمت تقریباً کچھ بھی نہیں ہے، لیکن یہ بہت سست ہے۔ کسی بھی چیز کے لیے آپ کا گیم پلے انحصار کرتا ہے۔ اگر onTick اپنے گیم کو چلاتا ہے، اپنی ضرورت کی شرح کا اعلان کریں۔
  • درخواستوں کو زیادہ سے زیادہ پلیٹ فارم پر بند کیا جاتا ہے (30 ہرٹج بذریعہ ڈیفالٹ)، لہذا کوئی گیم کم مانگ سکتا ہے۔ پلیٹ فارم اجازت دیتا ہے لیکن اس سے زیادہ کے لیے کبھی نہیں۔ مانگو 0 کسی گیم کے لیے ٹک کو مکمل طور پر غیر فعال کرنا جو صرف پلیئر کے حکموں پر ردعمل ظاہر کرتا ہے۔
  • قیمتیں ہوسکتی ہیں۔ جزوی: 0.5 ہر دو سیکنڈ میں ایک ٹک ہے۔ سب سے چھوٹی غیر صفر کی شرح ہے۔ 0.01 Hz — آپٹ آؤٹ کے طور پر پڑھنے کے بجائے اس پر ایک چھوٹا مثبت نمبر اٹھایا جاتا ہے، کیونکہ a چھوٹا حصہ ایک سست کھیل ہے۔ صرف کے لیے ٹک کرنا بند ہے۔ 0 یا منفی شرح۔ لاپتہ یا ناقابل استعمال اعلان (ایک تار، null, NaN) 0.25 ہرٹز ڈیفالٹ لیتا ہے۔
  • ایک آپریٹر کسی بھی سمت میں، کسی خاص گیم کے لیے شرح کو اوور رائیڈ کر سکتا ہے۔
  • ریئل ٹائم ان پٹس ٹک کے درمیان تازہ ترین جیت ہیں، جبکہ مجرد کارروائی کے کنارے ترتیب دیئے گئے ہیں۔ ایک سست وصول کنندہ ایک متروک سنیپ شاٹ کو چھوڑ سکتا ہے لیکن نقلی یا دوسرے وصول کنندگان میں تاخیر نہیں کر سکتا۔

ری پلے کرتا ہے۔

ایک سیشن ختم ہونے پر، پلیٹ فارم اپنا فائنل رکھ سکتا ہے۔ sessionState کے طور پر دوبارہ چلائیں - کی کی طرف سے پیش کردہ دستاویز GET /api/v1/games/{slug}/replays/{sessionId} (دیکھیں۔ گیمز API - ری پلے)۔ ری پلے کو اس وقت تک ذخیرہ کیا جاتا ہے جب تک کہ میچ کا ریکارڈ ہو۔ ہے، تو آپ کا کھیل صرف اس صورت میں ملتا ہے جب وہ پوچھے۔:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • اعلان لفظی ہونا چاہیے۔ true یا false - اور کچھ بھی بغیر اعلان کے پڑھا جاتا ہے، اور ایک کھیل جو کچھ بھی نہیں بتاتا ہے اس کا کوئی ری پلے نہیں ہوتا ہے۔
  • پڑھی جاتی ہے۔ جب آپ کا گیم شائع یا اپ ڈیٹ ہوتا ہے۔. اسے تبدیل کرنے کے بعد اپ ڈیٹ شائع کریں۔
  • ایک پلیٹ فارم آپریٹر کسی بھی طرح سے کسی خاص گیم کا جواب دے سکتا ہے، لہذا اعلان ایک درخواست ہے۔ گارنٹی کے بجائے۔ GET /api/v1/games/{slug} جواب کے طور پر رپورٹ کرتا ہے replaysEnabled - اس پر اپنے ری پلے UI کو برانچ کریں، اس پر نہیں کہ آپ کی اسکرپٹ نے کیا پوچھا ہے۔
  • ری پلے آف کے ساتھ کوئی اور چیز تبدیل نہیں ہوتی ہے: آپ کے سیشن کی حالت اب بھی محفوظ ہے اور پھر بھی واپس دی جاتی ہے۔ ہر دعا کے طور پر ctx.sessionState، اور یہ اب بھی کریش ریسٹور پوائنٹ ہے۔ کیا کھیل ہے ری پلے کے بغیر حاصل نہیں ہوتا ہے ایک کاپی جو سیشن سے باہر رہتی ہے، لہذا اس کے ری پلے اینڈ پوائنٹس جواب دیتے ہیں۔ 404.
  • فائنل ڈیزائن کریں۔ sessionState دوبارہ چلانے کے قابل ہونے کے لیے - ایک منتقل لاگ، یا جو کچھ بھی آپ کے کلائنٹ کی ضرورت ہے۔ میچ کو دوبارہ ترتیب دینے کے لیے۔ شطرنج کے حوالے کا نفاذ برقرار رہتا ہے۔ state.game.moves اور اس کے قدم انہی اصولوں کے ماڈیول کے ذریعے جو پلیٹ فارم پر عمل درآمد کرتا ہے۔

مستقل سیشن

ایک کھیل جو اعلان کرتا ہے۔ persistent: true ہر کھلاڑی کے جانے کے بعد اپنے سیشن جاری رکھتا ہے۔ تقریباً 15 آخری منقطع ہونے کے سیکنڈ بعد سیشن ہے۔ روک دیا - نہیں onTick کالز - اور پہلا دوبارہ جڑنے والا کھلاڑی اسے دوبارہ شروع کرتا ہے۔ منقطع ہونا یا غیرفعالیت سیشن کو ترک کرنے کے بجائے روک دیتی ہے۔ کھیل کا نتیجہ، مالک کارروائی، واضح حتمی رکن کی چھٹی، ترتیب شدہ برقراری کی میعاد ختم، یا ٹرمینل ریکوری کی ناکامی اب بھی اسے ختم کرو. دیکھیں سیشن لائف سائیکل.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • لغوی ہونا ضروری ہے۔ true یا false. پڑھی جاتی ہے۔ جب آپ کا گیم شائع یا اپ ڈیٹ ہوتا ہے۔.
  • ctx.now دیوار کی گھڑی رہتی ہے۔ مسلسل سیشن بھی ملتے ہیں۔ ctx.pausedMs، کل وقت گزارا۔ توقف، تو ctx.now - ctx.pausedMs ایک گھڑی ہے جو ساکن کھڑی ہے جب کہ وہاں کوئی نہیں ہے۔
  • روکے ہوئے سیشنز فی کھلاڑی سیشن کیپ کے حساب سے شمار ہوتے ہیں، اس لیے کھلاڑیوں کو ایک کمانڈ دیں جس کا اختتام a ہو۔ ایک کے ساتھ دنیا result.

دیکھیں مسلسل سیشن ٹیوٹوریل کام کی مثال اور کلائنٹ کے بہاؤ کے لیے۔

میچ میکنگ سیٹ لے آؤٹ

نئے میچ میڈ سیشن موصول ہوتے ہیں۔ ctx.matchmaking پر ہر درخواست (تخلیق، کمانڈ اور ٹک) یہ قطار کی شکل اور نشستوں کو محفوظ رکھتا ہے یہاں تک کہ اگر گیم کو بعد میں دوبارہ استعمال کیا جائے:

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players کے ساتھ صرف مقبوضہ نشستوں پر مشتمل ہے۔ team اور ai:true AI کے لیے ٹیم/ سلاٹ اشاریہ جات ہیں۔ صفر پر مبنی AI IDs اس سیشن کے اندر مستحکم ہیں اور StarHermit اکاؤنٹ IDs نہیں ہیں۔ صرف انسان سیشن/چیٹ کی رکنیت حاصل کریں اور اکاؤنٹ پلیئر اسٹیٹ، درجہ بندی یا کامیابی کی تحریریں حاصل کر سکتے ہیں۔ AI حالت میں رکھیں sessionState. کلائنٹس کو آپ کے گیم کی حالت میں جس بھی روسٹر فیلڈز کی ضرورت ہو اسے کاپی کریں۔ یا نشریات. پرانے سیشنز اور غیر میچ میکنگ سیشنز کو چھوڑا جا سکتا ہے۔ ctx.matchmaking.

آغاز کی آخری تاریخ اور زیادہ سے زیادہ AI شمار کا اعلان کریں۔ starhermit.txt. AI شمار کے ساتھ 0، خالی نشستیں خالی رہیں۔ اسی سیاق و سباق کو کنٹینر سرورز تک پہنچایا جاتا ہے۔

کمرہ بند سیشن

سیشن ہو سکتا ہے۔ ایک حقیقی وقت کے کمرے میں پابند: جب a ریئل ٹائم کمرہ a کے ساتھ کھیل کے لیے server= اسکرپٹ شروع ہوتا ہے، پلیٹ فارم کمرے کے لیے ایک این پلیئر سیشن بناتا ہے۔ انسان شرکاء (AI سیٹیں صرف اسکرپٹ کا سامنا کرنے والے روسٹر میں موجود ہیں)۔ اس طرح سرور سے مستند ریئل ٹائم گیمز (جیسے فٹ بال) چلتے ہیں: کمرے لابی/میچ میکنگ فراہم کرتے ہیں، اسکرپٹ میچ چلاتا ہے۔ دیکھیں ریئل ٹائم رومز - پل کمرے کی طرف لائف سائیکل کے لیے۔

ہر دعا (createSession, onPlayerMessage, onTick) ایک کمرے سے منسلک سیشن کو دو اضافی ctx فیلڈز موصول ہوتے ہیں:

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online - صارف کے پاس یا تو کنکشن رجسٹری پر لائیو ساکٹ ہے (ریئل ٹائم رومز یا ws/v1/games).
  • presence.left - صارف اب ایک فعال سیٹ نہیں رکھتا ہے: وہ واضح طور پر چھوڑ گئے اور ان کی سیٹ کو AI شریک میں تبدیل کر دیا گیا۔ left مستقل ہے؛ online پھڑپھڑا سکتا ہے. اسکرپٹ سے توقع کی جاتی ہے کہ ان جھنڈوں سے AI ٹیک اوور / دوبارہ جوائن منطق کو آگے بڑھائے گا۔
  • روسٹر کو ہر درخواست پر دوبارہ پڑھا جاتا ہے، اس لیے سیٹ کی تبدیلیاں (انسانی → AI) جیسے ہی ہوتی ہیں ظاہر ہوتی ہیں۔

جب ایک کمرے سے منسلک اسکرپٹ واپس آتا ہے۔ result، پلیٹ فارم سیشن ختم کرتا ہے، نتیجہ کمرے میں محفوظ کرتا ہے، اور کمرے کو بند کر دیتا ہے۔ - میزبان کی طرف سے پیش کردہ کوئی نتیجہ شامل نہیں ہے۔

الٹا سچ نہیں ہے: کمرہ بند ہونے سے اس کا سیشن ختم نہیں ہوتا ہے۔ اگر کمرہ پہلے بند ہوتا ہے (مثال کے طور پر کیونکہ اس کے آخری انسان نے بغیر جوائن ان پروگریس کے کمرہ چھوڑا — کبھی بھی محض اس لیے نہیں کہ میزبان آف لائن ہو گیا، جو صرف میزبان کے کردار کو منتقل کرتا ہے جب سیشن فعال ہوتا ہے)، سیشن چلتا رہتا ہے، ctx.room.roster خالی ہو جاتا ہے اور ہر انسان دکھاتا ہے۔ left: true. واپسی result پھر اگر میچ کمرے کے ساتھ ختم ہونا چاہئے۔ دیکھیں ریئل ٹائم رومز - 60 سیکنڈ کے میزبان اصول اور کمرے کے پابند سیشن.

واپسی کی شکل

ہر انٹری پوائنٹ ایک ہی شکل لوٹاتا ہے (تمام فیلڈز اختیاری سوائے ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

کلیدی اصول:

  • sessionState اور ہر اندراج playerStates تبدیل کریں ذخیرہ شدہ دستاویزات - ہمیشہ مکمل دستاویزات واپس کریں، کبھی اختلاف نہیں۔
  • صرف پیغامات درج ہیں۔ broadcast کلائنٹس کو ڈیلیور کیا جاتا ہے، ہر ایک کو واضح پلیئر آئی ڈیز یا "all". اور کچھ نہیں نکلتا۔
  • eloUpdates درجہ بندی کو تبدیل کرنے کا واحد طریقہ ہے۔ قدریں ہر کھلاڑی کی ہوتی ہیں۔ نئی مطلق درجہ بندی, بطور بھیجے گئے لاگو - پلیٹ فارم فی میچ کی تبدیلی کو محدود نہیں کرتا ہے، لہذا اسے خود ہی بند کریں (دیکھیں۔ ایلو فی میچ)۔ میزبان انہیں میچ میکنگ کے لیے استعمال کرتا ہے اور انہیں گیم کے لیڈر بورڈ پر شائع کرتا ہے۔ کلائنٹ کبھی بھی براہ راست اسکور جمع نہیں کر سکتے (دیکھیں۔ لیڈر بورڈز)۔ ریٹنگ برقرار رکھیں playerStates[id].elo تو ایک مالک کی ریٹنگ ری سیٹ آپ کی کاپی بھی پہنچ جاتی ہے۔
  • achievements کامیابیاں حاصل کرنے کا واحد طریقہ ہے۔ کلیدوں کو گیم کی کامیابیوں کے خلاف حل کیا جاتا ہے — اعلان کیا جاتا ہے، یا اس کے مالک کے ذریعے تخلیق کیا جاتا ہے — اور پلیٹ فارم کے ذریعے برقرار رہتا ہے۔ دیکھیں کامیابیاں.
  • scores آپ کے گیم کے اپنے لیڈر بورڈز کو تبدیل کرنے کا واحد طریقہ ہے — دیکھیں لیڈر بورڈز.
  • کے ذریعے کھیل ختم کریں۔ result. میزبان پھر سیشن ختم کرتا ہے، اور اس کے ساتھ کھیل کے لیے ری پلے فائنل کو محفوظ کرتا ہے۔ sessionState ری پلے کے طور پر (کی طرف سے پیش کیا گیا GET .../replays/{sessionId} - دیکھیں گیمز API).

کامیابیاں

آپ کا اسکرپٹ ہے۔ صرف وہ چیز جو آپ کے گیم کی کامیابیوں کو غیر مقفل کر سکتی ہے۔ کوئی کلائنٹ نہیں ہے۔ ان کے لیے اختتامی نقطہ: POST /api/v1/me/achievements/unlock گیم کے دائرہ کار کی کامیابیوں کو یکسر مسترد کرتا ہے، اور پبلشر CRUD اینڈ پوائنٹس ان کو چھونے سے انکار کرتے ہیں۔ گیم کا مالک اس کے ساتھ کامیابیاں شامل کر سکتا ہے۔ کے ذریعے اعلان کردہ /me/github-games/{id}/achievements; آپ کی اسکرپٹ ان کو کلید کے ذریعے بالکل اسی طرح کھول دیتی ہے۔ یہ سرور کے طور پر کامیابیوں کو بناتا ہے- کھیل کے باقی حصوں کی طرح مستند ہے، اور یہ طریقہ کار ہے۔ کوئی بھی a کے ساتھ کھیل server= سکرپٹ استعمال کرنا چاہئے - بشمول وہ جس کا گیم پلے کہیں اور چلتا ہے (دیکھیں۔ کون سے گیمز اسے استعمال کر سکتے ہیں۔).

اعلان کرنا

ایک جامد achievements پر صف game اعتراض صرف key درکار ہے:

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
میدان قسم نوٹس
key تار درکار ہے۔ مستحکم آئی ڈی، ≤ 128 حروف، گیم کے اندر منفرد۔ پہلے کے بعد نقل کو نظر انداز کر دیا جاتا ہے۔
name تار پہلے سے طے شدہ key.
description تار پہلے سے طے شدہ "".
icon تار اختیاری URL۔
secret بولین تک کسی کھلاڑی سے چھپا ہوا ہے۔ وہ اسے کھول دو. پہلے سے طے شدہ false.
points نمبر 0-10000 تک بند کر دیا گیا۔ پہلے سے طے شدہ 0.

جب گیم شائع یا اپ ڈیٹ کیا جاتا ہے تو صف کا اطلاق ہوتا ہے:

  • تعریفیں اس سے مماثل ہیں۔ key - کسی نام، آئیکن، پوائنٹس، یا خفیہ جھنڈے میں ترمیم کرنا موجودہ تعریف کو اپ ڈیٹ کرتا ہے، اور ہر وہ شخص جس نے اسے پہلے سے کمایا ہے اسے برقرار رکھتا ہے۔
  • ایک کلید جس کا آپ اعلان کرنا بند کر دیتے ہیں حذف کر دیا جاتا ہے۔ صرف اس وقت جب کہ کسی نے اسے غیر مقفل نہیں کیا ہے۔. کمائی ہوئی تاریخ کبھی تباہ نہیں ہوتی، اس لیے ریٹائرڈ کارنامہ ان کھلاڑیوں کے لیے نظر آتا ہے جو اسے رکھتے ہیں۔
  • زیادہ سے زیادہ 100 فی کھیل کامیابیاں؛ اس سے زیادہ اضافی چیزیں گرا دی جاتی ہیں۔
  • اعلامیہ ہے۔ بہترین کوشش: خراب اندراجات کو چھوڑ دیا جاتا ہے۔ ہمیشہ شائع شدہ تعریفوں کے ساتھ تصدیق کریں۔ GET /api/v1/games/{slug}/achievements کھیل کو اپ ڈیٹ کرنے کے بعد۔

غیر مقفل کریں۔

واپسی ایک achievements سے نقشہ کوئی بھی داخلی نقطہ - createSession, onPlayerMessage، یا onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • انلاک ہیں۔ کمزور - پلیئر کے پاس پہلے سے موجود کلید پر دوبارہ دعویٰ کرنا ایک غیر ضروری ہے، لہذا ایک اسکرپٹ اس شرط سے بحفاظت ایوارڈ دے سکتا ہے کہ وہ ٹریکنگ کے بجائے ہر ٹک پر دوبارہ جائزہ لیتا ہے۔ "پہلے ہی سے نوازا گیا ہے۔" اپنی حالت میں.
  • نامعلوم کلیدیں (گیم کے مالک نے نہ تو اعلان کیا اور نہ ہی تخلیق کیا)، وہ صارفین جو اس سیشن کے شریک نہیں ہیں، اور AI سیٹ کو خاموشی سے نظر انداز کر دیا جاتا ہے۔
  • زیادہ سے زیادہ 32 چابیاں فی کھلاڑی فی دعوت قبول کی جاتی ہیں۔ اسی صف میں مزید چابیاں گرا دی گئی ہیں۔
  • بقیہ درخواست کی تحریروں کے ساتھ قطاریں برقرار رہتی ہیں، لہذا ایک انلاک ناکام درخواست کو زندہ نہیں رکھ سکتا۔

ڈیلیوری

ہر نیا عطا کردہ انلاک کمانے والے کھلاڑی کو دھکیل دیا جاتا ہے۔ ws/v1/games ایک الگ فریم کے طور پر - یہ پلیٹ فارم کی سچائی ہے، آپ میں سے کوئی نہیں۔ broadcast پیغامات:

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

سے دیے گئے انلاک createSession کسی بھی ساکٹ کے موجود ہونے سے پہلے زمین، لہذا وہ بغیر کسی فریم کے پہنچ جاتے ہیں۔ گاہکوں کو پڑھنا چاہئے GET /api/v1/games/{slug}/achievements لوڈ پر اور فریم کے ساتھ سلوک کریں۔ لائیو اپ ڈیٹ کا راستہ۔ مکمل سطح میں کامیابیاں.

لیڈر بورڈز

ایلو بورڈ کے علاوہ، آپ کے گیم میں لیڈر بورڈز ہوسکتے ہیں جو اس کا مالک بناتا ہے۔ POST /api/v1/me/github-games/{id}/leaderboards, ہر ایک کے ساتھ a key. واپس کر کے انہیں پوسٹ کریں۔ scores کسی بھی انٹری پوائنٹ سے — بورڈ کی → پلیئر آئی ڈی → نمبر:

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • ہر کھلاڑی اپنا رکھتا ہے۔ بہترین ہر بورڈ پر بورڈ کی ترتیب کی سمت کے مطابق اسکور کریں، لہذا رپورٹ کریں۔ ہر نتیجہ - ایک بدتر کو صرف نظر انداز کیا جاتا ہے۔
  • صرف سیشن کے شرکاء شمار ہوتے ہیں۔ نامعلوم یا غیر فعال کلیدیں، اور بورڈ کے قواعد سے باہر اسکورز، خاموشی سے گرا دیا جاتا ہے. زیادہ سے زیادہ 16 بورڈز فی ریٹرن۔
  • کے برعکس eloUpdates، کچھ بھی شائع نہیں کیا گیا ہے۔ playerStates - اپنی کاپی اندر رکھیں playerStates اگر کھیل کو ذاتی بہترین واپس پڑھنے کی ضرورت ہے۔

جہاں آپ کا اسکرپٹ چلتا ہے۔

ایک اسکرپٹ جو بغیر کسی حد کے دوبارہ آتا ہے، اس کی یادداشت ختم کردیتا ہے، یا اپنے وقت کے بجٹ سے زیادہ ہوتا ہے دعا اس کا ناکام نتیجہ لاگو نہیں ہوتا ہے۔ کمانڈ یا ٹک ان میں سے ایک کی اطلاع دیتا ہے:

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

آپ کے گیم کا سرور کا حصہ

  • اسکرپٹ کا وقت۔ گیم کے تمام سیشنز اسکرپٹ ٹائم کا بجٹ شیئر کرتے ہیں، 2000 ms فی سیکنڈ پہلے سے طے شدہ، اس سے چارج کیا جاتا ہے جو ہر درخواست نے اصل میں لیا تھا۔ اس کے حصے پر ایک کھیل بلکہ انکار کر دیا گیا ہے قطار کے مقابلے میں: ایک ٹک کو چھوڑ دیا جاتا ہے، ایک کمانڈ کا جواب دیا جاتا ہے۔ "یہ گیم اپنے حصے سے زیادہ استعمال کر رہی ہے۔ اس وقت سرور کا تھوڑی دیر میں دوبارہ کوشش کریں."، اور سیشن کی واپسی کی تخلیق 429.
  • احکام۔ ہر کھلاڑی 20 پائیدار کمانڈز فی سیکنڈ فی سیشن بھیج سکتا ہے (ایک مختصر برسٹ کے ساتھ الاؤنس) اس سے آگے ایک حکم کا جواب ایک کے ساتھ دیا جاتا ہے۔ error فریم "بہت زیادہ احکامات؛ سست نیچے" فریم میں HTTP کی حیثیت شامل نہیں ہے۔ ریئل ٹائم ان پٹ الگ سے محدود ہے۔
  • نتائج۔ نتیجہ جس کے ساتھ سیشن ختم ہوتا ہے وہ زیادہ سے زیادہ 64 KB ہو سکتا ہے۔ ایک بڑے کے ساتھ انکار کر دیا گیا ہے 422.
  • اسکرپٹ کا سائز۔ A server= اسکرپٹ زیادہ سے زیادہ 2 ایم بی ہو سکتی ہے۔ ایک بڑے کے ساتھ انکار کر دیا گیا ہے 422 پہلے یہ ذخیرہ یا تجزیہ کیا جاتا ہے.

آپریٹرز انفرادی گیم کے لیے ان میں سے ہر ایک کو بڑھا یا کم کر سکتے ہیں۔

بجٹ

اسکرپٹ ان وسائل کے بجٹ کے تحت چلتے ہیں:

  • ~250 ms CPU فی درخواست
  • 32 ایم بی میموری
  • ایک بیان کی حد فی درخواست
  • فی کھلاڑی اسٹیٹ بائٹ بجٹ - تمام ریاستی دستاویزات کو سیریلائز اور چھوٹا رہنا چاہیے۔
  • جب وہ متن بن جاتے ہیں تو زیادہ سے زیادہ 64 سطحوں کی گہرائی میں قدروں کو گھوںسلا دیتا ہے۔ کوئی بھی چیز جو ایک انٹری پوائنٹ واپس آتی ہے، ہر اعلان، JSON.stringify، اور Array.prototype.join/toString/toLocaleString انکار a a کے ساتھ گہری قدر RangeError (واپس آنے والا درخواست میں ناکام ہوجاتا ہے: "64 سے زیادہ سطحوں کا اندراج گہرا"). JSON.parse پہلے ہی 64 پر رک گیا ہے، لہذا ایک گہری قدر کبھی بھی راؤنڈ ٹرپ نہیں کر سکتی۔ flat 64 سطحوں تک چپٹا ہو جاتا ہے اور پھینک دیتا ہے اگر سرنی گہرائی میں گھوںسلا کرتی ہے — بشمول ایک ایسی صف جس میں خود
  • ایک کال میموری بجٹ سے زیادہ مختص نہیں کر سکتی۔ repeat, padStart/padEnd, concat اور replace/replaceAll پھینکنا RangeError: Invalid string length جب نتیجہ نصف سے تجاوز کر سکتا ہے۔ حروف میں بجٹ (پہلے سے طے شدہ 32 MB پر 16M؛ ایک ریجیکس تبدیلی اس طرح پابند ہے جیسے ہر پوزیشن مماثل ہے، جو صرف ایک ملین یا اس سے زیادہ حروف کی تاروں کو متاثر کرتی ہے)۔ ArrayBuffer اور ٹائپ کردہ arrays تھرو RangeError بائٹس میں بجٹ گزر گیا، اور ارے ماضی بجٹ/8 عناصر سے انکار کر دیا گیا ہے۔ آپ کے ہک کی واپسی کے بعد بجٹ بھی چیک کیا جاتا ہے، لہذا ایک زائد بجٹ کا حتمی بیان کامیاب ہونے کی بجائے دعوت کو ناکام بناتا ہے۔

deadline میں ایک عدد یونکس ٹائم اسٹیمپ ہے۔ ملی سیکنڈ، یا کوئی آخری تاریخ نہ ہونے پر چھوڑ دیا جاتا ہے۔ آئی ایس او کی تاریخ کی تار کی شناخت نہیں ہے۔ turnPlayerId پلیئر UUID ہے۔

بہترین طریقے

  • ہر حکم کی توثیق کریں۔ علاج کریں۔ ctx.message.data مخالف کے طور پر: حالت کو چھونے سے پہلے اقسام، رینجز، ٹرن آرڈر اور گیم اسٹیٹس چیک کریں۔
  • دعاؤں کو تیز رکھیں اور چھوٹی حالت میں رکھیں۔ آپ کے پاس فی پلیئر ڈاک ~250 ms اور بائٹ بجٹ ہے۔ شطرنج کا حوالہ اسکرپٹ، مثال کے طور پر، کیپس recentGames اس وجہ سے 30 اندراجات پر۔
  • استعمال کریں۔ ctx.now / ctx.random صرف نہیں Date، نہیں Math.random - میزبان گھڑی اور ڈائس کا مالک ہے۔
  • ڈیزائن broadcast صرف کلائنٹ کے معاہدے کے طور پر پیغامات۔ کلائنٹس کو اسکرپٹ کی بھیجی گئی چیزوں سے پورا گیم رینڈر کرنے کے قابل ہونا چاہیے۔ جو کچھ بھی نشر نہیں کیا گیا وہ ان کے لیے موجود نہیں ہے۔
  • ایک فائل، دو سطحیں۔ ایک ہی فائل ایک الگ ایکسپورٹ کے ذریعے کلائنٹ سائیڈ رولز کے طور پر دوگنا ہو سکتی ہے: شطرنج کے حوالہ کا نفاذ، مثال کے طور پر، بے نقاب globalThis.chessRules براؤزر کے لیے (موو پیش منظر، توثیق کے اشارے) اور globalThis.game میزبان کے لئے. سچائی کا ایک ذریعہ، کلائنٹ پر صفر اختیار۔
  • ہمیشہ گیمز کے ذریعے ختم کریں۔ result لہذا پلیٹ فارم Elo اپ ڈیٹس شائع کرتا ہے اور جب آپ کے گیم میں ہوتا ہے تو دوبارہ پلے کو آرکائیو کرتا ہے۔ ری پلے.
