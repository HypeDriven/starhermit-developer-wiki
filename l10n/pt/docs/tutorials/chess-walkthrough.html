Passo a passo de integração: construindo um jogo no StarHermit

Esta página percorre todo o ciclo de vida de integração de um jogo com StarHermit, passo a passo – publicação, lançamento, menu, matchmaking, jogo, chat, voz, classificações, replays. Tudo o que é mostrado se aplica a qualquer jogo: seu jogo substitui seu próprio slug, seus próprios comandos e seu próprio script de regras.

O exemplo em execução é a implementação de referência de xadrez de código aberto, xadrez eremita estelar: um jogo de xadrez por correspondência (24 horas por jogada, classificação elo) construído como um jogo de navegador estático sem construção em HTML/JS/CSS vanilla. Para cada etapa, o passo a passo mostra as chamadas exatas que um cliente do jogo faz e o arquivo no repositório de referência que as faz. Onde quer que apareçam valores específicos do xadrez - o UUID do jogo de referência, os comandos de movimento, a codificação do tabuleiro, o "Hal" IA, o prazo de movimentação de 24 horas – são valores de exemplo que seu próprio jogo define para si mesmo em seu próprio script.

Leia-o junto com as páginas de referência da API às quais ele está vinculado. A lista de verificação no final condensa tudo no que seu jogo precisa replicar.

1. Anatomia de um jogo hospedado em plataforma

Um jogo de plataforma com script é um site estático simples com um arquivo de regras. A implementação de referência de xadrez, por exemplo, não tem bundler, nem framework, nem etapa de construção:

Arquivo Papel
index.html A página inteira: quadro, menu, chat e interface de voz
app.js Inicialização do aplicativo, menu principal, matchmaking, convites, replays, perfis
net.js Camada HTTP: caminhos de jogo com escopo definido, tokens de lançamento, atualização de token
game.js Controlador no jogo: jogabilidade WebSocket, chat, voz
ui.js Renderização de quadro e menu
style.css Estilos
server.js As regras - veja abaixo
starhermit.txt Publicar manifesto

Na implementação de referência, server.js merece atenção especial. Isso é ambos coisas de uma vez:

  • O script autoritativo do servidor a plataforma executa (por meio de seu host Jint) expondo globalThis.game. Cada movimento é validado aqui, no servidor, conforme contrato em game-scripts.md.
  • O cliente mecanismo de regras compartilhadas, exposto como globalThis.chessRules, que o navegador usa para renderização de quadro, visualizações de movimentos e reprodução de replay.

Um arquivo, uma fonte de verdade, autoridade de regras zero no cliente. Um cliente de jogo que segue esse padrão nunca decide se um movimento é legal — ele renderiza o que o servidor transmite. Esta é a ideia arquitetônica mais importante em um jogo de plataforma com script, e a implementação de referência demonstra isso.

2. Publicando seu jogo

A publicação de qualquer jogo começa com o starhermit.txt manifestar na raiz do repositório. Ele declara o jogo name, launch ponto de entrada, owner, e server roteiro. Opcional cover= é a obra de arte no bloco da biblioteca - veja O starhermit.txt manifesto. O manifesto da implementação de referência, por exemplo:

name=StarHermit Chess
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # StarHermit user ID, not username/nickname
server=server.js

Use o imutável id de GET /api/v1/me para owner; nomes de usuários e apelidos são exibidos valores e não devem ser usados como identificadores manifestos de propriedade.

A plataforma clona o repositório, exibe os arquivos estáticos em <slug>.starhermit.com — o slug é o uid que a plataforma atribui ao jogo, nunca um nome que você escolhe; o jogo de referência é 83fd04b1-3cbe-4b09-a251-3733ad4b9d94, então é jogável ao vivo em 83fd04b1-3cbe-4b09-a251-3733ad4b9d94.starhermit.com – e procuradores /api e /ws para o back-end mesma origem. Essa decisão elimina toda uma categoria de trabalho: sem CORS, sem configuração baseada em API, sem detecção de ambiente – os clientes do jogo usam apenas caminhos relativos.

Fluxo completo: github-games.md e publisher.md.

3. Lançamento e autenticação

O fluxo de referência de xadrez recebe credenciais do inicializador da plataforma:

  1. O lançador chama POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/launch-token (mostrado com o UUID do jogo de referência; substitua o seu) pelo JWT completo da plataforma do usuário.
  2. Ele volta com vida curta, escopo do jogo ficha:
{ "token": "<jwt>", "expiresInSeconds": 3600 }
  1. Ele abre o jogo em index.html#game_token=<jwt>, opcionalmente com &session_id=<guid> anexado para links diretos de convite.

Na implementação de referência, o cliente lê o hash uma vez, em seguida, tira-o com history.replaceState para que o token nunca permaneça na barra de URL ou no histórico (app.js, App.init). Ele decodifica a carga JWT para duas declarações:

  • sub - o ID do usuário
  • game_scope - a lesma do jogo

Essa segunda afirmação é importante: um cliente de jogo nunca deve codificar seu slug. A implementação de referência cria cada URL da API como /api/v1/games/<slug> mais um sufixo (net.js, Net.gamePath), então o mesmo código funciona para qualquer jogo, qualquer slug, qualquer implantação.

Atualizar. O token com escopo definido tem permissão para chamar novamente launch-token para seu próprio jogo, então os clientes normalmente atualizam periodicamente — a implementação de referência é atualizada a cada 45 minutos (net.js, Net.startRefresh), confortavelmente dentro do tempo de vida de 60 minutos.

Um jogo aberto diretamente pode oferecer login do navegador, que retorna #access_token em vez do lançador #game_token. Lide com ambos os caminhos de entrada se você apoia ambos. Renove usando o tempo de vida retornado e respeite a cadeia de renovação padrão de 12 horas teto. UM 403 terms_acceptance_required exige que o jogador aceitar através de sua conta; ou exiba os termos no jogo e aceite com o token de lançamento do jogador. Fazer login novamente não aceitação de registro.

Referência de autenticação: auth.md, games.md.

4. Carregando o menu principal

O menu de um jogo normalmente abre com um pequeno lote de GETs contra seu próprio slug. Na implementação de referência isso é refreshMenu em app.js:

Informações do jogo + minhas estatísticas:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "name": "StarHermit Chess",
  "enabled": true,
  "leaderboardId": "<guid>",
  "maxConcurrentSessionsPerPlayer": 20,
  "me": {
    "userId": "<guid>",
    "elo": 1420,
    "wins": 31,
    "losses": 18,
    "draws": 4,
    "activeSessionCount": 3
  }
}

O me bloco é o cartão inteiro do jogador - elo, registro e quantas sessões simultâneas permitidas estão em uso (20 no exemplo do xadrez).

Minhas sessões:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/mine

[
  {
    "sessionId": "<guid>",
    "status": "active",
    "players": [ /* ... */ ],
    "createdAt": "…",
    "finishedAt": null,
    "myTurn": true,
    "deadline": 1784642591000
  }
]

myTurn e deadline são o que tornam útil a lista de sessões de um jogo por correspondência - o jogador vê rapidamente quais jogos estão esperando por ele e quando cada movimento é devido.

Tabela de classificação de amigos:

GET /api/v1/leaderboards/{leaderboardId}/entries?friendsOnly=true&page=1&pageSize=10

usando o leaderboardId da resposta de informações do jogo.

Repetições recentes:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/mine?limit=10

Convites pendentes:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites

Referências: games.md, leaderboards.md.

5. Colocar os jogadores em uma sessão – três maneiras

Este passo a passo usa matchmaking, aceitação de convite e prática de IA para criar sessões. Jogos que precisam de lobby podem usar salas em tempo real, cujo fluxo inicial também pode criar uma sessão autoritativa vinculada.

um. Organização de partidas

Na implementação de referência, App.startMatchmaking em app.js:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking

A resposta é um ticket:

{ "ticketId": "<guid>", "status": "queued" }

ou uma correspondência imediata:

{ "status": "matched", "sessionId": "<guid>" }

Enquanto estão na fila, os clientes pesquisam o endpoint de matchmaking — as pesquisas de implementação de referência GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking a cada 3 segundos e DELETE /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/matchmaking cancela o bilhete. O cliente de referência também garante que o jogador nunca fique parado olhando para um botão giratório: após 30 segundos sem correspondência, um "Jogue contra Hal" aparece o botão ("Hal" é o oponente de IA integrado do exemplo de xadrez - veja §12), e POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai retorna { "sessionId" }.

b. Convite de amigo

Na implementação de referência, App.inviteFriend em app.js. Primeira lista de amigos — este endpoint é explicitamente permitido para tokens no escopo do jogo:

GET /api/v1/me/friends

Então envie o convite:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites
{ "toUserId": "<guid>" }

O destinatário aceita (ou recusa) do seu próprio cliente:

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/accept   → { "sessionId": "<guid>" }
POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/invites/{id}/decline  → 204

Aceitar é o que cria a sessão. O &session_id= deep-link launch-hash (§3) coloca o jogador convidado diretamente nele.

Os convites de amigos alcançam apenas pessoas que já são amigos. Para atrair alguém que não está (ou não está na plataforma), a implementação de referência também oferece uma Compartilhar link de convite botão (App.shareInviteLink): uma linha de construção de string que copia

https://dashboard.starhermit.com/game-invite/<Net.userId>/<slug>

para a área de transferência. O painel da web lida com tudo o que o destinatário precisa – login, solicitação de amizade, apelido, lançamento do jogo – e, em seguida, envia o convite para jogar de volta ao compartilhador, para que ele caia na mesma lista de convites. Ver Compartilhar links para o contrato completo.

c. A regra

As sessões são criadas por matchmaking, convite-aceitação, sessions/aiou iniciar uma sala em tempo real com um back-end do servidor. Para um lobby com assentos, use o API de salas em tempo real.

6. Jogando no WebSocket de jogo

O loop de jogo é o mesmo para todos os jogos com script: buscar a sessão, abrir o soquete, renderizar transmissões, enviar comandos. Na implementação de referência isso reside em game.js, GameController.

Busque a sessão:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/{sessionId}

{
  "sessionId": "<guid>",
  "status": "active",
  "players": [ /* ... */ ],
  "createdAt": "…",
  "finishedAt": null,
  "chatConversationId": "<guid>",
  "result": null
}

Observação chatConversationId — você precisará dele para bate-papo (§7) e voz (§8).

Conecte o soquete de jogo:

ws(s)://<host>/ws/v1/games?sessionId=<id>&access_token=<token>

Sobre open, o cliente envia imediatamente um comando de sincronização:

{ "type": "cmd", "data": { "type": "sync" } }

Em qualquer desconexão, ele se reconecta com backoff exponencial de 1 segundo até um teto de 30 segundos, e reenvia a sincronização em cada abertura. O comando sync torna a reconexão sem estado e idempotente: tudo o que o cliente perdeu, o servidor retransmite.

O envelope. Cada quadro é um envelope JSON fino:

  • Cliente → servidor: {"type":"cmd","data":<command>}
  • Servidor → cliente: {"type":"game","data":…}, {"type":"error","error":…}, {"type":"presence","userId","online"}

Os comandos do jogo são definidos pelo seu próprio script de regras. Os comandos do exemplo de xadrez, por exemplo (o data carga útil de um cmd quadro):

{ "type": "sync" }
{ "type": "move", "from": "e2", "to": "e4", "promo": "q" }
{ "type": "resign" }
{ "type": "offer-draw" }
{ "type": "accept-draw" }
{ "type": "decline-draw" }

No exemplo do xadrez, promo está presente apenas em movimentos de promoção.

As transmissões também são definidas por script. As transmissões do exemplo de xadrez (o data carga útil de um game quadro):

  • state - o instantâneo completo:
{
  "type": "state",
  "white": "<userId>",
  "black": "<userId>",
  "ratings": { "white": 1420, "black": 1388 },
  "board": "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr",
  "turn": "w",
  "moves": [ { "from": "e2", "to": "e4", "promo": null, "san": "e4", "at": "…" } ],
  "status": "active",
  "result": null,
  "deadline": 1784642591000,
  "drawOfferBy": null,
  "ai": false,
  "aiName": null
}

O board é uma sequência de 64 caracteres, index = rank * 8 + file com a1 = 0, usando PNBRQK para branco, pnbrqk para preto, . para casas vazias — uma codificação específica do xadrez; seu jogo define seu próprio formato de estado.

  • moved — um único movimento foi aplicado.
  • draw-offered / draw-declined.
  • game-over — { "result": { "kind", "reason", "at" }, "view" }, onde reason os valores são definidos por script; o exemplo do xadrez usa checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

A identidade nunca é retirada de cargas úteis. O cliente envia comandos sem ID de usuário, e o script nunca confia em um da rede - a plataforma passa o remetente autenticado para o script. Não há nada para falsificar.

Ver game-scripts.md pelo contrato do roteiro por trás de tudo isso.

7. Bate-papo no jogo

Cada sessão carrega um chatConversationId (§6) que os clientes do jogo podem usar para bate-papo no jogo. Na implementação de referência, initChat em game.js usa assim:

GET  /api/v1/chat/conversations/{id}/messages?page=1&pageSize=50
POST /api/v1/chat/conversations/{id}/messages
     { "content": "good luck!" }

O soquete de bate-papo em tempo real ws/v1/chat é bloqueado para tokens no escopo do jogo. O cliente de referência tenta uma vez, é recusado e volta a pesquisar o endpoint REST a cada 5 segundos – planeje fazer a pesquisa desde o início em seu próprio jogo.

O bate-papo funciona mesmo que os dois jogadores não sejam amigos: a conversa da sessão (tipo "game") é criado com ambos os jogadores como participantes, portanto as regras usuais de permissão de bate-papo já estão satisfeitas.

Referência: chat.md.

8. Voz

A voz é opcional e os clientes do jogo normalmente a mantêm desativado por padrão. A implementação de referência trata disso em game.js, VoiceController. Quando um jogador habilita:

  1. Encontre ou crie a sala vinculada à conversa da sessão:
GET  /api/v1/voice/rooms?conversationId=<chatConversationId>
POST /api/v1/voice/rooms
     { "conversationId": "<chatConversationId>" }
  1. Participe:
POST /api/v1/voice/rooms/{roomId}/join
  1. Conecte a tomada de voz:
ws(s)://<host>/ws/v1/voice?roomId=<id>&access_token=<token>

A mídia é WebRTC ponto a ponto com negociação perfeita; o soquete carrega apenas sinalização e controle:

  • Sinalização: {"type":"rtc","to":<userId>,"payload":{"sdp":…}} ou {"type":"rtc","to":<userId>,"payload":{"ice":…}}
  • Controlar: {"type":"mute","muted":…}, {"type":"speaking","speaking":…}
  • Eventos do servidor: voice.roster, voice.participant_joined, voice.participant_left, voice.mute_changed, voice.speaking, voice.rtc

Se o P2P falhar, o substituto são quadros binários opus retransmitidos pelo servidor: um ID de remetente de 16 bytes seguido pela carga útil de áudio.

Voz é desativado em jogos de IA — o cliente de referência verifica view.ai da transmissão estatal e nunca oferece a alternância.

Referência: voice.md.

9. Classificações e tabela de classificação

Os clientes do jogo nunca enviam uma pontuação. Quando um jogo termina, o roteiro retorna eloUpdates e o plataforma publica-os na tabela de classificação do jogo. Os clientes nunca podem escrever entradas na tabela de classificação diretamente; o servidor também deve validar a jogabilidade por trás de suas atualizações de classificação.

O lado do cliente é, portanto, trivial: leia as entradas (§4) e renderize-as, como faz a implementação de referência. Ver leaderboards.md.

10. Repetições

Um jogo que declara replays: true em seu script tem todas as sessões finalizadas mantidas pela plataforma; os clientes apenas buscam e renderizam. Verificar replaysEnabled sobre GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94 antes de oferecer a tela – um operador pode responder por um jogo de qualquer maneira, e os pontos finais abaixo retornam 404 quando os replays estão desligados. Na implementação de referência, a busca é App.loadReplays / App.openReplay em app.js:

GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/mine?limit=10
GET /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/replays/{sessionId}

Uma carga útil de repetição (mostrada com o formato de resultado do exemplo de xadrez):

{
  "sessionId": "<guid>",
  "players": [ /* ... */ ],
  "finishedAt": "…",
  "result": {
    "kind": "win",
    "reason": "checkmate",
    "at": "…",
    "white": "<userId>",
    "black": "<userId>",
    "moveCount": 41,
    "eloBefore": { "white": 1420, "black": 1388 },
    "eloAfter": { "white": 1436, "black": 1372 }
  },
  "state": { "game": { "moves": [ /* ... */ ] } }
}

Os passos do visualizador state.game.moves através do compartilhamento chessRules motor localmente - o mesmo server.js arquivo de regras, rodando no navegador - portanto, os replays não precisam de viagens de ida e volta ao servidor; preservar a versão das regras usada para uma correspondência arquivada quando as regras mudarem. Esta é a segunda recompensa do design de um arquivo e duas funções do §1, um padrão que qualquer jogo pode adotar com seu próprio arquivo de regras.

11. Perfis de jogadores

Os clientes do jogo resolvem outros jogadores por meio de endpoints de perfil público. Na implementação de referência, App.profileFor em app.js:

GET /api/v1/users/{id}/profile  → { "id": "…", "username": "…", "nickname": "…" }
GET /api/v1/users/{id}/avatar   → image/png, or 404

Duas regras de UI que o cliente de referência segue:

  • Renderizar apelidos, nunca nomes de usuário.
  • Volte para "Player " + id.slice(0, 8) quando um perfil está faltando ou um apelido está vazio.

Referência: profile.md.

12. IA pratica oponentes

POST /api/v1/games/83fd04b1-3cbe-4b09-a251-3733ad4b9d94/sessions/ai (mostrado com o slug de exemplo) cria uma sessão onde a plataforma sinaliza um assento ai: true em createSession. O próprio script desempenha esse papel – o comportamento da IA ​​é algo que seu próprio script define. No exemplo do xadrez, o assento é jogado por "Hal", um mecanismo ganancioso de captura de material que responde dentro da mesma invocação que processa o movimento do humano.

O script do jogo decide se a prática altera a classificação do jogador humano. O assento AI não pode receber registros de estado do jogador, classificação ou conquista da conta. Mantenha todas as estatísticas de IA no estado da sessão.

13. O que o jogo de referência NÃO usa

A implementação de referência do xadrez não aborda nada disso, mas estão todos disponíveis para jogos que precisam deles:

  • Conquistas — qualquer jogo com server= script pode declará-los (game.achievements) e conceda-lhes autoridade de servidor a partir de qualquer gancho de ciclo de vida; o xadrez simplesmente não funciona. Os títulos de catálogo têm um caminho separado reivindicado pelo cliente: achievements.md, game-scripts.md.
  • Catálogo/direitos — para jogos distribuídos e vendidos através do catálogo: catalog.md.
  • Relé - o canal de retransmissão de alta frequência para jogos em ritmo acelerado e em tempo real, onde a viagem de ida e volta do script por comando é muito lenta: relay.md.
  • Bibliotecas externas — vinculando bibliotecas de jogos Steam, Epic ou GOG: external-libraries.md.

O exemplo do xadrez, um jogo de tabuleiro baseado em turnos, não precisa de nenhum deles. Se o seu jogo for em tempo real, distribuído por catálogo ou precisar de cargas binárias, essas páginas são o próximo lugar para procurar.

14. Lista de verificação de integração

  • [ ] Adicione um starhermit.txt manifesto (name, launch, owner, server; opcional cover= para o bloco da biblioteca).
  • [ ] Ler #game_token do hash de URL uma vez e, em seguida, remova-o com history.replaceState.
  • [] Decodifique o JWT para sub (ID do usuário) e game_scope (slug) — nunca codifique seu slug.
  • [] Crie todos os caminhos de API como URLs relativos de mesma origem: /api/v1/games/<slug> + sufixo.
  • [] Atualize o token de lançamento a cada 45 minutos via POST …/launch-token.
  • [ ] Use o cmd / sync Padrão WebSocket: envelope tudo, sincronize em cada abertura, reconecte com espera de 1s → 30s.
  • [] Projete os comandos e transmissões do seu script como o contrato do cliente — o cliente renderiza transmissões e envia comandos, nada mais.
  • [] Retornar um objeto de resumo { turnPlayerId, deadline, status, moveCount } para que a lista de sessões possa mostrar de quem é a vez.
  • [] Termine os jogos retornando um result - esse valor de retorno é o que alimenta os replays e o elo.
  • [ ] Declarar replays: true em seu script se desejar que as sessões concluídas sejam mantidas e ramifique a IU de reprodução em replaysEnabled.

A plataforma fornece autenticação, sessões, matchmaking e armazenamento; seu script fornece o regras do jogo. Comece com o início rápido do navegador para um primeiro upload completo.
