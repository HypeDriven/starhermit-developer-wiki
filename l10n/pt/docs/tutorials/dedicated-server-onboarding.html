Publique um servidor de jogo dedicado e jogadores integrados no jogo

Este tutorial mostra como:

  1. Publique ou atualize um contêiner de servidor de jogo dedicado com a API de upload de pacote do StarHermit.
  2. Mantenha renovado o token do servidor StarHermit de um contêiner de longa duração.
  3. Integre jogadores do Steam, Epic, GOG ou de uma versão independente sem enviá-los através de um provedor OAuth ou exigindo que eles visitem o painel StarHermit.
  4. Dê a esses jogadores acesso a sessões StarHermit, matchmaking, tabelas de classificação, conquistas, bate-papo da sessão, voz, amigos, presença e replays.

A API voltada para o jogador é a mesma, quer o executável venha do Steam, Epic, GOG, do seu próprio lançador, ou https://<slug>.starhermit.com.

Limite importante: incorporado não é silencioso

StarHermit atualmente não expõe um privilégio "criar jogador arbitrário" ponto final para um jogo servidor. Um contêiner STARHERMIT_SERVER_TOKEN deliberadamente não tem identidade de jogador e não pode cunhar contas de jogadores ou personificar jogadores.

O registro de chave pública também requer um e-mail válido e um link de verificação único. Portanto:

  • Você pode mantenha o registro dentro da IU da marca do seu jogo e evite o Google/GitHub OAuth e o Painel StarHermit.
  • Você não pode crie silenciosamente uma conta StarHermit apenas a partir de um Steam ID, Epic account ID ou GOG IDENTIFICAÇÃO. O jogador deve consentir, fornecer um e-mail e confirmá-lo uma vez.
  • Gere e armazene a chave privada de cada jogador em seu dispositivo. Não gere a chave de cada jogador em seu servidor dedicado, carregue chaves privadas ou mantenha um banco de dados de chaves de custódia, a menos que você esteja assumindo intencionalmente a responsabilidade por todas essas contas.

Para um jogo nativo, a experiência suportada mais tranquila é: um painel de conta no jogo gera o chave, pede e-mail e consentimento, espera enquanto o jogador confirma o link em sua caixa de entrada e então faz login com a chave e mantém o token de atualização no cofre de credenciais do sistema operacional. O jogador nunca precisa navegue no site StarHermit. Um jogador que não consegue fornecer e verificar um e-mail não poderá concluir este fluxo com a API atual.

Arquitetura e limites de confiança

Steam/Epic/GOG/native client
  ├─ owns the player's private key
  ├─ performs public-key registration/login
  ├─ holds player access + rotating refresh token
  ├─ optionally links the external platform identity
  └─ uses a game-scoped launch token for game/social APIs
                  │
                  │ REST + ws/v1/games
                  ▼
StarHermit API ───────── authenticated command ────────► your container
  ├─ creates sessions and matchmaking                     ├─ owns simulation
  ├─ stamps the trusted StarHermit user id                 ├─ never trusts payload identity
  ├─ persists snapshots/results/elo/achievements           └─ uses narrow server token only
  └─ supplies session chat, voice, friends, and replays

O cliente do jogo prova quem é o jogador. StarHermit carimba essa identidade no tráfego enviado para o recipiente. O contêiner nunca aceita um Steam ID ou ID de usuário fornecido dentro do JSON do jogo como prova de identidade.

Pré-requisitos

Você precisa de:

  • Uma conta de desenvolvedor StarHermit e um token de acesso total.
  • Um jogo registrado que você possui, com um gameSlug e back-end oficial. O ponto final do pacote atualiza um jogo existente; ele não cria um registro de jogo nem reserva um slug.
  • Hospedagem de contêiner habilitada para sua conta.
  • Docker ou outra ferramenta capaz de produzir um arquivo compatível com Docker docker save arquivo.
  • Um contêiner implementando protocolo de jogo v1.

Para registro inicial de autoatendimento, use um repositório GitHub verificado com starhermit.txt e um válido container.image declaração conforme descrito em Jogos GitHub. Uma vez que Se o jogo existir, os pacotes push podem publicar compilações posteriores de cliente e servidor diretamente.

Parte 1: implementar o contrato de contêiner

Seu processo deve ouvir PORT e implementar:

Ponto final Responsabilidade
GET /health Retornar 200 somente quando as sessões podem ser aceitas
GET /describe Declarar protocolo 1, taxa/capacidade de tick solicitada e conquistas
POST /sessions Crie uma sessão ou restaure uma de snapshot
GET /sessions/{id}/snapshot Retorne um ponto de restauração durável completo
DELETE /sessions/{id} Liberar a sessão
WS /stream Receba comandos de jogadores autenticados e emita cargas de jogo
WS /control Envie instantâneos, conquistas, Elo, resultados e contrapressão

Validar X-Starhermit-Invoke-Key em cada solicitação HTTP e atualização do WebSocket em relação a STARHERMIT_INVOKE_KEY. Isso autentica o StarHermit em seu processo.

Uma declaração mínima é:

{
  "protocol": 1,
  "tickRateHz": 20,
  "maxSessions": 48,
  "replays": true,
  "achievements": [
    {
      "key": "first-win",
      "name": "First Win",
      "description": "Win a match.",
      "points": 10
    }
  ]
}

replays pede à plataforma para manter o último estado de cada sessão finalizada, que é o que GET /api/v1/games/{slug}/replays/{sessionId} serve. Declare isso apenas se o seu jogo quiser replays; sem ele, nada é mantido quando a partida termina. Ver Servidores de jogos em contêineres — GET /describe.

Os quadros de fluxo de jogo usam:

[1 byte type][16 byte sessionId][16 byte userId][payload...]

Tipo 1 é um comando de entrada; seu ID de usuário foi carimbado pelo jogador StarHermit autenticado. Tipo 2 é uma carga JSON de saída endereçada a esse jogador ou a todos quando o ID do usuário é todos zeros.

Efeitos duráveis ​​passam /control:

{ "type": "snapshot", "sessionId": "...", "state": { "round": 4 } }
{ "type": "achievements", "sessionId": "...", "unlocks": { "<userId>": ["first-win"] } }
{ "type": "elo", "sessionId": "...", "updates": { "<userId>": 1248 } }
{ "type": "result", "sessionId": "...", "result": { "kind": "win", "winner": "<userId>" } }

StarHermit filtra essas atualizações para os participantes da sessão e chaves de conquistas declaradas. Um resultado é terminal. Ver Servidores de jogos hospedados em contêineres para o protocolo completo, contrato de snapshot, isolamento e recuperação.

Parte 2: registre o jogo uma vez

Coloque um manifesto no repositório verificado usado para registro inicial:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6  # your user ID from GET /api/v1/me, not username

container.image=ghcr.io/your-github-login/orbit-server@sha256:<64-lowercase-hex>
container.port=8080
container.health=/health
container.memory_mb=1024
container.cpu=1.0

Definir owner para o imutável id retornado por GET /api/v1/me. Não use o nome de usuário da conta ou apelido; esses são valores de exibição e podem mudar.

Registre-o:

API=https://api.starhermit.com
ACCESS_TOKEN='developer-access-token'

curl -sS -X POST "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "repoUrl":"https://github.com/your-github-login/orbit-league"
  }'

Salve o devolvido id como GAME_ID e gameSlug como GAME_SLUGe confirme se o back-end existe: GET $API/api/v1/games/$GAME_SLUG respostas 200 assim que isso acontecer. Um presente gameSlug sozinho não prove – todo jogo verificado tem um, incluído apenas no navegador. Um registro que declara um contêiner sem provar que você possui o repositório é recusado com 403e registro inicial também pode falhar quando a hospedagem do contêiner estiver indisponível ou restrita.

A imagem apoiada pelo registro no manifesto é suficiente para implantar a primeira versão. A próxima seção cobre o caminho de upload direto, útil para CI e para compilações que você não deseja plataforma para clonar ou puxar novamente.

Parte 3: publicar um pacote de cliente e servidor dedicado

Construa o arquivo

O upload é um arquivo tar compactado com gzip com este layout:

client/            optional static web client, including the registered launch file
server/image.tar   optional `docker save` output
starhermit.txt     the manifest

Pelo menos client/ ou server/image.tar deve estar presente.

Se você publicar por meio do painel da web StarHermit ou do cliente Windows em vez de curl, você não construa este arquivo manualmente. Escolha um pasta de distribuição do servidor (contenção starhermit.txt e image.tar) ou o image.tar por conta própria, e o cliente empacota o layout acima. O starhermit.txt valores - nome de exibição e o container.* botões - são campos na caixa de diálogo, pré-preenchidos a partir do manifesto da pasta quando houver um, portanto, um simples image.tar publica tão bem.

rm -rf bundle game-bundle.tar.gz
mkdir -p bundle/client bundle/server

# Optional hosted web client.
cp -R dist/. bundle/client/

# Dedicated server image.
docker build -t orbit-server:release -f Dockerfile.server .
docker save orbit-server:release -o bundle/server/image.tar

# Keeps the artifact self-describing, and is what the dashboard/desktop clients require.
cp starhermit.txt bundle/starhermit.txt

tar -C bundle -czf game-bundle.tar.gz .

A imagem deve funcionar com um sistema de arquivos raiz somente leitura, usuário não-root forçado, sem recursos, sem volumes, sem internet e apenas um pequeno volume gravável /tmp. Dependências do fornecedor na imagem.

Faça upload

POST /api/v1/me/github-games/{id}/bundle considera o arquivo como o corpo bruto da solicitação, não como um formulário multiparte:

curl -sS -X POST "$API/api/v1/me/github-games/$GAME_ID/bundle" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game-bundle.tar.gz

Um pacote com mais de 100 MB não passará por esse caminho. O CDN na frente da API recusa um corpo de solicitação grande com um 413 por si só - algo que a plataforma nunca vê, por isso carrega não limitBytes e não aparece em nenhum registro que você possa ler. UM docker save de uma imagem de servidor real atinge esse tamanho facilmente. Se você ver um 413 sem limitBytes, isso é isso e não o do seu jogo subsídio, que é gigabytes.

Envie o arquivo idêntico ws/v1/game-upload em vez disso - quadros após um A atualização do WebSocket não é um corpo de solicitação, portanto, o limite não se aplica. Mesmo layout de arquivo, mesmo subsídio, mesmas respostas JSON; a única adição é que você deve enviar {"type":"complete"} quando o último byte foi eliminado, porque nada será publicado até que você o faça.

Exemplo de resposta:

{
  "clientPublished": true,
  "serverImageLoaded": true,
  "imageDigest": "sha256:4e7d...",
  "bytesReceived": 318767104
}

A plataforma:

  • troca atomicamente em client/, para que os usuários não vejam uma compilação parcialmente carregada;
  • cargas server/image.tar, calcula seu resumo imutável e fixa novamente a implantação;
  • coloca o contêiner antigo na fila para ser substituído pela imagem carregada;
  • restaura sessões ativas qualificadas de seus instantâneos persistentes.

Você pode fazer upload apenas do cliente ou apenas da imagem do servidor. Uso de patches somente cliente ?mode=merge no mesmo endpoint (veja atualizações parciais); uma imagem em uma mesclagem ainda é carregado inteiro. A franquia de disco de um jogo é 2GB em starhermit.com (ajustável pelo operador) e pode estar sintonizado por jogo; porque um push substitui o conteúdo de um jogo em vez de adicioná-lo, isso é ao mesmo tempo o maior empurrão e a maior quantidade de disco que o jogo pode ocupar. 413 inclui limitBytes; um inválido retorno de arquivo ou imagem 422; e 507 significa que o servidor não tem espaço no momento - está verificado antes que seu corpo seja lido, então um upload condenado é recusado, em vez de ser feito pela metade. Não coloque links simbólicos, links físicos, passagem de caminho ou arquivos fora do layout documentado no arquivo.

Um upload bem-sucedido não significa que o novo processo já passou nas verificações de integridade. Pesquise os existentes GET /api/v1/me/github-games/{id}/deployment visualizar e testar uma sessão real antes de promover o construir. Fixar um commit do repositório posteriormente alterna explicitamente a implantação de volta ao conteúdo do repositório.

Mudar um jogo existente de server= para um contêiner

Suportado e mantém o jogo: o mesmo id, slug, <uid>.starhermit.com endereço, jogadores, tabelas de classificação e conquistas. Não há etapa de registro separada.

  1. Substituir server=... com o seu container.* bloquear starhermit.txt. Os dois são mutuamente exclusivo; um manifesto declarando ambos é recusado.
  2. Empurre um pacote carregando client/ (com esse manifesto) e server/image.tar, sobre ws/v1/game-upload se for grande.
  3. A imagem que você carrega é aquela que é executada. UM container.image= linha no mesmo manifesto é bom manter, mas o resumo enviado vence.
  4. Enquete GET /api/v1/me/github-games/{id}/deployment até que leia running, então comece um verdadeiro quarto ou jogo.

Parte 4: renovar o token da plataforma do contêiner

Na inicialização, o contêiner recebe:

STARHERMIT_API_BASE
STARHERMIT_GAME_SLUG
STARHERMIT_SERVER_TOKEN
STARHERMIT_SERVER_TOKEN_EXPIRES_IN
STARHERMIT_REFRESH_KEY
STARHERMIT_INVOKE_KEY

STARHERMIT_SERVER_TOKEN é estreito: representa o servidor do jogo, não um jogador. Ele expira depois 24 horas por padrão. Agende a renovação em aproximadamente metade do STARHERMIT_SERVER_TOKEN_EXPIRES_IN:

POST {STARHERMIT_API_BASE}/api/v1/games/{STARHERMIT_GAME_SLUG}/server/token
X-Starhermit-Refresh-Key: {STARHERMIT_REFRESH_KEY}

{ "token": "eyJhbGciOi...", "expiresInSeconds": 86400 }

Nenhum token de portador é necessário para este terminal. Isso permite a recuperação mesmo que o token antigo tenha já expirou. Substitua o token na memória atomicamente e agende a próxima renovação do novo expiresInSeconds.

Mantenha os dois segredos de implantação separados:

  • STARHERMIT_INVOKE_KEY autentica solicitações StarHermit em seu contêiner.
  • STARHERMIT_REFRESH_KEY autentica seu contêiner ao renovar seu token StarHermit.

Ambos giram a cada reinicialização do contêiner. Nunca registre-os, devolva-os /describe, coloque-os em um instantâneo ou enviá-los para um player.

Parte 5: integrar um jogador não StarHermit sem OAuth

Execute esse fluxo no jogo ou inicializador nativo, não no contêiner dedicado. O passo a passo completo, com código de cliente testado, é Tutorial: jogadores integrados com chave pública; resumidamente:

  1. Gere uma chave por instalação na primeira inicialização (recomendado Ed25519) e mantenha a chave privada no armazenamento de credenciais do sistema operacional. Nunca faça upload e nunca gere chaves de jogadores em seu servidor.
  2. Peça consentimento e um endereço de e-mail, então POST /api/v1/auth/public-key/register com { email, keyType, keyData } do dispositivo do jogador. Ele é limitado a um registro por endereço e por IP a cada 24 horas (429 com Retry-After), então nunca faça proxy através do seu servidor – cada jogador compartilharia seu IP.
  3. Aguarde a confirmação do jogador. O link enviado por e-mail abre uma página que não muda nada até o jogador pressiona Confirm, que cria a conta e anexa a chave; em starhermit.com eles então chegam ao painel do StarHermit, para que seu jogo não receba esses tokens. Em vez disso entra com a chave até que isso seja bem-sucedido: challenge, assine StarHermit's bytes de desafio exatos, complete. Até o jogador confirma, complete respostas 401 "Public key not registered or revoked.".
  4. Mantenha a sessão com POST /api/v1/auth/refreshe faça login com a chave novamente sempre que a atualização falha. Aceite os termos atuais quando GET /api/v1/me relatórios termsAcceptanceRequired (tanto as sessões da conta quanto os tokens de lançamento do jogador podem — consulte aceitação dos termos). O token de implantação do seu contêiner é isento de termos; essa isenção não se estende aos seus jogadores.

Mais dispositivos. Cada instalação registra sua própria chave com o mesmo endereço de e-mail do jogador, e a chave se junta à conta existente. POST /api/v1/me/public-keys não é uma opção para estes jogadores: requer uma sessão conectada por meio de um provedor OAuth.

5. Adicione um nome voltado para o jogador e uma identidade externa

A conta gerada começa com um pk-... nome de usuário. Deixe o jogador escolher um apelido:

PATCH /api/v1/me
Authorization: Bearer <access-token>
Content-Type: application/json

{ "nickname": "RookPilot" }

Você pode associar a conta à plataforma em que o executável está sendo executado:

POST /api/v1/me/identities
Authorization: Bearer <access-token>
Content-Type: application/json

{
  "provider": "epic",
  "providerUserId": "epic-account-id",
  "metadata": "{\"displayName\":\"RookPilot\"}"
}

Use um não reservado nome do provedor (epic, gogou seu próprio ID de loja). Fazer não usar steam, google, github, ou qualquer outro nome que a plataforma trate como provedor OAuth — aqueles são rejeitados mesmo que esse provedor não esteja configurado. Obtenha o ID externo dessa plataforma SDK/sessão autenticado, não de entrada editável do player. Este endpoint associa uma identidade com a conta StarHermit; não é por si só prova de propriedade da loja e não deve substituir a verificação de tickets da própria plataforma para compras ou proibições.

A API de biblioteca externa separada é opcional e atualmente usa sincronização de demonstração enquanto o provedor as integrações são finalizadas; não é necessário para jogar em servidor dedicado.

Parte 6: entre no jogo e use os serviços StarHermit

Substituir {slug} nos exemplos HTTP abaixo com GAME_SLUG, o UUID do jogo que você obteve em registro. O nome do repositório orbit-league é um nome de exibição/fonte, não o slug da API.

Crie um token de jogo com privilégios mínimos

Use o token de acesso completo uma vez para cunhar um token vinculado ao seu jogo:

POST /api/v1/games/{slug}/launch-token
Authorization: Bearer <access-token>

{ "token": "eyJhbGciOi...", "expiresInSeconds": 3600 }

Use este token de inicialização para jogos e APIs sociais de sessão permitidas. Atualize-o antes de expirar. Mantenha o token completo da conta fora do código do jogo sempre que possível.

Organização de partidas

POST /api/v1/games/{slug}/matchmaking
Authorization: Bearer <game-token>

Enquete GET /api/v1/games/{slug}/matchmaking até status é matchede conecte:

wss://api.starhermit.com/ws/v1/games?sessionId=<sessionId>&access_token=<game-token>

As mensagens do cliente permanecem JSON:

{ "type": "cmd", "data": { "type": "input", "throttle": 0.8 } }

StarHermit converte o comando para o fluxo do contêiner e carimba o StarHermit autenticado ID do usuário. Seu contêiner retorna cargas de jogo autorizadas por meio de frames de fluxo tipo 2.

Classificações e conquistas

Cada jogo oficial recebe uma tabela de classificação Elo. Seu container envia alterações ao Elo e declara conquista é desbloqueada /control; os clientes leem apenas o estado da plataforma resultante:

GET /api/v1/games/{slug}/achievements
GET /api/v1/leaderboards/{leaderboardId}/entries

Um cliente Steam/Epic/GOG modificado não pode enviar diretamente as pontuações da tabela de classificação do jogo ou reivindicar um conquista de propriedade do jogo.

Bate-papo e voz da sessão

GET /api/v1/games/{slug}/sessions/{sessionId} retorna chatConversationId. Sessão as conversas permitem que os participantes conversem e usem a voz mesmo quando não são amigos.

Fluxo de voz típico:

  1. GET /api/v1/voice/rooms?conversationId=<chatConversationId>.
  2. Se necessário, POST /api/v1/voice/rooms com o ID da conversa.
  3. POST /api/v1/voice/rooms/{roomId}/join.
  4. Conectar wss://api.starhermit.com/ws/v1/voice?roomId=<roomId>&access_token=<game-token>.

A mesma conta também permite amigos, presença, convites para jogos, replays e identidade de perfil em todas as construções de vitrines. Mantenha uma chave/conta StarHermit por pessoa em vez de criar uma nova conta para cada partida ou lançamento em loja.

Lista de verificação de produção

Publicação

  • [] O jogo de propriedade existente tem um valor não nulo gameSlug.
  • [] O contêiner rejeita uma chave de invocação errada ou ausente.
  • [] A chave de invocação, a chave de atualização e o token do servidor são lidos do ambiente no início do processo, nunca inseridos na imagem ou armazenados em cache no disco (todos os três giram a cada início do contêiner).
  • [ ] /health não retorna 200 antes que o estado possa ser aceito.
  • [] Pacote usa raw application/gzip, não codificação multiparte.
  • [] A imagem funciona somente leitura, não root, offline e sem volumes.
  • [] O status de implantação e uma sessão real de matchmaking são testados após o upload.
  • [] A atualização do token do servidor é executada antes da metade de sua vida útil e troca os tokens atomicamente.
  • [] Nenhum segredo de implantação é registrado ou persistido em instantâneos.

Integração do jogador

  • [] O par de chaves é gerado no dispositivo do player e a chave privada usa armazenamento seguro.
  • [] A criação da conta é divulgada e consentida.
  • [] A verificação de e-mail é concluída uma vez; 429 Retry-After é respeitado.
  • [] Registro e tokens de jogador não passam pelo servidor dedicado.
  • [] Os tokens de acesso/atualização são armazenados com segurança e a rotação de atualização é serializada.
  • [] IDs externos vêm do estado autenticado do Steam/Epic/GOG SDK.
  • [] A jogabilidade usa um token no escopo do jogo após a configuração inicial da conta.
  • [ ] Atendimentos do cliente achievement, resumed, e abandoned quadros de jogo.
