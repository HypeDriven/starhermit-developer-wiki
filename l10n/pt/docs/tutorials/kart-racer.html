Tutorial: construa um piloto de kart multijogador

Este tutorial constrói a camada multijogador de um jogo de corrida de kart arcade – até oito karts, privados lobbies com amigos, conexão rápida com estranhos, drivers de CPU preenchendo slots vazios na grade, uma contagem regressiva, voltas, ordem de chegada e conquistas - na API StarHermit. Abrange o contrato netcode e as chamadas da plataforma; seu motor, arte da pista e modelo de manuseio são seus.

Tudo específico do jogo aqui – o grand-prix fila, o layout do quadro binário, o botão do item, as constantes físicas - é um valor de exemplo. Somente os pontos finais, envelopes de quadro e limites são comportamento da plataforma e cada um tem links para sua página de referência.

1. Escolha uma arquitetura

Um piloto é a forma de jogo mais difícil para um orçamento de servidor: os karts se movem rápido, colidem e os jogadores sentem 50 ms de atraso na direção. StarHermit oferece duas maneiras de executá-lo, ambas começando com um sala em tempo real:

A. Roteado por host B. Script autoritativo do servidor
Quem simula O cliente do host da sala, pelo menos que quiser (60 Hz+) Seu server= roteiro, no máximo 30Hz
Transporte Quadros binários ativados ws/v1/realtime JSON cmd/game quadros em ws/v1/games
Trapaceando O host é confiável Os clientes não têm autoridade
Elo, conquistas de roteiro Não (o host publica um resultado restrito) Sim - eloUpdates, achievements, repetições
Melhor para Corridas casuais com amigos, física com fidelidade total Corridas classificadas com física simples de arcade

Comece com A a menos que você precise de um jogo classificado; a seção 7 mostra o que muda para B. A servidor de contêiner também pode correr um kart de oito vinculado ao quarto corrida e simular em 60 Hz com autoridade. Sua combinação direta da API de jogos atualmente usa um 1v1 implícito fila, então use uma sala em tempo real para a grade maior. A plataforma não percorre o loop do contêiner.

2. Manifesto

Publique a pasta de compilação distribuível com este starhermit.txt na sua raiz (ver o manifesto). O control.* linhas dão aos jogadores uma interface de usuário religada e seu cliente um API de controles para ler ligações de:

name=Turbo Hermits
launch=index.html
cover=art/cover.png
control.accelerate=KeyW+ArrowUp | Accelerate
control.brake=KeyS+ArrowDown | Brake / reverse
control.left=KeyA+ArrowLeft | Steer left
control.right=KeyD+ArrowRight | Steer right
control.drift=ShiftLeft+ShiftRight | Drift
control.item=Space | Use item

O caminho A tem não server= linha. Se um jogo envia um script, iniciar uma sala cria uma sessão vinculada e somente o script pode encerrar a partida - o anfitrião POST .../result deixa de ser a forma como as corridas terminam (seção 7).

3. Faça login e leia o básico

Um jogo hospedado na plataforma é aberto com #game_token=<jwt> no URL - leia uma vez, remova-o com history.replaceStatee atualize-o antes de expirar em 60 minutos (detalhes no passo a passo de xadrez e autenticação). Sua lesma é do token game_scope reivindicação (ou location.hostnamede primeiro rótulo); nunca codifique-o.

Ao carregar, busque o que o menu precisa:

GET /api/v1/games/{slug}/controls     # effective key bindings (manifest defaults + overrides)
GET /api/v1/games/{slug}/settings     # camera, volume, last chosen kart — your own keys
GET /api/v1/realtime/rooms/mine       # 200 → the player is still in a race; rejoin it

Salvar opções de menu com PATCH /api/v1/games/{slug}/settings ({"settings":{"kart":"hermit-crab"}}). As configurações acompanham o player em todas as máquinas e não precisam de declaração.

4. O lobby

Um Grande Prêmio é gratuito para todos, então a sala tem uma equipe de oito lugares. Pista, contagem de voltas e motor aula vai no opaco metadata:

POST /api/v1/realtime/rooms
Authorization: Bearer <launch token>

{ "teamCount": 1, "seatsPerTeam": 8, "backfillAfterSeconds": 45,
  "aiPlayers": 0, "name": "Friday cup", "isVisible": true,
  "metadata": { "track": "coral-loop", "laps": 3, "cc": 150 } }

Com um token de lançamento, o jogo da sala vem do token, então gameSlug pode ser omitido. O criador é o anfitrião sentado (0, 0). A partir daqui, o lobby é o fluxo normal da sala:

  • Amigos — POST /rooms/{id}/invites com {"toUserId": ...}. A plataforma os notifica; aceitando assentos neles. Mostre o seis caracteres joinCode para que os amigos também possam digitá-lo POST /rooms/join-by-code.
  • Estranhos - o anfitrião chama POST /rooms/{id}/open. Jogadores sem chamada de sala POST /rooms/quick-join com {"seats": 1} e, em 404, crie e abra os seus próprios.
  • Rastrear votação/mudança de opinião do anfitrião — PATCH /rooms/{id} com novo metadata e o quarto revision como expectedRevision.
  • Solo contra CPUs - crie com "aiPlayers": 7, então POST /rooms/{id}/start.

Uma sala aberta começa sozinha quando todos os oito assentos são preenchidos ou backfillAfterSeconds passes; o anfitrião também pode POST /rooms/{id}/start. Cada assento ainda vazio se torna um participante da IA – esses são os seus Controladores de CPU.

5. O soquete de corrida (roteado pelo host)

Conectar

Cada participante abre o soquete em tempo real com um ticket de uso único:

const { ticket } = await api.post("/api/v1/realtime/connection-tickets"); // { ticket, expiresIn }
const ws = new WebSocket(
  `wss://api.starhermit.com/ws/v1/realtime?roomId=${roomId}&ticket=${encodeURIComponent(ticket)}`);
ws.binaryType = "arraybuffer";

Os quadros de texto são push JSON e quadros de controle; quadros binários são jogabilidade. O roster empurrar é sua grade: após o início ela fica congelada, assentos AI incluídos. Com uma equipe, a posição da grade de um kart é a sua do participante slot.

ws.onmessage = (e) => {
  if (typeof e.data === "string") return onControl(JSON.parse(e.data)); // roster, presence, event, ready, chat, result
  const bytes = new Uint8Array(e.data);
  const sender = guidFromDotNet(bytes.subarray(0, 16)); // server-stamped, trustworthy
  onGameplay(sender, new DataView(e.data, 16));          // your payload starts at byte 16
};

// The server prefixes the sender's participant id in .NET GUID byte order:
// the first three groups are little-endian.
function guidFromDotNet(b) {
  const h = (i) => b[i].toString(16).padStart(2, "0");
  return `${h(3)}${h(2)}${h(1)}${h(0)}-${h(5)}${h(4)}-${h(7)}${h(6)}-` +
         `${h(8)}${h(9)}-${h(10)}${h(11)}${h(12)}${h(13)}${h(14)}${h(15)}`;
}

Nunca coloque um ID de jogador em sua própria carga e confie nele — o prefixo de 16 bytes é a única identidade que o servidor garante.

Roteamento e orçamento

A plataforma impõe o formato do jogo roteado pelo host:

  • A convidados alcance de quadros binários apenas o anfitrião - esse é o canal de entrada.
  • O anfitrião alcance de quadros binários cada convidado - esse é o canal de instantâneo.
  • Cada quadro é no máximo 8 KB; cada conexão pode enviar 30 mensagens/segundo (2× explosão para um segundo). Passar fecha o soquete com PolicyViolation.

Portanto, o host simula na taxa que parecer correta (60 Hz é o típico), mas envia instantâneos em 20 Hz e os convidados enviam entradas em 20 Hz. Isso deixa espaço para o quadro de controle ocasional.

Layouts de quadros (exemplo)

Entradas, convidado → host, 7 bytes:

Desvio Tipo Campo
0 u8 1 = entrada
1 u16 seq — incrementa cada envio
3 i8 dirigir, −127…127
4 u8 acelerador, 0…255
5 u8 bits: 0 freio, 1 desvio
6 u8 itemPresses - um contador, não uma bandeira

itemPresses é uma contagem contínua de pressionamentos de botão de item. A 20 Hz, uma pressão inferior a 50 ms caso contrário, ficará entre as amostras; com um contador, o host dispara um item por incremento, porém o prensas pousaram.

Instantâneos, host → convidados, 4 + 22 bytes por kart (176 bytes para uma grade completa):

Desvio Tipo Campo
0 u8 2 = instantâneo
1 u16 carrapato hospedeiro
3 u8 contagem de karts
por kart u8, f32 ×4, u8, u16, u8, u8 slot, x, z, rumo, velocidade, volta, ponto de verificação, item, bandeiras

Convidados renderizam outros karts ~100 ms no passado, interpolando entre os dois instantâneos que colchetes nesse horário e prevejam seu próprio kart localmente a partir de suas entradas, facilitando a direção do anfitrião posição quando discordam. Incluir a última entrada seq o anfitrião aplicado por kart em flags ou um campo extra se desejar uma reconciliação exata.

Contagem regressiva, eventos de corrida, final

Os quadros de controle são JSON, no máximo 4 KB, e os carimbos do servidor from com o ID de participante do remetente:

  • Convidados enviam {"type":"ready"} assim que a faixa for carregada.
  • O host espera que todos os humanos conectados estejam prontos (ou um tempo limite) e, em seguida, envia {"type":"event","kind":"countdown","goInMs":3000}. Os convidados iniciam a contagem regressiva local em recibo - nenhuma sincronização de relógio é necessária com esta precisão.
  • Outras batidas de corrida também são event quadros: {"kind":"lap","slot":3,"lap":2}, {"kind":"finished","slot":3,"place":1,"timeMs":94210}.
  • chat está disponível para todos, mas os visitantes estão limitados a 10 quadros de controle por minuto – o suficiente para ready e alguns "ah"s, não para jogabilidade.

Quando o último humano cruzar a linha (ou um cronômetro após o vencedor acabar), o anfitrião envia o resultado, que fecha a sala e empurra {"type":"result"} para todos:

POST /api/v1/realtime/rooms/{id}/result

{ "teamScores": [0],
  "metadata": { "track": "coral-loop",
                "order": [ { "slot": 3, "timeMs": 94210 }, { "slot": 0, "timeMs": 95002 } ],
                "bestLapMs": 30112 } }

teamScores precisa exatamente de uma entrada por equipe (fixada de 0 a 50), o que não traz nada de útil em um de graça para todos; a ordem de acabamento reside em metadata. Uma corrida em equipe é a mesma sala com teamCount: 2 e os pontos de cada equipe em teamScores.

Drivers de CPU, abandonadores e alterações de host

  • Os assentos AI são seus para dirigir. A plataforma reserva o assento e nomeia o motorista; o anfitrião a simulação o orienta (uma linha de corrida através dos pontos de controle, com alguns elásticos).
  • Um convidado que sai no meio da corrida (POST /rooms/{id}/leave) mantém seu kart no grid: a escalação push mostra o mesmo participante id agora isAi: true, e a CPU do host assume o controle desse kart.
  • Um convidado que cai ainda está na sala; mantenha o kart em movimento e deixe-os se reconectar - o soquete mais novo substitui o antigo.
  • Se o anfitrião sair, o papel de hospedeiro passa para o humano remanescente há mais tempo e o roster push mostra o novo isHost. Cada convidado já possui o instantâneo completo mais recente, então o novo o host retoma a simulação e começa a enviar instantâneos; as entradas dos convidados agora são direcionadas para eles. A migração de host é tarefa do seu código — a plataforma apenas move a função.
  • Se o host simplesmente desconectar, a sala fecha após 60 segundos sem um soquete de host.

6. Ao redor da corrida

  • Voz e bate-papo. Cada convidado já pode chat no soquete em tempo real; para voz, veja Voz.
  • Revanche. A sala é fechada após o resultado. Peça ao anfitrião para criar uma nova sala e convide o humanos da escalação anterior ou enviar todos de volta para adesão rápida.
  • Tabelas de classificação de tempo de volta. A tabela de classificação da plataforma de um jogo é o seu tabuleiro elo, escrito apenas por um servidor tempo de execução. Um placar definido pelo editor aceita POST /api/v1/leaderboards/{id}/submit, mas isso a pontuação é reivindicada pelo cliente – ótimo para um contra-relógio amigável, não para nada com prêmios.

7. Variante B: corridas com autoridade de servidor

Para jogos classificados, mova a simulação para um script. O lobby permanece inalterado; adicione o script e configurações de matchmaking para o manifesto:

server=server.js
matchmaking.max_wait_seconds=20
matchmaking.ai_players=7

Agora, duas coisas criam corridas: começando um quarto cria uma sessão vinculada à sala para seus humanos e matchmaking (POST /api/v1/games/{slug}/matchmaking?queue=grand-prix) cria um quando oito jogadores são encontrados - ou, com as configurações acima, após 20 segundos com CPUs em até sete vazios assentos. Um lobby de amigos pode fazer fila junto com POST /realtime/rooms/{id}/matchmake.

De qualquer forma, os clientes levam o sessionId (o quarto é gameSessionId, ou o ticket correspondente) e brincar ws/v1/games?sessionId=…. O soquete em tempo real, se houver, é mantido apenas para a escalação.

O roteiro

Toda a simulação é executada em onTick no teto de 30 Hz. Cada invocação é uma nova sandbox que recebe sessionState entra e retorna, então mantenha esse estado pequeno - ele é serializado a cada tick.

const TRACK = { laps: 3, radius: 14,
  checkpoints: [[0, 0], [120, 0], [160, 60], [120, 120], [0, 120], [-40, 60]] };

globalThis.game = {
  tickRateHz: 30,
  replays: true,
  queues: [{ key: "grand-prix", teams: 8, teamSize: 1 }],
  achievements: [
    { key: "chequered-flag", name: "Chequered Flag", description: "Win a race.", points: 10 }
  ],

  createSession(ctx) {
    const karts = racers(ctx).map((r, i) => ({
      id: r.id, name: r.name, ai: r.ai, x: -8 * (i % 2), z: -6 * i, heading: 0, speed: 0,
      cp: 1, lap: 0, boost: 0, boosts: 1, input: {}, ack: 0, finishedAt: null
    }));
    return { ok: true, sessionState: { t: ctx.now, goAt: ctx.now + 4000, karts, order: [] } };
  },

  onPlayerMessage(ctx) {                       // durable commands: discrete actions
    const s = copy(ctx.sessionState);
    const k = s.karts.find((k) => k.id === ctx.message.from);
    if (ctx.message.data?.type === "use-item" && k && k.boosts > 0 && ctx.now >= s.goAt) {
      k.boosts--; k.boost = 1.2;
    }
    return { ok: true, sessionState: s };
  },

  onTick(ctx) {
    const s = copy(ctx.sessionState);
    const dt = Math.min(Math.max((ctx.now - s.t) / 1000, 0), 0.1);
    s.t = ctx.now;
    for (const i of ctx.inputs || []) {        // latest realtime input per player since last tick
      const k = s.karts.find((k) => k.id === i.from);
      if (k) { k.input = i.data; k.ack = Math.max(k.ack, Math.floor(+i.data.seq) || 0); }
    }
    if (ctx.now >= s.goAt) {
      for (const k of s.karts) {
        if (k.finishedAt) continue;
        move(k, k.ai ? aiInput(k) : k.input, dt);   // pure motion — shared with the client
        progress(k, s, ctx);                        // checkpoints, laps, finish — server only
      }
    }
    const snap = s.karts.map((k) =>
      [k.id, r2(k.x), r2(k.z), r3(k.heading), r2(k.speed), r2(k.boost), k.lap, k.cp, k.ack]);
    const out = { ok: true, sessionState: s,
      broadcast: [{ to: "all", data: { type: "snap", t: s.t, goAt: s.goAt, karts: snap } }] };
    if (raceOver(s, ctx)) Object.assign(out, finish(s, ctx));
    return out;
  }
};

Os ajudantes são códigos de jogo comuns. As partes com as quais a plataforma se preocupa:

  • racers(ctx) lê a grade a partir de qualquer início da sessão: ctx.room.roster por um sala (assentos AI têm userId: null, então dê a eles IDs como ai-0-5), ctx.matchmaking.seats por um corrida matchmade (pular assentos com id: null), outro ctx.players.
  • move(k, input, dt) deve fixar cada valor de entrada — steer para −1…1, throttle para 0…1 — porque ctx.inputs[].data é tudo o que o cliente enviou. Apenas from é confiável. Mantenha-o puro - não ctx, sem estado de sessão — então o cliente também pode executá-lo (consulte previsão do lado do cliente).
  • Aleatoriedade e tempo vem de ctx.random e ctx.now; não há Date ou Math.random.
  • finish(s, ctx) retorna result (que encerra a sessão e, para uma sala, fecha-a), achievements para o vencedor se for humano, e eloUpdates para pilotos humanos - por exemplo, em pares elo na ordem de acabamento, lido e escrito de volta para ctx.playerStates. Assentos AI não podem receber o estado do jogador, classificações ou conquistas.
  • raceOver também deveria acabar com corridas que ninguém pode terminar - cada humano morto de acordo com ctx.presence (quartos) ou um limite de tempo difícil.
  • Repetições guarde apenas o final sessionState. Mantenha uma tabela compacta de tempos de volta e finalização ordem nele, não um registro de posição por tick.

O cliente

Envie a direção como uma entrada em tempo real a cada tick e ações discretas como comandos duráveis:

// ~30 Hz: latest-wins, batched into the next onTick
send({ type: "cmd", data: { type: "input", realtime: true, seq: ++seq,
                            steer, throttle, brake, drift } });

// on key press: a durable command, runs onPlayerMessage immediately
send({ type: "cmd", data: { type: "use-item" } });

Unid deve passe por um comando durável. As entradas em tempo real são as últimas vitórias entre os ticks, e o plataforma preserva apenas os campos one-shot pass, tackle e shoot quando uma amostra mais recente substitui um botão mais antigo — qualquer outro botão em uma entrada em tempo real pode ser substituído antes do tick vê isso.

achievement os quadros chegam no mesmo soquete; ler GET /api/v1/games/{slug}/achievements ligado carregar por qualquer coisa concedida antes de ser aberta.

Previsão do lado do cliente

Renderizar apenas o que o servidor envia faz com que o kart pareça estar sendo conduzido na lama. Uma direção mudança tem que chegar ao servidor, aguardar o próximo tick (até 33 ms a 30 Hz) e voltar em um snap — a um ping de 80 ms que é superior a 100 ms antes do kart virar. A previsão esconde isso: o cliente movimentos seu próprio kart imediatamente e trata cada snap como uma correção, não como a imagem.

Compartilhe o código de movimento

Divida a simulação da maneira que o script acima faz: um puro move(k, input, dt) para manuseio e somente servidor progress para checkpoints, voltas e finalizações. Exponha o código de movimento de server.js como um segundo global - o padrão que o xadrez usa para globalThis.chessRules — e carregue o mesmo arquivo em o navegador:

// server.js — shared by the platform's sandbox and the browser
function move(k, input, dt) { /* clamp input, integrate speed, heading, x, z, boost */ }
globalThis.kartPhysics = { move, TRACK };
globalThis.game = { /* ... as above ... */ };

<script src="server.js"></script>  <!-- defines kartPhysics; the client never calls game.* -->

O cliente prevê apenas movimento. Voltas, posições, itens e a ordem de chegada permanecem no servidor ligue. Não espere resultados idênticos: a sandbox e o navegador podem discordar nas últimas partes do Math.sin/Math.cose posições em snap são arredondados. A reconciliação absorve esse desvio.

Siga o ritmo do servidor

O servidor não executa uma etapa por entrada. Cada tick aplica o mais recente entrada que vale para aquele kart, continua usando-o até que chegue um mais novo, e integra em tempo real desde o carrapato anterior. Portanto, espelhe essa forma em vez de pisar na taxa de quadros de exibição:

const pending = [];                              // inputs the server hasn't acknowledged yet
let seq = 0, predicted, previous;               // { x, z, heading, speed, boost }, seeded from the first snap
let error = { x: 0, z: 0, heading: 0 };          // visual offset, decays in render()

setInterval(() => {                              // 30 Hz, the script's tickRateHz
  if (!predicted || serverNow() < goAt) return;  // the server ignores movement before goAt
  const input = { steer: readSteer(), throttle: readThrottle(), brake: held("brake"), drift: held("drift") };
  const entry = { seq: ++seq, input, dt: 1 / 30 };
  send({ type: "cmd", data: { type: "input", realtime: true, seq: entry.seq, ...input } });
  pending.push(entry);
  previous = { ...predicted };
  kartPhysics.move(predicted, input, entry.dt);  // the kart responds now, not a round trip later
}, 1000 / 30);

O envio mais rápido do que a taxa de tick é desperdiçado – apenas a entrada mais recente por tick é usada – e o a plataforma reduz as entradas em tempo real acima de seu limite por conexão.

Reconcilie-se em cada snap

O roteiro ecoa ack, o mais alto seq foi aplicado para cada kart. Em cada snap, rebobine seu kart para o estado do servidor e reproduza o que o servidor ainda não viu:

function onSnap(snap) {
  const [, x, z, heading, speed, boost, lap, cp, ack] = snap.karts.find((k) => k[0] === myId);
  while (pending.length && pending[0].seq <= ack) pending.shift();   // applied or superseded

  const corrected = { x, z, heading, speed, boost };
  for (const p of pending) kartPhysics.move(corrected, p.input, p.dt);

  if (!predicted) { predicted = corrected; previous = { ...corrected }; return; } // first snap
  error.x += predicted.x - corrected.x;          // what the player would see jump
  error.z += predicted.z - corrected.z;
  error.heading += predicted.heading - corrected.heading;
  if (Math.hypot(error.x, error.z) > 3) error = { x: 0, z: 0, heading: 0 }; // wall hit, bump: snap
  predicted = corrected;
  hud.lap = lap; hud.checkpoint = cp;            // progress is never predicted
}

Descartando tudo até ack está certo, embora as últimas vitórias ignorem algumas entradas: um ignorado input foi substituído antes do servidor ser ativado, então também nunca afetou o kart do servidor.

Correções suaves, renderização na taxa de quadros

Pequenas correções devem ser invisíveis. Desenhe o kart na posição prevista mais um decaimento deslocamento de erro e interpolar entre as duas últimas etapas de previsão de 30 Hz para que uma exibição de 60 ou 144 Hz move-se suavemente:

function render(frameDt) {
  const decay = Math.exp(-frameDt / 0.1);        // ~100 ms to absorb a correction
  error.x *= decay; error.z *= decay; error.heading *= decay;
  const a = sinceLastStep() * 30;                // 0…1 between prediction steps
  drawKart(lerp(previous.x, predicted.x, a) + error.x,
           lerp(previous.z, predicted.z, a) + error.z,
           lerpAngle(previous.heading, predicted.heading, a) + error.heading);
}

Ajuste o limite do snap em vez do decaimento: uma correção maior que o comprimento do kart é uma verdadeira evento (um solavanco que você não previu) e é melhor lido como um estalo rápido do que como um deslizamento lento.

Saiba o que não prever

  • Outros karts. Eles são desenhados ~100 ms no passado (buffer snaps e interpolar entre os dois que suporte serverNow() - 100), então uma colisão prevista contra eles é uma colisão com onde eles eram. Preveja as paredes e a pista – elas não se movem – e deixe o servidor resolver solavancos de kart a kart. A correção chega em uma viagem de ida e volta. Se o buffer secar, extrapole da velocidade e direção por até ~100 ms e segure.
  • Unid. use-item é um comando durável, então ele é executado em onPlayerMessage assim que chegar - sem carrapato, espere. Toque a chama e o som ao pressionar a tecla; deixe a velocidade chegar reconciliação, uma vez que boost está no snap. Se o servidor recusar (sem cobranças restantes), o próximo snap reverte.
  • Estado de corrida. Contagem de voltas, posição e chegada vêm de snap e apenas as transmissões do seu script.

Estime o relógio do servidor

snap.t e goAt são o horário do servidor (ctx.now). Mantenha um deslocamento da menor lacuna observada, que filtra entregas lentas:

let offset = Infinity;
function noteSnap(snap) { offset = Math.min(offset, performance.now() - snap.t); }
const serverNow = () => performance.now() - offset;
