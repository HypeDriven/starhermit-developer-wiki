Reivindique um jogo adicionado por outra pessoa

Se alguém já adicionou seu jogo GitHub público ao StarHermit, você não precisa criar um segunda listagem. Reivindique a listagem existente para se tornar seu proprietário verificado e gerenciar seus metadados, hospedagem, implantação, back-end do servidor e transferências futuras.

A reivindicação é protegida pelo controle do repositório. Saber o ID do jogo ou o URL do repositório não é suficiente. Você deve provar o controle de uma das duas maneiras:

  1. Vincule a conta pessoal do GitHub que possui o repositório; ou
  2. Confirme seu ID de usuário StarHermit imutável como owner= no repositório starhermit.txt.

O segundo método é especialmente útil para repositórios de propriedade da organização, porque o atual A verificação de login do GitHub corresponde aos proprietários do repositório pessoal e não infere a associação à organização.

O que a reivindicação muda

Uma reivindicação bem-sucedida:

  • mantém o ID do jogo/lista existente e seu histórico acumulado;
  • altera o usuário StarHermit gerenciador da listagem para você;
  • marca a listagem como isVerifiedOwner: true;
  • atualiza metadados e controles confiáveis ​​de starhermit.txt quando aplicável;
  • provisiona ou atualiza um back-end de script/contêiner declarado;
  • permite hospedagem de plataforma quando disponível e filas de implantação conforme pending;
  • remove o acesso de gerenciamento da pessoa que enviou originalmente a listagem.

A reivindicação não dá ao remetente anterior acesso à sua conta GitHub e não mescla Contas de usuário StarHermit. Transfere a gestão dessa listagem específica.

Antes de começar

Você precisa de:

  • Uma conta StarHermit e um token de acesso completo do usuário – não um token de lançamento no escopo do jogo.
  • Acesso de gravação ao repositório se estiver usando o owner= método de prova.
  • O ID de listagem existente do StarHermit.
  • Para um jogo de repositório clonado, um código válido starhermit.txt na raiz do repositório.

Apenas github.com/<owner>/<repo> repositórios e seus sites GitHub Pages participam desta reivindicação fluxo. Um URL hospedado arbitrário não tem propriedade de repositório GitHub para provar e não pode ser reivindicado. caminho.

Exemplos abaixo usam:

API=https://api.starhermit.com
ACCESS_TOKEN='your-full-user-access-token'
OWNER='your-github-login'
REPO='your-game-repository'

Os tokens de acesso duram 15 minutos. Atualize o seu antes de começar se estiver próximo do vencimento.

Etapa 1: encontre a listagem existente

Listar jogos compartilhados:

curl -sS "$API/api/v1/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Cada item inclui a listagem imutável id, normalizado repoUrl, ownerLogin, repoName, o remetente atual e status de propriedade:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "isVerifiedOwner": false,
  "submittedByUserId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "submittedByUsername": "someone-else"
}

Combine em ambos ownerLogin e repoName; não selecione um jogo apenas porque seu nome de exibição é semelhante. Com jq:

GAME_ID=$(
  curl -sS "$API/api/v1/github-games" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r --arg owner "$OWNER" --arg repo "$REPO" \
    '.[] | select((.ownerLogin | ascii_downcase) == ($owner | ascii_downcase)
               and (.repoName | ascii_downcase) == ($repo | ascii_downcase)) | .id' |
  head -n1
)

printf 'Listing ID: %s\n' "$GAME_ID"

Pare se o resultado estiver vazio. Não ligue para reivindicação com um ID copiado de uma listagem não relacionada.

Etapa 2: escolha como comprovar a propriedade

Opção A: vincular a conta GitHub do proprietário do repositório

Use isto quando o repositório pertencer diretamente ao seu login pessoal do GitHub.

No fluxo de conta/configurações do StarHermit, inicie GitHub OAuth em link modo enquanto estiver conectado ao Conta StarHermit que deve gerenciar o jogo. Vincular é diferente de criar acidentalmente um segunda conta StarHermit com login no GitHub.

O fluxo da API começa em:

GET /api/v1/auth/oauth/github/authorize?link=true

É orientado pelo navegador e usa um cookie de estado de curta duração. A vinculação requer StarHermit recente autenticação. Conclua a autorização do GitHub na mesma sessão do navegador que a iniciou.

Verifique o resultado:

curl -sS "$API/api/v1/me/github" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Esperado:

{ "linked": true, "login": "octocat" }

O login retornado deve corresponder ao da listagem existente ownerLogin, sem distinção entre maiúsculas e minúsculas. Um pessoal O login do GitHub não prova ser membro de uma organização proprietária do repositório. Por um repositório de propriedade da organização, use a Opção B.

Opção B: adicionar owner= para starhermit.txt

Isso prova controle porque somente alguém capaz de publicar o conteúdo do repositório pode agregar valor. Definir owner ao seu ID de usuário StarHermit imutável (UUID), não seu nome de usuário ou apelido.

Obtenha sua identificação:

STARHERMIT_USER_ID=$(
  curl -sS "$API/api/v1/me" \
    -H "Authorization: Bearer $ACCESS_TOKEN" |
  jq -r '.id'
)

Na raiz do repositório, crie ou atualize starhermit.txt:

name=Orbit League
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html
owner=3fa85f64-5717-4562-b3fc-2c963f66afa6

Substitua o proprietário do exemplo por STARHERMIT_USER_ID. Não coloque seu nome de usuário ou apelido aqui; eles podem mudar, enquanto o ID do usuário é o identificador de propriedade estável.

Para um jogo oficial, mantenha exatamente uma declaração de back-end:

# JavaScript runtime:
server=server.js

# OR container runtime, never both:
# container.image=ghcr.io/your-org/orbit-server@sha256:<64-lowercase-hex>

Confirme e envie o manifesto para o repositório/versão que StarHermit pode ler:

git add starhermit.txt
git commit -m "Declare StarHermit game ownership"
git push

Antes de reivindicar, abra o arquivo bruto do repositório starhermit.txt URL em um navegador não autenticado e confirme se o novo valor pode ser lido publicamente. A reivindicação lê o repositório no momento da solicitação; um mudanças locais não impostas não podem provar nada.

Etapa 3: validar o manifesto

Para um jogo de repositório clonado normal, a reivindicação requer:

  • starhermit.txt na raiz do repositório;
  • não vazio name=;
  • launch= apontando para um relativo ao repositório .html ou .htm arquivo;
  • um opcional válido server= caminho que termina em .js/.mjs, ou um válido container.image= declaração;
  • nunca os dois tempos de execução do servidor ao mesmo tempo.

Uma listagem de páginas do GitHub mantém seu URL hospedado como destino de lançamento e não requer um manifesto quando a propriedade pessoal do GitHub for comprovada, embora um nome de manifesto válido ainda possa atualizar seu nome de exibição.

Se o jogo declarar um contêiner, sua imagem deverá satisfazer o registro, o namespace do proprietário e o resumo regras em Servidores de jogos hospedados em contêineres. A hospedagem de contêineres também pode ser restringido pelo operador da plataforma.

Etapa 4: reivindicar a listagem

A solicitação de reivindicação não tem corpo:

curl -sS -X POST \
  "$API/api/v1/me/github-games/$GAME_ID/claim" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Um sucesso 200 retorna o jogo atualizado:

{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "repoUrl": "https://github.com/octocat/orbit-league",
  "ownerLogin": "octocat",
  "repoName": "orbit-league",
  "displayName": "Orbit League",
  "launchPath": "index.html",
  "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "isVerifiedOwner": true,
  "metadataSource": "starhermit.txt",
  "hosting": {
    "hostingEnabled": true,
    "deployStatus": "pending"
  }
}

O ID deve ser o mesmo encontrado na Etapa 1. Não crie uma nova listagem após uma reivindicação bem-sucedida.

Reivindicar uma listagem que você já gerencia é permitido intencionalmente. Ele relê o manifesto, reprovisiona o back-end e recoloca a hospedagem na fila, para que a mesma chamada possa ser usada para ressincronizar um jogo gerenciado pelo proprietário após alterações no repositório.

Etapa 5: verificar a aquisição e implantação

Confirme se o jogo agora aparece na sua lista gerenciada:

curl -sS "$API/api/v1/me/github-games" \
  -H "Authorization: Bearer $ACCESS_TOKEN" |
jq --arg id "$GAME_ID" '.[] | select(.id == $id)'

Verifique o estado de implantação:

curl -sS \
  "$API/api/v1/me/github-games/$GAME_ID/deployment" \
  -H "Authorization: Bearer $ACCESS_TOKEN"

Uma declaração geralmente coloca uma implantação na fila, então pending imediatamente após a reclamação ser normal. Enquete com espera até atingir o estado ativo/sucesso do ambiente ou expor deployError.

Após a aquisição, os endpoints de gerenciamento disponíveis para você incluem:

PUT    /api/v1/me/github-games/{id}/deployment  pin a commit/branch and redeploy
POST   /api/v1/me/github-games/{id}/bundle      upload built client/container output
PUT    /api/v1/me/github-games/{id}/hosting     requeue hosting where supported
POST   /api/v1/me/github-games/{id}/transfer    transfer management deliberately
DELETE /api/v1/me/github-games/{id}             remove the game

O remetente original não vê mais esta listagem em GET /api/v1/me/github-games e não pode use esses endpoints de gerenciamento com escopo de proprietário para isso.

Solução de problemas

403: vincule o proprietário do repositório ou adicione owner=

O login vinculado do GitHub não corresponde ownerLogin, ou o manifesto owner não corresponde exatamente seu ID de usuário StarHermit.

  • Verificar GET /api/v1/me/github.
  • Verifique o exato ownerLogin retornado pela listagem pública.
  • Para repositórios de organizações, use owner=<your StarHermit user ID> no repositório.
  • Confirme que você enviou o manifesto e que seu URL bruto pode ser lido publicamente.

404: nenhum jogo compartilhado com esse ID

O ID está errado ou a listagem foi removida. Repita a Etapa 1. Listagens removidas não podem ser reivindicadas.

400: ausente ou inválido starhermit.txt

Para um repositório clonado, certifique-se de que o manifesto raiz seja válido name e HTML launch valores. Também validar declarações opcionais de script/contêiner. A declaração não confia originalmente nos metadados inserido por um não proprietário; ele os substitui por metadados controlados pelo repositório.

A reivindicação falha em torno do slug/backend

O script pode ser inválido ou a hospedagem do contêiner pode estar indisponível. Verifique o erro retornado e a declaração de back-end e chame a reivindicação novamente. A plataforma atribui o UUID do jogo como seu slug; não há nenhum slug manifesto para escolher ou resolver.

GitHub foi vinculado, mas a conta errada do StarHermit possui o link

Faça login na conta StarHermit pretendida e conclua o OAuth link fluir para lá. Não reivindique de uma segunda conta StarHermit temporária e depois contar com a fusão de contas; o jogo de transferências de API gerenciamento, não identidades de usuários.

Notas de segurança

  • Nunca aceite um link de reivindicação ou ID de listagem como prova de propriedade do repositório.
  • Não coloque tokens de acesso do GitHub, credenciais de contêiner ou outros segredos starhermit.txt.
  • Sempre use o ID de usuário StarHermit imutável em owner=; não use um nome de usuário ou apelido.
  • Revise a listagem existente e o URL do repositório antes de reivindicar; os nomes de exibição não são exclusivos.
  • Se você transferir o jogo posteriormente, o destinatário se tornará o gerente, mas o status de proprietário verificado será redefinir. Eles próprios deverão executar o fluxo de declarações se controlarem o repositório.
