Jogos GitHub

Publique um jogo de um repositório GitHub em Eremita Estelarou registre um jogo da web já hospedado. Para jogos de repositório, a plataforma lê starhermit.txt, clona o repositório e o veicula em <slug>.starhermit.com. Porque /api e /ws são proxy da mesma origem desse subdomínio, um jogo hospedado na plataforma precisa sem configuração baseada em CORS ou API. Um commit fixado controla qual versão do repositório está ativa. O implementação de referência de xadrez é publicado desta forma e serve como exemplo de referência do modelo.

URL base: https://api.starhermit.com. Todas as rotas estão sob api/v1/... e exigem um JWT, salvo indicação em contrário.

Os arquivos do cliente hospedado podem declarar vida útil do cache de pasta e origens CORS adicionais em starhermit.txt. Essas políticas são publicadas com os arquivos do cliente; uma mesclagem sem manifesto retém configurações existentes, enquanto um manifesto fornecido as substitui.

O manifesto: starhermit.txt

Lugar starhermit.txt na raiz do repositório. Formatar: key=value linhas, # inicia um comentário.

name=Your Game
# (There is no slug key: the platform assigns your game a uid and uses it as the
# slug — the same value as its <uid>.starhermit.com address. Nothing can choose
# it, so two games can never contend for a name. Your client reads its own slug
# from the launch token's game_scope claim.)
launch=index.html        # repo-relative HTML entry
cover=art/cover.png      # optional cover art for the library tile; or an https:// URL
description=One-line pitch\nSecond line   # optional; or description.file=DESCRIPTION.md
release_notes.file=CHANGELOG.md          # optional; or release_notes=inline text
owner=<starhermit user id>  # UUID from GET /api/v1/me; do not use username/nickname
# Choose at most one authoritative backend, or omit both for a browser-only game:
server=server.js         # sandboxed JavaScript; see game-scripts.md
# container.image=ghcr.io/owner/game@sha256:<64 lowercase hex>; see container-games.md

control.up=KeyW+ArrowUp | Move forward
control.shoot=Space | Shoot
  • Não há slug chave: a plataforma atribui um uid e o usa como subdomínio (<uid>.starhermit.com) e o namespace da API do jogo (/api/v1/games/<uid>/…).
  • cover (apelidos cover_art, coverart) é a arte mostrada no bloco da biblioteca do jogo: um caminho relativo ao arquivo de inicialização ou um valor absoluto https:// URL. Opcional – sem ele, o bloco mostra o favicon do seu site. Releia a cada implantação, então mudar a linha muda a capa. Ver Arte da capa para as culturas de azulejos.
  • description / release_notes (ou description.file / release_notes.file, que nomeia um .md/.markdown/.txt arquivo relativo ao manifesto) são textos opcionais para o seu jogo. Eles são relidos em cada implantação, como cover. Ver Descrição e notas de lançamento.
  • server declara um back-end JavaScript em sandbox; ver game-scripts.md.
  • container.image declara um back-end de contêiner; ver container-games.md. Ele deve ser fixado por resumo, hospedado no namespace verificado do proprietário do GitHub em um registro permitido e pode ser acompanhado por container.port, container.health, container.memory_mb, container.cpue não secreto container.env.* valores.
  • Ambas as chaves de back-end são opcionais para um jogo de navegador puro, mas são mutuamente exclusivas.

Ligações de controle padrão

Um jogo pode declarar zero ou mais ações do navegador de desktop:

control.<action>=<code>[+<code>...][ | <label>]
  • As ações estão em letras minúsculas [a-z0-9_]{1,32} identificadores e reter a ordem do manifesto.
  • Os códigos são KeyboardEvent.code valores; + separa chaves alternativas para uma ação.
  • O rótulo opcional é mostrado nas UIs de remapeamento de controle e o padrão é o ID da ação.
  • Um manifesto pode declarar até 32 ações e 4 códigos por ação. Um código não pode ser usado por duas ações. Linhas de controle inválidas são ignoradas.
  • Jogos sem control.* declarações não têm controles API/UI (404 "This game declares no controls."). As declarações são relidas a partir de cada build publicado — cada implantação, upload de pasta e substituindo o push do pacote. Passo a passo: Tutorial: adicione controles ao seu jogo.

Os jogadores podem substituir esses padrões por jogo através do API de controles de jogos.

Registrar um jogo

POST /api/v1/me/github-games

{
  "repoUrl": "https://github.com/HypeDriven/starhermit-chess",
  "displayName": "StarHermit Chess",
  "launchPath": "index.html"
}

Apesar do nome histórico, repoUrl aceita três fontes de lançamento:

  1. A github.com/<owner>/<repo> repositório. O backend lê seu manifesto e pode implantá-lo para hospedagem StarHermit.
  2. Um URL de páginas do GitHub já hospedado, como https://owner.github.io/game/. Repositório a identidade é inferida do URL; o próprio URL é iniciado, sem clonagem ou instalação.
  3. Qualquer outro público http:// ou https:// URL do jogo web hospedado. É lançado diretamente e não participa da reivindicação de propriedade do GitHub.
  • displayName e launchPath são substitutos opcionais. Eles são úteis para um repositório de terceiros sem metadados de manifesto confiáveis; um URL hospedado direto é o próprio local de lançamento.
  • Para proprietários de repositórios verificados, a plataforma valida starhermit.txt.
  • Um opcional server= roteiro ou container.image= backend fornece um jogo oficial; ver game-scripts.md e container-games.md. A hospedagem em contêiner está aberta a qualquer usuário conectado em starhermit.com; uma implantação auto-hospedada pode restringi-la a uma lista de permissões do operador.
  • Um back-end de servidor declarado precisa de um proprietário comprovado. Enviando um repositório que declara server= ou container.image= sem login do GitHub ou owner= a prova é 403 (nomeando ambas as provas), não uma listagem apenas para navegador que finge ter um back-end.
  • Limites: 100 jogos por usuário (substituíveis pelo operador por conta). Registrando devoluções duplicadas 409.

Os status de registro/implantação incluem: InvalidUrl, LimitReached, Duplicate, MissingManualMetadata, MissingStarhermitTxt, InvalidLaunchPath, InvalidServerScriptPath, InvalidContainerImage, ServerProvisionConflict, RemovedByOwner.

Os erros usam o formato padrão:

{ "error": "..." }

Adicione um jogo de uma pasta local

POST /api/v1/me/github-games/upload → 201

A contrapartida do registro de uma URL: não há repositório, e nada é clonado. A pasta viaja como um .tar.gz no corpo da solicitação e a plataforma hospeda o que ela contém. Mesmo arquivo formatar como empurrando um pacote, então a mesma embalagem funciona para ambos.

O jogo criado possui um gameSlug desde o início, declarando ou não um servidor, então um upload somente para navegador pode usar controles, configurações por jogador, isso é slot para salvar na nuvem, salas em tempo real e lançar tokens como qualquer outro jogo.

client/           the game's files, published as-is
starhermit.txt    name= and launch= instead of the query parameters

O manifesto é opcional para este ponto final — os parâmetros de consulta podem fornecer os mesmos valores — e os clientes StarHermit sempre enviam um, criado a partir de seus campos de manifesto. Enviando o arquivo para dentro ainda vale a pena fazer sua construção: ela torna a construção autodescritiva e preenche previamente esses campos, então pode ser reenviado sem lembrar quais valores são necessários. Ver O starhermit.txt manifesto para o formato e observe que tudo adjacente ao manifesto é carregado — carregue uma compilação distribuível, não uma árvore de origem.

Envie os bytes diretamente - não os dados do formulário multiparte - com Content-Type: application/gzip:

tar -czf game.tar.gz client/ starhermit.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/upload?displayName=My%20Game" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @game.tar.gz

{
  "game": { "id": "...", "displayName": "My Game", "launchPath": "index.html", "hosting": { "hostingEnabled": true } },
  "bytesReceived": 4194304
}

Os metadados são resolvidos nesta ordem, portanto a maioria das pastas não precisa de nenhum parâmetro de consulta:

  1. ?displayName= / ?launchPath= no pedido.
  2. name= / launch= em um starhermit.txt na raiz do arquivo.
  3. index.html na raiz de client/ - usado como caminho de lançamento quando nada mais nomeia um.

Notas específicas para esta rota:

  • O jogo estará ao vivo assim que a ligação retornar. Não há hospedagem ou implantação separada passo: deployStatus é live e deployedCommitSha é null, porque não há commit.
  • Os arquivos não podem ser regenerados, para que a plataforma nunca os reimplante de qualquer lugar. Um jogo adicionado desta forma carrega contentSource: upload e mantém a versão enviada até você publicar outro. Promova uma nova construção com o ponto final do pacote ou carregue a pasta novamente.
  • Nenhum repositório significa nenhuma reivindicação. ownerLogin está vazio, então nenhum login do GitHub poderá corresponder a ele; repoUrl carrega um sintético upload:<random> valor em vez de um URL – um novo token opaco, não o ID do jogo, portanto, não analise o ID do jogo.
  • A server/image.tar é recusado aqui (422). Uma imagem de servidor precisa de um jogo provisionado para anexar, que não existe até que o jogo exista - crie o jogo primeiro e depois envie a imagem para /{id}/bundle.
  • Um caminho de inicialização que nomeia um arquivo que o arquivo não contém é recusado (422) enquanto o upload é ainda em preparação, em vez de se tornar um 404 para cada jogador.

Os limites são iguais a qualquer outro push: consulte Limites de upload.

Uma pasta carregada pode trazer seu próprio back-end de servidor

Se o arquivo starhermit.txt declara a lógica do servidor, o upload provisiona-o também — a mesma coisa que o fluxo do repositório faz, sem um repositório. Escolha um estilo; declarar ambos é recusado.

Declaração O que acontece
server=path/to/server.js Um back-end de script. O arquivo viaja dentro da pasta que você carregou, então sua fonte é lida diretamente do arquivo — não há nada para buscar. Ver game-scripts.md.
container.image=name@sha256:… Um back-end de contêiner, fixado por resumo como sempre. Ver container-games.md. A imagem em si é empurrada posteriormente para /{id}/bundle.

As recusas aqui falham em toda a criação - nenhuma linha de jogo incompleta sobrevive a uma:

  • server= nomear um arquivo que o arquivo não contém.
  • server= apontando para fora dos arquivos do cliente (../).
  • Declarando ambos server= e container.image=.
  • Solicitar um contêiner onde os contêineres estão desativados ou de um proprietário não aprovado para eles.

Arte da capa

A imagem mostrada no bloco do seu jogo na biblioteca. Defina de qualquer maneira - qualquer que seja o seu uso, o anônimo GET /api/v1/github-games/{id}/cover é o que serve:

  • Na sua construção — a cover= linha em starhermit.txt, nomeando uma imagem relativa ao lançamento arquivo ou um absoluto https:// URL. Releia a cada implantação, para que seu repositório continue sendo a fonte da verdade.
  • Enviado — PUT /api/v1/me/github-games/{id}/cover com a imagem codificada em base64. Isto é o que é o painel da web Gerenciar → Capa faz e o que um operador StarHermit pode fazer por você.
PUT /api/v1/me/github-games/{id}/cover
Authorization: Bearer <token>
Content-Type: application/json

{ "imageBase64": "iVBORw0KGgoAAAANSUhEUg..." }

Um upload substituições o manifesto, deliberadamente: um desdobramento que relê starhermit.txt deve nunca desfaça a arte que alguém escolheu manualmente. DELETE /api/v1/me/github-games/{id}/cover é o caminho de volta - descarta o upload e o manifesto cover= aplica-se novamente.

PNG, JPEG, GIF, WEBP, BMP ou SVG, até 4MB. O tipo é detectado a partir dos bytes, então um Content-Type você afirma que não é necessário nem acreditado, e bytes que não são uma imagem decodificável são recusados com 400. Um parente cover= caminho deve terminar em .png, .jpg/.jpeg, .gif, .webp ou .svg (não .., sem liderança /); um valor inutilizável é descartado em vez de falhar no jogo.

A arte da capa é uma arte de pôster: ambas as bibliotecas dimensione-o para preencher o bloco e corte central o que quer que faça não cabe. Os ladrilhos não têm o mesmo formato.

Superfície Telha Cortar
Cliente Windows Retrato 96×128 (3:4) Preenche o retrato; arte mais ampla perde os lados
Painel da web Quadrado Preenche o quadrado; arte mais alta perde a parte superior e inferior

Mantenha o assunto no centro para que ambos os cortes pareçam corretos. Capas SVG são exibidas na biblioteca da web; o O cliente Windows não pode decodificar SVG, então esse bloco mostra o favicon. Um jogo sem cobertura em tudo volta ao seu favicon (GET /api/v1/github-games/{id}/icon). O ícone é resolvido a partir do URL que você enviou e, quando a plataforma hospeda o jogo, a partir da cópia em que ele veicula <uid>.starhermit.com - então, um pacote carregado com um favicon em seus arquivos ainda recebe um ícone.

Números de audiência para o seu jogo

GET /api/v1/me/github-games/{id}/stats → GameStatsDto

Quantas pessoas jogam um jogo você adicionou. Restrito ao dono do jogo — qualquer outra pessoa recebe 404, a mesma resposta de um jogo que não existe.

{
  "totalPlayers": 42,
  "playingNow": 3,
  "totalSessions": 130,
  "totalPlaytimeMinutes": 8140,
  "lastPlayedAt": "2026-07-29T08:45:24Z",
  "livenessWindowHours": 4
}
  • Apenas agregado. Você aprende o tamanho do seu público, nunca quem está nele.
  • totalPlayers conta pessoas distintas, não sessões - alguém que jogou seis vezes é um jogador.
  • playingNow conta jogadores distintos cuja sessão não terminou e começou dentro livenessWindowHours. A janela importa: um cliente que travou ou perdeu sua rede nunca envia a sessão termina e, sem ela, essas linhas seriam lidas como pessoas ainda jogando indefinidamente.
  • totalPlaytimeMinutes conta apenas sessões concluídas, correspondendo aos números de tempo de reprodução por usuário em activity.md. Uma sessão em voo ainda não contribui em nada.
  • lastPlayedAt é null por um jogo que ninguém jogou.

Os números vêm do mesmo registro de lançamento que cada cliente escreve (consulte activity.md), então um o jogo cujos jogadores nunca relatam lançamentos será lido como zero.

Reivindicar propriedade

POST /api/v1/me/github-games/{id}/claim → GitHubGameDto

Assuma o controle de uma listagem existente ao controlar seu repositório. Prove a propriedade vinculando o login pessoal do GitHub correspondente ao proprietário do repositório ou confirmando owner=<your StarHermit user ID> para o repositório starhermit.txt. owner deveria ser o UUID imutável retornado como id por GET /api/v1/me, não um nome de usuário ou apelido. O manifesto O método oferece suporte a repositórios de propriedade da organização, que não são inferidos da organização pessoal do GitHub adesão.

Em caso de sucesso, a listagem existente mantém seu ID/histórico, passa a ser gerenciada pelo reclamante, atualiza metadados controlados por repositório e declarações de back-end e hospedagem de filas, quando disponível. O o remetente anterior perde o acesso de gerenciamento no escopo do proprietário. Reivindicar uma listagem que você já gerencia ressincroniza-o em vez de retornar um conflito.

Armazenamentos de metadados de identidade do GitHub {"login":"…"}; vincule sua conta GitHub por meio do fluxo OAuth (consulte auth.md). Verifique o status do link com GET /api/v1/me/github → { linked, login }. Veja o tutorial de reivindicação passo a passo para descoberta, tanto prova métodos, validação, controle e solução de problemas.

Transferir propriedade

Uma transferência é um oferta pendente que o destinatário aceita, não um movimento imediato - um jogo (e seus bytes hospedados, que contam para o destinatário) não podem ser enviados para outra conta sem seu diga-se.

POST /api/v1/me/github-games/{id}/transfer (proprietário) registra a oferta e devolve um GameTransferOfferDto; o jogo permanece seu até que seja aceito.

{ "toUserId": "<user id>" }

// GameTransferOfferDto
{
  "id": "<offer id>",
  "gameId": "<game id>",
  "gameTitle": "StarHermit Chess",
  "fromUserId": "<guid>", "fromUsername": "alice",
  "toUserId": "<guid>",   "toUsername": "bob",
  "status": "pending",
  "createdAt": "2026-10-17T16:00:00Z"
}
  • O destinatário o vê em GET /transfers/incoming e aceita com POST /transfers/{offerId}/accept. Aceitação move o jogo agora, verificado naquele momento contra a contagem de jogos e o subsídio de hospedagem do próprio destinatário - para que uma oferta possa ser feita e ainda assim não conseguir pousar se o destinatário estiver no seu limite. Eles podem em vez disso POST /transfers/{offerId}/decline.
  • O ofertante vê suas ofertas pendentes em GET /transfers/outgoing e pode retirar um com POST /transfers/{offerId}/cancel.
  • Tudo é verificado novamente ao aceitar: um jogo movido, removido ou apontado novamente desde que a oferta foi respondida GameUnavailable, e oferecer o mesmo jogo novamente substitui uma oferta ainda pendente, então dois ao vivo ofertas de um jogo não podem ser aceitas.

Empurre um pacote de jogos

POST /api/v1/me/github-games/{id}/bundle publica a saída construída sem pedir ao StarHermit para cloná-lo novamente. O chamador deve possuir o jogo registrado. Envie o .tar.gz bytes diretamente - não dados de formulário multiparte - com Content-Type: application/gzip:

client/            optional static client files; must include the registered launch file
server/image.tar   optional output from `docker save`
starhermit.txt     optional manifest copy for bundle portability
remove.txt         merge only: client-relative paths to delete, one per line

Pelo menos client/ ou server/image.tar deve estar presente (uma mesclagem também pode ser apenas remove.txt). Os arquivos do cliente são trocados atomicamente. Um a imagem do servidor é carregada, fixada pela plataforma e enfileira a implantação do contêiner para reinicie nessa imagem. Uma imagem carregada tem precedência sobre a referência de registro do manifesto, e mais de um server= linha; um manifesto declarando ambos server= e container.image= é recusado antes de qualquer coisa ser carregada. Qualquer outra coisa no arquivo será ignorada.

O upload de uma imagem é em si a declaração. Se o jogo ainda não tiver back-end de servidor — um pasta carregada que não declarou nenhum - empurrando server/image.tar provisões um do resumo apenas carregado, sob o gameSlug o jogo já tem. Você não precisa nomear uma imagem fixada com resumo em um manifesto primeiro, que era circular: a definição tinha que existir antes que pudesse receber uma imagem, e a imagem era a única coisa que poderia descrevê-lo.

Um re-push aplica os botões de contêiner declarados pelo seu manifesto, e somente esses. Incluir starhermit.txt no pacote com um alterado container.port, container.health, container.memory_mb ou container.cpu e a implantação o pega na reinicialização; deixe um botão de fora e ele mantém tudo o que você definiu da última vez. Omita totalmente o manifesto e nada sobre a implantação alterações, exceto a imagem.

Um pacote cujo starhermit.txt carrega um utilizável name= também renomeia a listagem do jogo para isso - a atualização do nome de exibição acompanha o push. Deixar name= sair (ou omitir o manifesto) para manter o nome atual.

Os clientes StarHermit criam este pacote para você, a partir de uma pasta ou um único .tar:

  • Arquivos de cliente — a pasta de distribuição do jogo ou um .tar disso. Uma pasta está compactada em client/; a .taras entradas são realojadas lá (um arquivo já em client/ resta sozinho). apenas ustar - arquivos GNU de nome longo e PAX são recusados, porque realocá-los significa reescrevendo os blocos de metadados que nomeiam a entrada a seguir.
  • Servidor dedicado — a pasta de distribuição do servidor ou o docker save .tar por conta própria. De uma pasta apenas o manifesto e image.tar são carregados: a imagem já contém seu próprios arquivos do servidor, portanto, empacotar o restante enviaria gigabytes para a plataforma descartar.

Em ambos os casos o starhermit.txt é editável na caixa de diálogo. Seja qual for o O build escolhido carrega preenche previamente os campos, e tudo o que eles contêm é escrito na raiz do pacote - então uma compilação sem manifesto é publicável e aquela que é enviada como um .tar ainda pode ter seu manifesto atualizado.

mv image.tar bundle/server/image.tar
cp starhermit.txt bundle/

Atualizações parciais: ?mode=merge

Um empurrão é um substituir a menos que você pergunte o contrário: o arquivo é o jogo inteiro, e qualquer coisa que não esteja acabou. ?mode=merge (HTTP e o soquete de upload) o torna um correção do cliente ao vivo arquivos – a resposta para recarregar gigabytes de ativos inalterados para uma correção de um arquivo.

printf '%s\n' '# one client-relative path per line; a directory removes everything under it' \
    'assets/old-music.ogg' 'levels/cut/' > remove.txt
tar czf patch.tar.gz client/index.html client/js/app.js remove.txt

curl -X POST "https://api.starhermit.com/api/v1/me/github-games/$GAME_ID/bundle?mode=merge" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @patch.tar.gz

Com mode=merge:

  • arquivos em client/ são adicionados ou substituídos
  • caminhos em uma raiz remove.txt (# comentários; um diretório remove toda a sua subárvore) são excluídos
  • todos os outros arquivos ativos permanecem exatamente como estão

A árvore mesclada é preparada como uma cópia e trocada atomicamente — os jogadores veem o jogo antigo ou o totalmente novo, nunca uma mistura. O resultado é limitado pela jogo subsídio, não o upload, então um jogo não pode ultrapassar seu limite, um pequeno patch de cada vez. Uma mesclagem trata apenas de arquivos do cliente; um server/image.tar é carregado exatamente como em uma substituição. Um patch sem starhermit.txt folhas arte da capa como era.

Uma mesclagem é recusada (409/422, nada muda) quando o jogo ainda não tem nada publicado, quando removeria o arquivo de inicialização ou quando remove.txt pontos fora do jogo. UM remove.txt em um substituição simples também é recusada (422), porque ali só poderia significar algo que você não pretendo. mode deve ser replace (padrão) ou merge; qualquer outra coisa é 400.

O mesmo parâmetro funciona no soquete: ws/v1/game-upload?gameId=…&mode=merge. O ready quadro ecoa isso como "apply":"merge".

O endpoint atualiza um jogo registrado existente; ele nunca cria o registro do jogo — para isso, veja adicionando um jogo de uma pasta local. Isto pode provisionar o jogo back-end do servidor, como efeito colateral de carregar uma imagem do servidor em um jogo que não tinha nenhuma. Veja o tutorial de publicação de servidor dedicado.

Carregar de CI/CD

Não mantenha um token OAuth interativo em segredo de um repositório. Faça login através do OAuth uma vez e use nessa sessão para adicionar uma chave de implantação rotulada separadamente com POST /api/v1/me/public-keys. O CI o trabalho pode então assinar /auth/public-key/challenge, troque-o em /auth/public-key/completee usar o token de acesso de 15 minutos retornado neste endpoint do pacote.

A chave de implantação atua como sua conta proprietária, portanto essa conta deve possuir o jogo alvo. Não pode adicione outra chave ou revogue outras chaves. Pode revogar-se através /me/public-keys/current; gerenciar inscrições e outras chaves de uma sessão autenticada por OAuth. Use uma chave por ambiente para que um fluxo de trabalho possa ser desativado sem interromper os outros. Arquivos aproximadamente 100 MB devem usar o transporte WebSocket abaixo.

Ver Fazer upload de builds de CI/CD com uma chave pública registrada em OAuth para geração de chaves, configuração secreta do GitHub, um script completo de assinatura/uploader de desafio, estático e layouts de pacotes de contêineres e um fluxo de trabalho do GitHub Actions.

Fazer upload por meio de um WebSocket

GET /ws/v1/game-upload (atualizar) - use isso para qualquer coisa acima de 100 MB.

O CDN na frente da API recusa um corpo de solicitação HTTP aproximadamente 100 MB com um 413 do seu próprio. Essa recusa nunca chega à plataforma, por isso não acarreta limitBytes e aparece em nenhum log você sabe ler - um 413 sem limitBytes campo é o CDN, não a permissão do seu jogo, que é dois ordens de grandeza maiores. Qualquer realista docker save vai acertar.

Os quadros enviados após a atualização do WebSocket não são um corpo de solicitação, portanto, o limite máximo não se aplica. Apenas o transporte difere. Os quadros binários concatenam exatamente nos bytes que as rotas HTTP leia, passe pelo mesmo pipeline, e cada corpo de recusa, permissão e sucesso é aquele que o HTTP rota teria produzido - para que um cliente possa compartilhar um caminho de código entre ambos.

wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?gameId=$GAME_ID&mode=merge&access_token=$TOKEN
wss://api.starhermit.com/ws/v1/game-upload?displayName=My%20Game&launchPath=index.html&access_token=$TOKEN

Passar gameId para enviar para um jogo que você possui (o /{id}/bundle rota); omita e passe displayName/launchPath para criar um a partir de uma pasta (o /upload rota). O token vai para o string de consulta porque um navegador não pode definir um Authorization cabeçalho em um handshake WebSocket; é verificado uma vez, no handshake, para que um upload que sobreviva ao seu token de acesso ainda seja concluído.

Direção Quadro Significado
servidor → {"type":"ready","mode":"bundle","apply":"replace","limitBytes":N,"heartbeatSeconds":15} Subsídio liquidado e espaço livre verificado. Comece a enviar. mode é bundle ou create. apply é merge quando você solicitou uma atualização parcial.
→ servidor binário Arquive bytes, divididos como desejar — o servidor nunca remonta mensagens, portanto, 256 KB – 1 MB é um bom padrão. Concatenados, seus frames devem ser exatamente os .tar.gz.
servidor → {"type":"ack","bytesReceived":N} Progresso do recebimento, aproximadamente a cada 8 MB. Impulsione sua barra de progresso a partir disso.
→ servidor {"type":"complete"} O arquivo foi enviado na íntegra.
→ servidor {"type":"abort"} Desistir. Respondido com status: 499; nada é publicado.
servidor → {"type":"progress","phase":"publishing","bytesReceived":N} Batimento cardíaco a cada 15 segundos enquanto o upload chega. Ignore-os, mas espere por eles.
servidor → {"type":"result","status":200,...} Sucesso. O resto do objeto é o corpo da resposta HTTP literalmente (status é 201 para uma criação).
servidor → {"type":"error","status":413,"error":"...","limitBytes":N} Recusa. status e o corpo são o que a rota HTTP teria respondido.

Nada é publicado até {"type":"complete"} chega. Este é o único comportamento sem HTTP equivalente, e é deliberado: o marcador de fim de arquivo permanece dentro bytes de um tar, então o plataforma termina de ler um arquivo de aparência completa sem que a conexão termine. Uma tomada que simplesmente caiu após o último byte seria publicado exatamente como aquele que terminou - substituindo silenciosamente um jogo ao vivo por um push abandonado. Fechando o soquete sem o upload do quadro nada.

A publicação após o último byte pode levar algum tempo, especialmente para uma imagem de servidor. Esperar progress batimentos cardíacos enquanto termina; não trate um intervalo silencioso como uma falha no upload.

Limites de upload

Todas as rotas de upload — tanto os endpoints HTTP quanto o WebSocket — compartilham as mesmas regras.

Limite Valor
Subsídio de disco por jogo 2GB em starhermit.com (o subsídio pode variar de acordo com o jogo/implantação)
Arquivos hospedados por conta 20GB em todos os jogos de uma conta (ajustável pelo operador por conta)
Implantação de repositório 50MB arquivo
starhermit.txt / remove.txt 256 KB cada; remove.txt lista no máximo 10.000 caminhos (422)
Aplicação aplicado durante a transmissão, então um impulso superdimensionado é interrompido no meio do vôo

Um upload ou push é cortado no valor restante da franquia de hospedagem da conta (413 com limitBytes), e uma implantação de repositório que passaria falha com um motivo nomeando a permissão. Por push e por jogo têm o mesmo número em uma substituição. Uma mesclagem é limitada pelo resultante tamanho do jogo, então um pequeno patch que faria a árvore viva exceder o permitido é recusado.

Status Significado
400 mode não é nenhum dos dois replace nem merge.
409 Uma fusão com um jogo que ainda não possui arquivos publicados.
413 Acima do subsídio. Corpo carrega { "error", "limitBytes" }. A 413 sem limitBytes é o limite de corpo de aproximadamente 100 MB do CDN, não este - use o soquete de upload.
422 Arquivo malformado ou conteúdo inutilizável (arquivo de inicialização ausente, não client/, a server/image.tar na rota de criação, uma mesclagem que excluiria o arquivo de inicialização, remove.txt em uma substituição). Também um truncado archive — o resultado comum de uma queda de conexão no meio do upload.
507 O servidor não tem espaço no momento. Recusado antes do corpo ser lido quando a capacidade de publicação não estiver disponível; tente novamente mais tarde.

Os arquivos não podem escapar de sua raiz ou conter links, e apenas arquivos e diretórios regulares são extraído — links simbólicos, links físicos e nós de dispositivos são rejeitados. git archive Cabeçalhos globais PAX, ./-nomes prefixados de tar -czf game.tgz .e nomes de arquivos que contêm apenas .. (sprite..png) são aceitos. UM .. segmento de caminho ainda é recusado.

Limite de taxa

Enviar, reivindicar, alterar URL, hospedagem e implantação chegam ao GitHub no único token da plataforma, então juntos, eles são limitados a 10 solicitações por minuto por conta (429, com Retry-After). Um o operador pode aumentá-lo para uma conta.

Habilitar hospedagem

PUT /api/v1/me/github-games/{id}/hosting → GameHostingView ("Implantar para Starhermit")

{ "enabled": true }

Fixar uma implantação

PUT /api/v1/me/github-games/{id}/deployment → GameHostingView

{ "commit": "<sha or branch>" }

commit é opcional. Fixar um sha/branch enfileira uma reimplantação; enquete GET /api/v1/me/github-games/{id}/deployment para status.

Isso é recusado para um jogo que não nomeia nenhum repositório (um pacote carregado): fixar um commit é o que move um jogo para seu repositório, e um jogo criado em pacote não possui nenhum. Reimplantando um jogo carregado verifica os arquivos que ainda estão no volume em vez de buscar github.com.

Mova um jogo para um novo URL

PUT /api/v1/me/github-games/{id}/url

{ "repoUrl": "https://github.com/you/new-repo", "displayName": "optional for a hosted URL" }

A linha sobrevive - uid, <uid>.starhermit.com, tempo de reprodução, classificações — e é reimplantado a partir do destino. Um destino do github deve ser aquele que o chamador possa provar que controla (403 caso contrário), e seu starhermit.txt não deve nomear um diferente owner= (403). Um script ou contêiner backend está desabilitado, a menos que o destino declare um.

Sessões ao vivo (proprietário)

GET /api/v1/me/github-games/{id}/sessions lista as sessões ativas do servidor do jogo. DELETE .../sessions/{sessionId} termina através do caminho de abandono da plataforma (sem vencedor, sem elo, razão operator_ended). Isso retorna a capacidade ocupada por uma sessão travada.

Placares e conquistas (proprietário)

O proprietário de um jogo é o seu editor: você pode criar tabelas de classificação e conquistas por isso sob /me/github-games/{id}/leaderboards e /achievements sem uma conta de editor. Somente o servidor do seu jogo escreve para eles, então o jogo precisa de um server= roteiro ou container.image= back-end – um jogo somente para navegador obtém 409. As duas fontes não são iguais: um upload sempre vence e é o único DELETE /cover pode remover.

A reimplantação de notas idênticas não a move, por isso é seguro dirigir um "O que há de novo" emblema: lembre-se do valor que um jogador viu pela última vez e compare. Publique seu próprio jogo: passo a passo

Existem duas rotas. Se o seu jogo reside em um repositório git, siga as etapas numeradas abaixo. Se for apenas uma pasta na sua máquina, uma chamada faz tudo: adicione um jogo de uma pasta local registra o jogo, publica o arquivos e deixa-o ativo - sem alternância de hospedagem e sem pin de commit, porque não há repositório para pista.

  1. Escolha uma fonte: envie um repositório contendo starhermit.txt na raiz (opcionalmente declarando um server.js script ou imagem de contêiner) ou prepare o URL público de um jogo de navegador já hospedado.
  2. Vincule sua identidade GitHub por meio do fluxo OAuth (consulte auth.md); verifique com GET /api/v1/me/github.
  3. Registre o jogo: POST /api/v1/me/github-games com o repositório ou URL do jogo hospedado em repoUrl.
  4. Somente jogos de repositório – habilite hospedagem: PUT /api/v1/me/github-games/{id}/hosting com { "enabled": true }.
  5. Somente jogos de repositório — fixe um commit: PUT /api/v1/me/github-games/{id}/deployment com { "commit": "<sha>" }. O commit fixado controla a versão ao vivo.
  6. Os jogadores iniciam o jogo: um jogo de repositório implantado é servido em <slug>.starhermit.com; um jogo hospedado diretamente abre o URL enviado. Cada jogo com um gameSlug — backend ou não — recebe um token de lançamento de POST /api/v1/games/<slug>/launch-token no fragmento de URL (opcionalmente com &session_id=<guid> para links diretos de convite).

Para o contrato completo do lado do cliente — como o jogo lê o token de lançamento e se comunica com a API — consulte o passo a passo de xadrez da implementação de referência.
