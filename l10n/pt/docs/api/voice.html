Voz

A voz StarHermit fornece salas de voz por conversa em uma API REST (api/v1/voice) mais um WebSocket misto binário/texto (ws/v1/voice) para sinalização de áudio e WebRTC. Todos os endpoints REST requerem autenticação. A disponibilidade de voz pode variar. Os corpos de erro variam; ver Convenções de API.

Os quartos se ancoram em um conversa de bate-papo; a participação na conversa controla tudo, portanto, as regras de amizade no bate-papo também regem a voz (as conversas nas sessões de jogo ignoram a amizade). Limites: 3 salas ativas por conversa, máximo 10 participantes por sala, codec "opus".

Pontos de extremidade REST

Base: https://api.starhermit.com/api/v1/voice.

Método Caminho Autenticação Descrição
PUBLICAR /rooms JWT Crie uma sala de voz para uma conversa
PEGAR /rooms?conversationId= JWT Listar salas para uma conversa
PEGAR /rooms/{roomId} JWT Pegue um quarto
PUBLICAR /rooms/{roomId}/join JWT Entre em uma sala (obrigatório antes do WS)
PUBLICAR /rooms/{roomId}/leave JWT Saia de um quarto
PUBLICAR /rooms/{roomId}/mute JWT Defina seu próprio estado mudo
PUBLICAR /rooms/{roomId}/participants/{userId}/server-mute JWT (criador) Host silencia o participante não consegue levantar
PUBLICAR /rooms/{roomId}/close JWT Fechar uma sala (somente criador)

Crie uma sala

POST /rooms

{ "conversationId": "<guid>", "maxParticipants": 10 }

Retorna um VoiceRoomDto.

Formato da sala

GET /rooms?conversationId=<guid> → VoiceRoomDto[]; GET /rooms/{roomId} → VoiceRoomDto:

{
  "id": "<guid>",
  "conversationId": "<guid>",
  "creatorUserId": "<guid>",
  "codec": "opus",
  "status": "Active",
  "maxParticipants": 10,
  "createdAt": "2026-07-22T07:00:00Z",
  "participants": [
    {
      "userId": "<guid>",
      "username": "alice",
      "isMuted": false,
      "isConnected": true,
      "joinedAt": "2026-07-22T07:01:00Z"
    }
  ]
}

Entrar, sair, silenciar, fechar

POST /rooms/{roomId}/join → VoiceRoomDto. Esta junção REST é obrigatório antes de abrir o WebSocket; conectando sem que ele retorne 403. A reingresso limpa a conta do participante ter mudo (isMuted); um anfitrião isServerMuted sobrevive, sai e se reconecta.

POST /rooms/{roomId}/leave → 204.

POST /rooms/{roomId}/mute com { "muted": true } → 204. Este é o mudo do próprio participante e não pode limpar o mudo do host.

POST /rooms/{roomId}/participants/{userId}/server-mute com { "muted": true } → 204 (somente criador). O áudio será interrompido se o modo mudo estiver definido.

POST /rooms/{roomId}/close → 204 (somente criador).

Indique seu mudo ao conectar, em vez de herdar tudo o que a linha lembra.

WebSocket: ws/v1/voice

Conecte-se a wss://api.starhermit.com/ws/v1/voice?roomId=<guid> com um JWT por meio do Authorization cabeçalho, ?ticket=, ou ?access_token=. Um REST anterior join é necessário.

O protocolo é misto:

Quadros binários — áudio

Os quadros binários transportam áudio (por exemplo, Opus). O servidor retransmite cada quadro para os outros participantes como:

[16-byte senderUserId][audio…]

O servidor prefixa o autenticado ID do remetente e nunca confia em um remetente fornecido pelo cliente. O áudio de usuários silenciados é descartado. Limites: 100 pacotes/segundo por usuário, quadro máximo de 4.000 bytes.

Quadros de texto — cliente → controle do servidor

{ "type": "mute", "muted": true }

{ "type": "speaking", "speaking": true }

{ "type": "rtc", "to": "<guid>", "payload": { } }

{ "type": "deafen", "deafened": true }

rtc cargas úteis são sinalização WebRTC opaca, encaminhadas ao participante endereçado. deafen suprime o áudio binário retransmitido de entrada para este soquete; não silencia automaticamente áudio de saída ou uma conexão peer separada. Aplique-os localmente quando o jogador escolher Deafen.

A forma do participante REST expõe o próprio mudo, não o mudo do host. A lista inicial de vozes e eventos de participação incluir serverMuted; não há nenhum evento push separado de host-mute-changed. Se o seu jogo usa P2P áudio, sua sinalização e imposição de host-mute devem fazer parte de sua própria integração de mídia.

Quando o último soquete de voz for desconectado, a associação à sala de voz terminará. Chame REST join novamente antes reconectar e restaurar o mudo pretendido antes de enviar o áudio.

Servidor → eventos do cliente

Envelope: { "event": "<name>", "data": { } }.

Evento data
voice.roster { "roomId", "participants": [{ "userId", "muted", "serverMuted" }] } - enviado para o recém-chegado
voice.participant_joined { "roomId", "userId", "muted", "serverMuted" }
voice.participant_left { "roomId", "userId" }
voice.mute_changed { "roomId", "userId", "muted" }
voice.deafened `{ "ID da sala", "ID do usuário", "ensurdecido" }
voice.speaking { "roomId", "userId", "speaking" }
voice.rtc { "roomId", "from", "payload" }

Exemplo de padrão de integração (da implementação de referência de xadrez)

A voz é ativada por sessão de jogo. Um cliente típico enable() fluxo:

  1. GET /api/v1/voice/rooms?conversationId=<chatConversationId> para encontrar uma sala existente, caso contrário POST /api/v1/voice/rooms para criar um.
  2. POST /api/v1/voice/rooms/{roomId}/join.
  3. Abrir ws/v1/voice?roomId=<guid>.

No implementação de referência de xadrez, o áudio é executado em WebRTC P2P com negociação perfeita; a sinalização é trocada através do rtc mensagens de controle ({ "sdp": … } / { "ice": … } cargas úteis), com o caminho binário Opus retransmitido pelo servidor como substituto.

Tokens de lançamento no escopo do jogo poderia use a voz REST e WebSocket para salas anexadas às suas próprias sessões de jogo.
