Salas em tempo real

As salas em tempo real são lobbies generalizados para jogos multijogador em ritmo acelerado: criação de salas, convites de amigos, combinação rápida de partidas, jogadores de IA sob demanda, preenchimento de assentos de IA e transporte em tempo real com reconhecimento de função (ws/v1/realtime). O subsistema é deliberadamente agnóstico em termos de jogo - as salas têm escopo definido por slug de jogo, a sala metadata é um blob JSON opaco por jogo e teamCount = 1 modelos de jogos grátis para todos.

Uma partida ocorre de duas maneiras:

  • Roteado por host (padrão) — o servidor da plataforma é um transporte inteligente, não um simulador: o cliente do criador da sala é o hospedar e executa a simulação oficial do jogo; outros clientes (convidados) enviam entradas para o host e recebem os instantâneos do host. O servidor impõe roteamento, funções, capacidade, limites de taxa e identidade – os clientes não podem falsificar uns aos outros e apenas o host atribuído ao servidor pode transmitir.
  • Sessão vinculada à sala (autorizada pelo servidor) — para jogos que enviam um server= roteiro ou um recipiente: quando a sala começa, a plataforma cria uma sessão vinculada de N jogadores (com script ou contêiner) que executa a simulação no lado do servidor. A jogabilidade então flui ws/v1/games e o WS em tempo real é usado apenas para lobby/roster. Ver a ponte abaixo.

Compare isso com o retransmissão de pares (fan-out opaco vinculado a uma lista de sala/sessão existente, desativado por padrão) e simples jogos com script (autorizado pelo servidor, com matchmaking de sessão e convites, mas sem lobby de sala). As salas em tempo real são ativado por padrão.

Todos os endpoints REST exigem autenticação e funcionam com um token de usuário completo e um token de inicialização no escopo do jogo. Os corpos de erro variam; ver Convenções de API.

Modelo de dados

Sala vida útil: Lobby → Open (casamento) → Playing (lista congelada, assentos vazios preenchidos com IA até o limite da sala) → Closed. Uma sala criada com joinInProgress continua pegando jogadores enquanto Playing.

  • config.metadata é um blob JSON opaco que a plataforma nunca interpreta. Ele, e um enviado metadados do resultado, pode ter no máximo 16 KB (413), e uma sala tem no máximo 100 lugares; um operador pode mude para um jogo.
  • config.aiPlayers é quantos jogadores de IA o criador pediu para a partida começar - eles estão sentados quando a sala é criada (veja abaixo). Registra a solicitação; o participants a lista é oficial para quem realmente ocupa um assento.
  • Os participantes da IA ​​têm userId: null, isAi: truee um apelido aleatório gerado pelo servidor, exclusivo na sala.
  • (team, slot) é a coordenada do assento do participante; os humanos estão sentados em ordem conjunta.
  • gameSessionId é a sessão de jogo vinculada, definida quando a sala começa para um jogo com back-end de servidor - um server= roteiro ou um recipiente (ver a ponte); null de outra forma. Também está incluído nos impulsos de escalação.
  • result é o resultado, definido quando a sala fecha - enviado pelo host para jogos roteados pelo host, retornado por script para sessões vinculadas à sala.
  • joinCode tem seis caracteres (pares semelhantes removidos). É o convite para join-by-code. As listagens nunca o incluem.
  • isVisible lista o quarto em GET /rooms. Ser aberto (de adesão rápida) e estar listado são independentes.
  • revision aumenta apenas quando o host edita a configuração (PATCH), nunca quando uma vaga é ocupada. Passe como expectedRevision sobre PATCH para comparar e trocar (409 sobre conflito).

Convidar: { "id", "roomId", "gameSlug", "fromUserId", "fromUsername", "toUserId", "status", "createdAt", "notified" } com status um dos pending | accepted | declined | expired (os convites expiram quando a sala fecha ou iniciam antes de serem atendidos). notified aparece na resposta a POST /rooms/{id}/invites e informa se a notificação do convidado alcançou uma conexão ativa; isso é null ao listar.

Pontos de extremidade REST

Base: https://api.starhermit.com/api/v1/realtime - então POST /rooms abaixo está POST /api/v1/realtime/rooms.

Crie uma sala — POST /rooms

{ "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "teamCount": 2, "seatsPerTeam": 5, "backfillAfterSeconds": 30, "aiPlayers": 0, "backfillAiPlayers": 4, "name": "Friday night", "isVisible": false, "metadata": { "map": "arena" } }
  • gameSlug é necessário para tokens de usuário completos. Com um token de lançamento com escopo de jogo, o slug é retirado do token game_scope (um valor de corpo incompatível é rejeitado com 403).
  • Bonés: teamCount 1–2, seatsPerTeam 1–100, total de vagas ≤ 100 (uma equipe de 100 ou duas de 50). backfillAfterSeconds o padrão é 30 e deve ser pelo menos 1 (400 de outra forma); há sem máximo além do tamanho de um número inteiro de 32 bits. Um longo a contagem regressiva só dura enquanto alguém permanece conectado: um Open quarto sem ninguém ws/v1/realtime fecha após 60 minutos (ver Ciclo de vida automático da sala), portanto, uma contagem regressiva maior que essa só será alcançada se um participante mantiver um soquete aberto. Salas grandes são limitadas pela largura de banda, não pelos assentos: os frames de cada convidado vão para o host e cada frame do host é copiado para cada convidado - consulte Dimensionando uma sala grande.
  • aiPlayers o padrão é 0. Faixa 0–(teamCount × seatsPerTeam) − 1 – o anfitrião sempre precisa de um assento, então uma sala totalmente IA é uma 400.
  • backfillAiPlayers limita quantos assentos ainda vazios quando a partida começa são dados à IA - veja Subsídio de preenchimento. Omitido ou null preenche todos eles.
  • joinInProgress (padrão false) mantém a sala recebendo jogadores após o início — veja Junte-se em andamento.
  • Uma sala ativa por usuário: criar ou ingressar enquanto você estiver em qualquer sala nãoClosed quarto retorna 409.
  • O criador se torna o anfitrião, sentado na equipe 0, slot 0. Retorna a sala.

Jogadores de IA

aiPlayers diz quantos jogadores de IA o a partida deve começar com. Eles não são uma promessa resgatada posteriormente – o servidor os acomoda imediatamente, então a sala que você recebe já os contém:

  • Eles são participantes comuns (isAi: true, userId: null, apelido exclusivo) e aparecem na lista e em todos roster empurre a partir do momento em que a sala existe.
  • Eles ocupar assentos, então eles reduzem a capacidade deixada para os humanos: os convites e a adesão rápida preenchem apenas o que resta, e POST /rooms/invites/{id}/accept retorna 409 uma vez que não haja mais assento livre. Você obtém exatamente o número de IA que pediu – nunca mais com matchmaking.
  • A colocação preenche o time mais vazio primeiro (empates vão para o índice de equipe mais baixo), vaga livre mais baixa. Então um teamCount: 2, seatsPerTeam: 1 quarto com aiPlayers: 1 coloca a IA em frente ao host e salas maiores permanecem equilibradas. Recoloque-os como quiser com POST /rooms/{id}/seats antes da partida começar.
  • Eles são separados do preenchimento do horário de início, que preenche os assentos que ninguém ocupou quando a sala começa - até o limite da sala. subsídio de preenchimento.

Subsídio de preenchimento

Quando uma sala é iniciada — no prazo de preenchimento, assim que ela fica cheia ou no início forçado do host — assentos que ninguém ocupou são dados a jogadores de IA. backfillAiPlayers decide quantos:

backfillAiPlayers No início
omitido / null (padrão) cada assento vazio se torna um jogador de IA
0 sem IA: a partida começa com os assentos vazios deixados vazios
n no máximo n assentos vazios tornam-se IA; qualquer coisa além disso permanece vazia

A IA limitada vai para o time mais vazio primeiro (ligado ao índice de equipe mais baixo), então um 2 × 3 quarto com um anfitrião e backfillAiPlayers: 3 começa 2 contra 2. Faixa 0–teamCount × seatsPerTeam, outro 400. O anfitrião pode alterá-lo antes da partida com PATCH /rooms/{id} ("backfillAiPlayers": 2), ou voltar a preencher todos os lugares com "backfillAllEmptySeats": true. Não afeta aiPlayers, que estão sentados quando a sala é criada.

Se o seu jogo foi feito para ser jogado com falta de preenchimento - um vale-tudo, tudo bem com seis de oito jogadores - usar 0 e deixe seu jogo cuidar dos assentos vazios. Com o padrão, uma sala nunca inicia com um assento vazio.

Jogando sozinho contra o computador são, portanto, duas chamadas - crie a sala com todos os outros assentos como IA e, em seguida, inicie-a:

POST /api/v1/realtime/rooms
{ "gameSlug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94", "teamCount": 2, "seatsPerTeam": 1, "aiPlayers": 1 }

POST /api/v1/realtime/rooms/{id}/start

Os assentos de IA são identidades e reservas de assentos, não um serviço de bot – nada na plataforma os reproduz para você. Um jogo roteado por host os conduz em sua própria simulação; um jogo com um server= script os encontra em ctx.room.roster sinalizado ai: true e os reproduz dentro do script (veja Scripts de jogos).

Convites

POST /rooms/{id}/invites com { "toUserId": "<guid>" }. Os convites são somente amigos (403 de outra forma; a mesma regra de amizade dos convites para jogos), apenas participantes e somente enquanto a sala aceita entradas: em Lobby/Open, ou Playing com joinInProgress. 409 se o usuário já está na sala ou já possui convite pendente; 400 ao se convidar. Retorna o convite.

O convidado é notificado para você. Enviar um convite para sala emite um game_invite empurrar no soquete de bate-papo do convidado e adiciona o convite a GET /api/v1/me/game-invites, então um amigo que está no painel do StarHermit (ou em qualquer lugar que não seja o seu jogo) ainda ficará sabendo disso. Você faz não precisa também enviar um convite para a API de jogos - isso notificaria duas vezes. A resposta notified informa se o push alcançou uma conexão ativa; false significa apenas que o convidado não está conectado no momento e verá o convite em sua caixa de entrada.

Como uma notificação abrange ambos os sistemas de convite, sua carga útil carrega kind: "room" mais roomId e o acceptPath/declinePath para esse convidar. Responda a um convite de sala nos pontos de extremidade em tempo real abaixo — um ID de convite de sala não é válido em /games/{slug}/invites/... e vice-versa.

GET /rooms/invites lista os convites de sala pendentes do chamador em todos os jogos (os tokens de lançamento veem apenas os de seus próprios jogos). Use-o como a caixa de entrada de convites de sala pesquisada por um cliente de jogo. A caixa de entrada de convites unificada em GET /api/v1/me/game-invites retorna estes também.

POST /rooms/invites/{inviteId}/accept acomoda o chamador e retorna à sala. Fixação de festa: os ingressos por convite ficam sentados na equipe do anfitrião enquanto durar o espaço e, em seguida, transbordam para outras equipes. 409 se a sala estiver cheia, já iniciada/fechada ou se o chamador estiver em outra sala ativa (mundos exceto). Aceitar um convite para uma sala em que o chamador já está, basta aceitá-lo.

POST /rooms/invites/{inviteId}/decline → 204.

Organização de partidas

POST /rooms/{id}/open (apenas anfitrião): Lobby → Open, conjuntos openedAte inicia a contagem regressiva de preenchimento. Idempotente enquanto já Open; 409 uma vez Playing/Closed.

Um Open a sala não espera a contagem regressiva uma vez cada assento está ocupado — por humanos ou por jogadores de IA configurados na criação. Tudo começa ali e então, então a resposta a open (ou para o join que ocupou a última vaga) já pode ser um Playing quarto com startedAt definir. Uma sala criada com IA em todos os assentos, exceto no do anfitrião, começa no momento em que é aberta.

GET /rooms?gameSlug= navega pelas salas abertas e listadas do jogo que ainda têm um assento, o mais antigo aberto primeiro, com limite de 50. Cada linha tem nome, nome do host, contagem de jogadores/capacidade, freeSeats, metadados, startedAt e joinInProgress — sem código de adesão e sem lista. Adicionar includeInProgress=true para também listar em execução adesão em andamento salas com assento vago, depois de todas as salas ainda estarem ocupadas.

POST /rooms/join-by-code com { "joinCode": "K7MP2X" } senta-se. Os códigos não diferenciam espaços em branco e maiúsculas de minúsculas. Ao contrário do ingresso rápido, isso funciona em uma sala não listada ainda em Lobby. O código é liberado quando a sala fecha.

PATCH /rooms/{id} (hospedar): { "name", "isVisible", "metadata", "joinInProgress", "backfillAiPlayers", "backfillAllEmptySeats", "expectedRevision" }. Os campos omitidos são deixados de lado; enviar name: "" para limpar o nome. UM Playing a sala ainda pode ser renomeada, listada ou não listada, ter seus metadados substituídos e mudar joinInProgress; configurações de preenchimento são recusadas (409) assim que a partida começar.

POST /rooms/{id}/matchmake (hospedar, Lobby apenas) coloca na fila o quarto humano lista como um festa/equipe; os participantes da IA ​​pré-assentados não são membros do grupo. Com a política padrão, o tamanho do partido deve ser igual à fila selecionada teamSize. Com um prazo de início do manifesto, um partido menor pode ocupar uma equipe maior no prazo; os assentos restantes tornam-se IA até o limite configurado do jogo e fique vazio. As festas ficam juntas e os ingressos não são combinados em uma equipe.

Usar ?queue=duos para uma forma ou repita ?queues= para permitir um subconjunto, como na API Games:

POST /api/v1/realtime/rooms/{id}/matchmake?queues=duos&queues=trios
Authorization: Bearer <token>

Retorna o bilhete de matchmaking, incluindo status e sessionId quando combinado. As pesquisas anfitriãs GET /api/v1/games/{slug}/matchmaking e cancela com DELETE nesse caminho. Uma sala já na fila ou uma festa que não se enquadra em nenhum dos formatos permitidos retorna 409. Este fluxo oficial de matchmaking é independente da abertura de uma sala para adesão rápida e sua contagem regressiva de preenchimento no nível da sala.

POST /rooms/quick-join com { "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "seats": 1 } coloca o chamador no sala aberta mais antiga com assento livre para aquele jogo – os assentos de IA contam como ocupados, portanto, uma sala cujos assentos restantes são todos de IA é ignorada. 404 quando nenhuma sala estiver qualificada — o cliente deverá então criar sua própria sala e abri-la. Apenas a junção rápida de assento único é suportada (seats deve ser 1).

Filtros. Adicione qualquer um deles para ingressar apenas em uma sala adequada; cada filtro fornecido deve ser válido, e nenhum dado é o comportamento acima:

{ "gameSlug": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "seats": 1, "teamCount": 2, "seatsPerTeam": 4, "metadata": { "mode": "ranked", "map": "arena" }, "includeInProgress": true }
Filtro Combina com um quarto cujo…
teamCount a contagem da equipe é exatamente essa
seatsPerTeam assentos por equipe é exatamente isso
metadata metadados contém todo imóvel cedido, de igual valor. As propriedades que você não nomeia são ignoradas, então {"mode":"ranked"} partidas {"mode":"ranked","map":"desert"}. Os valores são comparados como JSON: números por valor (1 é igual 1.0), objetos independentemente da ordem das chaves, matrizes em ordem. Deve ser um objeto (400 de outra forma).

includeInProgress: true também considera listado, em execução adesão em andamento salas com vaga; os quartos que ainda estão cheios vêm primeiro de qualquer maneira. Sem ele, uma partida em andamento nunca é ingressada, portanto, um cliente anterior ao ingresso em andamento nunca chega a uma. UM metadata filtro que carrega um ID que seu jogo colocou nos metadados da sala é como um cliente entra um em particular sala listada, uma vez que as listagens não possuem código de adesão.

A sala aberta correspondente mais antiga com um lugar livre vence. Quando nenhum corresponde, o 404 diz "No open room with free seats matches those filters." — a dica usual para criar e abrir uma sala você mesmo com esses metadados, para que o ingresso rápido filtrado do próximo jogador os encontre.

Início, assentos, saída, resultado

POST /rooms/{id}/start (somente host): preenche ainda vazio assentos - todos eles, ou até o número da sala subsídio de preenchimento — com participantes de IA (isAi: true, userId: null, apelido aleatório exclusivo) — Os jogadores de IA sentados na criação mantêm seu id, apelido e assento — congela a escalação, define status: "Playing"e retorna a lista congelada. Se o jogo tiver um back-end de servidor (um server= script ou um contêiner), isso também cria a sessão vinculada à sala (consulte a ponte); a sala devolvida e o push carry da lista gameSessionId. A recipiente sessão que não pode ser criada — na maioria das vezes, uma implantação que ainda está ociosa — deixa a sala sem iniciar: start responde a esse erro (tente novamente) e uma sala cheia ou a varredura de aterramento tenta novamente em sua próxima passagem. Uma falha de script ainda inicia a sala roteada pelo host. Idempotente - iniciando um Playing room retorna a lista novamente. Uma sala pode iniciar automaticamente quando o prazo de preenchimento expirar.

POST /rooms/{id}/seats (somente anfitrião, Lobby/Open somente) reassenta os participantes:

{ "seats": [ { "participantId": "<guid>", "team": 1, "slot": 0 } ] }

400 para assentos fora dos limites da equipe/slot da sala ou participantes desconhecidos; 409 se dois participantes dividissem um assento.

POST /rooms/{id}/leave se comporta de acordo com o status do quarto:

  • Lobby/Aberto: o assento é removido. Se o hospedar sai, a função de anfitrião é transferida para o participante humano remanescente há mais tempo; se nenhum humano permanecer, a sala é Closed.
  • Jogando, adesão em andamento sala: o assento é desocupado (não fornecido à IA), o jogador é removido da sessão vinculada (seu ws/v1/games tomadas fechadas) e o jogo é contado. Quando o último humano sai e a sessão vinculada ainda está ativa, a sala é não fechado: o mundo permanece listado e acessível, e o primeiro jogador a voltar assume o papel de anfitrião.
  • Jogando (aquisição de IA): a partida continua — o assento do jogador que saiu se torna um assento da IA: isAi: true, userId: null, com um novo apelido exclusivo e o mesmo participante id, team, slot, e joinedAt. O que sai é imediatamente liberado (a regra de uma sala ativa não os conta mais, então eles podem criar ou ingressar em outra sala) enquanto o envio de lista informa a cada cliente que uma IA agora ocupa aquele assento. Se quem sai é o hospedar e pelo menos um outro humano permanece, o papel de anfitrião é transferido para o humano remanescente há mais tempo e a sala permanece Playing (a migração de host do lado do cliente é a preocupação do jogo); se nenhum humano permanecer, a sala é Closed.

Retorna o quarto.

POST /rooms/{id}/result (somente anfitrião, Playing somente) registra o resultado, fecha a sala e espalha o resultado pelo WebSocket. Apenas jogos roteados por host — uma sala com uma sessão vinculada com script termina quando o script retorna result, que fecha a sala automaticamente (ver a ponte).

{ "teamScores": [3, 1], "metadata": { "durationSeconds": 360 } }

teamScores deverá haver exatamente uma inscrição por equipe; cada pontuação é limitada pela sanidade em 0–50. O resultado fixado é armazenado no arquivo da sala result e enviado para participantes conectados como um {"type":"result"} quadro de controle.

GET /rooms/mine retorna o não atual do chamadorClosed sala (para reconexões), ou 404. Um jogador que também pertence mundos fica com o quarto que os ocupa, senão o mundo ao qual aderiram recentemente.

GET /rooms/joined listas todo sala em que o chamador se senta, o mais novo primeiro - seus mundos como bem como a sala que os ocupa - como salas completas (lista e código de adesão incluídos). Um lançamento o token vê apenas as salas de seu próprio jogo; com um token completo, ?gameSlug= restringe isso. Ele responde a um vazio lista, não uma 404, para que um cliente possa perguntar a cada inicialização sem um erro registrado.

Junte-se em andamento

Uma sala criada (ou PATCHed) com "joinInProgress": true continua pegando jogadores depois start. Convites, join-by-code e junte-se rapidamente a includeInProgress: true então trabalhe em um Playing quarto com um vago assento - ninguém nele, nem uma IA - então tal sala normalmente é iniciada com "backfillAiPlayers": 0. Sem a bandeira, uma sala iniciada recusa todas as junções, como antes.

  • O jogo decide. Se a sala estiver vinculada a uma sessão de jogo, o recém-chegado é admitido nessa sessão antes do assento ser mantido: a plataforma pede um script game.onMembershipChange(ctx) ou um contêiner POST /sessions/{id}/members. Um jogo que se recusa (ou não tem nenhum dos dois) recebe o assento de volta e a adesão é um 409; um convite aceito permanece pendente. Uma vez admitido, o jogador é um jogador de sessão em todos os sentidos - válido em ws/v1/games, em restaurações e reconexões.
  • Sair desocupa o assento e remove o jogador da sessão, e o jogo é contado.
  • O mundo sobrevive aos seus visitantes. Quando o último humano sair e a sessão ainda estiver ativa, a sala permanece aberta, listada e conectável; o primeiro jogador a voltar torna-se o anfitrião. Uma sala ligada a um sessão ativa também não é fechada para seu host ficar offline (veja a regra do host de 60 segundos). A própria sessão o ciclo de vida decide quando termina - um persistente pausas no jogo em vez de terminar – e a sala fecha com isso.
  • Encontrar um. GET /rooms?includeInProgress=true lista salas de ingresso em andamento com uma vaga assento; POST /rooms/quick-join com includeInProgress: true junta-se a um (adicione um metadata filtrar para escolha um quarto específico). A entrada rápida passa pelas salas em que o chamador já está.

Os mundos não contam como seu quarto

Um jogador pode estar em uma sala ativa por vez: criação, adesão por código, adesão rápida ou aceitar um convite é uma 409 "You are already in an active room." enquanto eles se sentam em outro sala que não está fechada. Um assento em um mundo não conta: um Playing, joinInProgress limite de quarto para uma sessão ativa de um persistente jogo. Um mundo dura tanto como sua sessão e sua sala permanecem abertas após a saída do último visitante, um assento em uma delas é membro, não é um lobby em que o jogador está - eles podem pertencer a vários mundos, em qualquer jogo, e ainda usar um quarto comum. Uma correspondência join-in-progress que não seja persistente ainda conta: ela termina, e enquanto ele roda o jogador está nele. Um segundo assento na mesma sala é recusado (409) em todos os caminhos. Liste um mundos do jogador com GET /rooms/joined.

WebSocket: ws/v1/realtime

Conecte-se a wss://api.starhermit.com/ws/v1/realtime?roomId=<guid> com um JWT por meio do Authorization cabeçalho, ?ticket= de POST /api/v1/realtime/connection-tickets, ou ?access_token=. Prefira o ingresso: é descartável e tem duração de segundos. Apenas participantes (403 de outra forma); um token de lançamento game_scope deve ser igual ao da sala gameSlug. A conexão mais recente substitui a anterior do usuário — o soquete antigo é fechado com PolicyViolation ("Substituído por uma conexão mais recente").

Quadros binários (jogabilidade)

Os frames binários são o canal de jogo para roteado por host jogos (sessões com script ligadas à sala são reproduzidas ws/v1/games em vez disso - veja a ponte). O servidor nunca analisa suas cargas — a autoridade do host é o contrato do jogo — mas impõe roteamento e identidade:

  • O servidor prefixa cada quadro com o ID do participante de 16 bytes do remetente (o GUID do participante na ordem de bytes do .NET). Os clientes devem retirar os primeiros 16 bytes e nunca devem confiar em um ID de remetente dentro da carga útil.
  • Anfitrião → sala: os quadros do host são distribuídos para todos os outros participantes conectados (instantâneos).
  • Convidado → apenas anfitrião: os frames de um convidado são entregues ao host e a mais ninguém (entradas).
  • Limite de tamanho do quadro: 8 KB. Limite de taxa: 30 mensagens/segundo por conexão, balde de token com permissão de burst de 2× por 1 segundo. Uma violação fecha o soquete com PolicyViolation.

Quadros de controle de texto JSON

Quadros JSON pequenos (≤ 4 KB) realizar eventos de lobby e jogos:

{ "type": "ready" }
{ "type": "chat", "text": "Ready to race" }
{ "type": "event", "kind": "countdown", "goInMs": 3000 }
  • O hospedar pode enviar event, chat, e ready; os quadros são transmitidos para todos os outros participantes.
  • Convidados só pode enviar ready e chat (também transmitido), taxa limitada a 10 por minuto.
  • O servidor re-etiqueta cada quadro de controle com o ID de participante do remetente: um fornecido pelo cliente from é removido e substituído por "from": "<participantId>".
  • Um quadro impossível de analisar, um desconhecido type, ou um tipo que a função do remetente não pode enviar fecha o soquete com PolicyViolation.

Empurrões do servidor

O servidor envia quadros de texto JSON por conta própria:

  • {"type":"presence","userId":"<guid>","online":true|false} — em cada conexão/desconexão.
  • {"type":"roster","roomId":"<guid>","status":"Playing","participants":[ ... ]} — à tomada de ligação e a toda a sala nas junções, folhas, mudanças de assento, aberturas e arranques. A lista empurra depois start é a lista de partidas congeladas, assentos AI incluídos e carrega gameSessionId quando a sala tem uma sessão com script vinculada.
  • {"type":"result","roomId":"<guid>","teamScores":[3,1],"metadata":{...}} — quando o host envia o resultado ou quando um script vinculado retorna um.

Dimensionando uma sala grande

Uma sala comporta até 100 jogadores, mas o limite prático é a largura de banda. O canal binário é roteado por host:

  • cada frame convidado vai para o host;
  • cada quadro de host é copiado para cada convidado;
  • cada quadro carrega um prefixo de remetente de 16 bytes.

Seguem duas coisas:

  • O download do host aumenta com o número de convidados. Ele recebe a opinião de cada convidado.
  • A saída da plataforma cresce com o quadrado do tamanho da sala. Um snapshot do host que descreve cada player cresce com a contagem de jogadores e é copiado para todos os convidados.

Exemplo resolvido: 100 jogadores. Cada convidado envia 30 entradas/s de 32 bytes. O anfitrião envia 20 snapshots/s com 12 bytes por player, cerca de 1,2 KB cada. A sobrecarga de TLS/TCP/WebSocket por mensagem é considerado como cerca de 70 bytes.

Link Avaliar
Cada convidado, carregue ~26kbit/s
Cada convidado, baixe ~0,21 Mbit/s
Hospedar, carregar ~0,21 Mbit/s
Hospedar, baixar ~2,8 Mbit/s, como ~3.000 mensagens/s
Saída da plataforma para a sala ~23 Mbit/s (~10,5 GB por hora)

O mesmo jogo em outros tamanhos mostra o crescimento quadrático na saída da plataforma:

Jogadores 8 22 50 100
Saída da plataforma ~0,4 Mbit/s ~1,8 Mbit/s ~6,9 Mbit/s ~23 Mbit/s

Os limites por conexão limitam o pior caso, não o típico. Uma sala para 100 jogadores na qual cada conexão envia quadros de 8 KB a 30/s é cerca de 390Mbps de saída da plataforma.

Para uma sala grande:

  • Mantenha baixas as taxas de entrada de hóspedes (10–20 Hz) e envia entradas somente quando elas mudam. O anfitrião recebe a entrada de cada convidado, e lidar com milhares de mensagens por segundo geralmente é uma tarefa mais difícil limite para um host de navegador do que a largura de banda.
  • Mantenha os instantâneos pequenos. Quantize posições, envie deltas em relação ao último estado reconhecido, e espalhar entidades que raramente mudam em vários instantâneos. Um único quadro é no máximo 8 KB, o que deixa cerca de 80 bytes por jogador em 100 jogadores.
  • O canal da sala não pode segmentar um convidado. Os quadros de host vão para todos, então todos os convidados recebe o mundo inteiro. Se o seu jogo precisar de gerenciamento de interesses por jogador (apenas nas proximidades jogadores, nevoeiro de guerra), execute-o em um servidor de jogos contêiner em vez de. Um contêiner pode endereçar frames para jogadores individuais, e o host não é mais a casa do jogador conexão.

Ciclo de vida automático da sala

  • Um Open a sala inicia automaticamente quando o prazo de preenchimento expira; assentos vazios tornam-se participantes de IA com nomes exclusivos, até o limite da sala subsídio de preenchimento.
  • Um Open A sala também começa automaticamente assim que cada assento é ocupado – por humanos, por jogadores de IA configurados na criação ou por uma mistura – sem esperar por esse prazo.
  • A Playing a sala fecha quando seu host não tem ws/v1/realtime conexão por mais de 60 segundos — a menos que esteja vinculado a uma sessão de jogo que ainda esteja ativa; nesse caso, a função de host é movida (veja abaixo). Os convidados conectados recebem um envio final da lista mostrando a sala fechada.
  • A Lobby ou Open a sala fecha após mais de 60 minutos sem participantes conectados.

Um participante que simplesmente perde a conexão não é afetado: reconectar o soquete (a conexão mais recente é substituída) e GET /rooms/mine ambos continuam trabalhando enquanto a sala está viva.

A regra do host de 60 segundos e sessões vinculadas à sala

Uma correspondência executada no servidor não pertence ao seu host. A Playing sala vinculada a uma sessão de jogo que é ainda active nunca é fechado porque seu host está offline: a função de host passa para um ser humano conectado se houver, caso contrário nada acontece. O ciclo de vida da sessão decide quando a partida será acabou e fecha a sala quando termina. A regra abaixo se aplica a salas roteadas pelo host (sem sessão) e para uma sala vinculada assim que sua sessão terminar.

Portanto, um jogo vinculado a uma sala não precisa do soquete em tempo real do host. Um anfitrião que joga ws/v1/games e fecha (ou nunca abre) ws/v1/realtime não fecha a sala durante a sessão é active; abra o soquete em tempo real apenas se o seu jogo quiser pushes de escalação.

Para uma sala roteada por host, apenas um ws/v1/realtime socket conta como a conexão do host. O relógio começa quando o último soquete em tempo real do host é fechado; um host que nunca se conectou é medido a partir do quarto startedAt.

Fechar uma sala não encerra a sessão vinculada à sala. Uma sala vinculada ainda pode fechar enquanto estiver a sessão é executada - na maioria das vezes quando é o último humano folhas um quarto sem adesão em andamento. Fechando (roster push, todos os assentos liberados, convites pendentes expirado) não faz mais nada:

  • A sessão permanece active. Seus jogadores podem continuar jogando ws/v1/games, e o script mantém funcionando em sua taxa de tick.
  • Da próxima invocação em diante, ctx.room.roster é vazio e cada ser humano em ctx.presence tem left: true, porque fechar a sala libera todos os assentos. online ainda reflete ws/v1/games soquetes. Um roteiro que trata "todo mundo foi embora" como o final da partida deve retornar result então.
  • Se o script retornar mais tarde result, a sessão termina normalmente, mas a sala está result fica null: a sala já estava fechada, então o resultado fica armazenado apenas na sessão.
  • Se o script nunca retornar result, a sessão é encerrada como qualquer outra sessão de jogo: 5 minutos depois do último ws/v1/games soquete fecha, ou após 24 horas sem ação do jogador (veja Jogos — Modelo de sessão).

Resumindo: uma partida ligada à sala sobrevive ao seu host ficar offline; se deve terminar quando seus jogadores saia da sala, termine no roteiro quando ctx.presence mostra que todos foram embora.

Resumo de segurança

  • Cada endpoint funciona com um JWT completo ou um token de lançamento no escopo do jogo; um token de lançamento game_scope deve corresponder ao da sala gameSlug, então dois jogos nunca poderão ver ou juntar-se às salas um do outro.
  • As leituras são apenas para participantes (mais convidados pendentes); open, seats, start, e result são apenas de host; os convites são apenas para amigos.
  • Validação: limites de assentos/equipes, uma contagem de IA que sempre deixa um assento para o anfitrião, uma sala ativa por usuário (exceto mundos), um ocupante por assento, início idempotente, pontuações de resultados fixadas em 0–50, convites expiram com a sala.
  • Transporte: IDs de remetente marcados pelo servidor, roteamento baseado em função, limites de tamanho de quadro, limites de taxa por conexão, sem análise de cargas binárias no lado do servidor.

Sessões vinculadas à sala

Para um jogo com backend de servidor — um server= script em seu manifesto ou um recipiente – uma sala em tempo real pode executar sua partida servidor com autoridade em vez de no cliente host. Os pontos abaixo foram escritos para scripts; um contêiner recebe a mesma lista através de seu POST /sessions ctx (room, presence) e mudanças de associação por meio de POST /sessions/{id}/members. Isso combina salas (lobby, convites, matchmaking, backfill) com simulação do lado do servidor, entradas validadas e resultados de propriedade do script.

  • Criação de sessão no início da sala. Quando a sala entra Playing, a plataforma cria um N-jogador sessão de jogo para os participantes humanos. As vagas de IA existem apenas na lista voltada para o script. A resposta da sala e os impulsos de escalação expõem gameSessionId para que os clientes saibam qual soquete de jogo abrir.
  • A jogabilidade passa para ws/v1/games. Os clientes se conectam a ws/v1/games?sessionId=<gameSessionId> e troca cmd/game frames com o script, exatamente como qualquer jogo com script; o WS em tempo real permanece conectado apenas para escalação/presença. A sessão funciona na taxa suportada solicitada por seu script via game.tickRateHz — um script que não solicita nada está marcado em 0,25 Hz, o que nenhum jogo em tempo real deseja, então declare um (veja Scripts de jogos).
  • Script estendido ctx. Cada chamada para uma sessão vinculada à sala (createSession, onPlayerMessage, onTick) recebe adicionalmente ctx.room (ID da sala, metadados e lista congelada — humanos e Assentos AI, ordenados por equipe e depois por slot) e ctx.presence ({ "<userId>": { online, left } } para cada usuário que é ou foi um participante humano). Detalhes em Scripts de jogo – sessões limitadas à sala.
  • Conquistas autorizadas pelo servidor. Cada gancho de uma sessão vinculada pode conceder conquistas retornando achievements: {userId: [keys]}, exatamente como em qualquer jogo com script – incluindo de createSession, que é acionado no momento em que a sala é iniciada. Os desbloqueios são enviados para o jogador ganhador ws/v1/games como {"type":"achievement"} quadros. Ver Conquistas.
  • O script encerra a partida. Quando o script retornar result, a plataforma encerra a sessão, armazena o resultado na sala e fecha a sala (inclui push final da escalação). POST /rooms/{id}/result não é usado para jogos dentro da sala.
  • Comece falhas. Uma sala apoiada por script pode ser iniciada sem uma sessão vinculada se a criação da sessão falhar; inspecionar gameSessionId antes de escolher um transporte de jogo. Uma sala apoiada por contêiner permanece inativa quando seu servidor não consegue criar a sessão. Tente novamente com espera em caso de erro temporário de inicialização; não mude para simulação de host.
  • Um jogo roteado pelo host pode vincular uma sessão apenas por conquistas. O canal de jogo binário nunca é bloqueado em uma sessão vinculada, portanto, um jogo que simula no cliente host ainda pode enviar um server= script cujo único trabalho é garantir concessões de sucesso (e elo), enquanto o caminho rápido continua fluindo ws/v1/realtime.

Como um jogo o usa

  1. Criar: o criador do lobby chama POST /rooms com seu layout de equipe, um opaco metadata blob, e quantos aiPlayers a partida deve começar e se torna o anfitrião. Preencher todos os outros lugares com IA aqui é todo o fluxo solo versus computador.
  2. Convidar: o anfitrião lista amigos (GET /api/v1/me/friends) e envia POST /rooms/{id}/invites. A plataforma notifica cada convidado (game_invite empurrar + GET /api/v1/me/game-invites), para que possam aceitar no painel sem ter o jogo aberto; os convidados que já estão no jogo veem os mesmos convites por enquete GET /rooms/invites. A aceitação os coloca na equipe do anfitrião.
  3. Abrir: o anfitrião chama POST /rooms/{id}/open. Jogadores solo chamam POST /rooms/quick-join e pousar na sala aberta mais antiga com assento livre (em 404 eles criam e abrem seu próprio quarto).
  4. Conectar: todo mundo abre ws/v1/realtime?roomId=… e relógios roster/presence empurra conforme os assentos são preenchidos.
  5. Começar: no prazo de preenchimento, assim que todos os assentos forem ocupados, ou quando a força do anfitrião começar, os assentos vazios restantes tornam-se participantes da IA ​​(até o subsídio de preenchimento) e a lista congela. Jogo roteado por host: os convidados enviam entradas como quadros binários (eles alcançam apenas o host); o host transmite instantâneos. Jogo com script limitado à sala: todos se conectam ws/v1/games?sessionId=<gameSessionId> e joga contra o roteiro com cmd/game quadros.
  6. Sair no meio da partida: em um adesão em andamento sala o assento fica vago para o próximo jogador. Caso contrário, um jogador que sai durante Playing é substituído onde estava por um participante da IA ​​(mesmo assento, novo apelido gerado pelo servidor) e pode imediatamente entrar na fila novamente; se o hospedeiro sair, a função de hospedeiro passa para o ser humano remanescente há mais tempo. Em um jogo roteado por host, um host que interrompe sua conexão em tempo real tem 60 segundos para se reconectar antes que a partida termine; uma partida com destino à sala nunca é encerrada porque seu anfitrião está ausente.
  7. Terminar: host-routed — o host envia o resultado; o servidor fixa as pontuações, armazena o resultado, envia-o para todos os soquetes e fecha a sala. Limite à sala – o script retorna result e a plataforma armazena e fecha a sala.
