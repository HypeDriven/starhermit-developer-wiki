Contratos REST e WebSocket

Esses contratos para download complementam as páginas de referência. Use-os para inspecionar operações, valide exemplos de cargas úteis ou importe solicitações REST para um cliente compatível com OpenAPI.

Arquivo Cobertura
Contrato REST OpenAPI Métodos REST públicos, caminhos, parâmetros, modelos de solicitação JSON, respostas bem-sucedidas e famílias de credenciais; operações de geração reservadas são marcadas como indisponíveis
Esquemas WebSocket JSON Quadros de texto conhecidos por protocolo e direção; os dados de jogabilidade/sinalização de propriedade do aplicativo permanecem abertos

Contratos REST

O arquivo REST usa OpenAPI 3.0.3 e a origem da API pública. Cada operação está vinculada à sua página de referência, que carrega as regras completas de autorização, validação, limites e erros. x-credentials identifica as famílias de credenciais aceitas; não substitui verificações de propriedade ou de adesão. x-required-policies descreve permissões nomeadas onde a API as aplica.

As respostas podem incluir campos adicionais. JSON, metadados, diagnóstico e upload específicos do jogo os resultados usam formas abertas onde a referência do jogo ou do endpoint define seu conteúdo. Sucesso esquemas não são uma promessa de que todo chamador está autorizado. Erros de endpoint podem ser JSON, texto simples, respostas vazias ou detalhes do problema de validação; usar análise de resposta defensiva.

Não trate as operações de geração reservada como um serviço funcional. Seu contrato descreve o atual 503 overloaded resposta, não campos de solicitação futuros ou comportamento de geração.

Contratos WebSocket

Escolha um $defs esquema para o protocolo e direção do seu soquete. Por exemplo, validar um cliente quadro de movimento contra GameRealtimeInput, em vez do durável genérico GameCommand:

{ "type": "cmd", "data": { "type": "input", "realtime": true, "seq": 1, "x": 0.5 } }

realtime pertence dentro data. Os campos de jogo posteriores são o contrato do seu jogo. Use um Esquema JSON 2020-12 validador com o documento de esquema completo para que as referências locais sejam resolvidas. O documento raiz contém definições; selecionar uma definição é necessário para validar um quadro.

Os tipos de quadros futuros devem chegar ao manipulador de quadros desconhecidos do seu cliente, em vez de travar o recebimento laço. A validação do formato JSON não valida regras do jogo, autoriza associação ou impõe taxa limites. As páginas de referência definem restrições de função e tamanho/taxa.

Ordem de bytes GUID

Os três primeiros grupos UUID são little-endian em um cabeçalho de byte .NET GUID. Por exemplo:

UUID:  00112233-4455-6677-8899-aabbccddeeff
Bytes: 33 22 11 00 55 44 77 66 88 99 aa bb cc dd ee ff

Um decodificador de navegador para o prefixo de 16 bytes:

function guidFromDotNet(bytes) {
  if (bytes.length !== 16) throw new Error('Expected a 16-byte GUID');
  const hex = i => bytes[i].toString(16).padStart(2, '0');
  return `${hex(3)}${hex(2)}${hex(1)}${hex(0)}-${hex(5)}${hex(4)}-${hex(7)}${hex(6)}-` +
    `${hex(8)}${hex(9)}-${hex(10)}${hex(11)}${hex(12)}${hex(13)}${hex(14)}${hex(15)}`;
}

Os prefixos em tempo real identificam participantes, enquanto os prefixos de voz identificam Usuários. Um contêiner stream tem um tipo de um byte seguido por UUIDs de sessão/usuário, então seu JSON começa em byte 33. O o relé não adiciona nenhum prefixo. Ler cada soquete como o mesmo layout binário corrompe cargas úteis e identidade.
