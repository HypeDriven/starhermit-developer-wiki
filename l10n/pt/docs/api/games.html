API de jogos

O subsistema de jogos é o núcleo do StarHermit: jogos multijogador com autoridade de servidor cujas regras são executadas em um arquivo JavaScript em área restrita ou em um contêiner fornecido pelo desenvolvedor. Ambos os tempos de execução compartilham esta API REST voltada para o jogador (api/v1/games/{slug}) e jogabilidade WebSocket (ws/v1/games). Para autoria de servidor, consulte Scripts de jogos ou Servidores de jogos hospedados em contêineres. Para obter um exemplo completo de tempo de execução de script, consulte o Passo a passo de xadrez e HypeDriven/starhermit-chess.

URL base: https://api.starhermit.com.

Os endpoints do jogador exigem autenticação e funcionam com tokens de usuário completos e inicialização no escopo do jogo fichas. Os dois /server/... endpoints são somente contêineres: a reconciliação de sessão usa um limite token portador do servidor, enquanto a renovação do token usa a chave de atualização de implantação.

O que {slug} é

A lesma de um jogo é a sua UID - o mesmo valor que o seu <uid>.starhermit.com endereço, por ex. 83fd04b1-3cbe-4b09-a251-3733ad4b9d94. É derivado do id imutável do jogo e nada pode configurá-lo: não starhermit.txt, não o nome do repositório, não um operador. Um nome que um desenvolvedor poderia escolher seria algo pelo qual dois jogos poderiam competir e precisaria da plataforma para arbitrar quem entendi; um uid não pode colidir nem ser solicitado.

Um slug não é um backend de servidor. Cada jogo adicionado de uma pasta local e cada jogo de repositório um proprietário verificado adicionado, tem um - com ou sem server= ou container.image= - porque é o endereço da superfície voltada para o jogador do jogo: tokens de lançamento, controles, configurações, isso é slot para salvar na nuvem e quartos. Um o jogo somente para navegador precisa disso tanto quanto qualquer outro. Os únicos jogos sem slug são repositório envios cujo proprietário não foi verificado (gameSlug é null em GET /api/v1/me/github-games).

Os pontos finais sobre o servidor de um jogo — informações do jogo, conquistas, sessões, matchmaking, convites, replays – precisa de um back-end. GET /api/v1/games/{slug} respostas 404 para um jogo que tem um slug e não backend, que é a maneira de diferenciar os dois.

Não codifique-o. Leia no token de lançamento game_scope reivindicação, ou - por um jogo de navegador hospedado na plataforma — de location.hostname, já que o subdomínio é o uid.

Informações do jogo

GET /api/v1/games/{slug}

Retorna a definição do jogo mais as estatísticas do chamador para esse jogo. 404 se tal jogo não existir, ou se o jogo for apenas para navegador (tem um slug, mas não possui back-end de servidor).

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "name": "Chess",
  "enabled": true,
  "leaderboardId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "maxConcurrentSessionsPerPlayer": 20,
  "replaysEnabled": true,
  "buildId": "s12",
  "me": {
    "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "elo": 1200,
    "wins": 4,
    "losses": 2,
    "draws": 1,
    "activeSessionCount": 2
  }
}
  • leaderboardId é opcional.
  • me.elo o padrão é 1200; wins/losses/draws são lidos no documento por jogador de propriedade do tempo de execução do servidor.
  • replaysEnabled diz se as sessões finalizadas deste jogo são mantidas - leia em vez de presumir e oculte sua IU de replay quando for false. Ver Repetições.
  • buildId nomeia a lógica do servidor atualmente servindo o jogo (s + versão do script ou c + prefixo de resumo da imagem). Envie de volta como ws/v1/games?build=… então um cliente obsoleto é recusado 409 {"error":"build_mismatch"} antes de agir nos campos movidos. Omitindo build conecta como antes.

Tokens de lançamento

POST /api/v1/games/{slug}/launch-token

Cria um JWT com escopo de jogo (vida útil padrão de 60 minutos) carregando game_scope={slug} e nenhuma reivindicação de permissão. Um token com escopo definido pode cunhar novamente um token para seu próprio jogo — este é o padrão de atualização do cliente — mas a renovação é limitada por launch_chain (padrão 12 horas a partir da sessão original do usuário). Além dessa renovação do teto é 403. Os clientes devem atualizar antes que o token expire; o cliente de referência de xadrez, por exemplo, é atualizado a cada 45 minutos. Renove também antes de reconectar uma tomada - consulte Jogabilidade WebSocket.

{
  "token": "eyJhbGciOi...",
  "expiresInSeconds": 3600
}

Conquistas

GET /api/v1/games/{slug}/achievements

Cada conquista declarada pelo back-end oficial do jogo, com o estado de desbloqueio do chamador. Segredo as conquistas permanecem ocultas até que o chamador as desbloqueie. Aceita um JWT de usuário completo ou um JWT com escopo de jogo token de lançamento. 404 quando o slug não tem uma definição de jogo oficial.

[
  {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "key": "first-win",
    "name": "First Win",
    "description": "Win a match.",
    "icon": null,
    "secret": false,
    "points": 10,
    "unlocked": true,
    "unlockedAt": "2026-07-25T09:14:02Z"
  }
]

As conquistas do jogo são autoridade do servidor: apenas o script ou contêiner do jogo os concede, e o cliente reivindicou POST /api/v1/me/achievements/unlock endpoint os recusa. Desbloqueios ao vivo chegar no soquete do jogo como {"type":"achievement"} quadros. Os contratos completos estão em Conquistas, Scripts de jogos, e Servidores de jogos em contêiner.

GET /api/v1/games/{slug}/linked-achievements/{otherSlug}

Os próprios desbloqueios do chamador em outro jogo, para que este jogo possa abrir recursos baseados neles. Funciona com o token de lançamento deste jogo. Ver Conquistas — Conquistas de outros jogos.

Ligações de controle por jogador

Os jogos podem declarar controles do navegador de desktop com control.* entradas em starhermit.txt. A API de controles armazena um substituição separada para cada usuário e jogo. JWTs de usuário completo e tokens de lançamento no escopo do jogo são aceito; um token de lançamento game_scope deve corresponder {slug}.

GET /api/v1/games/{slug}/controls

Retorna as ligações efetivas na ordem manifesta. codes contém a substituição do usuário quando existe um, caso contrário defaultCodes. Devoluções 404 "This game declares no controls." quando o construção ao vivo starhermit.txt não tem validade control.* line — declare-os e publique uma compilação; ver Tutorial: adicione controles ao seu jogo.

{
  "actions": [
    {
      "action": "up",
      "label": "Run forward",
      "defaultCodes": ["KeyW", "ArrowUp"],
      "codes": ["KeyW", "ArrowUp"]
    },
    {
      "action": "shoot",
      "label": "Shoot",
      "defaultCodes": ["Space"],
      "codes": ["KeyJ"]
    }
  ]
}

PUT /api/v1/games/{slug}/controls

Substitui as substituições do chamador. O bindings objeto pode conter um subconjunto do declarado ações; as ações omitidas continuam a usar seus padrões.

{
  "bindings": {
    "up": ["KeyW", "ArrowUp"],
    "shoot": ["KeyJ"]
  }
}

Cada ação deve ser declarada pelo jogo. Cada ação deve ter 1–4 válidas KeyboardEvent.code valores, e nenhum código pode ser atribuído a duas ações no resultado mapa eficaz. Ações, códigos ou conflitos inválidos retornam 400.

DELETE /api/v1/games/{slug}/controls

Exclui todas as substituições do chamador e restaura os padrões do manifesto. Devoluções 204. As gravações do token de lançamento são intencionais, portanto, um jogo hospedado pode fornecer sua própria tela de religação.

Configurações de jogo por jogador

Onde seu jogo continua suas próprias opções para um jogador — volume mestre, detalhes gráficos, legenda tamanho, câmera preferida, último carregamento escolhido – então eles seguem o jogador até qualquer máquina em que fizerem login de. Um armazenamento de chave/valor com escopo para um jogador e um jogo. Para uma seção de Idioma ao lado de Gráficos, Áudio e controles, consulte localize seu jogo e adicione configurações de idioma.

Nada declara um esquema. A plataforma armazena suas chaves e valores e nunca os lê, então você adiciona uma opção escrevendo-a: nenhuma entrada de manifesto, nenhuma reimplantação, nenhuma liberação de plataforma. Isso também significa que a plataforma não pode validá-los para você – um erro de digitação no nome de uma chave é uma nova configuração, não uma erro.

Assim como a API de controles, um token de inicialização no escopo do jogo é aceito (seu game_scope deve corresponder {slug}), portanto, uma tela de opções do jogo funciona apenas com o token que o jogo já possui. Ao contrário controles, nenhuma declaração de manifesto é necessária: todo jogo possui armazenamento de configurações a partir do momento em que existe, incluindo um jogo somente para navegador, sem nenhuma lógica de servidor.

Escolha a loja certa - salva na nuvem manter o progresso (um arquivo opaco por título, 10 MB, acessível também com o token de lançamento), e o estado do player do próprio back-end de um script ou contêiner é autoritativo do servidor e não pode ser gravado a partir de um cliente. As configurações são as pequenas preferências intermediárias de propriedade do cliente.

GET /api/v1/games/{slug}/settings

Tudo o que o chamador armazenou para este jogo. settings está vazio para um jogador que nunca salvou qualquer coisa - isso é um 200, não um 404. As chaves voltam ordenadas.

{
  "slug": "83fd04b1-3cbe-4b09-a251-3733ad4b9d94",
  "settings": {
    "audio.master": 0.8,
    "graphics.detail": "ultra",
    "graphics.options": { "shadows": true, "msaa": 4 }
  },
  "count": 3,
  "bytes": 118,
  "updatedAt": "2026-08-07T15:04:11Z",
  "limits": { "maxKeys": 200, "maxKeyLength": 128, "maxTotalBytes": 2097152, "maxAccountBytes": 67108864 }
}

bytes é o custo atual das configurações deste jogador limits.maxTotalBytes. Leia o limites em vez de codificá-los: a permissão é uma configuração do operador e um jogo pode ser concedido seu próprio. maxKeys (200 por padrão) também pode ser definido por jogo, e maxAccountBytes limita um configurações da conta em todos os jogos (64 MB por padrão).

PUT /api/v1/games/{slug}/settings

Substitui todo o mapa. Chaves que o corpo omite são excluídas - envie tudo ou use PATCH.

{ "settings": { "audio.master": 0.8, "graphics.detail": "ultra" } }

Um vazio settings object limpa as configurações do jogo para o chamador. Retorna a mesma forma que GET.

PATCH /api/v1/games/{slug}/settings

Mescla-se com o que está armazenado, deixando as chaves que não menciona sozinhas. UM null valor remove é chave. Isso mescla chaves de configuração de nível superior; um valor de objeto substitui todo o valor em sua chave, incluindo suas propriedades aninhadas. Isso é o que tela de opções deve usar - pode salvar o controle deslizante que se moveu sem primeiro ler e reescrevendo todo o resto.

{ "settings": { "audio.music": 0.25, "graphics.options": null } }

GET / PUT / DELETE /api/v1/games/{slug}/settings/{key}

Uma configuração de cada vez. GET retorna { "key", "value", "updatedAt" }, ou 404 se o chamador tiver nunca guardei. PUT leva { "value": <any JSON> } e armazena o valor literalmente - incluindo um explícito null, que aqui é um valor como qualquer outro, não uma exclusão. DELETE retorna 204e remover algo que não existe é um não-op em vez de um erro.

curl -X PUT "https://api.starhermit.com/api/v1/games/$SLUG/settings/audio.master" \
  -H "Authorization: Bearer $LAUNCH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"value": 0.35}'

Regras

Regra Valor
Configurando nomes 1–128 caracteres de A-Z a-z 0-9 . _ - : - namespace livremente (audio.master, graphics:shadows)
Valores Qualquer JSON: número, string, booleano, array, objeto, null
Configurações por jogador, por jogo 200
Bytes por jogador, por jogo 2 MB por padrão — um operador pode aumentá-lo ou diminuí-lo e conceder a um jogo uma franquia diferente

Uma única configuração pode usar toda a permissão de bytes; não há limite menor por valor separado.

Status Significado
400 Nome de configuração incorreto ou corpo que não é {"settings": {...}} / {"value": ...}
404 Nenhum jogo responde a esse slug, ou (tecla única GET) nada é armazenado sob essa chave
413 Acima do limite — muitas configurações ou muitos bytes. A mensagem indica o limite

Um lote que contém uma chave incorreta não grava nenhuma das chaves boas. As configurações são por jogador e por jogo: nada vaza entre dois jogadores ou entre dois jogos do mesmo jogador. Eles sobrevivem a um jogo sendo desativado ou removido da lista, porque são dados do jogador e não do jogo.

Sessões

GET /api/v1/games/{slug}/sessions/mine

As sessões ativas do chamador para este jogo. myTurn e deadline são analisados ​​a partir do estado do script summary objeto (ver Scripts de jogos). pausedAt é definido enquanto um persistente a sessão é pausada sem ninguém nela e null de outra forma.

Sessões vinculadas à sala estão incluídas. A sala em tempo realA sessão vinculada de lista todos os humanos que estavam sentados quando a sala começou, então aparece aqui para cada um deles enquanto está active. Assentos AI não estão disponíveis players. Sair da sala, ou fechar a sala, não remove ninguém da sessão, por isso permanece nesta lista até que a sessão termine - exceto em um adesão em andamento sala, onde um jogador que sai cede seu lugar e é retirado da sessão, e um recém-chegado admitido no meio da partida é adicionado a ela. Não há ID de sala na resposta: use GET /api/v1/realtime/rooms/joined para os quartos do chamador e combine seus gameSessionId contra sessionId.

[
  {
    "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e",
    "status": "active",
    "players": [
      { "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "username": "alice" },
      { "userId": "9b2f8c1a-1111-4222-8333-444455556666", "username": "bob" }
    ],
    "createdAt": "2026-07-20T14:03:11Z",
    "finishedAt": null,
    "myTurn": true,
    "deadline": 1784642591000,
    "pausedAt": null
  }
]

Detalhe da sessão. Apenas participantes - 403 de outra forma.

    { "userId": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "username": "alice" },

Recuperação e saída explícita

GET /api/v1/games/{slug}/sessions/{sessionId}/recovery retorna instantâneo efetivo, restauração, valores de retenção e transporte. Os participantes e o proprietário do jogo podem lê-lo. Unidades de tempo e tudo campos de resposta são descritos em Ciclo de vida e recuperação da sessão.

POST /api/v1/games/{slug}/sessions/{sessionId}/leave desiste de ser membro de um mundo persistente sem uma sala em tempo real. Não leva corpo e retorna 204; a partida humana final acaba com o mundo. 403 significa que não é membro, 404 significa nenhuma sessão, 410 significa terminado, e 409 significa um não persistente sessão ou uma sessão vinculada à sala. Para uma sessão vinculada à sala, use o /leave ponto final. Fechando apenas um soquete preserva a associação. Ver desconectando e saindo.

POST /api/v1/games/{slug}/sessions/ai

Cria uma sessão prática na plataforma AI: ID de usuário fixo 00000000-0000-4000-8000-00000000a1a1, nome de usuário "A casa". O back-end oficial do jogo reproduz a IA – não há serviço de bot externo.

{ "sessionId": "0f8fad5b-d9cb-469f-a165-70867728950e" }

Organização de partidas

Um script declara as formas de correspondência que aceita por meio game.queues. Um jogo sem aceitação declarações tem um implícito default fila (duas equipes de uma). O contêiner atual /describe leitor faz não importar queues, então os jogos de contêiner usam esse formato 1v1 implícito. Um cliente que não nomeia nenhuma fila recebe o jogo primeiro.

Até oito filas de script são retidas. As teclas são cortadas, minúsculas, não vazias e no máximo 32 personagens; chaves duplicadas mantêm a primeira. teams é fixado em 2–8 e teamSize para 1–16; formas que excedam 32 jogadores no total são descartadas. Declarações inválidas podem voltar ao implícito 1v1, então verifique as formas efetivas com GET /queues após a publicação.

GET /api/v1/games/{slug}/queues

[
  { "key": "duos", "teams": 2, "teamSize": 2, "players": 4 }
]

POST /api/v1/games/{slug}/matchmaking

Coloca o chamador na fila para o emparelhamento elo mais próximo. Repetível ?queues= chaves de consulta nomeiam um subconjunto de essas formas (por exemplo, 1v1 e 2v2, não 3v3). A correspondência apenas preenche um ticket em relação a uma forma permitida. Por exemplo:

POST /api/v1/games/{slug}/matchmaking?queues=solo&queues=duos
Authorization: Bearer <token>

Use chaves retornadas por GET /queues. ?queue=solo seleciona uma única forma; se ambos queue e queues são fornecidos, suas chaves são combinadas e desduplicadas sem distinção entre maiúsculas e minúsculas. Uma chave desconhecida é 404; uma lista vazia após a validação é 400. Devoluções 409 se o chamador já estiver na fila ou no limite de sessões simultâneas.

A pesquisa começa em uma banda elo estreita e se amplia enquanto o ticket aguarda (padrão 100, +10/s). Status: queued, matched, cancelled, expired (esperou além do limite, padrão 300 s, sem encontrar alguém - ofereça um jogo de treino em vez de girar). Uma festa é um sala em tempo real: POST /api/v1/realtime/rooms/{id}/matchmake (anfitrião, lobby) entra em toda a escalação como uma equipe.

{
  "ticketId": "b3b7c8d2-5c1e-4f3a-9e2d-1a2b3c4d5e6f",
  "status": "queued",
  "sessionId": null,
  "waitedSeconds": 12,
  "searchEloBand": 220,
  "maxWaitSeconds": 300
}

Os jogos podem optar por o prazo começa em starhermit.txt: matchmaking.max_wait_seconds inicia uma partida com preenchimento insuficiente após a espera e matchmaking.ai_players limita quantos assentos vagos se tornam IA. Outros assentos permanecem vazios. Humano completo as partidas começam cedo. maxWaitSeconds relata a configuração desse jogo; esses ingressos ficam queued até que o matchmaking os inicie, em vez de expirar no limite de espera global.

GET /api/v1/games/{slug}/matchmaking

Retorna o último ticket do chamador ou 404. A matched ticket é reportado apenas enquanto estiver sessão ainda está active. Depois que a partida terminar, isso é 404 então o lobby oferece uma nova partida em vez de apontar para um ID de sessão inoperante.

Convidando um amigo para um jogo em andamento

Adicione a sessão em que você está jogando:

{ "toUserId": "9b2f8c1a-1111-4222-8333-444455556666", "sessionId": "3f0c…" }

Aceitando então admite o amigo naquela sessão de corrida em vez de começar um novo - eles se tornam jogadores em todos os sentidos (socket, ctx.players, restaura, reconecta). Seu jogo decide se os aceita: a plataforma pede um script game.onMembershipChange(ctx) ou um contêiner POST /sessions/{id}/members, e um jogo que não recusa todas essas associações. Regras:

  • A sessão deve ser uma sessão ativa deste jogo que você jogar em (403 de outra forma, 410 se tiver terminado), seu amigo ainda não deve estar nele (409) e não deve pertencer a uma sala em tempo real (409 — convidar através da sala, cujos assentos são a escalação).
  • A resposta carrega targetSessionId; sessionId fica null até que o convite seja aceito.
  • Ao aceitar tudo é verificado novamente. Se o jogo recusar (completo, fechado…) a aceitação é uma 409 e o convite permanece pendente. Se a partida terminou o convite é cancelado e as respostas aceitas 410 - nunca se transforma em um novo jogo.
  • Somente o limite de sessões simultâneas do convidado se aplica. Você pode manter um convite pendente por amigo e por destino, para que um convite para sua partida e um convite para um novo jogo possam coexistir.

Uma construção de plataforma anterior a esse recurso ignora sessionId e inicia uma nova sessão ao aceitar; targetSessionId na resposta informa qual você obteve.

Qual convite você deve enviar? Aceitar um convite simples (não sessionId) cria uma nova sessão para os dois jogadores. Se o autor do convite já estiver sentado em um sala em tempo real (um saguão com assentos), convide-os para aquela sala - POST /api/v1/realtime/rooms/{id}/invites - então aceitar coloca-os na mesa em que você realmente está. Ambos notificam o convidado da mesma forma, portanto nunca envie os dois para um só convite: isso notifica duas vezes.

Compartilhe links (convite por URL)

O fluxo de convite acima exige que os dois jogadores já sejam amigos. Para convidar alguém que está ainda não está na plataforma (ou ainda não é amigo), um jogo pode distribuir um compartilhar link — uma URL para o painel da web que automatiza toda a integração:

https://dashboard.starhermit.com/game-invite/<userId>/<gameSlug>
  • <userId> — o ID de usuário do jogador que está compartilhando. Um cliente de jogo já tem: é o sub reivindicação de seu token de lançamento (a implementação de referência de xadrez o expõe como Net.userId).
  • <gameSlug> - a lesma do jogo (game_scope alegar). Jogos sem um script oficial ou back-end de contêiner usam o ID do jogo GitHub (um GUID); o painel também aceita.
  • String de consulta opcional — sua. Qualquer coisa depois ? é passado para o seu jogo inalterado: …/game-invite/<userId>/<gameSlug>?room=K7MP2X&map=arena abre seu jogo em https://<game-id>.starhermit.com/…?room=K7MP2X&map=arena. Use-o para descartar o destinatário diretamente em uma sala, um nível ou um lobby. Ele sobrevive ao login do destinatário e é adicionado ao seu URL do jogo em vez de substituir qualquer coisa lá. O token de lançamento ainda chega no #game_token= fragmento, para que os dois nunca colidam. Codifique em URL os valores que você colocou nele.

Quando o destinatário abre o link, o painel (não o jogo) faz a parte automatizada do convite de amizade — nenhum novo endpoint de back-end está envolvido, ele compõe as APIs existentes:

  1. Faz login (OAuth por meio de um provedor ativo) ou reutiliza a sessão existente. A intenção do link sobrevive à viagem de ida e volta de login.
  2. Mostra uma caixa de diálogo de consentimento nomeando o compartilhador e o jogo e, em seguida, amigos, o compartilhador: aceita o pedido de amizade pendente do compartilhador, se existir, caso contrário, envia um (POST /api/v1/me/friend-requests).
  3. Solicita que eles escolham um apelido se sua conta não tiver nenhum (os jogos exibem apelidos de perfil - consulte Perfil).
  4. Inicia o jogo (o servidor hospedado na plataforma https://<game-id>.starhermit.com cópia, com um token de lançamento no #game_token= fragmento como de costume).
  5. Envia o reproduzir convidar de volta para o compartilhador com POST /api/v1/games/{slug}/invites - assim, um link de compartilhamento termina como um convite de jogo normal que o compartilhador aceita (torneira do painel, balão da área de trabalho ou a própria lista de convites do jogo). Se a amizade ainda for uma solicitação pendente, o painel coloca o convite para jogar na fila e o envia automaticamente assim que o compartilhador aceita.

O que isso significa para o seu cliente de jogo:

  • Oferecer o link custa uma linha de construção de string - coloque um "Compartilhar link de convite" ao lado da interface de convite de um amigo e copie o URL para a área de transferência. Ver shareInviteLink() no implementação de referência de xadrez.
  • Nenhum manuseio especial é necessário do lado receptor. O convite do destinatário chega através do fluxo normal de convite: seu GET .../invites a votação mostra ao compartilhador o convite recebido, aceitá-lo cria a sessão e o destinatário vê a sessão aparecer em GET .../sessions/mine (mostrar convites de saída pendentes para que a espera fique visível - o cliente de xadrez "convidado - esperando" cartões).
  • O painel também usa esses URLs: o painel de detalhes de cada jogo hospedado jogável tem um Copiar link de convite botão, e o cliente Windows oferece o mesmo no menu de contexto do jogo.

Repetições

Um replay é o documento de estado final de uma sessão finalizada, mantido pela plataforma e enviado de volta ao jogadores que estavam nele. Replays são um recurso opcional de um jogo, desativado a menos que o jogo solicite eles, porque um replay é um armazenamento que a plataforma mantém enquanto existir o registro da partida.

Solicite-os no código do seu servidor - replays: true no game objeto para um roteiro, "replays": true de /describe por um servidor de contêiner – e publicar uma atualização para aplicá-la. Uma plataforma operador também pode responder por um jogo específico de qualquer maneira, então trate o replaysEnabled campo de GET /api/v1/games/{slug} como resposta, em vez de assumir que sua declaração é a última palavra.

Ambos os pontos de extremidade abaixo retornam 404 para um jogo cujos replays estão desligados e nada é impedido disso sessões finalizadas do jogo - então um cliente que oferece uma tela de replay deve ler replaysEnabled primeiro.

Modelo de sessão

  • Sessão status é "active" ou "finished".
  • Cada sessão recebe uma conversa de chat por sessão (digite "game") para que os oponentes possam conversar e fazer chamadas de voz sem ser amigos (ver Bater papo e Voz).
  • O limite de sessões simultâneas por jogador é padronizado como 20.
  • Um jogo que declara persistent mantém sessões vazias pausado em vez de acabar com eles; conectar-se a um o retoma. As sessões pausadas contam para o limite. Veja o tutorial de sessões persistentes.
  • Uma sessão ativa que ninguém está jogando é aposentado (status finished, abandonado): 5 minutos após o último ws/v1/games o soquete fecha sem que ninguém volte ou após 24 horas sem nenhuma ação do jogador. Em vez disso, as sessões persistentes são pausadas. Isso também se aplica a sessões vinculadas à sala; fechar o quarto não acaba com eles.
  • Status dos ingressos de matchmaking: queued | matched | cancelled | expired.
  • Status de convite: pending | accepted | declined | cancelled.
  • As sessões são criadas por meio de matchmaking, aceitação de convite, ponto final de IA ou início de sala em tempo real (sessões ligadas à sala - consulte Salas em tempo real) - não há "criar lobby" ponto final.
  • As atualizações do Elo vêm do script oficial (eloUpdates) ou canal de controle de contêiner, definem as classificações usadas para matchmaking e são publicadas na tabela de classificação do jogo (tipo de pontuação elo). Os clientes nunca podem enviar pontuações diretamente para uma tabela de classificação de jogo (ver Tabelas de classificação).

Jogabilidade WebSocket

ws/v1/games?sessionId={guid} (rota de versão neutra). Autenticar com o Authorization cabeçalho, ?ticket=, ou ?access_token=. Somente participantes (403); ao se conectar com um token de lançamento, seu game_scope deve corresponder ao jogo da sessão. Uma sessão concluída é 410 {"error":"session_not_active"}. Opcional ?build= é o buildId de GET /games/{slug} - incompatibilidade é 409 {"error":"build_mismatch"}.

  • Apenas quadros de texto, máximo de 16 KB por quadro.
  • Uma conexão mais recente substitui a antiga: a conexão anterior é fechada com PolicyViolation.
  • Conectando-se a uma pausa persistente session o retoma antes do seu primeiro comando. Se não puder ser retomado (normalmente um contêiner ainda em inicialização), você receberá uma mensagem error quadro e o soquete fecha com código 1001; a sessão permanece pausada – reconecte com espera.
  • Renove o token antes de cada reconexão. Um token expirado é recusado com 401 antes da atualização, que o navegador relata apenas como código fechado 1006 - indistinguível de uma queda de rede - portanto, uma falha na reconexão pode ser uma falha de autenticação e a reabertura da mesma ?access_token= O URL nunca pode ser recuperado. Renovar através POST /api/v1/games/{slug}/launch-token e reconecte-se com o novo token. A renovação funciona apenas enquanto o token atual for válido e dentro de 12 horas (padrão) após o lançamento original; uma vez recusado (401/403), pare de reconectar e envie o jogador de volta ao lançador para obter um novo token de lançamento.

Limites

O que a plataforma impõe ws/v1/games e nas classificações. Os números são os padrões da plataforma; um operador pode ajustá-los.

Mensagens ativadas ws/v1/games

Limite Valor O que acontece depois disso
Tamanho do quadro 16 KB por quadro de texto A tomada é fechada com 1009 (mensagem muito grande).
Tipo de quadro Somente texto Um quadro binário recebe um error quadro; a tomada permanece aberta.
Conexões Um por jogador por sessão Uma conexão mais recente fecha a mais antiga com 1008.

Entradas em tempo real são amostrados, não enfileirados: a plataforma mantém as últimas entradas e mãos de cada jogador o lote para o próximo do seu script onTick em ctx.inputs. Enviando mais rápido que o do seu jogo taxa de tick não ganha nada, porque as entradas entre dois ticks se fundem em um. Envie de acordo com sua taxa de tick ou quando a entrada mudar.

Comandos duráveis ​​para scripts são processados em ordem e limitados separadamente do tempo real entradas. Envie ações discretas quando elas acontecerem; enviar movimento contínuo através do tempo real marcado caminho de entrada. O limite de comando pode variar de acordo com o jogo. As invocações de script também são limitadas pelas características do jogo. orçamentos. O quadro de erro do WebSocket carrega uma mensagem, não um status HTTP. Seu script deve rejeitar comandos que não fazem sentido, como um movimento fora de hora.

Por um recipiente jogo, os comandos são retransmitidos para o seu contêiner assim que chegam, sem plataforma limite de taxa para eles. Seu servidor impõe o seu próprio. A limitação da taxa de entrada em tempo real se aplica a scripts apenas jogos.

Elo por partida

A plataforma faz não limitar o quão longe uma classificação pode se mover em uma partida. eloUpdates (roteiro) e o elo mensagem de controle (contêiner) carrega a mensagem de cada jogador nova classificação absoluta, não uma mudança, e o plataforma os aplica conforme enviados. O que ele impõe:

  • Apenas jogadores na sessão estão atualizados. Os IDs de qualquer outra pessoa e o assento da IA ​​são descartados.
  • As atualizações são aplicadas sempre que seu servidor as retorna. Uma sessão o plataforma termina (abandoned: jogadores deixados, inativos, substituídos, falha no servidor, encerrados pelo proprietário) publica não elo mudança.
  • A classificação é escrita na coluna pares de matchmaking e no tabuleiro elo do jogo como um entrada por jogador (sua classificação mais recente).
  • O dono do jogo pode redefinir a classificação de um jogador para 1200.

Portanto, o tamanho de um swing é uma decisão do seu jogo. Use um fator K padrão e fixe em seu código. O implementação de referência de xadrez usa K = 32, então um jogo move um classificação em no máximo 32 pontos:

function eloAfter(mine, theirs, score /* 1 win, 0.5 draw, 0 loss */, K = 32) {
  const expected = 1 / (1 + Math.pow(10, (theirs - mine) / 400));
  const next = mine + K * (score - expected);
  return Math.round(Math.max(100, next));      // your floor, if you want one
}

  • X-Starhermit-Event-Id — o evento (chave de idempotência; repete-se entre novas tentativas)
  • X-Starhermit-Delivery - esta tentativa

O URL deve ser https e não deve ser resolvido para um intervalo privado/loopback/CGNAT (marcado em registro e novamente antes de cada envio). Redirecionamentos não são seguidos. Endpoints com falha recuam e são desativados após falhas consecutivas; resume limpa o disjuntor.

Tempo de execução

Para jogos JavaScript, a plataforma roda onTick varreduras na taxa fixa solicitada através game.tickRateHz; 0 desativa os ticks, e um jogo que não solicita nada é marcado em 0,25Hz - declare uma taxa se sua jogabilidade depender do tick. Um contêiner conduz seu próprio loop de simulação e declara sua taxa solicitada por meio /describe; a plataforma usa essa taxa para agendamento e política de instantâneo, para não pisar no jogo. Ver Scripts de jogo – Taxa de ticks e Servidores de jogos em contêiner.

Ciclo de vida de um jogo

  1. Crie um token de lançamento — POST /api/v1/games/{slug}/launch-token. Os clientes devem atualizá-lo antes de expirar (o cliente de referência de xadrez é atualizado a cada 45 minutos).
  2. Buscar estado do jogo — GET /api/v1/games/{slug} para informações + suas estatísticas; GET .../sessions/mine para jogos em andamento; GET .../invites e GET /api/v1/realtime/rooms/invites para convites pendentes; GET .../replays/mine para a história quando replaysEnabled; GET .../achievements para a tela de conquistas.
  3. Encontre um oponente, uma das três maneiras:
    • Combinação: POST .../matchmaking, então enquete GET .../matchmaking a cada 3 s até status é matched (a resposta carrega sessionId). DELETE .../matchmaking para cancelar.
    • Fluxo de convite: escolha um amigo de GET /api/v1/me/friends (ver Amigos), POST .../invites com { "toUserId": "..." }; o convidado chama POST .../invites/{inviteId}/accept, que cria a sessão. (Se o seu jogo acomoda jogadores em um sala em tempo real primeiro, convide-os para a sala — a mesma notificação, mas aceitar os coloca na mesa em que você já está.)
    • Prática de IA: POST .../sessions/ai.
  4. Carregar a sessão — GET .../sessions/{sessionId}.
  5. Conecte o WebSocket — ws/v1/games?sessionId={guid} com o token de lançamento e, em seguida, envie qualquer comando de sincronização inicial definido pelo back-end do jogo - a implementação de referência de xadrez, por exemplo, envia {"type":"cmd","data":{"type":"sync"}}.
  6. Jogar - intercâmbio cmd/game quadros conforme definido pelo back-end, superfície achievement molduras e alça resumed descartando a previsão e solicitando um estado completo.
  7. Resultado — o backend oficial encerra o jogo; a plataforma publica atualizações elo na tabela de classificação e, para um jogo com replays, arquiva o estado final.
  8. Repetir — GET .../replays/{sessionId} para o estado final completo.

Exemplo: formas de comando de xadrez

Os seguintes formatos de carga útil são o exemplo: como o xadrez implementação de referência preenche data. Eles são definidos pelo script do xadrez, não pela plataforma - cada jogo define seu próprio conjunto de comandos e cargas úteis de transmissão em seu back-end oficial. O envelope de comando do cliente é cmd; envelopes de servidor comuns incluem game, error, presence, e achievement, com resumed/abandoned adicionalmente usado para recuperação de contêineres. O conteúdo de data são de propriedade do back-end.

Comandos do cliente (enviados como {"type":"cmd","data":{...}}):

{ "type": "move", "from": "e2", "to": "e4", "promo": "q" }
{ "type": "resign" }
{ "type": "offer-draw" }
{ "type": "accept-draw" }
{ "type": "decline-draw" }
{ "type": "sync" }

(promo é opcional em move.)
