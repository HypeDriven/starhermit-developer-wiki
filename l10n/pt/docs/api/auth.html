Autenticação

StarHermit tem sem autenticação de senha. Existem dois fluxos de login: autenticação de chave pública (Ed25519, ECDSA-P256 ou RSA-PSS, com registro verificado por e-mail) e OAuth. Todas as rotas de autenticação residem em api/v1/auth e são anônimos, exceto quando indicado. Esta página também aborda ciclos de vida de tokens, tokens de inicialização no escopo do jogo e tickets de conexão WebSocket.

Os corpos de erro variam; ver Convenções de API.

Após o login: termos atuais

O login bem-sucedido não implica permissão para usar APIs protegidas. Os titulares de contas devem aceite os termos atuais do StarHermit antes de chamadas REST protegidas ou As atualizações do WebSocket foram bem-sucedidas. Os clientes da conta podem verificar GET /api/v1/me, buscar GET /api/v1/terms, e registrar aceitação explícita com POST /api/v1/me/terms/accept. OAuth e chave pública sessões de conta suportam esse fluxo. A atualização de credenciais não resolve a aceitação pendente.

Um jogo de navegador aberto diretamente pode receber um token com escopo antes que a conta seja aceita. Se uma chamada de jogo retornar 403 com error: "terms_acceptance_required", buscar GET /api/v1/terms, exibir seu texto e oferecer uma ação Aceitar explícita. Um token de lançamento de jogador pode enviar o exibido hash para POST /api/v1/me/terms/accept; tente novamente a solicitação original após a aceitação. Não trate isso resposta como um loop de login de token expirado.

POST /api/v1/auth/public-key/register

Inicia o registro da chave pública e envia um e-mail de verificação. O registro de registro pendente expira após 4 horas. Se userId estiver definido, o e-mail deverá corresponder a essa conta. Limitado a 1 e-mail por endereço e por IP a cada 24 horas — quando limitado, a resposta é 429 com um Retry-After cabeçalho.

Quando userId estiver definido e o par não fizer check-out, a resposta será 403 com uma única mensagem independentemente de por que: uma conta desconhecida e um endereço errado respondem de forma idêntica. Este ponto final leva sem credenciais - é necessário, já que é assim que uma nova chave é anexada - então diferenciá-las seria torne-o um oráculo para o qual existam IDs de usuários e, em seguida, para seus endereços. Um chamador que possui o conta já sabe qual dos dois errou.

Solicitar:

{
  "email": "dev@example.com",
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>",
  "userId": null
}

Resposta - 202:

{
  "registrationId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "email": "dev@example.com",
  "emailSent": true,
  "deferralReason": null,
  "message": "A verification email has been sent. The key will be attached once you confirm."
}

emailSent: false significa que o e-mail está na fila para nova tentativa (deferralReason diz porquê); o registro ainda é aceito. E-mail ou material chave inválido é 400.

GET / POST /api/v1/auth/public-key/verify?token=

Abrir o link enviado por e-mail não muda nada. GET mostra uma página dizendo o que a confirmação faria - criar uma conta ou adicione uma chave à conta existente que já usa o endereço - com um Botão de confirmação. Os scanners de e-mail buscam links para visualizá-los, portanto, um link enviado por e-mail que agiu GET seria resgatado por qualquer pessoa que o escaneasse. O mesmo se aplica ao revogação e link de identidade confirmações abaixo.

POST para a mesma URL resgata: anexa a chave, criando o usuário (nome de usuário pk-<hex12>, papel User), a menos que uma conta já use esse endereço de email; nesse caso, a chave ingressa nessa conta. O e-mail está marcado como verificado. O link é de uso único e expira após 4 horas; um desconhecido, usado ou token expirado é 400, assim como um link cujo endereço não é mais o da conta — isso prova controle da caixa de entrada para a qual foi enviado, e somente enquanto esse endereço ainda for o da conta.

Quando o jogador pressiona Confirmar na página e os conjuntos de implantação PublicKeyAuth:VerificationSuccessRedirectUri - starhermit.com faz, para o painel - eles são enviado para lá com os tokens no fragmento (#access_token=…&refresh_token=…&token_type=Bearer&expires_in=900), conectado ao painel. Um o cliente nativo, portanto, não recebe esses tokens; ele entra com sua chave assim que o jogador tiver confirmado. Um cliente API que POSTo próprio URL recebe JSON:

{
  "userId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "keyId": "9b2f5c74-1d2e-4a6b-8c0d-1e2f3a4b5c6d",
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "dGhpcyBpcyBh..."
}

Login de chave pública

POST /api/v1/auth/public-key/challenge

Emite um desafio de login, válido por 5 minutos e de uso único.

A assinatura cobre a serialização do próprio servidor de payload, não o JSON que você recebeu: compacto, nomes PascalCase na ordem ChallengeId, Fingerprint, Issuer, Audience, Expiry, Nonce, ClientTimestamp, valores copiados exatamente como veiculados e cada + no nonce escrito como \u002B (as datas mantêm a sua +). Veja o exemplo trabalhado.

Solicitar:

{
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>"
}

Resposta:

{
  "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "payload": {
    "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "fingerprint": "4d9f3c...",
    "issuer": "starhermit",
    "audience": "starhermit",
    "expiry": "2026-07-22T07:24:44.1234567+00:00",
    "nonce": "NmL+tgMum6HXU/pa3T9xjQ==",
    "clientTimestamp": "2026-07-22T07:19:44.1235521+00:00"
  },
  "expiresIn": 300
}

POST /api/v1/auth/public-key/complete

Verifica a assinatura em relação a uma chave registrada e não revogada e retorna um par de tokens. Uma falha é 401: "Public key not registered or revoked." (incluindo uma chave cujo link enviado por e-mail não foi aberto ainda), "Invalid signature.", ou "Challenge not found or expired.". Desafie e complete compartilham um limite de 60 solicitações por minuto por IP (429).

Solicitar:

{
  "challengeId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "signature": "base64-signature...",
  "keyType": "Ed25519",
  "keyData": "<base64-raw-32-byte-public-key>"
}

Resposta:

{
  "userId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "dGhpcyBpcyBh..."
}

Ciclo de vida do token

POST /api/v1/auth/refresh

Atualização rotativa: o token antigo é revogado e substituído. A reutilização de um token de atualização revogado revoga toda a família de tokens.

Solicitar:

{ "refreshToken": "dGhpcyBpcyBh..." }

Resposta:

{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "bmV3IHJlZnJlc2g..."
}

Quando a atualização para de funcionar

Um token de atualização registra o estado da conta sob a qual foi emitido e a atualização o verifica. Duas respostas seu cliente deve lidar em vez de tentar novamente:

Status Significado O que o cliente deve fazer
401 A sessão foi revogada na plataforma – um "sair em todos os lugares"ou uma resposta de compromisso. Toda a família de tokens é queimada, incluindo o token que acabamos de apresentar. Descarte os dois tokens e inicie um novo login.
403 A conta é suspenso. Parar. Fazer login novamente não ajudará; o mesmo 403 retorna de todas as rotas de login até que a suspensão seja suspensa.

O 403 é deliberadamente distinto de 401, porque os dois precisam de reações opostas: um significa "autenticar novamente", o outro significa "autenticar novamente é inútil". Uma conta suspensa é recusado por todo rota de criação de credenciais - atualização, conclusão de chave pública, retorno de chamada OAuth, e tokens de lançamento de jogos – não apenas por atualização.

POST /api/v1/auth/logout

Revoga o token de atualização fornecido. Retorna 200.

{ "refreshToken": "dGhpcyBpcyBh..." }

OAuth

A plataforma envia sete provedores: google, github, discord, twitch, gitlab, linkedin, bitbucket. Somente os provedores para os quais esta implantação tem credenciais estão ativos. Um cliente não deve codifique a lista.

GET /api/v1/auth/oauth/providers

Anônimo. Retorna os provedores ativos na ordem em que devem ser oferecidos:

{
  "providers": [
    {
      "provider": "google",
      "displayName": "Google",
      "authorizeUrl": "/api/v1/auth/oauth/google/authorize",
      "linksExistingAccountsByEmail": true
    }
  ]
}

linksExistingAccountsByEmail é se um login nesse provedor pode encontrar uma conta que a pessoa já possui (a configuração de confiança da operadora para esse provedor). Pedindo para autorizar um nome que não é viver é 404, não um redirecionamento para a página de erro do próprio provedor.

GET /api/v1/auth/oauth/{provider}/authorize?link=&client=

Retorna um redirecionamento 302 para o provedor e define um oauth_state cookie (HttpOnly, SameSite=Lax, 10 minutos). link=true começa a vincular a identidade ao usuário conectado no momento; a vinculação requer autenticação recente (dentro de 5 minutos). client seleciona um redirecionamento de cliente compatível. Por um jogo aberto diretamente, use gameId e opcional returnUrl em vez de; ver Faça login em um jogo de navegador aberto diretamente.

GET /api/v1/auth/oauth/{provider}/callback?code=&state=

Para login normal na conta, retorna um redirecionamento 302 para o URL de front-end com os tokens no fragmento (o login no jogo retorna um token com escopo diretamente para o jogo, conforme descrito abaixo):

#access_token=…&refresh_token=…&token_type=Bearer&expires_in=900

Se o provedor recusar a troca de tokens, o retorno de chamada responderá 409 nomeando o erro do provedor código (a descrição permanece no log do servidor).

Um login normal encontra ou cria o usuário (nome de usuário oauth-{provider}-{guid}, papel User) e o novos registros de sessão auth_method=oauth. Um login cujo (provider, providerUserId) é desconhecido é adotado em uma conta existente somente quando a afirmação do provedor é confiável, exatamente um a conta já contém esse e-mail verificado e essa conta ainda não tem identidade deste provedor. Qualquer outra coisa provisiona uma conta separada. A adoção envia um e-mail para a conta nomeando o provedor.

Isso é importante porque apenas uma sessão autenticada por OAuth pode realizar alterações de credenciais de alto impacto:

  • adicionar ou revogar chaves públicas da conta;
  • alterar o e-mail da conta;
  • remover uma identidade gerenciada pelo OAuth.

Os tokens com escopo de jogo nunca podem realizar essas operações. Um token de atualização mantém o original método de autenticação da sessão, portanto, atualizar uma sessão OAuth não remove esse recurso e atualizar uma sessão de chave pública não a adiciona.

Quando link=true, o retorno de chamada não promove automaticamente a sessão apenas porque ela visitou um provedor OAuth. Um link iniciado em uma sessão OAuth é anexado imediatamente. Um link começou em uma sessão de chave pública, verificação de e-mail ou herdada é mantida até que o proprietário da conta abra o confirmação enviada para o e-mail verificado da conta; os relatórios de fragmentos de redirecionamento link=pending_email_confirmation. O e-mail único é aberto GET /api/v1/auth/oauth/link/confirm?token=…, uma página com o nome da conta do provedor que não altera nada; seu botão Confirmar POSTé o mesmo URL, que cria a identidade ({ "provider", "linked": true } para um cliente API). Um link cujo endereço não é mais a conta é recusada. Isto evita que uma chave pública roubada ligue o conta do provedor do invasor e transformando isso em um login OAuth permanente.

Armazenamentos de metadados de identidade do GitHub {"login":"…"} — isto é usado para verificações de propriedade de repositório em Jogos GitHub.

Chaves públicas registradas em OAuth para automação

Uma sessão OAuth pode chamar POST /api/v1/me/public-keys anexar imediatamente uma chave de máquina etiquetada. Mais tarde, a CI assina o desafio normal de chave pública e usa seu token de acesso de curta duração para carregar um pacote de jogo próprio; a chave privada nunca sai do armazenamento secreto do CI. Ver o tutorial de upload de build de CI/CD para configuração, um auxiliar de assinatura e um fluxo de trabalho do GitHub Actions.

Fichas

  • Token de acesso — JWT, vida útil de 15 minutos (expires_in=900). As reivindicações incluem sub (o ID do usuário) mais permission e reivindicações de função. A revogação entra em vigor imediatamente.
  • Atualizar token — Um token rotativo opaco com vida útil de 7 dias. Cada atualização emite um novo token de atualização e revoga o antigo; reutilizar um token revogado revoga toda a família de tokens.

Faça login em um jogo de navegador aberto diretamente

Um jogo hospedado aberto fora do painel pode mostrar um Entrar botão com link para:

https://api.starhermit.com/api/v1/auth/games/{gameId}/sign-in

gameId é o UUID imutável do jogo (o subdomínio em {gameId}.starhermit.com). Eremita Estelar mostra seus provedores de login habilitados. Continuar assina um jogador existente ou cria um novo conta usando as regras normais de correspondência de conta do OAuth e, em seguida, redireciona direto de volta para o jogo, sem visitar o painel.

O opcional returnUrl preserva uma página específica do jogo, string de consulta ou rota hash. Deve ser um URL HTTPS absoluto exatamente na origem hospedada do jogo; outros jogos, hosts externos, credenciais na URL e portas alternativas são rejeitadas com 400. Omita-o para retornar ao arquivo de lançamento publicado. Jogos desconhecidos, removidos, não hospedados ou nunca publicados retornam 404. Ambos implantações de repositório e jogos carregados são suportados; URLs externos/locais arbitrários não são.

Navegue no navegador até o origem da API pública acima, em vez de buscar a página ou iniciar através do jogo /api procuração. O cookie de estado OAuth e o retorno de chamada do provedor devem usar o mesmo Anfitrião de API. Use este fluxo quando o jogo não tiver um token válido fornecido pelo inicializador ou obtido anteriormente.

Exemplo de botão e token de retorno

<button id="starhermit-sign-in">Sign in</button>
<script type="module">
const api = 'https://api.starhermit.com';
const gameId = 'YOUR_GAME_UID';
const signIn = document.querySelector('#starhermit-sign-in');
let gameToken = null; // Or your existing launcher-provided game token.

// Read this before your game router or third-party scripts consume the fragment.
const auth = new URLSearchParams(location.hash.slice(1));
if (auth.has('access_token')) {
  gameToken = auth.get('access_token');
  const originalHash = auth.get('game_fragment');
  history.replaceState(null, '', location.pathname + location.search +
    (originalHash ? '#' + originalHash : ''));
}
signIn.hidden = Boolean(gameToken);
signIn.addEventListener('click', () => {
  const url = new URL(`/api/v1/auth/games/${gameId}/sign-in`, api);
  url.searchParams.set('returnUrl', location.href);
  location.assign(url.href);
});

// Pass gameToken to your game's API client as Authorization: Bearer <gameToken>.
// This example keeps it in memory; a reload can require sign-in again.
</script>

O fragmento de retorno é:

#access_token=…&token_type=Bearer&expires_in=3600

access_token é um token de lançamento no escopo do jogo, não um token de acesso para toda a conta. Nenhum token de atualização é emitido. expires_in usa o tempo de vida do token de inicialização configurado da implantação (padrão 3600 segundos). Um fragmento de URL de retorno original é codificado no formato opcional game_fragment campo; restaure-o após capturar o token e remover os dados de autenticação do histórico do navegador. Não registre ou encaminhe o token.

Renove antes de expirar usando POST /api/v1/games/{gameId}/launch-token com o token atual como Autorização do portador e, em seguida, substitua-a pela retornada token. O teto habitual da cadeia de renovação aplica-se (padrão 12 horas). Se o token expirar ou a renovação for recusada, limpe-o e mostre Entrar novamente. Ver Tokens de lançamento de jogo.

Escolhendo você mesmo um provedor

Em vez disso, os jogos podem ler GET /api/v1/auth/oauth/providers e navegue até um oferecido authorizeUrl na origem da API pública, adicionando gameId e opcionalmente returnUrl. A etapa de autorização valida e armazena o destino no estado OAuth existente de dez minutos; parâmetros de consulta de retorno de chamada não posso mudar isso. O cookie do navegador inicial ainda é necessário e o jogo é verificado novamente antes de emitir um token. Contas suspensas não podem receber token.

Não combine login no jogo com client ou link (400). A returnUrl sem gameId também é 400. O login normal no painel e na área de trabalho continua usando seus destinos de front-end configurados e pares de tokens de conta comuns.

Tokens de lançamento de jogo

POST /api/v1/games/{slug}/launch-token (JWT) cria um JWT com escopo de jogo:

{
  "token": "eyJhbGciOi...",
  "expiresInSeconds": 3600
}

O token carrega um game_scope reivindicação e o padrão é uma vida útil de 60 minutos. A renovação copia um launch_chain hora de início adiantada; a renovação das últimas 12 horas (padrão) é 403 e o titular deve ir de volta a uma sessão completa da conta. Detalhes completos estão em Jogos.

Reconectando soquetes. Um soquete aberto com um token de lançamento (?access_token= sobre ws/v1/games, ws/v1/realtime, ws/v1/voice) carrega esse token em sua URL e um handshake com um token expirado é recusado com 401 antes da atualização — o navegador reporta apenas código fechado 1006, o mesmo que um queda de rede. Trate uma falha na reconexão como possivelmente uma falha de autenticação: antes de reabrir, renove através POST /api/v1/games/{slug}/launch-token (possível apenas enquanto o token atual ainda for válido e dentro de 12 horas após o lançamento original) e crie a URL com o novo token. Assim que a renovação for recusado, envie o jogador de volta ao inicializador, ou através login no jogo se foi assim que o jogo foi aberto. Tentar novamente o mesmo URL nunca poderá ser recuperado.

Esgrima de escopo de jogo

Um token com escopo de jogo só pode alcançar:

  • próprio /api/v1/games/{scope} árvore,
  • /ws/v1/games,
  • sala em tempo real Rotas REST e /ws/v1/realtime para seu próprio jogo, incluindo ingressos de conexão,
  • GET /api/v1/time e GET /api/v1/terms,
  • POST /api/v1/me/terms/accept para o consentimento explícito do jogador autenticado,
  • GET /api/v1/me/friends,
  • GET /api/v1/users/{id}/avatar e GET /api/v1/users/{id}/profile,
  • a tabela de classificação do seu jogo,
  • o jogador salvar na nuvem para seu próprio jogo (/api/v1/me/cloud-saves/game:<scope> e seu /info) - nenhuma outra chave,
  • os endpoints REST e WebSocket de bate-papo/voz anexados às suas próprias sessões de jogo,
  • GET /api/v1/github-games/{id}/icon e /cover para qualquer jogo (ambos são públicos de qualquer maneira),
  • POST /api/v1/me/heartbeat, que marca apenas o jogador online,
  • GET /api/v1/github-games/{id}/release-notes para seu próprio jogo,
  • relé rotas, para revezamentos vinculados a uma de suas próprias sessões ou salas de jogo.

/ws/v1/chat está bloqueado para tokens de lançamento. Todo o resto retorna 403.

Fluxo de login típico (curl)

Login com chave pública, do desafio à chamada autenticada:

# 1. Request a challenge
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/challenge \
  -H "Content-Type: application/json" \
  -d '{"keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "challengeId": "...", "payload": { ... }, "expiresIn": 300 }

# 2. Sign the serialized payload JSON with your private key, then complete
curl -s -X POST https://api.starhermit.com/api/v1/auth/public-key/complete \
  -H "Content-Type: application/json" \
  -d '{"challengeId":"...","signature":"base64-signature...","keyType":"Ed25519","keyData":"<base64-raw-32-byte-public-key>"}'
# → { "userId": "...", "accessToken": "...", "refreshToken": "..." }

# 3. Call the API with the access token
curl -s https://api.starhermit.com/api/v1/me \
  -H "Authorization: Bearer eyJhbGciOi..."

# 4. When the access token expires (after 15 min), rotate the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

# 5. On logout, revoke the refresh token
curl -s -X POST https://api.starhermit.com/api/v1/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refreshToken":"dGhpcyBpcyBh..."}'

O login do OAuth é orientado pelo navegador: leia GET /api/v1/auth/oauth/providers, abra um provedor ativo authorizeUrl, consentimento completo e o retorno de chamada leva o usuário ao front-end com #access_token=…&refresh_token=… no fragmento de URL.

Revogação de chave enviada por e-mail

Para um proprietário que não consegue alcançar DELETE /me/public-keys (sem sessão OAuth ou bloqueado por um roubo chave). POST /api/v1/auth/public-key/revoke-request com { "email": "…" } detém um pedido e e-mail com um link. Abrindo (GET /api/v1/auth/public-key/revoke/confirm?token=…) mostra uma página que não muda nada; seu botão Confirmar POSTé o mesmo URL, que revoga todo chave ativa nisso conta e encerra as sessões que autenticaram. Ambos não são autenticados e questão não sessão. O pedido sempre responde 202 com o mesmo corpo, seja o que for que encontre; um pedido por conta a cada 15 minutos e o link expira após 4 horas. A confirmação POST respostas 200 { "revoked": <count>, "sessionsEnded": <count> } para um cliente API ou 400 para um desconhecido, usado ou token expirado ou cujo endereço não seja mais o da conta.

Bilhetes de conexão WebSocket

POST /api/v1/realtime/connection-tickets troca o token do portador do chamador por um ticket único válido por cerca de 30 segundos. Passe como ?ticket= em qualquer /ws/v1/* aperto de mão. Ele carrega o chamador afirma textualmente (incluindo game_scope e pk), é recusado no REST e gasto no primeiro uso. Qualquer chamador autenticado pode perguntar, incluindo um token de lançamento no escopo do jogo. ?access_token= ainda funciona até que os clientes se mudem.

Um soquete aberto termina quando sua credencial é revogada. A revogação da chave pública que a abriu termina imediatamente; uma suspensão ou saída em qualquer lugar encerra em cerca de 30 segundos. Expiração do token não encerra um soquete aberto — atualize antes de reconectar.

Integração incorporada para jogos nativos/de loja

Um cliente Steam, Epic, GOG ou independente pode gerar uma chave no dispositivo do jogador e apresentar o fluxo de registro de chave pública dentro de sua própria UI, evitando OAuth e uma visita ao StarHermit painel. O registro não é silencioso: o jogador deve consentir, fornecer um e-mail e seguir as link de verificação único. Um token de servidor de jogo não pode criar ou representar jogadores. Ver Tutorial: jogadores integrados com chave pública, e o tutorial de servidor dedicado para um jogo que também vem com um servidor.
