Scripts de jogos

Um jogo oficial StarHermit pode ser definido por um único arquivo JavaScript executado no lado do servidor em um sandbox Jint motor. O script é a única autoridade nas regras do jogo: ele valida cada comando do jogador, altera o estado, decide o que cada cliente pode ver, calcula Elo e encerra os jogos. Os clientes têm autoridade zero. Esta página documenta o tempo de execução do JavaScript; jogos que precisam de outra linguagem podem, em vez disso, implementar o Servidor de jogos de contêiner protocolo. Ambos usam o mesmo player voltado para o jogador API de jogos. O exemplo trabalhado é o xadrez - a implementação de referência em HypeDriven/starhermit-chess.

Modelo de execução

  • Um arquivo JS por jogo, executado em um novo mecanismo Jint em sandbox por invocação. Nada persiste na memória entre as chamadas – todo o estado reside nos documentos que você retorna.
  • Sem ambiente Date ou Math.random. Tempo e aleatoriedade são fornecidos como: ctx.now (época ms) e ctx.random (flutuar em [0, 1)).
  • A plataforma invoca o script quando um jogador envia um comando durável, quando uma sessão é criada e periodicamente. onTick varreduras (ver API de jogos – tempo de execução). Em tempo real {type:"input", realtime:true} os frames são a exceção: eles são as últimas vitórias armazenadas em buffer e entregues em lote para o próximo tick.

Pontos de entrada

Exponha os manipuladores em globalThis.game. Seis opcionais estático declarações ficam ao lado deles: tickRateHz pergunta à plataforma com que frequência invocar onTick — declare se o seu jogo depende do tick, já que um jogo que não diz nada é marcado uma vez a cada quatro segundos (veja Taxa de tick), achievements registra as conquistas do jogo (veja Conquistas), replays pede à plataforma para manter suas sessões concluídas (veja Repetições), persistent pausas sessões em vez de encerrá-las quando todos saírem (veja Sessões persistentes), linkedAchievements nomeia outros jogos cujos desbloqueios você recebe em ctx.linkedAchievements (ver Conquistas de outros jogos), e queues declara as formas de matchmaking aceitas (veja Jogos – Matchmaking). Um jogo que não declara nenhuma fila tem um 1v1 implícito:

globalThis.game = {
  tickRateHz: 0, // turn-based: opt out of periodic ticks
  replays: true, // keep finished sessions as replays
  queues: [{ key: "duos", teams: 2, teamSize: 2 }],
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 }
  ],
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};

As declarações são lidas avaliando seu script quando o jogo é publicado ou atualizado, não em todas as invocações - portanto, devem ser valores estáticos no game objeto. Publicar uma atualização para aplicar uma alteração.

  • createSession(ctx) — chamado quando uma sessão é criada (matchmaking, aceitação de convite, prática de IA ou início de sala em tempo real — consulte Sessões vinculadas à sala).
  • onPlayerMessage(ctx) - chamado para comandos de cliente duráveis ​​recebidos pelo WebSocket de jogo. Entradas marcadas explicitamente realtime:true ignorar este ponto de entrada.
  • onMembershipChange(ctx) - opcional. Chamado quando um jogador entra ou sai de uma sessão em execução (um sala de participação em andamento, ou um convidar para um jogo em andamento). ctx.players já reflete a mudança, e ctx.membership é { change: "joined" | "left", userId, name, team, slot }. Retornar { ok: false } recusar uma adesão; um script sem esse gancho recusa todas as junções. Uma licença é definitiva, independentemente do retorno. Conquistas e pontuações podem influenciar o resultado; um sessionState é ignorado.
  • onTick(ctx) — chamado pelo serviço de temporizador da plataforma à taxa efetiva de ticks; as últimas entradas em tempo real estão disponíveis em ctx.inputs. Um jogo com resolução de 0 Hz não recebe chamadas periódicas, mas a função ainda deve estar presente para satisfazer o contrato do script.

Objeto de contexto

ctx = {
  now: 1721473200000,              // ms epoch, from the host clock
  random: 0.7231,                  // float in [0, 1), from the host RNG
  sessionId: "0f8fad5b-...",       // current session id
  pausedMs: 0,                     // persistent games only: total ms this session has spent paused
  players: [                       // session participants
    { id: "7c9e6679-...", name: "alice", elo: 1312 },
    { id: "00000000-0000-4000-8000-00000000a1a1", name: "The House", ai: true, elo: 1200 }
  ],
  sessionState: { /* ... */ },     // this script's session document, or null
  playerStates: {                  // per-player documents (elo, history), or null
    "7c9e6679-...": { elo: 1200, wins: 4, losses: 2, draws: 1, /* ... */ }
  },
  message: {                       // onPlayerMessage only
    from: "7c9e6679-...",          // the authenticated user id — trusted
    data: { type: "move", from: "e2", to: "e4" }  // client payload — untrusted (example: a chess move)
  },
  inputs: [                        // onTick only; omitted when none are pending
    { from: "7c9e6679-...",        // authenticated sender id — trusted
      data: { type: "input", seq: 42, mx: 0.7, mz: -0.2 } }
  ]
}
  • O assento AI (se presente) é sinalizado com ai: true na entrada do jogador.
  • Cada entrada de jogador carrega elo, sua classificação atual para este jogo – o mesmo número armazenado em playerStates[id].elo, apareceu na lista para que um jogo contêiner (que não pode ler o somente script playerStates) pode gerar lógica de correspondência a partir dele. Um jogador sem classificação ainda lê 1200. É idêntico em criar, marcar, enviar mensagem e restaurar; alterar uma classificação apenas através eloUpdates.
  • Um jogo que declara linkedAchievements também recebe ctx.linkedAchievements: { <playerId>: { <otherSlug>: [unlocked keys] } }, releia a cada invocação. Ver Conquistas de outros jogos.
  • Sessões vinculadas à sala (iniciadas em uma sala em tempo real) recebem dois campos ctx adicionais, ctx.room e ctx.presence, sobre todo invocação - veja Sessões vinculadas à sala.
  • Não confie em nada ctx.message.data ou ctx.inputs[].data. A identidade confiável é a correspondente from, que o servidor conecta a partir da conexão autenticada — o cliente nunca poderá fornecê-la ou falsificá-la.
  • As entradas aceitam lote com {type:"input", realtime:true, ...}. Não marcado input os comandos permanecem duráveis onPlayerMessage exige compatibilidade com versões anteriores. As entradas em tempo real usam um slot pendente por remetente: o movimento é o mais recente, enquanto pass, shoot, e tackle as bordas da ação são mescladas para que uma amostra de movimento seguinte não possa apagá-las antes do próximo tick. Os scripts devem restringir e validar cada valor ao consumir o lote.

Taxa de tick

A plataforma funciona onTick varreduras por sessão ativa a uma taxa configurável. Seu script pede a taxa que deseja declarando uma estática tickRateHz no objeto do jogo, junto com os pontos de entrada:

globalThis.game = {
  tickRateHz: 15,          // ask the platform to tick this game 15x/second
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • A declaração é lida quando seu jogo for publicado ou atualizado, não em todos os ticks. Publique uma atualização após alterá-la.
  • Um jogo que declara nenhuma taxa é marcado em 0,25 Hz - uma vez a cada quatro segundos. Isso é bastante para julgar um relógio de movimento ou um tempo limite e não custa quase nada à plataforma, mas é muito lento para qualquer coisa de que sua jogabilidade dependa. Se onTick impulsiona seu jogo, declare a taxa que você precisa.
  • As solicitações são limitadas ao máximo da plataforma (30Hz por padrão), então um jogo pode pedir menos do que a plataforma permite, mas nunca mais. Pedir 0 desabilitar completamente os ticks de um jogo que apenas reage aos comandos do jogador.
  • As taxas podem ser fracionário: 0.5 é um tique a cada dois segundos. A menor taxa diferente de zero é 0.01 Hz — um número positivo menor é elevado a ele, em vez de ser lido como uma opção de exclusão, porque um pequena fração é um jogo lento. O tique-taque está desativado apenas para 0 ou uma taxa negativa. Uma falta ou declaração inutilizável (uma string, null, NaN) assume o padrão de 0,25 Hz.
  • Um operador pode substituir a taxa de um jogo específico, em qualquer direção.
  • As entradas em tempo real são as últimas vitórias entre os ticks, enquanto as bordas de ação discreta permanecem ordenadas. Um destinatário lento pode pular um instantâneo obsoleto, mas não pode atrasar a simulação ou outros destinatários.

Repetições

Quando uma sessão termina, a plataforma pode manter o seu final sessionState como o repetir - o documento entregue por GET /api/v1/games/{slug}/replays/{sessionId} (ver API de jogos – replays). Um replay é armazenado enquanto o registro da partida é, então seu jogo só ganha um se pedir:

globalThis.game = {
  replays: true,           // keep finished sessions as replays
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • A declaração deve ser literal true ou false - qualquer outra coisa é lida como nenhuma declaração, e um jogo que não declara nada não tem replays.
  • É lido quando seu jogo for publicado ou atualizado. Publique uma atualização após alterá-la.
  • Um operador de plataforma pode responder por um jogo específico de qualquer maneira, então a declaração é uma solicitação em vez de uma garantia. GET /api/v1/games/{slug} relata a resposta como replaysEnabled - ramifique sua interface de reprodução nisso, não no que seu script solicitou.
  • Nada mais muda com os replays desativados: o estado da sua sessão ainda é armazenado e devolvido ao cada invocação como ctx.sessionState, e ainda é o ponto de restauração da falha. Que jogo sem replays não obtém é uma cópia que sobrevive à sessão, então seus pontos finais de replay respondem 404.
  • Projete o final sessionState vale a pena repetir - um registro de movimentação ou o que seu cliente precisar para reconstruir a partida. A implementação de referência de xadrez mantém state.game.moves e dá um passo através do mesmo módulo de regras que a plataforma executa.

Sessões persistentes

Um jogo que declara persistent: true mantém suas sessões quando todos os jogadores saem. Cerca de 15 segundos após a última desconexão, a sessão é pausado - não onTick chamadas - e o primeiro jogador para reconectar o retoma. A desconexão ou inatividade pausa a sessão em vez de abandoná-la. Um resultado de jogo, dono ação, licença explícita do membro final, expiração da retenção configurada ou falha na recuperação do terminal podem ainda acabar com isso. Ver Ciclo de vida da sessão.

globalThis.game = {
  persistent: true,        // pause empty sessions instead of ending them
  createSession(ctx) { /* ... */ },
  onPlayerMessage(ctx) { /* ... */ },
  onTick(ctx) { /* ... */ }
};
  • Deve ser literal true ou false. É lido quando seu jogo for publicado ou atualizado.
  • ctx.now fica o relógio de parede. Sessões persistentes também recebem ctx.pausedMs, o tempo total gasto pausado, então ctx.now - ctx.pausedMs é um relógio que fica parado enquanto não há ninguém.
  • Sessões pausadas contam para o limite de sessão por jogador, então dê aos jogadores um comando que encerre um mundo com um result.

Veja o tutorial de sessões persistentes para um exemplo resolvido e o fluxo do cliente.

Layout de assento matchmaking

Novas sessões combinadas recebem ctx.matchmaking sobre todo invocação (criar, comandar e marcar). Ele preserva o formato da fila e os assentos mesmo se o jogo for reimplantado posteriormente:

ctx.matchmaking = {
  queue: "ffa", teams: 4, teamSize: 1,
  seats: [
    { id: "human-uuid", name: "Alice", team: 0, slot: 0, ai: false },
    { id: "synthetic-ai-uuid", name: "AI 2-1", team: 1, slot: 0, ai: true },
    { id: null, name: null, team: 2, slot: 0, ai: false },
    { id: null, name: null, team: 3, slot: 0, ai: false }
  ]
};

ctx.players contém apenas assentos ocupados, com team e ai:true para IA. Os índices de equipe/slot são baseado em zero. Os IDs AI são estáveis ​​nesta sessão e não são IDs de conta StarHermit. Apenas humanos ter associação de sessão/bate-papo e pode receber informações sobre o estado do jogador, classificação ou conquistas da conta. Mantenha o estado da IA ​​em sessionState. Copie quaisquer campos de escalação que os clientes precisem para o estado do seu jogo ou transmissões. Sessões mais antigas e sessões sem matchmaking podem ser omitidas ctx.matchmaking.

Declare um prazo de início e a contagem máxima de IA em starhermit.txt. Com contagem de IA 0, os assentos vagos permanecem vazios. O mesmo contexto é entregue aos servidores de contêiner.

Sessões vinculadas à sala

Uma sessão pode ser vinculado a uma sala em tempo real: quando um sala em tempo real para um jogo com server= script é iniciado, a plataforma cria uma sessão de N jogadores para a sala humano participantes (as vagas de IA existem apenas na lista voltada para o script). É assim que os jogos em tempo real autorizados pelo servidor (por exemplo, futebol) são executados: as salas fornecem o lobby/matchmaking, o script executa a partida. Ver Salas em tempo real – a ponte para o ciclo de vida do lado da sala.

Cada invocação (createSession, onPlayerMessage, onTick) de uma sessão vinculada à sala recebe dois campos ctx extras:

ctx.room = {
  roomId: "0f8fad5b-...",
  metadata: { /* ... */ },        // the room's opaque config.metadata blob
  roster: [                       // frozen match roster, humans AND AI seats,
    { userId: "7c9e6679-...",     //   ordered by team then slot
      name: "alice", team: 0, slot: 0, ai: false },
    { userId: null,               // AI seat — never a session player
      name: "Rafa Vento", team: 0, slot: 1, ai: true }
  ]
};
ctx.presence = {                  // every user who is or was a human participant
  "7c9e6679-...": { online: true, left: false }
};
  • presence.online — o usuário tem um soquete ativo em qualquer registro de conexão (salas em tempo real ou ws/v1/games).
  • presence.left — o usuário não possui mais um assento ativo: ele saiu explicitamente e seu assento foi convertido em participante de IA. left é permanente; online pode bater. Espera-se que o script conduza a lógica de controle/reintegração da IA ​​a partir desses sinalizadores.
  • A lista é relida a cada invocação, de modo que as conversões de assento (humano → IA) aparecem conforme acontecem.

Quando um script vinculado à sala retorna result, a plataforma encerra a sessão, armazena o resultado na sala e fecha a sala — nenhum resultado enviado pelo host está envolvido.

O inverso não é verdade: o fechamento de uma sala não encerra sua sessão. Se a sala fechar primeiro (por exemplo, porque seu último humano saiu de uma sala sem ingresso em andamento - nunca apenas porque o host ficou offline, o que apenas move a função de host enquanto a sessão está ativa), a sessão continua em execução, ctx.room.roster fica vazio e todo ser humano mostra left: true. Retornar result então se a partida terminar com a sala. Ver Salas em tempo real – a regra do host de 60 segundos e sessões vinculadas à sala.

Forma de retorno

Cada ponto de entrada retorna a mesma forma (todos os campos são opcionais, exceto ok):

return {
  ok: true,                        // false on failure
  error: "Illegal move",           // goes only to the sender (as a WS "error" frame)
  sessionState: { /* ... */ },     // REPLACES the stored session document
  playerStates: {                  // REPLACES stored per-player documents
    "7c9e6679-...": { elo: 1216, /* ... */ }
  },
  broadcast: [                     // only these messages ever reach clients
    { to: "all", data: { type: "moved", /* ... */ } },
    { to: ["9b2f8c1a-..."], data: { type: "state", /* ... */ } }
  ],
  eloUpdates: {                    // published to the game's leaderboard by the host
    "7c9e6679-...": 1216,
    "9b2f8c1a-...": 1184
  },
  achievements: {                  // server-authoritative unlocks, by player id
    "7c9e6679-...": ["first-win", "flawless"]
  },
  scores: {                        // to your game's own leaderboards, by board key
    "high-score": { "7c9e6679-...": 4200 }
  },
  result: { kind: "white-win", reason: "checkmate" }  // ends the session (example: a chess result)
};

Regras principais:

  • sessionState e cada entrada de playerStates substituir os documentos armazenados — retorne sempre documentos completos, nunca diferenças.
  • Somente mensagens listadas em broadcast são entregues aos clientes, cada um endereçado a IDs de jogadores explícitos ou "all". Nada mais vaza.
  • eloUpdates é a única maneira de as classificações mudarem. Os valores são de cada jogador nova classificação absoluta, aplicado conforme enviado — a plataforma não limita a alteração por partida, então fixe você mesmo (veja Elo por partida). O anfitrião os utiliza para matchmaking e os publica na tabela de classificação do jogo; os clientes nunca podem enviar pontuações diretamente (consulte Tabelas de classificação). Mantenha a classificação em playerStates[id].elo então um proprietário redefinição de classificação chega à sua cópia também.
  • achievements é a única maneira de as conquistas serem concedidas. As chaves são resolvidas de acordo com as conquistas do jogo – declaradas ou criadas por seu proprietário – e persistidas pela plataforma; ver Conquistas.
  • scores é a única maneira de mudar as tabelas de classificação do seu jogo - veja Tabelas de classificação.
  • Terminar jogos via result. O anfitrião então termina a sessão, e para um jogo com replays arquiva o final sessionState como o replay (servido por GET .../replays/{sessionId} - ver API de jogos).

Conquistas

Seu roteiro é o apenas coisa que pode desbloquear as conquistas do seu jogo. Não há cliente ponto final para eles: POST /api/v1/me/achievements/unlock rejeita completamente as conquistas no escopo do jogo, e os endpoints CRUD do editor se recusam a tocá-los. O proprietário do jogo pode adicionar conquistas ao lado os declarados através /me/github-games/{id}/achievements; seu script os desbloqueia por chave exatamente da mesma maneira. Isso faz com que as conquistas do servidor autoritário como o resto do jogo, e é o mecanismo qualquer jogo com um server= roteiro deveria usar - incluindo aquele cuja jogabilidade é executada em outro lugar (veja quais jogos podem usar isso).

Declarar

Uma estática achievements matriz no game objeto. Apenas key é necessário:

globalThis.game = {
  achievements: [
    { key: "first-win", name: "First Win", description: "Win a match.", points: 10 },
    { key: "flawless",  name: "Flawless",  description: "Win without conceding.",
      points: 50, secret: true, icon: "https://cdn.example/flawless.png" }
  ],
  // ...entry points
};
Campo Tipo Notas
key corda Obrigatório. ID estável, ≤ 128 caracteres, único no jogo. Duplicatas após a primeira são ignoradas.
name corda O padrão é key.
description corda O padrão é "".
icon corda URL opcional.
secret booleano Escondido de um jogador até eles desbloqueá-lo. O padrão é false.
points número Fixado em 0–10000. O padrão é 0.

A matriz é aplicada quando o jogo é publicado ou atualizado:

  • As definições são correspondidas por key — editar um nome, ícone, pontos ou bandeira secreta atualiza a definição existente e todos que já a conquistaram a mantêm.
  • Uma chave que você para de declarar é excluída somente enquanto ninguém o desbloqueou. O histórico ganho nunca é destruído, então uma conquista retirada permanece visível para os jogadores que a possuem.
  • No máximo 100 conquistas por jogo; extras além disso são descartados.
  • A declaração é melhor esforço: entradas malformadas são ignoradas. Sempre confirme as definições publicadas com GET /api/v1/games/{slug}/achievements depois de atualizar o jogo.

Desbloquear

Retornar um achievements mapa de qualquer ponto de entrada - createSession, onPlayerMessage, ou onTick:

onTick(ctx) {
  const state = JSON.parse(JSON.stringify(ctx.sessionState));
  const unlocks = {};
  for (const p of ctx.players) {
    if (!p.ai && state.scores[p.id] >= 10) unlocks[p.id] = ["ten-points"];
  }
  return { ok: true, sessionState: state, achievements: unlocks };
}
  • Os desbloqueios são idempotente - reafirmar uma chave que o jogador já possui não é operacional, portanto, um script pode conceder com segurança a partir de uma condição que ele reavalia a cada tick, em vez de rastrear "já premiado" em seu próprio estado.
  • Chaves desconhecidas (nem declaradas nem criadas pelo proprietário do jogo), usuários que não são participantes desta sessão e o assento da IA ​​são ignorados silenciosamente.
  • No máximo 32 as chaves são aceitas por jogador por invocação; outras chaves na mesma matriz são descartadas.
  • As linhas são persistidas com o restante das gravações da invocação, portanto, um desbloqueio não pode sobreviver a uma invocação com falha.

Entrega

Cada desbloqueio recém-concedido é enviado ao jogador ganhador ws/v1/games como uma moldura distinta - é a verdade da plataforma, não uma de suas broadcast mensagens:

{ "type": "achievement",
  "data": { "key": "first-win", "name": "First Win", "description": "Win a match.",
            "icon": null, "points": 10, "unlockedAt": "2026-07-25T09:14:02Z" } }

Desbloqueios concedidos de createSession pousam antes de existir qualquer soquete, então eles chegam sem moldura - os clientes devem ler GET /api/v1/games/{slug}/achievements sob carga e trate o quadro como o caminho de atualização ao vivo. Superfície completa em Conquistas.

Tabelas de classificação

Além do tabuleiro elo, seu jogo pode ter tabelas de classificação criadas pelo proprietário por meio de POST /api/v1/me/github-games/{id}/leaderboards, cada um com um key. Poste para eles retornando scores de qualquer ponto de entrada - chave do tabuleiro → ID do jogador → número:

onPlayerMessage(ctx) {
  var s = ctx.sessionState;
  if (ctx.message.data.type === "finish-run") {
    var scores = { "high-score": {}, "fastest-run": {} };
    scores["high-score"][ctx.message.from] = s.points[ctx.message.from];
    scores["fastest-run"][ctx.message.from] = ctx.now - s.startedAt;   // a time-ms board
    return { ok: true, sessionState: s, scores: scores };
  }
  /* ... */
}
  • Cada jogador mantém seu melhor pontuação em cada tabuleiro, de acordo com a direção de classificação do tabuleiro, então informe cada resultado – um pior é simplesmente ignorado.
  • Apenas os participantes da sessão contam. Chaves desconhecidas ou inativas e pontuações fora das regras do tabuleiro, são descartados silenciosamente. No máximo 16 pranchas por retorno.
  • Diferente eloUpdates, nada é publicado playerStates - mantenha sua própria cópia em playerStates se o jogo precisar ler um recorde pessoal.

Onde seu script é executado

Um script que recorre sem limite, esgota sua memória ou excede seu orçamento de tempo falha no invocação. Seu resultado com falha não é aplicado. O comando ou tick relata um dos seguintes:

  • Game script error: the script crashed its runtime (for example, by recursing without limit).
  • Game script error: the script exceeded its memory budget.
  • Game script error: the script exceeded its time budget.

A participação do seu jogo no servidor

  • Hora do roteiro. Todas as sessões de um jogo compartilham um orçamento de tempo de script, 2.000 ms por segundo por padrão, cobrado com o que cada invocação realmente levou. Um jogo acima da sua parte é recusado em vez do que na fila: um tique é ignorado, um comando é respondido com "Este jogo está usando mais do que deveria do servidor agora; tente novamente em breve.", e a criação de uma sessão retorna 429.
  • Comandos. Cada jogador pode enviar 20 comandos duráveis por segundo por sessão (com uma sequência curta subsídio); além disso, um comando é respondido com um error quadro, "Muitos comandos; desacelerar." O quadro não inclui um status HTTP. A entrada em tempo real é limitada separadamente.
  • Resultados. O resultado com o qual uma sessão termina pode ter no máximo 64 KB; um maior é recusado com 422.
  • Tamanho do roteiro. A server= o script pode ter no máximo 2 MB; um maior é recusado com 422 antes ele é armazenado ou analisado.

Os operadores podem aumentar ou diminuir cada um deles para um jogo individual.

Orçamentos

Os scripts são executados sob estes orçamentos de recursos:

  • ~250 ms de CPU por invocação
  • 32 MB de memória
  • Um limite de instrução por invocação
  • Um orçamento de bytes de estado por jogador – todos os documentos de estado devem permanecer serializáveis ​​e pequenos
  • Os valores se aninham no máximo em 64 níveis de profundidade quando se tornam texto. Qualquer coisa que um ponto de entrada retorne, a cada declaração, JSON.stringify, e Array.prototype.join/toString/toLocaleString recusar um valor mais profundo com um RangeError (um retornado falha na invocação: "aninhado mais de 64 níveis profundo"). JSON.parse já parou em 64, então um valor mais profundo nunca poderia ser ida e volta. flat nivela até 64 níveis e é lançado se o array se aninhar mais profundamente - incluindo um array que contém em si.
  • Uma chamada não pode alocar mais do que o orçamento de memória. repeat, padStart/padEnd, concat e replace/replaceAll lançar RangeError: Invalid string length quando o resultado pode ultrapassar a metade o orçamento em caracteres (16M no padrão 32 MB; uma substituição de regex é limitada como se cada posição correspondente, o que afeta apenas strings de cerca de um milhão de caracteres ou mais). ArrayBuffer e arrays digitados lançam RangeError além do orçamento em bytes e matrizes além orçamento/8 elementos são recusados. O orçamento também é verificado após o retorno do seu gancho, então um a declaração final acima do orçamento falha na invocação em vez de ser bem-sucedida.

O script de referência de xadrez mantém seus documentos pequenos propositalmente - como exemplo de como permanecer dentro do orçamento, seu documento por jogador é

{
  elo: 1200,
  wins: 0, losses: 0, draws: 0,
  lastColorVs: "9b2f8c1a-...",        // for color alternation on rematch
  lastColorOrder: "w",
  recentGames: [ /* up to 30 summaries */ ]
}

O limite de sessões simultâneas é de 20 por jogador por padrão.

A janela legível pela plataforma

Tudo em sessionState é opaco para a plataforma exceto um campo:

sessionState.summary = {
  turnPlayerId: "7c9e6679-...",
  deadline: 1784642591000,
  status: "active",
  moveCount: 41
};

deadline é um carimbo de data/hora Unix inteiro em milissegundos, ou omitido quando não há prazo. Uma sequência de data ISO não é reconhecida. turnPlayerId é o UUID do jogador.

GET /api/v1/games/{slug}/sessions/mine lê summary calcular myTurn e deadline para o chamador. Mantenha-o preciso em cada mudança de estado; mantenha todo o resto onde seu script desejar.

Exemplo resolvido: o script de xadrez

Tudo nesta seção é específico para a implementação de referência do xadrez - a forma do estado, a codificação do tabuleiro, o conjunto de comandos, os motivos do fim do jogo, a constante Elo, a IA e os tempos limite abaixo são escolhas do próprio xadrez, definidas em seu script. Nada disso é comportamento de plataforma; seu jogo define seus próprios equivalentes.

Estado da sessão:

{
  white: "7c9e6679-...",
  black: "9b2f8c1a-...",
  aiId: "00000000-0000-4000-8000-00000000a1a1",   // present in AI games
  game: {
    board: "RNBQKBNRPPPPPPPP................................pppppppprnbqkbnr", // 64 chars
    turn: "w",
    castling: { K: true, Q: true, k: true, q: true },
    epSquare: null,
    halfmoveClock: 0,
    fullmove: 1,
    moves: [ { from: "e2", to: "e4", promo: null, san: "e4", at: 1721473200000 } ],
    positionCounts: { /* fen-key: count, for threefold repetition */ },
    status: "active"
  },
  createdAt: 1721473200000,
  deadline: 1721559600000,
  result: null,
  drawOfferBy: null,
  summary: { turnPlayerId: "...", deadline: "...", status: "active", moveCount: 1 }
}

Codificação da placa: uma sequência de 64 caracteres onde index = rank * 8 + file e a1 é o índice 0. PNBRQK são peças brancas, pnbrqk preto, . é um quadrado vazio.

Comandos manipulados por onPlayerMessage: sync, move, resign, offer-draw, accept-draw, decline-draw (formas de fio em API de jogos).

Game Over reason valores: checkmate, stalemate, threefold-repetition, fifty-move-rule, insufficient-material, resignation, agreement, timeout, timeout-no-moves.

Outras especificações do xadrez:

  • Elo usa K = 32, calculado em finishGame quando um jogo termina e retornado via eloUpdates.
  • Jogo de IA: quando o assento AI deve se mover, aiReply peças "Hal" — um mecanismo ganancioso de captura de material — dentro da mesma invocação. Não há bot externo.
  • Tempos limite: onTick julga o relógio de movimentos de 24 horas - se nenhum movimento tiver sido jogado, o jogo é um timeout-no-moves empate; caso contrário, o jogador que se move perde por timeout.

Implantação

Declare o script no repositório do seu jogo starhermit.txt manifesto:

server=server.js

Publicação de fluxos por meio da integração do GitHub — consulte Jogos GitHub. A plataforma executa o script dentro dos orçamentos documentados. Não combine server= com container.image=; use o tempo de execução do contêiner em vez disso, ao enviar uma imagem.

Melhores práticas

  • Valide cada comando. Tratar ctx.message.data como hostil: verifique tipos, intervalos, ordem de turno e status do jogo antes de tocar no estado.
  • Mantenha as invocações rápidas e com estados pequenos. Você tem aproximadamente 250 ms e um orçamento de bytes por documento do jogador; o script de referência de xadrez, por exemplo, caps recentGames em 30 entradas por esse motivo.
  • Usar ctx.now / ctx.random apenas. Não Date, não Math.random — o anfitrião é dono do relógio e dos dados.
  • Projeto broadcast mensagens como o único contrato do cliente. Os clientes devem ser capazes de renderizar o jogo inteiro a partir do que o script envia; tudo o que não é transmitido não existe para eles.
  • Uma lima, duas superfícies. O mesmo arquivo pode funcionar como regras do lado do cliente por meio de uma exportação separada: a implementação de referência de xadrez, por exemplo, expõe globalThis.chessRules para o navegador (visualização de movimentação, dicas de validação) e globalThis.game para o anfitrião. Uma fonte de verdade, zero autoridade sobre o cliente.
  • Sempre termine os jogos via result então a plataforma publica atualizações do Elo e arquiva o replay quando seu jogo termina replays.
